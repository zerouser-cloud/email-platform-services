## Decisions Made

- **Atomic per-upstream commits (5 SHAs, one per upstream).** Each SHA touches exactly one of the 5 upstream directories — no cross-upstream batching. Rationale: per-upstream rollback granularity, easy bisect, mitigates Pitfall 2 (intermediate state would be TS-broken if constants file deleted before client.ts strips its import). Plan 04 will continue this pattern for the 3 cross-service upstreams.
- **Type-only ClientGrpc import** (`import type { ClientGrpc } from '@nestjs/microservices'`). Once `@Inject(...) grpc: ClientGrpc` becomes plain `grpc: ClientGrpc`, ClientGrpc is used only as a type annotation — no runtime value reference. Type-only import is the correct disposition (Pitfall 7); it also eliminates a lingering value-position dependency that ESLint Plan 05 may guard against.
- **Build verification scheduled for end of plan, not after every per-upstream commit.** Reason: post-Plan 02, the gateway build is intentionally red — the dropped `healthToken`/`grpcToken` opts fields trigger TS2353 errors in any module file that hasn't yet been refactored. Per-upstream `pnpm build` would surface the same N-1 unrelated errors after each commit (the just-committed upstream's TS errors are zero by construction; the noise is from the still-pending upstreams). One final gateway-wide build after upstream 5 is the high-signal verification point.
- **Comment block preserved on named re-exports.** Each module file carries the explanatory comment `// Do NOT export 'grpc' directly — that leaks imports/providers/exports and lets consumers bypass forRoot()`. This documents the encapsulation discipline (Anti-Pattern 4 from infrastructure-client-layering skill) inline at the point where the temptation to write `export const grpc = ...` is highest.
