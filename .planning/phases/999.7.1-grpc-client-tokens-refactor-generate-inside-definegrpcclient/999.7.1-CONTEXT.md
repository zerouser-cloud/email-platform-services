<decisions>
## Implementation Decisions

### Token derivation в foundation
- **D-01:** `defineGrpcClient()` деривирует токены из `service.id`: `grpcToken = Symbol.for(\`${opts.service.id}_CLIENT_GRPC\`)`, `healthToken = Symbol.for(\`${opts.service.id}_GRPC_HEALTH\`)`. Internal generation, не принимается извне.
- **D-02:** `DefineGrpcClientOpts` упрощается: остаются только `service: GrpcServiceDeclaration` и `clientToken: symbol` (последний — из catalog `SERVICE.{name}.diToken`). Поля `healthToken`/`grpcToken` удаляются из opts.
- **D-03:** `GrpcClientBuildResult` расширяется: добавляются `grpcToken: symbol` и `healthToken: symbol` в return — apps-уровень их именует.

### Catalog identity-only
- **D-04:** `SERVICE` catalog в `packages/config` БЕЗ изменений. Транспортные токены (`grpcToken`, `healthToken`) НЕ добавляются в `SERVICE.{name}.*`. Catalog остаётся transport-agnostic. Это базовое архитектурное правило, закреплённое в скилле `infrastructure-client-layering`.

### Удаление per-upstream constants
- **D-05:** Удалить 8 `*-client.constants.ts` файлов:
  - 5 в gateway: `apps/gateway/src/infrastructure/clients/{auth,sender,parser,audience,notifier}/{name}-client.constants.ts`
  - 3 в cross-service: `apps/sender/.../audience/audience-client.constants.ts`, `apps/parser/.../notifier/notifier-client.constants.ts`, `apps/audience/.../parser/parser-client.constants.ts`
- **D-06:** Named const re-export в `*-client.module.ts` (одно место истины + grep-ability + encapsulation):
  ```ts
  const grpc = defineGrpcClient({ service: SERVICE.auth, clientToken: SERVICE.auth.diToken }, (g,c,d) => new AuthClient(g,c,d));
  export const AUTH_GRPC_HEALTH = grpc.healthToken;
  export const AUTH_CLIENT_GRPC = grpc.grpcToken;
  ```
  НЕ экспортировать сам `grpc` объект — это leak'ает internals (`imports`/`providers`/`exports`).

### Очистка client classов от dead decorators
- **D-07:** Убрать `@Injectable()` и `@Inject(*_CLIENT_GRPC)` из 8 client classов (`apps/**/clients/**/*.client.ts` для gRPC). Причины:
  - Под `useFactory` decorators игнорируются NestJS — это dead code
  - Leak wiring concern в domain класс (smешивает уровни ответственности)
  - Без удаления — circular import между `auth.client.ts` и `auth-client.module.ts` (после переноса токенов в module)
- **D-08:** Client class становится чистым domain facade: positional constructor params, без NestJS импортов кроме типов:
  ```ts
  export class AuthClient extends AbstractGrpcClient<AuthProto.AuthServiceClient> {
    constructor(grpc: ClientGrpc, cls: ClsService, defaultDeadlineMs: number) {
      super(grpc, cls, SERVICE.auth.grpc.serviceName, defaultDeadlineMs, AuthClient.name);
    }
    // методы как были
  }
  ```

### Barrel export
- **D-09:** `apps/**/clients/{upstream}/index.ts` упрощается до двух строк:
  ```ts
  export * from './{upstream}.client';
  export * from './{upstream}-client.module';  // тянет Module + named tokens
  ```
  Третья строка (`export * from './{upstream}-client.constants'`) удаляется вместе с файлом.
- **D-10:** `health.controller.ts` gateway — НЕ меняется на уровне imports (`import { AUTH_GRPC_HEALTH } from '../infrastructure/clients/auth'` работает как раньше через barrel + named re-export из module).

### Migration safety
- **D-11:** Task #1 в PLAN.md — explicit audit: grep all `*_GRPC_HEALTH` и `*_CLIENT_GRPC` imports/usages по codebase, собрать inventory ПЕРЕД refactor. Inventory попадает в SUMMARY первого task'а.
- **D-12:** ESLint guard от регрессии:
  - Запрет файлов `apps/**/clients/**/*-client.constants.ts` (для gRPC clients) — `no-restricted-syntax` или custom file pattern rule
  - Запрет `@Injectable()` декоратора в `apps/**/clients/**/*.client.ts` файлах для gRPC client classов
  - Точная форма правил — research-задача в RESEARCH.md, верифицируется на planning-этапе

### Архитектурный эталон

Правило кодифицировано в `.agents/skills/infrastructure-client-layering/SKILL.md` и упомянуто в CLAUDE.md § "Code Style". <specifics>
## Specific Ideas

- **Naming convention для derived symbols:** `${service.id}_CLIENT_GRPC` и `${service.id}_GRPC_HEALTH`. Сохраняет существующие имена (`AUTH_CLIENT_GRPC` где `service.id === 'AUTH'`) — backward compatible через `Symbol.for()` global registry, поэтому даже если бы мы пропустили re-export где-то, runtime бы продолжил работать (но с потерей grep-ability). 
- **Re-export НЕ raw factory result:** экспортируем именованные const'ы (`AUTH_GRPC_HEALTH`), не сам объект `grpc`. Это сохраняет encapsulation — consumer не может случайно вытянуть `imports`/`providers` и обойти `Module.forRoot()`.
- **Фаза задаёт стандарт, не подстраивается под legacy:** PG/Redis/S3/HTTP в текущем виде — legacy. Они подтянутся к gRPC-эталону в следующих фазах через скилл `infrastructure-client-layering`. Не аргументировать gRPC-решения через "так же как в PG".
- **HTTP clients (telegram/cloudfn/appstorespy) НЕ трогаем** в этой фазе. Они следуют per-app constants паттерну (нет catalog identity для внешних API). Refactor — отдельная фаза с применением скилла.

</specifics>
