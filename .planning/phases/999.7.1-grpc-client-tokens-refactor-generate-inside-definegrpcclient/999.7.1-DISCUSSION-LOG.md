## Area 1: Barrel export shape

### Round 1 — Token export mechanism

| Option | Description | Selected |
|--------|-------------|----------|
| Named const re-export в module file | `export const AUTH_GRPC_HEALTH = grpc.healthToken;` в `*-client.module.ts`. Zero diff в health.controller. Сохраняет UPPER_SNAKE convention codebase. | ✓ |
| Static на module class | `AuthClientModule.healthToken` getter. Tighter coupling token ↔ module. Risk с TS decorator evaluation order. | |
| Catalog-derived inline в controller | Controller сам деривирует через `Symbol.for('${SERVICE.auth.id}_GRPC_HEALTH')`. Дублирует derivation pattern — нарушает single source of truth. | |
| Прямой re-export `grpc` объекта | Обсуждалось пользователем как альтернатива. Отклонено: leak'ает internals (imports/providers/exports), нарушает naming convention, теряется grep-ability. | |

**User's choice:** Named const re-export.
**Notes:** Пользователь предложил вариант с прямым `grpc.healthToken` доступом. После анализа трёх причин (naming convention, encapsulation, grep-ability) согласился на named const re-export.

### Round 2 — @Inject/@Injectable decorators в client classах

Обнаружено в процессе: чтобы удалить `*-client.constants.ts` физически, нужно решить проблему circular import между `auth.client.ts` (импортит `AUTH_CLIENT_GRPC`) и `auth-client.module.ts` (импортит `AuthClient`).

| Option | Description | Selected |
|--------|-------------|----------|
| Убрать @Injectable/@Inject в Phase 999.7.1 | Decorators dead code под useFactory. Resolves circular dep. Cleanest separation: client class = domain facade, module = wiring. | ✓ |
| Отдельная фаза 999.7.2 | Оставить мини-файл `*-client.tokens.ts` (rename), реальное удаление в следующей фазе. Фикция удаления. | |
| Оставить decorators + forwardRef | Плохо для tree-shaking, dead code остаётся. | |

**User's choice:** Убрать @Injectable/@Inject как часть Phase 999.7.1.
**Notes:** Пользователь сначала засомневался — подумал, что подход меняется. После разъяснения что (а) extends AbstractGrpcClient — это унаследовано от Phase 23 и не меняется, (б) per-service модули в apps/ уже сделаны в Phase 999.7 и не пересматриваются, (в) decorators — единственное что мешает чистому удалению constants — согласовал.

### Round 3 — Barrel scope

`apps/**/clients/{upstream}/index.ts` упрощается:
```
export * from './{upstream}.client';        // AuthClient class
export * from './{upstream}-client.module'; // AuthClientModule + AUTH_GRPC_HEALTH + AUTH_CLIENT_GRPC
```
Третья строка (re-export из constants) удаляется вместе с файлом.

## Area 2: HTTP/gRPC asymmetry policy

**User reframe:** "Я предпочитаю согласовать подходы, что бы это было правильно архитектурно а не размазано. У нас есть уровень контрактов, там есть каталог сервисов, далее у нас есть фондейшен, там у нас заготовки, дальше у нас есть уровень сервисов где конкретные реализации."

Затем: "не должен сильно обращать внимание на s3, http, rabbit, reddis, drizle+db — мы еще дойдем до этих сервисов в своем рефакторе, мы как раз должны сделать эталонный grpc подход."

**Resulting principle (codified в скилле + CLAUDE.md):**
- catalog (`packages/config`) — IDENTITY ONLY (transport-agnostic)
- foundation (`packages/foundation`) — MECHANISMS ONLY (service-agnostic)
- apps — ASSEMBLY + NAMING

**Decision:** не подстраиваем gRPC под существующие PG/Redis/S3 (они legacy). gRPC задаёт стандарт. Принцип закреплён в `.agents/skills/infrastructure-client-layering/SKILL.md` и one-liner в `CLAUDE.md` § "Code Style".

**User's choice:** Эталонный gRPC паттерн + skill для будущих рефакторов.
