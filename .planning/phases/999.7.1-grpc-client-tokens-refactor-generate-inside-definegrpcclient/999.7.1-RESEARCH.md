# Phase 999.7.1: gRPC client tokens refactor — generate inside defineGrpcClient() - Research

**Researched:** 2026-04-17
**Domain:** NestJS DI factory wiring, Symbol.for() registry, ESLint AST guards, monorepo refactor safety
**Confidence:** HIGH

## Summary

Phase 999.7.1 углубляет архитектурный паттерн родительской фазы 999.7. Два связанных изменения: (1) перенос derivation gRPC-токенов (`grpcToken`, `healthToken`) ИЗ opts В тело `defineGrpcClient()`; (2) удаление dead `@Injectable`/`@Inject` декораторов с 8 client classов. Результат: 8 файлов `*-client.constants.ts` физически удаляются, токены деривируются из `service.id` через `Symbol.for()`, named const re-export в `*-client.module.ts` сохраняет grep-ability и encapsulation.

Ключевые технические находки:
1. **NestJS подтверждено:** под `useFactory` декораторы `@Inject` на конструкторе игнорируются — параметры приходят из массива `inject:` по позиции [VERIFIED: Context7 /nestjs/docs.nestjs.com]. Удаление декораторов = устранение dead code, не изменение поведения.
2. **Symbol.for() глобальный реестр** возвращает идентичный Symbol для одного key между файлами/модулями/realms [CITED: MDN]. Деривация в foundation + named re-export в apps дают тот же Symbol — runtime сохраняет идентичность.
3. **service.id в lowercase** (`'auth'`), а имя символа в UPPER (`'AUTH_GRPC_HEALTH'`) — derivation должна делать `.toUpperCase()`. Это критическая деталь корректности.
4. **ESLint guard через AST selector** (`ClassDeclaration[decorators.length>0]`) с scoped `files` patterns — единственный практический подход для ESLint 8.x без новых плагинов.
5. **Filename guard:** HTTP clients тоже используют `*-client.constants.ts` (`appstorespy-client.constants.ts`, `cloudfn-client.constants.ts`) — blanket-block по pattern сломает их. Guard должен быть scoped по списку gRPC upstream путей.

**Primary recommendation:** Изменить `DefineGrpcClientOpts` (убрать `healthToken`/`grpcToken`), деривировать оба внутри `defineGrpcClient()` через `Symbol.for(\`${opts.service.id.toUpperCase()}_<KIND>\`)`, расширить `GrpcClientBuildResult` двумя полями. Удалить `@Injectable()` и `@Inject(*_CLIENT_GRPC)` с 8 client classов в одной волне с удалением 8 constants файлов (атомарно — иначе TS-build разрывается). ESLint guard через `no-restricted-syntax` + `check-file/filename-blocklist` (v2.8.0 для ESLint 8) с явным списком gRPC upstream путей.

### Pattern 1: `defineGrpcClient()` Factory With Internal Token Derivation

**What:** Foundation factory деривирует gRPC-токены из catalog identity, не принимая их извне.

**When to use:** Каждый per-service gRPC client module — единственный путь создания gRPC client wiring в проекте.

**Why this design:** Catalog (`SERVICE.auth`) — единый источник identity. Деривация в foundation — единый источник transport plumbing. Apps — единый источник naming/assembly. Эта триада устраняет дублирование и закрепляет границы слоёв.

**Implementation:**
```typescript
// packages/foundation/src/external/grpc/clients/define-grpc-client.ts
// Source: existing implementation, modified per D-01..D-03
import type { DynamicModule, Provider, Type } from '@nestjs/common';
import { ClientsModule, Transport } from '@nestjs/microservices';
import type { ClientGrpc } from '@nestjs/microservices';
import { ConfigService } from '@nestjs/config';
import { TerminusModule, HealthIndicatorService } from '@nestjs/terminus';
import { ClsService } from 'nestjs-cls';
import type { GrpcServiceDeclaration } from '@email-platform/config';
import { resolveProtoPath } from '../proto-resolver';
import { createDeadlineInterceptor } from '../../resilience/grpc-deadline.interceptor';
import { GRPC_CLIENT_HEALTH } from './clients.constants';
import { GrpcClientHealthIndicator } from './grpc-client-health.indicator';

const TOKEN_SUFFIX = {
  CLIENT_GRPC: '_CLIENT_GRPC',
  GRPC_HEALTH: '_GRPC_HEALTH',
} as const;

export interface DefineGrpcClientOpts {
  readonly service: GrpcServiceDeclaration;
  readonly clientToken: symbol;
  // healthToken / grpcToken УБРАНЫ — деривируются внутри
}

export interface GrpcClientBuildResult {
  readonly imports: Array<Type<unknown> | DynamicModule>;
  readonly providers: Provider[];
  readonly exports: symbol[];
  readonly grpcToken: symbol;     // NEW per D-03
  readonly healthToken: symbol;   // NEW per D-03
}

export function defineGrpcClient<T extends object>(
  opts: DefineGrpcClientOpts,
  build: (grpc: ClientGrpc, cls: ClsService, deadlineMs: number) => T,
): GrpcClientBuildResult {
  const upperId = opts.service.id.toUpperCase();
  const grpcToken = Symbol.for(`${upperId}${TOKEN_SUFFIX.CLIENT_GRPC}`);
  const healthToken = Symbol.for(`${upperId}${TOKEN_SUFFIX.GRPC_HEALTH}`);

  const facadeProvider: Provider = {
    provide: opts.clientToken,
    inject: [grpcToken, ClsService, ConfigService],
    useFactory: (grpc: ClientGrpc, cls: ClsService, config: ConfigService) =>
      build(grpc, cls, config.get<number>('GRPC_DEADLINE_MS')!),
  };

  const healthProvider: Provider = {
    provide: healthToken,
    inject: [HealthIndicatorService, grpcToken],
    useFactory: (his: HealthIndicatorService, grpc: ClientGrpc) =>
      new GrpcClientHealthIndicator(his, grpc),
  };

  return {
    imports: [
      TerminusModule,
      ClientsModule.registerAsync([
        {
          name: grpcToken,
          inject: [ConfigService],
          useFactory: (config: ConfigService) => ({
            transport: Transport.GRPC,
            options: {
              url: config.get<string>(opts.service.envKeys.GRPC_URL!)!,
              package: [opts.service.grpc.package, GRPC_CLIENT_HEALTH.PACKAGE],
              protoPath: [
                resolveProtoPath(opts.service.grpc.package, config.get<string>('PROTO_DIR')!),
                require.resolve('grpc-health-check/proto/health/v1/health.proto'),
              ],
              channelOptions: {
                interceptors: [createDeadlineInterceptor(config.get<number>('GRPC_DEADLINE_MS')!)],
              },
            },
          }),
        },
      ]),
    ],
    providers: [facadeProvider, healthProvider],
    exports: [opts.clientToken, healthToken],
    grpcToken,
    healthToken,
  };
}
```

**Critical detail (catches a bug):** `service.id` is **lowercase** (`'auth'`, `'sender'`, ...) — see `packages/config/src/catalog/services.ts:5,11,16,22,33`. Existing token names are `AUTH_GRPC_HEALTH` (uppercase). Derivation MUST do `.toUpperCase()`. The same `defineService` factory in `packages/config/src/catalog/define-service.ts:26,42` already does `input.id.toUpperCase()` for `diToken` and envKeys — derivation in `defineGrpcClient` follows the same convention. [VERIFIED: codebase grep — all existing `Symbol.for('AUTH_GRPC_HEALTH')` strings are UPPER]

### Pattern 2: Decorator-Free Client Class (Domain Facade)

**What:** Client class becomes pure domain facade with positional constructor params; all NestJS DI wiring concerns live in `*-client.module.ts`.

**When to use:** All 8 gRPC client classes; pattern extends to future infra-client classes wired via `useFactory`.

**Why:** Under `useFactory`, NestJS resolves dependencies via the `inject:` array — constructor `@Inject` decorators are dead code. Removing them:
1. **Eliminates dead code** [VERIFIED: NestJS docs § Custom Providers > Factory Providers — "the inject property specifies an array of providers that Nest will resolve and pass as arguments to the factory function in the same order"]
2. **Resolves circular import potential:** if tokens move into `auth-client.module.ts` (Round 2 of Discussion Log), the client class would import the module's exported tokens, while the module imports the client class — circular. Removing decorators removes the token import from client.ts entirely.
3. **Cleans architectural separation:** client class = domain facade (proto types + business methods); module = wiring concern (DI + transport).

**Implementation:**

### Pattern 3: Module File With Named Token Re-Exports

**What:** `*-client.module.ts` calls `defineGrpcClient`, captures tokens, re-exports them as named consts, wraps providers/imports in `@Module` class.

**When to use:** All 8 gRPC client modules. Pattern is tier "ASSEMBLY+NAMING" per skill.

**Why named const re-exports (not raw `grpc` object):**
- **Encapsulation:** consumer не может вытянуть `imports`/`providers` и обойти `Module.forRoot()`

### Anti-Patterns to Avoid

- **Adding transport tokens to catalog:** `SERVICE.auth.grpcToken` — leak слоя identity → transport. Catalog stays transport-agnostic per `infrastructure-client-layering` skill.
- **Exporting raw `grpc` object:** `export const grpc = defineGrpcClient(...)` — leak'ает internals (`imports`/`providers`/`exports`), нарушает encapsulation, ломает naming convention.
- **Keeping `@Injectable`/`@Inject` "for safety":** they are dead code under `useFactory` per NestJS docs. Leaving them mixes wiring concern into domain class и блокирует решение circular import.
- **Hardcoding token strings instead of derivation:** `Symbol.for('AUTH_CLIENT_GRPC')` literally in module file — violates single source of truth (catalog id).
- **Forgetting `.toUpperCase()`:** `Symbol.for(\`${service.id}_CLIENT_GRPC\`)` без `.toUpperCase()` создаст `auth_CLIENT_GRPC` ≠ `AUTH_CLIENT_GRPC` → runtime DI mismatch silently broken.

## Common Pitfalls

### Pitfall 1: Lowercase `service.id` vs Uppercase Token Name

**What goes wrong:** Derivation `Symbol.for(\`${opts.service.id}_CLIENT_GRPC\`)` без `.toUpperCase()` создаёт `Symbol.for('auth_CLIENT_GRPC')`. Existing consumers ожидают `Symbol.for('AUTH_CLIENT_GRPC')`. DI lookup mismatch — runtime "provider not found".

**Why it happens:** `service.id` в catalog stored as lowercase для readability (`'auth'`, не `'AUTH'`). Existing tokens — UPPER. Несоответствие легко missable если не читать catalog внимательно.

**How to avoid:** Always `opts.service.id.toUpperCase()`. Reference: `define-service.ts:26` (`const upperId = input.id.toUpperCase()`) — same pattern, follow it.

**Warning signs:** Build green (TypeScript не валидирует Symbol identity), runtime: `Nest can't resolve dependencies of XClient (?, ClsService, ...)`.

### Pitfall 2: Atomic Removal Required (Cannot Stage Constants Removal)

**What goes wrong:** Удалить `auth-client.constants.ts` пока `auth.client.ts` ещё импортит `AUTH_CLIENT_GRPC` → TS-build broken.

**Why it happens:** Tasks must be sequenced — единственный безопасный порядок: (1) update `defineGrpcClient` signature → (2) update `*-client.module.ts` (named re-export) → (3) remove `@Inject` from `*.client.ts` → (4) delete `*-client.constants.ts` → (5) update `index.ts` barrel. Шаги 2 и 3 для одного upstream **в одном commit** — иначе одна из сторон broken.

**How to avoid:** Plan task per-upstream as one atomic unit (4 file modifications + 1 file deletion). Per-upstream commit guarantees green build at each step.

**Warning signs:** TS error `Module './auth-client.constants' has no exported member 'AUTH_CLIENT_GRPC'` — означает разорвана атомарность.

### Pitfall 3: ESLint Guard Catching HTTP Clients

**What goes wrong:** Запретить `**/*-client.constants.ts` blanket — сломает HTTP clients (`appstorespy-client.constants.ts`, `cloudfn-client.constants.ts`), которые в out-of-scope для этой фазы.

**Why it happens:** HTTP и gRPC используют один naming pattern для constants files (verified by `ls` of `apps/parser/src/infrastructure/clients/appstorespy/` и `apps/sender/src/infrastructure/clients/cloud-functions/`).

**How to avoid:** Scope guard явно к gRPC upstream paths. После фазы будет 8 known gRPC upstream directories — список малый, стабильный, обновляется одновременно с catalog.

**Warning signs:** Lint error на HTTP `*-client.constants.ts` файлах при первом запуске после добавления rule.

### Pitfall 4: Decorator AST Selector Must Match `expression.callee.name`

**What goes wrong:** Selector `ClassDeclaration[decorators]` поймает ВСЕ декораторы. Selector `ClassDeclaration > Decorator` — ditto. Нужно matched specifically на `@Injectable()` (call expression with callee.name `'Injectable'`).

**Why it happens:** AST decorator node имеет два варианта: `Decorator > Identifier` (для `@Foo` без скобок) и `Decorator > CallExpression > Identifier` (для `@Foo()` со скобками). NestJS `@Injectable()` — второй вариант.

**How to avoid:** Selector — `'ClassDeclaration > Decorator > CallExpression[callee.name="Injectable"]'`. AST для `@Inject(TOKEN)` (на параметрах) — отдельный selector если нужно ловить и его. См. Pattern 5 ниже для exact selectors.

**Warning signs:** Lint passes для `@Injectable()` (false negative) или fails на любом декораторе (false positive).

### Pitfall 5: NestJS Auto-Resolution Edge Case (`@Inject` on Constructor Params)

**What goes wrong:** Если оставить `@Inject(AUTH_CLIENT_GRPC) grpc: ClientGrpc` параметр, под `useFactory` он действительно ignored. НО если в будущем этот класс будет wired через `useClass`, decorator вдруг станет live. Это латентная mine.

**Why it happens:** `useClass` activates constructor decorators; `useFactory` doesn't. Обе формы wiring выглядят одинаково в client class — нельзя сказать просто прочитав class какой режим используется.

**How to avoid:** Удалить decorators в этой фазе (D-07). ESLint guard блокирует regression. Future wiring decisions explicit на module-level (`useFactory` only — это standard для всех infra clients per skill).

**Warning signs:** Класс использует и `@Inject` и participates в `useFactory` — ambiguity smell.

### Pitfall 6: Symbol.for() Returns Same Symbol — But Object Identity Matters for DI

**What goes wrong:** Naive assumption: "I'll create my own `Symbol('AUTH_CLIENT_GRPC')` (без `.for`) — works the same." NO. `Symbol('X') !== Symbol('X')` — каждый call создаёт unique symbol. NestJS DI lookup использует object identity (`===`).

**Why it happens:** `Symbol(key)` and `Symbol.for(key)` визуально одинаковы. Difference критическая.

**How to avoid:** **Always `Symbol.for(key)`** for DI tokens that need to be derived in multiple places. Single-place tokens (entirely in foundation, never derived elsewhere) могут использовать `Symbol(key)` — но проще consistent `Symbol.for()`.

**Warning signs:** "Provider not found" с правильно выглядящим именем токена в error message.

[VERIFIED: MDN — `Symbol.for("foo") === Symbol.for("foo")` is `true`; `Symbol("foo") === Symbol("foo")` is `false`]

### Pitfall 7: `import { ClientGrpc }` vs `import type { ClientGrpc }`

**What goes wrong:** В новом decorator-free client class только `ClientGrpc` нужен как type (positional constructor param). Sub-optimally `import { ClientGrpc }` — value import. Может triggernuть `consistent-type-imports` lint rule.

**Why it happens:** `@nestjs/microservices` exports `ClientGrpc` как interface — value import не нужен, только type.

**How to avoid:** `import type { ClientGrpc } from '@nestjs/microservices';` (type-only import). Bundle slightly smaller, lint clean.

**Warning signs:** ESLint warning `prefer type-only import for 'ClientGrpc'`.
