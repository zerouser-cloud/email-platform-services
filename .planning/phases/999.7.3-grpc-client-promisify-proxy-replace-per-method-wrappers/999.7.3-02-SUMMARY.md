**2. [Rule 1 — Bug, follow-up to deviation #1] Drop CallOpts arg from sanity probe `auth.login()` call (separate commit `d84c2d8`)**

- **Found during:** Runtime smoke (gateway tsc emitted `TS2345: Argument of type 'CallOpts' is not assignable to parameter of type 'Metadata'` at `grpc-client-sanity.ts:37`)
- **Issue:** My Rule 3 auto-fix changed the `auth` parameter type to `Promisified<AuthProto.AuthServiceClient>`. The `Promisified<T>` mapped type preserves the original ts-proto signature `login(req, meta?: Metadata) => Promise<TokenPair>` — second arg is `Metadata`, NOT `CallOpts`. The runtime Proxy DOES accept `CallOpts` (per `promisify-grpc-client.ts:63`), but the public TYPE doesn't reflect that. Passing the existing `opts: CallOpts` tripped TS2345.
- **Fix:** Drop the second argument from the `auth.login(...)` call. Added a 4-line comment explaining the type/runtime asymmetry. Kept `const opts: CallOpts = ...` declaration with a `void opts` to preserve the lint-disable intent of the file.
- **Files modified:** `apps/gateway/src/test/grpc-client-sanity.ts`
- **Verification:** `pnpm --filter @email-platform/gateway exec tsc --noEmit` no longer emits TS2345 at this line.
- **Committed in:** `d84c2d8` (separate fix commit, since the bug was discovered AFTER Task 2 was already committed and the smoke surfaced it).
- **Why this is the right call:** Rule 1 (bug) — TS2345 is a real type error blocking compilation; without the fix, the gateway typecheck error count would NET INCREASE rather than decrease, contradicting the plan's success criterion. Could not be bundled into Task 2's commit because it was discovered later during smoke verification.

**3. [Observation, no fix] Plans 03/04 will need to widen Promisified second-arg type or accept the same workaround**

- **Found during:** Deviation #2 root-cause analysis
- **Observation:** `Promisified<T>` infers from `(req, meta?: Metadata) => Observable<R>` and emits `(req, meta?: Metadata) => Promise<R>`. But the runtime proxy actually accepts `CallOpts` (with `deadlineMs`). This is a foundation-level type/runtime asymmetry. Consumers using `Promisified<T>` with the second arg will either (a) need to construct a `Metadata` object and put deadline header in it manually, OR (b) call without the second arg (default deadline applies), OR (c) wait for foundation refinement to widen the typed signature.
- **Why no fix here:** Out of scope for Plan 02 (file boundary is `apps/gateway/src/infrastructure/clients/auth/`). Logging here for visibility — Plans 03/04 will hit the same wall the moment any consumer tries to pass a per-call deadline. Recommend adding a follow-up note to Plan 05 (final cleanup) or a backlog item for foundation type refinement.

### Runtime Smoke Gate — DID NOT PASS

**Per `<runtime_smoke_handling>` directive: smoke executed and result reported below. NOT pausing for user input. Orchestrator handles diagnosis surfacing.**

**What happened:**

1. `pnpm stop:native` ran cleanly (no stale infra).
2. `pnpm start:native` started infra (PostgreSQL, Redis, Garage, RabbitMQ all up via docker compose) AND launched `pnpm dev` (turbo run dev across all 6 services).
3. **Auth and notifier services started successfully** (both report `Nest application successfully started` at 12:05:43). These two services have NO upstream gRPC client wrappers — auth IS the upstream, notifier consumes only RabbitMQ events. This proves the Plan 01 foundation changes don't break independent services.
4. **Gateway, sender, parser, audience services FAILED to start.** All four are stuck in `nest start --watch` reporting tsc errors:
   - Gateway: `Found 47 errors. Watching for file changes.` (was 48 with my un-fixed TS2345 from deviation #2; dropped to 47 after `d84c2d8`)
   - Sender: `Found 13 errors`
   - Parser: `Found 7 errors`
   - Audience: `Found 12 errors`
5. **`curl http://localhost:3000/health/ready` failed with `curl: (7) Failed to connect to localhost port 3000`.** Gateway never bound to port 3000 because the tsc watch loop never emitted compilable JS.

**Root cause: PLANNING OVERSIGHT**

The Plan 01 SUMMARY's "Next Phase Readiness" section stated:
> "Do not run pnpm dev or pnpm start:native between Plan 01 and Plan 02 — runtime build will fail until the AuthClient pair is migrated. Next runtime smoke gate is in Plan 02 after the AuthClient pilot is committed."

This was incorrect. Migrating ONLY the AuthClient pair clears 2 TS errors out of the ~16 interim total (Plan 01 documented 8 × TS2554 + 8 × TS2305 = 16 root errors plus 74 cascading TS7006). The remaining ~14 errors continue to block gateway compilation. Specifically, gateway has 4 broken upstream client modules (sender, parser, audience, notifier) whose `*.client.ts` files import a non-existent `GrpcCaller` and whose `*-client.module.ts` files call `defineGrpcClient(opts, build)` with the wrong arity.

**`nest start --watch`** uses tsc-in-watch-mode. On any compilation error, it does NOT emit `dist/main.js` for the failing app, so the app never starts. This is different from `ts-node`/`ts-node-dev` which can run code with type errors.

**What would unblock the smoke:**

The smoke can only validate the AuthClient Promisified Proxy at runtime AFTER all 4 remaining gateway-side upstream client modules (sender, parser, audience, notifier) are also migrated. That work is scoped to **Plan 03 (gateway sweep)**.

**Recommendations for the orchestrator/user:**

- **Option A (preferred):** Proceed to Plan 03 immediately. Plan 03 closes the remaining 4 gateway upstream migrations using AuthClientModule as the canonical template. After Plan 03, re-run the smoke gate (`pnpm start:native` + `curl /health/ready`). At that point the gateway should boot and the auth indicator should show `up` if the Promisified Proxy is wired correctly. Move the BLOCKING smoke gate from Plan 02 to Plan 03.
- **Option B:** Treat Plan 02's auth migration as code-correct and merge the foundation+pilot work as a single "atomic refactor batch" (Plans 01+02), then continue Plan 03/04/05 normally. Smoke gate becomes the final acceptance for Plan 03 (or whichever plan first restores gateway boot).
- **Option C (NOT recommended):** Roll back Plan 02 commits. This destroys correct work and leaves the foundation in an even more inconsistent state (Plan 01 was atomic; rolling back Plan 02 leaves the auth wedge half-broken).

**My recommendation:** Option A. The Plan 02 code is correct; the planning sequence was wrong. Plan 02 should NOT have been gated on a runtime smoke that requires the rest of the gateway sweep to complete first.
