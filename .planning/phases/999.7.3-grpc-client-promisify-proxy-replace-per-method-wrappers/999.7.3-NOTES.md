## Why This Phase Exists

After Phase 999.7.2 shipped (composition + `GrpcCaller`), user questioned the purpose of the 8 `apps/**/*.client.ts` wrapper classes:

> «У нас есть контракты, где лежат протофайлы, эти контракты берёт сервис и реализовывает свои ендпоинты по этим контрактам, а другой сервис берёт заготовку для создания клиента из foundation, и на основе прото-контрактов реализовывает клиент audience, а у нас получается что класс AudienceClient это какая-то обвертка, зачем она нам нужна? Грубо говоря, мы должны получить просто `this.audience.getUser(req)`.»

The intuition was correct. **Phase 999.7.2 built a composition architecture around the wrong abstraction**: per-method wrappers that each look like `this.grpc.call('X', opts, m => raw.X(req, m))` — 58 method wrappers × ~1 line each across 8 files = ~60 lines of mechanical boilerplate.

Deep research (WebSearch + ts-proto/node_modules source + NestJS issue archaeology) revealed the idiomatic path:

1. **`nestJs=true` hard-codes `Observable<T>` on the client interface** — `ts-proto/build/src/generate-nestjs.js:96-97`: literal comment `// Return observable since nestjs client always returns an Observable`. No flag combination changes this.
2. **`@nestjs/microservices`'s `ClientGrpc.getService()` wraps every call in `new Observable(...)`** — `client-grpc.js:197`. No Promise mode exists.
3. **The "idiomatic consumer" in official NestJS samples does NOT use wrapper classes.** It returns the Observable from the HTTP controller (`sample/04-grpc/src/hero/hero.controller.ts`); NestJS HTTP auto-subscribes.
4. **If Promise ergonomics are wanted (they are — our domain uses `await`, not `.subscribe()`)**, Kamil Myśliwiec (NestJS creator) officially endorsed a **JavaScript Proxy `promisify`** in [nestjs/nest#3710](https://github.com/nestjs/nest/issues/3710): *"your solution (with `promisify`) is the only supported way so far."* Issue locked, recommendation unchanged through NestJS 11/12.
5. **The user's "coolcinema" counter-example (typed client via `@Inject`, `await this.audience.getUser(req)`) is `nice-grpc`, not `nestJs=true`.** `CallOptions` (not `Metadata`) is the nice-grpc signature. nice-grpc **replaces** `@nestjs/microservices` on both client AND server — not applicable without full stack migration.

**Therefore:** the next phase replaces our hand-written per-method wrappers with a single generic Proxy in `packages/foundation`. Same consumer API (`await this.auth.login(req)`), ~60 lines of boilerplate vanish, stack unchanged.

## Critical Evaluation: Is `GrpcCaller` Still Needed?

**Short answer: No, as a standalone class.** Its three responsibilities fold into the Proxy's trap handler.

| Current `GrpcCaller` responsibility | Still needed? | Lives where in new design |
|---|---|---|
| Build `Metadata` with `grpc-timeout` deadline header | Yes | Inside Proxy trap handler |
| Convert `Observable<T> → Promise<T>` via `lastValueFrom` | Yes | Inside Proxy trap handler |
| Structured logging (`grpc.client.call` with service/method/duration_ms/status/correlationId) | Yes | Inside Proxy trap handler |
| Class `GrpcCaller` as DI'able helper | **No** | Deleted |
| Callback-factory sig `call(method, opts, rpcFactory)` (D-05 of 999.7.2) | **No** | Proxy trap IS the intercept point — no callback needed |
| Separate construction + injection into each client class | **No** | `defineGrpcClient.useFactory` calls `promisifyGrpcClient(...)` once, returns ready Promisified proxy |

**Why folding in is cleaner than "Proxy + GrpcCaller" two-layer stack:**
- One abstraction, one file (`promisify-grpc-client.ts` in foundation)
- Proxy trap handler already has the lifecycle control D-05 of 999.7.2 was optimizing for — there is no need for a callback-factory because the Proxy IS the intercept site
- No intermediate GrpcCaller instance to construct/pass around
- Future concerns (tracing/retry/circuit-breaker) are added to the same Proxy trap — same extension point, no new class

**Why D-05's callback-factory sig becomes obsolete:** D-05 of 999.7.2 chose `call(method, opts, rpcFactory)` specifically so `GrpcCaller.call()` could own the lifecycle (metadata → span → rpc → catch → log). With Proxy, the trap handler owns the lifecycle directly — `rpcFactory` is redundant indirection.

## Target Consumer API

```ts
// In gateway or any service consumer:
@Controller('users')
export class UsersController {
  constructor(
    @Inject(SERVICE.audience.diToken)
    private readonly audience: Promisified<AudienceProto.AudienceServiceClient>,
  ) {}

  @Get(':id')
  async getUser(@Param('id') id: string): Promise<User> {
    return this.audience.getUser({ id });   // Promise<User>, fully typed
  }
}
```

- `audience` is the raw ts-proto `AudienceServiceClient` interface, TYPE-MAPPED from `Observable<T>` returns to `Promise<T>` returns.
- No `AudienceClient` wrapper class in apps/. Zero per-method boilerplate.
- Cross-cutting (deadline, logging, correlationId) applied automatically inside the Proxy trap.

## Proposed Implementation Sketch

### New file: `packages/foundation/src/external/grpc/clients/promisify-grpc-client.ts`

```ts
import { Metadata } from '@grpc/grpc-js';
import { PinoLogger } from 'nestjs-pino';
import type { Logger as PinoNativeLogger } from 'pino';
import { ClsService } from 'nestjs-cls';
import { type Observable, lastValueFrom } from 'rxjs';
import { GRPC_CLIENT_LOG, GRPC_CLIENT_DEADLINE } from './clients.constants';
import type { CallOpts, GrpcClientLogFields } from './grpc-client-logging.types';

/**
 * Maps every `(...args) => Observable<R>` method on T to `(...args) => Promise<R>`.
 * Non-function properties and streaming methods (returning Observable intentionally) pass through.
 */
export type Promisified<T> = {
  [K in keyof T]: T[K] extends (...args: infer A) => Observable<infer R>
    ? (...args: A) => Promise<R>
    : T[K];
};

export interface PromisifyOpts {
  readonly serviceName: string;       // ts-proto serviceName for log field + Metadata
  readonly defaultDeadlineMs: number;
  readonly cls: ClsService;           // for correlationId
  readonly logContext: string;        // e.g. "AuthClient"
}

/**
 * Wrap a raw `ClientGrpc.getService<T>()` return in a typed Promise-returning Proxy
 * that handles metadata + deadline + structured logging + correlationId per-call.
 *
 * Folds in the three responsibilities that Phase 999.7.2's `GrpcCaller` class held
 * (metadata, Observable→Promise, logging) into a single intercept point — no
 * standalone helper class, no per-method wrapper files in apps/.
 *
 * Streaming RPCs: today there are none. If added later, filter streaming method
 * names out of the Proxy so they keep returning raw Observable.
 */
export function promisifyGrpcClient<T extends object>(raw: T, opts: PromisifyOpts): Promisified<T> {
  let logger: PinoNativeLogger | undefined;
  const getLogger = () => (logger ??= PinoLogger.root.child({ context: opts.logContext }));

  return new Proxy(raw, {
    get(target, prop: string | symbol) {
      const orig = Reflect.get(target, prop);
      if (typeof orig !== 'function' || typeof prop !== 'string') return orig;

      return async (request: unknown, callOpts?: CallOpts) => {
        const start = Date.now();
        const deadlineMs = callOpts?.deadlineMs ?? opts.defaultDeadlineMs;
        const meta = new Metadata();
        meta.set(
          GRPC_CLIENT_DEADLINE.METADATA_HEADER,
          `${deadlineMs}${GRPC_CLIENT_DEADLINE.METADATA_UNIT_MILLISECONDS}`,
        );

        const observable = orig.call(target, request, meta) as Observable<unknown>;
        try {
          const response = await lastValueFrom(observable);
          emitLog(getLogger(), {
            service: opts.serviceName, method: prop, duration_ms: Date.now() - start,
            status: GRPC_CLIENT_LOG.STATUS_OK, correlationId: opts.cls.getId(),
          });
          return response;
        } catch (error) {
          emitLog(getLogger(), {
            service: opts.serviceName, method: prop, duration_ms: Date.now() - start,
            status: GRPC_CLIENT_LOG.STATUS_ERROR, correlationId: opts.cls.getId(),
          });
          throw error;
        }
      };
    },
  }) as Promisified<T>;
}

function emitLog(logger: PinoNativeLogger, fields: GrpcClientLogFields): void {
  const level = fields.status === GRPC_CLIENT_LOG.STATUS_OK ? 'info' : 'error';
  logger[level](fields, GRPC_CLIENT_LOG.EVENT);
}
```

### Modified: `packages/foundation/src/external/grpc/clients/define-grpc-client.ts`

`useFactory` returns a ready Promisified proxy instead of calling an external build callback:

```ts
export function defineGrpcClient<TRaw extends object>(opts: {
  readonly service: GrpcServiceDeclaration;
  readonly clientToken: symbol;
  readonly rawType: (new (...args: never[]) => TRaw) | symbol;  // or just use serviceName for getService<T> generic
}): GrpcClientBuildResult {
  // ... same token derivation as 999.7.1 ...
  const facadeProvider: Provider = {
    provide: opts.clientToken,
    inject: [grpcToken, ClsService, ConfigService],
    useFactory: (grpc: ClientGrpc, cls: ClsService, config: ConfigService): Promisified<TRaw> => {
      const raw = grpc.getService<TRaw>(opts.service.grpc.serviceName);
      return promisifyGrpcClient(raw, {
        serviceName: opts.service.grpc.serviceName,
        defaultDeadlineMs: config.get<number>('GRPC_DEADLINE_MS')!,
        cls,
        logContext: `${opts.service.id.toUpperCase()}Client`,
      });
    },
  };
  // ... imports + healthProvider unchanged ...
}
```

Architecturally, Option A (Promise-adapted) is NOT a commitment to unary-only — it's streaming-ready by design. Concrete implementation of streaming support deferred until streaming RPCs actually appear in the roadmap, but the door is wide open. See open question #8 below for the implementation sketch.
- **Distributed tracing, circuit breaker, retry policy.** Same point of extension (Proxy trap handler) that 999.7.2 D-05 prepared for. Implementation = separate phase.
- **HTTP/RMQ/Redis/S3/DB refactors.** Different infra mechanics. `infrastructure-client-layering` skill guides them separately.

## Open Questions for `/gsd:discuss-phase 999.7.3`

### 0. **[CRITICAL — architectural fork]** Promise-adapted vs Observable pass-through?

Surfaced by user 2026-04-17 after NOTES.md was first written. User asked: «а зачем мы пытаемся обсервер превратить в промис? В этом есть смысл? Почему нам не подходит работа с обсервом?»

This is the most important decision of the phase and cannot be deferred. Three concrete options:

**A. Promise-adapted (default assumed by this NOTES.md until this question is resolved):**
- Add `Promisified<T>` Proxy in foundation as described below.
- Consumers write `await this.audience.getUser(req)` uniformly.
- Rationale: entire rest of the stack is Promise-based (Drizzle, Redis, AWS S3 SDK, future RMQ publisher via `lastValueFrom`). Mixing Observable for gRPC only with Promise for everything else forces `from()` and RxJS `pipe()` in every use case that touches more than one adapter. Promise-uniform keeps `async/await` consistent across all adapters.
- Also keeps RxJS out of `application/domain` layers (Clean Architecture — RxJS is framework detail, belongs in infrastructure).

**B. Observable pass-through (canonical NestJS, as in official `sample/04-grpc`):**
- NO Proxy at all. `@Inject(SERVICE.X.diToken)` gives consumer the raw `AudienceServiceClient` — Observable-returning methods exactly as generated.
- HTTP controllers `return this.audience.getUser(req)` directly; NestJS HTTP layer auto-subscribes.
- Use cases that mix gRPC with non-gRPC async (DB, Redis, S3) must either:
  - use `from(promise)` to adapt Promise → Observable and compose via RxJS operators, OR
  - use `lastValueFrom(observable)` at specific call sites to drop back into Promise world.
- `grpc.client.call` logging, deadline, correlationId — NOT per-call via Proxy. Moved to either:
  - `@grpc/grpc-js` channel-level interceptor (globally applied, harder to get per-method fields in logs)
  - NestJS `Interceptor` at controller boundary (logs HTTP → gRPC edges, not per-method)
- Pros: zero foundation helper, consumer sees native ts-proto types, matches NestJS canon.
- Cons: observability is coarser or requires a separate channel interceptor mechanism; use cases mix `await` + `from()` + `pipe()`.

**C. Hybrid:** Observable-native adapter, plus a foundation helper `toPromise(observable, opts)` for use-case sites that want `await`. Consumer explicitly chooses per call. Pros: flexibility. Cons: fragmented style across codebase, no uniform convention.

**My leaning (to be validated in discuss-phase):** option A. Reason: our future use cases are almost certainly mixed-async (gRPC + DB + Redis + S3 + RMQ events), and `async/await` is already the dominant pattern outside gRPC. A uniform adapter surface avoids stylistic fragmentation in the part of the codebase that will grow the most (application layer).

**But option B is honestly purer NestJS.** If the team prefers RxJS-first composition and accepts the hybrid-async friction in use cases, B works. Decision should be conscious, not defaulted.

**[IMPORTANT — streaming is NOT a tie-breaker.]** User asked 2026-04-17: "if we later add streaming RPCs, can we get both Promise AND Observable views of the same service?" Answer: YES, via the Smart Proxy variant (see Q#8 below). Streaming methods pass through as Observable; unary methods become Promise; one inject, TypeScript mapped types make the distinction safe. This means Option A is **streaming-ready by design** — choosing A today does NOT close the streaming-capable future.

**Question dependencies:**
- If A: everything in this NOTES.md applies.
- If B: the NOTES.md implementation sketch (Promisified Proxy) is replaced by a much thinner `defineGrpcClient` that injects the raw `ClientGrpc.getService<T>()` result directly. `apps/**/*.client.ts` still vanishes; `GrpcCaller` still vanishes; but foundation helper becomes near-zero. Observability moves to channel-level interceptors or Nest Interceptors.
- If C: both Proxy and raw injection exist; consumers pick.

**Resolution mechanism:** `/gsd:discuss-phase 999.7.3` opens this as question #0 BEFORE anything else. Decision gates all subsequent design.

### 1. **Client-token injection shape.** Should consumers `@Inject(SERVICE.auth.diToken)` and get `Promisified<AuthProto.AuthServiceClient>` directly, or should there be a thin re-exported type alias (`type AuthClient = Promisified<AuthProto.AuthServiceClient>`) per upstream for ergonomic shorthand? Trade-off: less boilerplate per-consumer vs one extra type export per module file. Leaning toward (a) direct `Promisified<T>` — lets consumers inline-type without needing an alias file.

2. **`rawType` vs serviceName-only in `defineGrpcClient`.** The factory needs the generated client type `T` to compute `Promisified<T>`. Options:
   - Pass the ts-proto definition object (runtime value) — but ts-proto with `nestJs=true` generates `*Client` interfaces, not runtime definitions. `outputServices=grpc-js` (which we ALSO have enabled) does generate runtime definitions — check `packages/contracts/src/generated/*.ts` to see what's available.
   - Use generic parameter only (`defineGrpcClient<AuthServiceClient>(opts)`) and rely on `grpc.getService<T>(name)` for runtime dispatch. TypeScript inference only; no runtime type check. This is probably fine — ts-proto `getService` already takes `<T>` as generic.

3. **Deletion of 8 client module files entirely?** Could `defineGrpcClient` be called from a central composite module (`grpc-clients.module.ts`) for all 8 upstreams at once, eliminating even the `*-client.module.ts` files? Probably not worth — per-upstream modules give granular `forRoot()` semantics and match the per-app topology (gateway uses 5, sender uses 1, parser uses 1, audience uses 1). Keep them but let them become ~8-line declarations.

4. **Do we keep `GrpcCaller` as a named export for tests/mocking?** Probably no — tests can mock `Promisified<T>` directly as a plain object with jest/vitest mocks. No need for GrpcCaller symbol.

5. **How to mock `Promisified<AuthServiceClient>` in tests?** Trivial — `const mock: Promisified<AuthServiceClient> = { login: jest.fn().mockResolvedValue(...), ... }`. Actually BETTER than current GrpcCaller mocking because the raw interface is what the domain cares about.

6. **ESLint guard adjustment.** Decision: keep the `ClassDeclaration[superClass]` guard in Override 6 after the .client.ts files are gone — belt-and-braces. But the path pattern `apps/**/clients/**/*.client.ts` may match nothing; either remove the pattern or keep to prevent regression. Decide during planning.

7. **Skill file update scope.** Plan 04 of 999.7.2 extended `infrastructure-client-layering` with composition-over-inheritance language. This phase should update the gRPC reference further — declare the Proxy pattern as the canonical shape. Phrasing decisions during discuss-phase.

8. **Smart Proxy for mixed Promise/Observable (streaming support).** Surfaced by user 2026-04-17: "if we add streaming RPCs later, can we get both Promise AND Observable views?" Answer: yes, via mapped type `SmartPromisified<T, StreamingKeys>`:

   ```ts
   type SmartPromisified<T, StreamingKeys extends keyof T = never> = {
     [K in keyof T]: K extends StreamingKeys
       ? T[K]                                              // streaming passes through as Observable
       : T[K] extends (...args: infer A) => Observable<infer R>
         ? (...args: A) => Promise<R>                      // unary becomes Promise
         : T[K];
   };
   ```

   Proxy runtime detects streaming methods by reading ts-proto-generated `XxxServiceDefinition.methods[m].responseStream` (which `outputServices=grpc-js` already emits — check `packages/contracts/src/generated/*.ts`). Manual `StreamingKeys` parameter may not even be needed if runtime detection is reliable.

   Consumer gets ONE injected client with mixed method signatures:
   - `await audience.getUser(req)` — Promise (unary)
   - `audience.subscribeToUpdates(req).subscribe(...)` — Observable (streaming)

   Decision for the phase: start with simple `Promisified<T>` (unary-only, no streaming concern today). When streaming first appears, upgrade foundation helper to `SmartPromisified`. Breaking change risk is zero — unary methods keep same signatures.

   Alternative if team prefers explicit separation: dual DI tokens per service (`AUDIENCE_CLIENT` = Promisified, `AUDIENCE_CLIENT_RAW` = Observable). More verbose, less integrated, but some teams prefer the explicit `$` suffix convention (`audience$` for Observable-returning).

9. **Runtime smoke recipe.** Same as 999.7.2 Plan 05 Task 2 — native + isolated modes, curl `/health/ready` + `/test/parser/storage-service` + `/test/notifier/storage-service`, verify `grpc.client.call` log entries show `context=XxxClient correlationId=...`. Should pass as-is since the log field shape is preserved. No new test infrastructure needed.
