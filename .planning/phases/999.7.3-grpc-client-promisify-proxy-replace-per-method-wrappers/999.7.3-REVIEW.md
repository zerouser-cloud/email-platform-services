# Phase 999.7.3: Code Review Report

**Reviewed:** 2026-04-18T13:30:00Z

## Summary

Phase 999.7.3 replaces 8 hand-written per-method gRPC wrapper classes with a single `Promisified<T>` Proxy primitive in `packages/foundation/src/external/grpc/clients/`. The implementation is clean, the per-app modules are uniformly canonical, and the Pitfall 3 whitelist (`new Set(Object.keys(raw))` snapshot at construction) is correctly implemented and verified against `@nestjs/microservices/client/client-grpc.js:38-50` — `getService(name)` returns a plain object whose own keys are exactly the RPC method names, so the snapshot is sound.

The 8 per-app `*-client.module.ts` files are exact siblings with only domain-name substitutions (audience/auth/notifier/parser/sender × the appropriate consumer app), each ~22 lines, identical comments, identical structure. Token re-export naming follows `{UPPER_SVC}_CLIENT_GRPC` / `{UPPER_SVC}_GRPC_HEALTH` consistently. No DI tokens leak from `defineGrpcClient`'s internal helpers; only the named symbols (`grpcToken`, `healthToken`) are surfaced.

All identified issues are non-blocking. The most material one is a deliberate type/runtime asymmetry in `Promisified<T>`: the public type still expects ts-proto's `Metadata` as the second arg, but the runtime Proxy actually accepts `CallOpts`. The phase team acknowledged this in `999.7.3-02-SUMMARY.md` and worked around it in `grpc-client-sanity.ts` by dropping the second arg in probe calls. This is documented but creates a footgun: if a future consumer types `await this.auth.login(req, callOpts)` they will get a TypeScript error and likely reach for `as unknown as Metadata` or stop using `CallOpts` entirely. See WR-01.

Two minor `Reflect.get` ergonomics issues (WR-02, WR-03), and a cluster of stylistic / documentation observations (IN-01..IN-05) round out the findings. No bugs, no security issues, no project-rule violations.

## Warnings

### WR-01: `Promisified<T>` type/runtime second-arg asymmetry — silent footgun for `CallOpts` callers

**File:** `packages/foundation/src/external/grpc/clients/promisify-grpc-client.ts:18-22, 60`
**Issue:** The mapped type `Promisified<T>` preserves the original ts-proto signature `(...args: A) => Promise<R>`, where `A` for ts-proto-generated clients is `[req, meta?: Metadata]`. The runtime Proxy, however, declares `(request: unknown, callOpts?: CallOpts) => Promise<unknown>` (line 60) and reads `callOpts?.deadlineMs`. A consumer writing `await this.auth.login(req, { deadlineMs: 5000 })` gets a TypeScript error because `CallOpts` is not assignable to `Metadata`. A consumer writing `await this.auth.login(req, someMetadata)` typechecks but the runtime ignores `someMetadata` (it builds its own `Metadata` from `callOpts.deadlineMs`, falling back to the default).

The phase team acknowledged this in `999.7.3-02-SUMMARY.md` and worked around it in `grpc-client-sanity.ts:31-34, 42` by simply dropping the second arg in probe calls and adding a multi-line comment apologizing for the asymmetry. Today no production consumer passes a second arg (the only consumer is `storage-smoke.controller.ts`, which always omits it). But the asymmetry is latent: the next caller who needs a per-call deadline override will reach for `CallOpts`, hit the type error, and either widen with `as unknown` or stop using the override entirely.

**Fix:** Widen `Promisified<T>` to accept `Metadata | CallOpts` in the second position. Two reasonable shapes:

```typescript
// Option A — re-map the second arg explicitly (simpler)
export type Promisified<T> = {
  [K in keyof T]: T[K] extends (req: infer Req, meta?: Metadata) => Observable<infer R>
    ? (req: Req, opts?: CallOpts | Metadata) => Promise<R>
    : T[K] extends (...args: infer A) => Observable<infer R>
      ? (...args: A) => Promise<R>
      : T[K];
};

// Option B — keep the conditional but discriminate inside the runtime
// (then assert via instanceof Metadata in the trap and pass-through to orig.call)
```

Option A is preferred because it makes the public contract honest and unblocks `CallOpts` usage at every call site without `as` casts. The runtime trap then needs a discriminator: `if (arg instanceof Metadata) { /* pass through */ } else { /* build from CallOpts */ }`. This also removes the apologetic comment block in `grpc-client-sanity.ts:31-34, 42` and lets the negative probe additionally assert `audience.listGroups(req, { deadlineMs: 1000 })` typechecks.

If wider work isn't desirable in this phase, file as a follow-up and add a `// FIXME: type/runtime asymmetry — see REVIEW WR-01` marker on `promisify-grpc-client.ts:60` so the next consumer who hits this finds the trail immediately.

### WR-02: `Reflect.get(target, prop, receiver)` with the Proxy as `receiver` may bind `this` to the Proxy, not the raw target

**File:** `packages/foundation/src/external/grpc/clients/promisify-grpc-client.ts:51-53, 67`
**Issue:** Inside the `get` trap, `Reflect.get(target, prop, receiver)` is called with `receiver` defaulted to the Proxy itself. For accessor (`get`) properties on the target's prototype chain, this would invoke the getter with `this === Proxy`, not `this === raw`. For ts-proto-generated NestJS gRPC clients today this is benign — `getService()` returns a plain object of own data properties (each is a `(...args) => Observable<...>` value, not a getter), verified at `@nestjs/microservices/client/client-grpc.js:38-50`. So the live behavior is correct.

However, when `orig` is then invoked at line 67 via `orig.call(target, request, meta)`, the receiver is correctly bound to `target` (the raw object), which is good — but it means there are TWO different `this`-binding policies inside the trap: `Reflect.get` uses Proxy-as-receiver; method call uses target-as-receiver. The asymmetry is intentional but easy to miss when refactoring.

**Fix:** Either:
1. Pass `target` as the third arg to `Reflect.get` for symmetry: `Reflect.get(target, prop, target)`. This eliminates the (theoretical-today) accessor-binding hazard and matches the intent of "wrap a flat data object".
2. Keep current code and add a one-line comment at line 51 noting the assumption: `// Receiver=Proxy is safe here because grpc.getService() returns own data properties only, not accessors.`

Option 1 is preferred — it's a 5-character change that closes the hazard for future foundation consumers (someone might wrap something other than a raw gRPC client through this primitive once the pattern catches on).

### WR-03: Non-string symbol-keyed properties bypass the whitelist check correctly, but `Reflect.get` for unknown string props swallows symbol-named RPC methods (theoretical only)

**File:** `packages/foundation/src/external/grpc/clients/promisify-grpc-client.ts:46, 50`
**Issue:** `rpcMethods = new Set(Object.keys(raw))` snapshots only string keys (`Object.keys` ignores symbols). The trap on line 50 short-circuits non-string `prop` to `Reflect.get`, which correctly passes through symbol property accesses (e.g., `Symbol.toPrimitive`, `util.inspect.custom`). This is the desired behavior and matches the comment at line 44-45.

The latent assumption is that ts-proto / @nestjs/microservices never generates symbol-keyed RPC methods. Verified true today via the `getService` source: it iterates `Object.keys(clientRef[name].prototype)` (line 41 of client-grpc.js), so RPC methods are always string-keyed. If proto3 ever supports symbol identifiers (it does not), the whitelist would silently drop them.

This is a theoretical concern only and doesn't need fixing today.

**Fix:** No code change required. Add a one-line assumption comment at line 46:
```typescript
// String-keyed snapshot is sufficient — ts-proto + @nestjs/microservices generate
// only string-keyed RPC methods (verified at client-grpc.js:41).
const rpcMethods = new Set(Object.keys(raw));
```

### IN-01: Eight `*-client.module.ts` files are byte-identical templates — opportunity for higher-order helper later (do not refactor now)

**File:** `apps/{audience,gateway,parser,sender}/src/infrastructure/clients/*/*.ts` (8 modules)
**Issue:** Every per-app module is the same 22-line template with three substitutions: `{Domain}` (Auth/Sender/...), `SERVICE.{domain}`, and the `{DOMAIN}_CLIENT_GRPC` / `{DOMAIN}_GRPC_HEALTH` re-exports. The skill `infrastructure-client-layering` rule "Apps assemble + name" still requires the per-app naming layer to exist (the named tokens are real value adds for `health.controller.ts` consumption), so the template can't collapse to zero per-app code today. But ~16 lines of identical boilerplate × 8 modules = ~128 lines of mechanical text.

A future foundation helper could expose `defineGrpcClientModule({ service, clientToken, names: { CLIENT_GRPC: 'AUTH_CLIENT_GRPC', GRPC_HEALTH: 'AUTH_GRPC_HEALTH' } })` that returns `{ module: class, CLIENT_GRPC: symbol, GRPC_HEALTH: symbol }` — but that trades one form of repetition for another and may not net-save. Phase 999.7.3 made the right call by leaving the per-app modules as flat templates. Note for a future skill review.

**Fix:** No change. Document this observation in the phase summary so a future reviewer doesn't reach for the same simplification and discover the prior analysis.

### IN-02: `defineGrpcClient<TRaw>` returns the Promisified type only via `useFactory`'s inferred return — no surfaced `Promisified<TRaw>` type on `GrpcClientBuildResult`

**File:** `packages/foundation/src/external/grpc/clients/define-grpc-client.ts:23-29, 42`
**Issue:** `GrpcClientBuildResult` exposes `imports / providers / exports / grpcToken / healthToken` but no `clientType: Promisified<TRaw>`. Consumers must independently derive the type at the inject site (`Promisified<AuthProto.AuthServiceClient>`). This is fine because the consumer always knows the raw type at inject time, but it means `TRaw` only exists to type the `useFactory` return — it's a type-only generic. There's no runtime check that `clientToken` actually resolves to a `Promisified<TRaw>` value (Nest DI is unityped).

**Fix:** No code change required. Optionally add a JSDoc note to `defineGrpcClient` clarifying that consumers must inject as `Promisified<TRaw>`:
```typescript
/**
 * ...
 * @example
 * const grpc = defineGrpcClient<AuthProto.AuthServiceClient>({ service: SERVICE.auth, clientToken: SERVICE.auth.diToken });
 * // Consumer:
 * constructor(@Inject(SERVICE.auth.diToken) private readonly auth: Promisified<AuthProto.AuthServiceClient>) {}
 */
```

### IN-03: Non-null assertions in `define-grpc-client.ts:45, 67, 70, 74` mask configuration mistakes at runtime

**File:** `packages/foundation/src/external/grpc/clients/define-grpc-client.ts:45, 67, 70, 74`
**Issue:** Four `!` non-null assertions on `config.get<...>()` results: `GRPC_DEADLINE_MS`, `opts.service.envKeys.GRPC_URL`, `PROTO_DIR`, `GRPC_DEADLINE_MS` again. The project's env schema is Zod-validated with no defaults/optionals (per the `env-schema` skill), so these values are guaranteed to exist by config-load time — the assertions are factually correct. But `!` silences the type system; a future env-schema rename (e.g., `GRPC_DEADLINE_MS` → `GRPC_DEFAULT_DEADLINE_MS`) would still typecheck and only blow up at runtime when `config.get` returns undefined.

For consistency with the project's "no fallbacks in consumer code" rule (env-schema skill) and for future-proofing, prefer either:
1. A typed config helper that returns non-undefined values: `config.getOrThrow<number>('GRPC_DEADLINE_MS')` (NestJS provides this since 8.x).
2. An explicit assertion with a useful error: `const deadline = config.get<number>('GRPC_DEADLINE_MS') ?? throwMissingEnv('GRPC_DEADLINE_MS')`.

**Fix:** Replace `!` with `getOrThrow`:
```typescript
defaultDeadlineMs: config.getOrThrow<number>('GRPC_DEADLINE_MS'),
// ...
url: config.getOrThrow<string>(opts.service.envKeys.GRPC_URL),
protoPath: [
  resolveProtoPath(opts.service.grpc.package, config.getOrThrow<string>('PROTO_DIR')),
  // ...
],
channelOptions: {
  interceptors: [createDeadlineInterceptor(config.getOrThrow<number>('GRPC_DEADLINE_MS'))],
},
```

This produces a useful error message on missing env (`Configuration key "GRPC_DEADLINE_MS" does not exist`) instead of an opaque `Cannot read properties of undefined`.

### IN-04: `clientToken: opts.service.diToken` parameter at every call site is redundant — `defineGrpcClient` could read it from `service`

**File:** `packages/foundation/src/external/grpc/clients/define-grpc-client.ts:18-21, 39-40` and all 8 per-app modules
**Issue:** Every per-app module calls `defineGrpcClient({ service: SERVICE.parser, clientToken: SERVICE.parser.diToken })`. The `clientToken` is always `service.diToken`. This is intentional decoupling (a hypothetical future caller could use a different token), but in practice all 8 callers pass the same value, and there's no plausible scenario where a `defineGrpcClient` consumer would want a token that doesn't match the catalog identity (that would be the ANTI-PATTERN 6 from infrastructure-client-layering skill: hardcoded token strings outside the catalog).

**Fix:** Default `clientToken` to `service.diToken`:
```typescript
export interface DefineGrpcClientOpts {
  readonly service: GrpcServiceDeclaration;
  readonly clientToken?: symbol;  // defaults to service.diToken
}

export function defineGrpcClient<TRaw extends object>(opts: DefineGrpcClientOpts): GrpcClientBuildResult {
  const clientToken = opts.clientToken ?? opts.service.diToken;
  // ...
}
```

This eliminates 8 lines of redundant per-call boilerplate. Mark as Info (not Warning) because the explicit parameter is defensive and removing it tilts the API toward hidden defaults — there's a tradeoff. Note also: the env-schema skill forbids `??` defaults in env code, but this is application code, not env schema, and the default is a code-time wiring decision, not a config value. Still, the project tone leans against optional parameters with defaults; if the team prefers explicit > implicit, leave as-is.
