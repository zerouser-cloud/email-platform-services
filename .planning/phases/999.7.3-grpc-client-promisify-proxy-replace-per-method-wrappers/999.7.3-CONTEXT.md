# Phase 999.7.3: gRPC client promisify proxy — replace per-method wrappers - Context

**Gathered:** 2026-04-18
**Status:** Ready for planning

<domain>
## Phase Boundary

Заменить 8 hand-written `*.client.ts` per-method wrapper-классов и standalone `GrpcCaller` helper единым типизированным `Promisified<T>` Proxy в foundation. Consumer инжектирует `Promisified<XxxProto.XxxServiceClient>` напрямую — никаких custom client-классов в `apps/`. Proxy перехватывает любой Observable-возвращающий метод raw ts-proto клиента, добавляет `Metadata` с per-call deadline, конвертирует Observable→Promise через `lastValueFrom`, возвращает результат. Логирование/трассировку **временно вырезаем** — будущая фаза по observability вернёт их через DI-injected logger (outer Proxy chain), не через `PinoLogger.root` singleton anti-pattern.

Цель — устранить ~58 method wrappers boilerplate (8 файлов × ~7 методов) и одну избыточную абстракцию (`GrpcCaller` standalone class). Добавление нового RPC-метода в `.proto` автоматически становится доступным consumer'у через type mapping `Promisified<T>` без ручного wrapping в client-классе.

Out of scope:
- HTTP/RMQ/S3/Redis/DB+ORM refactors — отдельные будущие фазы, пользуются тем же skill
- Streaming RPC support — все RPC сейчас unary; streaming когда появится — отдельная фаза, простая миграция Promisified→SmartPromisified
- Distributed tracing, structured logging, retry policy, circuit breaker — отдельные будущие фазы; этот Proxy пишется как "pristine", чтобы оставить чистую extension point для outer Proxy с DI-injected dependencies
- nice-grpc / альтернативные gRPC stack миграции — стратегическое решение для будущего, не в этой фазе
- Server-side gRPC patterns

</domain>

<decisions>
## Implementation Decisions

### Q#0 — Surface contract: Promise vs Observable

- **D-01:** Promise-adapted via `Promisified<T>` Proxy в foundation. Consumer пишет `await this.audience.getUser(req)`. RxJS не протекает в application/domain — остаётся framework-detail инфраструктурного слоя. Согласовано с уже Promise-based стеком (Drizzle, Redis, AWS S3 SDK, future RMQ через `lastValueFrom`). Эталон в memory: «Kamil-endorsed Proxy promisify is the way; per-method wrapper classes — self-imposed friction». Отвергнуты: B (raw Observable pass-through — фрагментирует style между gRPC и остальной async infra), C (гибрид с opt-in toPromise — нет единой конвенции).

### GrpcCaller lifecycle

- **D-02:** `GrpcCaller` (foundation `packages/foundation/src/external/grpc/clients/grpc-caller.ts`) **удаляется полностью**. Три его обязанности (build metadata + `lastValueFrom` + структурное логирование) сворачиваются в Proxy trap handler. Single extension point — `promisifyGrpcClient`'s Proxy trap — заменяет двухслойный stack (Proxy → GrpcCaller). Превышает D-05 of 999.7.2: callback-factory `rpcFactory(meta)` сигнатура становится излишней индирекцией, потому что Proxy trap **сам** является intercept point — нет нужды передавать callback. 999.7.2 D-01..D-05 (форма GrpcCaller, callback-factory сигнатура) **superseded**.

### Logging/observability — exit clean, return through DI

- **D-03:** **Logging вырезается из Proxy сейчас.** `ClsService` injection, `PinoLogger.root.child({ context })` lazy lookup, `serviceName`/`logContext` параметры — всё уходит. Мотивация (от пользователя 2026-04-18): «логгер должен приходить через DI а не напрямую» — текущий pattern с `PinoLogger.root` это singleton anti-pattern, обходящий DI. Рассматривается как технический долг, который не должен путешествовать в новый код этой фазы.

- **D-04:** Текущее структурированное логирование `grpc.client.call` (поля service/method/duration_ms/status/correlationId) **временно перестаёт эмититься**. Это сознательная регрессия observability — компенсируется будущей фазой по logging/tracing. Runtime smoke fixtures проверяют только что RPC проходит end-to-end, не log-shape. 999.7.2 D-04 (cls внутри GrpcCaller для correlationId) — **superseded** в этой фазе, **return**ится в будущей фазе через DI правильным способом.

- **D-05:** **Extension point design.** Foundation `promisifyGrpcClient` остаётся pristine: только `Metadata` (deadline) + `lastValueFrom`. Будущая observability-фаза добавляет outer Proxy chain (`wrapWithObservability(promisified, { logger, cls })`) который оборачивает наш Promisified Proxy ещё одним слоем — добавляет tracing-headers в metadata, structured logging per call, distributed-trace propagation. Outer Proxy получает logger/cls через DI. Pristine inner Proxy = orthogonal architecture, никакого hack-injection через `PinoLogger.root`.

- **D-06:** Будущая observability-фаза также вернёт correlation-id propagation **по сети** через gRPC metadata header (например `x-correlation-id` или OpenTelemetry `traceparent`) — что прежний `GrpcCaller` НЕ делал (он только писал correlationId в локальный лог-field, не propagate'ил downstream). Это не регрессия, а apropos cleanup.

### Foundation: API shape and exports

- **D-07:** Новый файл `packages/foundation/src/external/grpc/clients/promisify-grpc-client.ts`. Экспортирует:
  - `type Promisified<T>` — mapped type, маппит каждый `(...args) => Observable<R>` метод в `(...args) => Promise<R>`. Не-функциональные свойства и intentional Observable (streaming) пропускаются как есть
  - `function promisifyGrpcClient<T extends object>(raw: T, opts: PromisifyOpts): Promisified<T>` — runtime функция, возвращает Proxy

- **D-08:** `PromisifyOpts` минимальный — содержит только `defaultDeadlineMs: number`. **Не** содержит `serviceName`, `logContext`, `cls` (всё removed по D-03). Если future нужен — добавляется тогда.

- **D-09:** `define-grpc-client.ts` модифицируется:
  - Сигнатура: `defineGrpcClient<TRaw extends object>(opts: DefineGrpcClientOpts): GrpcClientBuildResult` — **build callback убран** (`useFactory` сама строит Promisified Proxy)
  - `inject` массив `useFactory`: `[grpcToken, ConfigService]` — **`ClsService` убран** (по D-03)
  - `useFactory`: `(grpc, config) => promisifyGrpcClient(grpc.getService<TRaw>(serviceName), { defaultDeadlineMs: config.get('GRPC_DEADLINE_MS') })`
  - `DefineGrpcClientOpts` — без изменений (`service` + `clientToken`)
  - `GrpcClientBuildResult` shape — **без изменений** (стабилен с 999.7.1 D-08, 999.7.2 D-08)
  - 999.7.2 D-07 (build callback signature `(grpcClient, caller) => T`) — **superseded**

- **D-10:** Foundation barrel (`packages/foundation/src/external/grpc/clients/index.ts` + корневой `packages/foundation/src/index.ts`):
  - **Удалить exports:** `GrpcCaller` (тип), любые упоминания `grpc-caller.ts`
  - **Добавить exports:** `Promisified` (тип), `promisifyGrpcClient` (функция)
  - `CallOpts`, `GrpcClientLogFields` — пересмотр: `GrpcClientLogFields` сейчас не используется (логирование вырезано), но **сохраняется** для future observability-фазы — не удаляем, не deprecat'им. `CallOpts` — продолжает использоваться (deadline override per call)
  - 999.7.2 D-09 (export type `GrpcCaller`) — **superseded**

### Q#1 — Consumer DI shape

- **D-11:** Consumer типизирует напрямую: `Promisified<XxxProto.XxxServiceClient>`. Никаких per-upstream type alias (`type AuthClient = ...`). Несколько верboznее в constructor (`@Inject(SERVICE.auth.diToken) private readonly auth: Promisified<AuthProto.AuthServiceClient>`), но **минус 8 type alias exports**, **минус 1 entropy source**, и consumer всегда работает с raw proto types (видит все RPC методы из контракта без переименования).

### Q#2 — Generic parameter vs runtime ServiceDefinition

- **D-12:** Type-only через generic parameter: `defineGrpcClient<XxxProto.XxxServiceClient>({ service, clientToken })`. Runtime по-прежнему через `grpc.getService<TRaw>(serviceName)` — это native ts-proto pattern, нулевой overhead. **Runtime ServiceDefinition** (например `AuthServiceService` constant) **не** передаётся в фабрику. Trade-off: закрывает дверь к auto-detection streaming методов через `responseStream` поле — но (см. D-13) сейчас streaming нет, и переход на runtime ServiceDefinition остаётся возможен в будущей фазе если действительно понадобится.

### Q#8 — Streaming readiness

- **D-13:** Не предвосхищать. Простой `Promisified<T>` сейчас, все методы → Promise. Когда streaming RPC появятся в roadmap (сейчас их нет), отдельная фаза решит:
  - либо переход на `SmartPromisified<T, StreamingKeys>` с MANUAL параметром streaming-методов
  - либо переход на runtime `ServiceDefinition` с auto-detection через `responseStream`
  - либо отдельная функция/Proxy для streaming endpoints
  
  Migration safe в любом сценарии: unary методы сохраняют Promise-сигнатуру, streaming просто добавляются. Код подтверждено: `packages/contracts/src/generated/auth.ts:669` экспортирует `AuthServiceService` runtime constant с `responseStream: false` per method — runtime detection feasible когда будет нужен.

### Q#3 — Apps modules structure

- **D-14:** **Сохраняются 8 `*-client.module.ts` файлов** — granular `forRoot()` semantics, per-app topology (gateway 5, sender 1, parser 1, audience 1) сохранена. Каждый модуль упрощается до ~10 строк:
  ```ts
  const grpc = defineGrpcClient<AuthProto.AuthServiceClient>({
    service: SERVICE.auth,
    clientToken: SERVICE.auth.diToken,
  });
  export const AUTH_CLIENT_GRPC = grpc.grpcToken;
  export const AUTH_GRPC_HEALTH = grpc.healthToken;
  
  @Module({})
  export class AuthClientModule {
    static forRoot(): DynamicModule {
      return { module: AuthClientModule, imports: grpc.imports, providers: grpc.providers, exports: grpc.exports };
    }
  }
  ```
  
  Composite `grpc-clients.module.ts` per app отвергнут: ломает 999.7.1 named re-exports pattern (`AUTH_CLIENT_GRPC` re-export для health.controller). Granular approach — single source of truth per upstream.

- **D-15:** **8 `apps/**/*.client.ts` файлов удаляются полностью.** Список:
  - `apps/gateway/src/infrastructure/clients/auth/auth.client.ts`
  - `apps/gateway/src/infrastructure/clients/sender/sender.client.ts`
  - `apps/gateway/src/infrastructure/clients/parser/parser.client.ts`
  - `apps/gateway/src/infrastructure/clients/audience/audience.client.ts`
  - `apps/gateway/src/infrastructure/clients/notifier/notifier.client.ts`
  - `apps/sender/src/infrastructure/clients/audience/audience.client.ts`
  - `apps/parser/src/infrastructure/clients/notifier/notifier.client.ts`
  - `apps/audience/src/infrastructure/clients/parser/parser.client.ts`
  
  Соответствующие `apps/**/clients/{upstream}/index.ts` барреллы — пересматриваются: убрать `export * from './xxx.client'`; оставить `export * from './xxx-client.module'` (для `forRoot()` import) и named token re-exports.

### Q#6 — ESLint guard fate

- **D-16:** ESLint `no-restricted-syntax` guard на `ClassDeclaration[superClass]` в `apps/**/clients/**/*.client.ts` (Override 6, добавленный 999.7.2 D-16) — **сохраняется belt-and-braces**. После удаления `*.client.ts` файлов pattern ничего не matches (cost = 0), но защищает от регрессии: если в будущем кто-то возродит `apps/**/clients/**/*.client.ts` с `extends`, ESLint поймает. Альтернатива «удалить» — отвергнута: добавление обратно стоит дороже чем стейл-rule с нулевым impact.

## Specific Ideas

- **Pristine inner Proxy + future outer Proxy chain** — D-05 establishes orthogonal architecture. Сегодняшний `promisifyGrpcClient` делает только metadata + lastValueFrom, никаких cross-cutting concerns. Будущая observability-фаза напишет `wrapWithObservability(promisified, { logger, cls })` который оборачивает наш Proxy ещё одним слоем — добавляет structured logging, distributed tracing headers, retry hooks, circuit-breaker checks. Каждый Proxy слой = single concern. Композируемо как middleware chain
- **`PinoLogger.root` singleton anti-pattern** — текущий код в `GrpcCaller` обходил DI чтобы получить logger в `useFactory` (где DI ещё не готов на момент инстанциации). Pitfall 6 был *workaround*, не архитектурное решение. Удаление logger'а из этой фазы — chance reset accidental complexity. Будущая фаза сможет правильно DI-инжектить logger в outer Proxy
- **Correlation propagation по сети — pending future** — текущий `GrpcCaller` писал `correlationId` в local log field, но **не** propagate'ил downstream (в gRPC metadata). После distributed-tracing фазы это будет правильно решено через `traceparent` header (W3C trace context) — что purer чем local-only correlationId
- **Type-mapping `Promisified<T>` зеркалит runtime Proxy** — TypeScript видит ту же трансформацию что делает Proxy. Consumer получает полностью типизированный `Promisified<AuthServiceClient>`, видит `login(req): Promise<TokenPair>` (не `Observable<TokenPair>`). Никаких type-assertions, `as any`, `unknown` cast'ов. ts-proto generics + TypeScript conditional types справляются с любой сигнатурой
- **Streaming-friendly mapped type** — `Promisified<T>` пропускает не-функциональные свойства и intentional Observable returns как есть. Когда streaming RPC появится, методы возвращающие `Observable<T>` (intentionally streaming) останутся Observable. Mapped type signature: `T[K] extends (...args: infer A) => Observable<infer R> ? (...args: A) => Promise<R> : T[K]`. Streaming методы в ts-proto могут возвращать `Observable<T>` без unwrap'а — но это **future concern** (D-13). Сейчас все unary, всё Observable→Promise
- **Generic parameter route закрывает дверь к auto-detection** — D-12 trade-off: type-only generic = zero runtime overhead, но если хотим runtime streaming detection через `responseStream` поле, нужно будет добавить runtime ServiceDefinition в `defineGrpcClient` (refactor небольшой). Это сознательно отложено — runtime route добавит ~5 строк когда понадобится, не предвосхищаем

</specifics>

## Deferred Ideas

- **Distributed tracing** — отдельная будущая фаза. Outer Proxy chain (D-05) добавляет `traceparent` header в gRPC metadata, span creation вокруг RPC, trace_id/span_id в log fields. DI-injected `Tracer`/`ClsService`. Возвращает correlation-id propagation downstream
- **Structured logging** — отдельная будущая фаза, parallel with или после tracing. Outer Proxy chain эмитит `grpc.client.call` event с byte-for-byte совместимым shape (service/method/duration_ms/status/correlationId) **через DI-injected logger** (не через `PinoLogger.root.child()`). Восстанавливает observability которую D-04 временно убрал
- **Retry policy + circuit breaker** — отдельная будущая фаза. Outer Proxy chain или separate inner Proxy для retry-loop. Точка входа уже подготовлена (Proxy trap = единая extension point)
- **Streaming RPC support** — D-13. Когда streaming появится в proto: либо migration на `SmartPromisified<T, StreamingKeys>` с manual параметром, либо переход на runtime ServiceDefinition с auto-detection через `responseStream` поле. Generated proto (`packages/contracts/src/generated/*.ts`) уже экспортирует runtime ServiceDefinition с этим полем — feasibility подтверждена
- **HTTP / RMQ / Redis / S3 / DB+ORM refactors** — отдельные будущие фазы. Каждая применяет `infrastructure-client-layering` + `composition-over-inheritance` skills с учётом своих особенностей. HTTP может рассмотреть аналогичный Proxy подход если использует Observable-возвращающую обёртку (но native fetch/axios — Promise-based, маловероятно нужен Proxy). RMQ — вообще другой API surface (publish/subscribe), не applicable
- **AbstractGrpcClient `@deprecated` период** — N/A (уже удалён в 999.7.2). Тот же clean-break принцип применяется к `GrpcCaller` в этой фазе — codebase internal, нет внешних consumers

- **nice-grpc / альтернативные gRPC stack миграции** — стратегическое решение для будущего (заменяет `@nestjs/microservices` на server и client). Не в этой фазе, не в ближайшем roadmap

Audit — отдельная фаза наблюдательности
