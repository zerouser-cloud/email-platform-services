## Q#0 — Promise vs Observable surface

| Option | Description | Selected |
|--------|-------------|----------|
| A. Promise-adapted via Promisified<T> Proxy | Foundation Proxy, await everywhere, no RxJS leak | ✓ |
| B. Raw Observable pass-through | NestJS HTTP auto-subscribes; mixed await + RxJS in use cases | |
| C. Гибрид — raw + foundation toPromise() helper | Per-call choice; fragmented style | |

**User's choice:** A. Promise-adapted.
**Notes:** Согласовано с Promise-based стеком (Drizzle/Redis/AWS SDK/future RMQ). Memory-зафиксированный pattern «Kamil-endorsed Proxy promisify» подтверждается.

## Q#0 follow-ups: GrpcCaller fate + Logging shape

### GrpcCaller standalone class

| Option | Description | Selected |
|--------|-------------|----------|
| Удалить — fold в promisifyGrpcClient | Single Proxy trap = extension point. -1 файл foundation | ✓ |
| Оставить — Proxy → GrpcCaller.call() | Two-layer stack, separated concerns. D-05 callback redundant | |

**User's choice:** Удалить.
**Notes (cited):** «Удаляй. Но мне еще очень не нравится загрязнение логером. У нас будет отдельные фазы по логгированию и добавлению заголовков для трассировки, может мы пока удалим логгер, но учтем что он будет, но он должен вообще во все приложение приходить через DI а не напрямую»

### Logging shape

| Option | Description | Selected |
|--------|-------------|----------|
| Byte-for-byte совместимый | Те же поля, runtime smoke без изменений | |
| Расширить — добавить поля | Out of scope этой фазы | |
| Убрать logging вообще | Отложить на future logging/tracing фазу через DI | ✓ (см. notes) |

**User's choice:** Эффективно — выбран вариант "убрать", но с оговоркой "учтём что вернётся".
**Notes (cited):** «Это наверное как раз касается логгера, в прошлом ответе обговорил»
**Resolution:** Logging вырезается из Proxy сейчас (`ClsService`, `PinoLogger.root.child()`, `serviceName`/`logContext` параметры удаляются). Future фаза по logging/tracing вернёт через DI-injected logger в outer Proxy chain. Pristine inner Proxy = orthogonal architecture (D-03, D-04, D-05).

## Q#2 — Generic parameter vs runtime ServiceDefinition

| Option | Description | Selected |
|--------|-------------|----------|
| A. Generic parameter: defineGrpcClient<TRaw>({...}) | Type-only, zero runtime overhead | ✓ |
| B. Runtime ServiceDefinition: { definition: AuthServiceService } | Runtime streaming detection, +1 import | |

**User's choice:** A. Generic.
**Notes:** Trade-off зафиксирован в D-12 — закрывает дверь к auto-detection streaming через `responseStream` поле, но переход на runtime route остаётся возможен в будущей фазе.

## Q#8 — Streaming RPC readiness

| Option | Description | Selected |
|--------|-------------|----------|
| Не предвосхищать — простой Promisified<T> | YAGNI, future фаза решит manual keys vs auto-detection | ✓ |
| Сразу SmartPromisified<T, StreamingKeys = never> | Migration safe но conditional-type сложность без выгоды сейчас | |

**User's choice:** Не предвосхищать.
**Notes:** Все RPC сейчас unary. Generated proto уже содержит runtime ServiceDefinition с `responseStream` per method (`packages/contracts/src/generated/auth.ts:669`) — feasibility подтверждена для будущей фазы.
