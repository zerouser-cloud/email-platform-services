**1. [Rule 3 — Blocking] Removed dangling GrpcCaller export from clients/index.ts as part of Task 2**

- **Issue:** The plan's `<files>` for Task 2 declared only `define-grpc-client.ts` and `grpc-caller.ts`, but `clients/index.ts` line 7 was `export type { GrpcCaller } from './grpc-caller';` — a dangling reference to the just-deleted file. - **Fix:** Removed the single dangling line from `clients/index.ts` as part of the Task 2 commit. The barrel's positive update (adding `Promisified` + `promisifyGrpcClient` + `PromisifyOpts` exports) remained in Task 3 per D-10 plan ordering.
- **Files modified:** `packages/foundation/src/external/grpc/clients/index.ts` (line 7 removed in commit `4bb8bf0`)
- **Verification:** Foundation typecheck (`pnpm --filter @email-platform/foundation exec tsc --noEmit`) exits 0 silently after Task 2.
- **Committed in:** `4bb8bf0` (Task 2 commit)
- **Why this is the right call:** Deleting a file and leaving its barrel re-export pointing to nothing is incoherent at the atomic-commit boundary — the barrel reference IS part of the deletion semantically. Splitting them would create a transient "intentionally broken" commit that fails Task 2's own verify gate. Per Rule 3 scope-boundary, this fix is directly caused by Task 2's file deletion, not pre-existing.

**2. [Observation, no fix needed] Plan-predicted error code TS2614 actually fires as TS2305**

- **Found during:** Task 4 (workspace typecheck sanity check)
- **Observation:** Plan's `<acceptance_criteria>` for Task 4 expected `8 ± 2 TS2614` errors ("Module '@email-platform/foundation' has no exported member 'GrpcCaller'"). TypeScript actually emits **TS2305** for the import shape `import type { GrpcCaller, CallOpts } from '@email-platform/foundation'` — both error codes carry the same semantic meaning ("no exported member 'GrpcCaller'"), only the message format differs. TS2305 fires for `import { X }` from a module missing `X`; TS2614 fires for distinct namespace-vs-default-import disambiguation cases.
- **Why no fix:** This is plan-prediction inaccuracy, not a deviation in execution. The total root-error envelope still matches the plan's `~16` prediction exactly (8 TS2554 + 8 TS2305 = 16). The `±2` tolerance was on per-code counts; the spirit was clearly the total interim envelope. Plans 02-05 will sweep both TS2554 (call-site mismatch) and TS2305 (missing import) errors as they migrate the 8 upstream client modules.
- **Tail effects:** 74 cascading TS7006 ("Parameter implicitly has an 'any' type") errors propagate from the 16 root errors when type inference fails on the broken imports. These are NOT separate problems — they evaporate automatically when the root errors are fixed in Plans 02-05.

**3. [Observation] Foundation has no `typecheck` script — used `tsc --noEmit` directly via `pnpm exec`**

- **Found during:** Task 1 verify gate
- **Observation:** Plan's `<verify>` and `<acceptance_criteria>` use `pnpm --filter @email-platform/foundation typecheck`, but `packages/foundation/package.json` only declares `build` and `lint` scripts (no `typecheck`). Functional equivalent used: `pnpm --filter @email-platform/foundation exec tsc --noEmit`. This produces the same diagnostic output without dist mutation.

## Issues Encountered

**Initial workspace `pnpm typecheck` undercounted errors due to turbo early-termination.** First Task 4 run showed `5 TS2554` + `5 TS2305` (total 10 root errors) which would have failed the `8 ± 2` tolerance window. Investigation revealed turbo cancels remaining parallel tasks once the first failure (gateway) hits, losing stderr from sender/parser/audience tasks that were running concurrently. Switched to per-app `pnpm --filter <app> exec tsc --noEmit` aggregation which captured the true 16 root errors (8 TS2554 + 8 TS2305) across all 5 file pairs in gateway plus 3 file pairs in cross-service apps (sender→audience, parser→notifier, audience→parser).

This matters for Plans 02-05: the per-app aggregation method is more reliable for tracking the interim error count's monotonic decrease as each upstream is migrated. Recommend Plan 02 use per-app counts as the canonical metric.
