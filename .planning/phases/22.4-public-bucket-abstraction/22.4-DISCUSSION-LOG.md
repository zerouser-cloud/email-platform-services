## Architectural Direction (initial audit requested by user)

**Starting point:** Initial scope from ROADMAP/STATE suggested gateway-proxy with HMAC-signed URLs, gateway streaming from internal S3. User pushed back — выглядит слишком сложно, попросил аудит замысла и альтернатив.

Audit findings presented:
- `getSignedUrl` в production коде не используется (только в smoke 22.3). Notifier отправляет в Telegram bytes напрямую.
- Garage в prod публично доступен (`files.email-platform.pp.ua`) — противоречит "gateway-only external surface"
- Real pain: isolated mode где `STORAGE_ENDPOINT=minio` даёт presigned URL с internal hostname

Options presented:
- A. Убрать `getSignedUrl` совсем (download URL никому не нужен)
- B. `STORAGE_PUBLIC_ENDPOINT` для разделения internal/external endpoint
- C. Gateway-proxy с HMAC (исходный scope)
- D. Traefik ForwardAuth + internal Garage

**User decision:** нужна возможность качать файлы по ссылке, правило gateway-only можно нарушить для файлов если не будет простого способа без прокси. Private/public разделение на уровне bucket'ов.

## Bucket Topology (shared vs per-service-public)

User предложил: у каждого сервиса свой private bucket, плюс один **shared** bucket для файлов с внешним доступом. Inter-service communication через shared, не через прямой доступ к чужому private.

| Option | Description | Selected |
|--------|-------------|----------|
| Per-service public buckets (каждый сервис сам публикует) | Сервис может отдавать свои файлы наружу | |
| Shared public bucket + per-service private | Один public на всё, любой сервис пишет/читает | ✓ |
| Namespace-based visibility в одном bucket | Один физический bucket, path-based ACL | |

**User's choice:** Shared public bucket + per-service private. Consistency: bucket = `public`, env var = `STORAGE_PUBLIC_URL`, согласованно.

`reports` bucket переименовывается в `public`. Будущий report-сервис получит свой per-service private bucket когда появится.

## Env configuration

**Первоначальное предложение Claude:** `STORAGE_PUBLIC_BASE_URL` поверх существующего `STORAGE_ENDPOINT`.

**User pushback:** "Я не хочу завязываться на домены и расположение, у нас 12 факторное приложение".

**Claude попытка упрощения:** один endpoint с `s3.local`/host-gateway/`/etc/hosts` для унификации между internal и external.

**User pushback:** "слишком усложняешь". Также показал реальность prod: `STORAGE_ENDPOINT=garage-wgs8kw8o4c08840844ss0o8g.coolify` — internal Coolify DNS, недостижим из браузера.

**Claude revised:** split-brain (internal vs external endpoint) существует во ВСЕХ окружениях, не только isolated. Две env-vars — правильное 12-factor разделение двух разных концернов.

| Option | Description | Selected |
|--------|-------------|----------|
| Одна `STORAGE_ENDPOINT` унифицированная (через `/etc/hosts`/host-gateway) | Минимум vars, но инфра-трюки | |
| `STORAGE_ENDPOINT` (internal) + `STORAGE_PUBLIC_URL` (external) | Два concern'а, каждый в своей env-var | ✓ |
| Один endpoint + URL rewriting в коде | App знает структуру доменов | |

**User's choice:** два env-var'а, имя `STORAGE_PUBLIC_URL`.

## API Shape для public storage

**Progression:**

1. Claude proposed два метода `getPublicUrl(key)` + `upload(key, body, contentType)` с ручным построением key.
2. User contra: нужна абстракция над использованием — `await sharedReports.uploadPublic('weekly.pdf', buffer)`, namespace и contentType зашиты в инстансе.
3. Claude revised: per-namespace binding через `SharedNamespaceModule.forNamespace({ namespace, contentType, token })`, аналогично `BucketStorageModule.forBucket()` из phase 22.1.
4. User asked about buffer: можно ли спрятать?
5. Claude: contentType/namespace/key/url — прячем. Buffer — нет, это сами байты. Caller-source неизбежен.

| Option | Description | Selected |
|--------|-------------|----------|
| `sharedStorage.upload(namespace, filename, body, contentType)` — caller передаёт всё | Меньше DI-инстансов, больше параметров | |
| `SharedNamespaceModule.forNamespace({...})` + `namespaced.upload(filename, body)` | Namespace+contentType зашиты в binding, как `forBucket` pattern | ✓ |
| `buildKey` helper + ручной `upload` | Больше контроля, больше boilerplate | |

**User's choice:** per-namespace binding, namespace+contentType зашиты. API:
```ts
interface NamespacedStoragePort {
  upload(filename, body): Promise<{ url, key }>;
  delete, exists
}
```

## Body Type (Buffer vs Readable vs Union)

**Claude initial rec:** Buffer-only, лимит через `STORAGE_MAX_UPLOAD_BYTES`, для больших файлов добавим `uploadStream` позже.

**User contra:** "У нас точно будут большие файлы" — Buffer-only не подходит.

| Option | Description | Selected |
|--------|-------------|----------|
| `Buffer` only | Simple, OOM risk, предсказуемо для известных размеров | |
| `Buffer \| Readable` union | Оба кейса, но ветвление внутри сервиса (`instanceof Readable`) | |
| `Readable` only + multipart через `@aws-sdk/lib-storage` | Один путь кода, работает для любого размера, `Readable.from(buffer)` для Buffer-кейса | ✓ |
| Два метода (`upload` + `uploadStream`) | Явно, но два пути кода всё равно | |

**User's choice:** Readable-only. Буфер-кейс wrapped в `Readable.from(buffer)` — одна строка, никаких ветвлений в foundation.

## Size Limit

| Option | Description | Selected |
|--------|-------------|----------|
| `STORAGE_MAX_UPLOAD_BYTES` required env, hard ceiling через pass-through Transform stream | Защита от DoS, runaway uploads | ✓ |
| Нет лимита, полагаемся на S3 provider limits | Меньше конфига | |
| Отложить лимит до user-upload flow | YAGNI | |

**User's choice:** "Лимит нужен в любом случае, как защита". Включаем в scope 22.4, required env-var, проверка через Transform stream с counter.

## Security Model для public bucket

Обсуждено и зафиксировано без явной альтернативной таблицы:
- Anonymous read policy на bucket
- Неугадываемые ключи (UUID v4 = 122 бита)
- TTL отсутствует
- Формат key: `{namespace}/{uuid}/{filename}` — filename в конце чтобы браузер сохранял под human-readable именем
- Чувствительные файлы (PII, finance) — **deferred**, отдельный класс с presigned когда/если понадобится
