## Summary

Phase 999.11 is a **pure deletion phase with runtime verification**. CONTEXT.md (post-discuss-phase 2026-04-19) narrows scope from the originally imagined "audit + cleanup" to Area 1 only — *remove all smoke/test infrastructure for storage endpoints from `apps/gateway`, `apps/parser`, `apps/notifier`*. Audit/canonical-reference/skill-docs work is explicitly deferred to 999.12–999.15.

The orchestrator-supplied task header ("Immediate cleanup + Multi-service audit") is **stale** — it predates the 2026-04-19 discuss-phase narrowing. Research strictly honors CONTEXT.md D-01..D-07. Every finding below maps to an explicit decision or a trivial downstream consequence of one.

The work decomposes into three physical deletion waves plus a verification close: (1) gateway consumer-side (removes REST `/test/*` surface and its gRPC client dependency on backend smoke RPCs), (2) parser backend (removes `RunStorageSmoke` + `CleanupStorageSmoke` proto RPCs and their entire hexagonal stack — ports, services, use cases, commands, constants), (3) notifier backend (same two proto RPCs, but the hexagonal stack is notably thinner — smoke logic lives directly in `test/storage-smoke.controller.ts`, not in `application/services/`), (4) contract regeneration + dual-mode runtime smoke gate. Every downstream file the grep audit surfaces can be mapped to one of these four waves with zero ambiguity.

**Primary recommendation:** Execute in strict consumer→producer order (gateway first, then parser backend, then notifier backend, then regenerate) per D-04, with per-commit `pnpm lint && pnpm build` gate (D-06) and final dual-mode `start:native` + `start:isolated` smoke per `runtime-smoke-verification` skill (D-07). Three scope-boundary questions surfaced during research must be resolved before planning begins (see §Open Questions).

### Pattern 1: Consumer-first deletion

**What:** When removing a cross-service API, delete the consumer side before the producer. This keeps TypeScript compilation green at every intermediate commit.

**When to use:** Any deletion where a typed client (ts-proto, OpenAPI codegen, etc.) bridges two services. Applies verbatim to D-04 commit ordering (gateway → parser backend → notifier backend → contracts regeneration).

**Example (from D-04 ordering):**
```
Commit 1: gateway removes StorageSmokeController + SmokeTestModule import
   → gateway still compiles: ParserServiceClient type still has runStorageSmoke
     (unused, but present — no error)
   → parser/notifier still run: RPC handlers still registered, nobody calls them

Commit 4: parser backend removes RunStorageSmoke method + Service + UseCase + Port + Command
Commit 5: notifier backend removes same
Commit 6: pnpm generate:contracts → ParserServiceClient.runStorageSmoke disappears
   → Nothing references it anymore (gateway already cleaned in commit 1)
```

### Anti-Patterns to Avoid

- **Mega-commit "rip out all test endpoints":** Rejected by D-05. Use atomic per-feature commits.
- **Deleting proto RPCs before consumers:** Breaks typecheck in gateway for as long as any commit bridges the change. Always delete consumer references first.
- **Manual edits to `packages/contracts/src/generated/`:** Generated code. Always regenerate via `pnpm generate:contracts`.
- **Inventing new deletions during implementation:** D-03 explicitly forbids scope expansion. Any architectural issue discovered mid-delete goes to 999.12–15 backlog, not into 999.11 commits.
- **Skipping per-commit static gate:** D-06 mandates `pnpm lint && pnpm build` after each delete commit. Skipping this loses the bisect guarantee that atomic commits were supposed to provide.
- **Skipping the final dual-mode smoke (D-07):** Build+lint don't catch DI resolution errors or route registration regressions. The smoke gate is non-negotiable.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---|---|---|---|
| Runtime verification after DI changes | Custom "curl + grep logs" script | `pnpm start:native` / `pnpm start:isolated` + `curl /health/ready` per `runtime-smoke-verification` skill | Skill codifies 12-step protocol, user memory `feedback_use_package_scripts` mandates pnpm scripts |

**Key insight:** The deletion itself is hand-rolled by nature (no library automates "delete these files from a NestJS codebase"). But *every supporting activity* (regen, verify, commit) has a canonical tool — use it.

## Common Pitfalls

### Pitfall 1: Deleting parser backend before gateway consumer

**What goes wrong:** Gateway's `StorageSmokeController` imports `ParserProto.StorageSmokeResponse` and calls `this.parser.runStorageSmoke({})`. If parser.proto is edited and contracts are regenerated before gateway is cleaned, gateway fails to compile — every intermediate commit is red.

**Why it happens:** Intuition says "delete the backend first, it's the source". For CROSS-SERVICE deletions, the opposite is correct — consumer first.

**How to avoid:** Follow D-04 order strictly: gateway commits (1-3), then parser backend (commit 4), then notifier backend (commit 5), then regen (commit 6). `pnpm lint && pnpm build` after EACH commit per D-06 confirms the green-at-every-boundary invariant.

**Warning signs:** TS2339 "Property 'runStorageSmoke' does not exist on type 'ParserServiceClient'" during interim build.

### Pitfall 2: Assuming notifier has symmetric hexagonal stack to parser

**What goes wrong:** CONTEXT.md D-02 bullet 2 describes notifier backend as "полный структурный аналог parser'а" — but the filesystem contradicts this. Notifier has ONLY `apps/notifier/src/test/storage-smoke.controller.ts` and ONE entry in `notifier.module.ts` `controllers[]`. There are no `application/ports/inbound/run-storage-smoke.port.ts`, no `application/services/*.service.ts`, no `application/use-cases/run-*-smoke-cycle.use-case.ts`.

**Why it happens:** Discuss-phase author extrapolated from parser's shape without verifying notifier structure on disk.

**How to avoid:** Planner MUST read `apps/notifier/src/notifier.module.ts` + `ls apps/notifier/src/application/` before writing the notifier delete plan. If the plan template mechanically copies parser's deletion list and prefixes `apps/notifier/` — it will reference files that don't exist and task execution will fail.

**Warning signs:** `rm: cannot remove 'apps/notifier/src/application/services/run-storage-smoke.service.ts': No such file or directory` during task execution.

### Pitfall 3: The proto regeneration creates 0-RPC NotifierService

**What goes wrong:** Notifier.proto currently has exactly 3 RPCs (HealthCheck + RunStorageSmoke + CleanupStorageSmoke). After removing the two smoke RPCs, only HealthCheck remains. NestJS `@GrpcMethod('NotifierService', 'HealthCheck')` still works — it's a grpc-health-check protocol handler registered independently in `createGrpcServerOptions` (see `packages/foundation/src/external/grpc/grpc-server.factory.ts`). But a reviewer seeing a proto service with only `HealthCheck` may flag it as "dead" and attempt to delete the whole NotifierService block.

**Why it happens:** Confusion between `NotifierService` (the proto-defined application service, which becomes nearly empty) and the `grpc-health-check` protocol (the `grpc.health.v1.Health` service, separately registered — always alive). Both are served by the notifier binary; the latter is what answers `/health/ready` for the gateway.

**How to avoid:** Planner DOCUMENT explicitly in the plan that the HealthCheck RPC in `NotifierService` remains as a stub (returns `HEALTH.GRPC_STATUS_SERVING`) and is structurally redundant with `grpc-health-check`, but is out of scope (no proto surgery beyond smoke removal). Consistent with audience.proto which has its own narrow shape today.

**Warning signs:** Plan task says "delete NotifierService entirely" or "delete notifier.proto" — this is a scope expansion violation (D-03).

### Pitfall 4: `apps/gateway/src/infrastructure/clients/http-smoke/` dangling after deletion

**What goes wrong:** When `apps/gateway/src/test/` is deleted in its entirety per D-01, the ONLY consumer of `HttpSmokeClient` (and its creation-time constants `HTTP_SMOKE_CLIENT`, `HTTP_SMOKE_TARGET_URL`, `HTTP_SMOKE_LOG_CONTEXT` in `apps/gateway/src/infrastructure/clients/http-smoke/`) disappears. The infrastructure-side client becomes an orphan — no NestJS module imports it, no other class references it, it lives only because Phase 24.1 D-24/D-25 preserved it "for a future admin-diagnostic or health-probe phase that may never arrive".

**Why it happens:** Phase 24.1 split the http-smoke concern into two directories so the client could survive the planned deletion of its controller. That split was deliberate; CONTEXT.md D-01 lists `apps/gateway/src/test/http-smoke/` for deletion but is silent on `apps/gateway/src/infrastructure/clients/http-smoke/`.

**How to avoid:** This is an Open Question (OQ-1 below) that MUST be resolved during plan-phase, not deferred. Three paths:
  (a) Delete the infrastructure dir too — extends scope beyond D-01 literal text (violates D-03 if read strictly, but arguably a "trivial downstream consequence" per the D-03 escape hatch of "fix inline if minor")
  (b) Keep it — phase ships orphan code that dist tree-shakers drop anyway, but source tree has dead weight until 999.12+ ("cautionary tale" / audit phase revisits)
  (c) Return the client to `test/` before deletion — regresses Phase 24.1 D-24/D-25 decision
  
  Recommendation: option (a) — delete atomically with the `test/http-smoke/` commit (Commit 2 in D-04 sequence). Zero consumers means ESLint's unused-import and tsc's module resolution both stay green, and leaving orphan infrastructure is a worse cautionary tale than Phase 24.1 foresaw. Flag to user during plan-phase.

**Warning signs:** Post-delete grep `HttpSmokeClient` returns only `apps/gateway/src/infrastructure/clients/http-smoke/` — no other consumer. This is the dangling-code signal.

### Pitfall 5: Forgetting `grpc-client-sanity.ts` references deleted proto types

**What goes wrong:** `apps/gateway/src/test/grpc-client-sanity.ts` imports `NotifierProto` (line 18) and calls `notifier.runStorageSmoke({} as CommonProto.Empty)` (line 58). This file is listed for deletion in D-01 as a separate commit (Commit 3). If D-04 order is followed, this file is deleted BEFORE the proto regeneration (which erases `runStorageSmoke` from the type), so the TS error window is zero.

**Why it happens:** Commit 3 deletes the sanity file; Commit 6 regenerates contracts. Anyone reordering commits without understanding the dependency will see a compile break.

**How to avoid:** D-04 is prescriptive and correct — follow it verbatim. Planner must not reorder for "efficiency".

**Warning signs:** Any plan that places proto regeneration before sanity-file deletion.

### Pitfall 6: Runtime smoke skipped because "only deletion"

**What goes wrong:** "This is just deletion, it can't break anything at runtime" — a classic pre-production tragedy. Deletion of a module from `imports[]` can still silently miss a dangling `providers[]` entry elsewhere, leaving an unresolved DI token error that tsc DOESN'T catch (NestJS DI is runtime-resolved).

**Why it happens:** Underestimating NestJS DI graph complexity; `runtime-smoke-verification` skill ANTI-PATTERN 5 documents the exact same trap.

**How to avoid:** D-07 is non-negotiable. Final commit runs the full dual-mode gate: `pnpm stop:native && pnpm stop:isolated && pnpm build && pnpm lint && pnpm start:native && curl /health/ready && pnpm stop:native && pnpm start:isolated && curl /health/ready && pnpm stop:isolated`.
