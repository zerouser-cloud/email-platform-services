## Stub Preservation Rationale

The 2 throwing stubs in `apps/parser/src/infrastructure/controllers/grpc/parser.controller.ts` (lines 133-143 post-edit) are an **intentional bridge pattern**, NOT a scope reduction or workaround. They exist because:

1. The proto-generated interface `ParserProto.ParserServiceController` (in `packages/contracts/src/generated/parser.ts`) declares `runStorageSmoke(req: CommonProto.Empty): Promise<ParserProto.StorageSmokeResponse>` and `cleanupStorageSmoke(req: ParserProto.CleanupSmokeRequest): Promise<ParserProto.CleanupSmokeResponse>` as REQUIRED methods.
2. The `ParserController` declares `implements ParserProto.ParserServiceController` (line 25) — TypeScript will error TS2420 ("Class ParserController incorrectly implements ParserProto.ParserServiceController") if the methods are absent.
3. The `@ParserProto.ParserServiceControllerMethods()` bulk decorator (line 24) wires `@GrpcMethod` onto ALL proto-declared methods — removing it (the rejected alternative) would silently drop the 6 real methods from the gRPC server too.
4. Plan 04 will run `pnpm generate:contracts` after Plans 02/03 strip the RPC definitions from `packages/contracts/proto/parser.proto`. Once `ParserProto.ParserServiceController` no longer requires the methods, the stubs become safe to delete in the same Plan 04 sweep.

**Runtime risk during the bridge window (Commit 4 → Commit 6):** zero. Plan 01's Commit 1 removed the gateway `StorageSmokeController` that was the sole consumer; nothing routes to these methods. Direct gRPC calls would require internal-network access AND knowledge of method names, and the response is a synchronous error throw with no state mutation or data exfiltration (T-999.11-02-01 in plan threat register, accepted disposition).
