## F-01 — TopologySchema dynamic shape forces 12 × `as {Svc}Env` casts (blocker, L3)

**Problem:** `TopologySchema = z.object(buildTopologyShape())` builds its Zod shape via a dynamic `Record<string, z.ZodType>` loop over `SERVICE`. The resulting type erases key literals, so `z.infer<typeof {Svc}EnvSchema>` cannot resolve all fields statically — forcing every `loadConfig({Svc}EnvSchema)` call-site to cast to the hand-written `{Svc}Env` mapped type (12 cast sites: 6 × `main.ts` + 6 × `*-config.provider.ts`). Root cause of DESIGN I-1.4 + I-4.4 drift.

**Depends on:** —

| Variant | Approach | Pros | Cons | Complexity | Cost (files/commits) | Recommended |
|---------|----------|------|------|------------|----------------------|-------------|
| V1 | Refactor `buildTopologyShape` to a statically-typed overload: declare the shape literal with `as const` key list (driven by `SERVICE` tuple) and use TypeScript mapped types + `z.object` generic narrowing so `z.infer<typeof TopologySchema>` resolves every `{UPPER}_PORT` / `{UPPER}_GRPC_URL` key literally | Kills all 12 casts atomically; `z.infer` becomes the single source of truth (I-1.4 + I-4.4 healed simultaneously); adding a new service to `SERVICE` automatically produces typed fields — no dual-write | Requires mapped-type gymnastics (`{ [K in typeof SERVICE[number]['envKeys']['PORT']]: z.ZodNumber }` etc); TS error messages on `SERVICE` mis-shapes become longer | M | 13 files / 1 commit (`topology.ts` + 6 × `main.ts` + 6 × `*-config.provider.ts`) | ✅ |
| V2 | Delete `TopologySchema`; have each `{Svc}EnvSchema` declare its own `{UPPER}_PORT` / `{UPPER}_GRPC_URL` fields inline via a small per-service helper `topologyFieldsFor([SERVICE.auth, SERVICE.sender])` | Statically typed without mapped-type complexity; per-service schemas become self-contained | Breaks I-4.3 (topology env-key names become hand-typed per service); loses auto-propagation on adding a new service — every consumer schema must be updated manually; higher long-term drift risk | M | 7 files / 1 commit (delete `topology.ts`, update 6 × `{svc}-env.schema.ts`) | — |
| V3 | Keep `TopologySchema` dynamic; delete the `{Svc}Env` hand-written types and use `z.infer<typeof {Svc}EnvSchema>` with an `extends` constraint narrowing through runtime refinement; accept that IDE autocomplete lists only the non-topology fields and casts remain hidden inside the helper | Zero schema churn; existing callers untouched | Doesn't eliminate the cast — hides it one level deeper; I-1.4 remains violated by definition; worse developer experience (no autocomplete on topology fields) | S | 1 file / 1 commit | — |

**Rationale:** V1 is the only variant that satisfies both I-1.4 (static `z.infer`) and I-4.4 (`TopologySchema` produces resolvable types) simultaneously while preserving I-4.3 (envKeys derived from `SERVICE`, never hand-typed). Directly subsumes the scope of ROADMAP backlog Phase 999.1 TopologySchema Static Refactor — see §Backlog Impact. Cascade-aware per DESIGN §5 Principle 4: all 12 call-sites update in one atomic commit. Mapped-type complexity is a one-time cost that pays dividends every time `SERVICE` gains an entry. V2 rejected because it introduces manual env-key duplication (regresses I-4.3). V3 rejected because it merely relocates the cast (doesn't satisfy "no-cast" contract at boundary per I-0.3).

## F-02 — HTTP vendor modules use `deps.env[KEY] as string` × 3 (major, L3)

**Problem:** `httpClientProvider<T, TEnv>` defaults `TEnv` to `Record<string, unknown>`, so `env[key]` is typed as `unknown`. Per-vendor factories (Telegram / AppStoreSpy / CloudFn) extract pre-validated strings via `deps.env[VENDOR_ENV.KEY] as string` — 3 call-sites. The value IS a string at runtime (Zod guarantees it), but TypeScript cannot prove it; the cast is a type-safety hole on already-validated data. Violates I-0.3 (parse-don't-cast) + I-3.4 proposed (narrow ports per vendor).

**Depends on:** F-07 (the `TELEGRAM_ENV.BOT_TOKEN` style key-name constants become dead code once narrow ports exist; fixing F-02 cleanly requires F-07's deletion)

| Variant | Approach | Pros | Cons | Complexity | Cost (files/commits) | Recommended |
|---------|----------|------|------|------------|----------------------|-------------|
| V1 | Introduce 3 narrow ports in foundation — `TELEGRAM_CONFIG_PORT`, `APPSTORESPY_CONFIG_PORT`, `CLOUDFN_CONFIG_PORT` — each with a typed interface (`TelegramConfig`, etc.) re-exported from `packages/config/src/schemas/external-apis.ts`. Each app's `{Svc}ConfigModule.forRoot()` adds a slice-projection factory. Vendor factories inject the narrow port instead of `deps.env` | Healed end-to-end: no casts, no key-name constants, foundation remains service-agnostic (I-3.2), I-3.4 proposed invariant becomes realised canonical; mirrors Phase 999.11.1 D-10 Cache/Persistence/Logging pattern | Touches foundation + config + 3 apps in one coordinated change; requires updating `httpClientProvider` type signature (likely via new overload accepting typed config directly instead of `TEnv`); adds 3 new port files in foundation | M | 12 files / 1 commit (3 × foundation port trios [constants/interfaces/index], `external-apis.ts` re-export, 3 × `{Svc}ConfigModule.forRoot()` slice factory, 3 × vendor `*.module.ts`, 3 × vendor `*.client.ts` constructor) | ✅ |
| V2 | Keep `httpClientProvider` shape; narrow `TEnv` parameter at each vendor module to the exact sliced type: `httpClientProvider<TelegramClient, Pick<NotifierEnv, 'TELEGRAM_BOT_TOKEN' \| 'TELEGRAM_BASE_URL'>>` and let TS infer `env[key]` as the real string type | No foundation changes; per-vendor fix only | Still injects via `deps.env[key]` with bracket-access — dev experience retains the stringly-typed cognitive load; doesn't realise I-3.4 (no narrow port per vendor — foundation still knows `{Svc}Env` shape indirectly); re-introduces the wider dependency on compose-schema shape for each vendor | S | 3 files / 1 commit (one line change per `*.module.ts`) | — |
| V3 | Replace `deps.env[KEY] as string` with an inline Zod parse inside each vendor factory: `TelegramSchema.parse(deps.env).TELEGRAM_BOT_TOKEN`. Zod re-validates at the factory site and produces a proven-string type | No foundation shape change; explicit parse-don't-cast at each site; trivially diff-reviewable | Double-validates (already parsed at `loadConfig`) — wasted cycles at boot; each vendor re-imports Zod schema contract (tight coupling to `@email-platform/config` internals from apps); doesn't realise I-3.4 narrow-port canon | S | 3 files / 1 commit | — |

**Rationale:** V1 is the only variant satisfying DESIGN I-3.4 (proposed invariant locked into canonical by this fix) + I-0.3 (no casts) + I-3.2 (foundation service-agnostic) simultaneously. It aligns the 3 HTTP vendor clients with the 6 existing narrow-port patterns that foundation already owns (Cache / Persistence / Logging / gRPC / StorageCore / PublicStorage — RESEARCH §1.3). Atomic with F-07 cleanup because the vendor `*_ENV` constants become dead code once `deps.env` bracket access disappears (cascade-aware per Principle 4). V2 and V3 are rejected because they only address the type-safety symptom without realising the Level 3 narrow-port contract that the other 6 infra concerns enforce.
