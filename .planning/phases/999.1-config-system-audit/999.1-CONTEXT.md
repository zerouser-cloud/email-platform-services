<domain>
## Phase Boundary

**Docs-only, audit+design phase. Independent scope — не поглощает backlog-фазы превентивно.**

Полная оценка состояния конфиг-системы проекта и проектирование канонической системы, которая правильно покрывает все уровни конфигурации и ложится на Clean/Hexagonal. Результат — не patch-list, а **проектный документ** (DESIGN.md) + findings = drift от design (AUDIT.md) + migration варианты (SOLUTIONS.md).

**5-stage flow (внутри фазы):**
1. **Research** (RESEARCH.md, стандартный артефакт `gsd-phase-researcher`) — глубокое исследование кодбазы + 9 project skills + selected industry patterns. Скан всей конфиг-поверхности: apps/**, packages/**, infra/**, scripts/**, .env*, docker-compose*, Coolify артефакты в git, CI env.
2. **Level taxonomy identification** — researcher предлагает candidate config levels на основе reality; kandidates включают (non-exhaustive): `process.env` runtime, topology/catalog identity data, in-code constants, infra files env, build-time, CLI edge. Формальная locked taxonomy — в DESIGN stage.
3. **Design** (DESIGN.md) — canonical система. Для каждого level: boundary definition, Zod-валидация где применимо, DI-абстракции для consumers, соответствие Clean/Hexagonal. Formal invariants (см. ниже). Migration principles.
4. **Audit** (AUDIT.md) — findings = drift от DESIGN; grouped по 5 ROADMAP layers (Definition/Usage/Violations/Propagation/Missing), severity-classified, evidence inline.
5. **Solutions** (SOLUTIONS.md) — per finding 2-4 варианта migration path с trade-offs, approval placeholders, pre-assigned sub-phase numbers, Backlog Impact секция.

**Architectural invariants (формализуются в DESIGN.md):**
- `apps/**` никогда не читает `process.env` напрямую
- Все config-consumers через DI (`@Inject({SVC}_CONFIG)` или foundation narrow ports — `CacheConfig`, `PersistenceConfig`, `GrpcClientConfig`, `HttpClientConfig`, `StorageConfig`, `LoggingConfig`)
- `process.env` sealed за loader (`packages/config` entry point — `loadConfig()`)
- Не только env vars: любые config-данные на других уровнях (catalog/topology, in-code constants, infra artifacts, CLI edge) тоже должны быть Zod-validated где применимо
- Type-safety без `!` non-null assertions и `as XxxEnv` casts — покрывает «no casting» требование самостоятельно (включает и то, что backlog Phase 999.1 TopologySchema Static Refactor обещал; см. Backlog Impact в SOLUTIONS.md post-audit)
- Layer injection rule (из 999.11.1 D-09): `application/use-cases/**` получают env-values как method args, не через `@Inject`
- Совместимость с `infrastructure/bootstrap/config/` placement (999.11.2 D-08) — bootstrap как framework glue (Uncle Bob Ring 4), не adapter

**В scope:**
- Полная оценка всех config-touching файлов в git-версионированной части проекта
- Level taxonomy как первичная абстракция (не «env vars vs rest»)
- Canonical design covering все levels (app + infra coherence — docker-compose env, Coolify env refs, CI env, `.env`/`.env.docker`/`.env.example` sync)
- Findings для каждого level с cross-ref на violated architectural invariant
- Migration variants (2-4 per finding), design principles, приоритизация через severity
- Все 5 ROADMAP layers (Definition & Loading / Usage tracing / Violations / Propagation / Missing configs)

**НЕ в scope (exclusions):**
- Реализация fix'ов (docs-only; execution — sub-phases 999.1.N post-approval)
- Business-logic config (campaigns/recipients/parser rules — отсутствует в коде; PROJECT.md «без бизнес-логики»)
- Coolify UI state / external-to-git deployment config (вне reach audit)
- Runtime dynamic config / feature flags (в коде отсутствует; всё static через Zod)
- Zod library choice / замена validator'а (Zod закреплён; audit работает в рамках)
- Pre-absorption связанных backlog-фаз (999.1-topology, 999.4, 999.5, ...) — аудит независим; redundancy выявляется post-audit в Backlog Impact секции SOLUTIONS.md
- Тесты (PROJECT.md «без тестов»)
- Изменения в infrastructure credentials/ports (infrastructure-guard skill)

## Implementation Decisions

### Findings methodology (Area 1)

- **D-01: 3-tier severity.** `blocker` = нарушает canonical design или создаёт реальный bug (type-cast, `process.env` утечка в apps, missing config var вызывающий runtime failure). `major` = drift от design, не ломает runtime но создаёт incoherence (convention violation, abstraction leak). `minor` = cosmetic/docs/naming gap. Сигналит reviewer'у что promote'ить в sub-phase первым.
- **D-02: Grouping = 5 ROADMAP layers + severity sub-order.** AUDIT.md structure: 5 крупных секций (L1 Definition & Loading → L2 Usage tracing → L3 Violations → L4 Propagation → L5 Missing configs). Внутри каждой — blocker → major → minor. Читатель сразу видит «что с каким слоем не так».
- **D-03: Rich F-NN template per finding.**
  - `ID` (F-NN flat across phase; например F-01, F-02, …)
  - `Layer` (L1 / L2 / L3 / L4 / L5)
  - `Severity` (blocker / major / minor)
  - `Title` (one-liner)
  - `Evidence` (grep/Read output inline в fenced code-block)
  - `Violated contract` (skill name + D-NN / invariant name)
  - `Impact` (что ломается если не пофиксить)
  - `Solution ref` (cross-ref на SOLUTIONS.md F-NN section)
- **D-04: Evidence inline в AUDIT.md.** Grep/Read output под каждым finding в fenced code-block. Self-contained reader — видит и finding, и proof вместе. Длинный файл, но однопроходный. Executable grep-команды для re-check выносятся в VERIFICATION.md (D-16).

### SOLUTIONS.md format (Area 2)

- **D-05: 2-4 variants per finding, default 3.** ROADMAP явно говорит «2-4 варианта». По умолчанию 3 = recommended + 2 альтернативы. Если < 2 вариантов — finding слишком тривиален для отдельной записи, группируется с соседним.
- **D-06: 7-col trade-off table per finding + rationale.** Колонки: `Variant | Approach | Pros | Cons | Complexity | Cost (files/commits) | Recommended marker`. Под таблицей — 2-4 строки rationale обосновывающих recommended pick. Scan-friendly + decision-complete.
- **D-07: Explicit dependencies per finding.** Поле `Depends on: F-XX, F-YY` в solution metadata если solution F-NN требует другой finding-fix первым. Позволяет planner'у sub-phase'ов заказывать в правильном порядке.
- **D-08: Approval mark inline per finding.** Placeholder в SOLUTIONS.md:
  ```
  **Status:** ☐ Pending review / ☑ Approved (→ 999.1.N) / ☒ Rejected (reason: ...)
  ```
  User проходит SOLUTIONS, переключает checkbox'ы. Single source of truth для approval state.
- **D-09: Pre-assigned proposed sub-phase numbers.** SOLUTIONS.md предлагает «Рекомендуемая группировка approved findings в sub-phases: 999.1.1 (F-01, F-02 склеены), 999.1.2 (F-05), …» с обоснованием per grouping (shared файлы, migration atomicity, test-ability). User подтверждает/перегруппировывает на review — фаза не мутирует ROADMAP сама.
- **D-10: Rejected solutions inline с reason.** User отмечает `☒ Rejected (reason: ...)`. Finding остаётся в SOLUTIONS.md как audit trail — будущий audit увидит «рассматривалось, отклонено по причине X» и не переоткроет идентичный вариант.

### Canonical Config System Design (Area 2b + phase reframe)

- **D-11: DESIGN.md — standalone artifact.** Не inline в SOLUTIONS.md. Самодостаточный документ покрывающий:
  - Level taxonomy (locked, predлoженная researcher в RESEARCH.md)
  - Canonical architectural invariants (см. `<domain>`)
  - Abstraction layers per level (какие Zod schemas, какие DI ports, какие boundary-loaders)
  - Соответствие Clean/Hexagonal (layer injection rules, bootstrap placement, foundation vs apps разделение)
  - Migration principles (general rules для per-finding fix'ов)
- **D-12: Level taxonomy owned by researcher, locked в DESIGN.** `gsd-phase-researcher` сканирует кодбазу и предлагает candidate levels в RESEARCH.md. Taxonomy твердеет в DESIGN stage с учётом architectural principles. User видит обе стадии и может correкт'ить.

### Checkpoint mechanics (Area 3)

- **D-13: 5 финальных артефактов.** `999.1-AUDIT.md` + `999.1-DESIGN.md` + `999.1-SOLUTIONS.md` + `999.1-VERIFICATION.md` + `999.1-SUMMARY.md` (плюс `999.1-RESEARCH.md` — стандартный вывод `gsd-phase-researcher`).
- **D-14: User вручную per approved solution вызывает /gsd:insert-phase** после phase completion. Audit-only boundary остаётся clean — фаза не мутирует ROADMAP. Precedent: ROADMAP Phase 999.1 entry явно говорит «user review checkpoint вне фазы».
- **D-15: Backlog Impact section в SOLUTIONS.md.** Отдельный раздел post-audit: «После approval следующих solutions backlog-фазы становятся redundant: 999.1-topology (покрыт F-NN + DESIGN-invariant), 999.4 CacheService quality (F-NN), 999.5 CacheModule config placement (F-NN), …» с cross-ref на finding IDs и invariants. User на review отмечает cancel/keep per backlog entry. ROADMAP mutation — отдельная операция user'а post-approval.

### Verification discipline (inherited от 999.11.3 D-08 / D-03)

- **D-16: Verify-against-reality + VERIFICATION.md grep-proof table.**
  - *Во время audit:* каждое assertion проверяется grep/Read против реального кода (`apps/**`, `packages/**`, `infra/**`). Research stage использует `gsd-phase-researcher` с явной инструкцией проверять каждое утверждение перед записью.
  - *В конце фазы:* VERIFICATION.md в формате 999.11.2 VALIDATION.md / 999.11.3 VERIFICATION.md — таблица «Invariant / Grep command / Expected count / Observed count / Status + commit hash». Каждая строка executable — будущий reader запускает команду и получает тот же результат.

### Audit scope boundaries (Area 4)

- **D-17: App + infra coherence в scope.** 5 ROADMAP layers покрывают и app-level (Zod schemas в `packages/config`, bootstrap/config/, foundation narrow configs), и infra coherence (docker-compose env references, Coolify env refs в git-versioned файлах, CI env, `.env`/`.env.docker`/`.env.example` sync). Точка пересечения — env var names. НЕ аудируется Coolify UI state (вне git).
- **D-18: Phase independence — no pre-absorption.** 999.1 audit работает самостоятельно по конфиг-системе. Backlog phases (999.1 TopologySchema Static Refactor, 999.4 CacheService quality, 999.5 CacheModule config placement, и другие config-adjacent) НЕ абсорбируются превентивно. Post-audit SOLUTIONS.md Backlog Impact секция (D-15) выявляет какие из них становятся redundant — user решает cancel/keep.
- **D-19: Plan decomposition owned by gsd-planner.** Разбивка на plans делается plan-phase agent'ом на основе RESEARCH.md findings (размер/complexity заранее неизвестны). Precedent 999.11.3 закрепил 2 plans потому что структура была явная; здесь структура возникает после research.
