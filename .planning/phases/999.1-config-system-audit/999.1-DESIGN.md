## 1. Purpose & Scope

This document locks the canonical shape of the email-platform monorepo config system as of the end of Phase 999.11.3 and formalises the architectural invariants that Plans 02-04 of Phase 999.1 use to measure drift, propose migrations, and verify the result. It is derived from `999.1-RESEARCH.md` §§1-2 (inventory + candidate taxonomy) and locks that proposal per CONTEXT.md D-11 + D-12.

**What this doc IS:** a standalone, reusable canonical. It is intentionally scoped to be cross-referenced by every future infra phase that touches config surface — notably the backlog entries for Redis quality, RabbitMQ event plumbing, and any new external-API client. Invariants in this document replace ad-hoc "what does good look like" judgements during those phases with grep-verifiable, skill-linked rules. Promotion to a standalone skill (`.agents/skills/config-system-canon/SKILL.md`) is a deferred idea per CONTEXT.md `<deferred>` — not executed here.

**What this doc IS NOT:** an audit (that is Plan 02 `999.1-AUDIT.md`), a migration plan (Plan 03 `999.1-SOLUTIONS.md`), or a verification log (Plan 04 `999.1-VERIFICATION.md`). It proposes zero fixes. It describes the target shape and the rules that define whether a given piece of code is drift or canonical.

**Docs-only boundary (CONTEXT.md D-14 + infrastructure-guard skill):** Phase 999.1 mutates no code, no ports, no credentials, no docker-compose files, no `.env*` files. The phase produces six markdown artefacts under `.planning/phases/999.1-config-system-audit/` and nothing else. ROADMAP.md and the backlog are mutated ONLY by user-invoked `/gsd:insert-phase` calls after Plan 03 approval checkbox decisions — not by this phase.

**Clean/Hexagonal fit preview.** Config is treated as infra — it enters the system from Level 0 (`process.env` OS boundary) and is projected through Zod validation (Level 1) into DI tokens (Level 2), then further narrowed into concern-specific ports (Level 3). Ring 4 (framework glue) owns Levels 2 and 3; Ring 3 (infra adapters) consumes narrow ports and owns Levels 5 and 6; Ring 2 (application services) never sees config directly except through method arguments; Ring 1 (domain) has zero config awareness. The infrastructure-client-layering skill's Identity / Mechanism / Assembly triad maps cleanly onto Levels 4 / 3 / 2+5. Full treatment in §4.

**Evidence base.** Every "Current state" block in §2 cites file paths and line numbers from `999.1-RESEARCH.md` §1. No claim in this document should be unsupported by a reproducible grep or Read against the workspace. Where RESEARCH §10 flagged a documented CONTEXT.md inaccuracy (`infra/coolify/` directory absence), this DESIGN respects the RESEARCH reality over the CONTEXT.md assertion.

## 2. Level Taxonomy (LOCKED)

The system exposes seven distinct config levels, ordered from most-external (OS boundary) to most-internal (in-code constants and deployment artefacts). Each level has a boundary definition, a current-state description with file-path citations, a set of formalised invariants in `I-{level}.{N}` notation, and an abstraction strategy describing how consumers are expected to access it.

Levels are a taxonomy, not a layered loader: Level 6 (CLI-edge) and Level 7 (infra artefacts) are independent of Level 2 (DI binding) — they consume Level 1 schemas directly or declare values adjacent to Level 0 respectively. The numbering reflects concern-distance from the OS, not runtime load order.

### Level 0: process.env OS boundary

- **Boundary:** The OS-provided `process.env` object. Values arrive from `.env*` files (via `dotenv-cli` wrapping npm scripts), from Docker `env_file:` directives, from image-layer `ENV` directives in the Dockerfile, or from Coolify-injected deploy-time environment. The contract at this level is `Record<string, string | undefined>` with zero type or presence guarantees.
- **Current state (pre-Phase-999.1.8):**
  - Single legal runtime read-site: `packages/config/src/config-loader.ts:18` — inside `loadConfig<T>()` which calls `schema.parse(process.env)` (RESEARCH §1.1, §1.5). **Phase 999.1.8 Plan 04 relocates** this file to `packages/foundation/src/external/config/load-config.ts` (Mechanism in foundation per I-3.5) — cache-by-schema-reference semantics preserved verbatim.
  - Four **illegitimate** command-line-edge read-sites (surfaced as F-15 by re-audit): `apps/{auth,audience,parser,sender}/drizzle.config.ts:4` — each calls `DatabaseSchema.parse(process.env)` directly (RESEARCH §1.4). Previously misclassified as a legal carve-out for command-line tools — 2026-04-21 re-audit retired that carve-out per I-0.1 reworded statement. Phase 999.1.8 Plan 05 migrates these to `loadConfig(DatabaseSchema)`.
  - Total `process.env.*` reads workspace-wide: 5 today; target post-999.1.8 = **1** (the canonical boundary in foundation). Zero reads of `NODE_ENV`, `APP_ENV`, `ENVIRONMENT`, `isDev`, `isProd`, `isDevelopment`, `isProduction` anywhere in `apps/**/*.ts` or `packages/**/*.ts`.
- **Invariants:**
  - **I-0.1 (reworded 2026-04-21 — Phase 999.1.8 Plan 01 amendment; retires the former carve-out that listed five legal read-sites):** `process.env.*` direct reads are allowed in **exactly 1 legal read-site** across the entire monorepo: `packages/foundation/src/external/config/load-config.ts` (post-F-16 adoption — canonical location) or the equivalent pre-reloc path `packages/config/src/config-loader.ts:18` (until Phase 999.1.8 Plan 04 lands). This is the single canonical `loadConfig<T>()` wrapper. **No carve-outs of any kind — including for command-line tools.** `drizzle-kit` runs `drizzle.config.ts` through its own tsx loader, and that script calls `loadConfig(SubSchema)` the same way a NestJS bootstrap does — `loadConfig` is framework-free, requires no NestJS DI, and works identically in every consumer context. Any other read-site is a blocker violation of the sealed-boundary contract. Enforcing skills: `twelve-factor` SKILL.md §"No direct process.env reads in app code" + `env-schema` SKILL.md §"Every env var read must go through the loader". Grep invariant: `grep -rn 'process\.env' apps/` = 0 matches; `grep -rn 'process\.env' packages/` = 1 match (the canonical boundary at `foundation/src/external/config/load-config.ts`). Enforcement phase: Phase 999.1.8 Plan 04 (foundation creation) + Plan 05 (drizzle.config.ts migration × 4) + Plan 07 (verification gate).
  - **I-0.2:** No `NODE_ENV` / `APP_ENV` / `ENVIRONMENT` / `isDev` / `isProd` / `isDevelopment` / `isProduction` name reads anywhere in `apps/**` or `packages/**`. Enforces twelve-factor X (dev/prod parity). Build tools (Node.js, Express internals) MAY read `NODE_ENV` as an ecosystem convention — but app and workspace code MUST NOT. Enforcing skill: `twelve-factor`.
  - **I-0.3:** `process.env` type contract is explicitly untrusted — every downstream use MUST pass the value through `Zod.parse()` or equivalent static validator before consuming. Bypassing via `as string` or `!` non-null assertion on a `process.env.X` read is a blocker violation. Enforcing skill: `env-schema`.
- **Abstraction strategy (post-Phase-999.1.8):** sealed behind the single canonical `loadConfig(schema)` wrapper — runtime AND CLI both route through it. `loadConfig` is framework-free (no NestJS DI), idempotent-cached by schema reference, and works in every consumer context (main.ts bootstrap, bootstrap/config providers, drizzle-kit CLI). Consumers above Level 0 never touch `process.env` directly. No carve-outs.

### Level 1: Zod schema definition

- **Boundary:** Zod schemas describing the expected shape of `process.env` (or a subset relevant to a given consumer) with validation rules (types, min/max, enum, URL). Input: `unknown`. Output: a typed, validated object suitable for DI binding or CLI consumption.
- **Current state:**
  - **Per-concern sub-schemas:** 11 files in `packages/config/src/schemas/` (RESEARCH §1.1): `cors.ts`, `database.ts`, `external-apis.ts` (Telegram + AppStoreSpy + CloudFn), `grpc.ts`, `logging.ts`, `rabbitmq.ts`, `rate-limit.ts`, `redis.ts`, `storage.ts`, plus `index.ts` barrel.
  - **Dynamic topology schema:** `TopologySchema = z.object(buildTopologyShape())` in `packages/config/src/topology.ts:17`. The shape is built at module load by iterating `Object.values(SERVICE)` — dynamic derivation defeats `z.infer` at the type level, which is the root cause of finding V-1 (12 `as {Svc}Env` casts). A hand-written `GlobalTopology` mapped type at `topology.ts:22` compensates but the Zod infer path is broken.
  - **Per-service composed schema:** `{Svc}EnvSchema = composeSchemas(TopologySchema, ...relevant sub-schemas)` in each `apps/{svc}/src/infrastructure/bootstrap/config/{svc}-env.schema.ts` (RESEARCH §1.2 — 6/6 services).
  - **Global composed schema:** `GlobalEnvSchema` in `packages/config/src/env-schema.ts` — dead code post-999.11.1 (RESEARCH §1.8 F-1; zero consumers outside `.planning/**` docs).
  - **Composition primitive:** `composeSchemas(...schemas)` in `packages/config/src/compose.ts:16`. Documentation at source line 14 explicitly states `.refine()` on input schemas is NOT preserved; refines must be applied to the composed output (`gateway-env.schema.ts:23-29` pattern).
- **Invariants:**
  - **I-1.1:** Every env var consumed by apps or foundation MUST appear in exactly one sub-schema in `packages/config/src/schemas/`. No hand-rolled `z.object({ KEY: z.string() })` in `{svc}-env.schema.ts`. Enforces single-source-of-truth for the Zod surface. Enforcing skill: `env-schema`.
  - **I-1.2:** No `.default()`, no `.optional()`, no `z.coerce.boolean()` on any field in any sub-schema. Booleans use `z.string().transform(v => v === 'true')`; numbers use `z.coerce.number()` (safe because `Number("3000")` works correctly). Enforcing skill: `env-schema` SKILL.md §"No Defaults / No Optional / No z.coerce.boolean()".
  - **I-1.3:** Per-service schemas compose ONLY via `composeSchemas(...)` from `packages/config/src/compose.ts` — never by hand-rolling individual `z.object({ ... })` calls in `{svc}-env.schema.ts`. Service-specific refines apply to the composed output. Enforcing skills: `env-schema`, `infrastructure-client-layering`.
  - **I-1.4:** Schema types propagate without casts. `z.infer<typeof {Svc}EnvSchema>` MUST statically resolve all field names. Currently blocked by `TopologySchema` dynamic shape (see V-1). Removing the block is the canonical precondition for eliminating the 12 `as {Svc}Env` casts across `apps/*/src/main.ts` + `apps/*/src/infrastructure/bootstrap/config/*.provider.ts`. Enforcing skill: `infrastructure-client-layering` (identity data shape), `env-schema` (no casts on validated output).
- **Abstraction strategy:** sub-schemas are pure Zod with no NestJS or transport coupling. Per-service composed schemas live inside each app's `bootstrap/config/` slice and are consumed only by the loader factory.

### Level 2: Loading / provisioning (DI binding)

- **Boundary:** The seam where Zod-validated config values enter the NestJS DI container. Input: a Zod schema reference. Output: a `{SVC}_CONFIG` DI Symbol bound to the parsed `{Svc}Env` value, plus `@Global()`-visible narrow `*_CONFIG_PORT` projections.
- **Current state:**
  - `loadConfig<T extends z.ZodType>(schema: T): z.infer<T>` at `packages/config/src/config-loader.ts:14` — cached by schema reference via a module-level `Map<z.ZodType, unknown>` (RESEARCH §1.1). Idempotent; safe to call eagerly at module-definition time.
  - Per-service provider shape: `{svc}ConfigProvider = { provide: {SVC}_CONFIG, useValue: loadConfig({Svc}EnvSchema) as {Svc}Env }` — 6/6 services (RESEARCH §1.2 verification).
  - Per-service module: `@Global() {Svc}ConfigModule.forRoot()` exposes `{SVC}_CONFIG` + the narrow `*_CONFIG_PORT` slice-projection providers required by that service's foundation imports. 6/6 services compliant with 999.11.1 D-08..D-12 + 999.11.2 D-08.
  - `@Global()` decoration is REQUIRED (not optional) per 999.11.1 Plan 10 Rule 3: nested third-party `forRootAsync` modules (`PinoLoggerModule.forRootAsync({ inject: [LOGGING_CONFIG_PORT] })`, `ClientsModule.registerAsync({ inject: [GRPC_CLIENT_CONFIG_PORT] })`, `ThrottlerModule.forRootAsync({ inject: [GATEWAY_CONFIG] })`) run in a nested DI scope that cannot resolve tokens from the root module's own `providers:[]`.
  - `{Svc}ConfigModule.forRoot()` appears FIRST in every root module's `imports:[]` array — before any foundation module (RESEARCH §1.2 verification + nestjs-hexagonal-mapping SKILL.md "Composition root shape after 999.11.2").
- **Invariants:**
  - **I-2.1:** Exactly one `{SVC}_CONFIG` Symbol declaration per service — in `apps/{svc}/src/infrastructure/bootstrap/config/{svc}-config.constants.ts`. Symbol is created via `Symbol('{SVC}_CONFIG')` (project-local uniqueness; no cross-package collision concern). Enforcing skills: `nestjs-hexagonal-mapping`, `no-magic-values`.
  - **I-2.2:** Every `{Svc}ConfigModule` is decorated with `@Global()`. Missing `@Global()` causes boot-time `UnknownDependenciesException: can't resolve Symbol(<CONFIG_PORT>)` for any nested `forRootAsync`. Enforcing skill: `nestjs-hexagonal-mapping` SKILL.md + `infrastructure-client-layering` SKILL.md §Config "Critical: `@Global()` is REQUIRED, not optional."
  - **I-2.3:** `{Svc}ConfigModule.forRoot()` imported FIRST in each root module's `imports:[]` — before any foundation module. Placement under `apps/{svc}/src/infrastructure/bootstrap/config/` per 999.11.2 D-08 canonical tree. Enforcing skill: `nestjs-hexagonal-mapping` SKILL.md "Composition root shape after 999.11.2" + `references/LAYERS.md` §Canonical Tree.
  - **I-2.4:** `{SVC}_CONFIG` used ONLY in `inject:[{SVC}_CONFIG]` of narrow-port projection factories (at Level 3 bootstrap assembly) — NEVER in `@Inject({SVC}_CONFIG)` inside `application/use-cases/**` (use-cases receive env values as method args per 999.11.1 D-09) nor inside `domain/**` (framework-free). Enforcing skills: `clean-ddd-hexagonal`, `nestjs-hexagonal-mapping`; enforced statically by ESLint Override 9 (application isolation — pre-existing).
- **Abstraction strategy:** `{SVC}_CONFIG` is a bootstrap-local intermediate that exists solely to feed narrow-port projection factories. No business-logic class ever injects `{SVC}_CONFIG` directly — consumers depend on Level 3 narrow ports instead. RESEARCH §1.5 confirms zero direct `@Inject({SVC}_CONFIG)` call-sites in app code today (stronger compliance than minimum requirement).

### Level 3: Consumption abstractions (narrow ports)

- **Boundary:** Port interfaces consumers actually depend on. Each port represents exactly one infra concern (cache / persistence / logging / gRPC client / storage core / public storage). Input: a `{Svc}Env` slice. Output: a typed `XxxConfig` narrow interface injected via `<NARROW>_CONFIG_PORT` Symbol.
- **Current state:**
  - Six narrow ports in foundation (RESEARCH §1.3): `CACHE_CONFIG_PORT` (external/cache/cache.constants.ts:7), `PERSISTENCE_CONFIG_PORT` (external/persistence/persistence.constants.ts:7), `LOGGING_CONFIG_PORT` (external/logging/logging.constants.ts:3), `GRPC_CLIENT_CONFIG_PORT` (external/grpc/clients/clients.constants.ts:22), `STORAGE_CORE_CONFIG_PORT` (internal/storage/storage.constants.ts:5), `PUBLIC_STORAGE_CONFIG_PORT` (external/storage/public/public.constants.ts:11).
  - Interface-shape sources split by origin: three ports mirror env-schema shapes 1:1 and re-export via `type { X as Y }` from `@email-platform/config` (cache ← RedisConfig, persistence ← DatabaseConfig, logging ← LoggingConfig). Three ports are foundation-native because they encode derived shape — `GrpcClientConfig` carries `grpcUrls: Record<string, string>` (not a direct env-key mirror), `StorageCoreConfig` carries 6 composed fields, `PublicStorageConfig` carries subset-with-derivation (RESEARCH §1.3 design commentary).
  - Slice-projection factories in apps: `useFactory: (c: {Svc}Env): <NarrowConfig> => ({ ...slice })` — 17 hits across the 6 `{Svc}ConfigModule.forRoot()` registrations (RESEARCH §1.5).
  - External-API HTTP clients (Telegram / AppStoreSpy / CloudFn) currently DO NOT have narrow `*_CONFIG_PORT` symbols — they consume `{Svc}Env` directly via `httpClientProvider<T, TEnv>` with `envToken` cascade, and extract vendor-specific keys via `deps.env[VENDOR_ENV.KEY] as string` (RESEARCH §1.6 V-2, §1.8 F-7 + F-8 cast cluster — 3 call-sites).
- **Invariants:**
  - **I-3.1:** Every infra concern that foundation exposes via `forRootAsync` MUST have a `<NARROW>_CONFIG_PORT` Symbol + narrow interface in `packages/foundation/src/{external,internal}/{concern}/{concern}.constants.ts` + `{concern}.interfaces.ts`. Foundation is service-agnostic: it knows nothing about `SenderEnv` / `AuthEnv` / `ParserEnv` — only the narrow interface. Enforcing skill: `infrastructure-client-layering` SKILL.md §"Three-Layer Rule" + §Config.
  - **I-3.2:** Consumers inside `packages/foundation/src/**` inject ONLY `<NARROW>_CONFIG_PORT` — never `{SVC}_CONFIG`. Foundation stays transport- and service-agnostic. Enforcing skill: `infrastructure-client-layering`.
  - **I-3.3:** Narrow interface shapes live in `packages/foundation/src/{external,internal}/{concern}/{concern}.interfaces.ts`. If the shape is a 1:1 env-schema mirror, re-export via `type { X as Y } from '@email-platform/config'` (single source of truth). If the shape is derived/composed (e.g., `grpcUrls` dictionary, `StorageCoreConfig` 6-field composition), declare inline in foundation. Enforcing skill: `infrastructure-client-layering` SKILL.md §Config D-10 commentary.
  - **I-3.4 (proposed — addresses V-2 / F-7 / F-8):** External-API HTTP clients (Telegram, AppStoreSpy, CloudFn) SHOULD follow the same narrow-port pattern: `TELEGRAM_CONFIG_PORT`, `APPSTORESPY_CONFIG_PORT`, `CLOUDFN_CONFIG_PORT` — each with a typed `TelegramConfig` / `AppStoreSpyConfig` / `CloudFnConfig` interface re-exported from `packages/config/src/schemas/external-apis.ts`. Adoption would eliminate the 3 × `deps.env[KEY] as string` casts (V-2) and make the `VENDOR_ENV` key-name constants (`TELEGRAM_ENV = { BOT_TOKEN: 'TELEGRAM_BOT_TOKEN', ... }`) in `apps/{svc}/.../*-client.constants.ts` redundant (F-8). Enforcing skill: `infrastructure-client-layering` SKILL.md §HTTP. Marked proposed because current state does not comply — Plan 03 SOLUTIONS drives adoption per finding-fix.
  - **I-3.5 (new — added 2026-04-21 Phase 999.1.8 Plan 01; addresses F-16):** Per-service config DI binding is assembled via a foundation-provided factory: `createConfigModule<TEnv>({ schema, token, narrowPorts })`. Each service's `apps/{svc}/src/infrastructure/bootstrap/config/{svc}-config.module.ts` consumes this factory and exports the returned `DynamicModule` as a const (not a class with `static forRoot(): DynamicModule`). Self-assembled `@Global() {Svc}ConfigModule` classes with hand-rolled `forRoot()` static methods are drift. **Symmetry target:** gRPC clients at `packages/foundation/src/external/grpc/clients/define-grpc-client.ts` — the canonical Identity/Mechanism/Assembly reference. Config factory mirrors this shape. **Returned DynamicModule contract:** (a) `global: true` (preserves 999.11.1 Plan 10 Rule 3 fix — nested `forRootAsync({inject: [*_CONFIG_PORT]})` needs root-level narrow-port visibility); (b) `providers: [configProvider, ...narrowPortProviders]` — factory constructs both from `opts.schema` + `opts.narrowPorts`; (c) `exports: [opts.token, ...opts.narrowPorts.map(p => p.port)]`. **Grep invariants:** (a) `grep -rn '@Global()' apps/*/src/infrastructure/bootstrap/config/` = 0 matches (factory encapsulates the decorator); (b) `grep -lE 'createConfigModule\(' apps/*/src/infrastructure/bootstrap/config/*.module.ts` = 6 files; (c) `grep -cE '\w+ConfigModule\.forRoot\(\)' apps/*/src/*.module.ts` = 0 matches. Enforcing skills: `infrastructure-client-layering` SKILL.md §"Three-Layer Rule — Mechanism layer ownership" + `clean-ddd-hexagonal` SKILL.md §"Dependency Inversion" + `no-magic-values` SKILL.md §"Symbol DI tokens" (preserved — `{SVC}_CONFIG` Symbol remains the DI key). Enforcement phase: Phase 999.1.8 Plan 04 (factory creation) + Plan 06 (6-app migration) + Plan 07 (verification gate).
- **Abstraction strategy:** one narrow port per infra concern; app module projects the slice from `{Svc}Env`; foundation consumer is typed end-to-end with no `as` casts or bracket-access key lookups. DI-binding ceremony (`@Global()` decoration, `forRootAsync`-style factory, narrow-port provider construction, exports list) is encapsulated by `createConfigModule()` in foundation per I-3.5 — apps only declare the per-service tuple of identity (schema + token) and narrow-port slice projections.

### Level 4: Service catalog / topology (identity data)

- **Boundary:** In-code data describing "which services exist and what are their runtime identities" — service IDs, ports, gRPC package/service names, DI tokens for cross-service identification. NOT env values, though its KEYS (`{UPPER}_PORT`, `{UPPER}_GRPC_URL`) are the names used as env-key strings at Level 1's `TopologySchema`.
- **Current state:**
  - `SERVICE` const declared in `packages/config/src/catalog/services.ts:3` (RESEARCH §1.1) — 6 entries: auth, sender, parser, audience, gateway, notifier. Each entry is transport-agnostic: `{ id, displayName, port, grpc? (optional — 4 services have gRPC metadata, 2 don't), envKeys, diToken }`.
  - `defineService<const Id>(...)` factory in `packages/config/src/catalog/define-service.ts:1-45` generates `envKeys.PORT = '${UPPER}_PORT'` and `envKeys.GRPC_URL = '${UPPER}_GRPC_URL'` strings at construction time. `diToken = Symbol.for('${id}_CLIENT')` — `Symbol.for` ensures cross-module identity (same key = same symbol).
  - `TopologySchema = z.object(buildTopologyShape())` in `packages/config/src/topology.ts:17` dynamically builds the Zod shape by iterating `SERVICE` at module load. This couples Level 1 to Level 4 — adding a service to `SERVICE` automatically produces its `{UPPER}_PORT` and (if gRPC) `{UPPER}_GRPC_URL` fields in every `{Svc}EnvSchema` that composes `TopologySchema`.
  - Catalog consumption: `apps/*/src/main.ts → createGrpcServerOptions(SERVICE.{svc}, config.PROTO_DIR)` (6/6 services); `defineGrpcClient({ service: SERVICE.auth, clientToken: SERVICE.auth.diToken })` in foundation gRPC client module registrations (Phase 999.7.x canonical — referenced in infrastructure-client-layering skill).
- **Invariants:**
  - **I-4.1:** `SERVICE` is the SOLE source of service identity. Service IDs, HTTP ports, gRPC package names, gRPC service names are not duplicated anywhere else in the workspace — not in `*-constants.ts`, not in `.env*`, not in infra YAML. Enforcing skill: `infrastructure-client-layering` SKILL.md §"Token Classification" + §Decision Tree.
  - **I-4.2:** Catalog stays transport-agnostic: `SERVICE.xxx.diToken` is OK (public service identity); `SERVICE.xxx.grpcToken` / `httpToken` / `rmqToken` are NOT OK (transport-specific tokens belong in foundation, derived via `Symbol.for(`${service.id}_<KIND>`)`). Enforcing skill: `infrastructure-client-layering` SKILL.md §"Anti-Pattern 1 — Transport token in catalog".
  - **I-4.3:** Topology env-key name strings are DERIVED (never manually typed) from `SERVICE` via `defineService` → `envKeys`. Adding a new service automatically produces its env-key names. Hand-writing `'AUTH_GRPC_URL'` outside the catalog is a drift signal. Enforcing skill: `infrastructure-client-layering` SKILL.md §"Application by Infra Type — gRPC" + Phase 999.7.x reference.
  - **I-4.4:** `TopologySchema` MUST produce types that `z.infer` can resolve statically. Currently blocked because `buildTopologyShape()` is dynamic — this directly blocks I-1.4 and is the root cause of the 12 `as {Svc}Env` casts (V-1). Resolution typically requires either refactoring `buildTopologyShape` to a statically-typed overload or switching to a mapped-type approach with compile-time field projection. Enforcing skill: `infrastructure-client-layering`; blocks removal of the cast cluster in Plan 03 SOLUTIONS.
- **Abstraction strategy:** `SERVICE` is imported directly by code that needs identity data (main.ts gRPC bootstrap; defineGrpcClient in foundation); `TopologySchema` is auto-composed into every `{Svc}EnvSchema` via `composeSchemas(TopologySchema, ...)`. No per-service topology hand-rolling.

### Level 5: In-code constants (per-service + foundation)

- **Boundary:** Named constants that are NOT env-driven — they encode policy, naming, behaviour that is owned by the code. Categories: DI Symbols (port tokens, config tokens), enum-style `as const` groupings (status strings, header names, bucket names), domain defaults (pagination, timeouts not driven by env). Standalone from Level 0 — no env read path.
- **Current state:**
  - Per-service domain-port Symbols: `apps/{svc}/src/{svc}.constants.ts` × 5 (gateway deleted per 999.11.2 D-11a). Each file contains domain-port Symbols (`LOGIN_PORT`, `CAMPAIGN_REPOSITORY_PORT`, ...) + domain defaults (`PAGINATION_DEFAULTS`). Notifier has 2 lines (minimal); audience has 20 (largest). Purpose: cross-folder DI tokens consumed by both `infrastructure/inbound/grpc/` controllers and `infrastructure/outbound/persistence/` repositories. See nestjs-hexagonal-mapping SKILL.md §"File-path reference table" row "Cross-folder DI tokens".
  - Foundation cross-cutting: `packages/foundation/src/external/constants.ts` — exports `HEADER`, `SERVER`, `CORS`, `CONTEXT_TYPE`, `HTTP_ERROR`, `LOG_STATUS`, `BOOTSTRAP` as-const objects; plus per-concern `{concern}.constants.ts` files per foundation module (Symbol DI tokens, `REDIS_DEFAULTS.KEEP_ALIVE_MS`, `CB_DEFAULTS`, etc.).
  - Per-vendor HTTP client constants: `apps/{parser,sender,notifier}/src/infrastructure/outbound/http-clients/{vendor}/*-client.constants.ts` × 3. Contents: DI Symbols (`TELEGRAM_CLIENT`, `APPSTORESPY_CLIENT`, `CLOUDFN_CLIENT`), **env-key-NAME constants** (`TELEGRAM_ENV = { BOT_TOKEN: 'TELEGRAM_BOT_TOKEN', CHAT_ID: 'TELEGRAM_CHAT_ID' } as const`), log-context strings, paths, header names. The env-key-name constants are a known duplicate source of truth with `packages/config/src/schemas/external-apis.ts` (F-8) — both files declare "what keys Telegram expects".
- **Invariants:**
  - **I-5.1:** No unnamed literals except allowed exceptions per `no-magic-values` SKILL.md — type literals, import paths, 0/1/-1 idioms, log messages (human-readable, not identifiers), `process.exit(0 | 1)`. Every bare config number or identifier-string MUST be extracted to an `as const` object. Enforcing skill: `no-magic-values`.
  - **I-5.2:** DI tokens use `Symbol(...)` (apps-local uniqueness) or `Symbol.for(...)` (cross-module canonical identity — used in catalog for `diToken` and in gRPC-client derived tokens). NEVER string literals. Enforcing skill: `no-magic-values` SKILL.md §"Pattern 2 — Symbol Tokens for DI Injection".
  - **I-5.3:** Related constants group in a single `as const` object with UPPER_SNAKE_CASE keys. One object per concept (`PG_POOL_DEFAULTS`, `HEADER`, `REDIS_DEFAULTS`). Do NOT scatter related values across multiple single-value exports. Enforcing skill: `no-magic-values` SKILL.md §"Pattern 1 — as const Object".
  - **I-5.4 (addresses F-8):** Env-key NAME constants (e.g., `TELEGRAM_ENV.BOT_TOKEN = 'TELEGRAM_BOT_TOKEN'`) MUST NOT duplicate key-name information already typed in a Zod sub-schema. If a narrow `*_CONFIG_PORT` per vendor is adopted (I-3.4), the vendor-ENV key-name constants become dead code and their removal is coupled to I-3.4 adoption. Enforcing skill: `no-magic-values` (anti-pattern: two sources of truth for the same identifier set) + `infrastructure-client-layering` (Level 3 narrow port eliminates the need).
- **Abstraction strategy:** constants live closest to their consumer. Foundation cross-cutting → `packages/foundation/src/external/constants.ts`. Per-service domain ports → `apps/{svc}/src/{svc}.constants.ts`. Per-infra concern → `packages/foundation/src/{.../concern/}{concern}.constants.ts`. Per-vendor HTTP client → `apps/{svc}/.../{vendor}-client.constants.ts`. No duplicate sources of truth across scopes.

### Level 6: CLI-edge / build-time config

## 4. Clean/Hexagonal Fit

The seven levels map cleanly onto Uncle Bob's rings and Alistair Cockburn's primary/secondary adapter split, with the `infrastructure-client-layering` skill's Identity / Mechanism / Assembly triad providing the catalog/foundation/apps layer split within Ring 4.

**Ring 4 — framework glue (Uncle Bob).** Level 2 (DI binding via `{Svc}ConfigModule` at `apps/{svc}/src/infrastructure/bootstrap/config/`) + Level 3 (narrow-port projection factories via `useFactory: (c: {Svc}Env) => ({...slice})`). Both live inside the `bootstrap/` sub-bin of the canonical Phase 999.11.2 `infrastructure/inbound|outbound|bootstrap` direction-split tree — `bootstrap/` is explicitly NOT an adapter (Cockburn) but is framework-composition-root material. Per `nestjs-hexagonal-mapping` SKILL.md: "NestJS primitives that live in Ring 4 framework glue: `@Global()` modules, `forRoot` / `forRootAsync` factories, `APP_FILTER` / `APP_INTERCEPTOR` registrations, config modules". The `{SVC}_CONFIG` Symbol is a Ring-4 intermediate; it exists ONLY so that Ring-4 slice-projection factories can produce Ring-3-consumable narrow-port values.

**Ring 3 — infrastructure adapters (Cockburn secondary/driven + primary/driving).** Level 5 per-vendor constants (e.g., `TELEGRAM_ENV`, `APPSTORESPY_ENV`, `CLOUDFN_ENV` in `apps/{svc}/src/infrastructure/outbound/http-clients/{vendor}/{vendor}-client.constants.ts`) + Level 6 CLI edge (`drizzle.config.ts` is adapter-analogous: it runs outside the NestJS container but implements the "run migrations against the DB" secondary-adapter role). Per `clean-ddd-hexagonal` SKILL.md: "Infrastructure → Application → Domain. Dependencies point INWARD only. Outer layers depend on inner layers, never the reverse." Ring 3 consumes Ring 4's narrow-port projections and adapts them to the underlying external system (Postgres/Redis/RabbitMQ/Telegram/AppStoreSpy).

**Ring 2 — application services / use-cases.** NEVER sees config directly. Application services (in `apps/{svc}/src/application/services/`) may inject `{SVC}_CONFIG` because they are the seam between env data and business orchestration (999.11.1 D-09). Use-cases (in `apps/{svc}/src/application/use-cases/`) are STRICTLY env-agnostic — they receive env values as method arguments from their parent service (`execute(cmd, { timeout: this.config.OPERATION_TIMEOUT_MS })`). I-2.4 enforces this boundary; ESLint Override 9 provides static enforcement. The rationale (from `clean-ddd-hexagonal` SKILL.md §"The Dependency Rule" + `nestjs-hexagonal-mapping` SKILL.md §"Composition root shape"): use-cases must remain reusable across contexts; coupling them to env via DI makes them context-specific.

**Ring 1 — domain entities / value objects.** Zero config awareness. Pure TypeScript, no `@nestjs/*`, no `@grpc/*`, no proto, no `drizzle-orm`, no `pg`. ESLint Override 8 enforces domain isolation (pre-existing, Phase 999.10 Plan 06). Domain entities have no concept of "environment" — they represent business invariants that are identical in dev, staging, and production. This is twelve-factor X (dev/prod parity) applied at the innermost ring: the domain IS the parity contract.

**Infrastructure-client-layering fit.** The `infrastructure-client-layering` SKILL.md Three-Layer Rule maps onto the level taxonomy:
- **Identity (catalog, `packages/config`):** Level 4 `SERVICE` const — what a service IS (id, public diToken). Transport-agnostic. Catalog NEVER imports foundation.
- **Mechanism (foundation, `packages/foundation`):** Level 3 narrow-port Symbols + interfaces (`CACHE_CONFIG_PORT`, `PERSISTENCE_CONFIG_PORT`, `GRPC_CLIENT_CONFIG_PORT`, `STORAGE_CORE_CONFIG_PORT`, `PUBLIC_STORAGE_CONFIG_PORT`, `LOGGING_CONFIG_PORT`) + factory functions (`defineGrpcClient`, `httpClientProvider`, `LoggingModule.forGrpcAsync`). Foundation is service-agnostic.
- **Assembly (apps, `apps/{svc}`):** Level 2 `{SVC}_CONFIG` Symbol + `{Svc}ConfigModule = createConfigModule({ schema, token, narrowPorts })` (post-999.1.8 — declarative factory call; @Global() scope encapsulated inside the factory per I-3.5). Level 5 per-service domain-port Symbols + per-vendor HTTP client constants. Apps assemble identity from catalog + mechanism from foundation (including the `createConfigModule` + `loadConfig` pair) + local naming + environment-scoped composition.

## 5. Migration Principles

These principles govern how Plan 03 SOLUTIONS.md authors migration variants per finding and how Plan 04 VERIFICATION.md validates the final state. They are consumable in isolation — a future infra phase that promotes a DESIGN drift to a sub-phase uses the same principles.

1. **Every drift gets ≥ 2 variants per CONTEXT.md D-05.** SOLUTIONS.md MUST provide a recommended variant plus at least one alternative for each finding. Rationale: variants make trade-offs explicit (complexity vs. cascade blast radius vs. migration atomicity) and let the user approve the recommended option informed, rather than rubber-stamp. Rejected variants remain in SOLUTIONS.md as audit trail per D-10 — future audit sees "variant X was considered and rejected because Y" and does not re-propose it.

2. **Atomic commit per finding-fix.** Each approved solution translates into ONE commit (or one bisect-safe group of commits) when executed in its assigned sub-phase. Sub-phase groupings share ≥ 1 of: file-coupling (F-NN and F-MM both edit `packages/config/src/topology.ts`), migration atomicity (F-NN's fix breaks runtime if F-MM isn't applied simultaneously), test-ability (same grep-invariant set), or semantic coherence (all Level 3 narrow-port additions belong together). CONTEXT.md D-09 owns the grouping criterion taxonomy.

3. **Behaviour-preserving.** Phase 999.1 sub-phase migrations are docs-only or refactor-only — no business logic, no tests (PROJECT.md `<constraints>` "без бизнес-логики, без тестов"). Runtime behaviour MUST match pre-migration for every approved solution. Where a variant genuinely changes behaviour (e.g., strict-mode Zod rejecting unknown env keys that previously passed through silently), the variant MUST be flagged in SOLUTIONS.md trade-off column "Cons" and the user's approval is treated as informed consent for the behaviour change.

4. **Cascade-aware.** When a narrow-port shape changes, ALL projection call-sites update atomically in the same commit. The canonical cascade for this phase: V-1 (12 `as {Svc}Env` casts) → I-4.4 (static topology inference) → I-1.4 (schema types without casts). Fixing V-1 requires refactoring `buildTopologyShape` to a statically-typed form; the fix cascades through all 12 call-sites (6 × main.ts + 6 × `*-config.provider.ts`) AND unlocks type-safety for any future narrow-port that pulls from `TopologySchema`. Partial cascades are disallowed — either the whole chain moves or none of it does.

5. **Infra read-only during audit.** Per `infrastructure-guard` skill: Phase 999.1 is read-only across ports, docker-compose, credentials, and `.env*` files. SOLUTIONS variants that require infra mutations (e.g., "add GARAGE_ADMIN_TOKEN to `.env`" or "wire `scripts/check-env-parity.sh` into `.github/workflows/ci.yml`") MUST be flagged "user-approval required at sub-phase execution time". The sub-phase executor then applies `infrastructure-guard` SKILL.md §"Pre-Change Checklist" when the user approves. Standard ports (5432, 6379, 5672, 9000, 50051-50054) are preserved unconditionally.

6. **Verify-against-reality.** Every DESIGN invariant claim and every AUDIT finding MUST be grep-verifiable against the codebase at AUDIT-execution commit. VERIFICATION.md (Plan 04) captures the exact `bash` one-liners + expected counts + observed counts + commit hash per row; this is the 999.11.2 VALIDATION / 999.11.3 VERIFICATION precedent adapted to audit-phase specifics (CONTEXT.md D-16). Paraphrased or approximately-correct commands break the "reader reproduces the result" contract and are not acceptable.

- **`@nestjs/config` reintroduction.** The library was removed in Phase 999.11.1 Plan 09 due to three structural problems documented in `infrastructure-client-layering` SKILL.md §Config "Why not `@nestjs/config`": (1) `configService.get<T>(KEY)!` returns `T | undefined` forcing non-null assertions, (2) `ConfigService` was global and imported in foundation (layer violation), (3) dual-path `AppConfigModule.forRoot(XxxEnvSchema)` + `XxxEnv` type (naming confusion). The current per-service `{SVC}_CONFIG` Symbol + `@Global() {Svc}ConfigModule` + narrow foundation ports pattern is the canonical replacement; reintroducing `@nestjs/config` is not a candidate.
