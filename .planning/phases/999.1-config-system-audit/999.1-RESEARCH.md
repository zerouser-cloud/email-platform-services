## Project Constraints (from CLAUDE.md)

Treat these with the same authority as locked D-NN decisions. Planner MUST verify no plan contradicts any of them.

1. **No magic values** (`.agents/skills/no-magic-values/`) — `Symbol()` DI tokens, `as const` config constants. Allowed: type literals, import paths, 0/1/-1 idioms, log messages, `process.exit(0|1)`.
2. **No switch/case chains, no if/else chains (3+ branches)** (`branching-patterns/`) — use Record dispatch, Map + fallback, canHandle, or polymorphism.
3. **No environment branching** (`twelve-factor/`) — never read `NODE_ENV`, `isDev`, `isProd`. App consumes config VALUES (LOG_LEVEL, DATABASE_URL), never environment IDENTITIES.
4. **No infrastructure changes without user approval** (`infrastructure-guard/`) — no port / docker-compose / credential / connection-string mutations. **Audit is read-only.**
5. **No defaults or optionals in env schemas** (`env-schema/`) — no `.default()`, no `.optional()`, no `z.coerce.boolean()`. No fallbacks in consumer code (`?? value`, `|| value`).
6. **Infrastructure-client layering** (`infrastructure-client-layering/`) — Identity (catalog) / Mechanism (foundation) / Assembly (apps). Catalog transport-agnostic, foundation service-agnostic.
7. **bootstrap/config placement** (`nestjs-hexagonal-mapping/`) — Config artefacts live under `infrastructure/bootstrap/config/` per Uncle Bob Ring 4 framework glue.
8. **Runtime smoke verification** (`runtime-smoke-verification/`) — NOT applicable to this phase (docs-only, no runtime gate).
9. **PROJECT.md constraints** — no business logic, no tests, tech stack locked (NestJS 11, TypeScript, gRPC, PostgreSQL, RabbitMQ, Redis), architecture Clean/DDD/Hexagonal in `apps/**`, utility structure in `packages/**`.
10. **GSD workflow enforcement** — no direct edits outside a GSD phase.

## Overview

This research answers: *"What does the planner need to know to structure AUDIT / DESIGN / SOLUTIONS / VERIFICATION / SUMMARY work across plans?"*

The findings are deliberately **preliminary sighting reports** — the actual AUDIT.md is produced during plan execution, not here. But a surprising amount of ground truth can be established up-front: the Canonical Config Access Contract from Phase 999.11.1 D-08..D-12 + the `bootstrap/config/` placement from Phase 999.11.2 D-08 are **already green across the board**. That narrows the expected audit findings to a specific, well-bounded set.

**The phase's value is not "find huge violations"** — the Canonical Config Access Contract is already clean. The phase's value is:

1. **Formalise a level taxonomy** that generalises the current pattern to non-env config (catalog identity, in-code constants, infra artefacts, CLI edge) — which today has no unifying abstraction.
2. **Enumerate the narrow drift** (TopologySchema `as XxxEnv` casts × 12, three `as string` casts on HTTP env reads, single missing env key in `.env`, stale pre-999.11 tooling, dead `GlobalEnvSchema`, Dockerfile env injection competing with `.env.docker`).
3. **Propose migration solutions** per finding (2-4 variants) so user can promote each to a sub-phase independently.
4. **Produce a reusable DESIGN.md** that subsequent infra phases (999.12 Redis, 999.13 RabbitMQ) can cross-reference.

**Primary recommendation:** 4 plans — (1) AUDIT, (2) DESIGN, (3) SOLUTIONS, (4) VERIFICATION + SUMMARY merged. Dependencies: DESIGN needs RESEARCH level taxonomy; AUDIT needs DESIGN invariants to measure drift against; SOLUTIONS needs AUDIT findings; VERIFICATION + SUMMARY close the gate. See §4 for rationale.

**Key exports and runtime entry points:**

- `composeSchemas(...schemas)` — flat merge via `z.object(shape spread)`; does NOT preserve `.refine()` on input schemas (documented in source line 14).
- `TopologySchema = z.object(buildTopologyShape())` — dynamic shape built at module load from `Object.values(SERVICE)`; defeats `z.infer` at the type level; fixed via manually-written `GlobalTopology` type (topology.ts L22).

**Source-of-truth observations:**
- `zod` is the only runtime dependency (`packages/config/package.json:11`). `@nestjs/common` peer — no direct NestJS coupling.
- `config-loader.ts` uses a module-level `Map<z.ZodType, unknown>` cache so `useValue: loadConfig(schema)` at module-definition time is safe — one eager call per schema reference.

### 1.4 CLI edge (drizzle-kit × 4)

**Verified:** `find apps -maxdepth 3 -name 'drizzle.config.ts'` → 4 files; full Read of auth + parser.

4 services expose drizzle-kit config: auth / audience / parser / sender. All four follow the canonical Phase 999.11.1 D-07 pattern:

import { DatabaseSchema } from '@email-platform/config';
import { defineConfig } from 'drizzle-kit';

**Surprising positive finding:** the only consumers of `{SVC}_CONFIG` Symbol are the `useFactory(c: {Svc}Env)` binders inside the `*ConfigModule` itself. **No controller, service, use-case, repository, or adapter injects `{SVC}_CONFIG` directly** — everything consumes the narrow `*_CONFIG_PORT` projection. This exceeds the Phase 999.11.1 D-09 rule (which only prohibits `@Inject({SVC}_CONFIG)` in `application/use-cases/**`). The system is cleaner than the minimum requirement.

**Implication for DESIGN.md:** the `{SVC}_CONFIG` Symbol is effectively a **private intermediate** used only during bootstrap slice-projection. DESIGN.md should formalise whether this should remain a DI Symbol (current) or could become a pure function call — and on which principle.

**Implication for AUDIT.md Layer 2:** the audit plan's usage tracing should focus on (a) *foundation-internal* narrow-port consumption (verified above); (b) *cascade* paths like `httpClientProvider` where `envToken` brings in the full `{Svc}Env`; (c) direct `main.ts` reads for bootstrap (`config.PROTO_DIR`, `config.{SVC}_PORT`, `config.CORS_ORIGINS`, `config.CORS_STRICT`).

## 2. Candidate Config Level Taxonomy

**Authored by researcher per D-12.** Locked in DESIGN.md (researcher + planner + user review).

Seven levels proposed, ordered from most-external (OS boundary) to most-internal (in-code naming). Each level has a **boundary definition** (what enters / leaves), **current state** with evidence, **invariants** to formalise in DESIGN.md, and an **abstraction strategy** for consumers.

### Level 0: `process.env` OS boundary

- **Boundary:** The OS-provided `process.env` object. Enters the runtime from `.env*` files (via `dotenv-cli` wrapping npm scripts), from Docker `env_file`, or from Coolify-injected environment. Is by definition `Record<string, string | undefined>` with zero guarantees.
- **Current state:**
  - Single legal read-site in runtime: `packages/config/src/config-loader.ts:18 → schema.parse(process.env)` (verified grep).
  - Four legal CLI read-sites: `apps/{auth,audience,parser,sender}/drizzle.config.ts:4 → DatabaseSchema.parse(process.env)` (verified).
  - Zero other reads in `apps/**/*.ts` or `packages/**/*.ts`. Zero `NODE_ENV`/`isDev` branches.
- **Invariants (proposed for DESIGN.md):**
  - I-0.1: `process.env.*` direct reads ONLY in `packages/config/src/config-loader.ts` (runtime) and `drizzle.config.ts` × 4 (CLI). Any new read-site is a blocker violation.
  - I-0.2: No NODE_ENV / APP_ENV / ENVIRONMENT name reads anywhere in `apps/**` or `packages/**`. Twelve-factor X.
  - I-0.3: `process.env` type contract is explicitly untrusted — must pass through `Zod.parse()` before any downstream use.
- **Abstraction strategy:** sealed behind `loadConfig()`. Consumers never touch Level 0 directly.

### Level 1: Zod schema definition

- **Boundary:** Zod schemas that describe the expected shape of `process.env` (or subset) with validation rules (types, min/max, enum). Input: `unknown`. Output: typed validated object.
- **Current state (verified):**
  - **Per-concern sub-schemas** × 11 in `packages/config/src/schemas/` — Database, Redis, Rabbit, Storage, Logging, Grpc, Cors, RateLimit, Telegram, AppStoreSpy, CloudFn.
  - **Dynamic topology schema:** `TopologySchema = z.object(buildTopologyShape())` in `topology.ts:17`. Derives fields from `SERVICE` catalog at module load.
  - **Per-service composed schema:** `{Svc}EnvSchema = composeSchemas(TopologySchema, ...relevant sub-schemas)` in each `apps/{svc}/src/infrastructure/bootstrap/config/{svc}-env.schema.ts`.
  - **Global composed schema:** `GlobalEnvSchema` in `packages/config/src/env-schema.ts` — dead code (see F-1).
  - **Composition primitive:** `composeSchemas(...schemas)` at `compose.ts:16` — does NOT preserve `.refine()` on inputs; must apply refine after composition.
- **Invariants (proposed):**
  - I-1.1: Every env var consumed by apps MUST appear in exactly one sub-schema in `packages/config/src/schemas/` (enforces single source of truth for Zod surface).
  - I-1.2: No `.default()`, no `.optional()`, no `z.coerce.boolean()` on any field in a sub-schema (env-schema skill).
  - I-1.3: Per-service schemas compose ONLY from sub-schemas + `TopologySchema` — never hand-roll individual `z.object({ ... })` calls in `{svc}-env.schema.ts`.
  - I-1.4: Schema types propagate without casts: `z.infer<typeof {Svc}EnvSchema>` MUST resolve field names statically. (Currently blocked by `TopologySchema` dynamic shape — see V-1.)
- **Abstraction strategy:** sub-schemas are pure Zod, imported by per-service composed schemas. No runtime dependency on NestJS or transport.

### Level 2: Loading / provisioning (DI binding)

- **Boundary:** The seam where validated config values enter the DI container. Input: Zod schema. Output: `{SVC}_CONFIG` DI Symbol bound to the parsed value.
- **Current state (verified):**
  - `loadConfig<T>(schema)` in `config-loader.ts:14` — schema-idempotent cache (Map by schema reference), safe to call eagerly at module-definition time.
  - Per-service provider: `{svc}ConfigProvider = { provide: {SVC}_CONFIG, useValue: loadConfig({Svc}EnvSchema) as {Svc}Env }` — 6/6 services (grep verified).
  - Per-service module: `@Global() {Svc}ConfigModule.forRoot()` exposes `{SVC}_CONFIG` + narrow `*_CONFIG_PORT` projections — 6/6 services.
  - `@Global()` required per 999.11.1 Plan 10 Rule 3 (nested `forRootAsync` scopes can't walk up without it).
- **Invariants:**
  - I-2.1: Exactly one `{SVC}_CONFIG` Symbol per service; declared in `{svc}-config.constants.ts`.
  - I-2.2: Every `{Svc}ConfigModule` is `@Global()`. Required for nested `PinoLoggerModule.forRootAsync` / `ClientsModule.registerAsync` / `ThrottlerModule.forRootAsync` visibility.
  - I-2.3: `{Svc}ConfigModule.forRoot()` imported FIRST in root module's `imports:[]` — precedes every foundation module.
  - I-2.4: `{SVC}_CONFIG` used in `inject:[{SVC}_CONFIG]` of narrow-port projection factories — never in `@Inject` in business classes (`application/use-cases/**`).
- **Abstraction strategy:** `{SVC}_CONFIG` is a bootstrap-local intermediate; consumers of actual config values use Level 3 narrow ports.

### Level 3: Consumption abstractions (narrow ports)

- **Boundary:** The port interfaces that consumers actually depend on. Each port represents ONE infra concern (cache / persistence / logging / gRPC / storage). Input: `{Svc}Env` slice projection. Output: typed `XxxConfig` narrow interface.
- **Current state (verified):**
  - Six narrow ports in foundation: `CACHE_CONFIG_PORT`, `PERSISTENCE_CONFIG_PORT`, `LOGGING_CONFIG_PORT`, `GRPC_CLIENT_CONFIG_PORT`, `STORAGE_CORE_CONFIG_PORT`, `PUBLIC_STORAGE_CONFIG_PORT`.
  - Interface shapes: 3 mirror env-schema shapes (`CacheConfig = RedisConfig`, `PersistenceConfig = DatabaseConfig`, `LoggingConfig`); 3 are foundation-native (`GrpcClientConfig`, `StorageCoreConfig`, `PublicStorageConfig`) because they encode cross-cutting shape (e.g. `grpcUrls: Record<string, string>`) that does not map 1:1 to any env schema.
  - Apps project slices: `useFactory: (c: {Svc}Env): NarrowConfig => ({ ...slice })` — 17 hits across 6 services.
- **Invariants:**
  - I-3.1: Every infra concern that foundation exposes via `forRootAsync` must have a `<NARROW>_CONFIG_PORT` symbol + narrow interface. Foundation is service-agnostic; apps own the slice projection.
  - I-3.2: Consumers inside foundation only inject `<NARROW>_CONFIG_PORT` — never `{SVC}_CONFIG` (foundation doesn't know about services).
  - I-3.3: Narrow interface shapes live in `packages/foundation/src/{external,internal}/{concern}/{concern}.interfaces.ts`. If the shape is a 1:1 mirror of a sub-schema output, re-export via `type { X as Y } from '@email-platform/config'` (single source of truth). If the shape is derived (e.g. `grpcUrls` dictionary), declare inline in foundation.
  - I-3.4 (new — proposed): External-API HTTP clients (Telegram, AppStoreSpy, CloudFn) SHOULD follow the same pattern: `TELEGRAM_CONFIG_PORT`, `APPSTORESPY_CONFIG_PORT`, `CLOUDFN_CONFIG_PORT` — replaces F-7 / F-8 / V-2 cast cluster. Currently ad-hoc with `deps.env[KEY] as string`.
- **Abstraction strategy:** narrow port per concern; app module projects slice; foundation consumer is typed end-to-end.

### Level 4: Service catalog / topology (identity data)

- **Boundary:** In-code data describing "which services exist and what are their runtime identities" — ports, gRPC packages, DI tokens for cross-service identification. NOT env values, though its keys (`{UPPER}_PORT`, `{UPPER}_GRPC_URL`) are names USED as env keys at Level 1.
- **Current state (verified):**
  - `SERVICE` const in `packages/config/src/catalog/services.ts:3` — 6 entries. Transport-agnostic identity (`id`, `displayName`, `port`, `grpc?`, `envKeys`, `diToken`).
  - `defineService(...)` factory in `define-service.ts` generates `envKeys.PORT = '${UPPER}_PORT'` and `envKeys.GRPC_URL = '${UPPER}_GRPC_URL'` strings at construction time.
  - `TopologySchema = z.object(buildTopologyShape())` dynamically builds the Zod shape by iterating `SERVICE` at module load — coupling Level 1 to Level 4 at runtime.
  - Consumer: `apps/*/src/main.ts → createGrpcServerOptions(SERVICE.{svc}, config.PROTO_DIR)` (grep verified); `defineGrpcClient({ service: SERVICE.auth, clientToken: SERVICE.auth.diToken })` in foundation.
- **Invariants:**
  - I-4.1: `SERVICE` is the ONLY source of service identity — service IDs, ports, gRPC service names are not duplicated elsewhere.
  - I-4.2: Catalog stays transport-agnostic per infrastructure-client-layering skill: `SERVICE.xxx.diToken` OK; `SERVICE.xxx.grpcToken` / `httpToken` NOT OK.
  - I-4.3: Topology env-key names are derived (not manually typed) from `SERVICE` via `defineService` → `envKeys`. Adding a new service automatically produces its env-key names.
  - I-4.4: `TopologySchema` must produce types that `z.infer` can resolve statically (currently blocked — see V-1). This unlocks removing the 12 `as XxxEnv` casts.
- **Abstraction strategy:** `SERVICE` is imported directly by code that needs identity; `TopologySchema` auto-composed into every `{Svc}EnvSchema`.

### Level 5: In-code constants (per-service + foundation)

- **Boundary:** Named constants that are NOT env-driven but encode policy, naming, behaviour. Types: DI Symbols, enum-style `as const` objects, pagination defaults, header names, bucket identifiers.
- **Current state (verified):**
  - `apps/{svc}/src/{svc}.constants.ts` × 5 (gateway deleted per 999.11.2 D-11a): each contains domain-port Symbols (LOGIN_PORT, CAMPAIGN_REPOSITORY_PORT, ...) + PAGINATION_DEFAULTS. Notifier has the smallest (2 lines); audience largest (20 lines).
  - `packages/foundation/src/external/constants.ts` — cross-cutting `HEADER`, `SERVER`, `CORS`, `CONTEXT_TYPE`, `HTTP_ERROR`, `LOG_STATUS`, `BOOTSTRAP` as-const objects.
  - Per-infra constants files in foundation: `{concern}.constants.ts` × ~10 — Symbol DI tokens, defaults (`REDIS_DEFAULTS.KEEP_ALIVE_MS`, `CB_DEFAULTS`, etc.).
  - Per-vendor HTTP client constants: `apps/{svc}/.../{vendor}-client.constants.ts` × 3 — DI Symbols, ENV key-name constants (e.g. `TELEGRAM_ENV = { BOT_TOKEN: 'TELEGRAM_BOT_TOKEN', ... }`), log-context strings, paths, header names.
- **Invariants:**
  - I-5.1: No unnamed literals except allowed exceptions (type literals, import paths, 0/1/-1 idioms, log messages, `process.exit`). `no-magic-values` skill.
  - I-5.2: DI tokens use `Symbol(...)` (apps) or `Symbol.for(...)` (cross-module / catalog-derived). Never string literals.
  - I-5.3: Related constants group in a single `as const` object with UPPER_SNAKE_CASE keys. One object per concept.
  - I-5.4: Env-key NAME constants (e.g. `TELEGRAM_ENV.BOT_TOKEN = 'TELEGRAM_BOT_TOKEN'`) should not duplicate what's already typed in a Zod sub-schema (F-8). If narrow `*_CONFIG_PORT` per vendor is adopted (I-3.4), these become dead code.
- **Abstraction strategy:** constants live closest to their consumer; foundation cross-cutting; apps service-local; vendor-specific per-client.

### Level 6: CLI-edge / build-time config

- **Boundary:** Config consumed outside the NestJS runtime — drizzle-kit at migration time, Docker build args at image-build time, build-info generation at build time.
- **Current state (verified):**
  - `drizzle.config.ts` × 4 (auth/audience/parser/sender): `DatabaseSchema.parse(process.env)` inline; validates on `drizzle-kit` invocation. Canonical Phase 999.11.1 D-07 pattern.
  - Dockerfile build args: `APP_NAME` (per-service matrix), `BUILD_COMMIT` / `BUILD_BRANCH` (injected by CI into `build-info.json`), `NODE_VERSION=20-alpine` default.
  - `packages/foundation/src/external/build-info.ts`: reads `build-info.json` from `process.cwd()` at first call; silently falls back to `LOCAL_BUILD_INFO` constant if file absent (soft violation of no-fallbacks rule — F-6).
- **Invariants:**
  - I-6.1: Every CLI-edge env read uses the SAME Zod schema as the runtime — never `process.env.DATABASE_URL!` direct read with non-null assertion.
  - I-6.2: Build-args injected into env vars at image layer (e.g. `ENV PROTO_DIR=...`) MUST match the value in `.env.docker` for the same key (avoid duplicate source-of-truth — F-4).
  - I-6.3: Build-time artefacts (`build-info.json`) have Zod schema if code parses them structurally.
- **Abstraction strategy:** pattern-identical to runtime (Zod `.parse`), but direct (no DI available).

### Level 7: Infra artefacts (git-versioned deployment config)

- **Boundary:** Files in `infra/**` + `.github/**` + root compose/env files that reference the same env-key names as Level 1 schemas — but from a different angle (as env-file keys, compose `${VAR}` interpolation, CI secret names).
- **Current state (verified):**
  - `.env` / `.env.docker` / `.env.example` / `.env.docker.example` — 4 env files, 3 tracked by git (committed `.example`s); `.env` and `.env.docker` gitignored.
  - `docker-compose.prod.yml` (root) + `infra/docker-compose.{yml,infra.yml,dev-ports.yml,webui-ports.yml}` (4 files). Env var refs via `env_file` directive + shell-level `${VAR:-default}` interpolation.
  - `infra/docker/app.Dockerfile` — `ENV NODE_ENV=production` + `ENV PROTO_DIR=/app/proto` at image layer.
  - `.github/workflows/ci.yml` + `docker-build.yml` — CI env via `env:` block (TURBO_SCM_BASE) + GitHub Secrets (`${{ secrets.COOLIFY_* }}`).
  - `scripts/check-env-parity.sh` — Phase 24.1 tooling for key-set diff across env files. Runs comparisons but does NOT include `.env.example` (F-3).
  - `infra/coolify/` — **does NOT exist** in current tree (CONTEXT.md claim incorrect).
- **Invariants:**
  - I-7.1: Key sets across `.env` / `.env.docker` / `.env.example` / `.env.docker.example` are identical. Values differ per context. (Currently: `.env` drifts by 1 key — see Layer 5 preview.)
  - I-7.2: No env-key name appears in an `infra/**/*.yml` / `Dockerfile` that is NOT also in a Zod sub-schema. "If it's referenced in infra, it's validated at boot."
  - I-7.3: Dockerfile `ENV` directives do not duplicate values set by `env_file` in the compose stack that uses that image (F-4).
  - I-7.4 (optional / discretion): the env-parity check script runs in CI as a gate.
- **Abstraction strategy:** infra artefacts are *external* to the Zod schema surface but MUST respect the same key-set contract.

### Cross-level relationships

```
Level 7 (infra files) ─supplies─▶ Level 0 (process.env)
Level 0 (process.env) ─input to─▶ Level 1 (Zod sub-schemas)
Level 1 (Zod schemas) ─validated by─▶ Level 2 (loadConfig at DI bootstrap)
Level 2 ({SVC}_CONFIG) ─projected to─▶ Level 3 (narrow *_CONFIG_PORT)
Level 3 (narrow ports) ─consumed by─▶ foundation / apps providers

Level 4 (SERVICE catalog) ─feeds into─▶ Level 1 (TopologySchema auto-compose)
Level 4 (SERVICE catalog) ─consumed by─▶ apps/main.ts + foundation gRPC

Level 5 (in-code constants) ─standalone, no env dependency

Level 6 (CLI edge) ─parallel to Level 2─▶ reads process.env directly via Zod schema
```

This taxonomy is the starting point for DESIGN.md §"Level Taxonomy". Planner may refine labels / splits — the evidence for each is tight enough that the substance should not move.

## 3. Industry Patterns

### 3.1 Twelve-Factor III (Config)

**Canonical source:** [12factor.net III. Config](https://12factor.net/config). Codified locally in `.agents/skills/twelve-factor/SKILL.md`. Key rules:
- Store config in env (not files or code).
- Strict separation: if config could vary between deploys, it's env; if it never varies, it's code.
- No environment IDENTITIES (NODE_ENV / APP_ENV) in code — only VALUES (LOG_LEVEL, DATABASE_URL).

**Current system complies fully** (verified: 0 `NODE_ENV` reads in apps; 0 `process.env.*` outside legal zones; `@nestjs/config` removed; no `isDev`/`isProd` branches).

### 3.2 NestJS DI for config (post-`@nestjs/config` era)

**Reference:** local Phase 999.11.1 removed `@nestjs/config` entirely because:
1. `configService.get<T>(KEY)!` returns `T | undefined` — forced `!` everywhere.
2. `ConfigService` was global and imported in foundation — broke catalog/foundation/apps layering.
3. Dual-path `AppConfigModule.forRoot(XxxEnvSchema)` + `XxxEnv` type created naming confusion.

**Canonical replacement:** per-service `{SVC}_CONFIG` Symbol + `@Global() {Svc}ConfigModule.forRoot()` + typed `useValue: loadConfig({Svc}EnvSchema) as {Svc}Env` + narrow foundation `*_CONFIG_PORT` slice projections. Phase 999.11.1 D-08..D-12.

**Industry parallels:** this pattern is conceptually equivalent to Spring Boot's `@ConfigurationProperties` + `@EnableConfigurationProperties` but derived from Zod instead of reflection. See also:
- [`lostfictions/znv`](https://github.com/lostfictions/znv) — Zod-for-env wrapper with coercers; we essentially implement the same contract inline via `z.coerce.number()` + `z.string().transform(v => v === 'true')`.
- [BrightCoding 2025 guide](https://www.blog.brightcoding.dev/2025/12/17/the-ultimate-zod-playground-test-your-schema-validation-in-seconds-2025-guide) — `strict()` mode to reject extra env keys; we do not currently use strict (extra keys silently pass through Zod's default `strip` behaviour). Candidate for DESIGN.md invariant consideration.

### 3.3 Multi-source precedence (Go viper, Rust figment, Node dotenv)

**Go viper** (https://github.com/spf13/viper): explicit precedence `flag > env > config file > key/value store > default`. Multiple sources composable; keys resolved lazily.

**Rust figment** (https://docs.rs/figment): provider-based stacking (`Env::prefixed` + `Toml::file` + `Json::file`); later providers override earlier. "Layered config" model.

**Node dotenv-flow / dotenv** (https://github.com/motdotla/dotenv): single-source file resolution based on convention (`.env.local` > `.env.{NODE_ENV}` > `.env`).

**Our system** deliberately picks a **single source** (`process.env` at boot, fed by one `--env-file` via `dotenv-cli` or docker-compose) + **single validation layer** (Zod). Multi-source precedence is OUT of scope per PROJECT.md "1 server, Coolify". Industry refs are useful for DESIGN.md to document the rejected-alternatives matrix ("we could do X, we chose Y, because Z").

### 3.4 Zod beyond env-var validation

**Pattern:** Zod schemas for any structurally-shaped input that crosses a trust boundary. Current uses in the codebase:
- `DatabaseSchema.parse(process.env)` — runtime + CLI edge.
- `JSON.parse(raw) as BuildInfo` in `build-info.ts` (F-6) — cast instead of `BuildInfoSchema.parse(raw)`. Candidate for Zod application.
- `SERVICE` catalog is validated by TypeScript alone (not Zod) — `defineService<const Id>(...)` overload ensures shape at compile time. Arguably sufficient (compile-time > runtime for hand-authored code), but DESIGN.md could explore whether a `ServiceSchema` Zod equivalent makes sense for future dynamic catalog entries (e.g. loaded from a file).
- `GlobalTopology` typed via hand-written mapped type (topology.ts:22) — Zod output type can't be inferred due to dynamic shape.

**Industry pattern:** [Mingyang Li, Medium 2024](https://mingyang-li.medium.com/validating-environment-variables-like-a-pro-using-zod-in-node-js-1287f81c8350) — Zod for env is the standard; `strict()` mode is idiomatic for "fail fast on unknown keys". Consideration for I-1 invariant.

### 3.5 Secrets handling (git-legal vs runtime-inject)
