## §A — Survey Methodology + Sources Opened

### A.1 Метод

Это **design-research**, не survey-validate. Алгоритм:

1. **Фетчинг канонических первоисточников.** Для каждой компании из user-mandated списка (Google, Amazon, Netflix, Bazel, Buck2, Spotify, Etsy, GitHub, плюс anchor 12-Factor + chainguard distroless) — открывать engineering blog / official docs / paper / talk transcript, **не tutorials, не AI summaries, не listicles**.
2. **Per-source структурированное извлечение** через `extraction_methodology` блок: для каждого source — список архитектурных принципов, mechanism, rationale, universality, citation.
3. **Cross-source convergence analysis.** Принцип, на котором сходятся ≥5 of 8 named sources → universal. 3-4 → tendency (с пометкой dissensus). 1-2 → outlier / company-specific.
4. **Empirical decoupling criteria extraction.** Не trust user's hypothesis (replaceability / failure isolation / testability / cognitive load). Извлекать криterii из real practice: что MAANG explicitly motivates как separation rationale в их engineering writing.
5. **Design from criteria.** Layer count N, layer boundaries, per-layer SoT — derive из validated criteria, не из user's draft 6 layers, не из Vercel's Dockerfile shape.
6. **Validation.** Каждый layer pass через extracted criteria; failure case → re-design or accept с явным cost/benefit.

## §B — Architectural Principles Extracted Per Source

### B.1 — 12-Factor App, Factor V (Build/Release/Run)

```yaml
source: 12-Factor App
material_type: official methodology doc (Heroku, ratified 2011, still canonical)
url: https://12factor.net/build-release-run
fetched_via: WebFetch (this session)

architectural_principles:
  - principle: 'Three-stage strict separation: Build / Release / Run'
    mechanism: 'Build = code → executable bundle; Release = build + config; Run = launch processes against release'
    rationale: |
      Direct quote: "It is impossible to make changes to the code at runtime, since
      there is no way to propagate those changes back to the build stage."
      Plus: "the run stage should be kept to as few moving parts as possible, since
      problems that prevent an app from running can cause it to break in the middle
      of the night when no developers are on hand."
    universality: MAANG-canonical (anchor for 11+ years; cited by every named MAANG source)
    citation: https://12factor.net/build-release-run §"V. Build, release, run"

  - principle: 'Build is heavyweight; Run is minimal'
    mechanism: 'Build phase tolerates complexity (developers debug it); Run phase must be near-zero-moving-parts'
    rationale: 'Errors are always in the foreground for a developer at build-time; runtime errors are 3am pages'
    universality: MAANG-canonical
    citation: same page

  - principle: 'Release artifact is immutable + uniquely identified'
    mechanism: 'Each release has unique ID (timestamp / version number); never modify a release'
    rationale: 'Auditing, rollback, traceability'
    universality: MAANG-canonical
    citation: same page

decoupling_criteria_in_use:
  - criterion: 'Time-of-error proximity to developer'
    operational_definition: 'Build-time error = developer present; runtime error = no developer'
    citation: same page

  - criterion: 'Direction of change propagation'
    operational_definition: 'Code can flow from build to release to run, never backward — runtime modifications cannot reach build stage'
    citation: same page
```

### B.2 — Bazel (S-02 concepts + S-03 basics)

```yaml
source: Bazel — Hermeticity
material_type: official Bazel docs (Google open-source build system)
url: https://bazel.build/concepts/hermeticity + https://bazel.build/basics/hermeticity
fetched_via: WebFetch (this session)

architectural_principles:
  - principle: 'Hermetic build = same input always produces same output'
    mechanism: |
      "Isolating the build from changes to the host system" (verbatim).
      Treating tools as source code: "Hermetic build systems treat tools as source code.
      They download copies of tools and manage their storage and use inside managed file trees."
    rationale: 'Reproducibility, troubleshooting, parallel execution, multiple-version coexistence'
    universality: MAANG-canonical (Google + Meta-Buck2 + cited by Spotify, Netflix in adjacent contexts)
    citation: https://bazel.build/concepts/hermeticity

  - principle: 'Sandbox-per-action — declared inputs only'
    mechanism: |
      "Each action runs in an execroot that contains only declared inputs and explicit
      tool files, so compilers and linkers cannot accidentally read random files on the
      host or reach out to the network by accident." (Tweag summary, validates Bazel doc claim)
    rationale: "Non-hermeticity sources include 'system binaries that differ across hosts (such as /usr/bin binaries, absolute paths, system C++ compilers)' — sandbox closes this gap"
    universality: MAANG-canonical (Google's primary mechanism; Buck2 inherits)
    citation: https://bazel.build/concepts/hermeticity

  - principle: 'Reproducibility is consequence of hermeticity, not separate axis'
    mechanism: 'Same source + same env + same instructions → bit-identical artifacts'
    rationale: 'Verifiable provenance; security boundary; rollback safety'
    universality: MAANG-canonical
    citation: https://bazel.build/basics/hermeticity §"Multiple builds + Reproducibility"

decoupling_criteria_in_use:
  - criterion: 'Host-system independence'
    operational_definition: 'Build output insensitive to libraries/tools installed on host machine'
    citation: same page

  - criterion: 'Declared inputs vs implicit reads'
    operational_definition: |
      Hermeticity violations enumerated: "Actions or tooling that create files
      non-deterministically", "System binaries that differ across hosts",
      "Writing to the source tree during the build"
    citation: https://bazel.build/concepts/hermeticity (failure modes section)
```

### B.3 — Google SRE Book (Release Engineering)

```yaml
source: Google SRE Book — Release Engineering
material_type: book chapter (Google official)
url: https://sre.google/sre-book/release-engineering/
fetched_via: WebFetch (this session)

architectural_principles:
  - principle: 'Four release-engineering philosophies'
    mechanism: |
      (1) Self-Service Model: "teams must be self-sufficient" + "individual teams can
          decide how often and when to release new versions"
      (2) High Velocity: "frequent releases result in fewer changes between versions"
      (3) Hermetic Builds: "Build tools must allow us to ensure consistency and
          repeatability" — "identical results occur on different machines using known
          versions of build tools"
      (4) Enforcement of Policies: "Multiple security layers control who performs
          operations" including "Approving source code changes" and "Deploying a new release"
    rationale: 'Scale (thousands of teams), reliability (no human bottleneck), security (separated approvals)'
    universality: Google-canonical; partial echo at Amazon/Netflix
    citation: https://sre.google/sre-book/release-engineering/

  - principle: 'Three-stage tooling separation: Build / Release / Deploy (NOT Build/Release/Run)'
    mechanism: |
      Direct attribution to specific tools:
      - Building: "Blaze compiles binaries and runs unit tests"
      - Release: "Rapid orchestrates the workflow, manages branches/cherry-picks,
                 and packages artifacts via MPM"
      - Deployment: "Rapid handles simple deployments; Sisyphus (an SRE framework)
                    manages complex rollouts with finer control on how the rollout is performed"
    rationale: 'Different concerns (compile vs orchestrate vs roll out) → different tools → different teams own each'
    universality: Google-canonical; Netflix mirrors with Nebula/Bakery/Spinnaker triad
    citation: same page

  - principle: 'Config-as-code, in primary repo, reviewed alongside binaries'
    mechanism: |
      "Strict code review requirement" + storing "configuration in our primary source code repository"
      + "treating configs like binaries through MPM packaging and versioning alongside their corresponding binary releases"
    rationale: 'Auditability, rollback, single source of truth'
    universality: MAANG-canonical
    citation: same page

decoupling_criteria_in_use:
  - criterion: 'Concern boundary = tool boundary'
    operational_definition: 'Compile concern (Blaze) ≠ release packaging (Rapid) ≠ rollout choreography (Sisyphus). Each concern gets its own tool.'
    citation: same page

  - criterion: 'Self-service capability'
    operational_definition: 'Teams release without filing tickets — automation owns the path, not humans'
    citation: same page
```

### B.4 — AWS Builders' Library (Automating safe hands-off deployments)

```yaml
source: AWS Builders' Library
material_type: official AWS canonical publication
url: https://aws.amazon.com/builders-library/automating-safe-hands-off-deployments/
fetched_via: WebFetch (this session)

architectural_principles:
  - principle: 'Pipeline = four named stages, source → build → test → prod'
    mechanism: 'Pre-production stages (alpha, beta, gamma) precede prod; prod uses staggered waves (low-traffic region first, single AZ at a time)'
    rationale: 'Blast radius isolation'
    universality: AWS-canonical; mirrored conceptually at Google (Sisyphus rollouts)
    citation: https://aws.amazon.com/builders-library/automating-safe-hands-off-deployments/

  - principle: 'Compiled artifact is immutable + checksummed'
    mechanism: |
      "When the build is complete, the compiled code is packaged and signed."
      "Packages are immutable and use a checksum to verify their integrity."
    rationale: "Same artifact deployed across all environments → reproducibility; rollback uses 'the container image, AWS Lambda function deployment package, or internal deployment package that was previously deployed'"
    universality: MAANG-canonical (12-Factor V, Bazel hermetic, Google Rapid all converge)
    citation: same page

  - principle: 'Build phase distinct, pre-deploy'
    mechanism: '"In the build stage, the code is compiled and unit tested." Compilation + unit tests complete BEFORE artifact moves to test environments.'
    rationale: 'Test environments should never see un-built code; promotion is artifact-only, not source-code re-build'
    universality: MAANG-canonical (12-Factor V violation prohibition)
    citation: same page

  - principle: 'Auto-rollback on alarm'
    mechanism: '"The deployment system actively monitors an alarm to determine if it needs to automatically roll back a deployment."'
    rationale: 'Run-stage problems should not require human in the loop; system reverts to known-good immutable artifact'
    universality: AWS-canonical; Netflix Spinnaker has equivalent
    citation: same page

decoupling_criteria_in_use:
  - criterion: 'Artifact immutability + checksum at every boundary'
    operational_definition: 'Boundary X→Y receives signed checksummed artifact from X; Y NEVER rebuilds, only consumes'
    citation: same page

  - criterion: 'Blast-radius isolation'
    operational_definition: 'Deploy fails in one AZ/region must not affect others; pipeline waves enforce this'
    citation: same page

  - criterion: 'Code review = pre-build gate'
    operational_definition: '"All changes going to production start with a code review and must be approved by a team member before merging into the mainline branch."'
    citation: same page
```

### B.7 — Buck2 (Why + Architecture + Glossary)

```yaml
source: Buck2 — official Meta open-source docs
material_type: official Meta docs (3 pages combined)
urls:
  - https://buck2.build/docs/about/why/
  - https://buck2.build/docs/developers/architecture/buck2/
  - https://buck2.build/docs/concepts/glossary/
fetched_via: WebFetch + WebSearch (this session)

architectural_principles:
  - principle: 'Daemon ≠ Client architecture'
    mechanism: |
      "The Buck2 CLI runs in a client process, which sends commands to the Buck2 daemon
      via gRPC. The daemon goes through several phases after receiving a request from
      the client."
      Daemon definition: "The Daemon process lives between invocations and is designed
      to allow for cache reuse between Buck2 invocations, which can considerably speed
      up builds."
    rationale: 'Client invocation is short-lived; daemon retains compiled-graph state across invocations → cache hits'
    universality: Meta-canonical; Bazel has parallel concept (server/client)
    citation: https://buck2.build/docs/developers/architecture/buck2/

  - principle: 'Action = atomic unit, hermetic, cacheable'
    mechanism: |
      Action definition: "An individual, cacheable, ideally hermetic command that's run
      during the build. It takes artifacts as inputs and produces other artifacts as outputs."
    rationale: 'Atomicity enables remote execution + caching + parallel scheduling'
    universality: MAANG-canonical (Bazel "action graph" predates; Buck2 inherits + unifies)
    citation: https://buck2.build/docs/concepts/glossary/

  - principle: 'Rules separated from binary (language-agnostic core)'
    mechanism: 'Rules written in Starlark (deterministic Python subset); binary (Rust) is language-agnostic. C++/Rust/Python rules have no privileged internal access — all must use the same primitives.'
    rationale: "Adding a new language doesn't require modifying the build-system core"
    universality: Buck2-canonical (departure from Buck1 monolith); Bazel rules-as-data echoes
    citation: https://buck2.build/docs/about/why/

  - principle: 'Remote execution first'
    mechanism: '"Buck2 is remote execution first—local execution is considered a special case of remote execution." "Directory hashes can be pre-computed ready to send to remote execution."'
    rationale: 'Cluster-scale builds dominate at Meta scale; local optimization without RE-first design produces wasteful local-prep code'
    universality: Meta-specific design; Bazel has remote execution but not "first"
    citation: https://buck2.build/docs/about/why/

  - principle: 'Single dependency graph (DICE), not phased target/action graph'
    mechanism: '"Buck2 is not phased — there are no target graph/action graph phases, just a series of dependencies in a single graph on DICE that result in whatever the user requested."'
    rationale: 'Avoids redundant work; enables cross-phase parallelism; precise change tracking'
    universality: Buck2-specific (Bazel still phased); architectural improvement claim
    citation: https://buck2.build/docs/about/why/

decoupling_criteria_in_use:
  - criterion: 'Daemon lifecycle independent of CLI invocation'
    operational_definition: 'Daemon outlives CLI; CLI is thin gRPC client'
    citation: https://buck2.build/docs/developers/architecture/buck2/

  - criterion: 'Action atomicity = caching boundary = parallelism boundary'
    operational_definition: 'Each action declares inputs/outputs; identical (input,command) → cache hit'
    citation: https://buck2.build/docs/concepts/glossary/
```

### E.1 — Choosing N (Number of Layers)

- **12-Factor:** 3 layers (Build / Release / Run)

### E.4 — Layer Boundary Artifacts (Canonical Handoff)

| Boundary | Artifact handed across                                      | Mutability                                      |
| -------- | ----------------------------------------------------------- | ----------------------------------------------- |
| L1 → L2  | Workspace tree + lockfile                                   | Read-only at L2                                 |
| L2 → L3  | `dist/**` directories per workspace + populated turbo cache | Read-only at L3                                 |
| L3 → L4  | OCI image digest pushed to registry                         | Immutable (digest = checksum)                   |
| L4 → L5  | Deployed image (running container)                          | Immutable (rollback = redeploy previous digest) |
| L5 → out | PASS/FAIL signal                                            | Decision artifact                               |

This matches AWS/Netflix/Google canonical "immutable artifact at every boundary" (U-01).

## §G — Coupling Classification

### G.1 — Harmful Coupling (must break — empirical evidence)

The 5 failure modes from Iterations 3-6 mapped to layer-boundary violations:

| Iteration      | Failure                                            | Layers tangled                                                                                                                                       | Coupling type                                                                    | Mitigation                                                                                                                                   |
| -------------- | -------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Iter 3         | Orphan fetcher BuildKit DAG-pruning                | L2 (turbo prune scope) leaked into L3 (Dockerfile assumed fetcher would run)                                                                         | **Harmful** — L3 made assumption about L2's behavior that wasn't enforced        | D-08 Wave 3 fix removed orphan stage; canonical L3 should never reference L2 internals                                                       |
| Iter 4         | TS5083 missing tsconfig.base.json                  | L1 (workspace shape) leaked through L3 (Dockerfile rewrite dropped COPY)                                                                             | **Harmful** — L3 had to maintain a mirror of L1 root files; two sources of truth | Pattern E (D-09) — moved tsconfig.base.json into workspace dep graph; turbo prune now traverses it natively. **Canonical fix.**              |
| Iter 5         | TTY abort on pnpm prune                            | L1 (pnpm CLI behavior post-10.16) leaked into L3 (Dockerfile inherits TTY assumption)                                                                | **Harmful** — L3 had to know L1's TTY-detection internal                         | D-10 ENV CI=true (workaround). **Canonically resolves: drop pnpm prune via Path 3 (pnpm deploy --legacy).**                                  |
| Iter 6         | husky lifecycle re-run on prune                    | L1 (host-dev sub-concern: prepare script) leaked into L3 (Docker prune triggered prepare)                                                            | **Harmful — same axis as Iter 5** — L3 inherits L1 lifecycle script side-effects | Boundary fence: `ENV HUSKY=0` per husky-canonical guidance (S-13) **OR** drop pnpm prune via Path 3 (eliminates the re-run trigger entirely) |

**Pattern in harmful coupling:** **Every single iteration failure was a leak across the L1 ↔ L3 boundary.** Not L2↔L3 (orchestration↔packaging) directly, not L3↔L4 (packaging↔pipeline), not L4↔L5 (pipeline↔verification). The architectural lesson:

> **L1 ↔ L3 is the boundary that requires the strongest fence. L2 sits between them as an orchestrator but does NOT shield against L1 leaks — L3 must defend its own boundary.**

### G.3 — Coupling not present in current architecture (good!)

What this layer architecture EXPLICITLY does not couple:

- L1 → L4: Workspace shape changes do not trigger pipeline workflow changes (workflows invoke pnpm scripts only)
- L2 → L4: Turbo config changes do not trigger pipeline changes (workflows invoke `pnpm turbo run`)
- L3 → L5: Dockerfile changes do not trigger verify-script changes (verify scripts target image digest, not Dockerfile internals)
- L1 → L5: Source changes do not trigger verify-script changes (verify scripts test runtime behavior, not source structure)

These NON-couplings are the substitutability wins. Loss of any of these would be a regression to harmful-coupling territory.

## §H — Edge Cases Per Layer

Comprehensive (not sampled) catalogue of edge cases per layer, with industry-incident citations where applicable.

### H.1 — L1 Source Edge Cases

| EC-01 | Lockfile drift between dev and CI | DEV: `pnpm install` updates lockfile silently in some configs; CI uses `--frozen-lockfile`. Mitigation: `--frozen-lockfile` mandatory in CI; pre-commit gate ensures lockfile committed. **Project status:** addressed (CI workflows use `--frozen-lockfile`). |
| EC-02 | Workspace package added but not in dep graph | Adding `packages/foo/` without consumer declaring `"@scope/foo": "workspace:*"` → turbo prune skips it. **Project incident:** Pattern E (Iteration 4) — exactly this happened with tsconfig.base.json. **Mitigation:** ensure every workspace package has at least one declared consumer. |
| EC-03 | Lifecycle script fails in CI on `pnpm install` | `prepare: husky` runs even with `--prod` (pnpm issue #7068). **Project incident:** Iteration 6. **Mitigation:** `ENV HUSKY=0` (canonical per S-13) OR gate prepare script with `process.env.CI` check. |
| EC-04 | Stale lockfile after dep update outside pnpm | If a dep is added via `npm install` accidentally, lockfile becomes inconsistent. **Mitigation:** `packageManager: "pnpm@11.0.0"` field in package.json + CI gate. **Project status:** field present. |
| EC-05 | Workspace circular dep | A → B → A. pnpm allows; build fails non-obviously. **Mitigation:** pre-commit graph check (not currently present; defer). |
| EC-06 | Husky prepare-script triggers on every install | Even non-CI / non-Docker contexts. Slows local dev. **Mitigation:** husky 9 has fast no-op when already-installed; skip-on-CI per HUSKY=0. |
| EC-07 | tsconfig extends path drift | If consumer uses `extends: "../../tsconfig.base.json"` (path) vs `extends: "@scope/tsconfig-base"` (workspace package), turbo prune behavior differs. **Project incident:** Iteration 4 + Pattern E refactor. Resolved via D-09. |

### H.2 — L2 Orchestration Edge Cases

| EC-08 | Turbo cache hit when input changed via untracked file | Turbo's `inputs:` config defines what counts; missing input → false cache hit. **Mitigation:** explicit `inputs:` declaration; `globalDependencies:` for workspace-root files. Ours uses `$TURBO_ROOT$/pnpm-lock.yaml` which is correct. |
| EC-09 | Cross-package generate task ordering | `generate` depends on proto files but generate is not directly called by consumers. **Project status:** pre-build CI runs `pnpm generate:contracts` (Placement A per ADR Decision d) — addressed at L4. |
| EC-10 | Per-task env-var pass-through | `passThroughEnv: ["*"]` is a security vector (pass-through of secrets to deterministic tasks would break determinism). **Mitigation:** ours has `passThroughEnv: ["*"]` ONLY on `dev` and `start` tasks (which are non-cacheable). Build/lint/typecheck do not pass through. **Status: correct.** |
| EC-11 | Daemon corruption in long-running CI | Turbo daemon is mostly local-dev concern; CI uses one-shot. Edge case if cache writeback fails. **Mitigation:** turbo daemon recovers automatically; CI uses `--no-daemon` implicitly. |
| EC-12 | `pnpm --filter` bypassing turbo (anti-pattern) | F-03 historical root cause. **Mitigation:** Dockerfile + CI workflows use `pnpm exec turbo run` — not `pnpm --filter`. **Status: correct.** |

### H.3 — L3 Packaging Edge Cases

| EC-13 | BuildKit DAG-prune skips orphan stages | A stage not referenced by `COPY --from=` is silently dropped. **Project incident:** Iteration 3 (orphan fetcher). **Mitigation:** every stage must be reachable via final-stage dep chain. |
| EC-14 | Non-deterministic timestamp in build artifact | `date -u` in build-info.json → different bytes per build. **Project status:** present. **Mitigation:** use `SOURCE_DATE_EPOCH` (Reproducible Builds canonical env var). |
| EC-15 | Cache-mount target not aligned to PNPM_HOME | If `target=/pnpm/store` but pnpm writes to `~/.local/share/pnpm/store/v11`, cache misses 100%. **Project incident:** Iteration 3. **Resolved by D-08 (`ENV PNPM_HOME=/pnpm`).** |
| EC-16 | Multi-arch build BuildKit-platform-leg has missing apk package | `apk add wget` may not have arm64 binary on alpine version. **Mitigation:** alpine has multi-arch support; rare. |
| EC-17 | `apk add` reaches network — non-hermetic | Not blocking but reduces hermeticity. **Mitigation:** preinstall in base image (separate hardening phase). |

| EC-23 | Workspace symlink `link:../../packages/*` mismatch in COPY order | M3 architectural-eliminate semantics: packages/ COPY must precede node_modules COPY. **Project status:** addressed in current Dockerfile comment I-S2.3. |

- ✓ L1: each `apps/<svc>/` is self-contained with its own package.json (squad can own its app)

- ⚠ L5: smoke gates are workspace-wide today; per-service-smoke exists but is not invoked per-squad. **Hardening item:** support per-service squad invocation of L5.

**Verdict:** Architecture is **Inverse-Conway-compatible** at the layer level. Per-squad autonomy is achievable WITHOUT changing layer boundaries; only L5 invocation pattern needs refinement.
