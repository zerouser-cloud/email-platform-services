<!-- FR-13 K8s mechanism design — finalized DURING this plan execution в Task 1 (design step). -->
<!-- 6 decoupling criteria from LAYER-ARCHITECTURE §D.1: -->
<!--   1. Substitutability — can mechanism X be swapped for Y без rewrite? -->
<!--   2. Hermeticity — does mechanism contain its own state / not leak? -->
<!--   3. Reproducibility — same input → same K8s state? -->
<!--   4. Failure Containment — failure isolated to single concern? -->
<!--   5. Concern Atomicity — does it own ONE responsibility? -->
<!--   6. Lifecycle Independence — can it deploy without coupled framework upgrades? -->

| Mechanism     | Substitutability                                                          | Hermeticity                                                          | Reproducibility                                                          | Failure Containment | Concern Atomicity                                   | Lifecycle Independence                                      |
| ------------- | ------------------------------------------------------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------ | ------------------- | --------------------------------------------------- | ----------------------------------------------------------- |
| **Helm**      | Medium (templating runtime → values.yaml is leaky)                        | Medium (Tiller-less Helm 3 OK; CRD ownership questions)              | Medium (template engine + values composition non-deterministic at edges) | Medium              | High (single concern: deploy)                       | Low (Helm version coupled к chart API)                      |
| **Kustomize** | High (vanilla kubectl ≥1.14 ships kustomize built-in)                     | High (pure declarative — no runtime, no engine)                      | High (strategic merge → deterministic)                                   | High                | High (single concern: K8s overlay)                  | High (kubectl-native; no separate Kustomize binary install) |
| **ArgoCD**    | Low (commits-Git-as-state inverts deploy flow; coupled к ArgoCD instance) | Low (ArgoCD itself is a stateful controller — needs separate deploy) | High (GitOps reconciliation)                                             | Medium              | Medium (deploy + drift detection + auto-sync mixed) | Low (requires ArgoCD ops + RBAC + CRDs)                     |

**Default lock per Plan 08 design step:** **Kustomize**.

**Rationale (≥2 external citations per `feedback_no_guessing`):**

1. **Kubernetes SIG-CLI maintains Kustomize** — built into `kubectl apply -k <dir>` since v1.14 (2019); zero external tool installation needed на CI runners (per Kubernetes documentation https://kubernetes.io/docs/tasks/manage-kubernetes-objects/kustomization/ — official canonical).
2. **GitLab Auto-DevOps pattern** — Kustomize is the documented mechanism для declarative K8s deployment from GitLab CI без stateful operator (per GitLab docs https://docs.gitlab.com/ee/topics/autodevops/customize.html — vendor-canonical for our target CI platform per memory `project_gitlab_migration`).
3. **CNCF KubeCon 2023 talk «Kustomize: When to Use What»** (per RESEARCH-V2-SUPPLEMENT §S2.1.1) — Kustomize IS the canonical CNCF-aligned overlay mechanism for self-hosted multi-env deploys.

**Why not Helm:** templating runtime adds debugging complexity (helm template + diff); chart API version lock-in conflicts с Lifecycle Independence criterion. Acceptable choice if user later opts in but adds operational overhead now.

**Why not ArgoCD:** GitOps controller deploy = bootstrap problem (ArgoCD itself must be deployed first via Kustomize/Helm/manifests) — chicken-and-egg violates Hermeticity. Acceptable upgrade path AFTER 999.18.4 если user wants pull-based GitOps; не reasonable starting point.

**Migration path:** Kustomize is forward-compatible — Helm chart can WRAP a Kustomize overlay (via `helm template ... | kubectl apply -k`) и ArgoCD natively supports Kustomize sources. Choosing Kustomize первым keeps door open для both alternatives.

```bash
#!/usr/bin/env bash
# scripts/verify-k8s-rollout.sh
# Phase 999.18.3 — L5 K8s rollout gate (FR-20).
# Invoked from .gitlab-ci.yml deploy stage AFTER `kubectl apply -k`.
# Exits 0 only if все Deployments полностью rolled out + readiness probe passes.

set -euo pipefail

NAMESPACE="${KUBE_NAMESPACE:-${1:-}}"
if [[ -z "$NAMESPACE" ]]; then
  echo "ERROR: namespace required — pass as first arg or export KUBE_NAMESPACE" >&2
  exit 1
fi

SERVICES=(gateway auth sender parser audience notifier)
ROLLOUT_TIMEOUT="${ROLLOUT_TIMEOUT:-300s}"

echo "=== K8s rollout gate (namespace=$NAMESPACE) ==="

for SVC in "${SERVICES[@]}"; do
  echo "--- $SVC ---"

  # Wait для full rollout (kubectl-native primitive)
  if ! kubectl rollout status deployment/$SVC -n "$NAMESPACE" --timeout="$ROLLOUT_TIMEOUT"; then
    echo "FAIL: $SVC rollout did not complete within $ROLLOUT_TIMEOUT" >&2
    kubectl describe deployment/$SVC -n "$NAMESPACE" >&2 || true
    kubectl get pods -n "$NAMESPACE" -l app.kubernetes.io/name=$SVC >&2 || true
    exit 1
  fi

  # Verify ≥1 ready pod (defense-in-depth — rollout status sometimes returns 0 without ready replicas)
  READY=$(kubectl get deployment/$SVC -n "$NAMESPACE" -o jsonpath='{.status.readyReplicas}')
  : "${READY:=0}"
  if [[ "$READY" -lt 1 ]]; then
    echo "FAIL: $SVC has 0 ready replicas after rollout" >&2
    exit 1
  fi
  echo "$SVC: $READY ready replicas"
done

echo "=== K8s rollout gate PASS ==="
```
