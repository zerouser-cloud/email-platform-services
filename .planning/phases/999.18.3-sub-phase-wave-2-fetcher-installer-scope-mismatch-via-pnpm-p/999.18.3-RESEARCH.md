## Summary

999.18.3 закрывает narrow architectural gap, surfaced 999.18.2 Wave 4 final verification gate: фаза 999.18.2 структурно landed Dockerfile rewrite per 999.18.1 ADR-001, но empirically failed isolated smoke gate + 3 of 4 Wave 0 verifier scripts на ОДНОЙ root cause — Stage 1.1.5 fetcher (`pnpm fetch --prod`) и Stage 1.2 installer (`pnpm install --offline --frozen-lockfile` без `--prod`) имеют scope mismatch; девDeps (`@typescript-eslint/eslint-plugin@8.59.1`) отсутствуют в read-only fetch-store mount, installer не может фолбекнуться на сеть, build падает на первом devDep. Wave 4 falsified hypothesis «transient cache desync» через aggressive `docker buildx prune -af` (~1.8 GB reclaimed) — bug структурный, не transient.

User-locked Variant 2 fix per session 2026-05-04 — drop `--prod` от fetcher (Stage 1.1.5 → `pnpm fetch`), preserve installer как есть (Stage 1.2 → `pnpm install --offline --frozen-lockfile` full set), добавить `pnpm prune --prod` в Stage 1.3 builder ПОСЛЕ `nest build`, runner Stage 2 копирует уже pruned `node_modules`. Variant 2 — single-service-per-build canonical pattern (Bazyli Brzóska / Snyk Liran Tal / fintlabs Medium 2024). Variant 1 (Turborepo two-install) фиксируется как Considered Alternative с rejection rationale.

Канонический endpoint в research: `pnpm fetch` (full) → `pnpm install --offline --frozen-lockfile` → `nest build` → `pnpm prune --prod` → manual COPY runner. Это уточнение M3 sub-pattern, НЕ ревизия Decision (b). M3 retained, foot-gun extinct, F-01/F-02/F-14/F-15 closures сохраняются architecturally.

**Primary recommendation:** в Stage 1.1.5 fetcher строка 39 заменить `pnpm fetch --prod` → `pnpm fetch`; в Stage 1.3 builder ПОСЛЕ `pnpm exec turbo run build` (line 72) и ПОСЛЕ `RUN echo '...build-info.json' ...` (line 77) добавить `RUN --mount=type=cache,id=pnpm-install,target=/pnpm/store pnpm prune --prod`; runner Stage 2 unchanged (manual COPY уже copies post-prune `/app/node_modules`). Все изменения — within ADR-001 M3 mechanism scope, foot-gun посыпается architecturally.

### Pattern 1: `pnpm prune --prod` post-build placement (Stage 1.3 builder, after `turbo run build`)

**What:** Run `pnpm prune --prod` AFTER `pnpm exec turbo run build` finishes successfully and AFTER `build-info.json` is materialised; BEFORE the stage transitions to runner. Use the same `pnpm-install` cache mount for write-coherent removal of devDep symlinks.

**When to use:** Single-service-per-Dockerfile build (наш case — Dockerfile parametrised by `--build-arg APP_NAME=auth/sender/...`). Каждая `docker buildx build` invocation produces ровно один сервис; `pnpm prune --prod` operates на root workspace (`/app`) which после `turbo prune --docker` уже содержит ТОЛЬКО closure для target `APP_NAME`.

**Why это работает в нашем context (vs why prune обычно "не supports recursive on monorepo"):**

1. After `turbo prune --docker`, `/app/out/full/` contains only target `apps/${APP_NAME}` + transitive workspace closure (`packages/{config,contracts,foundation}`). Это уже pruned monorepo slice — `pnpm prune --prod` запущенный в `/app` имеет meaningful scope.
2. `injectWorkspacePackages: false` (M3) means workspace deps живут как symlinks (`link:../../packages/*`) — `pnpm prune --prod` removes только registered devDeps from `node_modules/.pnpm`, не workspace links.
3. ВЫЗОВ внутри `RUN` директивы Dockerfile = single shell invocation на single workspace root = pnpm нативно supports без `--recursive`.

**Example:**

```dockerfile
# Source: Variant 2 sub-pattern — fintlabs Medium pattern + Bazyli Brzóska canonical NestJS Dockerfile
# CITED: https://fintlabs.medium.com/optimized-multi-stage-docker-builds-with-turborepo-and-pnpm-for-nodejs-microservices-in-a-monorepo-c686fdcf051f
# CITED: https://pnpm.io/11.x/cli/prune

# ─── Stage 1.3: Builder ───────────────────────────────────────
FROM installer AS builder
WORKDIR /app
COPY --from=pruner /app/out/full/ ./
ARG APP_NAME
RUN pnpm exec turbo run build --filter=@email-platform/${APP_NAME}

# Build metadata
ARG BUILD_COMMIT=local
ARG BUILD_BRANCH=local
RUN echo "{\"commit\":\"${BUILD_COMMIT}\",\"branch\":\"${BUILD_BRANCH}\",\"built\":\"$(date -u +%Y-%m-%dT%H:%M:%SZ)\"}" > /app/build-info.json

# I-S1.Y (NEW invariant per 999.18.3 D-04): pnpm prune --prod removes devDeps in-place
# Runs AFTER nest build (devDeps were available при invocation) and BEFORE runner COPY.
# Cache mount reuses pnpm-install id для write-coherent removal of devDep symlinks.
# Reference: ADR-001 §Decision (b) M3 sub-pattern clarification (post-999.18.3 amendment).
RUN --mount=type=cache,id=pnpm-install,target=/pnpm/store \
    pnpm prune --prod
```

**SHA reference (for executor ground-truth):** Current `infra/docker/app.Dockerfile` HEAD as of 2026-05-04 has Stage 1.3 builder ending at line 77 (`RUN echo "{...build-info.json"`); the new `RUN ... pnpm prune --prod` line lands as new line 79 (с blank line 78 separating semantic groups).

### Pattern 2: `pnpm fetch` (без `--prod`) — full tarball cache prime

**What:** Stage 1.1.5 fetcher теперь fetches FULL dependency closure (prod + dev), not just prod. Cache mount ID `pnpm-fetch` остаётся unchanged.

**When to use:** When installer (Stage 1.2) needs ALL deps (включая `typescript`, `@nestjs/cli`, `ts-proto`, ESLint plugins для `nest build` в Stage 1.3). Это наш case под ADR-001 M3 + Decision (a) DROP `pnpm deploy --prod` — installer is single canonical install (no separate prod-only install).

**Trade-off (acknowledged in plan-phase as acceptance criterion):** `pnpm-fetch` cache layer становится larger by ~200-400 MB (estimate based на full vs prod-only diff в monorepos similar size — verify в plan-phase Wave 0 PoC). Acceptable trade-off because:

1. Cache layer survives lockfile-stable builds → bandwidth/storage cost amortizes across cache hits.
2. Empirical evidence (999.18.2 Wave 4): scope mismatch caused ZERO cache layer savings (every build failed before cache was useful). Larger but functional cache > smaller but broken cache.
3. M3 cache split (`pnpm-fetch` vs `pnpm-install` separate IDs) preserved → lockfile bump invalidates fetcher only; install layer cache survives if resolved deps unchanged.

**Example:**

```dockerfile
# Source: pnpm.io/cli/fetch + 999.18.1-RESEARCH §3.6 Dockerfile spike Stage 1.1.5
# CITED: https://pnpm.io/cli/fetch (без --prod = full set; --dev/--prod alternative flags)

# ─── Stage 1.1.5: Fetcher (M3 mechanism per ADR (b) sub-pattern, post-999.18.3) ──────────
FROM node:${NODE_VERSION} AS fetcher
WORKDIR /app
RUN corepack enable
COPY --from=pruner /app/out/json/ ./
# I-S1.X (UPDATED invariant per 999.18.3 D-04): pnpm fetch (NO --prod) caches full set
# Включая devDeps required в Stage 1.2 installer для Stage 1.3 builder needs.
# Cache layer survives lockfile-stable commits (manifests + lockfile only key).
RUN --mount=type=cache,id=pnpm-fetch,target=/pnpm/store \
    pnpm fetch
```

### Anti-Patterns to Avoid

- **`pnpm install --offline --frozen-lockfile --prod` (Wave 4 SUMMARY Option A).** Starves Stage 1.3 builder — `typescript`, `@nestjs/cli`, `ts-proto` all reside в devDependencies; build fails с TS compile error.

- **`pnpm prune --prod` BEFORE `nest build`.** Removes devDeps до того, как они нужны для compilation. TS compiler not found, build fails.

- **`pnpm prune --prod --recursive` или `pnpm -r prune --prod`.** pnpm 11 explicitly does NOT support recursive prune execution на monorepo per [pnpm/cli/prune docs](https://pnpm.io/11.x/cli/prune). Trying flag = error or silent no-op (depending on pnpm patch). НЕ relevant в нашем context потому что после `turbo prune --docker` workspace root уже содержит ровно closure for target service — flat invocation prunes именно то что нужно.

- **`pnpm prune --prod` followed by `pnpm install --prod`.** Tautology: prune already removes devDeps; subsequent install запускает full re-resolution and может re-introduce devDeps if package.json специфицирует их без `--prod` flag flattening. Stick with single prune invocation.

- **Drop `pnpm prune --prod` под предлогом "image size acceptable".** ADR-001 §C.4 R-02 contingent action explicitly authorises mitigation when image delta >20%. Even при <5% delta, prune подтверждает scope-discipline между builder и runner stages — это структурный signal, не just size optimisation.

- **Add `pnpm prune --prod` к Stage 1.2 installer instead of Stage 1.3 builder.** Builder needs devDeps DURING `nest build`. Pruning в installer = installer-stage devDeps removed → Stage 1.3 inherits FROM installer (`FROM installer AS builder`) → `nest build` fails. Prune ОБЯЗАТЕЛЬНО в Stage 1.3 после build complete.

## Common Pitfalls

### Pitfall 1: Running `pnpm prune --prod` BEFORE `nest build` (or BEFORE turbo build invocation)

**What goes wrong:** Builder stage cannot find `typescript`, `@nestjs/cli`, `ts-proto`, or ESLint plugins (all in `devDependencies`); compilation fails с module-not-found или command-not-found errors before producing `dist/main.js`.

**Why it happens:** Misreading "prune before COPY to runner" — it must be AFTER build outputs are materialised (in `apps/${APP_NAME}/dist`). The mental shortcut "fewer files в builder = faster" inverts the build/prune relationship.

**How to avoid:** Always sequence `nest build` → emit `build-info.json` → `pnpm prune --prod`. Per fintlabs Medium pattern + Bazyli Brzóska canonical NestJS Dockerfile.

**Warning signs:** First post-prune build attempt fails с messages like `Cannot find module 'typescript'` or `Error: Cannot find module '@nestjs/cli'` — ifшь видите это в builder logs, prune is positioned wrong.

### Pitfall 2: Not preserving `pnpm-install` cache mount during prune

**What goes wrong:** `pnpm prune --prod` без cache mount ID re-resolves dependency graph from network, fails offline, или introduces non-determinism in image digest.

**Why it happens:** Forgetting to add `--mount=type=cache,id=pnpm-install,target=/pnpm/store` к prune RUN directive.

**How to avoid:** Always reuse `pnpm-install` cache mount ID for prune step. Same store, same lockfile, same resolution → byte-deterministic prune output.

**Warning signs:** `verify:image-determinism` fails on second cycle with digest mismatch on `node_modules/.pnpm/...` paths — likely missed cache mount on prune.

### Pitfall 3: Workspace symlink integrity — `link:../../packages/*` resolution

**What goes wrong:** `pnpm prune --prod` removes workspace package symlinks if it misclassifies them as dev-only, breaking runtime workspace dep resolution. Per pnpm Issue #9796 (pnpm 10.13, July 2025), there's an open report где `pnpm prune --prod prunes linked workspaces deps` под `pnpm deploy` followed by prune scenario.

**Why it happens:** Issue #9796 is specific к `pnpm --filter=workspace2 deploy ./out` followed by prune in the deploy folder. Наш scenario differs: we don't use `pnpm deploy`; we use `turbo prune --docker` + manual COPY runner; prune runs at workspace root, not in a deploy directory.

**How to avoid:**

1. **Empirical verification in plan-phase Wave 1 PoC build:** After post-prune builder stage, `RUN ls -la apps/${APP_NAME}/node_modules/@email-platform/` should show 3 directories (config, contracts, foundation), each as a symlink (`ls -la` reveals `l` prefix in mode column). If они missing or broken — symlink integrity issue surfaces empirically.
2. **Prefer to keep `injectWorkspacePackages: false` (M3 — already locked in ADR-001 Decision (b)).** This means workspace deps live as `link:../../packages/*` symlinks in lockfile, not as injected hard-link copies. Symlinks survive `pnpm prune --prod` because они lockfile-recorded as `link:` protocol entries (NOT registered devDeps).
3. **Verifier coverage:** `verify:per-service-smoke` boots service entry point and exercises workspace dep resolution at runtime — failure here surfaces symlink breakage immediately.

**Warning signs:**

- Service container fails at startup с `Error: Cannot find module '@email-platform/contracts'` или `@email-platform/config` или `@email-platform/foundation`.
- `apps/{svc}/node_modules/@email-platform/` directory empty or contains broken symlinks (`ls -la` shows `?` permissions or arrows pointing к non-existent paths).

**Mitigation if surfaces:** Plan-phase 999.18.3 Wave 1 PoC build includes empirical validation step (per D-06 verifier suite re-run sequence). If verify:per-service-smoke fails on workspace symlink resolution post-prune, escalate к user immediately per CONTEXT D-06 acceptance ("никаких `Self-Check: ATTENTION` deferments — если что-то FAIL, escalate to user immediately").

### Pitfall 4: Multi-arch QEMU emulation interaction with prune

**What goes wrong:** During `docker buildx build --platform linux/amd64,linux/arm64`, prune step может execute slower under QEMU emulation на amd64 hardware producing arm64 leg. Не correctness issue — performance only.

**Why it happens:** QEMU dynamically translates instructions; pnpm internal hashmap operations (dep graph traversal during prune) are CPU-bound и see ~3-7x slowdown under emulation per RESEARCH 999.18.1 §6.1 Approach A cost estimate.

**How to avoid:**

1. Accept QEMU emulation cost per ADR-001 implicit-fifth Decision + CONTEXT D-09 + D-11. Native ARM runners migration is DevOps-owned timing per CONTEXT D-19 carry-forward and trigger T-CI-01 fire (CI cycle wall-clock >30 min consistently per RE-EVAL-TRIGGERS.md).
2. Ensure cache mount ID `pnpm-install` survives across CI runs (`type=gha` BuildKit cache backend per `.github/workflows/docker-build.yml`) — warm cache reduces prune wall-clock significantly.

**Warning signs:** First multi-arch CI run wall-clock >30 minutes consistently → fires T-CI-01 trigger per RE-EVAL-TRIGGERS.md.

### Pitfall 5: `pnpm prune --prod` "doesn't work correctly with workspaces" historical issue

**What goes wrong:** GitHub Issue #2396 (pnpm 4.11.1, March 2020) reported `pnpm prune --prod` not removing devDeps from workspace `node_modules`. Issue closed but resolution version not explicitly documented в issue page.

**Why it happens:** pnpm 4.x had recursive workspace handling bugs. Largely resolved через рефакторов в pnpm 5/6/7. By pnpm 10/11 era — behaviour stable for single-workspace-root invocation (наш case after `turbo prune --docker`).

**How to avoid:**

1. Empirical verification via `pnpm verify:image-determinism` (post-prune image size reasonable + digest stable across rebuilds) and `pnpm verify:per-service-smoke` (service starts and reaches `/health/ready`).
2. **Plan-phase Wave 1 PoC measurement (recommended):** capture image size before-fix vs after-fix (estimate +5-15% per RESEARCH §5.4 — verify в actuals); if delta >20%, revisit Variant 2 vs Variant 3 choice per CONTEXT D-01 deferral note ("PoC measurement").
3. Если empirical failure surfaces — reproduce locally first (`pnpm install` in fresh checkout, `pnpm prune --prod`, inspect `node_modules`); если bug reproduces, file pnpm Issue with version pinpoint (pnpm 11.0.0 specific).

**Warning signs:** After `pnpm prune --prod`, inspecting `apps/${APP_NAME}/node_modules` reveals devDep packages still present (e.g., `typescript`, `@nestjs/cli`); image size delta >+20%.

## Open Questions

1. **PoC image-size measurement scope (per CONTEXT discretion).**
   - What we know: RESEARCH §5.4 estimate = +5-15% delta for Variant 2 vs hypothetical broken-but-works baseline; ADR §C.4 R-02 contingent action triggers `pnpm prune --prod` mitigation if >20%.
   - What's unclear: should plan-phase Wave 1 task-list include explicit image-size delta acceptance criterion (capture `docker image ls` before/after fix per service × 6)?
   - Recommendation: **YES** — add acceptance criterion. Image-size measurement = ~5 min compute per service; 6 services × ~5 min = 30 min total. Provides empirical evidence для closing R-02 gap and feeds RE-EVAL-TRIGGERS T-PROC-04 baseline (image size budget under k8s digest-pinning context).

2. **Cache layer ordering — `pnpm prune --prod` BEFORE or AFTER `build-info.json` echo?**
   - What we know: build-info.json эcho is metadata-only (writes ~150 bytes к `/app/build-info.json`); prune affects `node_modules` only. Order between them не affects correctness.
   - What's unclear: для byte-determinism (F-20), should prune run в самой последней RUN directive (deterministic ordering) или mixed with metadata?
   - Recommendation: **prune AFTER build-info.json echo.** Reasoning: (1) metadata commit (build-info.json) finalises Stage 1.3 logical state pre-prune; (2) prune is the last "structural" operation before Stage 2 COPY — clearer rollback target if needed; (3) cache-mount semantics: prune writes to `pnpm-install` cache mount which doesn't affect layer hash, so ordering doesn't impact cache layer composition. Сохранение sequencing ⟶ build → metadata → prune → COPY runner stage.

3. **`pnpm prune --prod --no-optional` flag — apply or not?**
   - What we know: fintlabs Medium 2024 pattern uses `pnpm prune --prod --no-optional`. The `--no-optional` flag additionally removes optional dependencies (e.g., platform-specific binaries that didn't match build env).
   - What's unclear: does наш project have optional deps that runtime needs? Inspecting `package.json`s — `optionalDependencies: {}` empty for all 6 apps; `packages/foundation` has empty too. Workspace lockfile may pull in transitive optionals (e.g., `@swc/core-linux-x64-musl` for some toolchains).
   - Recommendation: **OMIT `--no-optional`** initially. If image-size measurement (Open Question 1) shows opportunity for further reduction (e.g., distroless runner pulls platform-specific optionals it doesn't need), revisit в follow-up phase. Conservative starting point — drop only registered devDeps, не optionals.

4. **Verifier suite re-run order — `verify:injection-extinct` first or last?**
   - What we know: per CONTEXT D-06, sequence is (1) injection-extinct (sanity), (2) image-determinism, (3) per-service-smoke, (4) multiarch (deferred-async), (5) dual-mode smoke, (6) rollback drill.
   - What's unclear: `verify:injection-extinct` is fast (~2 min), but `verify:image-determinism` is most expensive (~25 min single service × 5 cycles = ~25-30 min). Should fast verifier come first or last in sequence?
   - Recommendation: **fast first (injection-extinct), expensive next (image-determinism), then service-level expansion (per-service-smoke).** Per CONTEXT D-06 already specifies this order — it's CORRECT pattern. Sanity check first surfaces any "did the amendment break injection-eliminate?" issue cheaply before committing to expensive runs. If injection-extinct FAILS, abort sequence and escalate immediately per D-06 ("если что-то FAIL, escalate to user immediately").
