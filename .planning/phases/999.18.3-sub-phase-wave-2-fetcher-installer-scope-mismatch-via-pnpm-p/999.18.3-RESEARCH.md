# Phase 999.18.3 — Architecture Research (Post-Pause, First-Principles Rewrite)

## Summary

После 6 итераций и 5 различных слоёв empirical failure'ов phase 999.18.3 находится в архитектурной паузе. Предыдущая модель оформила выбор как «Path 1 (pnpm.io two-stage) vs Path 2 (`--ignore-scripts` workaround)». **Этот binary — артефакт неполного survey, а не реальная архитектурная дилемма.**

Эмпирическая верификация показала:

1. **Q1 verified:** smoking gun `a647f51` действительно удалил `COPY tsconfig.base.json ./` (одна строка плюс ещё 8 explicit-COPY строк, заменённых на `COPY . .` в pruner stage). Это документированный rewrite, не другой контекст.

2. **Q3 verified — критическое уточнение framing'а:** из 3 «костылей» только 2 (D-10 + предложенный `--ignore-scripts`) — следствия выбора `pnpm prune --prod`. **Pattern E (D-09) — каноничный architectural refactor, не workaround;** он остаётся правильным независимо от выбора Path. Предыдущая модель некорректно объединила эти orthogonal concerns.

3. **Q4 surfaced canonical mechanism missed by ADR-001:** pnpm 11 (включая нашу `pnpm@11.0.0`) поддерживает `pnpm deploy --legacy --prod` который **не требует** `injectWorkspacePackages: true`. ADR Decision (a) «DROP pnpm deploy» был принят на основе pnpm Discussion #9015 (старая foot-gun reality), но pnpm 10.2.1+ ввёл `--legacy` как explicit escape hatch. **Premise, на котором держалась Decision (a), устарел.** Это не «Path 3» — это canonical pattern из pnpm.io Example 2 minus `injectWorkspacePackages: true`.

4. **Q5 verified:** husky 9.x reads `HUSKY=0` env var и exit'ит cleanly (verified локально: `HUSKY=0 npx husky` → "HUSKY=0 skip install", exit 0). Это author-endorsed pattern из husky docs (https://typicode.github.io/husky/how-to.html), не `--ignore-scripts` костыль.

**Primary recommendation:** Заменить «pnpm install --frozen-lockfile + pnpm prune --prod» substrate на **pnpm.io Example 2 monorepo pattern с `--legacy` flag** — `pnpm install --frozen-lockfile` (full set) + `pnpm deploy --filter=@email-platform/${APP_NAME} --legacy --prod /prod/${APP_NAME}` в builder stage, runner копирует isolated `/prod/${APP_NAME}` (включая isolated node_modules per pnpm deploy semantics). Plus `ENV HUSKY=0` в installer + builder для clean lifecycle isolation. Pattern E (D-09 workspace tsconfig package) и distroless runner (ADR c) remain. Это устраняет husky issue без `--ignore-scripts`, устраняет TTY issue без D-10 (т.к. `pnpm deploy` не вызывает `validateModules` purge path), устраняет +30-60s rebuild от prune, и единственный source of truth — workspace dep graph.

**Confidence:** HIGH для empirical state и production canon; HIGH для architecture proposal (built on canonical mechanism); MEDIUM для размера delta (probe из PRUNE-VERIFY 9.6% на minimal repo, реальный monorepo unmeasured).

### Q2 — pnpm.io two-stage решает husky lifecycle? Частично. Husky лeak возможен; нужен HUSKY=0 явно

**Hypothesis (предыдущая модель):** «prod-deps stage с нуля без husky → нет lifecycle conflict».

**Empirical falsification:**

pnpm.io Example 1 (single-bundle) recipe:

```dockerfile
FROM base AS prod-deps
RUN --mount=type=cache,id=pnpm,target=/pnpm/store pnpm install --prod --frozen-lockfile
```

`pnpm install --prod` **в нашем root package.json** будет:

1. Читать root `package.json` → видит `"prepare": "husky"` lifecycle script.
2. С `--prod` flag: husky НЕ устанавливается (он в `devDependencies`).
3. **Lifecycle script `prepare` всё равно запускается** при install (это default pnpm behaviour, не зависит от dev/prod split).
4. `husky` binary missing → `sh: husky: not found` → exit 1.

Это эмпирически воспроизводимо в любом package.json с `prepare` zависящим от devDep binary; pnpm.io's own recipe **уязвим** к этому без `HUSKY=0` или `is-ci` guard.

**Подтверждение из husky docs** (https://typicode.github.io/husky/how-to.html):

> "To avoid installing Git Hooks on CI servers or in Docker, use `HUSKY=0`"

**Verified локально:** `HUSKY=0 npx husky` → output `HUSKY=0 skip install`, exit 0. **Это единственный canonical mechanism** — `--ignore-scripts` упоминается husky issue #914 как «wontfix workaround», не как maintainer-endorsed.

**Verdict:** **NEEDS AMENDMENT.** pnpm.io two-stage **не решает husky lifecycle сам по себе** — husky leak'ит через `prepare` even в `--prod` mode. **Решает связка** `pnpm.io two-stage + ENV HUSKY=0`. Но `HUSKY=0` — orthogonal concern: он нужен и для текущего prune-based path, и для предлагаемого deploy-based path, и для любого подхода. **Husky containment — отдельный axis, не bound к выбору install-strategy.**

**Source:** husky docs https://typicode.github.io/husky/how-to.html (canonical author docs); husky issue #914 (wontfix label confirms `--ignore-scripts` is workaround); local empirical `HUSKY=0 npx husky` probe.

**Confidence: HIGH** [VERIFIED: husky author docs + local probe].

### Q4 — Паттерны кроме pnpm.io two-stage? ДА — ключевой missed pattern в ADR

**Survey performed (5+ sources, см. §2 Production Canon):**

1. pnpm.io Example 1 — single-service, two-install split (prod-deps ∥ build).
2. **pnpm.io Example 2 — monorepo с `pnpm deploy --filter --prod` + `injectWorkspacePackages: true`.** — это canonical pnpm.io pattern для monorepo, который ADR-001 §O-07 mis-framed («Vercel two-install») и rejected на основе `injectWorkspacePackages` foot-gun.
3. pnpm.io Example 3 — `pnpm fetch --prod` single-stage (CI optimized).
4. Vercel Turborepo `examples/with-docker` — yarn-based, не pnpm; not directly applicable but established pattern.
5. **`pnpm deploy --legacy --prod`** — pnpm 10.2.1+ canonical escape hatch from `injectWorkspacePackages: true` requirement (https://pnpm.io/cli/deploy). **Эта опция не существовала на момент написания ADR-001.**
6. fintlabs Medium — single-install + post-build `pnpm prune --prod` (community cookbook; нашa текущая шапка).
7. Bun monorepo (Bun 1.x) — non-applicable (мы pinned pnpm@11).
8. Bazel/Buck2 (Google/Meta) — non-applicable (D-08 phase-level OCI/Dockerfile lock; full hermetic builds — overkill для N=6 services).

**The missed pattern:** ADR-001 Decision (a) DROP `pnpm deploy --prod` обосновывалось pnpm Discussion #9015 («deploy requires injectWorkspacePackages» — true pre-10.2.1). Но **pnpm 10.2.1 ввёл `--legacy` флаг** и **pnpm 11.0.0 (наш pinned) поддерживает его** (verified локально: `pnpm deploy --help` shows `--legacy   Force legacy deploy implementation`). Это снимает первоначальный foot-gun без принятия injection model.

**Дополнительная альтернатива — `force-legacy-deploy=true`** в `.npmrc` (per pnpm.io/cli/deploy docs) — настройка persistent для всего workspace, не нужно в каждом invocation.

**Verdict:** **FALSIFIED.** Path 1/Path 2 binary неполный. Существует **Path 3 = pnpm deploy --legacy --prod**, который пропустила ADR-001 (т.к. pnpm 10.2.1 vышел после ADR locking date). Этот path:

- Эмпирически canonical в pnpm.io Example 2 (modulo `injectWorkspacePackages` requirement, которое снимается `--legacy`).
- Не требует `pnpm prune --prod` step → eliminates D-10 + husky issue.
- Создаёт isolated `/prod/${APP_NAME}` dir с независимым node_modules → byte-determinism для F-20 actually улучшается.
- Совместим с Pattern E (D-09 workspace tsconfig package) — turbo prune не нужен в этом подходе, deploy filter сам traverses dep graph.

**Source:** pnpm.io/cli/deploy (verified via WebFetch this session); pnpm.io/docker Example 2 (verified via WebFetch raw markdown); local `pnpm deploy --help` showing `--legacy` flag in pnpm@11.0.0; pnpm Discussion #10156 (community confirms --legacy works since 10.2.1).

**Confidence: HIGH** [VERIFIED: pnpm.io docs + local CLI help].

### Q5 — Что делать с husky? Canonical = HUSKY=0 env var, не --ignore-scripts

**Survey** (husky docs + source code + community references):

| Approach                                       | Verdict                                                                                                                                   | Source                                                                                           |
| ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------- | ----------------------------------------------------- |
| `ENV HUSKY=0` в Dockerfile                     | **CANONICAL** — author-endorsed, single source-of-truth env flag                                                                          | https://typicode.github.io/husky/how-to.html ; verified local probe `HUSKY=0 npx husky` → exit 0 |
| `"prepare": "husky                             |                                                                                                                                           | true"`                                                                                           | Workaround — suppresses errors, prints confusing «not found» messages | husky docs (mentioned but not recommended as default) |
| `"prepare": "is-ci                             |                                                                                                                                           | husky"`                                                                                          | Pattern для local-only — requires extra `is-ci` devDep                | community pattern (not husky-author canonical)        |
| `RUN touch /usr/local/bin/husky` (stub binary) | Hacky workaround — Docker-only, not author-endorsed                                                                                       | husky issue #991                                                                                 |
| `pnpm prune --prod --ignore-scripts`           | **NOT husky-specific** — disables ALL lifecycle scripts (potentially security-relevant scripts too); marked «wontfix» in husky issue #914 | husky issue #914 (wontfix)                                                                       |
| Drop husky entirely from root devDeps          | Architectural removal — most invasive                                                                                                     | own decision                                                                                     |
| Use `lefthook` / `simple-git-hooks` instead    | Replacement of tool                                                                                                                       | non-husky-specific decision                                                                      |

**Production-grade pattern (canonical per husky docs):**

```dockerfile
ENV HUSKY=0
```

Helmet'ом одной строкой решает problem **во всех путях** (install, prune, deploy, fetch — потому что ANY pnpm operation которая re-triggers `prepare` — будет видеть `HUSKY=0` и exit'ить cleanly). Это:

- Не disables ALL scripts (как `--ignore-scripts` flag) — селективно отключает только husky.
- Не требует изменения root `package.json` (как `husky || true`) — host-side dev experience сохраняется.
- Documented author-canonical — no risk of removal в future husky versions.
- Empirically verified в этой сессии.

**Verdict:** **HOLDS** (research-recommended). `ENV HUSKY=0` в installer + builder stages — единственный canonical mechanism. Применим **независимо от** выбора install-substrate (prune / deploy --legacy / two-stage). Это **универсальный фикс husky containment**, не workaround конкретной install-strategy.

**Confidence: HIGH** [VERIFIED: husky author docs + local empirical probe + source-code reference в husky/index.js: `if (process.env.HUSKY === '0') return 'HUSKY=0 skip install'`].

### Source 1 — pnpm.io official Example 1 (single-bundle, prod-deps split)

**URL:** https://pnpm.io/docker (raw: https://raw.githubusercontent.com/pnpm/pnpm.io/main/docs/docker.md)
**Verified:** 2026-05-04 via WebFetch raw markdown

**Verbatim Dockerfile:**

```dockerfile
FROM node:20-slim AS base
ENV PNPM_HOME="/pnpm"
ENV PATH="$PNPM_HOME:$PATH"
RUN corepack enable
COPY . /app
WORKDIR /app

FROM base AS prod-deps
RUN --mount=type=cache,id=pnpm,target=/pnpm/store pnpm install --prod --frozen-lockfile

FROM base AS build
RUN --mount=type=cache,id=pnpm,target=/pnpm/store pnpm install --frozen-lockfile
RUN pnpm run build

FROM base
COPY --from=prod-deps /app/node_modules /app/node_modules
COPY --from=build /app/dist /app/dist
EXPOSE 8000
CMD [ "pnpm", "start" ]
```

**Classification:** **M2** (two parallel install lanes, no prune).
**Pattern features:** `ENV PNPM_HOME="/pnpm"`, `corepack enable`, cache-mount `id=pnpm`, no `pnpm fetch`, no `pnpm deploy`, no `pnpm prune`. Final image starts FROM `base` (clean), copies node_modules from prod-deps + dist from build.
**Husky handling:** **NOT explicitly addressed.** TTY error и `prepare`-with-devDep would fire here (PRUNE-VERIFY.md §4 probe D2 confirms) — recipe unsafe в 11.0.0 без `ENV CI=true` или `ENV HUSKY=0`.
**Workspace shared config:** N/A (single-package recipe).

### Source 2 — pnpm.io official Example 2 (MONOREPO with multiple images)

### 3.1 Build pipeline stages (recommended)

**Architecture target: M-deploy substrate с pnpm 11 `--legacy` flag, Pattern E preserved, husky containment via `ENV HUSKY=0`.**

```
Stage 0 — Build args (ARG APP_NAME, NODE_VERSION, GRPC_HEALTH_PROBE_VERSION)
        │
Stage 1.1 (pruner) — turbo prune carve dep-closure (preserved from current)
        │
Stage 1.2 (installer) — single full pnpm install + lifecycle isolation
        │ ENV PNPM_HOME="/pnpm" + ENV HUSKY=0
        │ COPY --from=pruner /app/out/json/ ./
        │ pnpm install --frozen-lockfile (cache-mount /pnpm/store)
        │ download grpc_health_probe (preserved)
        │
Stage 1.3 (builder) — turbo build + per-service deploy isolation
        │ FROM installer; ENV HUSKY=0 (re-declared for grep-discoverability)
        │ COPY --from=pruner /app/out/full/ ./
        │ pnpm exec turbo run build --filter=@email-platform/${APP_NAME}
        │ pnpm deploy --filter=@email-platform/${APP_NAME} --legacy --prod /prod/${APP_NAME}
        │ build-info.json materialised в /prod/${APP_NAME}
        │ NO pnpm prune --prod
        │ NO ENV CI=true (auto-supersedes — prune step removed)
        │
Stage 2 (runner) — distroless + COPY isolated tree
        │ FROM gcr.io/distroless/nodejs22-debian12:nonroot
        │ COPY --from=installer /usr/local/bin/grpc_health_probe ...
        │ COPY --from=builder /prod/${APP_NAME} /app
        │ USER 65532:65532
        │ CMD ["node", "dist/main.js"]
```

### 3.2 Workspace shared config (Pattern E preserved)

D-09 holds verbatim. Reasoning:

- `@email-platform/tsconfig-base` workspace package — single source of truth.
- `pnpm deploy --filter --legacy --prod` traverses workspace dep graph через consumer `devDependencies` declarations → автоматически включает `tsconfig-base` package.
- (Caveat: `tsconfig-base` is `devDependency`. С `--prod` flag, deploy исключает devDeps. **Но это TS build-time concern, не runtime concern**: build уже выполнен в `pnpm exec turbo run build` step ДО deploy. Deploy isolates runtime tree.)

**Confirmation:** pnpm deploy isolated tree включает только runtime deps по design (`--prod` flag); tsconfig-base нужен только при `tsc` invocation, не при `node dist/main.js` execution. Это правильный split: build needs devDeps, runtime — нет.

### 3.3 DevDeps elimination strategy

**Current state (D-01 prune):** install full → build → `pnpm prune --prod` post-build (in-place strip).
**Issues:** 5 layers of failure (NO_OFFLINE_TARBALL → TS5083 → TTY abort → husky lifecycle → ...).

**Recommended (Path 3 — pnpm deploy --legacy --prod):** install full → build → `pnpm deploy --filter --legacy --prod /prod/$APP` (isolated copy, no in-place mutation).
**Mechanism:** pnpm deploy создаёт fresh isolated `node_modules` tree в `/prod/$APP`, копирует только prod-deps (исходя из `--prod` flag), без re-running lifecycle scripts на target tree (verified per pnpm.io/cli/deploy semantics — deploy is "copy + isolate", not "install + prune").

**Critical advantages over prune:**

- **No in-place mutation** — builder's `node_modules` остаётся untouched после deploy. Если bug в deploy, можно re-run без re-build.
- **No re-running lifecycle scripts на target** — husky lifecycle issue eliminated structurally.
- **Byte-deterministic output** — given lockfile + filter, isolated tree контент одинаковый при каждом invocation. Лучше для F-20 image-determinism.
- **Workspace dep traversal correct** — `--filter` resolves transitive workspace deps (включая `tsconfig-base` если оно declared как dep, что Pattern E делает).

### 3.4 Multi-service scaling

Current: `--build-arg APP_NAME=auth/sender/...` parameterizes single Dockerfile, 6 images built (один per service).

Под предложенной архитектурой:

- N=6: каждый build делает один `pnpm deploy --filter`. Build time: cache-mount /pnpm/store shared across builds (cross-service caching работает); deploy step ~1-3s wall-clock per service (per pnpm.io performance claims).
- N=15-20 horizon: тот же Dockerfile параметризован новыми APP_NAME, без architectural изменений. **`pnpm deploy --filter` design'ом масштабируется linearly** (исключая каждый раз правильную dep slice).

**M3 horizon-rationale из D-04** (отдельный fetcher для granular cache) — **falsified** уже в SYSTEM-RESEARCH §4: «отдельная granularity = иллюзия» (orphan stage был dead code). С recommended pattern — единственный install + единственный cache-mount (`id=pnpm-store`) — **ту же cache-mount granularity получает каждый из N services**. Реальная granularity, не fictional.

### 3.5 Image determinism (F-20)

`pnpm deploy --legacy --prod` reproducibility:

- Input: `pnpm-lock.yaml` (frozen) + filter scope.
- Output: isolated `/prod/$APP` tree.
- Determinism: same lockfile + same filter + same pnpm version = byte-identical output (per pnpm contract).

Vs current `pnpm prune --prod`:

- Input: existing `node_modules` tree (potentially containing bind mounts, symlinks с относительными paths) + lockfile.
- Output: in-place modified `node_modules`.
- Determinism: depends on initial install state + prune algo. **Less robust** к non-deterministic input.

**Verdict:** F-20 strictly improved by deploy-based pattern.

### 3.6 Cache strategy

Single cache-mount `--mount=type=cache,id=pnpm-store,target=/pnpm/store` в installer stage. Builder inherits from installer (shared layer cache); deploy step не requires separate cache (resolves from already-installed tree).

**Layer ordering для optimal caching:**

```
ARG APP_NAME (доступен только где нужен, не invalidate'ит другие layers)
COPY --from=pruner /app/out/json/ ./       ← cache-key: lockfile hash
ENV PNPM_HOME=/pnpm + HUSKY=0              ← static
RUN pnpm install --frozen-lockfile         ← invalidates only on lockfile change
COPY --from=pruner /app/out/full/ ./       ← invalidates on workspace source change
RUN pnpm exec turbo run build              ← invalidates on workspace source change
RUN pnpm deploy --filter --legacy --prod   ← invalidates on dist/ change
```

Это optimal: install layer выживает source-code touch (manifest-only key); build layer инвалидируется только при изменении исходников; deploy layer — только при изменении `dist/`. **Same caching guarantees как current; lifecycle hazard removed.**
