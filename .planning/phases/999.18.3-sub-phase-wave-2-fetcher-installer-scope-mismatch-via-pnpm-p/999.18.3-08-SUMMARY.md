## Design Step Recap — K8s Mechanism Selection (FR-13)

Per Plan 08 design step (executed inside Task 1 design block before authoring manifests), Kustomize selected as L5 deploy mechanism per **6 decoupling criteria** comparison vs Helm and ArgoCD:

| Mechanism     | Substitutability | Hermeticity | Reproducibility | Failure Containment | Concern Atomicity | Lifecycle Independence |
| ------------- | ---------------- | ----------- | --------------- | ------------------- | ----------------- | ---------------------- |
| **Helm**      | Medium           | Medium      | Medium          | Medium              | High              | Low                    |
| **Kustomize** | High             | High        | High            | High                | High              | High                   |
| **ArgoCD**    | Low              | Low         | High            | Medium              | Medium            | Low                    |

**Default lock = Kustomize** with **3 external canonical citations** (≥2 required per `feedback_no_guessing`):

1. **Kubernetes SIG-CLI canonical** — `kubectl apply -k <dir>` built-in since v1.14 (2019); zero external CLI install per <https://kubernetes.io/docs/tasks/manage-kubernetes-objects/kustomization/>
2. **GitLab Auto-DevOps documentation** — Kustomize is the documented declarative deploy mechanism for GitLab CI per <https://docs.gitlab.com/ee/topics/autodevops/customize.html> (vendor-canonical for our target CI platform per memory `project_gitlab_migration`)
3. **CNCF KubeCon 2023 talk «Kustomize: When to Use What»** — RESEARCH-V2-SUPPLEMENT §S2.1.1; Kustomize IS the canonical CNCF-aligned overlay mechanism for self-hosted multi-env

**Why not Helm:** templating runtime + chart API version coupling violates Lifecycle Independence. Forward-compat: Helm can WRAP a Kustomize overlay (`helm template ... | kubectl apply -k`).

**Why not ArgoCD:** GitOps controller is itself stateful (bootstrap problem — must deploy ArgoCD via Kustomize/Helm/manifests first) → violates Hermeticity. Acceptable upgrade path post-999.18.4 if pull-based GitOps wanted; not reasonable starting point.
