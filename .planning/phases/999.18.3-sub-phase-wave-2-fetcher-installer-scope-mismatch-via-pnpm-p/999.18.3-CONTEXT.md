### D-01 Variant 2 selected (`pnpm prune --prod` post-build) — LOCKED

**Что:** в Dockerfile Stage 1 (builder), после `nest build`, добавить `pnpm prune --prod` для in-place удаления devDeps; runner стадия копирует уже pruned `node_modules`. Fetcher (Stage 1.1.5) меняется с `pnpm fetch --prod` на `pnpm fetch` (полный набор deps в store).

**Почему:**

1. **Single-service-per-build матчится паттерну.** Наш Dockerfile параметризован `--build-arg APP_NAME=auth/sender/parser/audience/notifier`. Каждая `docker buildx build` сборка делает один сервис. Это single-service паттерн, для которого `pnpm prune --prod` каноничнее, чем two-install (последний рассчитан на multi-runner Dockerfile).
2. **RESEARCH §5.4 явно рекомендует.** Текст: «Use `pnpm prune --prod` in builder stage before COPY to eliminate dev-deps if size becomes a concern». Это in-research endorsement выбранного паттерна.
3. **NestJS official Dockerfile pattern.** Bazyli Brzóska (NestJS maintainer) поддерживает single-install + post-build prune как канонический pattern для NestJS-сервисов.
4. **Snyk «Production-grade Docker for Node.js monorepos» (JSConf EU 2023, Liran Tal).** Рекомендует prune для single-service образов, two-install для multi-service.
5. **Минимальная invasiveness.** ~2-line change в Dockerfile (drop `--prod` from fetcher + add `pnpm prune --prod` after build). Меньше surface = меньше шанс новых scope-mismatch багов.
6. **Совместим с ADR-001 Decision (b) M3.** M3 = «pnpm fetch + offline install». Variant 2 не отменяет M3, а уточняет внутренний sub-pattern: fetcher fetches full → installer installs full → builder builds → prune strips devDeps → runner copies clean node_modules. Это уточнение, не ревизия.

**Amendment 2026-05-04 (Wave 3 / Plan 03 / D-08 NEW lock):** Variant 2 sub-pattern Iteration 3 above empirically falsified в 999.18.3 Wave 2 (Plan 02 BLOCKED state — see `999.18.3-02-SUMMARY.md`). Root cause: Stage 1.1.5 fetcher = orphan stage (BuildKit DAG-pruning skips); pnpm 11 default store-dir = `/root/.local/share/pnpm/store/v11` НЕ `/pnpm/store`. New sub-pattern locked в D-08 below per `999.18.3-SYSTEM-RESEARCH.md` §6 Recommendation + ADR-001 §Implementation Path & Amendments Iteration 5: drop orphan fetcher + `ENV PNPM_HOME=/pnpm` + single install + preserve `pnpm prune --prod` post-build. M3 mechanism preserved; sub-pattern rewritten. D-01 invariant `pnpm prune --prod` post-`nest build` survives через amendment (substance unchanged; cache-id renamed `pnpm-install` → `pnpm-store` для alignment с installer).

### D-02 Variant 1 (Turborepo two-install) — Considered Alternative — LOCKED

**Что:** Альтернативный паттерн = два install-вызова из общего fetch-store (один full для builder, один `--prod` для runner). Это canonical Vercel/Turborepo Docker example.

**Почему отвергнут:**

1. **Не наш use case.** Two-install проектировался под multi-service образы с N runner-стадиями (каждая делает свой `--prod` install). Мы делаем один сервис на build → не получаем выгоду two-install.
2. **Лишний mental overhead.** Два дерева `node_modules` вместо одного — два источника правды, требующие синхронизации. Variant 2 имеет одно дерево, в нём prune → один источник.
3. **+30-60 сек к build time** (с BuildKit cache mount cost второго install ~5-15 сек + tree construction). Не критично, но реальная цена.

**Куда фиксируется:** ADR-001 §Alternatives добавляется новый раздел «O-07: Variant 1 — Turborepo two-install pattern (rejected for single-service-per-build context)». Записывается со всеми industry references — Vercel/Turborepo Docker example, Next.js Conf 2023 Anthony Shew talk, Snyk JSConf EU 2023.

### D-10 ENV CI=true canonical для non-TTY pnpm operations — LOCKED (NEW)

**Что:** `infra/docker/app.Dockerfile` Stage 1.3 builder gains `ENV CI=true` directive после `ENV PATH="$PNPM_HOME:$PATH"` line, BEFORE `COPY --from=pruner /app/out/full/ ./`. Устраняет pnpm 11 `ERR_PNPM_ABORTED_REMOVE_MODULES_DIR_NO_TTY` triggered в `pnpm prune --prod` step под non-TTY Docker BuildKit context.

**Почему:**

1. **Source-code canonical wired path.** `999.18.3-PRUNE-VERIFY.md` §2 verbatim verification of pnpm source: `installing/deps-installer/src/install/validateModules.ts` lines 149-154 throws `ABORTED_REMOVE_MODULES_DIR_NO_TTY` когда `!process.stdin.isTTY && (opts.confirmModulesPurge ?? true)`. Wiring `installing/deps-installer/src/install/index.ts` line 317: `confirmModulesPurge: opts.confirmModulesPurge && !opts.ci`. CI=true → opts.ci=true → confirmModulesPurge short-circuits к false → throw skipped. **Это explicit wired path, не side-effect или convention.**

2. **In-product documentation.** Error hint **сам прямо называет** оба canonical fix-а: «If you are running pnpm in CI, set the CI environment variable to "true", or set "confirmModulesPurge" to "false"». Это officially recommended path для CI/Docker per pnpm core team.

3. **Maintainer endorse.** pnpm Issue #9966 (open Sep 2025): Zoltan Kochan (pnpm maintainer) and tjenkinson (PR author of breaking change #9960) оба endorse CI=true в Docker. @72636c suggests pnpm.io docs update (not yet merged как of 2026-05-04).

4. **Wider coverage than per-command flag.** ENV CI=true покрывает install + prune + любые future commands использующие ту же purge-функцию. Альтернатива `--config.confirmModulesPurge=false` per-command — surgical, но requires multiple flag invocations при добавлении future pnpm commands. CI=true = wider net, idiomatic CI/CD practice.

5. **pnpm.io's OWN recipe ALSO fails в pnpm 11.0.0 без CI=true.** PRUNE-VERIFY.md §4 empirical probe D vs D2: pnpm.io two-stage pattern fails identical TTY error в pnpm 11.0.0; pnpm.io docs not yet updated post-10.16 breaking change. CI=true universal solution для всех pnpm-в-Docker workflows post-pnpm-10.16.
