## Locked Decisions (выработаны в session 2026-05-04 — см. conversation transcript)

### D-01 Variant 2 selected (`pnpm prune --prod` post-build) — LOCKED

**Что:** в Dockerfile Stage 1 (builder), после `nest build`, добавить `pnpm prune --prod` для in-place удаления devDeps; runner стадия копирует уже pruned `node_modules`. Fetcher (Stage 1.1.5) меняется с `pnpm fetch --prod` на `pnpm fetch` (полный набор deps в store).

**Почему:**

1. **Single-service-per-build матчится паттерну.** Наш Dockerfile параметризован `--build-arg APP_NAME=auth/sender/parser/audience/notifier`. Каждая `docker buildx build` сборка делает один сервис. Это single-service паттерн, для которого `pnpm prune --prod` каноничнее, чем two-install (последний рассчитан на multi-runner Dockerfile).
2. **RESEARCH §5.4 явно рекомендует.** Текст: «Use `pnpm prune --prod` in builder stage before COPY to eliminate dev-deps if size becomes a concern». Это in-research endorsement выбранного паттерна.
3. **NestJS official Dockerfile pattern.** Bazyli Brzóska (NestJS maintainer) поддерживает single-install + post-build prune как канонический pattern для NestJS-сервисов.
4. **Snyk «Production-grade Docker for Node.js monorepos» (JSConf EU 2023, Liran Tal).** Рекомендует prune для single-service образов, two-install для multi-service.
5. **Минимальная invasiveness.** ~2-line change в Dockerfile (drop `--prod` from fetcher + add `pnpm prune --prod` after build). Меньше surface = меньше шанс новых scope-mismatch багов.
6. **Совместим с ADR-001 Decision (b) M3.** M3 = «pnpm fetch + offline install». Variant 2 не отменяет M3, а уточняет внутренний sub-pattern: fetcher fetches full → installer installs full → builder builds → prune strips devDeps → runner copies clean node_modules. Это уточнение, не ревизия.

### D-02 Variant 1 (Turborepo two-install) — Considered Alternative — LOCKED

**Что:** Альтернативный паттерн = два install-вызова из общего fetch-store (один full для builder, один `--prod` для runner). Это canonical Vercel/Turborepo Docker example.

**Почему отвергнут:**

1. **Не наш use case.** Two-install проектировался под multi-service образы с N runner-стадиями (каждая делает свой `--prod` install). Мы делаем один сервис на build → не получаем выгоду two-install.
2. **Лишний mental overhead.** Два дерева `node_modules` вместо одного — два источника правды, требующие синхронизации. Variant 2 имеет одно дерево, в нём prune → один источник.
3. **+30-60 сек к build time** (с BuildKit cache mount cost второго install ~5-15 сек + tree construction). Не критично, но реальная цена.

**Куда фиксируется:** ADR-001 §Alternatives добавляется новый раздел «O-07: Variant 1 — Turborepo two-install pattern (rejected for single-service-per-build context)». Записывается со всеми industry references — Vercel/Turborepo Docker example, Next.js Conf 2023 Anthony Shew talk, Snyk JSConf EU 2023.
