# Phase 999.18.3 — SYSTEM RESEARCH

## 1. Executive verdict

**M3 как идея верна, но текущая реализация — `[VERIFIED: probe m3-current]` дважды сломана архитектурно.** Stage `fetcher` в `infra/docker/app.Dockerfile` — **dead code**: ни один `COPY --from=fetcher` нигде не существует, поэтому BuildKit DAG-pruning её всегда пропускает. Параллельно cache-mount target `/pnpm/store` пустой, потому что pnpm 11 пишет в default `/root/.local/share/pnpm/store/v11` без явной конфигурации `PNPM_HOME=/pnpm` или `store-dir`. Эти два бага сложились — install крашится с `ERR_PNPM_NO_OFFLINE_TARBALL`, тех-лиду показалось «cache desync», и три фазы фиксили симптомы. **Правильный системный паттерн — single-stage fetch+install с `ENV PNPM_HOME=/pnpm` per pnpm.io official + canonical Vercel Turborepo prune-builder-runner shape**. Probe `m3-pnpmhome`: 10s cold, 0s warm-cached. Это и есть «MAANG-grade», без `pnpm prune --prod` гимнастики.

## 4. M3 rationale re-evaluation

ADR-001 §Decision (b) M3 rationale: «лучшая cache-mount granularity (отдельный `id=pnpm-fetch` vs `id=pnpm-install`); готовит проект к scale-out N=15-20 services per CONTEXT D-04».

**Эмпирическая фальсификация** `[VERIFIED: probe m3-current stage execution log]`:

1. **«Отдельная granularity»** = иллюзия. В текущем Dockerfile `fetcher` orphan-stage; `id=pnpm-fetch` cache **не пишется и не читается ни разу**. `id=pnpm-install` пустой — pnpm 11 пишет в `/root/.local/share/pnpm/store/v11`. Granularity нулевая, потому что **обе cache-mount targets пустые**.
2. **«Готовит к scale-out N=15-20»** — domain confusion. При N=15-20 single-service-per-build паттерне (наш constraint) каждый build триггерит Stage 1 заново per service. Shared `id=pnpm-store` cache-mount уже даёт cross-service sharing — нужна **одна** cache-mount, не две. Two-install (Vercel/pnpm.io official) даёт реальную granularity (full vs --prod), но мы её и так не имеем (`pnpm prune --prod` это не two-install).
3. **«M3 sub-pattern: fetcher → installer → builder → prune»** — текстовая фикция. DAG не имеет ребра fetcher→installer. ADR-001 §Decision (b) формально опровергнут эмпирией: декларируемый pipeline не равен исполняемому pipeline.

**Severity**: M3 rationale — **не speculation**, а **factually incorrect** в части of granularity claim. Scale-out claim — speculation, не подтверждённая benchmark'ом. **Decision (b) M3 mechanism (`pnpm fetch` ≠ orphan; offline install; manual COPY runner) сам по себе валиден** (Depot использует похожий паттерн). Сломана **наша конкретная реализация**, не paradigm.

## 6. Recommendation

**Один путь, основан на пересечении 3 production sources + 1 PASSED probe**:

1. **Удалить fetcher stage целиком** из `infra/docker/app.Dockerfile` (Stage 1.1.5). Это dead code per BuildKit DAG. `[VERIFIED: probe m3-current execution log #11→#12 skipped fetcher]`
2. **В оставшихся pnpm-touching stages (installer, builder)** добавить `ENV PNPM_HOME="/pnpm"` + `ENV PATH="$PNPM_HOME:$PATH"` per `[CITED: pnpm.io/docker]` + `[CITED: depot.dev/...node-pnpm-dockerfile]`. Это устраняет store-dir mismatch.
3. **Single install в installer stage**: `pnpm install --frozen-lockfile` (drop `--offline`, drop сложение через fetcher). Cache-mount: один `--mount=type=cache,id=pnpm-store,target=/pnpm/store`. `[VERIFIED: probe m3-pnpmhome 10s cold, 0s warm-cached]`
4. **Сохранить `pnpm prune --prod` post-build** в builder per CONTEXT D-01 (locked) + `[CITED: fintlabs.medium.com/...c686fdcf051f]`. Это и есть «M3 sub-pattern» — но теперь fetcher orphan отсутствует, а `prune --prod` — реальная dev/prod split механика.
5. **Stage 2 runner manual COPY** не меняется — ADR (a) drop deploy + ADR (c) distroless остаются.

**Result shape**: `pruner → installer (full deps, cache-mount /pnpm/store) → builder (FROM installer, build + prune --prod) → runner (distroless, manual COPY)`. Это пересечение Vercel canonical + pnpm.io official + fintlabs cookbook + измеренный m3-pnpmhome probe. `pnpm fetch` separation **отбрасывается** как over-engineering для нашего N — Vercel её и не использует, fintlabs не использует, pnpm.io two-install pattern не использует. Это **MAANG-grade simplicity**, не «MAANG-grade complexity».

**Подтверждение, что прежняя «исправляющая» гипотеза `ENV NPM_CONFIG_STORE_DIR=/pnpm/store` — half-measure**: probe `m3-fixed` даёт **тот же FAIL** при добавлении только этой ENV без устранения orphan fetcher и без перехода на `PNPM_HOME` (canonical pnpm var). Half-measure не закрывает root cause. Полный fix — три изменения вместе (drop fetcher + ENV PNPM_HOME + single install).
