## Summary

Reviewed the full gRPC client infrastructure layer: the shared `defineGrpcClient` factory in foundation, five per-service client modules in gateway, and three inter-service client modules in sender, parser, and audience. The layer is well-structured — the `defineGrpcClient` factory cleanly eliminates boilerplate, all client facades follow the same pattern, and the health indicator integration is consistent. ESLint layering rules look correct.

Two issues require attention before this layer is considered production-safe: a non-null assertion chain in `defineGrpcClient` that silently corrupts deadline/URL values if env vars are absent, and an unvalidated query parameter path in the smoke controller that will cause proto-level type corruption at runtime. Additionally, `Symbol.for()` usage for DI tokens across multiple apps that share a pnpm workspace introduces a cross-app collision risk that violates the project's no-magic-values convention (the project mandates `Symbol()`, not `Symbol.for()`).

## Critical Issues

### CR-01: `Symbol.for()` used for DI tokens — violates no-magic-values convention and creates cross-app token collision

**Files:**
- `apps/gateway/src/infrastructure/clients/auth/auth-client.constants.ts:1-3`
- `apps/gateway/src/infrastructure/clients/sender/sender-client.constants.ts:1-3`
- `apps/gateway/src/infrastructure/clients/parser/parser-client.constants.ts:1-3`
- `apps/gateway/src/infrastructure/clients/audience/audience-client.constants.ts:1-3`
- `apps/gateway/src/infrastructure/clients/notifier/notifier-client.constants.ts:1-3`
- `apps/sender/src/infrastructure/clients/audience/audience-client.constants.ts:1-3`
- `apps/parser/src/infrastructure/clients/notifier/notifier-client.constants.ts:1-3`
- `apps/audience/src/infrastructure/clients/parser/parser-client.constants.ts:1-3`

**Issue:** Every `*-client.constants.ts` file uses `Symbol.for('...')` for both the internal gRPC channel token and the health indicator token. `Symbol.for()` creates symbols in a **global cross-realm registry** — two calls with the same string key return the **same symbol object**. The project convention (CLAUDE.md, no-magic-values skill) explicitly requires `Symbol()` (unique, unregistered) for DI tokens. Using `Symbol.for()` means:

1. `gateway`'s `AUDIENCE_CLIENT_GRPC` and `sender`'s `AUDIENCE_CLIENT_GRPC` are the **same symbol** at runtime (`Symbol.for('AUDIENCE_CLIENT_GRPC') === Symbol.for('AUDIENCE_CLIENT_GRPC')` is `true`). While apps run as separate Node.js processes in production, in test/monorepo tooling contexts (e.g., Jest with shared module graph, NestJS testing module in e2e tests) this can cause the DI container to see a single token resolve to whichever provider was registered last — silently injecting the wrong client.

2. It bypasses TypeScript's structural token uniqueness. If a consumer imports `AUDIENCE_CLIENT_GRPC` from either module, they get the same symbol — there is no way to tell at the type level that they are "different" tokens.

3. The string keys are magic values, directly violating the no-magic-values rule which states "DI tokens use `Symbol()` (not strings)" and by extension not `Symbol.for()` (which is just a string-keyed global symbol).

**Fix:** Replace all `Symbol.for(...)` with `Symbol(...)` in every `*-client.constants.ts`:

```typescript
// Before
export const AUTH_GRPC_HEALTH = Symbol.for('AUTH_GRPC_HEALTH');
export const AUTH_CLIENT_GRPC = Symbol.for('AUTH_CLIENT_GRPC');

// After
export const AUTH_GRPC_HEALTH = Symbol('AUTH_GRPC_HEALTH');
export const AUTH_CLIENT_GRPC = Symbol('AUTH_CLIENT_GRPC');
```

Apply the same change across all 8 constants files. The description string inside `Symbol(...)` is only used for debugging (`.toString()` / `Symbol.keyFor()`) and does not affect uniqueness.

## Warnings

### WR-01: Non-null assertions on `config.get()` in `defineGrpcClient` silently pass `undefined` as typed values

**File:** `packages/foundation/src/external/grpc/clients/define-grpc-client.ts:34,54,57,61`

**Issue:** Four calls to `config.get<T>(key)!` use the non-null assertion operator to cast potentially-`undefined` values to their target types without any runtime check:

- Line 34: `config.get<number>('GRPC_DEADLINE_MS')!` — cast to `number`, passed as `deadlineMs`
- Line 54: `config.get<string>(opts.service.envKeys.GRPC_URL!)!` — cast to `string`, used as `url:`
- Line 57: `config.get<string>('PROTO_DIR')!` — cast to `string`, passed to `resolveProtoPath()`
- Line 61: `config.get<number>('GRPC_DEADLINE_MS')!` — cast to `number`, passed to `createDeadlineInterceptor()`

If any of these env vars is absent from the validated config schema (or if `ConfigService` is misconfigured), `config.get()` returns `undefined`. The `!` suppresses the TypeScript error, so the runtime receives `undefined` typed as `number` or `string`. For `GRPC_DEADLINE_MS` this would produce `NaN` arithmetic in deadline calculations. For `url` it would pass `undefined` directly to the gRPC channel constructor, causing a crash with an opaque error message rather than a clear "missing env var" message at startup.

The project's no-defaults-in-env-schema skill requires all env vars to be required in the Zod schema. If they are present in the schema, `config.get()` is safe after validation. If they are not, the assertions are a ticking bomb.

**Fix:** Either assert via a guard that throws a clear error at factory time, or validate that these keys exist in the env schema and document that assumption:

```typescript
// Option A: explicit guard in the factory (defensive)
useFactory: (config: ConfigService) => {
  const url = config.get<string>(opts.service.envKeys.GRPC_URL!);
  const protoDir = config.get<string>('PROTO_DIR');
  const deadlineMs = config.get<number>('GRPC_DEADLINE_MS');
  if (!url || !protoDir || !deadlineMs) {
    throw new Error(
      `GrpcClient[${String(opts.grpcToken)}]: required config keys missing`,
    );
  }
  return {
    transport: Transport.GRPC,
    options: {
      url,
      package: [opts.service.grpc.package, GRPC_CLIENT_HEALTH.PACKAGE],
      protoPath: [
        resolveProtoPath(opts.service.grpc.package, protoDir),
        require.resolve('grpc-health-check/proto/health/v1/health.proto'),
      ],
      channelOptions: {
        interceptors: [createDeadlineInterceptor(deadlineMs)],
      },
    },
  };
},

// Option B: verify GRPC_DEADLINE_MS and PROTO_DIR are in the global env schema
// (preferred — keeps factory clean, relies on schema validation at app startup)
```

Also note that `opts.service.envKeys.GRPC_URL!` on line 54 applies a non-null assertion to `envKeys.GRPC_URL` itself, meaning if the service declaration has no `GRPC_URL` key defined, this silently proceeds. Prefer an explicit check or ensure the type system enforces this.

### WR-02: Unvalidated query parameters passed as required proto fields in `StorageSmokeController`

**File:** `apps/gateway/src/test/storage-smoke.controller.ts:23-24,37-38`

**Issue:** The `@Delete` endpoints extract `bucket` and `key` from query parameters and pass them directly to `cleanupStorageSmoke({ bucket, key })`:

```typescript
cleanupParserSmoke(
  @Query('bucket') bucket: string,
  @Query('key') key: string,
): Promise<ParserProto.CleanupSmokeResponse> {
  return this.parser.cleanupStorageSmoke({ bucket, key });
}
```

TypeScript types `bucket` and `key` as `string`, but `@Query()` without a `ParseStringPipe` or `ValidationPipe` transformation will produce `undefined` if the query parameter is absent from the request. This `undefined` is then passed to the gRPC method as a required proto field. The proto layer will either crash with a type error or silently send an empty string/zero value depending on how ts-proto handles `undefined` on required fields. Since `ValidationPipe` is presumably global on the Gateway, `@Query()` string params are still not subject to `class-validator` unless a DTO class is used — raw `@Query()` bindings bypass transformation and validation.

This is a test/smoke controller but it is wired into the live Gateway module via `SmokeTestModule` and is reachable in production builds.

**Fix:** Add validation or a default to make the failure explicit:

```typescript
import { Query, BadRequestException } from '@nestjs/common';

cleanupParserSmoke(
  @Query('bucket') bucket: string | undefined,
  @Query('key') key: string | undefined,
): Promise<ParserProto.CleanupSmokeResponse> {
  if (!bucket || !key) {
    throw new BadRequestException('bucket and key query params are required');
  }
  return this.parser.cleanupStorageSmoke({ bucket, key });
}
```

Apply the same fix to `cleanupNotifierSmoke`.

### WR-03: `SmokeTestModule` and `StorageSmokeController` are registered in the production module graph

**File:** `apps/gateway/src/test/smoke-test.module.ts:5,9`

**Issue:** `SmokeTestModule` imports `ParserClientModule.forRoot()` and `NotifierClientModule.forRoot()` independently from `GrpcClientsModule`. This means in a Gateway context where both `GrpcClientsModule` and `SmokeTestModule` are imported, two separate instances of `ParserClientModule` and `NotifierClientModule` are registered. Each `ClientsModule.registerAsync()` call creates a separate gRPC channel. This doubles the open connections to parser and notifier when the smoke test module is active.

Additionally, the TODO comment on line 5 (`TODO(remove-before-release): Phase 24 HTTP framework smoke endpoints`) confirms this is meant to be removed. Until it is, it creates unnecessary resource consumption and exposes unauthenticated test endpoints in production (`DELETE /test/parser/storage-service?bucket=X&key=Y`).

**Fix:** Either remove `SmokeTestModule` from the production Gateway module before release (as the TODO indicates), or guard its registration behind a config flag:

```typescript
// In gateway.module.ts
imports: [
  // ...
  ...(config.get('ENABLE_SMOKE_ENDPOINTS') === 'true' ? [SmokeTestModule] : []),
]
```

Note: per project convention, this config flag must be a required env var in the schema (no defaults, no optionals).

### IN-01: Internal DI tokens exported from barrel files contrary to their "internal" comment

**Files:**
- `apps/sender/src/infrastructure/clients/audience/index.ts:3`
- `apps/parser/src/infrastructure/clients/notifier/index.ts:3`
- `apps/audience/src/infrastructure/clients/parser/index.ts:3`
- `apps/gateway/src/infrastructure/clients/auth/index.ts:3`

**Issue:** Each barrel `index.ts` re-exports the `*_CLIENT_GRPC` token (e.g., `AUDIENCE_CLIENT_GRPC`, `NOTIFIER_CLIENT_GRPC`, `PARSER_CLIENT_GRPC`, `AUTH_CLIENT_GRPC`). The corresponding constants files all carry the comment "Internal to this module — the ClientGrpc instance for X channel." Exporting internal tokens invites misuse: a consumer could inject the raw `ClientGrpc` instance instead of the typed facade.

**Fix:** Remove `*_CLIENT_GRPC` from the barrel exports. Only the health token and the client facade class need to be public:

```typescript
// apps/sender/src/infrastructure/clients/audience/index.ts
export * from './audience.client';
export * from './audience-client.module';
export { AUDIENCE_GRPC_HEALTH } from './audience-client.constants';
// AUDIENCE_CLIENT_GRPC intentionally not exported (internal gRPC channel token)
```
