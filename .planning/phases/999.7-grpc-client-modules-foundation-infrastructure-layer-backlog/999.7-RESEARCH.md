# Phase 999.7: Перенести gRPC client modules из foundation в infrastructure layer сервисов - Research

**Researched:** 2026-04-17
**Domain:** NestJS DynamicModule factories, gRPC client decoupling, monorepo layer architecture
**Confidence:** HIGH

## Summary

This phase moves 5 per-service gRPC client modules (Auth, Sender, Parser, Audience, Notifier) from `packages/foundation/` into `apps/{consumer}/src/infrastructure/clients/{upstream}/`, eliminating foundation's dependency on `@email-platform/contracts`. A new `defineGrpcClient()` factory function in foundation encapsulates the ~60 lines of boilerplate (ClientsModule.registerAsync, health indicator, deadline interceptor) into a ~15-line consumer-side module.

The critical technical finding is that NestJS DynamicModule **requires a `module` property referencing a class**, so `defineGrpcClient()` cannot return a standalone DynamicModule object -- it must return providers/imports that the consumer's `@Module` class uses in its `static forRoot()`. This matches the existing `httpClientProvider()` pattern (returns `Provider`, not `DynamicModule`). The alternative approach (returning a full DynamicModule with a dynamically-created class) is technically possible but fragile and non-standard.

**Primary recommendation:** Model `defineGrpcClient()` as a function returning `{ providers: Provider[], imports: DynamicModule[] }` (not a full DynamicModule), keeping the consumer's `@Module` class as the module identity owner. Constants (`*_GRPC_HEALTH`, `*_CLIENT_GRPC`) stay in per-service constants files in the consumer app.

### Pattern 1: `defineGrpcClient()` Factory Function

**What:** A foundation-level helper that generates the NestJS providers and imports needed for a gRPC client module, without knowing which specific service it connects to.

**When to use:** Every per-service gRPC client module in apps/.

**Critical Design Decision: Returning providers+imports, NOT a DynamicModule.**

NestJS DynamicModule requires `module: SomeClass` referencing the host module class. A plain function cannot create this class identity. Two approaches exist:

**Option A (Recommended): Return building blocks, consumer owns the module class.**
```typescript
// packages/foundation/src/external/grpc/clients/define-grpc-client.ts
import type { DynamicModule, Provider } from '@nestjs/common';
import { ClientsModule, Transport } from '@nestjs/microservices';
import type { ClientGrpc } from '@nestjs/microservices';
import { ConfigService } from '@nestjs/config';
import { TerminusModule, HealthIndicatorService } from '@nestjs/terminus';
import { ClsService } from 'nestjs-cls';
import type { GrpcServiceDeclaration } from '@email-platform/config';
import { resolveProtoPath } from '../proto-resolver';
import { createDeadlineInterceptor } from '../../resilience/grpc-deadline.interceptor';
import { GRPC_CLIENT_HEALTH } from './clients.constants';
import { GrpcClientHealthIndicator } from './grpc-client-health.indicator';

export interface DefineGrpcClientOpts {
  readonly service: GrpcServiceDeclaration;
  readonly clientToken: symbol;
  readonly healthToken: symbol;
  readonly grpcToken: symbol;
}

export interface GrpcClientBuildResult {
  readonly imports: DynamicModule[];
  readonly providers: Provider[];
  readonly exports: symbol[];
}

export function defineGrpcClient<T extends object>(
  opts: DefineGrpcClientOpts,
  build: (grpc: ClientGrpc, cls: ClsService, deadlineMs: number) => T,
): GrpcClientBuildResult {
  const { service, clientToken, healthToken, grpcToken } = opts;

  const facadeProvider: Provider = {
    provide: clientToken,
    inject: [grpcToken, ClsService, ConfigService],
    useFactory: (grpc: ClientGrpc, cls: ClsService, config: ConfigService) =>
      build(grpc, cls, config.get<number>('GRPC_DEADLINE_MS')!),
  };

  const healthProvider: Provider = {
    provide: healthToken,
    inject: [HealthIndicatorService, grpcToken],
    useFactory: (his: HealthIndicatorService, grpc: ClientGrpc) =>
      new GrpcClientHealthIndicator(his, grpc),
  };

  return {
    imports: [
      TerminusModule,
      ClientsModule.registerAsync([
        {
          name: grpcToken,
          inject: [ConfigService],
          useFactory: (config: ConfigService) => ({
            transport: Transport.GRPC,
            options: {
              url: config.get<string>(service.envKeys.GRPC_URL!)!,
              package: [service.grpc.package, GRPC_CLIENT_HEALTH.PACKAGE],
              protoPath: [
                resolveProtoPath(service.grpc.package, config.get<string>('PROTO_DIR')!),
                require.resolve('grpc-health-check/proto/health/v1/health.proto'),
              ],
              channelOptions: {
                interceptors: [
                  createDeadlineInterceptor(config.get<number>('GRPC_DEADLINE_MS')!),
                ],
              },
            },
          }),
        },
      ]),
    ],
    providers: [facadeProvider, healthProvider],
    exports: [clientToken, healthToken],
  };
}
```

**Consumer-side module (~15 lines):**
```typescript
// apps/gateway/src/infrastructure/clients/auth/auth-client.module.ts
import { Module, type DynamicModule } from '@nestjs/common';
import { SERVICE } from '@email-platform/config';
import { defineGrpcClient } from '@email-platform/foundation';
import { AuthClient } from './auth.client';
import { AUTH_CLIENT_GRPC, AUTH_GRPC_HEALTH } from './auth-client.constants';

const grpc = defineGrpcClient(
  {
    service: SERVICE.auth,
    clientToken: SERVICE.auth.diToken,
    healthToken: AUTH_GRPC_HEALTH,
    grpcToken: AUTH_CLIENT_GRPC,
  },
  (grpcClient, cls, deadlineMs) => new AuthClient(grpcClient, cls, deadlineMs),
);

@Module({})
export class AuthClientModule {
  static forRoot(): DynamicModule {
    return {
      module: AuthClientModule,
      imports: grpc.imports,
      providers: grpc.providers,
      exports: grpc.exports,
    };
  }
}
```

**Option B (NOT recommended): Create class dynamically.**
```typescript
// This works but is fragile and non-standard

      return { module: GeneratedModule, ... };

```

### Pattern 3: Symbol.for() Token Safety with Shared Tokens

**What:** `Symbol.for()` tokens are global singletons keyed by string. When gateway and sender both define `AUDIENCE_CLIENT_GRPC = Symbol.for('AUDIENCE_CLIENT_GRPC')`, they reference the same Symbol identity -- but this is safe because each app runs in a separate Node.js process. [VERIFIED: codebase uses Symbol.for() throughout, confirmed in define-service.ts]

**Important:** `SERVICE.auth.diToken` is `Symbol.for('AUTH_GRPC_CLIENT')` -- defined once in `packages/config/src/catalog/define-service.ts`. Each consumer uses this same token for the facade provider. Health and internal grpc tokens (`AUTH_GRPC_HEALTH`, `AUTH_CLIENT_GRPC`) are defined per-consumer in constants files.

### Anti-Patterns to Avoid
- **Putting contracts imports in foundation:** The entire point of this phase is removing `@email-platform/contracts` from foundation. `defineGrpcClient()` must NOT import contracts.
- **Generating module classes dynamically:** NestJS relies on class identity for deduplication. Dynamic classes break this.
- **Using `SERVICE.auth.diToken` for the internal ClientGrpc instance:** The `diToken` is for the typed facade. The raw `ClientGrpc` needs its own Symbol (`AUTH_CLIENT_GRPC`).
- **Skipping the health indicator:** Every gRPC client module must export a health token -- even cross-service ones.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| gRPC client registration boilerplate | Manual ClientsModule.registerAsync in each module | `defineGrpcClient()` factory | 60 lines of identical boilerplate per service, 5 config points to get wrong |
| Health indicator factory | Manual Provider in each module | Included in `defineGrpcClient()` result | GrpcClientHealthIndicator construction is identical for all services |
| Proto path resolution | Manual join/resolve in each module | `resolveProtoPath()` from foundation | Handles monorepo root detection, absolute vs relative paths |
| Deadline interceptor | Manual interceptor setup | `createDeadlineInterceptor()` from foundation | Already battle-tested, handles missing deadline case |

## Common Pitfalls

### Pitfall 1: DynamicModule `module` Property
**What goes wrong:** Trying to return a DynamicModule from `defineGrpcClient()` without a real module class.
**Why it happens:** NestJS requires `module: SomeClass` for module identity/deduplication.
**How to avoid:** Return `{ providers, imports, exports }` and let the consumer's `@Module` class own the DynamicModule identity.
**Warning signs:** Runtime error "Nest could not find module" or silent module deduplication issues.

### Pitfall 2: Circular Foundation-Contracts Dependency
**What goes wrong:** `defineGrpcClient()` accidentally imports `@email-platform/contracts`.
**Why it happens:** Copy-paste from existing client modules which import proto types.
**How to avoid:** `defineGrpcClient()` is generic -- it takes a build callback that creates the client. The callback is defined in the consumer (which legitimately imports contracts).
**Warning signs:** ESLint should catch this, but the rule currently does NOT restrict foundation->contracts. Need to verify.

### Pitfall 3: ESLint Missing foundation->contracts Restriction
**What goes wrong:** ESLint currently allows `packages/foundation/**` to import `@email-platform/contracts`.
**Why it happens:** The ESLint `no-restricted-imports` rule for foundation only blocks imports from apps, not from contracts.
**How to avoid:** Add `@email-platform/contracts` to the foundation restricted imports after migration is complete. This validates the cleanup.
**Warning signs:** Foundation builds with leftover contracts imports.

### Pitfall 4: `require.resolve` in defineGrpcClient()
**What goes wrong:** `require.resolve('grpc-health-check/proto/health/v1/health.proto')` may fail if `grpc-health-check` is not a dependency of the consumer app.
**Why it happens:** `require.resolve` resolves relative to the calling module's location. If `defineGrpcClient()` is in foundation but called from an app, resolution may differ.
**How to avoid:** `grpc-health-check` is listed in foundation's dependencies. Since module=node16 and CJS emission, `require.resolve` follows the standard Node resolution from foundation's installed deps. This works because the function body is compiled INTO foundation's dist. [VERIFIED: Phase 23 decision -- require.resolve works with module=node16 CJS]
**Warning signs:** "Cannot find module 'grpc-health-check/proto/...'" at runtime.

### Pitfall 5: `config.get<T>(KEY)!` Non-Null Assertions
**What goes wrong:** TypeScript silences null check, runtime gets undefined if env var missing.
**Why it happens:** ConfigService.get() returns T | undefined.
**How to avoid:** Deferred to Phase 999.2 (type-safe config access). For now, use `config.get<number>('GRPC_DEADLINE_MS')!` as-is -- the Zod schema guarantees the value exists at boot. Document as known tech debt.
**Warning signs:** Runtime NaN or undefined in gRPC options.

### Pitfall 6: Barrel Export Completeness After Cleanup
**What goes wrong:** After removing 5 per-service exports from foundation barrel, consumer code that still imports from `@email-platform/foundation` breaks.
**Why it happens:** Gateway, its health controller, test files, and grpc-client-sanity.ts all import specific client types from foundation.
**How to avoid:** Update ALL import sites before or atomically with the barrel cleanup. Checklist:
- `apps/gateway/src/infrastructure/clients/grpc-clients.module.ts` -- 5 module imports
- `apps/gateway/src/health/health.controller.ts` -- 5 health token imports + GrpcClientHealthIndicator type
- `apps/gateway/src/test/grpc-client-sanity.ts` -- 5 client type imports
- `apps/gateway/src/test/storage-smoke.controller.ts` -- ParserClient, NotifierClient types
- `apps/gateway/src/test/smoke-test.module.ts` -- ParserClientModule, NotifierClientModule
**Warning signs:** TypeScript build errors after barrel update.

## Discretion Recommendations

### GRPC_TOKEN location: generate inside defineGrpcClient() vs constants file

**Recommendation: Keep in per-service constants file.**

Rationale: The `grpcToken` (e.g., `AUTH_CLIENT_GRPC`) is used in the `@Inject()` decorator of the client class constructor. If `defineGrpcClient()` generates it internally, the client class can't reference it for `@Inject()`. The client needs the token at class definition time (decorator), not at factory call time. [VERIFIED: auth.client.ts line 14 uses `@Inject(AUTH_CLIENT_GRPC)`]

### Migration order

**Recommendation: Gateway first, then cross-service (sender, parser, audience).**

Rationale: Gateway has all 5 clients, making it the most comprehensive test. If defineGrpcClient() works for all 5 in gateway, cross-service apps are trivial (one client each). Foundation cleanup comes last, after all consumers are migrated.

### GrpcClientsModule compositor for single-upstream services

**Recommendation: Skip compositor for single-upstream services.**

Rationale: When sender only imports AudienceClientModule, a GrpcClientsModule compositor adds indirection without value. The root module can directly import `AudienceClientModule.forRoot()`. If a second upstream is added later, the compositor can be introduced then.
