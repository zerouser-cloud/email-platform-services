## Хелпер в foundation

| Option | Description | Selected |
|--------|-------------|----------|
| defineGrpcClient() factory (рек.) | Factory-функция принимает { service, clientClass }, возвращает { Module, HEALTH_TOKEN, GRPC_TOKEN }. ~15 строк per-service. Аналог httpClientProvider из Phase 24.1 | ✓ |
| createGrpcClientModule() DynamicModule | Статический метод на базовом классе, возвращает DynamicModule напрямую. Проще, но меньше контроля | |
| Оставить как есть | Перенести 60-строчные модули as-is. Упрощение — отдельная фаза | |

**User's choice:** defineGrpcClient() factory
**Notes:** Пользователь запросил примеры кода перед выбором. Были показаны оба варианта с preview. Выбран вариант A как более консистентный с httpClientProvider и сохраняющий явный @Module + forRoot() паттерн. Пользователь отметил: "Нужно будет проверить на этапе анализа что там все ок с типизацией и не будет никаких подводных камней".

## Файловая структура

| Option | Description | Selected |
|--------|-------------|----------|
| По upstream-сервису (рек.) | Per upstream директория: auth/, sender/, parser/, audience/, notifier/ с 4 файлами каждая | ✓ |
| Плоская структура | Все файлы в одной директории clients/. 15+ файлов рядом | |
| grpc/ поддиректория | clients/grpc/auth/, clients/grpc/sender/ — отделяет от HTTP клиентов | |

**User's choice:** По upstream-сервису
**Notes:** Preview показал полную структуру дерева. GrpcClientsModule остаётся на уровне clients/ как композитор.

## Scope миграции

| Option | Description | Selected |
|--------|-------------|----------|

**User's choice:** Gateway + известные consumers
**Notes:** Выбраны 3 cross-service связи: sender→audience, parser→notifier, audience→parser.
