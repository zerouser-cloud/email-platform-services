# Phase 999.7: Перенести gRPC client modules из foundation в infrastructure layer сервисов - Context

**Gathered:** 2026-04-17
**Status:** Ready for planning

<domain>
## Phase Boundary

Декаплинг foundation от contracts: 5 typed-facade gRPC клиентов (`AuthClient`, `SenderClient`, `ParserClient`, `AudienceClient`, `NotifierClient`) и их модули переезжают из `packages/foundation/src/external/grpc/clients/{service}/` в `apps/{consumer}/src/infrastructure/clients/{upstream}/`. Foundation остаётся domain-agnostic — предоставляет только инфраструктурные примитивы (`AbstractGrpcClient`, `GrpcClientHealthIndicator`, `defineGrpcClient()` factory, deadline interceptor, logging types). Импорт `@email-platform/contracts` из foundation исчезает полностью.

Out of scope: новые gRPC методы (бизнес-логика), server-side gRPC, correlation ID propagation (Phase 27), retry policy.

</domain>

<decisions>
## Implementation Decisions

### Foundation helper
- **D-01:** `defineGrpcClient()` factory-функция в foundation. Принимает `{ service: GrpcServiceDeclaration, clientClass: Class }`, возвращает `{ Module: DynamicModule, HEALTH_TOKEN: symbol, GRPC_TOKEN: symbol }`. Инкапсулирует boilerplate: `ClientsModule.registerAsync`, protoPath resolution, health indicator factory, deadline interceptor. Аналогичен `httpClientProvider` из Phase 24.1.
- **D-02:** Per-service модуль в consumer-сервисе становится ~15 строк: import `defineGrpcClient`, создать `const grpc = defineGrpcClient(...)`, обернуть в `@Module` с `static forRoot()`. Типизация и edge cases верифицируются на этапе research.

### Файловая структура
- **D-03:** Per upstream-service директория: `apps/{consumer}/src/infrastructure/clients/{upstream}/` содержит 4 файла:
  - `{upstream}.client.ts` — extends `AbstractGrpcClient<XxxProto.XxxServiceClient>`, методы из proto
  - `{upstream}-client.module.ts` — `defineGrpcClient()` + `@Module` с `static forRoot()`
  - `{upstream}-client.constants.ts` — `HEALTH_TOKEN`, `GRPC_TOKEN` (Symbol.for)
  - `index.ts` — barrel export
- **D-04:** `GrpcClientsModule` остаётся на уровне `infrastructure/clients/grpc-clients.module.ts` как композитор нужных клиентов для данного сервиса.

### Scope миграции
- **D-05:** Gateway (все 5 клиентов) + 3 cross-service связи:
  - `sender` → `AudienceClient` (GetRecipientsByGroup, MarkAsSent)
  - `parser` → `NotifierClient` (оповещение о завершении парсинга)
  - `audience` → `ParserClient` (импорт контактов через parser)
- **D-06:** Полный facade — каждый client class содержит все методы из proto, независимо от того сколько использует конкретный consumer. Бизнес-логика решает какие методы вызывать.

### Очистка foundation
- **D-07:** Полная очистка — 5 per-service директорий (`auth/`, `sender/`, `parser/`, `audience/`, `notifier/`) удаляются из `packages/foundation/src/external/grpc/clients/`. Никаких deprecated re-export обёрток.
- **D-08:** В foundation остаётся (domain-agnostic каркас):
  - `AbstractGrpcClient` — абстрактная база с Observable→Promise, logging, deadline
  - `GrpcClientHealthIndicator` — health indicator для gRPC upstream
  - `defineGrpcClient()` — новая factory-функция (D-01)
  - `clients.constants.ts` — shared constants (GRPC_CLIENT_HEALTH, GRPC_CLIENT_LOG, GRPC_CLIENT_DEADLINE)
  - `grpc-client-logging.types.ts` — CallOpts, GrpcClientLogFields
  - `proto-resolver.ts` — resolveProtoPath
  - `resilience/grpc-deadline.interceptor.ts` — createDeadlineInterceptor
- **D-09:** Barrel `packages/foundation/src/external/grpc/clients/index.ts` обновляется: убираются 5 per-service export блоков, добавляется export `defineGrpcClient`.

### Claude's Discretion
- Точная сигнатура generic types в `defineGrpcClient()` — главное чтобы TypeScript-проверка работала end-to-end
- Нужен ли `GRPC_TOKEN` в constants или он генерируется внутри `defineGrpcClient()`
- Порядок миграции (gateway первый, потом cross-service, или параллельно)
- Нужен ли `GrpcClientsModule` композитор в sender/parser/audience (если только 1 upstream — может быть излишне)

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `AbstractGrpcClient<T>` — полностью domain-agnostic, не импортирует contracts, остаётся в foundation
- `GrpcClientHealthIndicator` — domain-agnostic, использует grpc.health.v1 protocol, остаётся
- `defineGrpcClient()` — новая factory (создаётся в этой фазе), аналогична `httpClientProvider` из Phase 24.1
- `SERVICE` каталог с Symbol.for() DI tokens — единый источник истины, без изменений
- Все 5 `*.client.ts` файлов — переносятся as-is, только меняются import paths

### Established Patterns
- **httpClientProvider pattern (Phase 24.1):** factory-функция `httpClientProvider(params)` возвращает providers для HTTP клиента. `defineGrpcClient()` следует этому паттерну.
- **Per-service infrastructure modules:** HTTP клиенты уже в `apps/{service}/src/infrastructure/clients/{api}/` (telegram, appstorespy, cloudfn). gRPC клиенты следуют тому же layout.
- **Foundation external/internal partition (Phase 22.1):** public API через `@email-platform/foundation`, internals через `@email-platform/foundation/internal`.

### Integration Points
- `apps/gateway/src/infrastructure/clients/grpc-clients.module.ts` — главная точка обновления
- `apps/gateway/src/health/health.controller.ts` — 5x `*_GRPC_HEALTH` injection
- `apps/gateway/src/test/` — smoke controllers + sanity probe
- `apps/sender/src/sender.module.ts` — добавляется AudienceClientModule
- `apps/parser/src/parser.module.ts` — добавляется NotifierClientModule
- `apps/audience/src/audience.module.ts` — добавляется ParserClientModule
- `packages/foundation/package.json` — exports field, возможно обновление subpath

</code_context>

<specifics>
## Specific Ideas

- `defineGrpcClient()` по духу аналогичен `httpClientProvider` — минимальный конфиг-объект на вход, готовые NestJS-артефакты на выход
- При переносе `*.client.ts` файлы копируются as-is, меняются только import paths (contracts уже импортируются напрямую из `@email-platform/contracts`)
- ESLint layered architecture rule уже запрещает apps импортировать друг друга — каждый consumer создаёт свой собственный экземпляр client class
- Для sender/parser/audience с одним upstream-клиентом: решение о необходимости GrpcClientsModule композитора — на усмотрение Claude

</specifics>
