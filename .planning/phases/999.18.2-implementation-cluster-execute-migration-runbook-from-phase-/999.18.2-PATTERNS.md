**Critical insight — gRPC Health is ALREADY registered structurally:**

Текущий `createGrpcServerOptions` factory из `packages/foundation/src/external/grpc/grpc-server.factory.ts` УЖЕ инстанцирует `HealthImplementation` и регистрирует к gRPC server через `addToServer(server)`:

```typescript
// packages/foundation/src/external/grpc/grpc-server.factory.ts lines 23-43 (current state)
export function createGrpcServerOptions(
  service: GrpcServiceIdentity,
  grpcPort: number,
  protoDir: string,
): MicroserviceOptions {
  const healthImpl = new HealthImplementation({
    [HEALTH.GRPC_SERVICE_OVERALL]: HEALTH.GRPC_STATUS_SERVING,
  });

  return {
    transport: Transport.GRPC,
    options: {
      package: service.grpc.package,
      protoPath: resolveProtoPath(service.grpc.package, protoDir),
      url: `${SERVER.DEFAULT_HOST}:${grpcPort}`,
      onLoadPackageDefinition: (_pkg: unknown, server: Server) => {
        healthImpl.addToServer(server);
      },
    },
  };
}
```

Это значит Wave 2 task #6 ("register `grpc.health.v1.Health`") по факту structurally already в place — `grpc-health-check` package уже в `packages/foundation/package.json` deps (line 29), `HealthImplementation.addToServer(server)` уже invoked в `onLoadPackageDefinition` callback per service. **Planner MUST verify (не re-implement)** что после Wave 2 cleanup эта existing wiring is preserved + grpc_health_probe binary в container смогает достучаться. ### 6. NEW `apps/{auth,sender,parser,audience,notifier}/src/infrastructure/bootstrap/health/grpc-health.module.ts` (5 new files)

 * wires TerminusModule + foundation PersistenceModule (exports PERSISTENCE_HEALTH)
 * + AppCacheModule (re-exports foundation CacheModule, namespace from catalog)

  imports: [TerminusModule, PersistenceModule.forRootAsync(), AppCacheModule],
  controllers: [HealthController],

**Open question for planner — does Wave 2 task #6 actually need this NEW module?**

Per critical insight в §5 above: `HealthImplementation.addToServer(server)` call lives inside `createGrpcServerOptions` factory (foundation package). The `grpc-health-check` package's API is **functional**, not a NestJS module — `HealthImplementation` is instantiated as plain JS object, not as `@Injectable()` provider. There's no DI surface to wrap в `@Module({})`.

**Two design paths planner must choose between (plan-time decision):**

- **Path A — NO new module.** Wave 2 task #6 simplifies к "verify existing `createGrpcServerOptions` registers gRPC Health" — no new file authoring. RUNBOOK Wave 2 task #6 wording «(если needed) `apps/{...}/src/infrastructure/bootstrap/health/grpc-health.module.ts`» explicitly leaves this conditional ("если needed"). Planner concludes **NOT needed** because `HealthImplementation.addToServer` call site is already в foundation factory.
- **Path B — Author new module for symmetry.** Each service gets `grpc-health.module.ts` that wraps service-state mutation API of `HealthImplementation` (e.g., expose `setStatus(service, status)` so app-code can mark service NOT_SERVING during graceful shutdown). This is forward-looking enhancement, NOT blocked by RUNBOOK acceptance criteria. **Planner SHOULD defer to RE-EVAL-TRIGGERS** if not strictly required.

**Recommended (planner's call):** Path A — RUNBOOK acceptance criterion (`grpc_health_probe -addr=localhost:50051` returns 0) is satisfied by existing wiring. Don't add ceremony. If Path B chosen, file shape would mirror REST sibling shape above (placement в `infrastructure/bootstrap/health/` per CLAUDE.md NestJS↔Hexagonal mapping table — `bootstrap/health/` partition).
