## Smoke Notes

**Multi-arch buildx (Task 3 step 1):** The configured local builder is the default `docker` driver, which serves a single platform per-build by design. Concurrent `linux/amd64,linux/arm64` build requires either a `docker-container` driver buildx instance with QEMU emulation, or a remote multi-arch BuildKit. Per user decision 1, accepted single-arch local fallback as sufficient pre-commit evidence — manifest probe (Task 1) already proved the v0.4.48 manifest list covers both architectures, and CI builds with multi-arch BuildKit will validate real cross-arch on merge. No blocker.

**Isolated mode:** `pnpm reset:isolated` → `pnpm build` (host typecheck OK, all 6 apps + 3 packages clean) → `pnpm start:isolated`. All 5 gRPC services (auth, sender, parser, audience, notifier) reached compose-`(healthy)` after the start_period — empirical proof the bumped v0.4.48 binary at `/usr/local/bin/grpc_health_probe` executes inside the running containers and reports SERVING via `grpc.health.v1.Health`. Gateway compose-`(healthy)` (Plan 02 busybox-as-wget invariant intact). Direct probes:

- `docker compose exec auth grpc_health_probe -addr=:50051` → exit 0, status SERVING
- `docker compose exec sender grpc_health_probe -addr=:50052` → exit 0, status SERVING
- `curl -fsS http://localhost:4000/health/ready` → HTTP 200, all 5 gRPC + cache `up`

**Native mode:** `pnpm reset:native` → `pnpm start:native`. All 6 services boot on host Node (ts-node-dev). `curl -fsS http://localhost:3000/health/ready` → HTTP 200. Native does NOT exercise `app.Dockerfile`; this run confirms infra-side has no regression and matches Plans 01/02 baseline.
