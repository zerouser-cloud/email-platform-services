<objective>
Migrate the four gRPC-service k8s base manifests (`deploy/k8s/base/auth.yaml`, `sender.yaml`, `parser.yaml`, `audience.yaml`) from `exec.command: [/usr/local/bin/grpc_health_probe, -addr=:NNNN]` probes to k8s 1.24+ native declarative `grpc: { port: NNNN }` probes. Each manifest carries one `livenessProbe` and one `readinessProbe` block — 8 probe blocks total across 4 files. Tuning fields (`initialDelaySeconds`, `periodSeconds`, `timeoutSeconds`) are preserved verbatim. The in-image `/usr/local/bin/grpc_health_probe` binary is RETAINED because docker-compose `healthcheck.test:` for the 5 gRPC services in `infra/docker-compose.yml` still invokes it.

Purpose: Production readiness on k8s 1.27+ clusters. With declarative `grpc:` probes, kubelet itself opens a gRPC connection to PodIP:port and calls `grpc.health.v1.Health/Check` — no shell-exec into the container, no per-probe process spawn (`exec` probes spawn a new process every interval, ~1.5 MB of binary memory + Go runtime startup × 6 probes/min × N pods), no dependency on the binary being on PATH. The server-side endpoint (`HealthImplementation` from `grpc-health-check` npm in `packages/foundation/src/external/grpc/grpc-server.factory.ts`) is the SAME endpoint compose's `grpc_health_probe` already calls — kubelet just removes the middleman. ASVS L1 §10.3 supply-chain (one fewer userland binary that probes need to trust) and §14.2.5 (kubelet probe is built into kubelet itself, no third-party Go binary in the probe path).

Output:

- `deploy/k8s/base/auth.yaml` — `livenessProbe` and `readinessProbe` blocks rewritten from `exec.command:` form to `grpc:` form with `port: 50051`. Tuning fields verbatim.
- `deploy/k8s/base/sender.yaml` — same shape, `port: 50052`.
- `deploy/k8s/base/parser.yaml` — same shape, `port: 50053`.
- `deploy/k8s/base/audience.yaml` — same shape, `port: 50054`.

Scope discipline: ONLY the 4 base manifests are touched. Gateway uses HTTP probes (not gRPC) and is byte-identical. Notifier has no probe and is byte-identical. Both overlays (`deploy/k8s/overlays/{dev,prod}/kustomization.yaml`) are byte-identical (they patch image newTag + prod replicas, never probe blocks). The Dockerfile is byte-identical (Plan 05 is k8s-side, never Dockerfile-side). The compose file is byte-identical (compose still uses the in-image binary; that contract was set by Plans 01/03/04 and is preserved). No `apps/*` / `packages/*` / CI workflow modifications.

Why `autonomous: false`: the empirical end-to-end probe test requires a live k8s 1.27+ cluster — kubelet's declarative `grpc:` codepath is what we're actually exercising, and only a real kubelet-pod handshake can prove the server's `grpc.health.v1.Health` endpoint is reachable through the new probe transport. Locally we can prove **schema validity** (`kubectl --dry-run=client apply -k`) and **YAML-render correctness** (compare rendered overlay vs expected). Cluster smoke is deferred to whoever rolls the manifests via `kubectl apply -k deploy/k8s/overlays/dev/` (CI's `deploy-dev` job per `.gitlab-ci.yml` line 275, or local cluster via `kind`/`minikube` if the user has one). Task 4 surfaces this distinction: schema gate passes locally; functional gate is deferred to the actual rollout.

Why `wave: 1` and `depends_on: []`: Plan 05 modifies k8s YAML files only. Plan 06 modifies the Dockerfile only. Their `files_modified` sets are disjoint (k8s base manifests vs `infra/docker/app.Dockerfile`). They have zero coupling — no shared file, no shared invariant either touches mutates, no temporal ordering required (unlike Plan 04 which depended on Plan 03 because both rewrote the same FROM line). Both run in Wave 1.
