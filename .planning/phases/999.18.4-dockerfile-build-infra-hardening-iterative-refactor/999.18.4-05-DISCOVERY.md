## Probe (d): baseline overlay render (PRE-edit state)

### Tooling-environment deviation (Rule 3 — auto-fix blocking issue)

The Plan's documented command was:

```
kubectl --dry-run=client apply -k deploy/k8s/overlays/dev/ -o yaml > /tmp/__plan05_overlay_pre.yaml 2>&1
```

In this environment, kubectl 1.35.4 hard-couples `apply --dry-run=client` to live API-server discovery (object recognition step). The active kubectl context points at a stale minikube cluster (`https://192.168.49.2:8443`) which is unreachable from this worktree:

```
$ kubectl --dry-run=client apply -k deploy/k8s/overlays/dev/ -o yaml > /tmp/__plan05_overlay_pre.yaml 2> /tmp/__plan05_overlay_pre.err
EXIT=1
$ cat /tmp/__plan05_overlay_pre.err
# Warning: 'commonLabels' is deprecated. ...
error: error validating "deploy/k8s/overlays/dev/": error validating data:
  failed to download openapi: Get "https://192.168.49.2:8443/openapi/v2?timeout=32s":
  dial tcp 192.168.49.2:8443: i/o timeout
```

`--validate=false` does NOT bypass it (kubectl still calls API discovery for object recognition). `KUBECONFIG=/dev/null` falls back to `localhost:8080`, also unreachable.

**Substitute (Rule 3): `kubectl kustomize` — pure local kustomize render, no API contact.**

`kubectl kustomize` is the modern, recommended way to inspect what `kubectl apply -k` would submit; it is byte-equivalent to `kustomize build` shipped with kubectl 1.21+. It does NOT contact the API server, so it is unaffected by the unreachable minikube context. The output is the exact stream `kubectl apply -k` would POST. All YAML structural validation (kustomize parser + reassembler) is preserved. The k8s-API field-name validation that `--dry-run=client` adds on top is the validation the cluster does at `kubectl apply` time — that is exactly the **deferred end-to-end functional gate** the Plan already acknowledges (objective §"Why `autonomous: false`" + Task 4 §7).
