<objective>
Extract a shared `base` stage from `infra/docker/app.Dockerfile` that consolidates the four duplicated setup directives currently inlined in both the `prod-deps` and `builder` stages. After the refactor:

- New stage `base` lives between `pruner` and `prod-deps`, containing four directives: `WORKDIR /app`, `ENV PNPM_HOME="/pnpm"`, `ENV PATH="$PNPM_HOME:$PATH"`, `RUN corepack enable`.
- `prod-deps` becomes `FROM base AS prod-deps` (inherits the four directives from `base`).
- `builder` becomes `FROM base AS builder` (inherits the four directives from `base`).
- `pruner`, `runner`, `health-probe`, `busybox` stages are byte-identical to HEAD (deliberately not inheriting from `base`; rationale per stage in `<interfaces>` block below).

Purpose: Pure DRY readability refactor — the canonical Vercel/Next.js Dockerfile pattern (`FROM node:VERSION AS base` → multiple inheriting stages) extracted across the wider Node.js Dockerfile ecosystem. After the refactor: ~6 lines of duplication removed (4 directives × 2 stages = 8 directive instances at HEAD → 4 in `base` + 0 in prod-deps + 0 in builder = 4 directive instances; net -4 lines + 4 lines for the `FROM base AS …` headers + 1 new `FROM` for `base` itself; the readability and maintainability gain is per-future-edit consistency: bumping pnpm setup or adding a helper directive happens in ONE place, not two).

Output:

- `infra/docker/app.Dockerfile` — single file modified. New `base` stage inserted between pruner and prod-deps; prod-deps + builder refactored to `FROM base AS …`; their inlined four-directive blocks removed. Stage names preserved (4 existing: pruner, prod-deps, builder, runner); 1 new stage name added (`base`); stage count rises from 6 to 7.

Scope discipline: ONLY `infra/docker/app.Dockerfile` is modified. No `apps/*` / `packages/*` / compose / k8s / CI / docs touched. Pure DRY. The runner stage at `gcr.io/distroless/nodejs22-debian12:nonroot AS runner` is OUT of scope (different base — distroless has no pnpm, no shell; runner deliberately doesn't share the `base` ENV stack). The pruner stage at `FROM node:${NODE_VERSION} AS pruner` is OUT of scope (deliberate — pruner uses `pnpm dlx` which does not need the persistent PNPM_HOME ENV; inheriting from `base` would bloat pruner's ENV without benefit; preserving pruner unchanged minimises diff scope).

**Where to insert the new `base` stage:** AFTER pruner (line 51) and BEFORE prod-deps (line 53). The `base` stage uses `FROM node:${NODE_VERSION} AS base` and contains exactly the four directives consolidated.

**Why `pruner` does NOT inherit from `base` (preserved verbatim by design):**

- `pruner` uses `pnpm dlx turbo prune` (NOT a persistent install). `pnpm dlx` is ephemeral — it doesn't need the `PNPM_HOME` cache directory or `PATH` munging that prod-deps + builder rely on for `pnpm install`. Adding those ENVs to pruner is unused state.
- `pruner` deliberately does `WORKDIR /app` then `RUN corepack enable` then `COPY . .` — its sequencing is constraint-driven (corepack must run BEFORE COPY in case the COPY brings in a `.npmrc` that mutates pnpm behaviour; the COPY brings the FULL workspace, not just manifests). The `base` stage as designed for prod-deps + builder runs `corepack enable` AFTER WORKDIR but with NO `COPY` — different pattern.
- Inheriting pruner from `base` would either (a) add unused PNPM_HOME/PATH, OR (b) require splitting `base` into two stages (one minimal, one with PNPM_HOME) — adding complexity instead of removing it. Net: keep pruner as-is.
- The "duplicated WORKDIR /app" between pruner-base-prod-deps-builder is acceptable — pruner's WORKDIR establishes the workspace root for the FULL workspace COPY, while base+prod-deps+builder's WORKDIR establishes it for the dep-closure-only flow. They're conceptually the same value but different consumers; refactoring all 4 to one stage would couple pruner's lifecycle to base's, which is undesirable.

**Why `runner` does NOT inherit from `base`:**

- `runner` uses `gcr.io/distroless/nodejs22-debian12:nonroot` — completely different base image (distroless has no pnpm, no shell, no `/pnpm` directory possible at runtime).
- Distroless contract per Phase 999.18.3 is sacred — preserving it requires the runner stage to derive directly from the distroless image, NOT from a node:alpine-derived `base`.
- Refactoring runner to inherit from `base` would break the distroless contract entirely.

**Why `health-probe` and `busybox` do NOT inherit from `base`:**

- Both are ephemeral binary-source stages. They derive from external images (Plan 04 digest pins) whose sole purpose is providing a single binary for the runner's `COPY --from=…` directives.
- They have NO need for `WORKDIR`, `PNPM_HOME`, `PATH`, or `corepack`.
- Inheriting from `base` is structurally impossible (those upstream images are NOT node-derived; you can't `FROM base AS health-probe` if the conceptual `health-probe` is `ghcr.io/grpc-ecosystem/grpc-health-probe@sha256:…`).

**Layer-equivalence claim formalized:** The directives executed inside `prod-deps` and `builder` after the refactor are bytewise-identical to those executed pre-refactor — only their ORIGIN differs (now they come from inherited `base` instead of inline). BuildKit's layer caching is content-addressable — the cache key for a layer is `(parent-image-digest, command-string, file-content-hashes)`. Since the parent image (`node:${NODE_VERSION}`) and the command strings (`WORKDIR /app`, `ENV PNPM_HOME=…`, etc.) and file content hashes are identical, the resulting layer SHA256 is identical too. **Provable empirically:** `docker buildx build --target prod-deps --load .` before and after the refactor produces the same final layer ID per `docker image inspect --format '{{.RootFS.Layers}}'`.
