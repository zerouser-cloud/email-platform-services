<objective>
Replace the tag-form pins on the two non-Email-Platform-built base images that supply binaries to the distroless runner — `ghcr.io/grpc-ecosystem/grpc-health-probe:v0.4.48` (Plan 03 baseline) and `busybox:1.37.0-musl` (Plan 02 baseline) — with content-addressable manifest-list digest pins (`@sha256:…`). Both pins go into `infra/docker/app.Dockerfile` Stage 1.0 and Stage 1.0.5 FROM directives. A new `infra/docker/PINS.md` audit-trail registry records the (image, tag-equivalent, digest, harvested-date, verified-by) tuple per pin so future maintainers can re-harvest and rotate without spelunking through commit history.

Purpose: Close the textbook supply-chain attack vector that Plan 03's threat model accepted: tag-form pins are mutable. An attacker with control of `ghcr.io` or Docker Hub (or a network MITM, or a compromised registry CDN) can replace the bytes behind `:v0.4.48` or `:1.37.0-musl` without changing the tag string — our subsequent builds would silently consume the substituted binary. With digest pins, the registry-side bytes are SHA-256-content-addressable: a substituted image would have a different digest, BuildKit would error with "manifest digest mismatch" instead of building. Real-world precedents this defends against: codecov bash uploader (2021), SolarWinds Orion (2020), `ua-parser-js` npm hijack (2021), `event-stream` npm hijack (2018), the persistent stream of compromised Docker Hub images flagged by Sysdig/Aqua reports throughout 2023-2024. ASVS L1 §10.3 ("verify that all third-party software components are pinned to specific versions") and §14.2.5 ("verify that the application uses only software with verifiable supply chain") both call for content-addressable pins for production builds.

Output:

- `infra/docker/app.Dockerfile` — Stage 1.0 and Stage 1.0.5 FROM directives rewritten from `:tag` form to `@sha256:digest` form. Inline `# Digest harvested YYYY-MM-DD` comments added above each FROM. The `ARG GRPC_HEALTH_PROBE_VERSION=v0.4.48` line is either REMOVED (because nothing consumes it once the FROM uses `@sha256:`) or kept as a documentation-only stub with explicit comment (decision surfaced at Task 4 checkpoint).
- `infra/docker/PINS.md` — new file. Markdown table with at minimum 5 columns (image, tag-equivalent, digest, harvested-date, verified-by). Two rows seeded from this Plan: grpc-health-probe v0.4.48 and busybox 1.37.0-musl. Documents the harvest procedure (one short subsection) so future PRs that change either pin can run the same recipe.

Scope discipline: ONLY `infra/docker/app.Dockerfile` and the new `infra/docker/PINS.md` are modified. Plan 03 baseline (v0.4.48 tag) is the input — Plan 04 takes Plan 03's commit as HEAD~1 and rewrites the FROM directives on top of it. The compose file is byte-identical (Plan 02 invariant). The k8s manifests are byte-identical (Plan 05 territory). No CI workflow changes (none reference the digests). No `apps/*` / `packages/*` changes.

Why `autonomous: false`: digest harvest depends on live `docker buildx imagetools inspect` calls against ghcr.io and Docker Hub at the moment Task 1 runs. Network failures, registry rate limits, or stale local Docker daemon state could yield wrong digests. Task 4 (human-verify checkpoint) requires the user to read the harvested digests aloud and confirm them against an independent registry inspection (e.g. `docker manifest inspect`, the GitHub web UI, or `crane manifest`) before Task 5 commits the pins to the Dockerfile. A wrong digest doesn't break security per se (an arbitrary 64-hex-char string would just fail at `docker pull` time with `manifest unknown`), but it does break the build, so verifying-before-commit saves a noisy round-trip.

Why this Plan depends on Plan 03 (`depends_on: ['999.18.4-03']`): the digest is harvested for `ghcr.io/grpc-ecosystem/grpc-health-probe:v0.4.48`. If Plan 04 ran before Plan 03, we'd harvest the v0.4.24 digest then immediately bump to v0.4.48 in a separate plan — wasteful churn (two non-revertable touches on the same FROM line, the second one stranding the first's harvest record).

    ## Why digest pins (not tag pins)

    Tag-form pins (`:v0.4.48`, `:1.37.0-musl`) are mutable. An attacker controlling
    the registry, or a registry CDN compromise, or a network MITM, can replace the
    bytes behind a tag without changing the tag string. Subsequent builds would

    `@sha256:<digest>` the bytes are content-addressable: any substitution would
    yield a different digest, and BuildKit would error with a manifest-mismatch
    error rather than building.

    specific versions") and §14.2.5 ("verify that the application uses only software

    production builds.
