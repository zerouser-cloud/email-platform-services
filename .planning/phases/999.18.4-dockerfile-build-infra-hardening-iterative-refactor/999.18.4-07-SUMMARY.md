## What Was Done

Closed the root cause behind the observed 100+ GB Docker disk accumulation by shipping a **3-layer remediation**:

1. **Reactive (on-demand cleanup)** — `pnpm clean:docker:{diagnose,dangling,builder,safe,nuclear}` orchestration entries delegating to `scripts/clean-docker.sh` dispatcher (5 subcommands; readonly constants top-of-file per `no-magic-values` SKILL; no `--volumes` / `-a` / `--all` flags anywhere; `nuclear` gated behind interactive prompt or `CLEAN_DOCKER_YES=1` env opt-out).
2. **Proactive (automatic GC)** — `builder.gc.policy` block in `/etc/docker/daemon.json` with V2-A conservative thresholds (`defaultReservedSpace=10GB`, cache-mounts `maxUsedSpace=2GB`, regular layers `maxUsedSpace=20GB`, catch-all ceiling `maxUsedSpace=30GB`, `keepDuration=168h`). Tracked in repo as `infra/docker/daemon.json.example` for reproducible apply.
3. **Documentation** — `docs/docker-disk-hygiene.md` operational runbook covering diagnostics, on-demand cleanup catalog, daemon.json apply/rollback procedure, expected disk-usage profile, and a "what this runbook does NOT do" enumeration of 4 prohibited commands (`system prune --volumes`, `volume prune`, `image prune -a`, `buildx prune --all`).

## Decision Record

### V2-A vs V2-B threshold decision (Task 3)

| Option                                           | Decision      | Reason                                                                                                                                                          |
| ------------------------------------------------ | ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **V2-A** Conservative (10/2/20/30 GB, 168h keep) | ✓ chosen      | Faster cold-starts (more cache survives); current machine has plenty of headroom for 30 GB ceiling; aligned with RESEARCH.md default and ASSUMED A1 disposition |
| V2-B Aggressive (5/1/10/15 GB, 168h keep)        | not chosen    | Smaller footprint useful only on constrained disks; cold-start regress 2-4 min between sessions when GC reclaims pnpm-store                                     |
| Custom values                                    | not requested | —                                                                                                                                                               |

### Empirical finding — `_comment_phase` rejected by dockerd 29.4.1

**RESEARCH.md §223 + Plan §219-224 assumed dockerd ignores unknown top-level JSON keys.** This is WRONG for dockerd 29.4.1: the daemon performs strict whitelist validation and exits with `unable to configure the Docker daemon with file /etc/docker/daemon.json: the following directives don't match any configuration option: _comment_phase`. After 3 retries, systemctl marked the service `start-limit-hit`; recovery required `systemctl reset-failed docker.service` before another `start` attempt was accepted.

**Fix:** dropped `_comment_phase` entirely from `infra/docker/daemon.json.example`. Banner / provenance / apply procedure / rollback / expected disk profile already live in `docs/docker-disk-hygiene.md` (committed in `5a222a0`). The `.example` file is now pure JSON byte-matching the applied `/etc/docker/daemon.json` (verified: `diff <(jq -S . /etc/docker/daemon.json) <(jq -S . infra/docker/daemon.json.example)` produces no output).

**Lesson for future planning iterations:** "dockerd ignores unknown keys" is NOT a safe assumption. Any banner/comment for a JSON config consumed by a strict daemon must live in a sibling `.md` file or in dedicated docs, never inline. Plan-checker iter 2 could not have caught this without empirical apply — RESEARCH §223 was the failure-injection point.
