## Summary

Анализ был выполнен **на той самой машине, где наблюдается аномалия**. На момент исследования Docker занимает не «100+ ГБ» — после промежуточного очищения сейчас на диске **~14.9 ГБ** (Images 9.28 ГБ + Build Cache 5.02 ГБ + Volumes 0.60 ГБ + Containers 7 МБ). Из них **8.7 ГБ — мусор, который можно безопасно убрать прямо сейчас**: 5.71 ГБ reclaimable images (61% от 9.28 ГБ; **68 dangling-слоёв ≈ 226 МБ × 68 = ~15.4 ГБ суммарно** — частично пересекаются с shared-слоями) + 3.72 ГБ reclaimable build cache (74% от 5.02 ГБ).

Эмпирическая декомпозиция через `docker buildx du --verbose` показала, что **доминирующие потребители build-cache — НЕ pnpm-store cache mount**, как предполагала первая гипотеза в seed-note. Топ-список:

Ключевое: cache-mount `/pnpm/store` (278 МБ) — это **ОДИН** запись типа `exec.cachemount`. Остальные 5+ записей по 260-304 МБ — это **слои всего workspace-root /app**, оставшиеся после `RUN pnpm install` на каждом из шести `APP_NAME` rebuild-ов. Эти слои становятся dangling и не реклеймятся, пока не запущен `image prune` или `buildx prune`. То есть hypothesis #1 из seed-note (cache-mount никогда не GC'ится) **частично верна — но не доминирует**; реальный доминант — hypothesis #2 (stale image layers from frequent rebuilds × 6 services).

**Primary recommendation (приоритетный путь Plan 07):**

1. **Diagnostic baseline** через зафиксированный набор команд (`docker system df -v`, `docker buildx du --verbose`, `docker images --filter dangling=true | wc -l`) с записью в `.planning/notes/docker-cache-bloat-baseline.md` — empirical truth для до/после.
2. **One-time scoped cleanup** в три шага через `pnpm clean:docker:dangling` (только dangling images), `pnpm clean:docker:builder` (`buildx prune --filter unused-for=168h`) и (опционально, после явного approval) `pnpm clean:docker:nuclear` (полная очистка builder + dangling + остановленных контейнеров; **никогда не `--volumes`**).
3. **Long-term hygiene primary mechanism = BuildKit GC config** в `/etc/docker/daemon.json` — `builder.gc.policy` со скользящими `keepDuration` + `maxUsedSpace` (Docker 29.x native, без cron, без cargo-cult cleanup). **Secondary defence = `pnpm clean:docker` package.json scripts** для on-demand ручного контроля разработчика (память `feedback_use_package_scripts`). CI hygiene job отложен в Plan 08 (объявлен out-of-scope в seed).
4. **Documentation deliverable** — секция в `CONTRIBUTING.md` (или новый `docs/docker-disk-hygiene.md`) с: ожидаемым profile-роста («15-30 ГБ это нормально после месяца активной разработки»), как читать `docker system df -v`, какой `pnpm clean:*` запускать в каком случае.

## Domain Map — Ontology of Docker Disk Consumption

Когда пользователь говорит «Docker занимает 100+ ГБ», это **не одна сущность**. На диске Docker'а живут **шесть независимых категорий** хранения, у каждой свой жизненный цикл и своя команда удаления. Путать их — главный источник «cleanup испортил мне образы» инцидентов.

```
                            ┌──────────────────────────────────────────┐
                            │       /var/lib/docker (root tree)        │
                            └──────────────────────────────────────────┘
                                                │
        ┌─────────────────┬────────────────┬────┴──────────┬──────────────────┬─────────────────┐
        ▼                 ▼                ▼               ▼                  ▼                 ▼
   ┌─────────┐      ┌──────────┐    ┌───────────┐   ┌───────────┐      ┌──────────┐      ┌──────────────┐
   │ Images  │      │Containers│    │  Volumes  │   │BuildKit   │      │ Networks │      │  Tmp/Logs    │
   │(layers) │      │ (writable│    │           │   │ cache     │      │          │      │              │
   │         │      │  layer)  │    │           │   │           │      │          │      │              │
   └─────────┘      └──────────┘    └───────────┘   └───────────┘      └──────────┘      └──────────────┘
        │                 │                │               │
        ▼                 ▼                ▼               ▼
  Чем удалить:     Чем удалить:     Чем удалить:     Чем удалить:
  docker image     docker container docker volume    docker buildx
  prune (-a/       prune            prune            prune (--filter
  dangling)        OR docker rm                      type=...)
                                                      OR builder.gc
                                                      в daemon.json
```

### Категория 1 — Images (на этой машине: 9.28 ГБ, 95 image, 61% reclaimable)

«Образ» — последовательность read-only слоёв в `/var/lib/docker/overlay2/`. Каждый `RUN`/`COPY` в Dockerfile создаёт отдельный слой. После каждой пересборки `infra-gateway:latest` старый image становится **dangling** (image-id остаётся, тег `<none>:<none>`), пока его слои используются как parent для других образов или ссылаются buildkit cache. Когда последняя ссылка пропадает, dangling image можно удалить.

- **Что удаляет `docker image prune`:** только dangling images (`<none>:<none>`).
- **Что удаляет `docker image prune -a`:** все unused images (даже с тегами, если на них не запущен ни один контейнер). Опасно — может убрать `node:22-alpine`, `gcr.io/distroless/nodejs22-debian12:nonroot`, `busybox:1.37.0-musl`, `ghcr.io/grpc-ecosystem/grpc-health-probe:v0.4.24`, `postgres:16`, `redis:7-alpine`, `rabbitmq:3-management`, `garage:latest`. Эти образы **обязаны быть в кэше для cold-start `pnpm start:isolated`** — иначе compose будет долго pull'ить заново.
- **Эмпирический факт (этой машины):** 68 dangling-слоёв по ~226 МБ ≈ накопление от Plans 01-02 + iter rebuilds Phase 999.18.3. Это **прямой кандидат на one-time cleanup**.

### Категория 2 — Containers (на этой машине: 7 МБ, 3 контейнера, 0% reclaimable)

Каждый запущенный/остановленный контейнер имеет writable layer over read-only слои образа. После `docker rm` writable layer удаляется. На этой машине только 3 контейнера (linkfactory-localstack, securepass_db, legacy-claude-mongo) — **ни один не относится к email-platform проекту**, чужие — НЕ ТРОГАТЬ.

- **Что удаляет `docker container prune`:** только остановленные контейнеры. Не трогает `Up`-status контейнеры. Безопасно для running compose-стека.

### Категория 3 — Volumes (на этой машине: 601 МБ, 36 volumes, 8% reclaimable, 32 dangling)

Persistent storage. Содержат данные Postgres, Redis, RabbitMQ, MinIO/Garage, MongoDB. **СМЕРТЕЛЬНО важная категория** — `docker volume prune` (даже без `-a`) удаляет все volumes **не привязанные к существующему контейнеру**. Если `pnpm stop:isolated` остановил compose-стек, его volumes становятся «не привязанными» — и `docker volume prune` их **гарантированно убьёт**.

- **Что удаляет `docker volume prune`:** все volumes без активного использования (с container.State == removed). **Удалит данные.**
- **`docker system prune --volumes`** = смерть-команда для local dev. **Никогда не запускать без явного approval пользователя в Plan 07.** На этой машине из 36 volumes 32 dangling — но **некоторые из них могут быть ценными** (например, прежние Postgres data dirs от закрытых проектов — пользователь может захотеть их сохранить как archive). [VERIFIED: empirical inspection]

### Категория 4 — BuildKit cache (на этой машине: 5.02 ГБ, 235 records, 74% reclaimable)

**ЭТО ОТДЕЛЬНАЯ ВСЕЛЕННАЯ.** BuildKit cache живёт в `/var/lib/docker/buildkit/` (для embedded `docker` driver) или в специальном volume `buildx_buildkit_default` (для `docker-container` driver). Содержит:

- **`exec.cachemount`** — записи кэш-маунтов (`--mount=type=cache,id=...`). На этой машине — `pnpm-store` (278 МБ).
- **`source.local`** — снимки build-контекста (то, что прислал клиент после `.dockerignore`-фильтрации). На этой машине 235 МБ — это копия workspace.
- **`regular`** — обычные слои промежуточных stages, которые BuildKit держит для cache-hit'ов в следующих сборках. Большинство 304 МБ × 6 / 95 МБ × 6 / 66-71 МБ × 12 — это слои `pruner` / `prod-deps` / `builder` stages **по одному на каждый APP_NAME × каждую генерацию lockfile**.
- **`internal`** / **`frontend`** — служебные образы BuildKit (`docker.io/docker/dockerfile:1`, `moby/buildkit:buildx-stable-1`). Удаляются только с `docker buildx prune --all`.

**Critical fact:** `docker system prune` НЕ ТРОГАЕТ buildkit cache. Чтобы его очистить — `docker buildx prune` (или эквивалентный путь через `docker builder prune`). [VERIFIED: docs.docker.com/reference/cli/docker/buildx/prune/]

**Critical fact 2:** `docker buildx prune` НЕ ТРОГАЕТ images, containers или volumes — только buildkit cache. Полная безопасность по отношению к base images cold-start'а. [VERIFIED: docs.docker.com]

**Critical fact 3:** `--mount=type=cache,id=pnpm-store` shared между всеми builds, использующими один `id`. На этой машине — ОДНА запись (278 МБ), а не шесть. То есть hypothesis #1 из seed-note частично опровергнута: cache-mount **не балует** — `id`-shared механизм работает корректно, и чтобы pnpm-store ballooned до десятков ГБ, нужно либо менять `id`, либо BuildKit GC должен быть отключён, либо у pnpm-store должна быть **другая по структуре проблема** (мусор от старых package versions, не reused). На этой машине это не главный консьюмер.

### Категория 5 — Networks

Незначительный размер (~kB). `docker network prune` удаляет неиспользуемые. Безопасно. Plan 07 не нужен.

### Категория 6 — Tmp/Logs внутри контейнеров

Лог-роутер `json-file` (видно в `/etc/docker/daemon.json`: `max-size: 10m, max-file: 5` → потолок ~50 МБ на контейнер). На этой машине ограничение есть. Не главный консьюмер.

## Validation Architecture — Empirical Diagnostic Recipe

Цель: **до/после**-измерение которое доказывает что (1) cleanup реально освободил место и (2) long-term hygiene mechanism реально предотвращает регрост. Это feed для `nyquist_validation` (если включено в `.planning/config.json` — см. Implementation Notes).

### Diagnostic baseline command-set (deterministic, повторяемый, копи-пейст)

Сохранять stdout каждой команды в `.planning/notes/docker-cache-bloat-baseline-{TIMESTAMP}.md` — это и есть «documentation deliverable» одной из частей Plan 07.

```bash
# Шаг 1 — высокоуровневый snapshot ВСЕХ четырёх категорий
docker system df

# Шаг 2 — детальная декомпозиция (per-image, per-volume, per-cache-record sizes)
docker system df -v

# Шаг 3 — buildkit cache по типам (exec.cachemount vs regular vs source.local)
docker buildx du --filter type=exec.cachemount   # cache mount records (pnpm-store)
docker buildx du --filter type=source.local      # build context snapshots
docker buildx du --filter type=regular           # intermediate stage layers (доминант)
docker buildx du --filter type=internal          # buildkit internals
docker buildx du --filter type=frontend          # frontend images
docker buildx du                                 # total

# Шаг 4 — top-N records by size (нужно хитро, потому что `docker buildx du`
# выдаёт табличный формат без сортировки по размеру; есть workaround через
# `--verbose` + awk):
docker buildx du --verbose | awk 'BEGIN {RS=""} {
  desc=""; size=""; typ="";
  n=split($0, lines, "\n");
  for (i=1; i<=n; i++) {
    if (lines[i] ~ /^Description:/) desc=substr(lines[i], 14);
    if (lines[i] ~ /^Size:/)        size=substr(lines[i], 7);
    if (lines[i] ~ /^Type:/)        typ=substr(lines[i], 7);
  }
  print size "\t" typ "\t" desc;
}' | grep -v "^0B" | sort -h -r | head -25

# Шаг 5 — dangling images count + total size
docker images --filter dangling=true --format '{{.Size}}' | wc -l
docker images --filter dangling=true --format '{{.Size}}'

# Шаг 6 — список builders (полезно если случайно появился `docker-container` driver)
docker buildx ls

# Шаг 7 (опционально, требует sudo — пропустить если нет прав) — host filesystem
# view; верифицирует что вычитанные через docker df числа НЕ undercounted
sudo du -sh /var/lib/docker/overlay2 /var/lib/docker/volumes /var/lib/docker/buildkit 2>/dev/null
```

**Подводный камень:** `du -sh /var/lib/docker/overlay2` может показывать число БОЛЬШЕ чем `docker system df` — overlay2 использует hardlinks для shared layers, и `du` без `-l --apparent-size` может либо undercount (если работает hardlink-aware, по-умолчанию это так в современных GNU coreutils), либо overcount если флаги выставлены неправильно. **Правильный путь — доверять `docker system df`/`docker buildx du`** как источник правды; `du` использовать только как cross-check (если две оценки расходятся в **разы**, есть скрытый источник вне Docker'а).

### Экспериментальный синтетический profile (для documentation deliverable, опционально)

Чтобы доказать пользователю «вот сколько места занимают N rebuild'ов», можно сделать controlled-эксперимент в новой ветке:

```bash
# В отдельной чистой папке
docker buildx prune --force --all      # zero baseline
docker system df                       # должно быть всё около нуля

# Симулировать N rebuild'ов одного сервиса
for i in 1 2 3 4 5; do
  pnpm start:isolated     # foreground build
  pnpm stop:isolated
  # туда сюда модифицировать pnpm-lock.yaml для cache-bust симуляции
done

docker system df            # measure
docker buildx du --verbose | grep -c "^Description:"   # cache record count
```

Этот эксперимент **не нужен для plan-execution**, но даёт твёрдые числа для CONTRIBUTING.md секции «expected disk growth».

### Регрессионный тест — после landing'а Plan 07 long-term hygiene должен предотвратить регрост

После того как `daemon.json` будет дополнен `builder.gc.policy`, regression test:

```bash
# Pre: измерить
docker system df                                       # baseline N1

# Симулировать рост (5 rebuild'ов с принудительным cache-bust)
for i in 1 2 3 4 5; do

```

### Recommended primary: **V2 — BuildKit GC policy в `/etc/docker/daemon.json`**

**Концепт config (Docker 29.x native):**

```json
{
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "5" },
  "dns": ["8.8.8.8", "1.1.1.1"],
  "bip": "172.17.0.1/16",
  "builder": {
    "gc": {
      "enabled": true,
      "defaultReservedSpace": "10GB",
      "policy": [
        {
          "keepDuration": "168h",
          "filter": ["type==source.local,type==exec.cachemount"],
          "maxUsedSpace": "2GB"
        },
        { "keepDuration": "168h", "maxUsedSpace": "20GB" },
        { "all": true, "reservedSpace": "5GB", "minFreeSpace": "20GB", "maxUsedSpace": "30GB" }
      ]
    }
  }
}
```

**Чтение этого config (для понимания):**

- `defaultReservedSpace: 10GB` — daemon **никогда** не будет реклеймить ниже этого порога (защита от cold-start latency).
- Policy 1: source.local + cache mounts старше 7 дней с потолком 2 ГБ — самое агрессивное правило для самых дешёвых-к-восстановлению записей.
- Policy 2: всё остальное старше 7 дней с потолком 20 ГБ.
- Policy 3 (catch-all): держать 5 ГБ всегда, стремиться к 20 ГБ free space, но не больше 30 ГБ всего.

**Эффект:** на этой машине после применения и `dockerd restart` daemon в фоне реклеймит build cache до 20-30 ГБ потолка (сейчас 5 ГБ — далеко от потолка, ничего не произойдёт, но если разработчик уйдёт в отпуск и cache вырастет до 100 ГБ — daemon сам подрежет).

### Recommended secondary: **V1 — `pnpm clean:docker:*` package.json scripts (defence-in-depth)**

**Зачем secondary, если V2 работает в фоне?** Три сценария:

## One-Time Cleanup Recipe

> **Цель:** освободить ~8.7 ГБ (5.71 ГБ reclaimable images + 3.72 ГБ reclaimable build cache на этой машине) **БЕЗ** ущерба для running compose-стека и без потери volumes.
>
> **Безопасный pattern:** stop-here-if checkpoints — после каждого шага пользователь подтверждает прежде чем переходить к следующему, более агрессивному.

### Pre-flight (read-only, всегда сначала)

```bash
# Захватить baseline в файл-артефакт (это и есть «documentation deliverable»)
docker system df > .planning/notes/docker-cleanup-pre.txt
docker system df -v >> .planning/notes/docker-cleanup-pre.txt
docker buildx du >> .planning/notes/docker-cleanup-pre.txt
echo "---" >> .planning/notes/docker-cleanup-pre.txt
docker images --filter dangling=true --format '{{.ID}} {{.Size}}' | wc -l >> .planning/notes/docker-cleanup-pre.txt

# Покажем активный compose-стек (всё что running — НЕ трогать)
docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.Image}}'

# Покажем какие images используются running контейнерами (НЕ удалять)
docker ps --format '{{.Image}}' | sort -u
```

**STOP-HERE-IF:** есть running контейнер email-platform проекта (`infra-gateway`, `infra-auth`, ...) — **сначала остановить через `pnpm stop:isolated`** прежде чем переходить к Шагу 1. Иначе `image prune` может промахнуться, или (реже) container prune убьёт running stack.

### Шаг 1 — Dangling images (САМОЕ безопасное, освобождает больше всего)

```bash
docker image prune --force        # NO -a flag, ТОЛЬКО dangling
```

Это удалит только `<none>:<none>`-тегированные images, у которых нет children и нет ссылок из running контейнеров. **На этой машине: ~5 ГБ.** Никакие base images (postgres:16, redis:7-alpine, node:22-alpine, distroless, busybox, grpc-health-probe) **не пострадают** — у них реальные теги.

**STOP-HERE-IF:** пользователь не просил продолжать. Многие cleanup-сессии заканчиваются на Шаге 1.

### Шаг 2 — Stopped containers (нулевой риск)

```bash
docker container prune --force
```

Удалит контейнеры в `Exited`/`Created` status. Не трогает `Up`-status. На этой машине только 1 такой (`legacy-claude-mongo` от 3-дневной давности — пользователь должен решить, нужен ли он). Ничтожный размер (3 контейнера × ~МБ writable layers). Можно скипнуть.

### Шаг 3 — BuildKit cache старше 7 дней (безопасно — не трогает images/volumes)

```bash
docker buildx prune --filter "unused-for=168h" --force
```

Удалит только cache records, к которым не обращались последние 7 дней. На этой машине **сейчас ничего не удалит** (всё свежее, последняя сборка 19 минут назад, самая старая запись 3 часа). Но через неделю-две регулярного использования начнёт срабатывать. Полезно держать в bashrc как weekly habit.

### Шаг 4 (АГРЕССИВНО, требует ЯВНОЕ user approval) — весь reclaimable build cache

```bash
docker buildx prune --reserved-space 2GB --force
```

Сохранит 2 ГБ cache в качестве warm-up, остальное снесёт. На этой машине освободит **~3.7 ГБ**. Следующий `pnpm start:isolated` cold start пересоберёт workspace (pnpm install + turbo build) — **дольше первый раз на 2-4 минуты**, потом снова кэшируется.

**STOP-HERE-IF:** пользователь не подтвердил. Важно: cold-start будет медленный — это **прямая ценная плата за освобождённое место**. Если пользователь работает на горящем deadline — лучше скипнуть до конца сессии.

### Шаг 5 (ЯДЕРКА, ТОЛЬКО под approval) — система prune без `--volumes` и без `-a`

```bash
docker system prune --force      # БЕЗ --volumes, БЕЗ -a
```

Эквивалент: dangling images + stopped containers + buildkit cache + unused networks. **БЕЗОПАСНО относительно named base images и volumes** (нет флагов `-a` или `--volumes`).

**STOP-HERE-IF:** Пользователь не подтвердил. Не запускать без явного «yes, do system prune».

### Шаги, которые НИКОГДА не запускаются без явного одобрения и письменного предупреждения

```bash
# ЭТИ КОМАНДЫ — НЕ В ПЛАНЕ. Plan 07 их **не предлагает** — упомянуты только
# чтобы исключить их из автоматических pnpm-скриптов.
docker system prune -a --volumes --force    # СНЕСЁТ Postgres/Redis volumes, base images
docker volume prune -a --force              # ТОЛЬКО volumes — но всё равно опасно
docker image prune -a --force               # уберёт node:22-alpine, postgres:16 и пр.
docker buildx prune --all --force           # уберёт также frontend/internal images
```

### Mid-prune Ctrl-C — failure mode

Что произойдёт, если пользователь нажмёт Ctrl-C посреди `docker buildx prune`?

- Daemon обрабатывает удаление транзакционно per record. Те records, которые уже удалены до Ctrl-C — удалены. Те, что в очереди — остаются. **Не остаётся corrupted state.**
- `image prune` аналогично: per-image транзакция.
- `volume prune` — per-volume транзакция, но **уже удалённые volumes невосстановимы**. Поэтому Plan 07 не запускает volume prune.
- `daemon.json` GC policy работает в фоне на отдельном goroutine — Ctrl-C на CLI не прерывает; daemon продолжает в свой ритм.

**Практический вывод:** Ctrl-C безопасен. Но если в середине Шага 4 вдруг исчезли свежие кэши Plans 01-02 — это означает, что previous-build-cache ушло, и следующий build будет cold-start (medium-латеционный, не катастрофа).

## Pitfalls & Landmines

### P1 — `docker system prune --volumes` смерть-команда

`pnpm reset:isolated` уже делает `docker compose down --volumes` — это **scoped** removal только compose-volumes. **`docker system prune --volumes` снесёт ВСЁ** включая чужие проекты на машине (Postgres от LinkFactory, MongoDB от legacy-claude и т.д.). Не упоминать в README/CONTRIBUTING. Не запускать ни при каких обстоятельствах в Plan 07.

### P2 — `docker image prune -a` после `pnpm stop:isolated` снесёт base images

В состоянии «нет running компосе-стека» **все** base images (`postgres:16`, `redis:7-alpine`, `rabbitmq:3-management`, `garage:latest`, `node:22-alpine`, `gcr.io/distroless/...`, `busybox:1.37.0-musl`, `ghcr.io/grpc-ecosystem/grpc-health-probe:v0.4.24`) формально «unused». `image prune -a` их удалит. Следующий `pnpm start:isolated` будет 5-10 минут pull'ить заново (особенно postgres:16 ~150 МБ + redis ~50 МБ + rabbitmq ~250 МБ + minio/garage). На медленном интернете — недвусмысленно болезненно. **`-a` флаг в Plan 07 НЕ ИСПОЛЬЗОВАТЬ.**

### P3 — `docker buildx ls` показывает только default — на этой машине проблемы НЕТ

На некоторых машинах команда `docker buildx create --use --name mybuilder` создаёт **отдельный builder instance** со своим `buildx_buildkit_mybuilder0` volume. Этот volume **survives `docker system prune`** и его cache видно ТОЛЬКО через `docker buildx du --builder mybuilder`. Hypothesis #4 из seed-note. Эмпирически на этой машине: только default builder (`docker buildx ls` показывает один) — **гипотеза не релевантна для этого user'а**, но если разработчик использует ad-hoc `docker buildx create`, ему нужно проверить через `docker buildx ls` и сделать prune для каждого builder.

### P4 — `daemon.json` invalid syntax после правки = dockerd refuses to start

После любой правки `/etc/docker/daemon.json`:

```bash
sudo dockerd --validate /etc/docker/daemon.json   # NEW в Docker 25+ — pre-flight check
# или: jq . /etc/docker/daemon.json    # минимальная JSON-валидация
sudo systemctl restart docker
sudo systemctl status docker            # подтвердить, что не failed
docker version                          # подтвердить, что daemon доступен
```

**Если дocker не стартанул после правки — плохой день.** План 07 обязан включать (1) backup `daemon.json` перед правкой, (2) валидация JSON через `jq`, (3) post-restart `pnpm start:isolated` smoke. Это сертифицированная **infra change**, требует full `infrastructure-guard` checklist.

### P5 — Multi-arch QEMU локально (Tier 2 Q7)

Проект CI делает `docker buildx build --platform linux/amd64,linux/arm64` (per Phase 999.18.2 D-09+D-11). Локально на этой машине (Linux Arch x86_64, default builder driver = `docker`, не `docker-container`) **multi-arch builds НЕ происходят** — `pnpm start:isolated` использует обычный native amd64 build. Поэтому QEMU emulation cache **не контрибутирует** к локальной аномалии. Это CI-бремя (Plan 08, отложен).

**Verify**: `docker buildx ls` на этой машине → `default` builder, driver `docker` (embedded в dockerd, не buildx-container). Multi-platform colon в выводе (`linux/amd64 (+4), linux/386`) — это `binfmt_misc` поддержка через QEMU **внутри ядра**, не отдельный builder-instance с накопленной emulation-state.

### P6 — `.dockerignore` regression risk (Tier 2 Q8)

`.dockerignore` на этой машине (1114 байт) **выглядит здоровым**: исключает `**/node_modules`, `**/dist`, `.git`, `.planning`, `.env*`, `infra`, `docs`, `.turbo`, `.idea`, `.vscode`. **`source.local` запись 235.1 МБ в build cache соответствует ожиданию** — это весь workspace minus node_modules/dist/.git. Поскольку рост `source.local` ограничен `.dockerignore` качеством — здесь нет известного утечного источника. **Out of scope для Plan 07.** Если в будущем добавится новый workspace package с большими binary assets, нужно ревизировать `.dockerignore` — но сейчас это не баг.

### P7 — pnpm-store cache mount **shared across all builds**, но **не deduplicated по version**

`--mount=type=cache,id=pnpm-store,target=/pnpm/store` означает что cache mount имеет **persistent identity** "pnpm-store" — все builds (gateway, auth, sender, parser, audience, notifier) используют **один и тот же mount**. Это правильное поведение и **снижает** disk usage относительно 6 отдельных mounts. **Но:** pnpm-store не GC'ится сам — старые версии пакетов накапливаются. На этой машине только 278 МБ — пока не катастрофа. Через несколько кварталов активного развития (десятки lockfile churn'ов) этот mount может вырасти до пары ГБ. Решение: **periodic `pnpm clean:docker:builder`** (Шаг 4 в cleanup recipe) — он реклеймит и cache mounts тоже. Долгосрочно: BuildKit GC policy с `keepDuration=168h` для `type==exec.cachemount` сделает это автоматически. Поэтому в `daemon.json` policy первая запись (`filter: ["type==source.local,type==exec.cachemount"]`) есть.

### P8 — `dockerd restart` обрывает все running контейнеры

После правки `daemon.json` нужен `systemctl restart docker`. Это **остановит** все running контейнеры (включая чужие проекты — linkfactory-localstack, securepass_db). После рестарта они автоматически НЕ поднимутся (если у них нет `restart: unless-stopped`). Plan 07 обязан **предупредить пользователя**: «после рестарта тебе надо вручную поднять чужие compose-стеки заново».
