### Pattern 1: gitleaks v8 `[[allowlists]]` (top-level)

**What:** Top-level allowlists evaluated for all rules. `condition = "AND"` requires all listed criteria (paths AND regexes AND/OR commits) to match for a finding to be skipped.
**When to use:** When discriminating by combined criteria — e.g., "skip findings only when located in this specific file AND with this exact shape." Industry-standard idiom for `package-lock.json` integrity hashes (canonical gitleaks README example) and `pnpm-lock.yaml` SHA-512 hashes (community precedent).
**Example:**

```toml
# Source: gitleaks v8 README — package-lock.json example, adapted to our manifest
# https://github.com/gitleaks/gitleaks/blob/master/README.md (top-level [[allowlists]] section)

[[allowlists]]
description = "GSD framework integrity manifest — ~280 SHA-256 file hashes. Suppresses findings only when match shape is bare 64-char lowercase hex inside this exact file. Real AWS keys, JWTs, or PEM blocks in the same file still fire (default rules unaffected)."
condition = "AND"
paths = ['''^\.claude/gsd-file-manifest\.json$''']
regexes = ['''^[a-f0-9]{64}$''']
regexTarget = "match"
```

### Pattern 2: gitleaks `git` mode (vs `dir` mode)

**What:** `gitleaks git <path>` traverses commit history via `git log -p`, scanning patches/diffs (= what is or has been tracked). `gitleaks dir <path>` scans the filesystem at the path, including untracked content.
**When to use:** Pre-push gate wants "what is being pushed" → `git` mode. CI wants the same — final defense before merge. `dir` mode is for ad-hoc filesystem scans (rarely the right choice in a tracked repo).
**Example:**

```bash
# Source: gitleaks docs (verified empirically 2026-04-30 against current branch)
docker run --rm -v "$(pwd):/repo" -w /repo "$GITLEAKS_IMAGE" \
  git /repo --no-banner
# Reads /repo/.gitleaks.toml automatically. Reads /repo/.gitleaksignore for fingerprint suppressions.
```

Both modes honor `.gitleaks.toml` config identically (same precedence: `--config` flag → `GITLEAKS_CONFIG` env → `GITLEAKS_CONFIG_TOML` env → `.gitleaks.toml` in target → built-in default). [CITED: gitleaks README — Configuration section]

### Pattern 3: Native env-var override for backing service config (D-10)

**What:** Backing service reads secret value from process env, not from tracked config file. Tracked config file contains everything except the secret. Real value lives in `.env.docker` (gitignored, env-injection mechanism — different category from "config file with secrets").
**When to use:** Whenever the backing service supports it natively (Garage v2 does — `GARAGE_RPC_SECRET`, `GARAGE_ADMIN_TOKEN`, `GARAGE_METRICS_TOKEN`). Avoid envsubst preprocessing when native env override exists.
**Example:**

### Pattern 4: Redacted-format secrets in examples (D-07)

**What:** Examples in code comments / planning docs / SUMMARY files use placeholder formats that **don't match default gitleaks rules**. The discriminator is the format itself — defense via shape, not via path.
**When to use:** Any time you write an example credential / connection string / API key in any documentation. Test against gitleaks default rules: would this trigger? If yes, it's not redacted.
**Examples (D-07 standard):**

```markdown
<!-- Connection strings -->

postgres://user:<redacted>@host:5432/db
redis://default:<redacted>@host:6379/0
mongodb://user:<redacted>@host:27017/db
amqp://<redacted>@host:5672

<!-- Cloud keys -->

AKIA<redacted-suffix> ← NOT AKIA[A-Z0-9]{16} real-format
<aws-access-key-redacted>

<!-- Tokens -->
<api-token-redacted>
<github-token-redacted>
<digits>:<redacted-bot-token>   ← NOT \d+:[A-Za-z0-9_-]+ telegram-format

<!-- Generic / hex -->
<rpc-secret-redacted>
<32-byte-hex-redacted>
<password-redacted>

<!-- Private keys — ALWAYS just the placeholder, NEVER PEM blocks even as examples -->
<private-key-redacted>
```

### Anti-Patterns to Avoid

- **`.gitleaksignore` glob entries** — file format accepts only fingerprints `commit:file:rule:line`. Glob entries silently emit `WRN Invalid .gitleaksignore entry` per scan; no path-block effect. (This is the AM-01 root cause — Plan 03 of 999.17.1 added a glob, didn't catch the warning.) [VERIFIED: empirical baseline run produces this WRN twice]
- **Unanchored regex in allowlist `paths`** — original `(.*?)(jpg|gif|...)` matched `apps/auth/src/documentation.ts` as substring (CR-02 in 999.17). Always anchor: `^scripts/security/fixtures/`, `^\.claude/gsd-file-manifest\.json$`. [CITED: 999.17 Plan 12 lessons-learned]
- **Path-allowlist for user content** (CONTEXT.md D-01 violation) — AI agents writing into "safe" paths can leak real secrets. Use shape-based allowlists (D-06 pattern) or content cleanup (D-08), never blanket path carve-outs.
- **`.gitignore` for config files containing secrets** — hides the file from git, but real value still exists on host + in Docker layer cache + in process state. False security. (CONTEXT.md D-10 explicitly rejects this.) Use native env override or env-injection mechanism (`.env*`) instead.
- **Custom rules for connection strings before exhausting default rules + content cleanup** — D-13 explicit. Default rules + redacted examples = sufficient. Add custom rules only if real-format URL escapes default rules in production code (separate follow-up phase).
- **`gitleaks dir` for pre-push** — scans untracked filesystem (`.pnpm-store/`, `.claude/worktrees/`). Use `gitleaks git`. (AM-02 root cause.)
- **envsubst preprocessing when native env override exists** — adds template file + custom entrypoint complexity for the same outcome. Use what the backing service offers natively. [Research finding 2026-04-30, applies to D-10]

## Garage envsubst mechanism (deep dive — answers Q1/Q2/Q3/Q7/Q8)

### Q1: Does Garage support native env-var override for `rpc_secret`?

**YES.** [VERIFIED: garagehq.deuxfleurs.fr/documentation/reference-manual/configuration]

Quote from official Garage configuration documentation:

> "The RPC secret should be specified in the `rpc_secret` configuration variable. Since Garage `v0.8.2`, the RPC secret can also be stored in a file whose path is given in the configuration variable `rpc_secret_file`, or specified as an environment variable `GARAGE_RPC_SECRET`."

Same pattern available for:

- `admin_token` / `admin_token_file` / `GARAGE_ADMIN_TOKEN` / `GARAGE_ADMIN_TOKEN_FILE` (since v0.8.2)
- `metrics_token` / `metrics_token_file` / `GARAGE_METRICS_TOKEN` / `GARAGE_METRICS_TOKEN_FILE`
- `rpc_secret` / `rpc_secret_file` / `GARAGE_RPC_SECRET` / `GARAGE_RPC_SECRET_FILE` (since v0.8.5/v0.9.1 for `_FILE` variants)

We are on v2.1.0 (well past v0.8.2). All env-var overrides apply.

### Q2: Is there an existing envsubst pattern in `infra/docker/` we can reuse?

**NO existing envsubst pattern.** All current secret/config values flow into containers via:

- docker-compose `environment:` block (e.g., `GARAGE_ADMIN_TOKEN: ${GARAGE_ADMIN_TOKEN}` in `infra/docker-compose.infra.yml`)
- `env_file: ../.env.docker` directive (used by all `apps/*` services in `infra/docker-compose.yml`)
- bash scripts reading `.env.docker` directly (e.g., `infra/docker/storage-bootstrap.sh` lines 19–30)

**There is no `*.template` file in the project today.** Confirmed by `find infra/docker -name '*.template'` (empty result). Adding the first envsubst-template introduces a new pattern to the project that none of the team is familiar with.

### Q3: Docker-compose substitution mechanism

**Existing pattern (which D-10 native-override path piggybacks on):**

```yaml
# infra/docker-compose.infra.yml — already-working pattern
services:
  garage:
    environment:
      GARAGE_ADMIN_TOKEN: ${GARAGE_ADMIN_TOKEN}
```

Docker-compose performs variable substitution at compose-up time, reading values from `--env-file .env.docker` (passed via the `pnpm infra:up` / `pnpm docker:up` scripts). If `GARAGE_ADMIN_TOKEN` is unset, docker-compose either uses the default `${VAR:-default}` (none specified here) or substitutes empty string. This is the same mechanism we need for `GARAGE_RPC_SECRET` — zero new infrastructure.

The compose `command:` field is **not** the right substitution mechanism for D-10 — that runs inside the container (which here is distroless, no shell), and `command:` is for changing the container entrypoint args, not for templating files.

### Q7: envsubst behavior with missing env vars (moot if we use native override)

If we did use envsubst (we don't, recommendation is native override): `envsubst` (gettext utility) substitutes `${VAR}` with the env value, or with an empty string if unset. There is no built-in fail-fast mode. To force fail-fast, one would need to either:

- Pre-validate env vars before invocation: `: "${GARAGE_RPC_SECRET:?missing}"` in bash before `envsubst`
- Use the `-i` mode (read variable list from a file) plus a secondary check

This is moot in the recommended approach.

## gitleaks v8 [[allowlists]] semantics (answers Q4/Q5/Q6)

### Q4: top-level `[[allowlists]]` vs `[[rules.allowlists]]`, `condition = "AND"` semantics, `regexTarget` values

**Top-level `[[allowlists]]`** (which we use for D-05 + D-06):

- Apply to ALL rules.
- "Higher order of precedence than rule-specific allowlists" [CITED: gitleaks README — Allowlists section]
- Default `condition = "OR"`: any criterion (commits / paths / regexes / stopwords) matching → finding suppressed.
- `condition = "AND"`: ALL specified criteria must match. Required for D-06 (path AND regex must both apply, otherwise we'd suppress everything in `gsd-file-manifest.json` including real findings).
- **`useDefault = true` is set in `[extend]` block, NOT inside `[[allowlists]]`** — confirmed by reading current `.gitleaks.toml`. Our config already has it. No change needed.

**Rule-level `[[rules.allowlists]]`** (we don't use these):

- Only apply to the rule they are nested under.
- Multiple rule-level allowlists per rule allowed — finding ignored if ANY matches (OR semantics across rule-level allowlists).
- `targetRules` field (introduced v8.25.0) lets a rule-level allowlist target multiple rules. **Known issue #1919: silently ignored under some config combinations.** [CITED: gitleaks issues #1919, #1844] — concern carried forward in CONTEXT.md, confirmed in research.

**`regexTarget` values:**

- `"secret"` (default) — regex matches against the extracted secret only (the captured group from the rule).
- `"match"` — regex matches against the entire match (everything the rule's regex matches, including surrounding context).
- `"line"` — regex matches against the complete line containing the match.

For D-06 we use `"match"` because the SHA-256 hashes appear as the match value (the rule captures `"<filename>": "<64-hex-hash>"` as a whole; the `<64-hex-hash>` portion is what we want to discriminate against). `"secret"` would also work for some rules but `"match"` is safer and matches the canonical README example pattern.

### Q5: `.gitleaksignore` syntax

**Format (per official docs):** `<commit-sha>:<file-path>:<rule-id>:<line-number>` — the unique fingerprint of a finding. Globs are NOT supported. [CITED: gitleaks README — Suppressing Findings section]

**Empirical confirmation:** Current `.gitleaksignore` line 33 (`scripts/security/fixtures/**`) produces `WRN Invalid .gitleaksignore entry fingerprint=scripts/security/fixtures/**` on every gitleaks run (confirmed 2026-04-30 baseline scan).

**Permitted abbreviated form:** Lines 25–30 of current `.gitleaksignore` use `<file>:<rule>:<line>` (no commit prefix). Empirical evidence: these don't trigger `WRN Invalid` warnings. This appears to be tolerated as fingerprints can match either full or abbreviated form against findings — but **not documented officially**. Plan-phase keeps these existing entries as-is (CONTEXT.md doesn't mandate cleanup).

### Q6: `gitleaks git` vs `gitleaks dir` — config honor + flags

Both modes:

- Honor `.gitleaks.toml` identically (precedence: `--config` flag → `GITLEAKS_CONFIG` env → `GITLEAKS_CONFIG_TOML` env → `.gitleaks.toml` in target → built-in default).
- Honor `.gitleaksignore` identically.
- Same flag set for `--no-banner`, `--report-path`, `--report-format`, etc.

Differences:

- `git` traverses `git log -p` (commit history). Sees only what is or has been tracked.
- `dir` walks filesystem. Sees everything on disk including untracked.

Both modes have the same **exit code semantics** (0 = clean, 1 = findings, other = config/runtime error).

**Confirmed empirically 2026-04-30:** Running `git /repo` produces 23 findings on current branch; running `dir /repo` produces 142 findings (extra 119 from untracked filesystem). Same `.gitleaks.toml` honored in both runs.

## Common Pitfalls

### Pitfall 1: Unanchored regex in `paths` allowlist

**What goes wrong:** `(.*?)(jpg|gif|...)` matches `apps/auth/src/documentation.ts` as substring; everything in `apps/` gets silently allowlisted.
**Why it happens:** Author treats path regex like a glob; gitleaks treats it as Go regex with no implicit anchoring.
**How to avoid:** ALWAYS anchor: `^scripts/security/fixtures/`, `^\.claude/gsd-file-manifest\.json$`. Test the regex against the actual paths in the repo before committing.
**Warning signs:** `[allowlist].paths` regex with no `^` at start. CR-02 in 999.17 Plan 12 was exactly this.

### Pitfall 2: `.gitleaksignore` glob entries silently fail

**What goes wrong:** Author adds `scripts/security/fixtures/**` to `.gitleaksignore`. Gitleaks doesn't error — it warns once: `WRN Invalid .gitleaksignore entry`. The path-block has no effect; findings still surface.
**Why it happens:** `.gitleaksignore` accepts only fingerprints `commit:file:rule:line`. The author confused it with `.gitignore`.
**How to avoid:** Always use `.gitleaks.toml [[allowlists]]` for path-blocks. `.gitleaksignore` is ONLY for per-finding fingerprints.
**Warning signs:** `WRN Invalid .gitleaksignore entry` in scan output. (This is the AM-01 root cause.)

### Pitfall 3: Path-allowlist for user content erodes defense-in-depth

**What goes wrong:** Author adds `^\.planning/` to `[[allowlists]] paths`. AI agent later writes a real AWS key into a planning doc; gate doesn't fire; secret leaks.
**Why it happens:** Author thinks "planning docs are safe" — but AI agents can write anything anywhere.
**How to avoid:** Discriminate by **shape** (D-06 pattern), not by **path**. Or fix the content (D-07/D-08). CONTEXT.md D-01 codifies this principle.

### Pitfall 4: `gitleaks dir` scans untracked filesystem

**What goes wrong:** Pre-push gate scans `.pnpm-store/`, `.claude/worktrees/`, untracked `node_modules/.cache/` — produces 100+ false positives that aren't even being pushed.
**Why it happens:** Author confuses semantics: `dir` = "scan filesystem"; `git` = "scan git-tracked".
**How to avoid:** Use `gitleaks git` for any "what's being committed/pushed" gate. Use `dir` only for ad-hoc filesystem scans.
**Warning signs:** Pre-push noise from paths that don't appear in `git status`.

### Pitfall 5: envsubst with distroless image

**What goes wrong:** Author writes `garage.toml.template` and an entrypoint script that does `envsubst < garage.toml.template > garage.toml && exec /garage server -c /etc/garage.toml`. Container fails to start: `exec: /bin/sh: not found`.
**Why it happens:** `dxflrs/garage:v2.1.0` is distroless — only the `/garage` binary, no shell, no envsubst.
**How to avoid:** Check upstream's image filesystem before writing entrypoint scripts: `docker create --name X image:tag false; docker export X | tar -tf - | head`. Prefer native env-var override when available (D-10).

### Pitfall 6: Confusing `condition` semantics in [[allowlists]]

**What goes wrong:** Author writes `[[allowlists]] paths = [...]; regexes = [...]` without `condition = "AND"`. Default OR semantics: any match suppresses the finding. So either path OR regex match → suppression. Result: every file matching the path is allowlisted regardless of content shape.
**Why it happens:** Default condition is `OR`; author assumes `AND`.
**How to avoid:** When combining criteria for "must satisfy ALL", explicitly set `condition = "AND"`. D-06 has this.

### Pitfall 7: `targetRules` field silently ignored

**What goes wrong:** Author writes a rule-level allowlist with `targetRules = ["aws-access-token"]` to share allowlist across rules. Under some config combos, gitleaks ignores `targetRules`; allowlist applies broadly or not at all.
**Why it happens:** Known regression — gitleaks issue #1919.
**How to avoid:** For shared-across-rules allowlists, use top-level `[[allowlists]]` (which apply globally). D-05 + D-06 use this form.

### Pitfall 8: Custom Garage entrypoint maintenance burden

**What goes wrong:** Author builds custom Garage image (`FROM dxflrs/garage:v2.1.0; COPY --from=alpine envsubst /usr/bin/envsubst; ENTRYPOINT [/entrypoint.sh]`). Image works locally. Garage v2.2.0 ships with breaking config field; custom image now blocks upgrade until entrypoint script is rewritten.
**Why it happens:** Custom downstream images decouple from upstream upgrade cadence.
**How to avoid:** Prefer native upstream env-var override (D-10 research finding). Stay on stock image.

### Pitfall 9: `.gitignore`-ing a tracked config file

**What goes wrong:** Author rotates `garage.toml` rpc_secret, then adds `infra/docker/garage.toml` to `.gitignore` to "hide" the new value. The file still exists on every host (developers, CI runners). Real value is in Docker layer cache, in process state, in `docker inspect` output. Same exposure surface as before, with worse traceability.
**Why it happens:** Author treats `.gitignore` as security mechanism rather than tracking-control mechanism.
**How to avoid:** Secrets go in env vars. Tracked config files contain only non-secret config. CONTEXT.md D-10 codifies the rejection.
