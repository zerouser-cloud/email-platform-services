## Findings

### WARNING-1 (Dimension 4 + 14): Raw `docker compose` violates `feedback_use_package_scripts` memory + `runtime-smoke-verification` skill

**Location:** `999.17.2-02-PLAN.md` Task 4, Step 4 (lines ~391–399).

**What:** Plan instructs executor to run:

```bash
GARAGE_RPC_SECRET= docker compose -f infra/docker-compose.infra.yml up garage --no-deps 2>&1 | tee /tmp/garage-failfast.log
```

And later:

```bash
docker compose -f infra/docker-compose.infra.yml down garage --remove-orphans
```

**Why it's a warning, not a blocker:** The fail-fast probe is documented as Manual-Only in VALIDATION.md ("Requires temporarily unsetting an env var in shell, not safe to automate inside CI"). It is a one-shot empirical verification, not an automated gate. However, the plan as written has the executor run it without explicit user authorization or pnpm wrapper.

**Remediation guidance for planner:**

- Option A (preferred): Reframe Step 4 as a manual checkpoint requiring user permission (`<task type="checkpoint:human-verify">` segment), per `runtime-smoke-verification` skill rule "ASK the user to add one or grant one-time permission for a concrete command".
- Option B: Add a `pnpm garage:fail-fast-probe` script to `package.json` and reference it.
- Option C: Move the fail-fast verification entirely into Task 6 (checkpoint) and frame it as one-time-permission.

### WARNING-2 (Dimension 9): Plan 01 Task 4 action structure is self-contradicting

**Location:** `999.17.2-01-PLAN.md` Task 4 action (lines 392–428).

**What:** The `<action>` shows TWO different fingerprint-line specifications:

1. First, a "verbatim block below" containing two abbreviated entries `.env.docker:telegram-bot-api-token:52` (both lines identical).
2. Then in REQUIREMENTS, a "WAIT — gitleaks abbreviated form does NOT discriminate between commits..." amendment instructing FULL form `c638e69:.env.docker:telegram-bot-api-token:52` + `382fc1f:.env.docker:telegram-bot-api-token:52`.

The action's first block is invalidated mid-flight by the REQUIREMENTS clause. An executor reading top-down may stage the abbreviated form before reaching the WAIT clause; an inattentive executor may not realize the two duplicate abbreviated lines were never meant to ship.

Additionally: line `:52` is hardcoded in both the action block and the FULL-form replacement, then a separate REQUIREMENTS bullet says "verify against current scan output; if scanner reports a different line, USE the actual reported line". This produces a three-way ambiguity (abbreviated vs FULL with `:52` vs FULL with empirical line).

**Why it's a warning, not a blocker:** The intent is unambiguous on careful read; the verify command in `<verify><automated>` uses regex `[0-9]+` which tolerates any line number; the empirical-line step is correct.

**Remediation guidance for planner:** Rewrite the action to present a single, final block:

```
<action>
Append to .gitleaksignore (after line 30) the comment block (verbatim below) followed by TWO fingerprint entries in FULL `commitSHA:path:rule:line` form.

EMPIRICAL LINE LOOKUP FIRST: run `bash scripts/security/secrets-full.sh 2>&1 | grep -E "(c638e69|382fc1f).*telegram-bot-api-token"`. Use the actual line numbers reported by gitleaks (likely `:52` based on prior scan, but verify).

Final fingerprint lines (replace LINE with empirical value):
  c638e69:.env.docker:telegram-bot-api-token:LINE
  382fc1f:.env.docker:telegram-bot-api-token:LINE

Comment block (verbatim, above the fingerprints):
[full comment block]
</action>
```

Remove the duplicate-abbreviated false start and the WAIT amendment.
