# Phase 999.1.9 Plan 05: Sender Service Migration (config per-app layout + D-21 external-apis split) — Summary

**Status:** COMPLETE. Task 1 committed (`ef85b48`). Extends the W3 audience canary pattern to sender's more complex shape — 1 peer (audience), CACHE_CONFIG_PORT (Redis), and first application of D-21 per-service external-apis split.

## Goal

Migrate the `sender` service end-to-end to the Phase 999.1.9 per-app config structure. Third proof point after W3 audience canary + W4 auth. W5 specifically validates:

1. **Peer topology spread** — sender spreads `AudienceTopologyShape` (upstream gRPC call)
2. **D-21 external-apis split** — `CloudFnSchema` relocated to per-service `apps/sender/external-apis.schema.ts`
3. **CACHE_CONFIG_PORT binding** — sender is the only service currently narrowing `REDIS_URL` via `CacheConfig`

Reduces the set of legacy 2-generic `createConfigModule` call sites from 4 → 3 (parser, gateway, notifier remain on Pitfall 2 escape hatch).

- **`external-apis.schema.ts`** — `CloudFnSchema` (`CLOUDFN_API_KEY` + `CLOUDFN_BASE_URL`) + `CloudFnConfig` type. Keys verbatim from legacy `schemas/external-apis.ts` (T-999.1.9-13 tampering mitigation — grep-verified identical).
