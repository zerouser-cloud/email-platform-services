## Background (pre-discussion context)

Phase 999.1.9 была запланирована после длинного ad-hoc обсуждения по итогам 999.1.8. Обсуждение выявило:

- Динамический `buildTopologyShape()` в `packages/config/src/topology.ts` — корень проблемы с типами (`z.infer` теряет ключи топологии).
- `SERVICE` каталог смешивает identity и topology (port 3001, grpc.port 50051 хардкожены, при этом `port` нигде в runtime не используется — dead code).
- Асимметрия: HTTP server port из env, gRPC server port из каталога.
- В процессе 999.1.8 добавлен костыль WR-02 (`createConfigModule<TSchema, TEnv>` double generic) для type safety — он откачен перед стартом 999.1.9 (`git revert aa4f988` → `7c272af`).

Архитектурные решения, locked ДО начала формального discuss-phase (через разговор):
- 4-слойная модель Identity/Topology/Internals/Constants
- Per-app раскладка `packages/config/src/apps/{name}/` зеркально `/apps/{name}/`
- Shared blocks в `packages/config/src/infra/`
- Static TopologySchema (per-app spread)
- Удаление ручных intersection-алиасов
- Откат WR-02 double generic

Фаза создана через `/gsd:insert-phase 999.1 config-layering-refactor-services-first-structure` → получила номер 999.1.9 (next-available decimal, как и 999.1.8 ранее).

## Gray Area 2.4: createConfigModule factory fate

**First iteration (rejected):**

User поставил under challenge изначальный двойной путь (factory + module-level const для main.ts). Question: «зачем два источника истины?»

Claude пересмотрел подход и нашёл: в NestJS есть `app.get(TOKEN)` — достаёт provider из DI после `NestFactory.create()` но до `app.listen()`. Это даёт **один** путь доступа ко всему.

**Second iteration (final):**

| Option | Description | Selected |
|--------|-------------|----------|
| Сохранить factory, унифицировать доступ через DI | Один loadConfig внутри createConfigModule, один DI-контейнер, один путь доступа. main.ts использует `app.get<AudienceEnv>(AUDIENCE_CONFIG)`. Консьюмеры — через `@Inject`. Упрощённая сигнатура factory. Narrow-port сохраняется. drizzle.config.ts (не-Nest CLI) — исключение по среде. | ✓ |
| Удалить factory, всё через прямые импорты | Module-level `export const audienceConfig = loadConfig(...)`. Ломает narrow-port DI pattern, httpClientProvider, throttle.module.ts useFactory. Каждый консьюмер видит весь env. Борется с NestJS-фреймворком. | |

**User's choice:** Сохранить factory, унифицировать доступ через DI
**Notes:** User argument: «один подход, один источник истины». Factory остаётся ОДНИМ местом вызова loadConfig + ОДНИМ источником registration в DI. main.ts через `app.get` — тот же DI, без module-level const. CLI — другая среда, не второй путь.

## Gray Area 5: Migration Strategy

| Option | Description | Selected |
|--------|-------------|----------|
| A — атомарный switchover | Один большой коммит всё переключает. Как Plan 04 в 999.1.8. Нет двух паттернов одновременно, git revert легко. Но риск: если что-то сломалось — всё сломалось. | |
