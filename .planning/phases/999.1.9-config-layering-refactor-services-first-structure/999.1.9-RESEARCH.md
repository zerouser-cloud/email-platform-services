## Summary

Фаза 999.1.9 — первый комплексный рефакторинг конфигурационной подсистемы после долгого цикла фаз 999.1 → 999.1.8. В 999.1.8 мы вытащили `loadConfig` в foundation и ввели foundation-factory `createConfigModule` (I-3.5), устранив ~240 LOC boilerplate'а в 6 сервисах. Но **костяк остался из старой модели**: динамический `TopologySchema` в `packages/config/src/topology.ts` через `buildTopologyShape()`-цикл собирает shape на runtime — `z.infer` не резолвится статически, потому каждый `{Svc}EnvSchema` имеет ручной intersection-alias (`GlobalTopology & DatabaseConfig & ...`), а main.ts / provider.ts содержат 12× `as {Svc}Env` cast'ов (F-01 blocker).

Цель 999.1.9 — **устранить F-01 через рестуктуризацию**, а не через type-level gymnastics (как предлагал вариант V1 в SOLUTIONS). Выбрана более фундаментальная версия: пер-сервисные топологии объявляются статически (`{Svc}TopologyShape as const`), `TopologySchema`/`GlobalTopology`/`GlobalEnv` удаляются целиком, схемы собираются через native `z.object({ ...OwnTopology, ...PeerTopologies, ...infra })` без helper-обёртки (D-05..D-07). Заодно: (A) вся `packages/config/src/` перестраивается на path-symmetry с `/apps/{name}/`; (E) вводится `{SVC}_GRPC_PORT` env-переменная для симметрии HTTP↔gRPC server port; (D) доступ к config унифицируется через `app.get<{Svc}Env>({SVC}_CONFIG)` в main.ts; (F) env-parity validation переезжает в CI-скрипт; (G) мертвые поля (`SERVICE.*.port`, `displayName`, `envKeys`, `compose.ts`, `env-schema.ts`) удаляются.

**Primary recommendation:** Plan-режим — **incremental per-service migration (D-23), canary=audience, 6 per-service commits подряд + atomic cleanup commit в конце**. Старый `TopologySchema` + новый per-service `{Svc}TopologyShape` сосуществуют на время миграции — `topology.ts` удаляется ТОЛЬКО после того, как все 6 сервисов ушли на per-app схемы. Валидация — dual-mode smoke gate (pnpm start:native + pnpm start:isolated) после каждого сервиса И в финале, плюс grep-инварианты (0 `as XxxEnv`, 0 `composeSchemas`, 0 `TopologySchema` imports) в Verification.

## User Constraints (from CONTEXT.md)

### Locked Decisions

**Structural Layout**

- **D-01:** `packages/config/src/apps/{name}/` зеркально отображает `/apps/{name}/` (audience, auth, sender, parser, gateway, notifier). Path symmetry — тот же mental model, та же навигация: работаешь над audience → код в `/apps/audience/`, конфиг в `/packages/config/src/apps/audience/`.
- **D-02:** `packages/config/src/infra/` содержит **shared building blocks** (database.schema.ts, redis.schema.ts, rabbitmq.schema.ts, logging.schema.ts, grpc.schema.ts, cors.schema.ts, rate-limit.schema.ts, storage.schema.ts). Инфраструктурные куски, переиспользуемые между сервисами, не принадлежат ни одному app'у.
- **D-03:** Per-app файлы: `identity.config.ts` + `topology.schema.ts` + `env.schema.ts` + `external-apis.schema.ts` (опционально, для parser/notifier/sender) + `index.ts` (barrel). Содержимое каждого:
  - `identity.config.ts` — pure identity object (id, grpc.package, grpc.serviceName, diToken). БЕЗ port/displayName/envKeys.
  - `topology.schema.ts` — `{Svc}TopologyShape = { {SVC}_PORT, {SVC}_GRPC_PORT, {SVC}_GRPC_URL } as const`. Для gateway — без GRPC_PORT/GRPC_URL.
  - `env.schema.ts` — `{Svc}EnvSchema = z.object({ ...OwnTopology, ...PeerTopologies, ...infraBlocks })` + `type {Svc}Env = z.infer<typeof {Svc}EnvSchema>`.
  - `external-apis.schema.ts` — service-specific 3rd-party API schemas (Telegram→notifier, AppStoreSpy→parser, CloudFn→sender). Не все сервисы имеют.

**Catalog Aggregation**

- **D-04:** Папка `packages/config/src/catalog/` **удаляется**. `defineService` factory + `SERVICE` aggregator переезжают в `packages/config/src/index.ts` (или близко к корню). Меньше уровней папок. `SERVICE` собирается как `{ audience: AUDIENCE, auth: AUTH, ... }` через импорты из `apps/{name}/identity.config.ts`. Публичный API `SERVICE.audience.diToken` не меняется.

**Topology (static, not dynamic)**

- **D-05:** `packages/config/src/topology.ts` **удаляется**. Динамический `buildTopologyShape()` больше не существует. Каждый сервис объявляет свой статический `{Svc}TopologyShape` в `packages/config/src/apps/{name}/topology.schema.ts`. Глобального `TopologySchema` нет — каждый сервис явно спредит peer topologies из других сервисов, кого он зовёт.
- **D-06:** `GlobalTopology` mapped-type **удаляется**. `GlobalEnv` тип и `GlobalEnvSchema` (если где-то нужен — маловероятно) — либо удаляются, либо переводятся на `z.infer` над статическим spread всех per-service topologies.

**Env Composition Style**

- **D-07:** Per-service `env.schema.ts` композируется через **явные spread'ы** (не `.merge()` chain, не helper функция). Пример:

  ```typescript
  export const AudienceEnvSchema = z.object({
    ...AudienceTopologyShape,         // own topology
    ...ParserTopologyShape,           // peer: audience → parser
    ...DatabaseSchema.shape,
    ...RabbitSchema.shape,
    ...LoggingSchema.shape,
    ...GrpcSchema.shape,
  });
  export type AudienceEnv = z.infer<typeof AudienceEnvSchema>;
  ```

  Grep по `ParserTopologyShape` сразу показывает, кто зовёт parser. Self-documenting peer graph через импорты.

**Type System Cleanup**

- **D-08:** Все ручные intersection-алиасы **удаляются**: `AudienceEnv = GlobalTopology & DatabaseConfig & ...`, `AuthEnv = ...` и т.п. (6× файлов в apps/*/infrastructure/bootstrap/config/*-env.schema.ts). Заменяются на `type {Svc}Env = z.infer<typeof {Svc}EnvSchema>`.
- **D-09:** `loadConfig` сигнатура упрощается: `loadConfig<T extends z.ZodType>(schema: T): z.infer<T>`. TEnv generic удаляется (был добавлен в WR-02 fix 999.1.8, уже откачен в коммите 7c272af перед стартом этой фазы).
- **D-10:** Аналогично `createConfigModule<T>({ schema, token, narrowPorts })` — упрощается, без TEnv generic (типы выводятся автоматически из schema).
- **D-11:** Все `as XxxEnv` cast'ы удаляются. В main.ts (6× мест), в external consumers (4× мест: telegram.module.ts, cloudfn.module.ts, appstorespy.module.ts, throttle.module.ts). После удаления intersection-алиасов + z.infer — cast'ы становятся не нужны.

**Unified DI Access**

- **D-12:** Единый путь доступа к конфигу — **через NestJS DI**. `createConfigModule` factory остаётся и работает как сейчас: внутри eager `loadConfig(schema)`, регистрирует `{SVC}_CONFIG` token + narrow-port providers. main.ts использует `const config = app.get<AudienceEnv>(AUDIENCE_CONFIG)` **после** `NestFactory.create()` но **до** `app.listen()`. Никаких module-level `export const audienceConfig = loadConfig(...)` в пакете. Никакого двойного пути.
- **D-13:** Narrow-port DI pattern (PERSISTENCE_CONFIG_PORT, LOGGING_CONFIG_PORT, GRPC_CLIENT_CONFIG_PORT, etc.) сохраняется как есть. Drizzle/Pino/gRPC-clients продолжают получать только свои срезы через `@Inject(XXX_CONFIG_PORT)`.
- **D-14:** Исключение из "DI only": `drizzle.config.ts` (CLI-скрипт для миграций, выполняется вне Nest). Он продолжает вызывать `loadConfig(DatabaseSchema)` напрямую из `@email-platform/foundation`. Это **не второй путь**, это **другая среда выполнения** (Node CLI без DI-контейнера).

**HTTP↔gRPC Server Port Symmetry**

- **D-15:** Добавляется новый env var `{SVC}_GRPC_PORT` для всех 5 gRPC сервисов (auth=50051, sender=50052, parser=50053, audience=50054, notifier=50055). HTTP port (`{SVC}_PORT`) и gRPC port (`{SVC}_GRPC_PORT`) — симметрично из env, оба через Zod.
- **D-16:** `createGrpcServerOptions(SERVICE.{svc}, config)` в foundation меняется: вместо `url: '0.0.0.0:${service.grpc.port}'` (из каталога) читает `config.{SVC}_GRPC_PORT` (из env). `SERVER.DEFAULT_HOST` остаётся константой из foundation.
- **D-17:** `SERVICE.{svc}.grpc.port` (литерал 50051 и т.п.) **удаляется** из каталога вместе с полями `port`, `displayName`, `envKeys`. В identity.config.ts остаются только: `id`, `grpc.package`, `grpc.serviceName`, `diToken`.

**Env Parity Validation**

- **D-18:** Runtime env parity check **убирается**: больше нет "каждый сервис при старте валидирует все env-переменные всех сервисов". Каждый сервис валидирует только то, что ему реально нужно (own topology + peer topologies + infra blocks которые он использует). Быстрее старт, меньше false-positive в dev.
- **D-19:** Env parity переносится в CI-скрипт `scripts/check-env-parity.sh` (или эквивалент). Скрипт собирает все `{SVC}EnvSchema` из packages/config/src/apps/*, объединяет набор ключей, сравнивает с `.env.example` + `.env.docker.example`. Падает, если есть расхождения. Интегрируется в GitHub Actions (до build job).

**File Cleanup**

- **D-20:** `packages/config/src/compose.ts` **удаляется** целиком. `composeSchemas` helper не нужен — нативный `z.object({ ...A.shape, ...B.shape })` делает то же самое, со статической типизацией (когда входные схемы статические). Заодно закрывается `ban-types` lint-error с неверным `eslint-disable` именем.
- **D-21:** `packages/config/src/schemas/external-apis.ts` разносится: `TelegramSchema` → `apps/notifier/external-apis.schema.ts`, `AppStoreSpySchema` → `apps/parser/`, `CloudFnSchema` → `apps/sender/`. Общий файл удаляется.
- **D-22:** `packages/config/src/env-schema.ts` (GlobalEnvSchema) — удаляется если не используется. Если где-то импортируется — переводится на `z.infer` над статическими частями или тоже удаляется после миграции всех консьюмеров.

**Migration Strategy**

- **D-23:** Migration **инкрементальная по сервисам** (не атомарный switchover, не по уровням). Последовательность: (1) setup структуры пакета — create `infra/` + `apps/` скелеты, переместить shared schemas в `infra/` (старые файлы временно остаются); (2) добавить `{SVC}_GRPC_PORT` в `.env.example`, `.env.docker.example`, `infra/docker-compose*.yml`; (3) мигрировать **audience как canary** — создать `apps/audience/{identity,topology,env.schema}`, обновить `apps/audience/src/infrastructure/bootstrap/config/*`, main.ts на `app.get`, smoke gate (pnpm start:native + pnpm start:isolated); (4-8) последовательно остальные 5 сервисов, по плану на каждый с smoke после; (9) cleanup — удалить `topology.ts`, `env-schema.ts`, `catalog/`, `schemas/external-apis.ts`, `compose.ts`, все intersection-алиасы, SERVICE dead fields; (10) env parity CI script; (11) final verification + dual-mode smoke gate.

### Claude's Discretion

- Точные имена экспортов в barrel'ах (например, `export { AudienceEnvSchema, AudienceTopologyShape, AUDIENCE } from './audience'` vs раздельные re-exports) — по consistency.
- Формат per-service external-apis.schema.ts (inline схем vs импорт отдельных блоков из infra/ если общие).
- Именование helper'ов внутри реализации (defineService может переименоваться при переносе в index.ts, если уместно).
- Детали CI env-parity скрипта (bash vs Node, точное API).

### Deferred Ideas (OUT OF SCOPE)

- **Extraction of non-env config sources** (если появятся feature flags, quotas, etc. не из env) — рассмотреть в отдельной фазе, когда появится реальная необходимость. Сейчас гипотетично.
- **Code-gen topology** из SERVICE каталога (альтернатива D-05 static spread) — phased-out в обсуждении. Если потом появится 10+ сервисов и ручное spread станет тяжёлым, можно рассмотреть. Сейчас 6 сервисов — ручной spread оптимален.
- **Schema refinements (cross-field validation)** на уровне per-service env.schema — вне scope (пока нет реальных refinements в проекте, не вносим гипотетически).

## Project Constraints (from CLAUDE.md)

- **Архитектура apps/:** Clean/DDD/Hexagonal. 999.1.9 не меняет hexagonal layout; `infrastructure/bootstrap/config/*` остаётся канонической точкой `{Svc}ConfigModule` per nestjs-hexagonal-mapping skill §Bootstrap.
- **Архитектура packages/:** утилитарная, без DDD. `packages/config/src/{infra,apps}/` вписывается в эту модель.
- **Без бизнес-логики, без тестов.** Валидация — grep-инварианты + dual-mode runtime smoke.
- **Tech stack (не меняем):** NestJS 11, TypeScript 5.7+, gRPC, Postgres, RabbitMQ, Redis. Zod `^4.3.6` [VERIFIED: `packages/config/package.json`].
- **no-magic-values:** DI tokens через `Symbol()`. Все литералы (порты 50051-50055, 3000-3005) только в `.env*` и `apps/{name}/topology.schema.ts` (именованные константы). [CITED: CLAUDE.md §Code Style]
- **No switch/case, no if/else chains (3+ branches):** используем dispatch/polymorphism. Для 6-сервисного рефакторинга — per-service атомарные commits, а не `switch(svc)` в одном общем скрипте.
- **No environment branching:** никакого `NODE_ENV`/`isDev`. Гarантия: после миграции ни в одном `packages/config/src/**` / `apps/*/src/**` нет `process.env` кроме canonical boundary `packages/foundation/src/external/config/load-config.ts`.
- **No infrastructure changes without user approval:** добавление `{SVC}_GRPC_PORT` в `.env*` + `docker-compose*.yml` — инфраструктурное изменение. Каждый PLAN для этих файлов **требует** явной паузы/подтверждения. Ports 5432, 6379, 5672, 9000 неприкасаемы (не затрагиваются); новые gRPC ports 50051-50055 уже были в каталоге и в expose-секциях compose — просто делаем их видимыми через env.
- **No defaults or optionals in env schemas:** новые `{SVC}_GRPC_PORT` — `z.coerce.number().positive()`, БЕЗ `.default()`/`.optional()`. 5 required вписываются в `.env*` файлы.
- **Infrastructure-client layering:** Phase 999.1.9 УКРЕПЛЯЕТ Three-Layer Rule — Identity (`packages/config/src/apps/{name}/identity.config.ts` — pure data) / Mechanism (`packages/foundation/src/external/config/` — уже на месте после 999.1.8) / Assembly (`apps/{svc}/src/infrastructure/bootstrap/config/*.module.ts` — тонкий `createConfigModule()` вызов). Config становится symmetrical-copy gRPC-клиентского паттерна (999.7.x).
- **Runtime smoke verification:** обязателен dual-mode gate (`pnpm start:native` + `pnpm start:isolated`) после canary-сервиса и после завершения фазы. Пауза/подтверждение у пользователя после каждого smoke. Скрипты: `pnpm build`, `pnpm lint`, `pnpm check-arch`, `pnpm infra:up/down`. [CITED: package.json]

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|--------------|----------------|-----------|
| Zod schema definitions (env structure) | Identity (`packages/config/`) | — | Pure data contracts, no framework/runtime. |
| Per-service env composition (shape spread) | Identity (`packages/config/src/apps/{name}/env.schema.ts`) | — | Каждый сервис знает какие shared infra-блоки + peer topologies он использует; выражено через spread. |
| `loadConfig(schema)` (Zod parse of `process.env`) | Mechanism (`packages/foundation/src/external/config/load-config.ts`) | — | Framework-free wrapper с кэшем по schema-ref. Не меняется. |
| `createConfigModule({schema,token,narrowPorts})` factory | Mechanism (`packages/foundation/src/external/config/`) | — | DI-binding механизм. Уже на месте; только упрощается сигнатура. |
| `SERVICE` catalog (identity data) | Identity (`packages/config/src/index.ts` после D-04) | — | Чистая identity без транспортных tokens/ports. |
| `createGrpcServerOptions(service, config)` + gRPC port resolution | Mechanism (`packages/foundation/src/external/grpc/grpc-server.factory.ts`) | — | Принимает `{SVC}_GRPC_PORT` как параметр из config вместо чтения service.grpc.port из каталога (D-16). |
| Per-service `{Svc}ConfigModule = createConfigModule({...})` | Assembly (`apps/{svc}/src/infrastructure/bootstrap/config/*.module.ts`) | — | Тонкая обёртка-композер; выбор narrow-ports — service-specific. |
| Per-service main.ts bootstrap (gRPC server registration, `app.listen`) | Assembly (`apps/{svc}/src/main.ts`) | — | `app.get<{Svc}Env>({SVC}_CONFIG)` + `createGrpcServerOptions(identity, { port: config.{SVC}_GRPC_PORT, protoDir: config.PROTO_DIR })`. |
| Infra-side env-files + docker-compose exposure of `{SVC}_GRPC_PORT` | Deployment (`infra/`, `.env*`) | — | User-approval required; инфраструктурное изменение per infrastructure-guard skill. |
| Env-parity validation (CI) | Build-tool (`scripts/check-env-parity.sh`, `.github/workflows/ci.yml`) | — | Статический cross-file check вне runtime. |

### Pattern 1: Per-service static topology shape

**What:** Каждый gRPC-сервис объявляет свои 3 env-ключа как `as const` объект.
**When to use:** D-03 + D-05 для всех 6 сервисов (gateway — особый случай, только HTTP port).
**Example:**

```typescript
// packages/config/src/apps/audience/topology.schema.ts
import { z } from 'zod';

export const AudienceTopologyShape = {
  AUDIENCE_PORT: z.coerce.number().positive(),
  AUDIENCE_GRPC_PORT: z.coerce.number().positive(),
  AUDIENCE_GRPC_URL: z.string().min(1),
} as const;
```

**Для gateway:**

```typescript
// packages/config/src/apps/gateway/topology.schema.ts
import { z } from 'zod';

export const GatewayTopologyShape = {
  GATEWAY_PORT: z.coerce.number().positive(),
  // нет GRPC_PORT / GRPC_URL — gateway не экспонирует gRPC server и не зовёт себя
} as const;
```

**Почему это решает F-01:** `as const` → ключи сохраняются как literal types. `z.object({ ...AudienceTopologyShape, ...})` → `ZodObject<{ AUDIENCE_PORT: ZodNumber, AUDIENCE_GRPC_PORT: ZodNumber, AUDIENCE_GRPC_URL: ZodString, ... }>`. `z.infer` резолвит до конкретных ключей-литералов. Cast не нужен.

### Pattern 2: Per-service env schema composition via native spread

### Pattern 4: Unified DI access in main.ts

**What:** D-12 — `app.get<{Svc}Env>({SVC}_CONFIG)` вместо прямого `loadConfig(Schema) as {Svc}Env`.
**When to use:** все 6 main.ts.
**Example (audience/src/main.ts after migration):**

```typescript
import 'reflect-metadata';
import { NestFactory } from '@nestjs/core';
import { Logger } from 'nestjs-pino';
import { SERVICE, AUDIENCE_CONFIG, type AudienceEnv } from '@email-platform/config';
import { createGrpcServerOptions, SERVER, BOOTSTRAP } from '@email-platform/foundation';
import { AudienceModule } from './audience.module';

async function bootstrap() {
  const app = await NestFactory.create(AudienceModule, { bufferLogs: true });

  const config = app.get<AudienceEnv>(AUDIENCE_CONFIG);    // ← D-12: DI access after create(), before listen()

  app.useLogger(await app.resolve(Logger));
  app.enableShutdownHooks();

  app.connectMicroservice(createGrpcServerOptions(
    SERVICE.audience,
    config.AUDIENCE_GRPC_PORT,    // ← D-16: port from env, not catalog
    config.PROTO_DIR,
  ));

  await app.startAllMicroservices();
  await app.listen(config.AUDIENCE_PORT, SERVER.DEFAULT_HOST);
}
bootstrap().catch((err) => {
  console.error(BOOTSTRAP.FAILED_MESSAGE, err);
  process.exit(1);
});
```

**Важные детали (verified via WebSearch + existing NestJS usage in codebase):**
- `app.get<T>(token)` работает **сразу после** `NestFactory.create()` — контейнер полностью инициализирован. [CITED: NestJS docs; см. §Sources — Mastering Providers, Tokens, and Scopes in NestJS DI]
- `app.get(Symbol)` работает для `useValue` providers (наш случай — `createConfigModule` регистрирует `{ provide: opts.token, useValue: loadConfig(opts.schema) }`). [VERIFIED: `create-config-module.ts:83-86`]
- `@Global()` module (`global: true` в returned DynamicModule) гарантирует, что `{SVC}_CONFIG` виден из root `app.get()` scope'а. [VERIFIED: `create-config-module.ts:98`]
- **Async-providers edge case:** `useValue: loadConfig(...)` — eager (sync), никаких async-complications. Если бы был `useFactory` + `async factory`, нужно было бы `await app.resolve()` вместо `app.get()`. Не наш случай.
- Gateway main.ts уже использует `app.get(Logger)` / `app.get(GrpcToHttpExceptionFilter)` — [VERIFIED: `apps/gateway/src/main.ts:20,40`] — паттерн уже живой в codebase.

### Anti-Patterns to Avoid

- **Hand-rolled `@Global() @Module({}) class { static forRoot() {...} }` в apps.** Уже устранено в 999.1.8 через `createConfigModule`; 999.1.9 сохраняет factory, только упрощает сигнатуру.
- **`composeSchemas(A, B, C)` helper.** Удаляется D-20. Native `z.object({ ...A.shape, ...B.shape, ...C.shape })` даёт то же самое + лучшую TS-инференцию + закрывает `ban-types` lint error.
- **Dynamic `Record<string, z.ZodType>` в Zod-схемах.** Корень F-01. Никакие циклы, reduce'ы, dynamic shape building — только static literal `as const` объекты.
- **Intersection-aliases (`AudienceEnv = GlobalTopology & DatabaseConfig & ...`).** Удаляются D-08. `type {Svc}Env = z.infer<typeof {Svc}EnvSchema>` — единственный источник истины для типа.
- **`as {Svc}Env` cast на выходе loadConfig/createConfigModule.** Удаляются D-11. После D-05/D-07/D-08 — cast больше не нужен.
- **`import type { {Svc}Env } from './env.schema';` в external consumers типа telegram.module.ts через `httpClientProvider<X, {Svc}Env>`.** Паттерн `envToken: NOTIFIER_CONFIG` + `deps.env[KEY] as string` — это F-02 (отдельный backlog). 999.1.9 НЕ решает F-02 (это работа фазы 999.1.2 per SOLUTIONS §Sub-Phase Grouping), но 999.1.9 должен **не сделать F-02 хуже**: после D-05/D-08 тип `NotifierEnv` становится `z.infer`, external consumers (telegram.module.ts) потребуют минимальных правок (import path change + cleanup cast'а в 3 местах per D-11).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Композиция Zod-схем | Кастомный `composeSchemas(...)` helper | Native `z.object({ ...A.shape, ...B.shape })` | [CITED: Zod 4 docs — `.shape` is the canonical spread primitive; D-20] Helper добавляет wrapper, не добавляет capability. |
| Извлечение ключей из Zod-схемы для env-parity check | Кастомный reflection на ZodObject internals | `schema.shape` + `Object.keys(schema.shape)` — нативный API Zod | [CITED: Zod 4 API — `.keyof()` returns `ZodEnum`; `Object.keys(obj.shape)` работает напрямую] |
| Peer topology resolution | Dynamic цикл по `SERVICE` (как текущий `buildTopologyShape`) | Явные import'ы + spread в каждом env.schema.ts | D-07: «self-documenting peer graph через импорты». Grep показывает зависимости. |
| DI binding per-service config | Hand-rolled `@Global() {Svc}ConfigModule.forRoot()` class | `createConfigModule({...})` factory из foundation | [VERIFIED: 999.1.8 Plan 04 уже внедрил pattern; 999.1.9 упрощает сигнатуру] |
| `process.env` reading в CLI (drizzle) | `DatabaseSchema.parse(process.env)` в `drizzle.config.ts` | `loadConfig(DatabaseSchema)` из `@email-platform/foundation` (D-14) | [VERIFIED: commit 8cba247 — все 4 drizzle.config.ts уже на loadConfig; I-0.1 compliance] |
| gRPC server URL construction | Inline `'0.0.0.0:50051'` в main.ts | `createGrpcServerOptions(identity, config.{SVC}_GRPC_PORT, config.PROTO_DIR)` | D-16: foundation-factory инкапсулирует конструкцию + HealthImplementation wiring. |

**Key insight:** Phase 999.1.9 — это **structural refactor, а не introduce-new-mechanisms** рефакторинг. Все механизмы уже в foundation (loadConfig, createConfigModule, createGrpcServerOptions). Задача — перепроектировать **Identity слой** (`packages/config/src/`) так, чтобы Mechanism-слой (foundation) использовался без cast'ов.

## Common Pitfalls

### Pitfall 1: Circular imports in per-service schemas (audience↔parser, sender↔audience)

**What goes wrong:** `audience/env.schema.ts` импортирует `ParserTopologyShape` из `../parser/topology.schema.ts`. Если parser позже (гипотетически) начнёт зависеть от audience, получится circular import.
**Why it happens:** native TS module system кеширует, но circular imports дают undefined exports в момент module evaluation.
**How to avoid:** (a) `topology.schema.ts` файлы — **атомарные**, содержат ТОЛЬКО `{Svc}TopologyShape as const` без импортов из других `apps/{name}/*`. (b) `env.schema.ts` импортирует `topology.schema.ts` (own + peers) + `infra/*` shared — односторонний граф. Нет `env.schema.ts` → `env.schema.ts` imports.
**Warning signs:** `pnpm build` error `X is not a function` (on an object destructure), `Module has no exported member ...`, `TypeError: Cannot read property 'shape' of undefined` в runtime.
**Grep invariant:** `grep -rE "from '.*/apps/" packages/config/src/apps/*/topology.schema.ts` должно дать 0 результатов (topology schemas — terminal leaves).

### Pitfall 2: `createConfigModule` generic inference degrades without explicit TEnv

**What goes wrong:** D-10 убирает `<typeof AudienceEnvSchema, AudienceEnv>` generic. Если TS-инференция не резолвит корректно `TSchema extends z.ZodType` для `z.object({ ...A, ...B.shape })` в Zod 4 — slice functions получают `env: unknown`.
**Why it happens:** Zod 4's `z.ZodType<TEnv>` output-generic — wide, исторически у `composeSchemas(...)` был `ZodObject<MergeShapes<T>>` и нужен был explicit type hint. Native `z.object({...})` должен инферить нативно, но edge-cases возможны.
**How to avoid:** **Сначала верифицировать на canary (audience)**. Если `slice: (c) => ({ DATABASE_URL: c.DATABASE_URL })` — типа `c` выводится как `AudienceEnv` (hover в IDE), все ОК. Если `c: unknown` — вариант A: возвращаем explicit generic temporarily; вариант B: добавляем slice return-type annotations (`slice: (c): PersistenceConfig => ({...})`) — static narrowing.
**Warning signs:** `tsc` error `Property 'DATABASE_URL' does not exist on type 'unknown'` в slice functions.
**Mitigation:** VerificationPlan должен включать explicit `pnpm build` + `pnpm typecheck` после audience migration, до выхода на другие сервисы.

### Pitfall 3: `loadConfig` cache — Zod-schema reference identity

**What goes wrong:** `loadConfig` кэширует по reference на ZodType (Map<z.ZodType, unknown>). Если создать две копии `AudienceEnvSchema` (например, через `z.object({...})` дважды) — две cache entries + две runtime parses.
**Why it happens:** `packages/foundation/src/external/config/load-config.ts:14` — `const cache = new Map<z.ZodType, unknown>()`. Идентичность по `===`.
**How to avoid:** `AudienceEnvSchema` объявлен ОДИН РАЗ в `packages/config/src/apps/audience/env.schema.ts` как `export const`. Все консьюмеры (audience-config.module.ts, main.ts если бы ещё где-то, drizzle.config.ts аналогичный pattern) импортируют один и тот же reference. Безопасно.
**Warning signs:** двойной лог parsing (`loadConfig` сам не логирует, но surrounding logs могут показать дублирование) или performance-regression.
**Verification:** `loadConfig` выполняется 1 раз per service per service-startup. Smoke-test боевой.

### Pitfall 4: Gateway peer-topology explosion

**What goes wrong:** Gateway зовёт все 5 downstream-сервисов → нужен spread 5 peer topologies. Если забыть хотя бы один — main.ts не скомпилируется (`config.AUTH_GRPC_URL` не типизирован), но smoke test пропустит если тот сервис не зовётся на старте.
**Why it happens:** Human error при копировании apps/audience/env.schema.ts шаблона на gateway — можно случайно забыть добавить 1 из 5 peers.
**How to avoid:** (a) В gateway/env.schema.ts — **явный** комментарий `// Gateway calls ALL 5 downstream services`. (b) В Verification — grep `GATEWAY_CONFIG_PORT` reference count: `grep -c '_GRPC_URL' apps/gateway/src/infrastructure/bootstrap/config/gateway-config.module.ts` должен быть ≥ 5.
**Warning signs:** `config.AUTH_GRPC_URL is possibly undefined` в TSC, или runtime `Cannot read property 'AUTH_GRPC_URL' of undefined` в ClientGrpcProxy creation.

### Pitfall 5: docker-compose `expose:` блоки уже содержат hardcoded gRPC ports — не путать с env-driven

**What goes wrong:** `infra/docker-compose.yml:39 expose: ["3001", "50051"]` — хардкод, не из env. Если в `.env.docker` поставить `AUTH_GRPC_PORT=50099`, сервис попытается забиндиться на 50099, но compose expose только 50051 — connectivity failure.
**Why it happens:** Docker Compose `expose:` это literal number list, не переменные. Env-file `AUTH_GRPC_PORT=50051` внутри контейнера управляет только биндингом; внешняя видимость управляется `expose:` + `ports:`.
**How to avoid:** Plan для infra-wave должен (a) добавить `{SVC}_GRPC_PORT` в `.env*` со значениями 50051-50055 (совпадают с current expose lists), (b) НЕ менять `expose:` в docker-compose.yml — они уже правильные, (c) опционально сделать `expose: ["${AUTH_PORT}", "${AUTH_GRPC_PORT}"]` как cleanup-finalization, но это risk-prone (Docker Compose interpolation в arrays) — может быть вне scope.
**Warning signs:** `pnpm start:isolated` → gateway → auth connection `ECONNREFUSED`.
**Verification:** manual smoke после env update. Expose lists и env values должны совпадать.

### Pitfall 6: drizzle.config.ts × 4 — НЕ требуют изменений, но сохранить бдительность

**What goes wrong:** Если в cleanup wave случайно удалить `DatabaseSchema` экспорт из `packages/config/index.ts` или переместить файл без re-export — drizzle-kit рушится.
**Why it happens:** `drizzle.config.ts` импортирует `DatabaseSchema, SERVICE` из `@email-platform/config`. [VERIFIED: всех 4 drizzle.config.ts файлов]. D-02 перемещает `database.ts` в `infra/database.schema.ts`; D-04 убирает `catalog/services.ts`.
**How to avoid:** `packages/config/src/index.ts` должен **re-export `DatabaseSchema`** из `./infra/database.schema` + **re-export `SERVICE`** (composed in index.ts per D-04) — public API preserved. grep-invariant post-fase: `DatabaseSchema` и `SERVICE` продолжают импортиться из `@email-platform/config` без смены path в 4 drizzle.config.ts.
**Warning signs:** `pnpm --filter audience drizzle:generate` (или аналог) → `Module has no exported member 'DatabaseSchema'`.

### Pitfall 7: `SERVICE.*.envKeys` + `.port` + `.displayName` — все 4 drizzle.config.ts + main.ts не используют их, НО foundation grpc-server.factory.ts зависит

**What goes wrong:** D-17 удаляет `.port`, `.displayName`, `.envKeys` из `defineService` return. `createGrpcServerOptions` на строке 22 читает `service.grpc.port`.
**Why it happens:** Фаза 999.1.9 одновременно удаляет поле и вводит новый способ чтения (D-16: config.{SVC}_GRPC_PORT). Cascade — `grpc-server.factory.ts` должен быть refactored ДО или ВМЕСТЕ С удалением catalog поля.
**How to avoid:** Ordering: (1) refactor `createGrpcServerOptions` signature + 5 main.ts call-sites FIRST (atomic commit), (2) затем DELETE `.grpc.port` from catalog. Иначе промежуточный commit имеет broken type (`service.grpc.port is undefined`).
**Grep-invariant post-fase:** `grep -rn 'service\\.grpc\\.port' packages/` = 0.

### Pitfall 8: `export * from './catalog'` removal breaks downstream type imports

**What goes wrong:** `packages/config/src/index.ts` сейчас: `export * from './catalog/types'; export * from './catalog/define-service'; export * from './catalog/services';`. После D-04 catalog удаляется. Если `GrpcServiceDeclaration` type используется где-то еще — break.
**Why it happens:** `grpc-server.factory.ts:3` импортирует `GrpcServiceDeclaration` — [VERIFIED]. Если удалить catalog без re-definition — foundation не билдится.
**How to avoid:** Plan order: (1) create new `GrpcServiceIdentity` type в `packages/config/src/index.ts` (или `packages/config/src/apps/types.ts` barrel), (2) обновить `grpc-server.factory.ts` на новое имя (D-16 refactor), (3) DELETE old `catalog/types.ts`.
**Grep-invariant:** `grep -rn 'GrpcServiceDeclaration' packages/ apps/` после фазы = 0, `grep -rn 'GrpcServiceIdentity' packages/` = 1+ (definition + import).

### Example 3: createConfigModule — simplified signature (D-10)

```typescript
// packages/foundation/src/external/config/create-config-module.ts (target after D-10)
// Source: D-10 — no TEnv generic, types derived from schema
import { Global, Module, type DynamicModule, type Provider } from '@nestjs/common';
import type { z } from 'zod';
import { loadConfig } from './load-config';

export interface CreateConfigModuleOptions<TSchema extends z.ZodType> {
  readonly schema: TSchema;
  readonly token: symbol;
  readonly narrowPorts?: ReadonlyArray<{
    readonly port: symbol;
    readonly slice: (env: z.infer<TSchema>) => unknown;
  }>;
}

@Global()
@Module({})
class ConfigModuleHolder {}

export function createConfigModule<TSchema extends z.ZodType>(
  opts: CreateConfigModuleOptions<TSchema>,
): DynamicModule {
  const configProvider: Provider = {
    provide: opts.token,
    useValue: loadConfig(opts.schema),
  };

  const narrowPortProviders: Provider[] = (opts.narrowPorts ?? []).map(({ port, slice }) => ({
    provide: port,
    inject: [opts.token],
    useFactory: (env: z.infer<TSchema>) => slice(env),
  }));

  return {
    module: ConfigModuleHolder,
    global: true,                       // preserves 999.11.1 Plan 10 Rule 3
    providers: [configProvider, ...narrowPortProviders],
    exports: [opts.token, ...(opts.narrowPorts ?? []).map((p) => p.port)],
  };
}
```

**Diff from current:** удаляется второй параметр `TEnv = z.infer<TSchema>` — автоматически выводится.

#!/usr/bin/env bash
# Source: existing scripts/check-env-parity.sh + Zod schema key extraction
# Extracts keys from all {Svc}EnvSchema files + diffs against .env* templates
set -euo pipefail

    echo "  --- Expected keys only in schemas ---"

    echo "  --- Actual keys only in $file ---"
    comm -13 <(expected_keys) <(keys_of "$file") | sed 's/^/    /'
    return 1
  fi
  echo "PASS: $label"
}

ERRORS=0
diff_against .env.example ".env.example vs schemas" || ERRORS=$((ERRORS+1))
diff_against .env.docker.example ".env.docker.example vs schemas" || ERRORS=$((ERRORS+1))
# pre-existing 2 diffs (preserved for F-12/F-13/F-14 class):
# (actually post-999.1.9, these two diffs may be replaced by schema-driven parity above)
