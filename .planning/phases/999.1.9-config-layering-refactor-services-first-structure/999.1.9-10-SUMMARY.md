## Decisions Made

- **Whitelist over schema pollution (orchestrator-only vars):** Four env vars required by `infra/docker-compose.infra.yml` (postgres init + garage admin token) never flow to NestJS apps. Three alternatives were considered: (a) delete from `.env*.example` → breaks docker-compose; (b) add to an app Zod schema → violates D-03 services-first layering (no app consumes them); (c) whitelist in the script → preserves both layering and CI strictness. Chose (c). Whitelist is self-documenting (inline provenance comments) and extensible (append + document when a new infra container appears).
- **Minimal CI job surface:** `env-parity` does not install pnpm or node, does not restore turbo cache, does not run `pnpm install`. It is pure bash + grep over checked-out source. This keeps gate feedback on the order of seconds and avoids cache-pollution risk.
- **Parallel `needs:` fan-out:** `lint`, `typecheck`, `build` each depend on `env-parity` individually rather than chaining `lint → typecheck → build`. Preserves existing pipeline parallelism for the three existing jobs; env-parity is a single choke-point in front of all of them.
- **docker-build.yml left untouched:** env-parity is a PR-check concern (CI runs on `pull_request`). `docker-build.yml` runs post-merge and already consumes a different set of secrets; touching it would expand scope beyond what user approved.

## Manual-Review Checklist (per Assumption A6)

**Future schema additions require manual verification if they use non-standard key-declaration patterns.**

The CI gate relies on a single grep regex (`^\s*[A-Z][A-Z0-9_]*:\s*z\.`) that matches plain top-level `KEY: z.xxx(...)` declarations inside Zod schemas (or inside static `as const` topology shapes — structurally identical). Any future phase that introduces a Zod schema declaring env keys via one of the following patterns will bypass the gate silently:

1. Nested `.merge()` / `.extend()` composition.
2. `z.record(z.enum([...]), z.string())` for dynamic key sets.
3. Dynamic construction via loops / `Object.fromEntries` / spread-from-helper-fn.
4. Computed property keys (e.g., `[DYN_KEY]:`).

**When adding such a schema, the developer MUST:**

1. **Manually diff** the schema's resolved key set against `.env.example` and `.env.docker.example` before merging.
2. **Extend `scripts/check-env-parity.sh`** to cover the new declaration pattern — either (a) refactor the schema to the plain pattern (strongly preferred; grep stays one-line), (b) add a dual-pass grep for the new syntax, or (c) migrate the script to a Node-runtime variant that does `Object.keys(XxxSchema.shape)` reflection on an imported `@email-platform/config` module.
3. **Update the `ORCHESTRATOR-ONLY KEYS` docstring** if the new env var is consumed only by docker-compose (never by an app).

**The current regex is only safe while all schemas under `packages/config/src/apps/` + `infra/` use the plain `KEY: z.xxx` top-level pattern.** Verified present state (as of 2026-04-21): all 8 `infra/*.schema.ts` + 6 `apps/*/env.schema.ts` + 6 `apps/*/topology.schema.ts` + 3 `apps/{notifier,parser,sender}/external-apis.schema.ts` conform.
