## Problem Statement

After Phase 999.7.1, all 8 gRPC client classes follow this shape:

```ts
// apps/gateway/src/infrastructure/clients/audience/audience.client.ts
export class AudienceClient extends AbstractGrpcClient<AudienceProto.AudienceServiceClient> {
  constructor(grpc: ClientGrpc, cls: ClsService, defaultDeadlineMs: number) {
    super(grpc, cls, SERVICE.audience.grpc.serviceName, defaultDeadlineMs, AudienceClient.name);
  }

  listGroups(req: AudienceProto.ListGroupsRequest, opts?: CallOpts): Promise<AudienceProto.GroupList> {
    return this.call('listGroups', this.raw.listGroups(req, this.buildMetadata(opts)));
  }
  // ... 8 more methods, all identical pattern
}
```

The user surfaced concerns:

1. **Скрытое состояние.** `this.raw`, `this.call`, `this.serviceName`, `this.cls`, `this.logger` приходят «откуда-то» из base. В IDE надо go-to-definition чтобы увидеть.
2. **Жёсткая связанность.** Нельзя поменять одну часть без изменения base.
3. **Multiple inheritance невозможна.**
4. **Тестирование.** Наследование требует наследовать в тестах же или mock'ать всё подряд.
5. **«is-a» semantically странно.** `AudienceClient` is-a `AbstractGrpcClient`? Скорее uses-a — отношение has-a/uses-a, не is-a.

User explicitly said: «Я не очень люблю наследование, щас это в целом многие считают антипаттерном. Это очень не явно... может это можно сделать как-то через DI, явно? Что бы это было архитектурно красиво.»

## Alternatives Considered (from session log)

### Alternative A: Composition + injected helper (CHOSEN)

```ts
// foundation
@Injectable()
export class GrpcCaller {
  constructor(
    private readonly cls: ClsService,
    private readonly logger: PinoNativeLogger,
    private readonly defaultDeadlineMs: number,
    private readonly serviceName: string,
  ) {}

  buildMetadata(opts?: CallOpts): Metadata { /* ... */ }
  async call<T>(method: string, observable: Observable<T>): Promise<T> { /* ... */ }
}

// apps
export class AudienceClient {
  private readonly raw: AudienceProto.AudienceServiceClient;

  constructor(
    grpcClient: ClientGrpc,
    private readonly grpc: GrpcCaller,  // ← explicitly injected
  ) {
    this.raw = grpcClient.getService(SERVICE.audience.grpc.serviceName);
  }

  listGroups(req: AudienceProto.ListGroupsRequest, opts?: CallOpts) {
    return this.grpc.call('listGroups', this.raw.listGroups(req, this.grpc.buildMetadata(opts)));
  }
}
```

**Pros:** explicit dependencies, no hidden `this.call`, mock GrpcCaller in tests = one line, idiomatic NestJS DI, symmetric with future HTTP/RMQ helpers.
**Cons:** slightly more constructor boilerplate, two-step "get raw stub" (ClientGrpc.getService) plus helper inject.

### Alternative B: Factory function (functional, no class)

```ts
export function createAudienceClient(grpcClient: ClientGrpc, deps): AudienceClient {
  const raw = grpcClient.getService<AudienceProto.AudienceServiceClient>(SERVICE.audience.grpc.serviceName);
  const helper = createGrpcCall({ ...deps, serviceName: SERVICE.audience.grpc.serviceName });

  return {
    listGroups: (req, opts) => helper.call('listGroups', raw.listGroups(req, helper.metadata(opts))),
    // ... etc
  };
}
export type AudienceClient = ReturnType<typeof createAudienceClient>;
```

**Pros:** zero `this`, zero classes, easy to test, tree-shaking friendly.
**Cons:** no `instanceof` discrimination, NestJS DI culture is class-heavy (need `useFactory`).

### Alternative C: Decorator pattern via Proxy

```ts
const audienceClient = wrapGrpcClient(
  grpcClient.getService<AudienceProto.AudienceServiceClient>(...),
  helper,
);
```

`wrapGrpcClient` returns a Proxy that auto-wraps every method with `helper.call(...)`.

**Pros:** zero per-upstream boilerplate.
**Cons:** Proxy magic loses precise types, debug stack traces harder, `opts` plumbing through Proxy with type safety is nontrivial.

### Alternative D: Codegen from .proto

Generate the entire client class (including the `helper.call(...)` wrapping) from `.proto` files via custom protoc plugin.

**Pros:** zero hand-written boilerplate, most idiomatic gRPC approach.
**Cons:** very high migration cost, requires maintained protoc plugin or ts-proto fork.

## User's Decision

**Alternative A — composition + injected GrpcCaller.** Reasons (per session log):

1. **Idiomatic NestJS** — DI injects the helper as any other service (`ClsService`, `ConfigService`)
2. **Explicit:** all dependencies visible in constructor — no «магических» `this.call`
3. **Low migration cost** — pattern already familiar after 999.7.x (defineGrpcClient uses useFactory)
4. **Symmetry:** fits into `infrastructure-client-layering` skill as universal pattern (HTTP, RMQ, S3, Redis, DB+ORM all eventually pull `XxxCaller` helpers)
5. **Testability:** mock GrpcCaller — one line, no need to extend in tests

Trade-off accepted: more constructor boilerplate per upstream is OK because it's explicit.

## Open Questions for Discuss-Phase to Resolve

1. **`GrpcCaller` lifetime / scope:** singleton per app, or per-client (one instance per upstream because `serviceName` differs)?
   - Likely per-client, since `serviceName` and `defaultDeadlineMs` are baked into closure
   - But could be a service-locator pattern (`grpcCaller.for(serviceName, deadlineMs)`)

2. **`GrpcCaller` location in foundation:** new file `packages/foundation/src/external/grpc/clients/grpc-caller.ts` adjacent to `define-grpc-client.ts`? Same module/barrel?

3. **`defineGrpcClient` evolution:** the factory itself produces `useFactory: (grpc, cls, config) => new ClientClass(grpc, cls, deadlineMs)`. After Variant A migration, the factory needs to also instantiate `GrpcCaller`. Options:
   - `defineGrpcClient` injects `GrpcCaller` itself and passes it to constructor
   - `defineGrpcClient` exposes a builder that the consumer module uses to create both
   - Helper instantiation moves out of factory entirely

4. **Migration order:** all 8 upstreams in one PLAN, or one upstream per PLAN (atomic per-upstream like 999.7.1)? Probably atomic per-upstream — same 8-way replication pattern.

5. **`AbstractGrpcClient` deprecation:** delete entirely after migration, or keep as `@deprecated` with warning until next major? Codebase has no consumers outside the 8 we're migrating, so straight delete is fine.

6. **`raw` stub access:** in Alternative A, the client class holds `private readonly raw: AudienceProto.AudienceServiceClient`. Should this be:
   - Initialized in constructor (current sketch)
   - Lazy via `OnModuleInit` (current `AbstractGrpcClient` pattern — Pitfall 3 in 999.7-RESEARCH said "must happen in lifecycle hook, not constructor" because `getService` may not be ready)
   - Need to verify: does `ClientGrpc.getService()` work in constructor, or only after `onModuleInit`?

7. **Logger acquisition:** `AbstractGrpcClient` uses `PinoLogger.root.child({ context })` deferred to `onModuleInit` (Pitfall 6). `GrpcCaller` needs the same care — when does it get its logger?

8. **`infrastructure-client-layering` skill update:** the skill currently says "Apps own assembly + naming". Add a new prescription: "use injected callers (composition) over inheritance for all infra clients". Keep the same principle for HTTP/RMQ/S3/Redis/DB.

9. **Effects on `defineGrpcClient` return shape:** if `GrpcCaller` is per-client, then `GrpcClientBuildResult` may need to expose it (or keep it internal — the consumer module shouldn't care).

10. **ESLint guard from Phase 999.7.1:** the `no-restricted-syntax` block on `@Injectable()` in client classes — keep it as is. After Variant A, client classes still won't have `@Injectable` because they're constructed via `useFactory` in `defineGrpcClient`.
