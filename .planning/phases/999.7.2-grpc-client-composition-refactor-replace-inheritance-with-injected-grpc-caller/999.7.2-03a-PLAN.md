<objective>
Sweep-migrate the 4 remaining gateway-side gRPC client facades (sender, parser, audience, notifier in `apps/gateway/src/infrastructure/clients/`) from `extends AbstractGrpcClient<T>` to composition with injected `GrpcCaller`. Each upstream is ONE atomic commit per D-14 — if any commit fails typecheck/lint, STOP and discuss before proceeding.

The pattern is IDENTICAL to the Plan 02 pilot `AuthClient` migration — only the class name, proto namespace, `SERVICE.<id>` reference, and method list vary per upstream. PATTERNS.md entry 7 documents the replication rule.

**Purpose:** After Plan 02 healed 1/8 gRPC clients (auth), this plan heals 4/8 more (all gateway-side). Plan 03b follows immediately to heal the remaining 3/8 cross-service clients. After Plans 03a + 03b, all 8 gRPC client facades are on the unified composition pattern.

**Output:** 8 MODIFIED files (4 `*.client.ts` + 4 `*-client.module.ts`). Estimated ~31 total method-body rewrites across the 4 clients (11 sender + 8 parser + 9 audience + 3 notifier).

**Task structure:** 4 tasks, one per upstream, executed sequentially. Each task's scope is exactly 2 files (the client + its module) and 1 atomic commit. Per-task typecheck + lint is MANDATORY.

**Mid-sweep failure policy (D-14):** If any per-task `pnpm --filter=@email-platform/gateway typecheck && lint` fails and cannot be fixed within ~15 min of investigation, STOP the sweep. Revert the failing commit, resume with `/gsd-debug`, do NOT stack subsequent tasks on a broken base.

**Cross-service clients deferred to Plan 03b:** The 3 cross-service gRPC clients (sender→audience, parser→notifier, audience→parser) live under `apps/sender/`, `apps/parser/`, `apps/audience/` respectively — they are migrated in Plan 03b to keep this plan's task count ≤ 4. Runtime smoke for both waves is deferred to Plan 05's final smoke per D-14.
</objective>
