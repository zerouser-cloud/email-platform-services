# Phase 999.7.2: gRPC client composition refactor — replace inheritance with injected GrpcCaller - Context

**Gathered:** 2026-04-17
**Status:** Ready for planning

<domain>
## Phase Boundary

Заменить наследование `extends AbstractGrpcClient` на композицию через инжектируемый `GrpcCaller` helper. 8 gRPC client classов перестают наследоваться от базового класса, получают `GrpcCaller` через DI (внутри `useFactory` от `defineGrpcClient`), хранят `this.raw` явно. `GrpcCaller` выносится в foundation как plain class (без декораторов) и инкапсулирует: построение metadata с deadline, конверсию Observable→Promise через `lastValueFrom`, структурное логирование с correlationId, точку расширения для будущей трассировки / error-policy / retry / circuit breaker. `AbstractGrpcClient` удаляется полностью. Skill `infrastructure-client-layering` расширяется разделом «Composition over inheritance»; дополнительно создаётся новый универсальный skill `composition-over-inheritance`, применимый ко всему codebase.

Out of scope:
- HTTP/RMQ/S3/Redis/DB+ORM refactors — отдельные будущие фазы, применят те же принципы через skill `infrastructure-client-layering` + новый `composition-over-inheritance`
- Streaming RPC поддержка (tracked в backlog 999.9)
- Новые gRPC методы или бизнес-логика
- Server-side gRPC patterns
- Реализация трассировки (OpenTelemetry), error policy, circuit breaker — `GrpcCaller` оставляет для них **точку расширения**, но сами механизмы в этой фазе не внедряются

## Implementation Decisions

### GrpcCaller: форма и lifecycle

- **D-01:** `GrpcCaller` — plain class в foundation, **без** `@Injectable()` и прочих NestJS декораторов. Инстанцируется напрямую через `new GrpcCaller(...)` внутри `useFactory` фабрики `defineGrpcClient`. Симметрично client class — та же «decorator-free под useFactory» регулярность, закреплённая в 999.7.1 D-07/D-08.

- **D-02:** Per-upstream scope. `serviceName` и `defaultDeadlineMs` baked в closure конструктора как `private readonly`. Один instance `GrpcCaller` создаётся для каждого из 8 upstream'ов (не singleton, не service-locator).

- **D-03:** Lazy logger acquisition. Конструктор принимает `logContext: string` (НЕ готовый logger). При первом вызове `call()` внутри `emitLog()` лениво строится `PinoLogger.root.child({ context: logContext })` и кэшируется в `private logger: PinoNativeLogger | undefined`. Избегает Pitfall 6 (last-init overwrites all) из 999.7-RESEARCH и защищает от ситуации, когда `PinoLogger.root === undefined` в момент выполнения `useFactory` (до `LoggerModule.onModuleInit`).

- **D-04:** `ClsService` живёт внутри `GrpcCaller`, не в client class. Конструктор GrpcCaller принимает `ClsService`, `cls.getId()` читается в `emitLog()` для поля `correlationId`. Client class вообще не импортирует `nestjs-cls` — cross-cutting concern корректно принадлежит helper'у, не domain facade'у.

- **D-05:** Сигнатура публичного `call()` — `call(method, opts, rpcFactory: (metadata: Metadata) => Observable<T>): Promise<T>`. Это **архитектурный твик** относительно исходного эскиза в NOTES.md: вместо передачи готового Observable клиент передаёт **callback-фабрику**, получающую уже построенные metadata. Что это даёт:
  - `buildMetadata()` становится **приватным** методом `GrpcCaller` — одной публичной точкой API меньше
  - `GrpcCaller.call()` получает **полный контроль** над жизненным циклом RPC: создание span'а до metadata, повторный вызов `rpcFactory(meta)` при retry, централизованная обёртка catch для error policy
  - 8 client classов остаются стабильными при добавлении трассировки / circuit breaker / retry — все изменения локальны в `grpc-caller.ts`
  - Эта точка расширения критически важна, потому что логирование, error escalation и distributed tracing в проекте ещё не финализированы

### Foundation: wiring и экспорты

- **D-06:** Файл располагается по пути `packages/foundation/src/external/grpc/clients/grpc-caller.ts` — рядом с `define-grpc-client.ts` и `abstract-grpc-client.ts` (последний удаляется). Тот же barrel (`clients/index.ts`). Не создаём подпапку `callers/` — преждевременно, пока единственный экземпляр.

- **D-07:** `defineGrpcClient` сам инстанцирует `GrpcCaller` внутри своей `useFactory`. `inject` расширяется: добавляется `ClsService` (`ConfigService` уже был). `useFactory` создаёт `new GrpcCaller(cls, serviceName, deadlineMs, logContext)` и передаёт его в build callback. Новая сигнатура build: `(grpcClient: ClientGrpc, caller: GrpcCaller) => T`. Consumer-module не видит `GrpcCaller` — инкапсуляция.

- **D-08:** `GrpcClientBuildResult` interface **не изменяется** относительно 999.7.1: `imports | providers | exports | grpcToken | healthToken`. `GrpcCaller` остаётся internal — не добавляем `callerToken` в return, не регистрируем отдельный провайдер. Один instance принадлежит одному client class через closure build callback'а.

- **D-09:** Тип `GrpcCaller` экспортируется из foundation barrel (`packages/foundation/src/external/grpc/clients/index.ts` и корневой `packages/foundation/src/index.ts`). Необходимо, чтобы client class мог типизировать `constructor(grpc: ClientGrpc, private readonly grpc: GrpcCaller)`. Exported как `export type { GrpcCaller }` — structural typing достаточен, не обязательно экспортировать сам класс (экспорт имплементации убивает возможность легко подменить в тестах).

- **D-10:** `AbstractGrpcClient` удаляется из barrel полностью: строка `export { AbstractGrpcClient } from './abstract-grpc-client'` убирается, файл `abstract-grpc-client.ts` физически удаляется (`git rm`). История в git сохраняется.

### Client class lifecycle

- **D-11:** `this.raw` инициализируется **в конструкторе** напрямую: `this.raw = grpcClient.getService<TRaw>(SERVICE.<name>.grpc.serviceName)`. Client class становится полностью NestJS-free — **без** `implements OnModuleInit`, **без** импорта `@nestjs/common`, **без** non-null assertions на полях. Под `useFactory` порядок резолва провайдеров гарантирует, что `ClientGrpc` готов к моменту `new AuthClient(...)`; `getService()` — синхронный вызов, возвращающий proxy (real channel биндится лениво на первый RPC).

## Specific Ideas

- **Твик сигнатуры call() ≠ cosmetic** — смена с `call(method, observable)` на `call(method, opts, rpcFactory)` сделана **явно ради будущего**: логирование, distributed tracing (OpenTelemetry), circuit breaker, retry policy, error escalation — все эти механизмы в проекте не финализированы, но будут. Callback-сигнатура даёт `GrpcCaller.call()` полный контроль над жизненным циклом RPC (metadata → span → invoke → catch → log), чтобы 8 client classов оставались стабильными при их внедрении. Точка расширения — единственный файл `grpc-caller.ts`

- **Symmetric design language** — pattern «plain class + useFactory + positional params + decorator-free» применён последовательно к трём типам артефактов: (a) client class (AuthClient — установлено в 999.7.1), (b) GrpcCaller (новый, эта фаза), (c) factory build callback `(grpcClient, caller) => T`. Единая регулярность упрощает мысленную модель для HTTP/RMQ/S3/Redis refactor'ов

- **Composition-over-inheritance как универсальный принцип, не локальный pattern** — пользователь явно попросил skill, действующий **везде**, не только в infrastructure. Это отличает D-17 от `infrastructure-client-layering` (D-15): последний конкретизирует трёхслойную раскладку для infra-clients, первый запрещает наследование как таковое с narrow exception'ами. Два skill'а должны ссылаться друг на друга
