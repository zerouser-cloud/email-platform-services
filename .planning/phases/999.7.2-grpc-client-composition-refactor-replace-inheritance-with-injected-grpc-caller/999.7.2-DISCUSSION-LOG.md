## Area 1 — GrpcCaller: scope + lifecycle

**User clarification before answering:** Asked to see concrete code examples. Claude produced 4-file sketch (grpc-caller.ts, auth.client.ts, define-grpc-client.ts, auth-client.module.ts). User approved with one architectural refinement.

### Q1.1 — GrpcCaller — в какой форме?

| Option | Description | Selected |
|---|---|---|
| Plain class, no decorators | `class GrpcCaller` без `@Injectable()`. Instantiated в useFactory | ✓ |
| @Injectable + TRANSIENT + per-client provider | @Injectable({scope: Scope.TRANSIENT}), per-client useFactory под own token | |
| createGrpcCaller() factory function | Return object без class и `this`. Functional style | |

**Decision:** Plain class. Симметрично client class — та же decorator-free регулярность 999.7.1.

### Q1.2 — serviceName + defaultDeadlineMs — где хранятся?

| Option | Description | Selected |
|---|---|---|
| Baked in closure — one GrpcCaller per upstream | Constructor accepts both, private readonly. Один instance per upstream | ✓ |
| Service-locator: grpcCaller.for(serviceName, deadlineMs) | Один global singleton + factory method per upstream | |
| DefaultDeadlineMs читается от ConfigService per-call | ConfigService в конструкторе, overhead каждого call | |

**Decision:** Baked in closure. Immutable, no indirection.

### Q1.3 — Logger acquisition в GrpcCaller — когда?

| Option | Description | Selected |
|---|---|---|
| Lazy: context в конструкторе, logger = PinoLogger.root.child() on first call | Avoid Pitfall 6 and PinoLogger.root-undefined-in-useFactory | ✓ |
| Eager в конструкторе | Consumer module делает .child() до `new GrpcCaller`. Risk — useFactory может выполниться до LoggerModule.onModuleInit | |
| OnModuleInit (как AbstractGrpcClient сейчас) | Ломается под useFactory — lifecycle hooks не вызываются на products без @Injectable | |

**Decision:** Lazy on first call, cached.

### Q1.4 — ClsService — где живёт?

| Option | Description | Selected |
|---|---|---|
| Внутри GrpcCaller | GrpcCaller reads cls.getId() in emitLog() | ✓ |
| Client class получает ClsService, передаёт в grpc.call() | Каждый client дублирует correlationId reading, leak cross-cutting | |
| ClsService как factory-dep, callback closure | Testability +1, но чужда NestJS DI-идиоме | |

**Decision:** ClsService внутри GrpcCaller. Client class вообще не знает о ClsService.

### User's architectural refinement — call() signature twik

После утверждения 4 вопросов user поднял вопрос extensibility: «у нас еще не выработаны полностью подходы к логгированию и эскалации и обработке ошибок, это может меняться. А так же у нас будет трассировка… это не будет проблемой при расширении и изменении в будущем?»

Claude предложил твик сигнатуры `call()`:

| Before | After |
|---|---|
| `grpc.call('login', raw.login(req, grpc.buildMetadata(opts)))` | `grpc.call('login', opts, (meta) => raw.login(req, meta))` |
| buildMetadata() публичный на GrpcCaller | buildMetadata() приватный |
| Observable создан до того, как call() получает управление | call() полностью контролирует lifecycle: span → metadata → rpc → catch |

**User's decision:** «Хорошо, делаем с твиком». Зафиксировано как D-05.

**Rationale:** логирование, distributed tracing, circuit breaker, retry policy, error escalation — всё ещё не финализировано в проекте. Callback-сигнатура оставляет точку расширения в `grpc-caller.ts` одного файла, не в 8 client'ах.

## Area 2 — Factory & module wiring

### Q2.1 — Где в foundation живёт файл grpc-caller.ts?

| Option | Description | Selected |
|---|---|---|
| Adjacent to define-grpc-client.ts | `packages/foundation/src/external/grpc/clients/grpc-caller.ts`. Same barrel | ✓ |
| Новая подпапка callers/ | Отделить helper от facade primitives. Premature — единичный файл | |
| Internal submodule | В internal/. Overkill для типа, который клиент видит | |

**Decision:** Adjacent to define-grpc-client.ts.

### Q2.2 — Кто инстанцирует GrpcCaller?

| Option | Description | Selected |
|---|---|---|
| defineGrpcClient сам, внутри useFactory | Фабрика получает ClsService + ConfigService, создаёт new GrpcCaller, передаёт в build() | ✓ |
| Consumer-module вручную | auth-client.module.ts пишет свой provider. Boilerplate дублируется 8 раз | |
| Helper-фабрика createGrpcCallerProvider(service) | Отдельный хелпер. Лишний слой, serviceName всё равно из opts.service | |

**Decision:** defineGrpcClient сам внутри useFactory. Consumer-module не видит GrpcCaller.

### Q2.3 — GrpcClientBuildResult — нужно ли экспортировать GrpcCaller instance?

| Option | Description | Selected |
|---|---|---|
| Нет, GrpcCaller внутренний | BuildResult как в 999.7.1: imports/providers/exports/grpcToken/healthToken | ✓ |
| Да, callerToken в return для DI-доступа | Extra provider, нет use case'а | |
| Да, экспорт типа + instance через build callback | Тип нужен для типизации параметра, сам instance — нет | |

**Decision:** GrpcCaller внутренний. BuildResult не меняется. Тип экспортируется из barrel (разрешённо D-09).

### Q2.4 — AbstractGrpcClient после рефактора — что с barrel export?

| Option | Description | Selected |
|---|---|---|
| Удалить AbstractGrpcClient + экспорт из barrel полностью | git rm + убрать export. Git history хранит историю | ✓ |
| Оставить @deprecated на 1 фазу | Nobody outside to benefit from deprecation. Half-measure | |
| Переместить в internal/legacy | Dead file занимающий место. Git даёт archaeology | |

**Decision:** Delete полностью в этой же фазе.

## Area 3 — Client class lifecycle

### Q3.1 — Инициализация this.raw в client classes — где?

| Option | Description | Selected |
|---|---|---|
| В конструкторе напрямую | this.raw = grpcClient.getService<T>(...). Client class полностью NestJS-free | ✓ |
| В onModuleInit (вернуться к текущему паттерну) | Защита от Pitfall 3, но тащит NestJS import в domain facade + non-null assertion | |
| Lazy getter на первом методе | Избегает Pitfall 3 без OnModuleInit. Runtime-check на каждый call | |

**Decision:** В конструкторе. Под useFactory grpcClient уже готов, getService() синхронный возвращающий proxy.

### Q3.2 — Что включить в research-фазу, чтобы verify'ить выбор?

| Option | Description | Selected |
|---|---|---|
| Code+runtime smoke: 1 pilot client + pnpm start:native | Pilot AuthClient, smoke test, fallback на OnModuleInit если ломается | ✓ |
| Только документация: прочитать @nestjs/microservices source | Fast, но может пропустить integration-эффекты | |
| Сохранить OnModuleInit defensively | Не тратим время, но теряем цель фазы (decorator-free domain facade) | |

**Decision:** Pilot + runtime smoke + fallback план.
