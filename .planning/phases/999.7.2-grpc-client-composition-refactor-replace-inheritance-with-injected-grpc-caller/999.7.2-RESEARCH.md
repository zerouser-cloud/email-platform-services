### Locked Decisions

**GrpcCaller: форма и lifecycle**

- **D-01:** `GrpcCaller` — plain class в foundation, БЕЗ `@Injectable()` и прочих NestJS декораторов. Инстанцируется напрямую через `new GrpcCaller(...)` внутри `useFactory` фабрики `defineGrpcClient`. Симметрично client class — та же «decorator-free под useFactory» регулярность, закреплённая в 999.7.1 D-07/D-08.
- **D-02:** Per-upstream scope. `serviceName` и `defaultDeadlineMs` baked в closure конструктора как `private readonly`. Один instance `GrpcCaller` создаётся для каждого из 8 upstream'ов (не singleton, не service-locator).

### Pattern 1: GrpcCaller — Plain Helper Class

**What:** `GrpcCaller` is a plain ES class (no `@Injectable`, no decorators, no NestJS lifecycle hooks) that encapsulates metadata construction, Observable→Promise conversion, and structured logging. It's instantiated inside `defineGrpcClient`'s `useFactory` — symmetric with how client facades are instantiated.

**When to use:** Every gRPC client facade receives one via composition.

**Example:**

```typescript
// packages/foundation/src/external/grpc/clients/grpc-caller.ts
// Source: synthesized from CONTEXT.md D-01..D-05, verified against current AbstractGrpcClient
import { Metadata } from '@grpc/grpc-js';
import { PinoLogger } from 'nestjs-pino';
import type { Logger as PinoNativeLogger } from 'pino';
import { ClsService } from 'nestjs-cls';
import { type Observable, lastValueFrom } from 'rxjs';
import { GRPC_CLIENT_LOG, GRPC_CLIENT_DEADLINE } from './clients.constants';
import type { CallOpts, GrpcClientLogFields } from './grpc-client-logging.types';

export class GrpcCaller {
  // Pitfall 6 defence: PinoLogger.root is populated during NestApplication.init
  // step 2 (registerRouter → registerMiddleware → LoggerModule.configure).
  // useFactory fires in step 1 (registerModules), so root may still be undefined.
  // First call() fires from a controller handler — long after step 2 completes.
  // Lazy acquisition is therefore safe.
  private logger: PinoNativeLogger | undefined;

  constructor(
    private readonly cls: ClsService,
    private readonly serviceName: string,
    private readonly defaultDeadlineMs: number,
    private readonly logContext: string,
  ) {}

  async call<TResponse>(
    method: string,
    opts: CallOpts | undefined,
    rpcFactory: (metadata: Metadata) => Observable<TResponse>,
  ): Promise<TResponse> {
    const start = Date.now();
    const metadata = this.buildMetadata(opts);
    // Extension point: span creation, retry loop, circuit check would go here.
    try {
      const response = await lastValueFrom(rpcFactory(metadata));
      this.emitLog(method, start, GRPC_CLIENT_LOG.STATUS_OK);
      return response;
    } catch (error) {
      this.emitLog(method, start, GRPC_CLIENT_LOG.STATUS_ERROR);
      throw error;
    }
  }

  private buildMetadata(opts: CallOpts | undefined): Metadata {
    const metadata = new Metadata();
    const deadlineMs = opts?.deadlineMs ?? this.defaultDeadlineMs;
    metadata.set(
      GRPC_CLIENT_DEADLINE.METADATA_HEADER,
      `${deadlineMs}${GRPC_CLIENT_DEADLINE.METADATA_UNIT_MILLISECONDS}`,
    );
    return metadata;
  }

  private emitLog(
    method: string,
    startedAt: number,
    status: typeof GRPC_CLIENT_LOG.STATUS_OK | typeof GRPC_CLIENT_LOG.STATUS_ERROR,
  ): void {
    const fields: GrpcClientLogFields = {
      service: this.serviceName,
      method,
      duration_ms: Date.now() - startedAt,
      status,
      correlationId: this.cls.getId(),
    };
    const logLevel = status === GRPC_CLIENT_LOG.STATUS_OK ? 'info' : 'error';
    this.getLogger()[logLevel](fields, GRPC_CLIENT_LOG.EVENT);
  }

  private getLogger(): PinoNativeLogger {
    if (!this.logger) {
      this.logger = PinoLogger.root.child({ context: this.logContext });
    }
    return this.logger;
  }
}
```

### Pattern 2: Client Facade — Composition via Positional Constructor

**What:** Client facade is a plain ES class with NO NestJS imports (neither `@Injectable` nor `OnModuleInit` nor `@Inject`). It receives both `ClientGrpc` and `GrpcCaller` as positional constructor params and initializes `this.raw` in the constructor.

import type { ClientGrpc } from '@nestjs/microservices';
import { AuthProto, CommonProto } from '@email-platform/contracts';
import { SERVICE } from '@email-platform/config';
import type { GrpcCaller, CallOpts } from '@email-platform/foundation';

export class AuthClient {

    );

### Pattern 3: defineGrpcClient — Instantiates GrpcCaller Inside useFactory

**What:** Evolution of 999.7.1's defineGrpcClient. Inject array extended with `ClsService`. useFactory constructs `GrpcCaller` before calling build callback. GrpcClientBuildResult shape unchanged.

**Example:**

```typescript
// packages/foundation/src/external/grpc/clients/define-grpc-client.ts  (evolution)
// ... imports unchanged, plus:
import { GrpcCaller } from './grpc-caller';

// DefineGrpcClientOpts may gain a `logContext?: string` field (Claude discretion per CONTEXT.md),
// defaulting to `${upperId}Client` if absent.

export function defineGrpcClient<T extends object>(
  opts: DefineGrpcClientOpts,
  build: (grpcClient: ClientGrpc, caller: GrpcCaller) => T,   // ← new signature
): GrpcClientBuildResult {
  const upperId = opts.service.id.toUpperCase();
  const grpcToken = Symbol.for(`${upperId}${TOKEN_SUFFIX.CLIENT_GRPC}`);
  const healthToken = Symbol.for(`${upperId}${TOKEN_SUFFIX.GRPC_HEALTH}`);

  const facadeProvider: Provider = {
    provide: opts.clientToken,
    inject: [grpcToken, ClsService, ConfigService],            // ← same inject list as today
    useFactory: (grpc: ClientGrpc, cls: ClsService, config: ConfigService) => {
      const caller = new GrpcCaller(
        cls,
        opts.service.grpc.serviceName,
        config.get<number>('GRPC_DEADLINE_MS')!,
        `${upperId}Client`,                                    // ← logContext (default)
      );
      return build(grpc, caller);
    },
  };
  // healthProvider, ClientsModule.registerAsync, return — UNCHANGED
}
```

### Anti-Patterns to Avoid

- **`extends AbstractGrpcClient<T>`** — the target pattern of this phase. See composition-over-inheritance skill for the universal form.
- **Passing a pre-built Observable instead of a callback** — `call('login', this.raw.login(req, meta))` was the 999.7.1 shape. It prevents retry (can't recreate), tracing (span wraps observable, but metadata is already baked), and clean error policy. Callback shape `(m) => this.raw.login(req, m)` fixes all three.
- **Storing PinoLogger instead of PinoNativeLogger** — `PinoLogger` (from nestjs-pino) has a shared `setContext()` that mutates a singleton. Always use `PinoLogger.root.child({ context })` to get an independent `Logger` from pino. This is the original 999.7 Pitfall 6 defence.
- **Calling `getService()` in `onModuleInit`** — was required by the old Pitfall 3 claim, but verified false (see Target 1 below). Constructor is correct. Keeping onModuleInit leaks NestJS lifecycle into a domain class that should be pure.
- **Eager `PinoLogger.root.child()` in constructor** — `root` may not be set during useFactory execution (step 1 of init). Lazy getter sidesteps the issue.

## Verification Summary (7 Targets)

### Target 1 — Pitfall 3 Obsolescence (`getService()` in constructor)

**VERDICT: PASS — Pitfall 3 is OBSOLETE under useFactory.**

**Claim from CONTEXT.md D-11:** `this.raw = grpcClient.getService<T>(serviceName)` can run synchronously in the client constructor (inside a useFactory).

**Evidence (highest confidence):** Read `node_modules/.pnpm/@nestjs+microservices@11.1.16_…/@nestjs/microservices/client/client-grpc.js`.

- Line 24-37 (`ClientGrpcProxy.constructor`): `this.grpcClients = this.createClients()` — proto is loaded and package definitions are ready during the constructor of the gRPC proxy itself (which runs first in `registerModules`, step 1 of init). This happens synchronously, before the facade's useFactory fires.
- Line 38-50 (`getService`):
  ```js
  getService(name) {
      const grpcClient = this.getClientByServiceName(name);
      const clientRef = this.getClient(name);
      if (!clientRef) { throw new InvalidGrpcServiceException(name); }
      const protoMethods = Object.keys(clientRef[name].prototype);
      const grpcService = {};
      protoMethods.forEach(m => { grpcService[m] = this.createServiceMethod(grpcClient, m); });
      return grpcService;
  }
  ```
  Pure synchronous function. No `async`, no `await`, no `connect()`. Builds a wrapper object with one method per proto RPC. Returns immediately.
- Line 262-264 (`connect`): `async connect() { throw new Error('The "connect()" method is not supported in gRPC mode.'); }` — gRPC in NestJS explicitly has NO async init step. Nothing to wait for before `getService()` can run.
- Line 159-211 (`createUnaryServiceMethod`): the actual gRPC channel (`new clientRef[name](this.url, credentials, options)` on line 79) is created lazily in `createClientByServiceName` on the first call to `getService` — and even that is synchronous. The Observable it returns from the generated method only *starts* the wire call when subscribed (line 197-211).

**Why Pitfall 3 was claimed in 999.7-RESEARCH:** The old `AbstractGrpcClient` inherited from a class that used `@Inject(AUTH_CLIENT_GRPC) private readonly grpc: ClientGrpc` — a DI-resolved reference. Early experiments likely hit `undefined` because `@Inject` without a useFactory has different resolution timing, OR the abstract class was built defensively before the pattern was fully understood. ## Common Pitfalls

### Pitfall 1: Lazy PinoLogger.root — Timing During useFactory [CARRIED FORWARD FROM 999.7-RESEARCH Pitfall 6, STATUS REFINED]

**What goes wrong:** Eagerly calling `PinoLogger.root.child({ context })` in `GrpcCaller`'s constructor throws `TypeError: Cannot read property 'child' of undefined`.

**Why it happens:** `useFactory` inside `defineGrpcClient` runs during `NestApplication.init` step 1 (`registerModules`). `PinoLogger.root` is set during step 2 (`registerRouter` → `registerMiddleware` → `LoggerModule.configure`). Step 2 runs AFTER step 1.

**How to avoid:** Lazy pattern — store only `logContext: string` in constructor. On first `call()`, inside `emitLog()`, call `getLogger()` which does:
```ts
private getLogger(): PinoNativeLogger {
  if (!this.logger) {
    this.logger = PinoLogger.root.child({ context: this.logContext });
  }
  return this.logger;
}
```
First `call()` only fires from a controller handler, which runs long after step 2 completes.

**Warning signs:** Any code path that invokes `grpcCaller.call(...)` during module initialization (e.g., from another provider's useFactory, or from `onModuleInit`) would hit root-undefined. Controllers and other request handlers are safe.

**Status:** Still relevant. The defence is stronger than in `AbstractGrpcClient` (which deferred to `onModuleInit`): lazy getter is simpler, one less lifecycle concern.

### Pitfall 2: `getService()` Timing — OBSOLETE UNDER useFactory [CARRIED FORWARD FROM 999.7-RESEARCH Pitfall 3, STATUS REVISED]

**What was claimed:** `ClientGrpc.getService()` must run inside `onModuleInit`, not the constructor, because the gRPC connection isn't ready.

**Revised verdict — 2026-04-17:** FALSE under `defineGrpcClient`'s useFactory pattern.

**Evidence:** Verified via `node_modules/.pnpm/@nestjs+microservices@11.1.16_…/client/client-grpc.js:L24-50` (Target 1 above). `getService()` is a synchronous proto-lookup that returns an object with method proxies. The `ClientGrpcProxy` constructor itself loads proto and populates `grpcClients` synchronously. No `connect()` exists — gRPC does not have an async init step. Under useFactory, `grpc: ClientGrpc` is fully resolved (constructor done, proto loaded, clients map populated) before the build callback fires.

**Implication for phase 999.7.2:** Client constructor safely calls `this.raw = grpcClient.getService<T>(serviceName)`. No `OnModuleInit`, no `!`-assertion.

**Warning signs that it might still bite in edge cases:** if a future refactor changes from `useFactory` to `useClass` with `@Inject`, the resolution order could conceivably differ. Keep the runtime smoke in the pilot task (D-12) as a defensive check.

### Pitfall 3: ESLint Override Blocks Do Not Merge

**What goes wrong:** Creating a new override block for the same file glob (`'apps/**/clients/**/*.client.ts'`) in `.eslintrc.js` to add the composition rule leads to unexpected rule scoping — later overrides REPLACE earlier ones for matching files, not merge them.

**Why it happens:** ESLint override evaluation is order-dependent. Multiple overrides can match the same file, but each rule only applies from the LAST override whose `files:` pattern matches. If Override 6 has `@Injectable()` / `@Inject()` checks and a new Override 7 has only the `ClassDeclaration[superClass]` check, files matching both will lose the old checks.

**How to avoid:** Append the new `no-restricted-syntax` rule entry to the SAME array in Override 6. See Target 6 above for the copy-pasteable snippet.

**Warning signs:** After adding the guard, verify all three rules fire by attempting a local violation of each (e.g., add `@Injectable()` back to `auth.client.ts` and run `pnpm lint` — it should fail on @Injectable specifically, not silently pass).

### Pitfall 4: Consumer-Side Exports Must Survive the Build Callback Signature Change

**What goes wrong:** 8 `*-client.module.ts` files call `defineGrpcClient(opts, build)`. After this phase, `build` signature changes from `(grpcClient, cls, deadlineMs) => T` to `(grpcClient, caller) => T`. Files not updated → TypeScript build error.

**Why it happens:** `defineGrpcClient`'s second parameter is strongly typed via a generic inference. Existing call sites pass three-arg arrows. When the signature becomes two-arg, the old `cls` and `deadlineMs` positional args become type errors.

**How to avoid:** Task 1 changes `defineGrpcClient`'s signature AND simultaneously updates no caller (caller updates happen in Tasks 2-3). Therefore Task 1's atomic commit MUST be landed with a broken `pnpm typecheck` temporarily — which contradicts the project's atomic commit rule. Two options:
- **Option A (recommended):** Task 1 also updates all 8 consumer modules to the new two-arg shape AS PART of the same commit, but the client classes still extend AbstractGrpcClient (old class pattern). Tasks 2-3 then update each client class internally (composition + `this.raw`) without module-file changes. Requires Task 1 to be a larger atomic change.
- **Option B:** Task 1 changes the build callback to accept BOTH old (3-arg) and new (2-arg) shapes via TypeScript overloads, then Tasks 2-3 migrate each client, then a final cleanup task removes the overload. Adds churn.

**Recommendation:** Option A. Keep Task 1 slightly larger (foundation change + 8 module-file build-callback signature updates) so every atomic commit leaves the project buildable.

**Warning signs:** After Task 1, running `pnpm build` or `pnpm typecheck` reports failures in `apps/**/*-client.module.ts` → Task 1 wasn't complete.

### Pitfall 5: `export type { GrpcCaller }` vs `export { GrpcCaller }`

**What goes wrong:** If foundation barrel only exports the TYPE (`export type { GrpcCaller }`), client modules can reference the type but cannot `import { GrpcCaller }` to call `new GrpcCaller(...)` at runtime. This is fine — `defineGrpcClient` is the only runtime constructor call site.

**Why it matters:** Tests that want to inject a mock GrpcCaller don't need the real constructor — they construct a plain object matching the type (structural typing). Client classes only need the type for their constructor param annotation. `defineGrpcClient` lives in foundation, so it imports GrpcCaller internally as a value.

**How to avoid:** Export the type only from the barrel (`export type { GrpcCaller } from './grpc-caller'`). This prevents apps from importing and `new GrpcCaller(...)`-ing directly, which would bypass `defineGrpcClient` (encapsulation violation).

**Status:** Covered by D-09. No action needed beyond following D-09.

import type { ClientGrpc } from '@nestjs/microservices';
import { AuthProto, CommonProto } from '@email-platform/contracts';
import { SERVICE } from '@email-platform/config';
import type { GrpcCaller, CallOpts } from '@email-platform/foundation';

export class AuthClient {
  private readonly raw: AuthProto.AuthServiceClient;

  constructor(grpcClient: ClientGrpc, private readonly grpc: GrpcCaller) {
    this.raw = grpcClient.getService<AuthProto.AuthServiceClient>(
      SERVICE.auth.grpc.serviceName,
    );
  }

    return this.grpc.call('healthCheck', opts, (m) => this.raw.healthCheck(req, m));

    return this.grpc.call('login', opts, (m) => this.raw.login(req, m));

  }
  validateToken(req: AuthProto.ValidateRequest, opts?: CallOpts): Promise<AuthProto.UserContext> {
    return this.grpc.call('validateToken', opts, (m) => this.raw.validateToken(req, m));
  }
