## Summary

This audit examines the build/deploy/runtime pipeline that emerged from the 999.17.x cycle (DevSec gates + pnpm 9→11 migration + vulnerability remediation), with empirical anchors from two post-close regressions: Issue #1 (`.dockerignore` nested-glob, closed via `caaad40`) and Issue #2 (foundation tsc workspace-inject at Dockerfile Step 4a, deferred into this phase). The 5 prior infra fixes (`132138d` → `da70085`) — each a patch on the previous one — form the core archaeological subject of D9.

**Three high-confidence findings already provable from research:**

1. **`syncInjectedDepsAfterScripts` is the canonical pnpm 11 mechanism for built-dist sync** [CITED: pnpm.io/workspaces, pnpm.io/docker]. The current Dockerfile uses `rm -rf node_modules + pnpm install --frozen-lockfile` × 2 cycles (Step 4b + Step 4d) which is the OPPOSITE of the canonical pattern. The pnpm community itself discusses `injectWorkspacePackages` as a "foot gun" and the official mitigation is `syncInjectedDepsAfterScripts: [build]` in `pnpm-workspace.yaml`. This single setting may obsolete Steps 4b and 4d entirely. Issue #2 root cause is precisely this gap.

2. **Contract generation belongs at commit-time (CI), not Docker build-time × 6 parallel** [CITED: Buf docs, multi-source ecosystem consensus]. Current state: `pnpm --filter @email-platform/contracts run generate` runs inside Dockerfile Step 4a per app — × 6 parallel CI jobs perform identical proto compilation. `grpc-tools` on Alpine + musl + arm64 is known-fragile [CITED: grpc/grpc#21446, grpc/grpc#18338, ctaggart/froto#98], creating future portability risk for k8s arm64 nodes. Generated files (`packages/contracts/src/generated/*.ts`) are ALREADY tracked in git (per W5 D-W5-03), making the Docker re-generation redundant work that solely exposes the codebase to grpc-tools' multi-arch fragility.

3. **Health probe shape is k8s-ready already**, but Docker-compose healthcheck wires it incorrectly. `apps/*/src/infrastructure/bootstrap/health/health.controller.ts` exposes BOTH `/health/live` (deps-free) AND `/health/ready` (deps-checked) — exactly the k8s livenessProbe + readinessProbe contract [VERIFIED: file read]. However, `infra/docker-compose.yml` healthcheck uses `/health/live` for ALL 6 services [VERIFIED: file read] — which means even the Coolify deploy is exercising only the trivial path. UAT smoke runs `/health/ready`; healthcheck runs `/health/live`. This asymmetry is a low-cost finding.

**Primary recommendation:** Plan structure should mirror 999.1 (4-plan pattern: research synthesis → AUDIT.md catalog → SOLUTIONS.md variants → fix waves), but with audit-and-fix mode enabling BLOCKER/MAJOR fixes inline as separate plans rather than separate sub-phases. Expect 12-18 findings across 9 dims; expect 3-5 inline fix plans (Dockerfile refactor likely the largest).

#### K8s future-destination implications (D-13)

- **Image determinism for k8s pull-by-digest**: Current Dockerfile builds are NOT byte-deterministic — `rm -rf node_modules + pnpm install` produces different `node_modules` ordering on different BuildKit cache states. K8s deployments using `image: ghcr.io/...:latest` with `imagePullPolicy: Always` survive this; deployments pinning to digest do not.
- **Multi-arch readiness**: `.github/workflows/docker-build.yml:42-48` does NOT pass `platforms: linux/amd64,linux/arm64` to `docker/build-push-action@v7` [VERIFIED: file read]. DigitalOcean k8s nodes are often arm64. Without multi-arch builds, deployment to arm64 k8s nodes fails. This is a CI-side finding (not Dockerfile-side) but affects D8 readiness.
- **`grpc-tools` on Alpine + musl + arm64**: known-fragile [CITED: grpc/grpc#21446, grpc/grpc#18338]. Adding multi-arch build × 6 services × proto-gen will multiply this fragility. Strong argument for D-12 (commit-time generation).
- **Layer reuse across rebuilds**: Step 4b/4d's `rm -rf node_modules + reinstall` invalidates the Step 2 install-layer cache for every code change. A canonical refactor using `syncInjectedDepsAfterScripts` could restore install-layer cache reuse.

### Dockerfile multi-stage chain (current shape — subject of D1 audit)

```
Stage 1 (builder):
  Step 1: COPY manifests        → install-layer cache key
  Step 2: pnpm install          → install-layer (cache-mounted store)
  Step 3: COPY source           → source-layer
  Step 4a: build packages       → fills source dist/
  Step 4b: rm + reinstall       → refresh injected (PROBLEM: heavy operation)
  Step 4c: build app            → fills app dist/
  Step 4d: rm + reinstall       → refresh again (PROBLEM: redundant)
  Step 5: pnpm deploy --prod    → bundles to /prod/app
  Step 6: COPY proto            → /prod/app/proto

Stage 2 (runner):
  COPY --from=builder /prod/app
  bake build-info.json
  USER appuser
  CMD ["node", "dist/main.js"]
```

## Common Pitfalls (process + technical, anchored to UAT)

### Process pitfalls

1. **Misclassifying regression as pre-existing** (D-W5-04 anti-pattern) — what it looks like: SUMMARY claims "pre-existing baseline issue (NOT W5 regression)" without independent differential-test verification. **Detection**: any "pre-existing" claim must cite differential test on PRIOR-wave lockfile/state in clean BuildKit cache. **Mitigation**: D-09 differential-test mandate codified in 999.18.

2. **`/gsd:fast` scope creep** — what it looks like: initial fast fix succeeds; sanity check surfaces deeper issue; team continues fixing in same /gsd:fast budget instead of stopping. **Detection**: when fast-workflow sanity check produces error different from targeted one. **Mitigation**: STOP and redirect (per `gsd-flow-guard`).

3. **Trusting host node_modules state for Docker-build claims** — what it looks like: differential test runs on host; "host says it's fine" reports fool review. **Detection**: any Docker-build claim made without `docker compose build --no-cache --progress=plain` in clean BuildKit. **Mitigation**: always inspect inside container.

4. **HANDOFF.json singleton confusion** (per `.continue-here.md` Anti-Pattern 4) — naive overwrite drops parent carve-out context. **Mitigation**: `carve_out_chain[]` field preserves all levels.

5. **Patch-on-patch debugging** (5 prior infra fixes within 22 min) — symptom: each fix references the prior commit explicitly. **Detection**: 3+ same-day commits to same file with similar subject pattern. **Mitigation**: when reaching this density, STOP and reason from canonical pattern (D9 archaeological lens).

### Technical pitfalls

6. **Hard-link staleness with `injectWorkspacePackages: true`** — primary subject of D1 + D7. Hard links don't track source-to-dist relationship like symlinks do. Mitigation: `syncInjectedDepsAfterScripts: [build]`.

7. **`.dockerignore` nested-glob semantics** — Issue #1 root cause. Top-level `node_modules` does NOT match nested `packages/*/node_modules`. Mitigation: `**/` prefix (already applied via `caaad40`).

8. **grpc-tools on Alpine + musl + arm64** — known fragility class [CITED]. Multi-arch + Alpine + grpc-tools at build time = high failure surface.

9. **Step 6 PROTO_DIR duplication** — `Dockerfile:82 ENV PROTO_DIR=/app/proto` duplicates `.env.docker:46` (same value). Two sources of truth. Mitigation per F-05 of 999.1 audit precedent: remove Dockerfile ENV, env_file is single source.

10. **Generate-on-every-build amplification** — proto codegen × 6 services × N architectures × M CI runs = unnecessary work amplified by every dimension we add. Mitigation: D-12-V2 commit-time generation.

11. **Notifier in `/health/ready` aggregate** — gateway aggregates 5 upstreams via gRPC health indicator; notifier is RMQ-only with no gRPC server. How is `NOTIFIER_GRPC_HEALTH` indicator wired? Plan-phase needs to verify whether this is a stub or actually exercised.
