## Phase Boundary

Закрыть systemic gap фазы 999.17 («tooling installed, not proven» — D-6 meta-finding). Phase 999.17 структурно завершена (12/12 plans, 14/14 verifier truths), но операционная posture слабее заявленной цели — из 5 security gates 3 имели silent fail-open на момент сдачи. Per skill `feedback_phase_completeness` это systemic gap размером full-cycle sub-phase, не inline patch.

**Primary input:** `.planning/phases/999.17-devsecops-shift-left-security-tooling/deferred-items.md` D-2..D-6 — discuss/research/plan агенты ОБЯЗАНЫ прочитать его как основной источник scope.

**Scope (in):**

1. **D-2 Quality/Security/Hygiene decoupling** — split `package.json#scripts` на namespaces `quality:*` / `security:*` / `hygiene:*`, независимая `.husky/pre-{commit,push}` orchestration, Docker-граница для security tooling (Docker-pinned images), patterns для `--no-verify`-friendly delete-only push.
2. **D-3 Semgrep ruleset gap** — закрыть silent fail-open #3 (текущие 5 рулсетов / 79 правил пропускают `eval(input.code)` direct call).
3. **D-4 Semgrep non-determinism** — устранить расхождение exit code между pre-push hook (exit 2) и manual run (exit 0); `--metrics=off`, husky→pnpm→bash→docker env propagation, optional Docker image pre-pull.
4. **D-5 cosmetic counter bug** — fix `${#RULESET_FLAGS[@]} / 2` или restructure в `scripts/security/semgrep-diff.sh:40` (рапорт «10 ruleset(s)» при 5 configured).
5. **D-6 self-test harness** — positive+negative fixtures per security gate (gitleaks/semgrep/trivy fs/trivy config/pnpm-audit/build-trust); empirical proof что каждый gate ловит то что заявлено; execution-phase verifier должен прогонять fixtures, не только config grep.

**Architectural framing (locked from ROADMAP, не обсуждаемо):**

- **Quality** axis (ESLint/Prettier/tsc) — IDE-bound, native node_modules, fast feedback
- **Security** axis (gitleaks/semgrep/trivy/audit/build-trust) — fail-closed by design, Docker-pinned images, independent of quality
- **Hygiene** axis (env-parity и пр.) — третья ось, не смешивается с двумя другими
- **Layer 3 (CI)** — duplicates everything (`--no-verify` bypass-able locally, un-bypass-able server-side)

**Scope (out):**

- Изменения в существующих security tools без empirical evidence («не "поправить ради красоты"»)
- Расширение coverage за пределы 999.17 (новые scanners типа kube-bench/checkov, runtime security, DAST)
- Изменения в CI workflow (`.gitlab-ci-security.yml.example` остаётся template до отдельной DevOps-фазы)
- Local SCA-scanning of project deps (trivy fs остаётся CI-only per 999.17 D-06; sandbox subdir в этой фазе — proof-of-functionality, не SCA)
- Расширение custom Semgrep rules за пределы минимального стартового набора (отдельная follow-up фаза если найдём пробелы)

**Acceptance:**

- Все 6 security gates имеют positive+negative fixture
- Прогон fixtures завязан на execution-phase verifier через `pnpm security:verify`
- Pre-push chain decoupled — quality failure НЕ блокирует security gates
- Semgrep deterministic между pre-push и manual
- Bash counter показывает корректное число рулсетов
- CR-01/CR-02/D-3 fail-open закрыты с empirical proof
- Delete-only push (cleanup workflow) не требует `--no-verify`

## Implementation Decisions

### Self-test harness shape (D-6)

- **D-01:** Verify orchestrator интегрируется в pre-push через **Подход B (verify-if-changed)** — `pnpm security:verify-if-changed` срабатывает только если в diff vs `origin/main` есть изменения в `scripts/security/**`, `.gitleaks.toml`, `.semgrep.yml`, `.gitleaksignore`, `.semgrepignore`, `.trivyignore`. Идиома точно совпадает с уже существующими `audit-if-lock-changed.sh` и `trivy-config-if-changed.sh`. Ответ на «manual забывается через два дня» (отвергнуто) и «AI-only flow не универсален» (отвергнуто).
- **D-02:** **Double safety** — `gsd-verifier` (execution-phase verifier) дополнительно вызывает `pnpm security:verify` на phase-boundary как обязательную verification truth. Двойная защита: pre-push ловит drift на коммитах, verifier ловит если кто-то закоммитил с `--no-verify`.
- **D-03:** Verify mechanism per scanner: используем native test patterns где есть.
  - **Semgrep:** встроенный `semgrep test` framework с annotations `// ruleid: <rule>` (must match) и `// ok: <rule>` (must NOT match). Каноничный паттерн.
  - **Gitleaks/Trivy fs/Trivy config/pnpm audit:** thin bash wrappers (~10 строк каждый) которые инвертируют exit code на negative fixtures (positive expects exit 0, negative expects non-zero).
  - **Build-trust gate:** двухпасс `pnpm install` на подготовленных fixture `package.json` файлах (один с only-allowed builds, второй с unrecognized postinstall).
- **D-04:** Fixtures расположены в `scripts/security/fixtures/{gate}/{positive|negative}/`. Ровно 6 поддиректорий по числу gate'ов: `gitleaks/`, `semgrep/`, `trivy-config/`, `trivy-fs/`, `audit/`, `build-trust/`. В каждой — `positive/` (clean code, scanner должен пропустить) и `negative/` (намеренная угроза, scanner должен поймать).
- **D-05:** **Trivy fs vuln-sandbox subdir, verify-only** — `scripts/security/fixtures/trivy-fs/negative/package.json` с pinned known-CVE (например `lodash@4.17.20` или `axios@0.21.0`). `trivy fs` вызывается ТОЛЬКО в verify-режиме на этот subdir через `docker run`, НЕ на репо. CVE feed (~1GB) живёт в Docker layer cache, не в репозитории. **999.17 D-06 (no local SCA project deps) остаётся в силе** — sandbox = proof-of-functionality сканера в другом измерении, не SCA проекта.
- **D-06:** `apps/auth/src/test/semgrep-fixture.ts` (созданный при manual smoke 999.17 — именно он выявил D-3) переносится через `git mv` → `scripts/security/fixtures/semgrep/negative/`. Удаляется директория `apps/auth/src/test/` (конфликт с PROJECT.md «no tests» constraint). История файла сохраняется через `git mv`. Файл выходит из `apps/auth/tsconfig.json` scope — typecheck перестаёт видеть `eval(input.code)`.
- **D-07:** Production scan игнорирует fixture-файлы через **path-block в `.ignore`-файлах**: одна запись `scripts/security/fixtures/**` в каждом из `.gitleaksignore`, `.semgrepignore`, `.trivyignore`. Verify mode обходит allowlist двумя способами:
  - Явный path argument: `gitleaks dir scripts/security/fixtures/gitleaks/negative/`
  - Флаг отключения: `--no-gitleaks-ignore` / `--disable-nosem` где scanner поддерживает.

### Semgrep coverage strategy (D-3)

- **D-08:** **Добавляем `p/security-audit` ruleset** к существующим 5 (`p/typescript`, `p/javascript`, `p/owasp-top-10`, `p/nodejs`, `p/r2c-security-audit`). `p/security-audit` — broader registry-ruleset, покрывает eval/Function/dangerous sinks, закрывает D-3 исходный кейс (`eval(input.code)`).
- **D-09:** **Добавляем 1-2 custom Email-Platform-specific rules** в минимальном стартовом наборе:
  - **Rule 1:** Raw `process.env.<X>` access вне `packages/config/` — нарушает 12-Factor + проектное правило «No environment branching in app code» (см. `.agents/skills/twelve-factor/SKILL.md`)
  - **Rule 2:** gRPC controller без proper exception filter / auth context propagation (см. `.agents/skills/nestjs-hexagonal-mapping/SKILL.md`)
  - Расширение custom rules в **последующих фазах** при выявлении пробелов — НЕ scope creep в 999.17.1.
- **D-10:** Custom rules живут в `.semgrep/rules/{rule-name}.yml` — одно правило на файл (стандартный Semgrep convention). Каждое правило имеет описание, severity, examples. semgrep-diff.sh парсит `.semgrep.yml` для registry rulesets, custom rules добавляются отдельным `--config` flag (плюс правило для `.semgrep/rules/` директории).
- **D-11:** **Baseline-mark + diff-only rollout** для новых правил. Используем уже существующий `--baseline-commit origin/main` в `semgrep-diff.sh` — новые правила автоматически игнорируют существующие findings, блокируют только НОВЫЕ в diff. Cleanup legacy = отдельный follow-up todo, НЕ scope 999.17.1. Zero pre-push disruption на момент включения.
- **D-12:** **`--config auto` остаётся отвергнутым** (per 999.17 D-13) — требует Semgrep cloud account, не воспроизводим, может меняться без git diff. Explicit composition сохраняется как принцип.

### Quality/Security/Hygiene namespace split (D-2)

- **D-13:** **Atomic-per-tool + meta granularity** в `package.json#scripts`:
  - **Quality:** `quality:lint` (eslint), `quality:typecheck` (turbo run typecheck), `quality:format` (prettier), `quality:check` (= все три параллельно через wait-pids или sequential)
  - **Security:** `security:secrets-staged` (gitleaks staged-only), `security:semgrep-diff` (existing), `security:audit-if-changed` (rename of audit-if-lock-changed), `security:trivy-config-if-changed` (existing), `security:scan` (= meta production scan: secrets-full + semgrep-diff + audit-if-changed + trivy-config-if-changed), `security:verify` (= verify все 6 fixtures), `security:verify-if-changed` (= verify только если security configs изменились)
  - **Hygiene:** `hygiene:env-parity` (rename of security:env-parity), `hygiene:check` (= env-parity сейчас единственный inhabitant)
- **D-14:** Husky hooks orchestration:
  - **`.husky/pre-commit`** (бюджет <5s): `pnpm run quality:staged && pnpm run security:secrets-staged` — где `quality:staged` это lint-staged (lint+format на staged-файлах). Quality и Security обе оси на pre-commit, hygiene на pre-push.
  - **`.husky/pre-push`** (бюджет <30s): `bash scripts/security/pre-push-orchestrator.sh` — этот скрипт вызывает три оси (`quality:typecheck`, `hygiene:check`, `security:scan`, `security:verify-if-changed`) **параллельно с collect-all** (без fail-fast), агрегирует exit codes.
- **D-15:** **Hygiene содержит только env-parity сейчас**. Третья ось имеет 1 inhabitant — `check-arch` остаётся manual `pnpm run check-arch`, не переносится в `hygiene:*`. Будущие hygiene-checks ложатся в этот namespace по мере выявления.
- **D-16:** **Параллельный run с collect-all** в pre-push orchestrator. Все три оси отрабатывают независимо — quality typecheck failure НЕ блокирует security scan. Это **ключевое решение D-2**: устраняет «typecheck в apps/auth блокирует semgrep/audit/trivy». Реализация: `pnpm` background processes + `wait` на все PIDs + bash array exit codes + final summary с per-axis статусом.
- **D-17:** **Существующий `security:pre-push` chain ликвидируется** — это компромиссный chain из 999.17 (typecheck+env-parity+semgrep-diff+audit+trivy-config через `&&`). Заменяется на новый `pre-push-orchestrator.sh` через 999.17.1.
- **D-18:** **Существующий `security:pre-commit` рефакторится** — текущий `lint-staged && pnpm run security:secrets-staged` становится двухзначным: `pnpm run quality:staged` (lint-staged переименование, pure quality) + `pnpm run security:secrets-staged` (gitleaks). Husky pre-commit вызывает оба последовательно (на pre-commit fail-fast разумен, бюджет <5s, нечего параллелить).

### Delete-only push pattern (D-2)

- **D-19:** **Auto-detect 40-zero SHA в `.husky/pre-push`**: в начале hook читаем stdin (формат git: `<local-ref> <local-sha> <remote-ref> <remote-sha>` per ref). Если ВСЕ ref-lines имеют `local-sha = 0000000000000000000000000000000000000000` (40 нулей) — `exit 0` без вызова orchestrator. Documenter в DEVOPS-HANDOFF.md / CONTRIBUTING.md что cleanup branches не требуют `--no-verify`.
- **D-20:** **Mixed push (some deletes + some commits) → conservative full chain**. Если хотя бы ОДНА ref-line имеет non-zero local-sha — вызываем orchestrator на весь push. Не пытаемся per-ref selective skip — слишком хрупко, никто так не делает в практике, edge-case ROI слишком низкий.

### Claude's Discretion (research/plan-phase resolves)

- **D-4 Semgrep non-determinism root cause investigation** — research-phase должен изучить:
  - Semgrep `--metrics=off` поведение (registry phone-home unstable в некоторых network contexts)
  - Husky → pnpm → bash → docker env-var propagation chain
  - Docker daemon cold-start race на image pull
  - Optional pre-pull в setup hook (Renaissance: `pnpm prepare` уже зовёт husky install — можно добавить docker-pull-images.sh)
  - Минимальный fix: `--metrics=off`. Расширенный: pre-pull + env audit. Plan-phase решит depth.
- **D-5 Cosmetic counter bug** — `scripts/security/semgrep-diff.sh:40` reports `${#RULESET_FLAGS[@]}` (counts both `--config` and ID elements). Trivial fix: `${#RULESET_FLAGS[@]} / 2` или restructure в parallel array только для IDs (`RULESET_IDS=()`). Plan-phase trivial 1-line fix.
- Точные Docker image теги для verify-режима (semgrep, trivy fs, gitleaks при необходимости — production scan уже использует pinned tags из 999.17 Plan 04+) — plan-phase финализирует, сверяет с current latest.
- Структура `pre-push-orchestrator.sh` (parallel via `&` + `wait` vs `xargs -P` vs `parallel` GNU tool) — plan-phase решает на базе runtime smoke testing.
- Точное содержимое 1-2 custom Semgrep rules (pattern syntax, severity, message text) — plan-phase finalize по официальной [Semgrep rule writing docs](https://semgrep.dev/docs/writing-rules/overview).
- Whitelist стратегия для `Rule 1` (raw process.env outside packages/config) — за исключением `packages/config/src/**` нужны другие исключения (тесты, scripts) — plan-phase разрулит после baseline-scan.

<specifics>
## Specific Ideas

- **«Manual verification забывается через 2 дня»** — drove rejection of standalone-script approach. AI-only verification rejected as not-universal. Resulting Approach B (verify-if-changed) trigger автоматически на изменения security configs — закрывает forgetting + не зависит от AI flow.
- **«Conflict с 999.17 D-06 на самом деле иллюзорный»** — vuln-sandbox subdir работает в другом измерении (proof of scanner functionality), не SCA проекта. 999.17 D-06 («no local SCA on project deps») остаётся в силе. Этот разбор должен попасть в plan/research как объяснение почему trivy fs локально OK именно для sandbox.
- **«Quality fail НЕ должен блокировать security»** — **ключевая мотивация всей фазы D-2**. Воспроизведено 2026-04-29: pre-existing TS2742 в любом сервисе блокировал semgrep/pnpm-audit/trivy локально. Параллельный run с collect-all решает напрямую.
- **Approach B vs always-verify** — verify-if-changed выигрывает потому что: (1) использует уже established паттерн в проекте (`if-lock-changed`, `if-changed`), (2) не штрафует обычный workflow (бизнес-код, доки → 0 overhead), (3) ловит drift на ТОМ push где он возникает (изменили `.semgrep.yml` → verify запускается).
- **«Custom rules — минимальный старт, расширение в follow-up phases»** — отвергаем «kitchen sink» подход. 1-2 правила доказывают паттерн, дают immediate value, не создают maintenance debt. При необходимости 999.17.2 / 999.17.3 расширят.
- **«Semgrep test framework — каноничный паттерн»** — не изобретаем велосипед для Semgrep; используем встроенный `// ruleid:` / `// ok:` annotation system. Только для gitleaks/trivy/audit (которые не имеют test framework) пишем bash wrappers.
