````markdown
## Delete-Only Push Pattern (D-19)

You DO NOT need `--no-verify` for branch deletions:

```bash
# Cleanup remote branch — pre-push hook auto-skips:
git push origin :stale-feature-branch
# Output: [INFO] Delete-only push detected — skipping pre-push checks (D-19).
```
````

Mixed pushes (some deletes + some commits) run the full chain — by design (D-20). Per-ref selective skip was rejected as fragile; the conservative full-chain approach matches industry practice.

## --no-verify Policy

Pre-push is a LOCAL fast-feedback layer. CI is the un-bypassable enforcement layer (per 999.17 D-04 + 999.17.1 architectural framing).

**OK to use --no-verify:**

- Investigation pushes to a feature branch you control
- Time-sensitive fixes where you've manually verified the relevant gates
- Cleanup pushes (use delete-only auto-detection instead — see above)

**NOT OK:**

- Pushing to main or release branches with --no-verify
- Routine workflow — if you find yourself reaching for --no-verify daily, the pre-push budget is too tight and we should adjust the orchestrator

CI runs the same gates server-side. Bypassing pre-push locally does NOT bypass them in CI.

## Trivy CVE Feed Cache (RESEARCH §Pitfall 4)

`scripts/security/verify-trivy-fs.sh` mounts `$HOME/.cache/trivy` to avoid the ~1GB CVE feed redownload per run.

One-time setup per dev workstation:

```bash
mkdir -p "$HOME/.cache/trivy"
docker pull aquasec/trivy:0.50.4
# Pre-warm the CVE cache (1-3 min depending on bandwidth):
docker run --rm -v "$HOME/.cache/trivy:/root/.cache/trivy" aquasec/trivy:0.50.4 fs --download-db-only
```

After that, `pnpm run security:verify` reuses the cache — no further downloads unless trivy db is force-refreshed.
