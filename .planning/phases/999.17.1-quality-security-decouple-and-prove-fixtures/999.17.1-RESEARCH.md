## Summary

Phase 999.17 shipped 5 security gates (gitleaks / semgrep / trivy config / pnpm audit / build-trust) but only 2 had been empirically proven catch-what-they-claim at delivery (CR-01 build-trust, CR-02 gitleaks — closed in Plans 11/12). The remaining 3 gates (semgrep coverage, trivy fs verify, pnpm audit verify) plus the cross-cutting pre-push chain ordering and a cosmetic counter bug constitute D-2..D-6 in `deferred-items.md`. This phase closes the systemic gap.

The fix decomposes into five orthogonal workstreams: **(D-2)** decouple `package.json#scripts` into `quality:* / security:* / hygiene:*` namespaces and replace the `&&`-chain `security:pre-push` with a parallel collect-all bash orchestrator so quality failures stop blocking security gates; **(D-3)** add the broader `p/security-audit` ruleset plus 2 minimal custom Semgrep rules (raw `process.env` outside config layer, gRPC controllers without auth/error filters) to close the eval-injection silent fail-open; **(D-4)** add `--metrics=off` and investigate husky→pnpm→bash→docker env propagation to fix Semgrep nondeterminism; **(D-5)** trivial 1-line counter fix; **(D-6)** create `scripts/security/fixtures/{gate}/{positive,negative}/` with 6 sub-trees and a `verify.sh` orchestrator wired into pre-push via verify-if-changed and into the gsd-verifier as a phase-boundary truth.

The Semgrep `semgrep test` subcommand is the canonical verify mechanism for the SAST gate (built-in, with `// ruleid:` / `// ok:` annotations). All other gates verify via thin bash wrappers that invert exit-code expectations on negative fixtures. Trivy fs `--exit-code 1 --severity HIGH,CRITICAL <subdir>` semantics are confirmed and scope cleanly to a single subdirectory — preserving the 999.17 D-06 invariant (no SCA on project deps).

**Primary recommendation:** Build `scripts/security/verify.sh` as a 6-row table-driven dispatcher (no switch/case — Record-style associative array per `branching-patterns` skill) that invokes per-gate verify scripts; mirror this dispatch pattern in `scripts/security/pre-push-orchestrator.sh` for the parallel collect-all flow; keep all docker invocations pinned to the same major.minor tags already in use (gitleaks v8.30.1, semgrep 1.50, trivy 0.50.4); install custom Semgrep rules under `.semgrep/rules/` with one rule per file.

### Pattern 1: Bash dispatch table (replaces switch/case per `branching-patterns` skill)

**What:** Map gate name → verify command via associative array, iterate.
**When to use:** Any time the orchestrator needs to invoke N gates with the same shape.

```bash
# Source: convention from .agents/skills/branching-patterns/SKILL.md (Pattern 1: Record<Key, Handler>)
# Bash equivalent of TypeScript Record<Key, Handler>.
declare -A GATES=(
  [gitleaks]="bash scripts/security/verify-gitleaks.sh"
  [semgrep]="bash scripts/security/verify-semgrep.sh"
  [trivy-config]="bash scripts/security/verify-trivy-config.sh"
  [trivy-fs]="bash scripts/security/verify-trivy-fs.sh"
  [audit]="bash scripts/security/verify-audit.sh"
  [build-trust]="bash scripts/security/verify-build-trust.sh"
)

declare -A RESULTS=()
for gate in "${!GATES[@]}"; do
  if ${GATES[$gate]}; then
    RESULTS[$gate]="OK"
  else
    RESULTS[$gate]="FAIL($?)"
  fi
done

# Print summary table; exit non-zero if any gate failed.
```

### Pattern 2: Parallel collect-all with per-PID exit array

**What:** Launch N background jobs, capture PIDs, wait on each, collect exit codes.
**When to use:** Pre-push orchestrator — quality / security / hygiene must run independently.

```bash
# Source: bash idiom (klotzandrew.com/blog/parallel-bash-with-wait/, Greg's wiki ProcessManagement)
# CRITICAL: with `set -e`, `wait <pid>` does NOT trigger immediate exit on non-zero —
# it returns the child's exit status as the wait builtin's status. We capture it explicitly.

declare -A AXES=(
  [quality]="pnpm run quality:check"
  [security]="bash -c 'pnpm run security:scan && pnpm run security:verify-if-changed'"
  [hygiene]="pnpm run hygiene:check"
)

declare -A PIDS=()
declare -A EXITS=()

for axis in "${!AXES[@]}"; do
  ${AXES[$axis]} > "logs/${axis}.log" 2>&1 &
  PIDS[$axis]=$!
done

for axis in "${!PIDS[@]}"; do
  if wait "${PIDS[$axis]}"; then
    EXITS[$axis]=0
  else
    EXITS[$axis]=$?
  fi
done

# Compute final exit: 0 only if all axes are 0; otherwise non-zero.
final=0
for axis in "${!EXITS[@]}"; do
  status=${EXITS[$axis]}
  if [ "$status" -ne 0 ]; then
    final=1
    echo "[FAIL] $axis exit=$status — see logs/${axis}.log"
  else
    echo "[ OK ] $axis"
  fi
done
exit $final
```

**Note on `set -euo pipefail`:** `wait` does NOT cause early exit under `set -e` because the docs explicitly call it out as a builtin whose exit status is reportable (Greg's wiki). The pattern above is correct. However: backgrounded subshells with `set -e` inherit the option but errors INSIDE them propagate to their own exit status, which is what `wait` then reports. Verify this empirically during plan-phase smoke.

### Pattern 4: Pre-push delete detection from stdin

```bash
# Source: git-scm.com/docs/githooks#_pre_push
# Per-line format: "<local-ref> <local-sha> <remote-ref> <remote-sha>"
# For deletion: local-ref is "(delete)" AND local-sha is 40 zeros.

ZEROS="0000000000000000000000000000000000000000"
ALL_DELETES=true

# git ALWAYS sends at least one line on stdin to pre-push.
while read -r local_ref local_sha remote_ref remote_sha; do
  if [ "$local_sha" != "$ZEROS" ]; then
    ALL_DELETES=false
    break  # mixed push → conservative full chain
  fi
done

if [ "$ALL_DELETES" = "true" ]; then
  echo "[INFO] Delete-only push detected — skipping pre-push checks."
  exit 0
fi

# else fall through to orchestrator
```

**CRITICAL husky stdin caveat:** [VERIFIED: github.com/typicode/husky/issues/1591] husky v9 sources `~/.config/husky/init.sh` BEFORE the hook runs. If a user has init.sh that consumes stdin (rare but possible), the hook may receive an empty stdin. Mitigation: orchestrator MUST handle `read` returning EOF gracefully (loop body simply doesn't execute → `ALL_DELETES` stays `true` → safe early-exit). This means: no input on stdin == treated as "all deletes" == hook skips. Slight false-skip risk but acceptable; CI is the enforcement layer (D-04 from 999.17).

### Anti-Patterns to Avoid

- **Hardcoded scanner image tags inside multiple scripts.** Centralize tags in one file (`scripts/security/_versions.sh` sourced by all verify-\*.sh). Keeps version bumps to a single edit.
- **Bash `if/elif/elif` over gate names.** Forbidden by `branching-patterns` skill. Use `declare -A` dispatch.
- **Inlining `docker run` invocations.** Use single shared variable `DOCKER_RUN_BASE='docker run --rm -v $(pwd):/repo -w /repo'` per script-section.
- **Trusting `set -e` to fail-fast inside backgrounded subshells in collect-all mode.** Explicitly `wait $pid; status=$?` per child.
- **Using `git diff --name-only ... | grep ...` instead of `git diff --quiet -- <pathspec>`.** The `--quiet` form is the project idiom (used by `audit-if-lock-changed.sh`).
- **Using `AKIA + IOSFODNN7EXAMPLE` as the gitleaks negative fixture's fake key.** It's hardcoded in gitleaks default allowlist → false negative. Use `AKIA + QYLPMN5HEXAMPLE2` (or any 20-char base32-uppercase NOT in the canonical AWS docs example list). [VERIFIED: 999.17-12-SUMMARY.md key-decisions]
- **Calling `semgrep` against `--config p/...` rulesets without `--metrics=off`.** Semgrep phones home + fetches rules from registry; metrics path can timeout in network-constrained contexts (D-04 root cause candidate). Always pass `--metrics=off`.
- **Mounting `node_modules/` into trivy fs verify.** The trivy fs verify must scope to `scripts/security/fixtures/trivy-fs/negative/` ONLY — passing repo root would scan project deps and break 999.17 D-06.

## Common Pitfalls

### Pitfall 1: gitleaks default allowlist hardcodes `AKIA + IOSFODNN7EXAMPLE`

**What goes wrong:** Negative fixture uses the canonical AWS-docs example key → gitleaks ignores it → fixture appears to "pass" → silent fail-open (the very bug 999.17 was supposed to prevent).
**Why it happens:** Gitleaks ships with a community-audited list of fake/example AWS keys to avoid false positives in tutorials. `AKIA + IOSFODNN7EXAMPLE` is one of those.
**How to avoid:** Use `AKIA + QYLPMN5HEXAMPLE2` (or generate a 20-char A-Z2-7 string and verify it's not in the gitleaks default allowlist).
**Warning signs:** "Why does my obvious fake key not trigger the rule?"
**Source:** [VERIFIED: .planning/phases/999.17.../999.17-12-SUMMARY.md key-decisions]

### Pitfall 2: Semgrep `--config p/<id>` requires network even with `--metrics=off`

**What goes wrong:** `--metrics=off` disables phone-home but does NOT disable rule download from Semgrep registry. `p/security-audit`/`p/typescript`/etc. are fetched fresh each run unless cached.
**Why it happens:** Registry rule fetches are separate from metrics; only fully-local `--config <file.yml>` is offline. [VERIFIED: semgrep.dev/docs/metrics — "Semgrep does not enable metrics when running with only local configuration files or command-line search patterns"]
**How to avoid:** (a) Always pass `--metrics=off`; (b) optionally `docker pull` the semgrep image at install time to eliminate cold-start; (c) document in DEVOPS-HANDOFF.md that semgrep registry must be reachable from dev machines for pre-push to work; (d) in `verify-semgrep.sh`, prefer `--config .semgrep/rules/` (local) for custom-rule verify and accept registry fetch only for the coverage-fixture path.
**Warning signs:** Inconsistent exit codes between local and CI; D-4 reproduction.

### Pitfall 3: Husky v9 init.sh consumes stdin

**What goes wrong:** Hook reads empty stdin → delete-detection logic incorrectly treats it as "all deletes" → orchestrator skips → push proceeds without security checks.
**Why it happens:** Husky sources `~/.config/husky/init.sh` BEFORE the hook. If init.sh reads stdin (e.g., to prompt user), the hook gets nothing.
**How to avoid:** Treat empty-stdin case explicitly. The Pattern 4 code defaults `ALL_DELETES=true` — but if no lines arrive at all, that's actually NOT proven to be a delete. Safer: track `LINE_COUNT` and require `LINE_COUNT > 0` before allowing skip.
**Warning signs:** "Hook silently skipped on a real push" — observable via husky `~$ HUSKY_DEBUG=1`.
**Source:** [VERIFIED: github.com/typicode/husky/issues/1591]

```bash
# CORRECTED Pattern 4 — explicit empty-stdin handling
ZEROS="0000000000000000000000000000000000000000"
LINE_COUNT=0
ALL_DELETES=true
while read -r local_ref local_sha remote_ref remote_sha; do
  LINE_COUNT=$((LINE_COUNT + 1))
  if [ "$local_sha" != "$ZEROS" ]; then ALL_DELETES=false; fi
done

# If no input arrived — fall through to orchestrator (conservative: run checks)
if [ "$LINE_COUNT" -gt 0 ] && [ "$ALL_DELETES" = "true" ]; then
  exit 0  # genuine all-delete push
fi
# else: fall through to orchestrator
```

### Pitfall 4: Trivy fs CVE feed (~1GB) downloaded every container start

**What goes wrong:** First `trivy fs` invocation pulls a 1GB CVE feed; subsequent in same container session reuse it. But `docker run --rm` discards the layer state — so EVERY verify run could pull 1GB.
**Why it happens:** Default `--cache-dir` lives inside the container, evicted with `--rm`.
**How to avoid:** Mount a host cache dir: `docker run --rm -v "$(pwd):/repo" -v "$HOME/.cache/trivy:/root/.cache/trivy" aquasec/trivy:0.50.4 ...`. The verify scripts MUST include this volume mount. Document in DEVOPS-HANDOFF.md.
**Warning signs:** "Pre-push takes 2+ minutes" / "Network bound, slow on CI."
**Source:** [CITED: trivy.dev/latest/docs — `--cache-dir` flag documentation]

### Pitfall 5: `set -euo pipefail` interaction with backgrounded jobs

**What goes wrong:** Author writes `set -e`, expects backgrounded job failure to abort orchestrator. Doesn't happen — `wait` returns the child's status WITHOUT triggering ERR trap.
**Why it happens:** Bash `set -e` does NOT propagate from backgrounded subshells until `wait` is called, AND `wait`'s exit status is reportable (a builtin like `test`).
**How to avoid:** Always `wait <pid>` followed by `status=$?` capture; never `wait` in a position whose exit code is unchecked.
**Warning signs:** Orchestrator reports "all OK" but logs show one axis crashed.
**Source:** [CITED: mywiki.wooledge.org/ProcessManagement — wait builtin semantics]

### Pitfall 6: `apps/auth/src/test/semgrep-fixture.ts` is not in git

**What goes wrong:** `git mv` planned in CONTEXT.md D-06 will fail — the file was never committed (it was created during 999.17 manual smoke and ignored).
**Why it happens:** The smoke tester wrote it locally to reproduce D-3, then never staged/committed.
**How to avoid:** Plan-phase task: (a) check `git ls-files apps/auth/src/test/semgrep-fixture.ts` — if empty, the file is untracked or absent; (b) write the fixture content fresh into `scripts/security/fixtures/semgrep/negative/eval-injection.ts`; (c) `git add` directly. Skip `git mv`. Empirically verified via `git log --all --oneline -- apps/auth/src/test/semgrep-fixture.ts` (returns empty in current branch).
**Warning signs:** "fatal: bad source, source=apps/auth/src/test/semgrep-fixture.ts, destination=…"
**Source:** [VERIFIED: git log query during research]

### Pitfall 7: Counter bug fix shape — `$/2` is fragile

**What goes wrong:** Plan picks `${#RULESET_FLAGS[@]} / 2` for D-5 fix. Future scanner-option additions (e.g., `--severity HIGH` per ruleset) break the divisor.
**Why it happens:** The math depends on every flag being exactly `--config <id>` (2 elements per ruleset). Adding `--exclude-rule` or similar breaks ratio.
**How to avoid:** Use parallel array: keep `RULESET_FLAGS=()` for invocation, also keep `RULESET_IDS=()` populated in the same loop. Print `${#RULESET_IDS[@]}` for the counter.
**Warning signs:** Future-engineer puzzled why the count is wrong after adding any new per-ruleset flag.

### Pitfall 8: `p/security-audit` overlap with `p/r2c-security-audit`

**What goes wrong:** Plan adds `p/security-audit` next to existing `p/r2c-security-audit` — same finding fires twice.
**Why it happens:** Both are broad security rule packs. Naming is similar but they're distinct packs (different curation).
**How to avoid:** [VERIFIED: search results indicate `p/security-audit` is the broader moderate-confidence catch-more set, while `p/r2c-security-audit` is the in-depth-but-curated set.] Acceptable risk: minor duplication appears as separate finding entries; both rules fire in same file → user sees 2 findings; baseline-mark D-11 captures both as legacy. Plan-phase: smoke `semgrep test` with both rulesets active and assess noise. If duplicates dominate signal, drop `p/r2c-security-audit`.
**Warning signs:** Pre-push noise increases significantly after adding the new ruleset.

### Pitfall 9: `--config auto` accidentally gets re-introduced

**What goes wrong:** Engineer reads "Semgrep recommends `--config auto` as default" from upstream blog → patches semgrep-diff.sh.
**Why it happens:** `auto` is the documented Semgrep onboarding default but requires login + sends rule list per-call.
**How to avoid:** Add a `# rejected: --config auto` comment in `.semgrep.yml` AND in `semgrep-diff.sh` referencing 999.17 D-12.
**Source:** [CITED: 999.17 D-13 (locked decision) carried forward as 999.17.1 D-12]

## Open Questions

1. **Should `security:scan` (production meta) include `security:secrets-full` (`gitleaks dir <repo>`) or only `security:secrets-staged`?**
   - What we know: Pre-commit uses `gitleaks --staged`; pre-push currently has no full-repo secret scan.
   - What's unclear: Adding `gitleaks dir .` to `security:scan` adds ~3-5s per pre-push but covers the case "engineer commits secret via `--no-verify` then pushes."
   - Recommendation: Plan-phase decision — the symmetric security argument favors inclusion; performance budget is fine.

2. **For the `verify-semgrep.sh` script: invoke `semgrep test` once per rule subdir, or once with `--config .semgrep/rules/`?**
   - What we know: `semgrep test` resolves test files by name-matching to rule files. Single invocation should auto-discover.
   - What's unclear: Whether registry-ruleset coverage fixture (negative/eval-injection.ts) needs a separate `semgrep scan --error` step alongside `semgrep test`.
   - Recommendation: Two-step verify — `semgrep test --config .semgrep/rules/` for custom rules + `semgrep scan --config p/security-audit --error <fixture>` for ruleset coverage. Both wrapped in one `verify-semgrep.sh`.

3. **D-09 Rule 1 whitelist: which paths beyond `packages/config/` are exempt?**
   - What we know: `packages/foundation/src/external/config/load-config.ts` reads `process.env` (the canonical loader).
   - What's unclear: Test files (none in scope per PROJECT.md), scripts/ directory, possibly mocks.
   - Recommendation: Plan-phase runs baseline-scan with draft rule, lists unexpected hits, decides whitelist. Initial whitelist: `packages/config/**`, `packages/foundation/src/external/config/**`, `scripts/**`, `**/*.test.ts`.

4. **Docker image pre-pull in `pnpm prepare` (extending husky-install)?**
   - What we know: First `docker pull` per scanner is ~30-200s; subsequent runs are cached.
   - What's unclear: Whether D-4 non-determinism actually traces to cold-pull race vs `--metrics=off` alone.
   - Recommendation: Plan-phase tries `--metrics=off` first; if D-4 reproduces, add a `scripts/security/setup-docker-images.sh` invoked from `pnpm prepare` post-husky.

5. **Where should the gsd-verifier verification truth wire in?**
   - What we know: 999.17 had 14 verifier truths — phase-specific; gsd verifier reads phase context.
   - What's unclear: Exact mechanism — is "pnpm security:verify exits 0" added to a `.planning/phases/.../999.17.1-VERIFICATION.md` truth list, or to the phase's checker config?
   - Recommendation: Plan-phase reads `.agents/skills/gsd-flow-guard/SKILL.md` and prior phase VERIFICATION.md files for the wiring pattern.

6. **Counter-bug fix shape (D-5): `/2` vs parallel array?**
   - Recommendation: parallel `RULESET_IDS=()` array — defends against future flag additions (Pitfall 7).
