## Decisions Made

1. **Kustomize substitution через CI (не env-var в YAML).** Kustomize **не** resolves env vars в `kustomization.yaml`. Canonical pattern (per kubectl docs) — invoke `kustomize edit set image NAME=NEW_NAME:NEW_TAG` в CI shell перед `kubectl apply -k`. Это сохраняет YAML декларативным и переносимым; substitution атомарно происходит в CI workspace.
2. **Tags: `dev-placeholder` / `prod-placeholder` (не `latest`).** Fail-loud canary: если CI substitution не выполнен (например, manual `kubectl apply -k` без preceding `kustomize edit set image`), manifest ссылается на несуществующий тег → быстрый ImagePullBackOff с однозначным error message. `:latest` создаёт ambiguity (либо тянет stale image, либо deployment-wedge при missing tag).
3. **kustomize CLI install через curl+tar в before_script.** `bitnami/kubectl:1.30` не bundles standalone kustomize CLI. Опции рассмотрены:
   - **Option A (chosen):** one-shot install через curl+tar (v5.4.3 pinned, deterministic; idempotent через `command -v` guard).
   - **Option B:** switch на custom Docker image с pre-bundled kustomize — overkill для текущей фазы, deferred к 999.18.4 hardening.
   - **Option C:** `kubectl kustomize` (built-in since 1.14) — но `kustomize edit set image` (substitution mutation) экспонируется только через standalone kustomize CLI, не через `kubectl kustomize`. Therefore curl-install — minimum path.
4. **Сохранить `verify:k8s-rollout` в package.json.** Script `"verify:k8s-rollout": "bash scripts/verify-k8s-rollout.sh"` остаётся для local development (developer-mode `pnpm verify:k8s-rollout` после ручного `kubectl apply` против локального cluster). CI просто вызывает skрипт напрямую — zero overlap, zero conflict.
5. **`variables:` блок job-level vs `variables:` global.** Global `variables:` (top-of-file) применяется ко всем jobs — KUBE_NAMESPACE специфичен для каждого env (dev/prod), потому job-level scope корректен. CI vendor-canonical pattern.
