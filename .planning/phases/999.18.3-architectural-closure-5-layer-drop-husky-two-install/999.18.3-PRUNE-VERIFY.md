# pnpm prune --prod TTY Fix Forensic Verification

## 1. Verdict (TL;DR)

**Q1 — `ENV CI=true` canonical?** **ДА, это canonical wired-in mechanism, не костыль.** Проверено в pnpm source `installing/deps-installer/src/install/validateModules.ts` line 149-154 + wiring `installing/deps-installer/src/install/index.ts` line 317: `confirmModulesPurge: opts.confirmModulesPurge && !opts.ci`. Error hint **сам прямо называет** оба canonical fix-а: «set the CI environment variable to "true", **or** set "confirmModulesPurge" to "false"» [VERIFIED: pnpm source via gh API, commit 2ebd45a]. Эквивалентные пути; `CI=true` чаще встречается в community-Dockerfiles потому что одна ENV покрывает install + prune + любые future commands использующие ту же purge-функцию.

**Q2 — `pnpm prune --prod` подход в целом?** **Текущий path работает, но pnpm.io official Example 1 (two-stage prod-deps + build, COPY --from=prod-deps node_modules в final) — concept-level cleaner.** ADR-001 §O-07 отверг **Vercel Turborepo with-docker two-install** — это **другой паттерн** чем pnpm.io two-stage (Vercel uses `yarn install` once + Next.js standalone output tracing; our use-case = NestJS, нет standalone analog). **ADR не рассматривал pnpm.io two-stage отдельно как alternative.** Empirical probe: minimal package.json → 9.6% smaller image (188MB vs 208MB), нет TTY workaround нужен в prune (но prod-deps stage сама хитает TTY error в pnpm@11.0.0 → CI=true required anyway). **No single dominant winner empirically — depends на priorities.**

**Recommendation**: KEEP Variant 2 + apply `ENV CI=true` в installer/builder stage. Document pnpm.io two-stage как Considered Alternative для future revisit (cleaner conceptually, но non-trivial Dockerfile rewrite — `--build-arg APP_NAME=...` parameterization compatible но требует `pnpm deploy --filter` inside prod-deps для proper monorepo isolation).

## 2. Q1 — `CI=true` canonical mechanism analysis

### Throw site (verified source)

`installing/deps-installer/src/install/validateModules.ts` lines 149-154 [VERIFIED via gh api commit 2ebd45a + current main]:

```typescript
if (opts.confirmModulesPurge ?? true) {
  if (!process.stdin.isTTY) {
    throw new PnpmError('ABORTED_REMOVE_MODULES_DIR_NO_TTY',
      'Aborted removal of modules directory due to no TTY', {
      hint: 'If you are running pnpm in CI, set the CI environment variable to "true", or set "confirmModulesPurge" to "false".',
    })
  }
  ...
}
```

**Trigger condition**: `opts.confirmModulesPurge ?? true` (default ON) + `!process.stdin.isTTY` (true в Docker BuildKit).

### CI=true wiring (verified)

`installing/deps-installer/src/install/index.ts` line 317 [VERIFIED via gh api]:

```typescript
confirmModulesPurge: opts.confirmModulesPurge && !opts.ci,
```

`opts.ci` populated через pnpm config from `process.env.CI`. `CI=true` → `opts.confirmModulesPurge` short-circuits в `false` → throw skipped. **Это explicit wired path, не side-effect или convention.**

### Документация

- pnpm.io/cli/prune НЕ упоминает CI/TTY (gap в docs) [CITED: pnpm.io/cli/prune].
- Error hint **сам** документирует оба fix-а (CI=true OR confirmModulesPurge=false) — это in-product documentation [VERIFIED: source].
- pnpm Issue #9966 (open Sep 2025): Zoltan Kochan (pnpm maintainer) and tjenkinson (PR author) оба endorse CI=true в Docker. @72636c suggests pnpm.io docs update [CITED: github.com/pnpm/pnpm/issues/9966 comments].
- Введено в pnpm 10.16 (commit 2ebd45a, PR #9960, closes #9744) — **breaking change подтверждён pnpm core team** [VERIFIED: changeset .changeset/slimy-baths-tan.md].

### Альтернативы

| Fix                                    | Mechanism                                                | Scope                                                  |
| -------------------------------------- | -------------------------------------------------------- | ------------------------------------------------------ |
| `ENV CI=true`                          | Sets `opts.ci=true` → forces `confirmModulesPurge=false` | Whole stage (covers install + prune + future commands) |
| `--config.confirmModulesPurge=false`   | CLI flag direct override                                 | Per-command only                                       |
| `--config.confirm-modules-purge=false` | kebab-case alias                                         | Per-command only                                       |
| Avoid prune (use prod-deps stage)      | Doesn't use `purgeModulesDirsOfImporters`                | Architectural — see Q2                                 |

**Verdict**: CI=true — canonical, not костыль. Mention в error hint = officially recommended path для CI/Docker.

## 3. Q2 — `pnpm prune --prod` подход itself (architectural re-eval)

### ADR O-07 чтение (verbatim)

ADR-001 §O-07 отверг «Variant 1 — Turborepo two-install pattern (rejected for single-service-per-build context)». Verbatim rationale: «Variant 1 — Turborepo canonical two-install Docker pattern (один full install для builder + один `--prod` install для runner stage из общего pnpm-fetch store) — подходит для multi-service-per-Dockerfile use cases с N runner-стадиями».

**Ссылки в O-07** указывают на Vercel `examples/with-docker` [CITED: github.com/vercel/turborepo/tree/main/examples/with-docker]. Я **прочитал actual Dockerfile** через gh api: Vercel `apps/web/Dockerfile` использует `yarn install` (один раз) + Next.js `standalone` output tracing для финального image. **Vercel НЕ делает «два install-а»** в любой форме. ADR O-07 framing «Turborepo two-install pattern» **некорректно описывает то, что Vercel actually делает** [VERIFIED: gh api repos/vercel/turborepo/contents/examples/with-docker/apps/web/Dockerfile].

### pnpm.io official Example 1 (canonical)

```dockerfile
FROM node:20-slim AS base
ENV PNPM_HOME="/pnpm"; ENV PATH="$PNPM_HOME:$PATH"
RUN corepack enable; COPY . /app; WORKDIR /app

FROM base AS prod-deps
RUN --mount=type=cache,id=pnpm,target=/pnpm/store pnpm install --prod --frozen-lockfile

FROM base AS build
RUN --mount=type=cache,id=pnpm,target=/pnpm/store pnpm install --frozen-lockfile
RUN pnpm run build

FROM base
COPY --from=prod-deps /app/node_modules /app/node_modules
COPY --from=build /app/dist /app/dist
```

[VERIFIED: pnpm.io/docker via gh api repos/pnpm/pnpm.io/contents/docs/docker.md, retrieved 2026-05-04].

**Это НЕ что O-07 отверг.** O-07 отверг multi-service multi-runner pattern. pnpm.io = **single service, two parallel install lanes share same cache-mount** (id=pnpm). BuildKit DAG runs prod-deps + build **в parallel** (cache-mount race-safe per BuildKit lock semantics).

### Сравнение паттернов

| Aspect                       | Variant 2 (current: full install + prune)              | pnpm.io Example 1 (prod-deps + build split)                   |
| ---------------------------- | ------------------------------------------------------ | ------------------------------------------------------------- |
| Docker stages                | 4 (pruner, installer, builder, runner)                 | 4 (base, prod-deps, build, final)                             |
| pnpm install invocations     | 1 (full set)                                           | 2 (prod set + full set, **shared cache-mount**)               |
| `pnpm prune --prod` needed   | YES                                                    | NO                                                            |
| TTY error trigger sites      | 1 (prune)                                              | 1 (prod-deps install — empirical, see §4)                     |
| `CI=true` needed             | YES                                                    | YES (both stages purge node_modules)                          |
| BuildKit parallelism         | Sequential (install → build → prune)                   | **prod-deps ∥ build run in parallel**                         |
| Workspace symlinks preserved | YES (in-place)                                         | Requires `pnpm deploy --filter` для proper monorepo isolation |
| Latent bug: pnpm Issue #9796 | YES (workspace deps prune edge case, low risk для нас) | NO (different code path)                                      |

### Production survey (5 sources cross-check)

| Source                           | Pattern used                                              | Citation                                         |
| -------------------------------- | --------------------------------------------------------- | ------------------------------------------------ |
| pnpm.io official Example 1       | prod-deps + build split, no prune                         | pnpm.io/docker                                   |
| pnpm.io official Example 2       | `pnpm deploy --filter --prod` (monorepo)                  | pnpm.io/docker                                   |
| Vercel Turborepo `with-docker`   | yarn install once + Next.js standalone                    | github.com/vercel/turborepo/examples/with-docker |
| fintlabs Medium (Turbo+pnpm)     | pnpm prune --prod + turbo prune --docker                  | fintlabs.medium.com                              |
| Bazyli Brzóska (NestJS official) | single install + post-build prune                         | (cited in ADR O-07, not re-verified)             |
| Liran Tal (Snyk JSConf EU 2023)  | «prune для single-service, two-install для multi-service» | (cited in ADR O-07)                              |

**Split**: 2/6 use prod-deps split (pnpm.io itself), 2/6 use prune (fintlabs, Bazyli), 1/6 uses pnpm deploy (pnpm.io Example 2), 1/6 uses Next.js-specific tracing (Vercel). **Нет single dominant pattern**; и official pnpm.io Example 1 (prod-deps split) и community NestJS guides (prune) — both well-attested.

## 4. Empirical comparison probe

`/tmp/probes/prune-verify/` — 5 Dockerfile-ов; minimal package.json (lodash prod + typescript dev), pnpm@11.0.0, BuildKit cold builds:

| Probe | Pattern                                                     | Result                                                                      | Cold time | Image size |
| ----- | ----------------------------------------------------------- | --------------------------------------------------------------------------- | --------- | ---------- |
| A     | full install + `pnpm prune --prod` (no fix)                 | PASS (this minimal case doesn't trigger TTY)                                | 3.3s      | 208 MB     |
| B     | full install + prune + **ENV CI=true**                      | PASS                                                                        | 3.3s      | 207 MB     |
| C     | full install + prune + `--config.confirmModulesPurge=false` | PASS                                                                        | 2.9s      | 208 MB     |
| D     | pnpm.io Example 1 (prod-deps + build split, no CI)          | **FAIL** — `ERR_PNPM_ABORTED_REMOVE_MODULES_DIR_NO_TTY` в `prod-deps` stage | n/a       | n/a        |
| D2    | pnpm.io Example 1 + **ENV CI=true**                         | PASS                                                                        | 2.8s      | **188 MB** |

**Ключевые наблюдения**:

1. **TTY error reproduces в pnpm.io's OWN recipe** в pnpm@11.0.0 без CI=true. pnpm.io docs не updated после 10.16 breaking change (issue #9966 commenter @72636c flagged это, docs PR не merged до 2026-05-04). **pnpm.io recipe is broken-as-published в 11.0.0**.
2. **Размер**: pnpm.io two-stage 188 MB vs prune 208 MB = **9.6% разница** для minimal probe. Реальная разница для нашего monorepo (NestJS + Drizzle + gRPC tooling) likely larger потому что Probe A/B/C carry full corepack chain + intermediate state в final layer; Probe D2 final stage starts с clean base.
3. **Probe A не воспроизвёл TTY error** на minimal package.json. PATTERN-E probe в `/tmp/probes/pattern-e/` (с workspace symlinks `link:../../packages/*` после M3) **воспроизводит**. Trigger condition specific к workspace+devDeps mismatch — NOT generic к prune itself.
4. **Cold build time** в пределах noise (2.8-3.3s); cache-mount benefits not visible на minimal probe.

**Probe artifacts**: `/tmp/probes/prune-verify/Dockerfile.{A,B,C,D,D2}-*` preserved.

## 5. Recommendation

**KEEP current path (Variant 2 + ENV CI=true)** — обоснование:

1. **CI=true is verified canonical** (Q1) — apply без guilt в installer + builder stages.
2. **Architectural switch к pnpm.io two-stage = non-trivial Dockerfile rewrite** (~30-50 lines) с:
   - Adding `pnpm deploy --filter @email-platform/${APP_NAME} --prod` для proper monorepo workspace isolation в prod-deps stage (наш `--build-arg APP_NAME=...` pattern requires это, иначе `node_modules` carries deps от ВСЕХ apps).
   - Reconciling с existing `turbo prune --docker` стадией и `out/full` / `out/json` flow.
   - **Это re-opens ADR-001 Decision (a)** (drop pnpm deploy → currently DROPPED), что = full ADR amendment cycle, не ad-hoc Dockerfile change.
3. **9.6% image size delta для minimal probe** недостаточно alone для re-opening ADR. OQ-03 deferred к 999.18.2 Wave 0 PoC (per ADR §"Open Questions") — measure real monorepo image diff first; если delta >20%, then trigger T-NEW-NN re-eval.
4. **Issue #9796 latent risk** — applicable только для `pnpm deploy ./out` + `pnpm prune --prod` chain (которого у нас нет). Variant 2 in-place prune без `pnpm deploy` = different code path, low risk.

**Action items для plan amendment** (atomic, минимально-инвазивно):

- Add `ENV CI=true` в `infra/docker/app.Dockerfile` installer stage (line ~47, перед PNPM_HOME setup) — covers install + prune purge calls + future commands.
- **OPTIONAL** alternative: `pnpm prune --prod --config.confirmModulesPurge=false` (per-command, more explicit intent). Choose based on style preference; CI=true wider-net; flag more surgical.
- Document pnpm.io two-stage в RE-EVAL-TRIGGERS как **T-NEW-XX** trigger: «If image size becomes problem (OQ-03 measurement >20% over baseline), re-evaluate switch к pnpm.io Example 1 + `pnpm deploy --filter --prod` для monorepo isolation».

**NO unilateral switch к pnpm.io two-stage** — это architectural decision requiring user approval per memory `feedback_infra_changes` + `feedback_report_dont_fix`.
