## §A Architectural Foundations

### A.1 — 12-Factor App principles per layer

12-Factor (Heroku, 2011 — anchor MAANG-canonical) — это методологический якорь, к которому привязаны все 5 слоёв. [VERIFIED: WebFetch 2026-05-04 from https://12factor.net/build-release-run]

Прямая цитата из канона:

> "It is impossible to make changes to the code at runtime, since there is no way to propagate those changes back to the build stage."
> "the run stage should be kept to as few moving parts as possible, since problems that prevent an app from running can cause it to break in the middle of the night when no developers are on hand."
> "A release cannot be mutated once it is created. Any change must create a new release."

### A.3 — Cockburn primary/secondary adapters analogy для L1↔L5 boundary

Alistair Cockburn (Hexagonal Architecture, 2005) — primary (driving) adapters call **into** the application; secondary (driven) adapters are called **by** the application. [CITED: Cockburn "Hexagonal Architecture" 2005 — широко цитируется в DDD / Clean Architecture литературе]

**Mapping на L1-L5 build-system architecture (analogy, not exact):**

| Cockburn primitive                                    | Build-system analogue                                              | Layer                         |
| ----------------------------------------------------- | ------------------------------------------------------------------ | ----------------------------- |
| **Primary adapter** (driving — initiates work)        | Developer commit / git push trigger                                | Внешний (developer) → L1      |
| **Application core**                                  | The codebase + business logic                                      | inside L1 + L2 (orchestrated) |
| **Secondary adapter** (driven — application calls it) | Build tool (turbo) / packager (Docker) / pipeline / verify scripts | L2 / L3 / L4 / L5             |

Уровень analogue **не строгий** — build system это external pipeline, не inverted-control приложение. Но полезно: layers L2-L5 это **secondary adapters в Cockburn sense** — orchestrator / packager / pipeline / verifier работают **на запрос** от L1 (workspace state), не initiate сами.

**Decoupling implication:** в Cockburn terms, primary adapters легко заменимы (rename CI provider) потому что они только initiate; secondary adapters легко заменимы (swap packager Docker → Bazel rules_oci) потому что они работают через port. **Это и есть основа Substitutability (C-01).**

Confidence: MEDIUM — analogy полезна но не строгая; build-system literature не использует Cockburn terms напрямую.

### A.4 — Uncle Bob Clean Architecture rings analogy

Robert C. Martin (Clean Architecture, 2017) — concentric rings: Entities (центр) / Use Cases / Interface Adapters / Frameworks & Drivers (внешнее кольцо). Dependency rule: dependencies point inward. [CITED: Martin "Clean Architecture" 2017]

**Mapping на L1-L5 (analogy):**

| Clean Architecture ring                   | Build-system analogue                                | Layer                             |
| ----------------------------------------- | ---------------------------------------------------- | --------------------------------- |
| **Entities** (бизнес-сущности)            | The source code itself (`apps/`, `packages/`)        | L1                                |
| **Use Cases** (что система делает)        | Build / lint / typecheck tasks                       | L2 (turbo.json defines use cases) |
| **Interface Adapters** (DTOs, presenters) | Dockerfile (adapter from build artifact → OCI image) | L3                                |
| **Frameworks & Drivers** (внешний мир)    | CI platform + K8s + observability                    | L4 + L5                           |

**Dependency rule check:**

- L1 знает только себя → ✓ соответствует "Entities know nothing"
- L2 знает L1 → ✓ соответствует "Use Cases depend on Entities"
- L3 знает L2 (через `dist/`) → ✓
- L4 знает L3 (через image digest) → ✓
- L5 знает L4 (verify against deployed image) → ✓

**Anti-pattern в этом mapping:** если L4 знает про L1 internals (например, workflow embeds `pnpm install` shell-команду напрямую вместо `pnpm <script>`), это **inversion of dependencies** — внешнее кольцо ссылается на внутреннее. Точно противоречит Uncle Bob's "dependencies point inward". В нашей архитектуре правило **"workflow invokes only `pnpm <script>` + `docker buildx`"** — exactly эта инверсия предотвращается.

Confidence: MEDIUM — analogy полезна для понимания dependency direction, но build-system это не приложение с runtime DI graph.

### A.5 — 6 decoupling criteria — empirical test для каждого

Six criteria из LAYER-ARCHITECTURE §D ratified. Здесь — **operational empirical test для каждого**, грounded в Liskov-style substitutability + canonical patterns.

#### C-01 Substitutability

**Definition:** Layer X has defined contract with X-1 below and X+1 above. Replace X with X' (different impl, same contract) — does NOT require changes in X-1 or X+1.

**Empirical test (Liskov-style):**

1. Identify layer X's contract (input artifact + output artifact + invariants)
2. Construct X' that satisfies same contract via different impl
3. Substitute X' in place of X
4. Run X-1 → X' → X+1 path
5. **Pass criteria:** X-1 produces same artifact as input to X' (no changes); X+1 receives same artifact from X' (no changes)
6. **Fail criteria:** X-1 has to change shape of output OR X+1 has to change shape of input → contract was implicit in X's impl, not in interface

**Worked example для L4 (GitHub Actions → GitLab CI):**

- L4 contract: input = git event + workspace + image registry credentials; output = OCI image at registry digest + deploy webhook
- L4' = GitLab CI implementation
- Substitution succeeds if: L1-L3 (`pnpm <script>` + `docker buildx`) untouched; L5 verify scripts untouched; only `.gitlab-ci.yml` replaces `.github/workflows/*.yml`
- This IS the project's GitLab migration plan (per memory `project_gitlab_migration`) — substitutability IS the design target

#### C-02 Hermeticity

**Definition:** Layer's behavior depends only on declared inputs. Same input → same output. Host system changes do not affect layer output.

**Empirical test:**

1. Build artifact in environment E1 → output O1
2. Build artifact in environment E2 (different host OS, different system libs, different tool versions outside declared inputs) → output O2
3. **Pass criteria:** O1 == O2 byte-for-byte
4. **Fail criteria:** O1 != O2 → layer depends on undeclared input

**Worked example для L3 (current state):**

- Current: `node:22-alpine` tag (not digest-pinned) → tag drift over time → O1 != O2 across rebuild
- Hardened: `node:22-alpine@sha256:abc...` → tag drift impossible → O1 == O2 (modulo other non-determinism)
- Bazel comparison: rules_oci hermetic by design — toolchain pinned, network reads forbidden
- Verdict for project: L3 hermeticity = MEDIUM-FAIL currently; LOW gap (hardened in 999.18.4 deferred phase)

#### C-03 Reproducibility

**Definition:** Given identical declared inputs, layer produces bit-identical output. Verifiable via checksum.

**Empirical test:**

1. Build artifact A1 from inputs I → checksum H1
2. Wait time T (T = days)
3. Build artifact A2 from same I → checksum H2
4. **Pass criteria:** H1 == H2
5. **Fail criteria:** H1 != H2 → non-determinism somewhere (timestamps, file ordering, non-deterministic tool output)

**Reproducible Builds canon:** SOURCE_DATE_EPOCH env var [CITED: https://reproducible-builds.org/docs/source-date-epoch/]. Tools that respect SOURCE_DATE_EPOCH produce timestamps deterministically.

**Worked example для L3:**

- Current: `RUN ... --build-arg BUILD_COMMIT=${SHA} && date -u > build-info.json` → build-info.json не bit-identical across rebuild because `date -u` non-deterministic
- Hardened: `RUN ... && SOURCE_DATE_EPOCH=${BUILD_TIMESTAMP} date -u -d @${SOURCE_DATE_EPOCH} > build-info.json` → bit-identical
- LOW gap (deferred to 999.18.4)

#### C-04 Failure Containment

**Definition:** Failure inside layer X does NOT corrupt layer X-1 or X+1. Boundary = sandbox = error isolation.

**Empirical test:**

1. Inject failure in layer X (make build command fail mid-way)
2. Check layer X-1 state — should be unchanged
3. Check layer X+1 state — should not have started consuming artifact (because no artifact produced)
4. **Pass criteria:** X-1 unchanged + X+1 not invoked
5. **Fail criteria:** X-1 mutated by X's partial work OR X+1 invoked with corrupt artifact

**Worked example для L3:**

- Inject failure in builder stage (typescript compile error)
- L2 (`dist/`) — было пусто перед build, не корруптируется
- L4 — не получает image (no push because build failed)
- Containment: PASS

**Bazel comparison:** sandbox-per-action — каждое action в isolated execroot, partial failure cannot corrupt other actions. Bazel hermeticity == failure containment by design. Docker BuildKit — каждый stage в isolated container, similar isolation.

#### C-05 Concern Atomicity

**Definition:** Layer's responsibility maps to one named concern из canonical pipeline (compile / package / deploy / orchestrate / configure / verify). No layer owns two unrelated concerns.

**Empirical test (rename test):**

1. Articulate layer's concern in 1 sentence
2. If sentence contains "and" connecting two unrelated nouns → C-05 violation
3. If sentence single concern with adjectives → PASS

**Per-layer check:**

- L1: "Declare what code exists" — single concern PASS
- L2: "Compute and execute build DAG with caching" — single concern (DAG-aware build is one concern, caching is its property, not separate concern) PASS
- L3: "Produce OCI image artifact from L2 output" — single concern PASS
- L4: "Orchestrate trigger / matrix / push / deploy" — borderline (4 sub-concerns под одним зонтиком pipeline) PARTIAL — at our scale acceptable
- L5: "Empirical post-build proof" — single concern PASS

**Anti-pattern example:** if Dockerfile owned both "build artifact" AND "run migrations" concerns → split into separate concerns (build image + migration job). Distroless USER + tini help enforce this.

#### C-06 Lifecycle Independence

**Definition:** Layer X can change at its own cadence. No required co-changes in X-1 or X+1 when X version updates.

**Empirical test:**

1. Update layer X to new minor version (e.g., turbo 2.9 → 2.10)
2. Run X-1 → X → X+1 path
3. **Pass criteria:** X-1 + X+1 unchanged; only X version pinned changes
4. **Fail criteria:** X-1 needs config update OR X+1 needs config update

**Worked example для L2 (turbo upgrade):**

- L1: pnpm-lock.yaml updates devDependency turbo version → that's L1's natural changе not driven by L2
- L2: turbo.json — schema мог измениться → potentially needs update (this would be a Lifecycle violation if minor version)
- L3: Dockerfile pulls turbo from devDeps → unchanged
- L4: workflow `pnpm exec turbo run build` — unchanged
- L5: verify scripts — unchanged
- Verdict: PASS for minor; PARTIAL for major (turbo 1 → 2 has breaking changes; expected per semver)

**Conway's Law connection:** lifecycle independence is expression of team-boundary autonomy. If layers were owned by separate teams, each team's release cadence is independent. At N=1 dev (current project state) this is theoretical, but architecture design preserves capability for future team scaling. [CITED: Conway 1967; Fowler bliki ConwaysLaw]

### B.3 Edge cases (минимум 6 — actually 9)

#### EC-L1-01: Dev forgot setup → marker file pattern

**Scenario:** Developer clones repo, runs `pnpm install`, but forgets `pnpm setup-hooks`. Hooks not installed locally. Developer commits with secrets / un-linted code → reaches GitLab MR.

**What breaks:** Developer perception of "pre-push validates locally" is broken — security checks don't fire.

**Mitigation (ratified — defense lives in L4):** GitLab CI required pipeline catches gitleaks / semgrep / audit / trivy / typecheck / lint on every MR. **Local hooks are convenience, not security layer.** «Dev forgot setup» does NOT compromise security because L4 IS the security gate.

**Future-phase mitigation (out of 999.18.3 scope, per HANDOFF future_phase_seed):** marker file pattern — `pnpm setup-hooks` generates `.git/hooks-installed` marker. Dev runtime scripts (`pnpm dev`, `pnpm start`) check marker on startup; if missing → fail fast with «Run `pnpm setup-hooks` first».

**Decoupling proof — does this break C-04 Failure Containment?** No. Local hooks failure is contained at L1; cannot affect L3-L5. Only L4 enforcement remains.

#### EC-L1-02: CI vs local parity

**Scenario:** Local runs `pnpm install` + `pnpm setup-hooks`. CI runs `pnpm install --frozen-lockfile`. CI doesn't run setup-hooks (no need — CI doesn't have local Git for hook installation).

**What breaks:** None — by design.

**Mitigation:** CI invokes pnpm scripts directly (`pnpm lint`, `pnpm typecheck`, `pnpm security:*`) — same scripts as hooks invoke. **Hooks are L1 ergonomics; CI is L4 enforcement. Both invoke same source-of-truth scripts.**

**12-Factor X (dev/prod parity) compliance:** ✓ — same scripts everywhere; only invocation context differs.

#### EC-L1-03: Secrets rotation flow без husky

**Scenario:** Phase 999.17.2 adds `security:secrets-staged` script (gitleaks staged-files scan). Without husky `pre-commit` hook auto-firing, dev может skip locally.

**What breaks:** Dev может accidentally commit a secret. Pre-push (server-side L4 GitLab CI gitleaks scan) catches it before merge.

**Mitigation:**

1. `.githooks/pre-commit` script invokes `pnpm security:secrets-staged` — runs locally if `pnpm setup-hooks` was executed
2. L4 GitLab CI required pipeline runs gitleaks scan на every push (catches if pre-commit was skipped via `--no-verify` or hooks not installed)
3. Defense-in-depth: 2 gates (local hook + server-side CI). Server-side CI is mandatory; local hook is convenience.

**Per `feedback_security_verification` memory:** «Never trust config-only validation; require fixture-based end-to-end testing». GitLab CI runs against fixture commits to verify gitleaks fires correctly — established в Phase 999.17.

#### EC-L1-04: Branch hooks vs commit hooks

**Scenario:** `.githooks/pre-commit` fires on every commit. `.githooks/pre-push` fires on every push. What about post-checkout / post-merge / pre-rebase?

**What breaks:** If hooks scope is wrong (e.g., pre-commit invokes pre-push checks), CI duplicates work, dev gets slow-down per commit.

**Mitigation:** Per Phase 999.17.1 design: pre-commit = staged-files-only scope (`security:secrets-staged`); pre-push = full chain (`security:pre-push-orchestrator.sh`). Two separate hooks, two separate scope levels.

**MAANG canon:** Atlassian / GitHub Engineering pattern — pre-commit = lightweight (seconds), pre-push = thorough (tens of seconds). Anything multi-minute → CI only. [CITED: Atlassian Git tutorials + GitHub blog "Working with hooks" — historical reputation]

#### EC-L1-05: Multi-OS compatibility (macOS / Linux / WSL)

**Scenario:** `.githooks/pre-commit` is shell script. macOS + Linux: bash works. Windows native (cmd / PowerShell): bash not present. WSL: works.

**What breaks:** Windows-native dev cannot run hooks (and probably cannot run pnpm in non-WSL anyway, given Node ecosystem reality).

**Mitigation:**

1. Project's stated platform per `package.json` engines: Node 20+. Implicitly: Linux / macOS / WSL only.
2. `.githooks/pre-commit` script с shebang `#!/usr/bin/env bash` — bash universal на macOS / Linux / WSL.
3. Document в README: «Windows users: use WSL» — standard MAANG-aligned guidance.

**Alternative considered:** Cross-platform hooks (e.g., simple-git-hooks library, lefthook) auto-detect shell. **Rejected:** adds dependency we don't need; ratified decision is "drop tools, not swap". User explicitly: «зачем менять tool, если можно просто убрать?»

#### EC-L1-06: Корпоративные dev-workstation policies

**Scenario:** Corporate machine policy disables shell script execution from arbitrary dirs. Dev cannot install hooks because `git config core.hooksPath .githooks` — the directory not in approved exec path.

**What breaks:** `pnpm setup-hooks` succeeds but hooks don't fire (silent) or fire with permission denied.

**Mitigation:**

1. Document в CONTRIBUTING: «Corporate-policy environments: hooks may be disabled. CI is the security gate; local hooks are convenience.»
2. Per ratified architecture, this is acceptable: L4 CI is the enforcement layer.
3. Defense-in-depth from EC-L1-03: server-side gates catch missed local checks.

**This is the architectural rationale для drop-husky:** husky's prepare-script tries to install hooks at npm-install time, which fails silently in corporate-policy envs. `.githooks/` + explicit `pnpm setup-hooks` makes the failure mode visible — dev sees "permission denied" and knows to ask IT.

#### EC-L1-07: Workspace package добавлен но не в dep graph

[CITED: from LAYER-ARCHITECTURE §H.1 EC-02]

**Scenario:** Adding `packages/foo/` без consumer declaring `"@scope/foo": "workspace:*"` → turbo prune skips it (Iter 4 incident with tsconfig.base.json).

**Mitigation (Pattern E / D-09 RATIFIED):** every workspace package MUST have at least one declared consumer. tsconfig.base.json moved into `packages/tsconfig-base/` and consumed via `extends: "@email-platform/tsconfig-base"`.

**Verification:** turbo prune output (`out/json/` + `out/full/`) includes the package iff it's in dep graph. Manually `pnpm exec turbo prune <app> --docker --dry-run | grep tsconfig-base` — ✓ reachable.

#### EC-L1-08: Stale lockfile after dep update outside pnpm

[CITED: from LAYER-ARCHITECTURE §H.1 EC-04]

**Scenario:** Dep accidentally added via `npm install` → lockfile becomes inconsistent with package.json.

**Mitigation:** `packageManager: "pnpm@11.0.0"` field in root package.json + Astro's `preinstall: only-allow pnpm` pattern. **Recommendation для 999.18.3 plan:** add `"preinstall": "npx only-allow pnpm"` to root package.json (matches Astro empirical canon).

**Decoupling proof:** preinstall is L1's package-manager-policy enforcement, not Git-hooks. Separate concern from drop-husky decision. Could coexist: `preinstall` allowed (different lifecycle moment), `prepare` removed.

**Open question:** Should 999.18.3 plan include `preinstall: only-allow pnpm`? Surfaced as part of P-01 expanded scope в §J.

#### EC-L1-09: tsconfig extends path drift

[CITED: from LAYER-ARCHITECTURE §H.1 EC-07]

### C.5 Edge cases (минимум 6 — actually 8)

#### EC-L2-01: Cache invalidation на cross-package change

**Scenario:** Change in `packages/contracts/proto/auth.proto` should invalidate cache для всех services that consume contracts (auth, sender, parser, audience, gateway, notifier).

**What breaks:** If turbo.json's `inputs:` doesn't declare proto files as input для downstream packages, false cache hits → services run with stale generated code.

**Mitigation (CURRENT STATE — preserved per ratified):**

```jsonc
// turbo.json
{
  "tasks": {
    "build": {
      "dependsOn": ["^build", "generate"], // generate is upstream
      "inputs": ["src/**", "package.json", "tsconfig.json"],
      "outputs": ["dist/**"],
    },
    "generate": {
      "inputs": ["proto/**", "scripts/**"],
      "outputs": ["src/generated/**"],
    },
  },
}
```

`dependsOn: ["generate"]` ensures contracts regenerate before downstream builds. `inputs:` for `generate` includes proto files — change triggers regeneration → downstream sees new generated → cache invalidation cascades.

**Verification (manual):** `touch packages/contracts/proto/auth.proto && pnpm exec turbo run build --dry-run | grep "cache miss"` — expect ALL services in cache miss.

#### EC-L2-02: Parallel pipeline failure containment

**Scenario:** Turbo runs `build` для 6 services in parallel. Service C build fails → what about A, B (still running), D, E, F (not started)?

**Mitigation:** Default turbo behavior — fail-fast (kills running, skips not-started). Override via `turbo run build --continue` if want to see all failures.

**Trade-off:** Fail-fast is faster feedback (ship CI faster); --continue is comprehensive feedback (one CI run shows all failures). Project canonical: fail-fast in CI for speed; --continue locally for debugging.

**Decoupling proof — does this break C-04?** No. Failure in one service contained (other services either complete or never start). L3 doesn't see partial output (turbo only commits cache on success).

#### EC-L2-03: Remote cache (Turborepo Cloud / Bazel BES) — not yet used

**Scenario:** Local cache hits 80% but CI cold-runs (new machine each run) → 0% cache hits → every CI build is cold.

**Mitigation OPTION A (Turborepo Cloud):** `turbo login` + `turbo link` → remote cache hosted by Vercel. Free tier: limited; paid tier: $$/month per developer.

**Mitigation OPTION B (self-hosted):** Turbo supports custom remote cache backends. Could host on internal MinIO / S3 / GitLab artifact storage. Requires DIY plumbing.

**Mitigation OPTION C (rely on GitLab CI cache):** GitLab CI `cache:` directive caches `.turbo/` between jobs/runs — works для same branch. Less universal than remote cache, sufficient at our scale.

**Current state (ratified):** Option C — GitLab CI cache + per-branch / per-MR cache scope. **Sufficient at N=6.** Re-evaluate when build time exceeds threshold.

#### EC-L2-04: Workspace dependency cycle detection

**Scenario:** `packages/foundation` depends on `packages/contracts` → A. `packages/contracts` depends on `packages/foundation` → B. **Cycle.** Turbo / pnpm allow it; build fails non-obviously.

**Mitigation (current — partial):** ESLint `no-restricted-imports` rules per layer (per `.eslintrc.js` enforces layered architecture: contracts → config → foundation → apps; apps cannot import other apps). This catches most cycles at lint time.

**Hardening (deferred — LOW gap):** explicit pre-commit cycle check via `madge` or `dependency-cruiser`. Surfaced как §L Open Question.

**Decoupling proof:** cycle violates C-05 (Concern Atomicity) — two packages have circular dependency means they're really one concern. Architectural refactor required, not just lint rule.

#### EC-L2-05: Hot reload в dev mode

**Scenario:** `pnpm dev` → turbo watches all packages. File change in `packages/foundation` should trigger rebuild + restart consumer service.

**Current behavior:** `turbo run dev` with `dev` task `passThroughEnv: ["*"]` and `cache: false`. ts-node-dev / nodemon в каждом app handles per-app watch.

**Edge case:** `packages/contracts` regen requires explicit `pnpm generate:contracts` — dev script doesn't auto-watch proto files. Manual trigger after proto change.

**Mitigation (current):** documented в README. Could automate via `turbo run dev` + `chokidar` on proto/ — deferred enhancement.

#### EC-L2-06: Polyglot support ceiling

**Scenario:** New service в Go или Python. Turborepo officially TS-first. Bazel polyglot.

**Mitigation:** Turborepo CAN run arbitrary commands (turbo.json tasks just `pnpm <script>` invocations) — language-agnostic from turbo's perspective. **Limitation:** dependency graph traversal for non-JS workspaces requires manual `dependsOn` declarations; turbo doesn't auto-detect Go/Python deps.

**Project current state:** TS-only. If polyglot needed → re-evaluate (Bazel canonical). Out of 999.18.3 scope.

#### EC-L2-07: `pnpm --filter` bypassing turbo (anti-pattern)

[CITED: from LAYER-ARCHITECTURE §H.2 EC-12]

**Scenario:** Dockerfile or CI script invokes `pnpm --filter=<svc>... run build` directly (not through turbo) → turbo cache не hit, dependencies not respected, builds in random order.

**Mitigation:** Project convention — Dockerfile + CI workflows invoke `pnpm exec turbo run build` always. ESLint rule could enforce (deferred).

**Decoupling proof:** `pnpm --filter` bypass IS C-05 violation — L3 (Dockerfile) bypasses L2 orchestrator, doing L2's job directly. Boundary blurs.

#### EC-L2-08: Daemon corruption в long-running CI

**Scenario:** Turbo daemon (long-lived process for cache state) corrupted between CI runs. Causes false cache hits.

**Mitigation:** CI uses one-shot turbo invocations (no daemon long-lived). `--no-daemon` flag explicit OR daemon dies with CI runner. Acceptable risk at our scale.

## §D L3 Packaging — Docker / OCI image build

### D.1 Decision recap

**Ratified 2026-05-04:** two-install Vercel canonical pattern. Docker BuildKit + distroless runner. ZERO flags / env vars / workarounds.

```
Stage 1.1 pruner    — turbo prune --docker (.git not copied — turbo strips it)
Stage 1.2 prod-deps — pnpm install --prod --frozen-lockfile (NO prepare → zero leak)
Stage 1.3 builder   — pnpm install --frozen-lockfile + turbo build (NO prepare → zero leak)
Stage 2  runner     — distroless + COPY --from=prod-deps node_modules + COPY --from=builder dist
```

ZERO of: `pnpm prune --prod`, `ENV CI=true`, `ENV HUSKY=0`, `--legacy`, `--ignore-scripts`, `injectWorkspacePackages`.

D-08 PNPM_HOME preserved (in both install stages 1.2 and 1.3 — cache mounts share store path). D-09 Pattern E (workspace tsconfig package) preserved.

### D.2 Two-install pattern detailed

#### D.2.1 Why two install stages, not one

Pattern (Vercel turborepo canonical via `examples/with-docker/`) — **one install** in builder stage. Then COPIES whole node_modules to runner. **At Vercel, this is fine** — they don't deploy через Docker, they deploy через Vercel platform with custom optimization.

For self-hosted Docker pattern, we want **production-only deps in runner image**. Solutions:

| Approach                              | Stages                                                                                                | Pros                                                                                      | Cons                                                                                                | Verdict                          |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- | -------------------------------- |
| **Single install** (Vercel canonical) | One install in builder; whole node_modules copied to runner                                           | Simplest                                                                                  | Runner image has devDeps (linters, test frameworks, ts-node, etc.) — bloated, larger attack surface | Rejected for self-hosted         |
| **`pnpm prune --prod` after build**   | Install + build + prune-in-place                                                                      | Single install layer                                                                      | pnpm bug #7068: prune triggers prepare-script re-run; husky lifecycle leak (Iter 6 root cause)      | **REJECTED — D-01 superseded**   |
| **`pnpm deploy --legacy --prod`**     | Install + build + deploy-extract to /prod/${APP}                                                      | Isolated production bundle                                                                | Requires `--legacy` escape hatch flag (pnpm 10.2.1+); user rejected «странные флаги»                | **REJECTED — Path 3 superseded** |
| **Two-install (parallel stages)**     | Stage 1.2 prod-deps install (--prod) **‖** Stage 1.3 builder install (full) → runner COPIES from both | No prepare leak (no husky in package.json after L1 ratified); canonical pnpm.io Example 1 | +30-60s build time (two installs)                                                                   | **CHOSEN — RATIFIED**            |

#### D.2.2 Two-install pattern — verbatim shape

[VERIFIED: WebFetch 2026-05-04 from https://github.com/vercel/turborepo/blob/main/examples/with-docker/apps/api/Dockerfile]

Vercel canonical Dockerfile uses **single install** в builder stage (yarn install), затем COPY whole `/app` to runner. Это Vercel-канонично, но НЕ нашего use case.

Наш ratified pattern — **гibrid Vercel turbo prune + pnpm.io Example 1 two-install**:

[CITED: pnpm.io Example 1 from LAYER-ARCHITECTURE S-11 (verified iter 7)]

```dockerfile
# Stage 1.1 — pruner (turbo prune scope)
FROM node:22-alpine AS pruner
WORKDIR /app
RUN apk add --no-cache wget
RUN corepack enable && corepack prepare pnpm@11.0.0 --activate
COPY . .
RUN pnpm dlx turbo prune ${APP_NAME} --docker
# Outputs: /app/out/json/ + /app/out/full/

# Stage 1.2 — prod-deps install (PARALLEL to builder)
FROM node:22-alpine AS prod-deps
WORKDIR /app
RUN corepack enable && corepack prepare pnpm@11.0.0 --activate
ENV PNPM_HOME=/pnpm
COPY --from=pruner /app/out/json/ .
RUN --mount=type=cache,target=/pnpm,id=pnpm-store pnpm install --prod --frozen-lockfile

# Stage 1.3 — builder install (full deps + build)
FROM node:22-alpine AS builder
WORKDIR /app
RUN corepack enable && corepack prepare pnpm@11.0.0 --activate
ENV PNPM_HOME=/pnpm
COPY --from=pruner /app/out/json/ .
RUN --mount=type=cache,target=/pnpm,id=pnpm-store pnpm install --frozen-lockfile
COPY --from=pruner /app/out/full/ .
RUN pnpm exec turbo run build --filter=${APP_NAME}...

# Stage 2 — runner (distroless)
FROM gcr.io/distroless/nodejs22-debian12 AS runner
WORKDIR /app
COPY --from=prod-deps /app/node_modules ./node_modules
COPY --from=builder /app/apps/${APP_NAME}/dist ./dist
COPY --from=builder /app/packages ./packages
USER 65532:65532
ENTRYPOINT ["node", "dist/main.js"]
```

**Note:** This is illustrative; concrete Dockerfile for `infra/docker/app.Dockerfile` will be implementation detail of Plan 07. The ratified ARCHITECTURE is the four-stage shape; implementation specifics (which stages, which COPY directives) are Plan 07's task scope.

#### D.2.3 Why each stage is needed

| Stage                   | Concern                               | Why separate stage                                                                         |
| ----------------------- | ------------------------------------- | ------------------------------------------------------------------------------------------ |
| **Stage 1.1 pruner**    | "What files matter for this APP_NAME" | Turborepo's prune outputs a minimal subtree — saves cache invalidation на irrelevant files |
| **Stage 1.2 prod-deps** | "Production node_modules only"        | Parallel to builder — doesn't depend on build artifact; only on json                       |
| **Stage 1.3 builder**   | "Compile dist"                        | Needs full node_modules (devDeps for tsc, ts-proto, etc.)                                  |
| **Stage 2 runner**      | "Execute artifact"                    | distroless minimal — only Node + app code                                                  |

**Cache layer ordering rule** [VERIFIED: WebFetch 2026-05-04 from https://docs.docker.com/build/cache/optimize/]:

> "Because a change causes a rebuild for steps that follow, try to make expensive steps appear near the beginning of the Dockerfile. Steps that change often should appear near the end."

**Application:** package.json files copied first (rare changes); source code copied later (frequent changes). Stage 1.2 + 1.3 do this naturally — pnpm install layer cached when only source code changes.

### D.3 Docker BuildKit deep

#### D.3.1 Cache mount strategy

[VERIFIED: WebFetch 2026-05-04 from https://docs.docker.com/build/cache/optimize/]

> "The cache is cumulative across builds, so you can read and write to the cache multiple times. This persistent caching means that even if you need to rebuild a layer, you only download new or changed packages."

Syntax: `--mount=type=cache,target=/pnpm,id=pnpm-store`

**Application для two-install:**

- Both Stage 1.2 + 1.3 use `id=pnpm-store` → share pnpm content-addressable store across stages
- Only npm registry changes trigger downloads; existing packages are reused

**D-08 (RATIFIED):** `ENV PNPM_HOME=/pnpm` aligned with cache mount target. Without alignment (Iter 3 incident), pnpm writes to `~/.local/share/pnpm/store/v11/` — cache miss 100%.

#### D.3.2 Secret mounts (`--mount=type=secret`)

[VERIFIED: WebFetch 2026-05-04 from https://docs.docker.com/build/building/secrets/]

> "Build arguments and environment variables are inappropriate for passing secrets to your build, because they persist in the final image. Instead, you should use secret mounts or SSH mounts, which expose secrets to your builds securely."
>
> "Secret mounts do not persist in image layers" — accessible only during build instruction.

**Application:** if Dockerfile needs npm registry auth token (private packages) — use `--mount=type=secret,id=npm_token,target=/run/secrets/npm_token` rather than `ENV NPM_TOKEN=...` or `--build-arg NPM_TOKEN=...`.

**Current state (project):** No private npm packages → no secrets in build. **Future:** if private packages added, use `--mount=type=secret`.

[CITED: from LAYER-ARCHITECTURE §H.3 EC-41]
**Anti-pattern:** secrets in `--build-arg` — persist in image history.

#### D.3.3 BuildKit frontend versions

BuildKit syntax: `# syntax=docker/dockerfile:1.6` or higher для cache mount + secret mount features.

**Recommendation:** pin specific BuildKit syntax version в Dockerfile (`# syntax=docker/dockerfile:1.6`) — НЕ `dockerfile:1` (latest, drift) для reproducibility.

### D.4 Distroless / minimal images

#### D.4.1 Google distroless

[CITED: from LAYER-ARCHITECTURE §B.9 (S-10 verified iter 7)]

> "Distroless images contain only your application and its runtime dependencies. They do not contain package managers, shells or any other programs you would expect to find in a standard Linux distribution."
>
> Security: "no shell means an attacker who gets remote code execution in your app cannot drop into a terminal, install tools, or explore the filesystem the way they normally would."
>
> Size: distroless static = ~2 MiB vs alpine ~5 MiB vs debian ~124 MiB.

**Project choice (RATIFIED):** `gcr.io/distroless/nodejs20-debian12` (или nodejs22 на upgrade). Available variants:

- `:nonroot` — runs as user 65532 (non-root)
- `:debug` — has busybox shell (debug only, not prod)
- digest-pinned (`@sha256:...`) recommended; current state uses tag (LOW gap)

#### D.4.2 Chainguard / Wolfi alternative

[VERIFIED: WebFetch 2026-05-04 from https://www.chainguard.dev/unchained/minimal-container-images-towards-a-more-secure-future]

> "Chainguard builds on the distroless concept... centers its toolchain around apk (Alpine's package manager), apko, and melange."
>
> Customization: "adding a new package only requires editing a single line of a YAML file" vs Google's Bazel approach.
>
> "the fewer binaries and packages in an image — the lower the risk of something going wrong or being targeted by hackers."

**Comparison matrix:**

| Property            | Google distroless           | Chainguard                                    |
| ------------------- | --------------------------- | --------------------------------------------- |
| Base                | Debian-derived              | Wolfi (custom Alpine-based distro)            |
| Toolchain           | Bazel                       | apko + melange (YAML-driven)                  |
| Customization ease  | Bazel learning curve        | Single-line YAML edit                         |
| Languages           | Go / Java / Python / NodeJS | Multiple apk-based; building own glibc distro |
| Verification        | sigstore signed             | sigstore signed                               |
| Public availability | Free (gcr.io/distroless)    | Free + paid tiers (cgr.dev/chainguard)        |

**Recommendation для project:** start with Google distroless (chosen, working). Re-evaluate Chainguard в future hardening phase if customization needs grow (e.g., add CA cert, add specific glibc lib).

#### D.4.3 Trade-off vs alpine

| Property             | Alpine (musl libc)                                    | Distroless (glibc)                 | Wolfi (glibc available) |
| -------------------- | ----------------------------------------------------- | ---------------------------------- | ----------------------- |
| Size                 | ~5 MiB                                                | ~2 MiB (static) / ~50 MiB (nodejs) | comparable              |
| libc                 | musl                                                  | glibc                              | glibc (or musl)         |
| Package availability | apk (broad)                                           | NONE (no package manager)          | apk (broad)             |
| Attack surface       | shell, busybox, apk                                   | NONE                               | NONE in prod variants   |
| Runtime issues       | Some Node packages have musl-incompatible binary deps | Compatible с standard Node         | Compatible              |

**Project history:** **Alpine in build stages, distroless in runner.** Build stages need shell + apk for `wget` install; runner doesn't. This is canonical multi-stage pattern.

### D.7 Edge cases (минимум 8 — actually 11)

#### EC-L3-01: Base image digest-pin (rotation strategy)

**Scenario:** `node:22-alpine` tag (NOT digest-pinned). Tag content changes over time → reproducibility (C-03) breaks.

**Mitigation (deferred):** pin `node:22-alpine@sha256:abc...`. Trade-off: blocks easy minor updates. Mitigation для mitigation: Renovate auto-PR on new digest; merge after CI green.

**Status:** LOW gap, deferred to 999.18.4.

#### EC-L3-02: Reproducibility (SOURCE_DATE_EPOCH)

**Scenario:** `date -u > build-info.json` non-deterministic. Same build inputs → different bytes.

**Mitigation:** `SOURCE_DATE_EPOCH` env var per Reproducible Builds canon. Pass commit timestamp:

```dockerfile
ARG SOURCE_DATE_EPOCH
RUN date -u -d @${SOURCE_DATE_EPOCH} +%FT%TZ > build-info.json
```

**Status:** LOW gap, deferred.

#### EC-L3-03: `--chown` for non-root user

**Scenario:** distroless USER 65532:65532 reads files. Default `COPY` uses root ownership. Distroless reads OK (just needs read perm), но writes FAIL (no write perm).

**Mitigation:** `COPY --chown=65532:65532 ...` explicit per LAYER-ARCHITECTURE EC-18.

**Status:** LOW gap. Currently works because app reads only; doesn't write to filesystem (logs to stdout, state via DB/Redis/MinIO).

#### EC-L3-04: Image rebuild trigger (lockfile change, base image CVE)

**Scenario:** lockfile changes → all stages rebuild from Stage 1.2 onwards. Base image CVE → only base layer rebuild, downstream cached.

**Mitigation:** Renovate auto-PR on lockfile change; `cache-from/to: type=gha,scope=${matrix.service}` ensures cache hit when only `node_modules` rebuild needed.

#### EC-L3-05: Layer cache invalidation cascade

**Scenario:** small change to `apps/auth/src/main.ts` should NOT invalidate `pnpm install` layer.

**Mitigation:** Stage 1.2 + 1.3 install BEFORE source code COPY:

```dockerfile
COPY --from=pruner /app/out/json/ .       # Only json files (rare changes)
RUN pnpm install --frozen-lockfile         # Cached if json unchanged
COPY --from=pruner /app/out/full/ .         # Source code (frequent changes)
```

This is canonical Docker layer ordering rule [VERIFIED: docs.docker.com/build/cache/optimize/].

#### EC-L3-06: pnpm store path (PNPM_HOME D-08)

[CITED: from LAYER-ARCHITECTURE §H.3 EC-15]

**Scenario:** Cache mount target=/pnpm/store but pnpm writes to ~/.local/share/pnpm/store/v11 → 100% cache miss.

**Mitigation (D-08 RATIFIED):** `ENV PNPM_HOME=/pnpm` in install stages aligns store path с cache mount target.

#### EC-L3-07: node_modules vs pnpm hoisting

**Scenario:** pnpm uses content-addressable store + symlinks. `COPY --from=prod-deps /app/node_modules ./node_modules` copies symlinks → broken if store at different path in source vs target.

**Mitigation:** keep PNPM_HOME aligned across stages. Project verified working state via Iter 3 D-08 fix.

#### EC-L3-08: tini / signal forwarding (PID 1)

**Scenario:** Distroless `nodejs22-debian12` — no init system. Node.js as PID 1 → signals not forwarded gracefully on `docker stop` / K8s preStop.

**Mitigation:**

- Distroless `:nonroot` variant DOES include tini-equivalent (verify in actual image)
- OR explicitly use `gcr.io/distroless/nodejs22-debian12:nonroot` and rely on Node.js 16+ proper signal handling (`process.on('SIGTERM')`)

[ASSUMED — distroless nodejs SIGTERM handling status; not freshly verified — see §L]

#### EC-L3-09: BuildKit DAG-prune skips orphan stages

[CITED: from LAYER-ARCHITECTURE §H.3 EC-13, Iter 3 incident]

**Scenario:** Stage not referenced via `COPY --from=` → BuildKit silently drops it. Iter 3: orphan fetcher stage.

**Mitigation:** every stage MUST be reachable from final stage's COPY chain. After ratified two-install: Stage 1.1 → Stage 1.2 + Stage 1.3 → Stage 2. All stages reachable.

#### EC-L3-10: `apk add wget` reaches network — non-hermetic

[CITED: from LAYER-ARCHITECTURE §G.2]

**Mitigation:** preinstall в base image (separate hardening phase). LOW gap, deferred.

#### EC-L3-11: `pnpm dlx turbo prune` (network reach in pruner stage)

[CITED: from LAYER-ARCHITECTURE §G.2]

**Mitigation:** use turbo from devDependencies (already installed by L1) instead of dlx. Trade-off: adds turbo to pruner stage's needed deps. Workable.

**Status:** LOW gap, deferred.

#### E.2.3 Cache strategy

GitLab CI cache types:

- **Per-branch cache** — cached state per Git branch
- **Per-key cache** — explicit cache key (typically `${CI_COMMIT_REF_SLUG}-${SHA}` or similar)
- **Distributed cache** — S3-backed (если есть S3 bucket); makes parallel jobs share cache

**For our project:**

```yaml
cache:
  key: '$CI_COMMIT_REF_SLUG'
  paths:
    - node_modules/.pnpm-store/
    - .turbo/
```

This gives per-branch incremental builds. CI cold-builds first time per branch; warm thereafter.

### E.4 Kubernetes deployment patterns

#### E.4.1 Helm vs Kustomize vs Argo CD

| Tool          | What it does                                                     | Best for                                 | Project fit                                     |
| ------------- | ---------------------------------------------------------------- | ---------------------------------------- | ----------------------------------------------- |
| **Helm**      | Chart-based templating (values.yaml + templates/)                | Apps that need vendor packaging          | OK for project — but reusable chart per service |
| **Kustomize** | Pure YAML overlays (no templating)                               | Multi-env (dev/staging/prod) overlays    | Could work — simpler than Helm                  |
| **Argo CD**   | GitOps controller — declarative state в Git → cluster reconciles | Multi-env, multi-cluster, declarative    | **RECOMMENDED** for self-hosted at scale        |
| **Flux v2**   | GitOps controller — alternative to Argo CD                       | Kubernetes-native, stricter Helm support | Comparable to Argo CD                           |

[VERIFIED: WebFetch 2026-05-04 from https://argo-cd.readthedocs.io/en/stable/operator-manual/architecture/]

> "API Server: gRPC/REST server handling application management"
> "Repository Server: maintains local cache of the Git repository holding the application manifests"
> "Application Controller: continuously monitors running applications and compares the current, live state against the desired target state"

**Recommendation:** Argo CD or Flux v2 — DevOps choice, NOT project-locked. Either works with our architecture (image digest pushed by GitLab CI → Argo CD or Flux watches Git repo with K8s manifests → deploys).

#### E.4.2 GitOps workflow (canonical for Argo CD / Flux v2)

```
Developer push commit → GitLab CI → docker buildx build → push image to GitLab CR (digest)
                                                        ↓
                                       Update K8s manifests repo (image: digest)
                                                        ↓
                                       Argo CD / Flux detects manifest change → applies → cluster reconciles
                                                        ↓
                                       L5 verify suite runs against deployed digest → PASS/FAIL gate
```

Two repos pattern (canonical GitOps):

- **App repo** (this project) — code + Dockerfile + .gitlab-ci.yml
- **Manifests repo** — K8s YAML (Deployment, Service, ConfigMap, etc.)

CI updates manifests repo with new image digest → controller reconciles.

**Decoupling proof — does this preserve C-01 Substitutability?** Yes. App repo doesn't know about Argo CD vs Flux. CI just commits to manifests repo OR triggers webhook. DevOps zone owns mechanism.

#### E.4.3 Single repo alternative

Some teams keep manifests in same repo (in `k8s/` directory). Argo CD can watch sub-path of repo. Trade-off:

- Pro: single source of truth; PR review covers both code and manifests
- Con: app repo bloated with K8s details; merge conflicts between code MRs and ops MRs

**Project recommendation:** start with single repo (`k8s/` subdirectory), split if needed. Out of 999.18.3 scope (DevOps ownership).

### E.8 Edge cases (минимум 8 — actually 10)

#### EC-L4-01: Rollback drill (RTO targets)

**Scenario:** prod deploy goes bad. How fast can we revert?

**Mechanism:** image digest immutable (per L3 + 12-Factor V) → `kubectl set image deployment/${APP} ${APP}=${REGISTRY}/${APP}@sha256:${PRIOR_DIGEST}` → rollback in seconds.

**Argo Rollouts:** automated rollback on alarm (per AWS canon ECP-04, Argo Rollouts Analysis).

**RTO target:** 5 min for mid-scale projects. Project-internal — discussed with DevOps.

#### EC-L4-02: Observability hand-off

**Scenario:** L4 deploys image; L5 verifies behavior. Beyond L5: long-term observability (metrics / traces / logs).

**Mechanism:** Grafana + Prometheus + OpenTelemetry — out of 999.18.3 scope. **Boundary:** L5 verifies fitness-for-deploy (binary PASS/FAIL); production observability is run-stage concern.

#### EC-L4-03: Multi-env promotion (dev → staging → prod)

**Scenario:** image ${SHA} deployed to dev. Promote to staging. Promote to prod.

**Mechanism (canonical):** same image digest promoted across envs. Different K8s namespaces / clusters / config. **Image NEVER rebuilt for staging/prod** — preserves 12-Factor V "release = build + config".

**GitLab CI mechanism:** trigger promotion job на manual approval; uses `${PRIOR_BUILD_DIGEST}` env var.

#### EC-L4-04: DB migration ordering vs deploy

**Scenario:** new release requires DB schema change. Migrate before или after deploy?

**Mechanism (canonical):**

1. Migration step backwards-compatible (add column, не drop)
2. Deploy new code (uses both old + new schema)
3. Drop old schema in NEXT release after old code retired

OR: K8s Job runs migration as pre-deploy step; deploy waits на job completion (initContainer pattern).

**Project applicability:** out of 999.18.3 scope. Deferred until first migration arrives.

#### EC-L4-05: Zero-downtime deploy

**Scenario:** in-flight requests at deploy moment. Old pod gets SIGTERM; new pod starts.

**Mechanism:**

- K8s readiness probe — new pod не routes traffic until ready
- preStop hook — old pod drains in-flight requests
- `terminationGracePeriodSeconds: 30` — gives time для drain
- distroless нужен правильный signal forwarding (см. EC-L3-08)

**Project status:** partially addressed. Health probes exist (`/health/ready`); preStop hook NOT YET; terminationGracePeriodSeconds default. **Hardening item для 999.18.4 ops phase.**

#### EC-L4-06: Failover strategy

**Scenario:** prod cluster failure. Where does traffic go?

**Mechanism:** Multi-region K8s clusters; DNS or load balancer routing. **Out of 999.18.3 scope** — DevOps single-region currently.

#### EC-L4-07: Incident response integration (PagerDuty / Opsgenie)

**Scenario:** L4 deploy fails. How is on-call notified?

**Mechanism:** GitLab CI job failure → webhook to PagerDuty / Opsgenie → page. Out of 999.18.3 scope.

#### EC-L4-08: Chaos engineering hooks

**Scenario:** does our system survive failure? Chaos Mesh / Litmus inject failures.

**Boundary с L5:** L5 verifies "deploy worked"; chaos engineering verifies "system survives failures". Different concerns. Out of 999.18.3 scope; mentioned для completeness.

#### EC-L4-09: Concurrent push to multiple branches

[CITED: from LAYER-ARCHITECTURE §H.4 EC-24]

**Scenario:** push to dev + main same SHA → two builds for same SHA.

**Mitigation:** `concurrency: docker-${ref}` cancels previous of same ref but не cross-ref. Acceptable.

#### EC-L4-10: Required pipeline drift

**Scenario:** Phase 999.17 added 8 security:\* jobs. Plan 08 wires them up. Six months later, Phase 999.18 adds new check. Required-jobs config (GitLab branch protection) drifts.

**Mitigation:** required-jobs list in code (`.gitlab-ci.yml` `rules:`) + branch protection config (GitLab UI / API). **Two sources of truth** — drift risk.

**Hardening:** GitLab `required:` keyword in pipeline jobs (since GitLab 14+) — single source of truth. Project plan: use `rules:` + `interruptible: true` to ensure only required jobs gate merge.

### F.8 Edge cases (минимум 6 — actually 8)

#### EC-L5-01: Gate timeouts

**Scenario:** verify scripts timeout. Was service slow или dead?

**Mitigation:**

- Each verify script must have explicit timeout (e.g., `timeout 60 curl /health/ready`)
- Differentiate "slow boot" (retry с exponential backoff) vs "dead" (immediate fail)
- Per `runtime-smoke-verification` skill — health probe boot retry pattern

#### EC-L5-02: False positives (flaky tests)

**Scenario:** `verify-multiarch-manifests.sh` queries registry — transient registry latency → false fail.

**Mitigation:** retry с backoff. Maximum N retries (e.g., 3) before declaring fail.

#### EC-L5-03: Partial deploy state

**Scenario:** K8s rolling update — pods 1-3 new version (green), pods 4-6 old (still updating). At what point is verify supposed to run?

**Mitigation:** verify runs ONLY after `kubectl rollout status` returns success (all pods updated, ready). Per `runtime-smoke-verification` skill.

#### EC-L5-04: Long-running migrations vs probe timing

**Scenario:** new release runs DB migration on startup. Probe times out before migration completes.

**Mitigation:**

- Migrations as separate K8s Job (initContainer or pre-deploy job) → app starts already-migrated
- OR: increase probe `initialDelaySeconds` для known long migrations
- OR: separate `/health/startup` probe с longer timeout

#### EC-L5-05: Multi-region verification ordering

**Scenario:** deploy to us-east first, then eu-west, then ap-south. Each region has own verify gate.

**Mitigation:** GitLab CI sequential jobs per region; each region's verify must PASS before next region deploy. AWS canonical "blast radius" pattern.

**Project status:** single region currently; out of 999.18.3 scope.

#### EC-L5-06: Synthetic monitoring

**Scenario:** beyond build-stage verify, run-time external probes (StatusCake / Pingdom / custom prober) check from outside.

**Mitigation:** runs continuously; alerts on regression. Different concern from L5 (build-stage gate). Out of 999.18.3 scope.

#### EC-L5-07: Verifier dependencies on L1 shell tools

[CITED: from LAYER-ARCHITECTURE §H.5 EC-42]

**Scenario:** `bash` not in distroless runner. Smoke gate using `wget` from inside container fails.

**Mitigation:** smoke gates run from HOST (CI runner / dev host) against running container, NOT inside container. **Status: correct** — verify scripts already run from host context.

#### EC-L5-08: Verifier suite leak (compose containers)

[CITED: from LAYER-ARCHITECTURE §H.5 EC-37]

**Scenario:** smoke verify spins up compose. On FAIL, compose containers leak (not stopped).

**Mitigation:** `trap cleanup EXIT` в bash scripts. Ensures stop:\* runs even on failure.

### L.2 — Surfaced Tensions (architecture противоречит чему-то — назвать честно)

#### T-01: Pragmatic accept of Turborepo (vs Bazel/Buck2 hermeticity)

**Tension:** §G.2 of LAYER-ARCHITECTURE acknowledges «L2 hermeticity PARTIAL vs HIGH». §C.6 here scores L2 PARTIAL. **MAANG canon (Google, Meta) chooses Bazel/Buck2 for HIGH hermeticity.** Our project chooses Turborepo for ergonomics at small scale.

**Honest framing:** this is a trade-off, not principled superiority of either. Cost (Bazel onboarding) at our N=1-engineer scale exceeds benefit (HIGH hermeticity unused at N=6 services). **We're explicitly accepting LESS hermetic L2 in exchange for LESS cognitive load.** Not «MAANG pattern»; it's «optimized для our scale».

**Resolution:** documented в §G.2 LAYER-ARCH «Pragmatic Coupling». RE-EVAL-TRIGGERS at §C.4 here document when to revisit. Tension acknowledged, not concealed.

#### T-02: GitHub Actions current state vs GitLab CI target

**Tension:** ratified architecture says «L4 = GitLab CI → Kubernetes». Project current state uses GitHub Actions + Coolify (but Coolify deprecated 2026-04-30). **Gap between ratified and current.**

**Honest framing:** ratified architecture is target. Current state is intermediate. Plan 08 wires L5 to current L4 (`.github/workflows/`). Migration to GitLab is dedicated future activity (per `project_gitlab_migration` memory).

**Resolution:** L4 substitutability rule («workflow invokes only `pnpm <script>` + `docker buildx`») IS the bridge — current GitHub Actions follows rule, future GitLab CI will follow same rule. Migration is bounded one-time cost, not architectural rework.

#### T-03: 12-Factor «Run stage minimal» vs distroless 50 MiB

**Tension:** 12-Factor V says «run stage should be kept to as few moving parts as possible». Distroless `nodejs22-debian12` is ~50 MiB (includes Node runtime + minimal Debian). MAANG-aligned alternative: `distroless/static` (~2 MiB) for Go binaries. NOT applicable to Node.js (which needs runtime).

**Honest framing:** distroless 50 MiB is **as minimal as possible для Node.js runtime**. Trade-off with Node.js choice is on Node, not on distroless. Bun / Deno alternatives could reduce runtime size, но это language change, not architecture change.

**Resolution:** accepted. Distroless is canonical at Node.js level. If runtime-size critical (it's not at our scale), evaluate Bun/Deno migration as separate axis.
