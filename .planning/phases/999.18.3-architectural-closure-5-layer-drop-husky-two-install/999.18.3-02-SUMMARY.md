## Root Cause Analysis (Empirical)

### Investigation Steps

1. **Task 1 attempt #1** (clean-state, no prior buildx cache modification):
   - Command: `pnpm verify:injection-extinct auth`
   - Result: FAIL cycle 1 at Stage 1.2 installer step
   - Error: `ERR_PNPM_NO_OFFLINE_TARBALL: A package is missing from the store but cannot download it in offline mode. The missing package may be downloaded from https://registry.npmjs.org/@typescript-eslint/eslint-plugin/-/eslint-plugin-8.59.1.tgz`
   - Hypothesis: stale buildx cache from pre-Wave-1 builds (Wave 1 Dockerfile fix needs fresh fetcher cache to populate full dep tree)

2. **Cache housekeeping (Rule 3 auto-fix attempt)**:
   - Action: `docker buildx prune -af` → reclaimed 797.9MB cache
   - Justification: Task 2 already mandates this; same `id=pnpm-fetch` cache mount shared across all verifier scripts; pre-Wave-1 contamination plausible hypothesis

3. **Task 1 attempt #2** (post-cache-clear):
   - Same command, same exit code 1, **same exact error message** at Stage 1.2 installer step
   - Hypothesis falsified: cache state is NOT the cause

4. **Direct fetcher cache probe** (synthetic Dockerfile mirroring Stage 1.1.5 fetcher):
   - Replicated `RUN --mount=type=cache,id=test-pnpm-fetch,target=/pnpm/store pnpm fetch`
   - Empirical result: `pnpm fetch` reported "Progress: resolved 673, reused 0, downloaded 673, added 673, done"
   - **`ls -la /pnpm/store/` returned `total 0` (empty) immediately after `pnpm fetch` reported success**
   - **`find /pnpm/store -type f` returned no files**

5. **pnpm 11 store-dir verification** (host node:22-alpine, identical к Dockerfile base):
   - Synthetic project + `pnpm install` from registry
   - `pnpm store path` → returns **`/root/.local/share/pnpm/store/v11`**
   - `ls /root/.local/share/pnpm/store/v11/` shows populated store post-install
   - `pnpm config get store-dir` returns `undefined` (lazy-resolved at runtime)

### Confirmed Root Cause

**pnpm 11 default store-dir is `/root/.local/share/pnpm/store/v11`, NOT `/pnpm/store`.** Dockerfile cache mounts use `target=/pnpm/store`, but pnpm ignores this location and writes to its xdg-defaults path. Cache mounts thus persist **empty volumes** на disk без impact на pnpm operations:

- Stage 1.1.5 fetcher: `pnpm fetch` writes to `/root/.local/share/pnpm/store/v11/` (which is **NOT** mounted as a buildx cache; lives only inside the fetcher stage filesystem layer; not preserved across stages or builds).
- Stage 1.2 installer: `pnpm install --offline --frozen-lockfile` ищет store при `/root/.local/share/pnpm/store/v11/` — НЕ существует в installer stage filesystem (different stage, different layers). Pnpm's `--offline` flag prevents network fallback. Result: `ERR_PNPM_NO_OFFLINE_TARBALL` for first dep that needs resolving (alphabetically: `@typescript-eslint/eslint-plugin`).

### Why CONTEXT D-01 Variant 2 Fix Was Insufficient

CONTEXT D-01 hypothesized scope mismatch = «`pnpm fetch --prod` cached only prod deps, but installer needs full set including devDeps for builder». Variant 2 fix:

- Drop `--prod` from fetcher → fetch full set ✅ (correct intent, but works only IF store path matches between stages)
- Add `pnpm prune --prod` post-build in builder stage ✅ (correct intent, NO impact on the install→build chain)

**CONTEXT D-01 missed an underlying fact:** the cache-mount **target** path does not match pnpm's default store-dir. Even with `pnpm fetch` (no `--prod`) writing to its actual default store-dir, that store doesn't survive across multi-stage Docker boundaries because the buildx cache mount target (`/pnpm/store`) doesn't intercept pnpm's I/O. Variant 2 fixes a label-level concern (full vs prod set), not the actual cross-stage caching mechanism.

This was **also true under 999.18.2 Wave 2 baseline** (`pnpm fetch --prod`): the prod-only cache mount also wrote nowhere useful. The reason 999.18.2 Wave 4 also failed is the same. Wave 1 amendments don't change this — they address a different (and orthogonal) concern.

### Architectural Decision Needed (Rule 4)

Three plausible paths forward — **user input required, not in scope of Plan 02**:

**Option A: Align cache mount target with pnpm 11 default store-dir.**

- Change cache mount from `target=/pnpm/store` to `target=/root/.local/share/pnpm/store/v11` in fetcher (Stage 1.1.5) AND installer (Stage 1.2 — both `pnpm-install` and `pnpm-fetch` ro mount).
- Minimal-surface fix, preserves intent of M3 sub-pattern.
- Cost: pnpm version bump may change `v11` → `v12` etc., requires Dockerfile maintenance.

**Option B: Pin pnpm store-dir к /pnpm/store explicitly.**

- Add `--store-dir=/pnpm/store` to `pnpm fetch` AND `pnpm install` invocations, OR set `store-dir=/pnpm/store` в .npmrc, OR `ENV PNPM_HOME=/pnpm` + companion config.
- Removes pnpm-version coupling.
- Cost: extra Dockerfile/.npmrc directive; .npmrc impact на host dev environment requires verification.

**Option C: Re-examine M3 mechanism — switch к O-07 Variant 1 Turborepo two-install.**

- Reject Variant 2 sub-pattern, adopt rejected Variant 1 (recorded в ADR-001 §Alternatives O-07).
- Two-install pattern не relies on offline cache surviving across stages — каждая install gets its own fetch-then-install cycle within a single stage.
- Cost: full sub-phase rework (CONTEXT amendment, 999.18.3-01 plan rewrite, ADR amendment); supersedes 999.18.3 Wave 1 work.
