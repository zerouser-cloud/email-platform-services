# Phase 999.18.3: Code Review Report

**Reviewed:** 2026-05-05
**Depth:** standard
**Files Reviewed:** 19
**Status:** issues_found

## Summary

Фаза закрывает 5-уровневую архитектуру (drop husky + two-install Dockerfile + L4 GitLab CI + L5 K8s). L1 (githooks) и L3 (Dockerfile) выглядят сделаны корректно. **Однако L4 (`.gitlab-ci.yml`) и L5 (`deploy/k8s/`) содержат серию блокирующих дефектов, которые гарантированно ломают пайплайн на стадиях `verify` + `deploy`.**

Самые серьёзные проблемы:

1. **Image registry mismatch** между CI (`$CI_REGISTRY_IMAGE/...`) и Kustomize overlays (`registry.example.com/...`) — `kubectl apply -k` не подтянет свежесобранные образы; pods будут крашиться (`ImagePullBackOff`).
2. **`bitnami/kubectl:1.30` основан на Debian, а не Alpine** — `apk add` в `before_script` обоих deploy jobs упадёт сразу с `apk: command not found`.
3. **`scripts/verify-k8s-rollout.sh` требует `KUBE_NAMESPACE`**, но deploy jobs его не пробрасывают → exit 1 с "namespace required".
4. **Несколько `verify-*` jobs либо запускаются в окружении без нужных бинарей (docker/pnpm) и тихо `exit 0` через SKIP-guard**, либо вызываются без обязательных аргументов (`verify:multiarch`), что превращает `allow_failure: false` в фикцию.
5. **`deploy/k8s/` ссылается на `email-platform-config`/`email-platform-secrets`**, которых в репозитории нет ни как Kustomize-ресурсов, ни как генераторов → каждый pod будет крашиться при старте на Zod env-validation.
6. **`scripts/verify-per-service-smoke.sh:67`** — `docker run | head -5` со `set -o pipefail` сломан логически: для долгоживущего NestJS-сервера job либо повиснет навсегда, либо упадёт по SIGPIPE; при «нормальной» работе зелёного результата не будет.

L1/L3 (hooks + Dockerfile) к merge готовы; L4/L5 в текущем виде ломают каждый dev/prod deploy и должны быть переработаны до того, как ветка пойдёт в main.

## Critical Issues

### CR-01: Image registry mismatch — Kustomize overlays никогда не подхватят CI-образы

**File:** `.gitlab-ci.yml:113-114` + `deploy/k8s/overlays/dev/kustomization.yaml:10-21` + `deploy/k8s/overlays/prod/kustomization.yaml:10-21`
**Issue:** В CI `build` stage образы тегаются как `$CI_REGISTRY_IMAGE/email-platform-$SERVICE:$CI_COMMIT_SHORT_SHA`. В Kustomize overlays (dev/prod) `images:` секция перечисляет `registry.example.com/email-platform-<svc>` с `newTag: latest`. Комментарий «CI replaces with `$CI_COMMIT_SHORT_SHA` via `kustomize edit set image`» намекает, что это должен делать CI — но в `.gitlab-ci.yml` нет ни одного вызова `kustomize edit set image`. Deploy-job делает `kubectl apply -k`, который применяет манифесты как есть с `latest` + неверным registry. K8s попытается тянуть `registry.example.com/email-platform-gateway:latest` (домен-заглушка) → `ImagePullBackOff` для всех 6 сервисов на каждом deploy.

**Fix:** Либо переписать base/overlays на реальный registry, либо добавить шаг `kustomize edit set image` в deploy-jobs:

```yaml
deploy-dev:
  script:
    - cd deploy/k8s/overlays/dev
    - for svc in gateway auth sender parser audience notifier; do
        kustomize edit set image registry.example.com/email-platform-$svc=$CI_REGISTRY_IMAGE/email-platform-$svc:$CI_COMMIT_SHORT_SHA;
      done
    - cd -
    - kubectl apply -k deploy/k8s/overlays/dev/
    - KUBE_NAMESPACE=email-platform-dev pnpm verify:k8s-rollout
```

(плюс в base заменить `registry.example.com/...` на реальный registry или оставить как «alias» специально для `kustomize edit set image`).

### CR-02: `bitnami/kubectl:1.30` — Debian, не Alpine; `apk add` в before_script упадёт

**File:** `.gitlab-ci.yml:236-238, 250-253`
**Issue:** Образ `bitnami/kubectl:1.30` (Bitnami images) построен на `debian-12` / `minideb`, не на Alpine. Команда `apk add --no-cache bash` (deploy-dev) и `apk add --no-cache bash nodejs npm` (deploy-prod) упадёт с `/bin/sh: apk: not found` или подобным сразу же. Оба deploy job с `allow_failure: false` будут падать на каждом запуске.
**Fix:** Заменить `apk add` на `apt-get` или вообще выбросить (bash в bitnami/kubectl уже есть, отдельно ставить не надо). Для prod, где нужен pnpm — это уже отдельный архитектурный вопрос (см. CR-03), скорее всего стоит сделать отдельный кастомный CI-образ или вынести `verify:k8s-rollout` в отдельный job на `node:22-alpine` после деплоя.

```yaml
deploy-dev:
  image: bitnami/kubectl:1.30
  # before_script: УДАЛИТЬ — bash уже в образе
  script:
    - cd deploy/k8s/overlays/dev && <kustomize edit set image ...> && cd -
    - kubectl apply -k deploy/k8s/overlays/dev/
    - KUBE_NAMESPACE=email-platform-dev bash scripts/verify-k8s-rollout.sh
```

### CR-03: `pnpm verify:k8s-rollout` в deploy-dev вообще не выполнится — pnpm не установлен

**File:** `.gitlab-ci.yml:237-241`
**Issue:** `deploy-dev` job использует `bitnami/kubectl:1.30` и в `before_script` ставит только `bash` (через сломанный `apk` — см. CR-02). Затем вызывает `pnpm verify:k8s-rollout`. ```

Никакого pnpm/node в deploy-job не требуется — `verify-k8s-rollout.sh` всё делает через `kubectl`.

### CR-04: `verify-k8s-rollout.sh` требует `KUBE_NAMESPACE`, deploy-jobs его не выставляют

**File:** `scripts/verify-k8s-rollout.sh:9-13` + `.gitlab-ci.yml:241, 256`
**Issue:** Скрипт начинается с

NAMESPACE="${KUBE_NAMESPACE:-${1:-}}"

deploy-dev:

    KUBE_NAMESPACE: email-platform-dev

    - kubectl apply -k deploy/k8s/overlays/dev/

(плюс убрать `pnpm` префикс — см. CR-03).

### CR-05: ConfigMap `email-platform-config` и Secret `email-platform-secrets` нигде не определены

**File:** все `deploy/k8s/base/*.yaml` (auth:31-34, audience:31-34, gateway:31-34, parser:31-34, sender:31-34, notifier:27-30)
**Issue:** Все 6 Deployment'ов делают `envFrom: configMapRef: name: email-platform-config` + `secretRef: name: email-platform-secrets`. Этих ресурсов нет ни в `deploy/k8s/base/`, ни в overlays, ни в виде `configMapGenerator`/`secretGenerator` в kustomization. На применении (`kubectl apply -k`) NestJS-приложения стартуют без env, проваливают Zod-валидацию (`@email-platform/config` запрещает defaults и optionals — см. CLAUDE.md «No defaults or optionals in env schemas»), и pods входят в CrashLoopBackOff. `verify-k8s-rollout.sh` ловит это таймаутом 300s → exit 1 → CI красный. Без определения этих ресурсов deploy физически не может работать.

K8s **не валидирует** наличие ConfigMap/Secret на момент `apply` — он валидирует на момент `pod scheduling`. То есть `kubectl apply -k` пройдёт, но подa никогда не станут Ready.

**Fix:** Добавить `configMapGenerator` + `secretGenerator` в overlay (или внешний sealed-secret/external-secret manager); как минимум, описать это в DEVOPS-HANDOFF.md как обязательное предусловие deploy:

```yaml
# deploy/k8s/overlays/dev/kustomization.yaml
configMapGenerator:
  - name: email-platform-config
    envs: [.env.k8s.dev]
secretGenerator:
  - name: email-platform-secrets
    envs: [.env.k8s.dev.secrets]   # mount via SOPS/sealed-secrets, не commit cleartext
```

И/или: эти ресурсы шипуются другой командой (helmfile, sealed-secrets controller, vault-injector) — тогда явно задокументировать «pre-deploy contract» в DEVOPS-HANDOFF.md и упомянуть, что без них `verify-k8s-rollout` сломается.

### CR-06: `verify-injection-extinct` — silently disabled в CI (no docker → exit 0)

**File:** `.gitlab-ci.yml:191-201` + `scripts/verify-injection-extinct.sh:25-32`
**Issue:** Job задан с `image: node:22-alpine` (без `services: [docker:24-dind]`), но скрипт делает `docker buildx build` 5 раз. У скрипта guard:

```bash
if ! command -v docker >/dev/null 2>&1; then
  echo -e "${YELLOW}  SKIP${NC}: docker CLI not found; verifier requires Docker."
  exit 0
fi
```

В `node:22-alpine` нет `docker` CLI → SKIP → `exit 0` → job зелёный. **`allow_failure: false` ничего не блокирует**, потому что guard превращает любой запуск в success. Это quality gate, который выглядит работающим, но никогда не фейлит на регрессиях. Skill `runtime-smoke-verification` в проекте требует, чтобы такие verifiers именно блокировали merge.

**Fix:** Либо заменить образ на `docker:24` + `services: [docker:24-dind]` (как в `verify-image-determinism`), либо превратить SKIP в FAIL в CI-окружении:

```yaml
verify-injection-extinct:
  stage: verify
  image: docker:24
  services:
    - docker:24-dind
  before_script:
    - apk add --no-cache bash nodejs npm
    - corepack enable && corepack prepare pnpm@11.0.0 --activate
    - pnpm install --frozen-lockfile
  script:
    - pnpm verify:injection-extinct
```

Альтернатива — в скрипте: если выставлен `CI=true` (GitLab автоматически выставляет), то SKIP должен превращаться в FAIL.

### CR-07: `verify-multiarch` — нет docker_dind, нет pnpm, нет обязательного аргумента → 100% fail

**File:** `.gitlab-ci.yml:203-214` + `scripts/verify-multiarch-manifests.sh:31`
**Issue:** Тройной баг в одном job:
1. `image: docker:24` без `services: [docker:24-dind]` — `docker buildx imagetools inspect` упадёт с «Cannot connect to the Docker daemon».
2. `before_script` ставит только `bash` — нет `pnpm`, нет corepack. `pnpm verify:multiarch` упадёт с `pnpm: command not found`.
3. Скрипт требует первый аргумент `IMAGE`:
   ```bash
   IMAGE="${1:?usage: pnpm verify:multiarch <full-image-ref> ...}"
   ```
   В CI вызов `pnpm verify:multiarch` без аргумента → `${1:?...}` exit 1.

Любого из трёх достаточно, чтобы job падал каждый запуск. `allow_failure: false` → каждый main-pipeline красный.

**Fix:**

```yaml
verify-multiarch:

  services:
    - docker:24-dind

```

(вызов без pnpm; передан реальный image-ref; добавлен dind для docker-доступа).

### CR-08: `verify-per-service-smoke.sh:67` — `docker run | head -5` структурно ломан для NestJS-сервера

**File:** `scripts/verify-per-service-smoke.sh:65-71`
**Issue:** Логика:
```bash
if docker run --rm --entrypoint node "smoke-test:$SVC" -e "require('./dist/main.js')" 2>&1 | head -5; then
  pass "$SVC smoke OK (require() succeeded)"
else
  fail "$SVC smoke FAILED (require() error)"
fi
```

Под `set -euo pipefail` exit-код пайплайна = последний non-zero exit. Сценарии:

- **NestJS bootstrap успешен → стартует HTTP/gRPC сервер → процесс висит вечно** (NestJS keeps event loop alive после `app.listen()`). Если приложение печатает ≥5 строк лога (а Pino + nestjs-pino + ClsModule стартовые логи это легко), `head -5` закроет stdin → `docker run` получает SIGPIPE → exit 141 → pipefail → ветка `else` → **fail-репорт на работающем приложении**.
- **NestJS bootstrap печатает <5 строк** → `head -5` ждёт EOF → `docker run` висит вечно → CI job висит до общего таймаута runner'а (часы), `allow_failure: false` ⇒ фактически блокирует pipeline.
- **NestJS падает на старте** → ошибка может полностью пройти через `head -5` (если короткая) → `docker run` exit non-zero → fail. Только этот сценарий работает «как задумано», и то случайно.

Комментарий в скрипте («NestJS bootstrap is async — process completes/keeps running depending on listeners») явно показывает, что автор не учёл, что для server-приложения процесс **всегда** будет «keep running». Smoke-test, который при зелёной ситуации даёт fail (или вис), бесполезен.

**Fix:** Структурный smoke должен запускать процесс с явным таймаутом и ловить exit-код:

```bash
# Use `--init` + timeout — kill the container after N seconds, treat
# 0 (clean exit) and 124/137 (killed by timeout — process kept running)
# as success; anything else = require() / startup error.
set +e
output=$(timeout --preserve-status 5 docker run --rm --entrypoint node "smoke-test:$SVC" -e "require('./dist/main.js')" 2>&1)
rc=$?
set -e
echo "$output" | head -20
case "$rc" in
  0|124|137|143)  pass "$SVC smoke OK (require() loaded; process exited or hit timeout)" ;;
  *)              fail "$SVC smoke FAILED (rc=$rc — require() / bootstrap error)" ;;
esac
```

Или: сборка stage заменить на `docker run --rm` команды `node -e "Promise.resolve().then(() => require('./dist/main.js'))"` с `timeout 10s`, который гарантированно exit'ает и не зависит от `head -5`.

## Warnings

### WR-01: K8s containers — отсутствует Pod Security Standards baseline

**File:** все `deploy/k8s/base/*.yaml`
**Issue:** Pod-уровневый `securityContext` задан (`runAsNonRoot`, `runAsUser: 65532`, `fsGroup`) — корректно для distroless-runner. Но container-уровневый `securityContext` отсутствует целиком: нет `allowPrivilegeEscalation: false`, нет `readOnlyRootFilesystem: true`, нет `capabilities: drop: ["ALL"]`, нет `seccompProfile: type: RuntimeDefault`. K8s «restricted» Pod Security Standard (PSS) этого требует. Trivy `config` (`container-config` job в `.gitlab-ci.yml`) на это сработает HIGH/CRITICAL и заблокирует MR — что хорошо в долгосрочной перспективе, но прямо сейчас означает, что pipeline не сможет пройти даже до deploy stage.
**Fix:** Добавить container-уровневый securityContext каждому контейнеру:

```yaml
containers:
  - name: gateway
    image: ...
    securityContext:
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
      capabilities:
        drop: ["ALL"]
      seccompProfile:
        type: RuntimeDefault
```

(distroless образы запускают node read-only; для NestJS возможно потребуется `emptyDir` volume для `/tmp` если Pino пишет лог-буферы).

### WR-02: `commonLabels` в base/kustomization — selector immutability риск

**File:** `deploy/k8s/base/kustomization.yaml:12-14`
**Issue:** `commonLabels` (Kustomize <5) или `labels` с `includeSelectors: true` (Kustomize 5+) добавляет labels не только в pod-template, но и в **selectors**. Если в будущем понадобится добавить ещё один common-label (например `app.kubernetes.io/version`), kubectl apply упадёт на selector-immutability — потребуется `kubectl delete deployment/...` + переcreate, что прерывает rollout. Best-practice — использовать `labels: [{pairs: ..., includeSelectors: false}]` для общих label'ов, и явный `selector` оставить под контролем base-манифестов.
**Fix:**

```yaml
labels:
  - pairs:
      app.kubernetes.io/part-of: email-platform
      app.kubernetes.io/managed-by: gitlab-ci
    includeSelectors: false
```

(Kustomize ≥5; в 4.x использовать `commonLabels` плюс зафиксировать инвариант, что эти 2 label'а никогда не меняются).

### WR-03: Notifier — нет ни readiness, ни liveness probe; миф «K8s default = process exit»

**File:** `deploy/k8s/base/notifier.yaml:31-32`
**Issue:** Комментарий «K8s default liveness = process exit; sufficient for RMQ consumer pattern» содержит миф. У K8s **нет** «default liveness probe». K8s рестартует container только когда главный процесс exit'ит (через kubelet container-runtime watch). Если RMQ-consumer повисает в дедлоке (lost connection без auto-reconnect, infinite reconnect-loop без backoff, вечный poll без сообщений), процесс не exit'ит → kubelet не рестартует → consumer молча мёртв. Для RMQ-consumer pattern идиоматический probe — TCP-check на heartbeat-port или exec-probe `rabbitmq-management-cli list_consumers | grep <queue>`.
**Fix:** Добавить хотя бы liveness-probe со стороны RMQ-клиента (например, exposing `/health/live` маленьким HTTP-сервером в notifier, который читает «last-heartbeat» из in-memory переменной и возвращает 503 если >60s без активности). Альтернатива — exec-probe в pod через `wget`/`curl`/`grpc_health_probe` (если notifier inhouse-добавит health-endpoint).

### WR-06: pnpm-lock.yaml — частичный rebuild через `pnpm install --frozen-lockfile` в каждом job

**File:** `.gitlab-ci.yml:46, 58, 78, 101, 184, 224`
**Issue:** Каждый из 6 жобов делает свою копию `pnpm install --frozen-lockfile` без shared cache. На GitLab CI этот шаг занимает 30-90s (зависит от runner image cache). Идиоматичное решение — `cache:` на `node_modules`/.pnpm-store, или один общий job (`prepare:deps`) → артефакт `node_modules.tar.gz` → consume в downstream'ах через `dependencies:`. Текущая схема сделает каждый MR-pipeline ≥6x медленнее, чем нужно. Не блокер для корректности, но drift c FR-12+ acceptance criteria («fast feedback loop») если такая цель была.
**Fix:** Добавить `cache:` ключ:

```yaml
.pnpm_cache: &pnpm_cache
  cache:
    key:
      files: [pnpm-lock.yaml]
    paths:
      - .pnpm-store/
      - node_modules/

env-parity:
  <<: *pnpm_cache
  image: node:22-alpine
  before_script:
    - corepack enable && corepack prepare pnpm@11.0.0 --activate
    - pnpm config set store-dir .pnpm-store
    - pnpm install --frozen-lockfile
  ...
```

### WR-07: `verify-image-determinism.sh` — `git checkout "$SHA"` на CI обычно ломает HEAD

**File:** `scripts/verify-image-determinism.sh:36, 55, 44`
**Issue:** В GitLab CI default checkout — detached HEAD на конкретный commit; `git symbolic-ref --short HEAD` падает, fallback на `git rev-parse HEAD` возвращает SHA. Затем скрипт делает `git checkout "$SHA"` (по умолчанию `SHA=HEAD`) — операция почти no-op, но если CI настроен с shallow clone (`GIT_DEPTH=20`), для произвольного `$SHA` за пределами глубины это `error: pathspec '...' did not match any file(s)`. Cleanup'ом через trap делается `git checkout "$ORIGINAL_REF"`, но если первый checkout упал, оригинальный ref всё равно пересобран. Не блокер для default-вызова `pnpm verify:image-determinism` (без аргументов), но subtle pitfall если кто-то передаст `git tag`/`branch` в CI.
**Fix:** Не делать `git checkout` если `$SHA == HEAD`:

```bash
if [ "$SHA" != "HEAD" ] && [ "$(git rev-parse HEAD)" != "$(git rev-parse "$SHA")" ]; then
  git checkout "$SHA"
fi
```

И добавить `--depth=...` increase или `git fetch --unshallow` если SHA не разрешим в shallow-клоне.

### WR-08: `pnpm-lock.yaml` определён `lockfileVersion: '9.0'`, package.json требует pnpm ≥11

**File:** `package.json:60-64` + `pnpm-lock.yaml:1`
**Issue:** `engines.pnpm: ">=11.0.0"` + `packageManager: pnpm@11.0.0` + lockfileVersion `9.0`. Это **технически валидно** (pnpm 11 читает lockfileVersion 9 без миграции), но создаёт неоднозначность: контрибьютор с pnpm 8/9/10 успешно делает `pnpm install --frozen-lockfile` локально (lockfileVersion 9 совместим с pnpm ≥9), но CI при этом запускает pnpm 11 и может выявить subtle разницы в hoisting / peer-dependencies resolution. Если `engines-strict=true` нет в `.npmrc`, `engines` это soft-requirement.
**Fix:** Либо `engines-strict=true` в `.npmrc`, либо upgrade lockfile через `pnpm install` под pnpm 11 → lockfileVersion bump (что 11.0 теоретически делает автоматически, если только не закреплён `--prefer-frozen-lockfile`). Низкий приоритет, но pnpm 7068 / Phase 999.18.x контекст показал, что pnpm-version-mismatch уже был источник тяжёлых багов в этой кодовой базе.

### WR-09: README.md / CONTRIBUTING.md — `pnpm setup-hooks` не в `prepare` хуке, легко пропустить

**File:** `package.json:6-47` + `README.md:7-17` + `CONTRIBUTING.md:5-13`
**Issue:** Phase явно отказался от husky / `prepare`-script gating (FR-03; см. memory `feedback_phase_completeness` + 999.18.3 ADR Iteration 7). Вместо этого хук-инсталляция выведена в ручной `pnpm setup-hooks`. Плюсы: нет pnpm injection-debt. Минусы: новый контрибьютор делает только `pnpm install` (стандартный workflow в ~95% монорепозиториев), забывает `setup-hooks`, локально пушит без gates, упирается в CI failures. README/CONTRIBUTING это упоминают, но dev на автопилоте не читает их. Project-level fallback — **server-side enforcement через GitLab branch protection** (DEVOPS-HANDOFF.md §«Branch protection» это документирует) — но до миграции на GitLab self-hosted (memory `project_gitlab_migration`) этого нет в текущем GitHub-окружении проекта.
**Fix:** Один из двух подходов (или оба):
1. Добавить `postinstall` script, который проверяет `git config core.hooksPath` и печатает yellow warning если не выставлен, **без** автоматической установки (т.е. без husky-style auto-install — это сохраняет FR-03 invariant). Декоративный, но видимый.
2. В CI (даже на GitHub Actions параллельно) — required-check «security-fast» уже выполняется server-side; обозначить это явно в CONTRIBUTING.md «MR без passing CI не мерджится — server-side gates это enforcement layer; client-side hooks это convenience».

CONTRIBUTING.md строка 53 («These gates ARE enforced server-side too — required CI jobs on every MR») это говорит, но мягко; для нового контрибьютора warning при первом run'е был бы explicit.
