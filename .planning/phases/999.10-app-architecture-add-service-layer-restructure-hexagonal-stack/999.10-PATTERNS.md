### PATTERN 2 — gRPC Controller (rename + move + enrich)

**Analog:** `apps/auth/src/infrastructure/grpc/auth.grpc-server.ts` (current — complete file, 38 lines — shown below verbatim)

**Core pattern** (lines 1-38):
```typescript
import { Controller, Inject, NotImplementedException } from '@nestjs/common';
import { AuthProto, CommonProto } from '@email-platform/contracts';
import { LoginPort } from '../../application/ports/inbound/login.port';
import { LOGIN_PORT } from '../../auth.constants';

@Controller()
@AuthProto.AuthServiceControllerMethods()
export class AuthGrpcServer implements AuthProto.AuthServiceController {
  constructor(@Inject(LOGIN_PORT) private readonly loginPort: LoginPort) {}

  async healthCheck(_request: CommonProto.Empty): Promise<CommonProto.HealthStatus> {
    throw new NotImplementedException('healthCheck not yet implemented');
  }

  async login(_request: AuthProto.LoginRequest): Promise<AuthProto.TokenPair> {
    throw new NotImplementedException('login not yet implemented');
  }
  // ... 5 more stubs
}
```

**What MUST be preserved:**
1. `@Controller()` decorator FIRST, `@XxxServiceControllerMethods()` SECOND (Pitfall 1).
2. `implements XxxProto.XxxServiceController` — keeps TypeScript enforcing camelCase method names + all RPC methods present (Pitfall 2).
3. Every method is `async method(req): Promise<X>` (never `Observable`) — ts-proto recipe.

**What MUST change (per D-07, D-09, D-20, RESEARCH.md §Controller Pattern):**
1. **File move:** `infrastructure/grpc/auth.grpc-server.ts` → `infrastructure/controllers/grpc/auth.controller.ts` (use `git mv`).
2. **Class rename:** `AuthGrpcServer` → `AuthController`.
3. **Constructor expansion:** inject N ports (one per RPC):
   ```typescript
   constructor(
     @Inject(LOGIN_PORT)          private readonly loginPort: LoginPort,
     @Inject(REGISTER_PORT)       private readonly registerPort: RegisterPort,
     @Inject(REFRESH_TOKEN_PORT)  private readonly refreshTokenPort: RefreshTokenPort,
     @Inject(VALIDATE_TOKEN_PORT) private readonly validateTokenPort: ValidateTokenPort,
     @Inject(REVOKE_TOKEN_PORT)   private readonly revokeTokenPort: RevokeTokenPort,
     @Inject(CREATE_USER_PORT)    private readonly createUserPort: CreateUserPort,
     @Inject(LIST_USERS_PORT)     private readonly listUsersPort: ListUsersPort,
   ) {}
   ```
4. **Method body swap** (stub → Command-DTO dispatch):
   ```typescript
   async login(req: AuthProto.LoginRequest): Promise<AuthProto.TokenPair> {
     const cmd = new LoginCommand(req.email, req.password);         // proto → command
     const result = await this.loginPort.execute(cmd);              // cross boundary
     return {                                                        // domain → proto
       accessToken: result.accessToken,
       refreshToken: result.refreshToken,
       expiresAt: result.expiresAt,
     };
   }
   ```
5. **Import path updates** — all relative paths shift one level deeper (`../../` → `../../../`). E.g., `../../auth.constants` → `../../../auth.constants`.
6. **`healthCheck` stays stubbed** — proto-level health is still a NotImplemented stub; actual health is via `grpc-health-check` (registered by `createGrpcServerOptions` in main.ts) and REST `/health/ready` (Pitfall 8, D-14).

**Pitfalls that apply (RESEARCH.md §Pitfalls):**
- **Pitfall 1** — decorator ordering (`@Controller()` before `@XxxServiceControllerMethods()`).
- **Pitfall 2** — camelCase method names must match `implements` interface (TypeScript catches).
- **Pitfall 3** — parser-specific: `runStorageSmoke` / `cleanupStorageSmoke` duplicate registration. See §Shared Patterns §Parser Storage-Smoke Resolution below.

**Same pattern applies to sender, parser, audience controllers** — the entire transformation is mechanical.

### PATTERN 3 — Application Service (new, no prior analog)

**Analog:** no existing service layer file exists — the pattern is introduced by this phase. Closest conceptual analog: `apps/auth/src/application/use-cases/login.use-case.ts` (current 2-layer `UseCase implements Port`).

**Reference implementation (from RESEARCH.md §Service Layer Pattern):**

```typescript
// apps/auth/src/application/services/login.service.ts
import { Injectable } from '@nestjs/common';
import { LoginPort, LoginResult } from '../ports/inbound/login.port';
import { LoginCommand } from '../commands/login.command';
import { VerifyCredentialsUseCase } from '../use-cases/verify-credentials.use-case';
import { IssueTokenPairUseCase } from '../use-cases/issue-token-pair.use-case';

@Injectable()
export class LoginService implements LoginPort {
  constructor(
    private readonly verifyCredentials: VerifyCredentialsUseCase,
    private readonly issueTokenPair: IssueTokenPairUseCase,
  ) {}

  async execute(cmd: LoginCommand): Promise<LoginResult> {
    const user = await this.verifyCredentials.execute(cmd.email, cmd.password);
    return this.issueTokenPair.execute(user);
  }
}
```

**Pure-delegation variant (when D-23 audit concludes one atomic use case suffices):**

```typescript
// apps/sender/src/application/services/create-campaign.service.ts
import { Injectable } from '@nestjs/common';
import { CreateCampaignPort, CreateCampaignResult } from '../ports/inbound/create-campaign.port';
import { CreateCampaignCommand } from '../commands/create-campaign.command';
import { CreateCampaignUseCase } from '../use-cases/create-campaign.use-case';

@Injectable()
export class CreateCampaignService implements CreateCampaignPort {
  constructor(private readonly useCase: CreateCampaignUseCase) {}
  async execute(cmd: CreateCampaignCommand): Promise<CreateCampaignResult> {
    return this.useCase.execute(cmd);
  }
}
```

**Rules (D-01, D-02, D-04 + ESLint Override 9):**
- `@Injectable()` decorator (NestJS DI).
- `implements XxxPort` — our own inbound port, NEVER proto interface.
- Service imports Commands + UseCases (plain classes) — no `@Inject()` token needed for use cases (type-injected as plain providers per RESEARCH.md §Module Composition Updates).
- Service MUST NOT import `@email-platform/contracts` (proto) — enforced by ESLint Override 9.
- Service MUST NOT import `@nestjs/microservices` — enforced by ESLint Override 9.
- Input is always `cmd: XxxCommand` — never positional args, never inline object (D-20 antipatterns).

**Body during 999.10:** per PROJECT.md "без бизнес-логики", `execute()` either delegates to stub use cases (which throw `NotImplementedException`) or throws directly. Compose as if implementation were real — stubs propagate.

### PATTERN 5 — Command DTO (new POJO class, no prior analog)

**Analog:** none in repo — new convention introduced by D-20. Closest sibling: positional args in `LoginUseCase.execute(email, password)` (anti-pattern being replaced).

**Reference implementation (from RESEARCH.md §Command DTO Pattern):**

```typescript
// apps/auth/src/application/commands/login.command.ts
export class LoginCommand {
  constructor(
    public readonly email: string,
    public readonly password: string,
  ) {}
}
```

```typescript
// apps/auth/src/application/commands/create-user.command.ts
export class CreateUserCommand {
  constructor(
    public readonly email: string,
    public readonly password: string,
    public readonly role: string,
    public readonly organization: string,
    public readonly team: string,
  ) {}
}
```

**Rules:**
- Class, NOT interface (enables future `class-validator` decorators like `@IsEmail()`, `@MinLength()`).
- All fields `public readonly` — immutable once constructed.
- NO decorators in 999.10 (validation deferred per CONTEXT.md deferred section).
- NO imports of `@nestjs/common`, `@email-platform/contracts`, etc. — pure POJO.
- File naming: `{feature}.command.ts` ↔ class `{Feature}Command` (D-12).
- Per-feature (per-RPC) — NOT a generic `CommandBase` hierarchy.

**Controller call site:**
```typescript
const cmd = new LoginCommand(req.email, req.password);
const result = await this.loginPort.execute(cmd);
```

**Expected count:** ~35 `*.command.ts` files across 4 services (one per RPC method).

### Shared Pattern A — NestJS DI with Symbol tokens

**Source:** `apps/auth/src/auth.constants.ts` (existing pattern — 2 lines).

**Apply to:** `auth.constants.ts`, `sender.constants.ts`, `parser.constants.ts`, `audience.constants.ts` — each gets N new `Symbol('XxxPort')` declarations per RPC method.

```typescript
export const USER_REPOSITORY_PORT = Symbol('UserRepositoryPort');
export const LOGIN_PORT           = Symbol('LoginPort');
```

**Rules (from `.agents/skills/no-magic-values/SKILL.md` + D-11 + RESEARCH.md Pitfall 7):**
- Use `Symbol(...)` NOT `Symbol.for(...)` — per-service unique identity, not global registry.
- File name: `{svc}.constants.ts` at service root (NOT inside `application/` or `infrastructure/`).
- Tokens are `UPPER_SNAKE_CASE`.
- NEVER import port tokens across services (each bounded context owns its tokens).

**Use cases get NO token** — injected by type (`constructor(private readonly uc: VerifyCredentialsUseCase)`). Symbol tokens are reserved for interface-typed bindings (ports).

### Shared Pattern B — Stub business logic

**Source:** `apps/auth/src/application/use-cases/login.use-case.ts` L14 + all current `*.grpc-server.ts` files.

**Apply to:** every new use case and service body in 999.10. PROJECT.md constraint "каркас, без бизнес-логики".

**Two stub flavours currently in use:**
1. **Controller + NotImplementedException** (preferred for gRPC methods — maps to proper gRPC status):

2. **Use case + plain Error** (acceptable for application-layer bodies):

**Service bodies:** compose as if implementation were real — they delegate to use cases; stubs propagate naturally without extra `throw` statements:
