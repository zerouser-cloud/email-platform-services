## Why This Phase Exists

После Phase 999.7.3 (gRPC client `Promisified<T>` Proxy завершено) пользователь поднял два связанных архитектурных вопроса:

1. **Server-side proto типы:** «У нас есть proto контракты, на их базе генерируем клиенты — это OK. Но на основе тех же proto-типов мы должны писать свои контроллеры. Должны получать абстрактные классы которые имплементировать. Готово ли у нас всё?»
2. **NestJS↔Hexagonal layer mapping:** «У нас бизнес логика спрятана за слоями DDD, есть use cases / ports / adapters. Как это сочленяется с NestJS? Контроллер дёргает service который дёргает use case — нужно продумать структуру и где это лежит. Service implements proto interface? Где живут файлы?»

Research показал:
- **Server-side gRPC pattern уже идиоматичен** — все 4 gRPC сервиса (auth/sender/parser/audience) используют `implements XxxServiceController` + `@XxxServiceControllerMethods()` decorator. Это endorsed ts-proto core team путь.
- **Hexagonal layout у auth — reference implementation** (Phase 4 validated) — domain/application/infrastructure разделение присутствует, но НЕТ Application Service слоя (composition layer). Use cases имплементируют inbound ports напрямую.
- **Главный gap:** нет **унифицированной модели "Controller→Service→UseCase"** через все 6 микросервисов. Текущий auth: `Controller → UseCase implements Port` (2-слой). Нужен: `Controller → Service implements Port → UseCase` (3-слой).
- **Naming inconsistency:** `AuthGrpcServer` ≠ `HealthController` — разные суффиксы для одного типа NestJS-сущности (controller). Нужна единая convention.
- **HealthController** живёт в `apps/auth/src/health/` — outlier из общей структуры, должен быть в `infrastructure/controllers/rest/`.
- **Skill `nestjs-hexagonal-mapping` отсутствует** — паттерн нигде не зафиксирован → drift риск при добавлении новых сервисов или RPC методов.

## Locked Decisions (от пользователя в дискуссии 2026-04-18)

Эти решения **уже приняты** и не требуют re-litigation в discuss-phase. Они должны попасть в CONTEXT.md как D-XX.

### D-LOCKED-01: Унифицированный 3-слойный stack

**Controller → Service → UseCase везде, во всех 6 микросервисах, всегда.**

- Даже когда service это просто прокидка к одному use case — слой остаётся (для единообразия и роста).
- YAGNI ломается в пользу uniformity: все сервисы выглядят одинаково, junior может добавить endpoint без раздумий.
- Trade-off acknowledged: некоторые services будут pure delegation сегодня — это OK, завтра туда добавится validation/events/transactions/retry.

### D-LOCKED-02: Per-feature service granularity

**Один service = одна бизнес-операция = один inbound port.**

```
LoginService implements LoginPort
RegisterService implements RegisterPort
RefreshTokenService implements RefreshTokenPort
```

НЕ один большой `AuthApplicationService` со всеми методами proto. Per-feature даёт:
- Single Responsibility
- Тестирование атомарно (mock один port)
- Easy growth (добавить feature = добавить файл)

Controller @Inject'ит N portов, по одному на каждый proto method.

### D-LOCKED-03: Use case всегда отдельный класс

Даже если сегодня service делает `return this.useCase.execute(cmd)` — use case остаётся отдельным `*.use-case.ts` файлом. Завтра в нём появится validation / event emission / transaction wrapping.

Use case переиспользуем — может быть вызван из нескольких services если бизнес-операция атомарна и встречается в разных flows.

### D-LOCKED-04: Controller class naming — без суффикса

```
AuthController         (НЕ AuthGrpcServer, НЕ AuthGrpcController)
SenderController
ParserController
AudienceController
HealthController       (REST — уже правильно)
```

NestJS-нативная convention. Транспорт виден по декораторам (`@GrpcMethod` / `@AuthServiceControllerMethods` / `@Get`/`@Post`) и по пути файла (`infrastructure/controllers/grpc/` vs `infrastructure/controllers/rest/`).

Файл: `auth.controller.ts` (вместо `auth.grpc-server.ts`).

### D-LOCKED-05: Service implements OWN port (не proto)

**Controller** implements proto interface (`AuthProto.AuthServiceController` — generated by ts-proto).
**Service** implements **наш собственный port** (`LoginPort` — мы пишем руками).

Mapping proto ↔ domain happens IN THE CONTROLLER:
```ts
async login(req: LoginRequest): Promise<TokenPair> {
  const cmd = new LoginCommand(req.email, req.password);   // proto → domain
  const result = await this.loginPort.execute(cmd);
  return { accessToken: result.accessToken, ... };          // domain → proto
}
```

Service / use case / domain — **никогда не видят proto**. Если завтра gRPC заменится на REST/RMQ — весь stack ниже controller остаётся неизменным.

### D-LOCKED-06: Port = TypeScript interface который МЫ пишем руками

Port — это **наш** interface в `apps/{service}/src/application/ports/`. НЕ из proto, НЕ генерируется.

Зачем 2 разных interface (proto + port):
- Proto = транспортный контракт (transport concern, infrastructure)
- Port = доменный контракт (что service делает, application boundary)
- Port работает с domain types (`LoginCommand`, `LoginResult`), не с proto types

### D-LOCKED-07: Один Module на bounded context

**Flat module structure.** Один `AuthModule` для всего auth микросервиса. Нет `LoginModule` / `RegisterModule` подмодулей.

Подмодули появляются только для **shared infrastructure** из foundation (`PersistenceModule`, `LoggingModule`, `AppConfigModule`, `BucketStorageModule`).

### D-LOCKED-08: File structure — Hexagonal layout, без NestJS-овских корневых папок

NestJS-овские `src/controllers/`, `src/services/`, `src/dto/`, `src/entities/` НЕ существуют как корневые папки. Они **поглощены** Hexagonal слоями:

| Привычка NestJS | Куда переезжает |
|---|---|
| `src/controllers/` | `src/infrastructure/controllers/{grpc,rest}/` (по transport) |
| `src/services/` | `src/application/services/` (composition) **или** `src/application/use-cases/` (atomic) |
| `src/dto/` | `src/application/ports/` (interfaces) + `src/domain/value-objects/` |
| `src/entities/` | `src/domain/entities/` (POJO, no Drizzle decorators) |
| `src/repositories/` | `src/infrastructure/persistence/` (implements outbound port) |

### D-LOCKED-09: Транспорт явный в пути

`infrastructure/controllers/grpc/auth.controller.ts` vs `infrastructure/controllers/rest/health.controller.ts`. Сразу видно какой transport. Если у сервиса появится REST endpoint — кладётся в `rest/` соседствующий с health.

### D-LOCKED-10: Health всегда REST

`infrastructure/controllers/rest/health.controller.ts`. Стандарт для NestJS health checks. Текущий outlier `apps/{service}/src/health/health.controller.ts` переезжает.

### D-LOCKED-11: Domain полностью изолирован

В `apps/{service}/src/domain/`:
- НЕТ `@Injectable()`, `@Inject()` декораторов
- НЕТ proto типов
- НЕТ Drizzle типов / decorators
- НЕТ NestJS imports

Чистый TypeScript. Entity = POJO. Value objects = immutable classes с валидацией.

### D-LOCKED-12: Naming convention для файлов

| Тип | Файл | Класс |
|---|---|---|
| Controller | `auth.controller.ts` | `AuthController` |
| Application Service | `login.service.ts` | `LoginService` |
| Use Case | `verify-credentials.use-case.ts` | `VerifyCredentialsUseCase` |
| Inbound Port | `login.port.ts` | `LoginPort` |
| Outbound Port | `user-repository.port.ts` | `UserRepositoryPort` |
| Repository (adapter) | `pg-user.repository.ts` | `PgUserRepository` |
| Mapper | `user.mapper.ts` | `UserMapper` |
| Entity | `user.entity.ts` | `User` |
| Value Object | `email.vo.ts` | `Email` |
| Domain Service | `password-hasher.ts` | `PasswordHasher` |
| Domain Event | `user-registered.event.ts` | `UserRegisteredEvent` |

One-to-one файл↔класс. Никаких `*.handler.ts`, `*.processor.ts` без причины.

## Call flow (canonical)

```
gRPC request (proto types)
  → AuthController.login(req)                    [Controller — implements AuthServiceController]
       │ proto LoginRequest → LoginCommand (domain)
       ▼
  → loginPort.execute(cmd)                       [Inbound port — domain types]
       ▼
  → LoginService.execute(cmd)                    [Application Service — implements LoginPort]
       │ orchestration (даже если сегодня pure delegation к ОДНОМУ use case)
       ▼
  → VerifyCredentialsUseCase.execute(...)        [Use Case — atomic operation]
       │
       ├─ userRepoPort.findByEmail(email)        [Outbound port — domain types]
       │     ▼
       │   PgUserRepository.findByEmail(email)   [Outbound adapter — implements port]
       │     → drizzle SELECT
       │     → UserMapper.toDomain(row)          [Drizzle row → User entity]
       │     ◀ User
       │
       └─ password.matches(stored)               [Domain logic]
       ◀ LoginResult (domain types)
       │
  ← AuthController formats LoginResult → TokenPair (proto)
```

## Composition Root Example

```ts
// apps/auth/src/auth.module.ts
@Module({
  imports: [
    AppConfigModule.forRoot(AuthEnvSchema),
    PersistenceModule.forRootAsync(),
    LoggingModule.forGrpcAsync('auth'),
  ],
  controllers: [
    AuthController,                            // ← infrastructure/controllers/grpc/
    HealthController,                          // ← infrastructure/controllers/rest/
  ],
  providers: [
    // OUTBOUND port → adapter
    { provide: USER_REPOSITORY_PORT, useClass: PgUserRepository },

    // INBOUND ports → services (per-feature)
    { provide: LOGIN_PORT,           useClass: LoginService },
    { provide: REGISTER_PORT,        useClass: RegisterService },
    { provide: REFRESH_TOKEN_PORT,   useClass: RefreshTokenService },
    { provide: VALIDATE_TOKEN_PORT,  useClass: ValidateTokenService },
    { provide: REVOKE_TOKEN_PORT,    useClass: RevokeTokenService },
    { provide: CREATE_USER_PORT,     useClass: CreateUserService },
    { provide: LIST_USERS_PORT,      useClass: ListUsersService },

    // Use cases (вызываются services через @Inject(USE_CASE_TOKEN) или прямой инжект)
    VerifyCredentialsUseCase,
    IssueTokenPairUseCase,
    PersistUserUseCase,
    RevokeTokenUseCase,
    HashPasswordUseCase,
    // ...

    // Domain services (если нужны DI)
    PasswordHasher,
  ],
})
export class AuthModule {}
```
