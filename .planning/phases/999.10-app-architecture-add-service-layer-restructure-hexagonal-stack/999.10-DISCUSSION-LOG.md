## Zone 1 — Scope & migration strategy

### Q1.1 — Scope сервисов

| Option | Description | Selected |
|--------|-------------|----------|
| 4 gRPC сервиса целиком | auth/sender/parser/audience — полный refactoring. Gateway и notifier — отдельные фазы (разная специфика: REST facade, RMQ consumer). | ✓ |
| 4 gRPC + REST health-move для gateway/notifier | 4 сервиса полностью + только тривиальный перенос health у gateway/notifier. | |
| Все 6 сервисов сразу | +30-40 файлов, требует разработки pattern'ов для REST-only и RMQ-only сервисов. | |

**User's choice:** 4 gRPC сервиса целиком (auth, sender, parser, audience).

**Notes / дискуссия:**
- Пользователь уточнял разницу между **inbound и outbound portами** — ответил таблицей: inbound = driving (controller вызывает), outbound = driven (application вызывает infrastructure).
- Пользователь спросил как REST HealthController матчится с gRPC-сервисом — разобрал: **hybrid NestJS app** (gRPC microservice + HTTP server в одном процессе), два независимых канала health check (Docker/Coolify REST loopback + gateway gRPC aggregated).
- Пользователь спросил про изоляцию — проверил docker-compose: `expose:` у микросервисов (Docker internal only), `ports:` только у gateway. Подтверждено: ничего не торчит наружу, REST health — loopback внутри контейнера.
- Дополнительно зафиксировано как **Deferred Idea**: переход на gRPC-only health probe (убрать REST + `app.listen()` у микросервисов) — отдельная будущая фаза, требует изменений docker-compose и добавления `grpc_health_probe` в Docker image.

### Q3.2 — Command DTO convention

| Option | Description | Selected |
|--------|-------------|----------|
| Вариант A — LoginCommand класс | POJO в application/commands/. execute(cmd: LoginCommand). Scalable, named fields, foundation для class-validator. | ✓ |
| Вариант B — позиционные args | execute(email, password). Просто, но не scalable. | |
| Вариант C — inline object без named class | execute({ email, password }). Named fields без класса. Нет reusable type. | |

**User's choice:** Вариант A — `LoginCommand` POJO класс в `application/commands/`.

**Notes / дискуссия:**
- Пользователь попросил объяснить "как это выглядит, какие варианты" — показал реальный код текущего `LoginUseCase.execute(email, password)` и три варианта на его базе с mapping proto→command в controller'е.

### Q3.3 — Mapper folder structure

| Option | Description | Selected |

| Flat в persistence/ с правилом роста | Рядом с repository (1-2 mapper сейчас). Переезд в mappers/ когда > 5. | |
| Отдельная mappers/ сразу | infrastructure/persistence/mappers/ с первого дня. Единообразие. Extra nesting. | ✓ |

**User's choice:** Отдельная `infrastructure/persistence/mappers/` подпапка сразу.

**Notes / дискуссия:**
- Пользователь спросил "что вообще делают эти мапперы" — разъяснил на реальном `UserMapper` в auth: `toDomain` (Drizzle row → User entity, отбрасывание hash), `toPersistence` (User → row с добавлением passwordHash). Четыре задачи: изоляция domain от ORM, разные модели БД и домена, composing из JOIN'ов, центральная точка для тестов.
