# Phase 999.10: Application architecture — add Service layer + restructure Hexagonal stack - Context

**Gathered:** 2026-04-18
**Status:** Ready for planning

<domain>
## Phase Boundary

Унифицировать NestJS↔Hexagonal layer mapping для 4 gRPC микросервисов (auth, sender, parser, audience). Ввести трёхслойный stack `Controller → Service → UseCase` (Service = composition layer implementing наш inbound port; UseCase = атомарная операция), переименовать gRPC контроллеры без транспортного суффикса (`AuthGrpcServer` → `AuthController`), перенести REST HealthController в `infrastructure/controllers/rest/`, ввести Command DTO convention для use case входа, зафиксировать паттерн как skill `nestjs-hexagonal-mapping`, добавить ESLint layer guards для изоляции domain/application от proto/NestJS/Drizzle, обновить CLAUDE.md + `.planning/codebase/ARCHITECTURE.md` + `STRUCTURE.md`.

Gateway (REST facade) и notifier (RabbitMQ consumer) имеют принципиально другую структуру (нет proto controller у первого, нет gRPC server у второго) — отдельные будущие фазы. REST HealthController сохраняется; переход на gRPC-only health probe для микросервисов — отдельная deferred идея. Бизнес-логика остаётся stub'ами per PROJECT.md constraint (каркас, не реализация).

</domain>

<decisions>
## Implementation Decisions

### Layer Stack & Architecture (locked до дискуссии, подтверждены в NOTES.md)
- **D-01:** Унифицированный 3-слойный stack **Controller → Service → UseCase** везде во всех сервисах, всегда. Даже когда service = pure delegation к одному use case — слой остаётся. YAGNI ломается в пользу uniformity: одинаковый look & feel, junior легко добавляет endpoint.
- **D-02:** **Per-feature service granularity** — один service = одна бизнес-операция = один inbound port. `LoginService implements LoginPort`, `RegisterService implements RegisterPort` и т.д. НЕ один `AuthApplicationService` со всеми методами. Контроллер `@Inject`ит N port'ов (по одному на каждый proto метод).
- **D-03:** **Use case всегда отдельный класс** (`*.use-case.ts`). Даже если service сегодня делает `return this.useCase.execute(cmd)` — use case остаётся отдельным файлом. Завтра туда добавится validation / event emission / transaction wrapping. Use case переиспользуем между service'ами.
- **D-04:** **Service implements OWN port, не proto interface.** Controller implements proto interface (`AuthProto.AuthServiceController` — generated by ts-proto). Service implements наш собственный port (`LoginPort` — ручной). Mapping proto↔domain **живёт в Controller'е**. Service / use case / domain — никогда не видят proto. Если завтра gRPC заменится на REST/RMQ — stack ниже controller'а не меняется.
- **D-05:** **Port = TypeScript interface который МЫ пишем руками** в `apps/{service}/src/application/ports/`. НЕ из proto, НЕ генерируется. Proto = транспортный контракт (infrastructure). Port = доменный контракт (application boundary). Port работает с domain types (`LoginCommand`, `LoginResult`), не с proto types.
- **D-06:** **Domain полностью изолирован.** В `apps/{service}/src/domain/` нет `@Injectable()`, нет proto типов, нет Drizzle decorators, нет NestJS imports. Чистый TypeScript. Entity = POJO. VO = immutable class с валидацией.

### Naming & File Structure (locked)
- **D-07:** **Controller class naming — без транспортного суффикса.** `AuthController`, `SenderController`, `ParserController`, `AudienceController`, `HealthController`. Транспорт виден по декораторам (`@AuthServiceControllerMethods`, `@GrpcMethod`, `@Get`/`@Post`) и по пути файла (`infrastructure/controllers/grpc/` vs `infrastructure/controllers/rest/`). Файл: `auth.controller.ts` (не `auth.grpc-server.ts`).
- **D-08:** **File structure — Hexagonal layout, без NestJS-корневых папок.** НЕТ корневых `src/controllers/`, `src/services/`, `src/dto/`, `src/entities/`. Поглощены слоями: controllers → `infrastructure/controllers/{grpc,rest}/`, services → `application/services/` + `application/use-cases/`, dto → `application/commands/` + `application/ports/` + `domain/value-objects/`, entities → `domain/entities/`, repositories → `infrastructure/persistence/`.
- **D-09:** **Транспорт явный в пути.** `infrastructure/controllers/grpc/auth.controller.ts` vs `infrastructure/controllers/rest/health.controller.ts`. Сразу видно какой transport.
- **D-10:** **Health всегда REST в `infrastructure/controllers/rest/health.controller.ts`.** Стандарт для NestJS health checks (Docker/Coolify probes). Текущий outlier `apps/{service}/src/health/health.controller.ts` переезжает.
- **D-11:** **Один Module на bounded context** — flat, без подмодулей. Один `AuthModule` для всего auth сервиса (не `LoginModule` / `RegisterModule` подмодулей). Подмодули только для shared infrastructure из foundation (`PersistenceModule`, `LoggingModule`, `AppConfigModule`).
- **D-12:** **Naming convention файлов one-to-one с классами.**
  | Тип | Файл | Класс |
  |---|---|---|
  | Controller | `auth.controller.ts` | `AuthController` |
  | Application Service | `login.service.ts` | `LoginService` |
  | Use Case | `verify-credentials.use-case.ts` | `VerifyCredentialsUseCase` |
  | Command | `login.command.ts` | `LoginCommand` |
  | Inbound Port | `login.port.ts` | `LoginPort` |
  | Outbound Port | `user-repository.port.ts` | `UserRepositoryPort` |
  | Repository (adapter) | `pg-user.repository.ts` | `PgUserRepository` |
  | Mapper | `user.mapper.ts` | `UserMapper` |
  | Entity | `user.entity.ts` | `User` |

- **Hybrid NestJS app** (gRPC microservice + HTTP server в одном процессе) — `main.ts` делает `connectMicroservice(gRPC)` + `startAllMicroservices()` + `listen(PORT)`. Остаётся без изменений в 999.10.

- **Proto generation via ts-proto** — сервер использует `implements XxxServiceController` + `@XxxServiceControllerMethods()` decorator. Это endorsed ts-proto core team путь, не трогаем.
- **Drizzle ORM via `PersistenceModule`** — repositories используют `this.db.select().from(...)`, pg schema per service (auth / sender / parser / audience) для namespace isolation.
- **Cross-package layer rules** (phase 5): `no-restricted-imports` в `.eslintrc.js` для contracts→config→foundation→apps. Новые intra-app domain/application rules добавляются в Plan 6, существующие не трогаем.

## Specific Ideas

- **Call flow pattern (канонический)** — из NOTES.md:
  ```
  gRPC request → AuthController.login(req) → loginPort.execute(cmd)
               → LoginService.execute(cmd) → VerifyCredentialsUseCase.execute(...)
               → userRepoPort.findByEmail → PgUserRepository (Drizzle) → UserMapper.toDomain
               → domain logic → LoginResult → AuthController формирует proto response
  ```

- **Controller pattern** — reference пример из NOTES.md:
  ```ts
  @Controller()
  @AuthServiceControllerMethods()
  export class AuthController implements AuthServiceController {
    constructor(
      @Inject(LOGIN_PORT) private readonly loginPort: LoginPort,
      @Inject(REGISTER_PORT) private readonly registerPort: RegisterPort,
      // ...
    ) {}

    async login(req: LoginRequest): Promise<TokenPair> {
      const cmd = new LoginCommand(req.email, req.password);
      const result = await this.loginPort.execute(cmd);
      return { accessToken: result.accessToken, refreshToken: result.refreshToken };
    }
  }
  ```

- **Composition root pattern** — из NOTES.md для `auth.module.ts`:
  ```ts
  @Module({
    imports: [AppConfigModule.forRoot(AuthEnvSchema), PersistenceModule.forRootAsync(), LoggingModule.forGrpcAsync('auth')],
    controllers: [AuthController, HealthController],
    providers: [
      { provide: USER_REPOSITORY_PORT, useClass: PgUserRepository },
      { provide: LOGIN_PORT, useClass: LoginService },
      { provide: REGISTER_PORT, useClass: RegisterService },
      // ... все inbound ports
      VerifyCredentialsUseCase, IssueTokenPairUseCase, PersistUserUseCase,
      // ... use cases как plain providers (@Injectable)
    ],
  })
  ```

- **Skill triada mental model:** user explicitly named:
  - `clean-ddd-hexagonal` — общая Hexagonal философия (existing)
  - `infrastructure-client-layering` — client-side gRPC layering из 999.7.x (existing)
  - `nestjs-hexagonal-mapping` — server-side NestJS-Hexagonal mapping (новый, 999.10)

- **Gateway vs notifier deferred rationale:** gateway = REST facade без бизнес-логики (его "service layer" был бы пустой facade к gRPC clients). Notifier = RMQ consumer без inbound HTTP/gRPC (его controllers — event handlers). Оба требуют собственного архитектурного решения.
