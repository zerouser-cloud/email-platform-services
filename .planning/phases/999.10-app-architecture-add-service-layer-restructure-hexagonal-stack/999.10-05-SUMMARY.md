- `GroupRepositoryPort` (NEW — methods: `findAll(limit, offset, userId)`, `findById(id)`, `save(group)`, `deleteById(id)`). Implemented by stub `PgGroupRepository` (no Drizzle `groups` schema yet — all methods throw). `Group` domain POJO entity: `{id, name, userId}` minimal shape.

**Controller rewrite:** `AudienceController` implements full `AudienceServiceController` (all 9 methods), decorated with `@AudienceServiceControllerMethods()` bulk decorator, injects 8 inbound ports via Symbol tokens. Proto DTO shapes mapped field-by-field to Command DTOs and back to proto response types. Pagination defaults (page=1, limit=20) applied at the proto→Command boundary when the client omits `pagination`.

**Module rewrite:** `AudienceModule` providers[] in 3-zone format (Zone 1: 2 outbound ports → PgRecipientRepository + PgGroupRepository; Zone 2: 8 inbound ports → 8 services; Zone 3: 7 use cases as plain @Injectable providers without tokens). controllers[] holds `AudienceController` + `HealthController`. imports[] preserves `ParserClientModule.forRoot()` (audience calls parser gRPC — pre-dating 999.10).

## Decisions Made

1. **Shared `TransitionRecipientsStatusUseCase` (D-03 realised for the third time).** The `markAsSent` and `resetSendStatus` proto RPCs differ in both selector type (ids-list vs group-id) AND target status (sent vs pending), yet they perform the same atomic operation: transition recipient sent-status. Captured as a single use case taking a tagged `RecipientSelector = { kind:'by-ids', recipientIds } | { kind:'by-group', groupId }` plus `newStatus: 'sent'|'pending'`. Services pass the appropriate selector; zero branching inside the use case body. First two D-03 reuse cases in the phase came from auth (`IssueTokenPairUseCase`) and sender (`TransitionCampaignStatusUseCase`); this is the third.

2. **`GroupRepositoryPort` added for cross-aggregate symmetry.** The 3 group RPCs (`listGroups`, `createGroup`, `deleteGroup`) need persistence. Two options: (a) let use cases throw without a port (PROJECT.md permits this), (b) introduce a second outbound port. Chose (b) because the Recipient ≠ Group distinction is a real DDD aggregate boundary — mixing group operations into `RecipientRepositoryPort` would be a structural leak (threat T-999.10-05-03 mitigation). Repository methods stay as stubs until business logic arrives. Cost: +3 files (`group.entity.ts`, `group-repository.port.ts`, `pg-group.repository.ts`), benefit: hexagonal symmetry preserved.

3. **0 proto-shape auto-deviations — Plan 02/03/04 lesson carried forward.** Read `packages/contracts/src/generated/audience.ts` BEFORE writing any port/service/controller. All 9 RPC shapes (including `healthCheck`, `ListGroupsRequest.userId`, `CreateGroupRequest.{name, userId}`, `Group.recipientCount`, `GetByGroupRequest.onlyUnsent`, `MarkSentRequest.recipientIds[]`, `ResetStatusRequest.groupId`) captured up front and encoded into Command DTOs + Port Results verbatim.

4. **Health controller relative-import depth was already correct — no Pitfall 9 fix needed.** `apps/audience/src/health/health.controller.ts` (at depth 1) used only absolute imports (`@nestjs/common`, `@nestjs/terminus`, `@email-platform/foundation`). After `git mv` to `infrastructure/controllers/rest/` (depth 3) nothing changed. Contrasts with parser Plan 04 where Pitfall 9 fired because parser's health controller imported `parser.constants` via relative path.

5. **`RecipientList.pagination` set to `undefined` for `getRecipientsByGroup`.** The proto declares `RecipientList.pagination` as optional. The group-scoped query returns the full unpaged slice (no page/limit selector in `GetByGroupRequest`), so emitting `undefined` is the canonical proto-consistent choice rather than fabricating zeros.
