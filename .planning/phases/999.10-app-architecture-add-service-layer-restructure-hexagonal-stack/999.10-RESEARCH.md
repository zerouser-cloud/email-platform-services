## User Constraints (from CONTEXT.md)

### Locked Decisions

**Layer Stack & Architecture (D-01..D-06):**
- **D-01:** Унифицированный 3-слойный stack **Controller → Service → UseCase** везде во всех 4 сервисах, всегда. Даже когда service = pure delegation к одному use case — слой остаётся. YAGNI ломается в пользу uniformity.
- **D-02:** **Per-feature service granularity** — один service = одна бизнес-операция = один inbound port. Controller `@Inject`-ит N port-ов (по одному на каждый proto метод).
- **D-03:** **Use case всегда отдельный класс** (`*.use-case.ts`). Даже для pure delegation сегодня.
- **D-04:** **Service implements OWN port (не proto interface).** Controller implements proto interface. Mapping proto↔domain **живёт в Controller-е**. Service / use case / domain — никогда не видят proto.
- **D-05:** **Port = TypeScript interface который МЫ пишем руками** в `apps/{service}/src/application/ports/`. НЕ из proto, НЕ генерируется.
- **D-06:** **Domain полностью изолирован** — нет `@Injectable()`, нет proto, нет Drizzle, нет NestJS imports. Чистый TypeScript.

**Naming & File Structure (D-07..D-12):**
- **D-07:** Controller class naming — без транспортного суффикса. `AuthController`, `SenderController`, `ParserController`, `AudienceController`, `HealthController`.
- **D-08:** File structure — Hexagonal layout, без NestJS-корневых папок (`src/controllers/`, `src/services/`, `src/dto/`, `src/entities/` — нет).
- **D-09:** Транспорт явный в пути — `infrastructure/controllers/grpc/` vs `infrastructure/controllers/rest/`.
- **D-10:** Health всегда REST в `infrastructure/controllers/rest/health.controller.ts`.
- **D-11:** Один Module на bounded context, flat. Подмодули только для shared infrastructure из foundation.
- **D-12:** Naming convention one-to-one файл↔класс (см. таблицу в CONTEXT.md).

## Project Constraints (from CLAUDE.md)

- **Архитектура apps/:** Clean/DDD/Hexagonal — проверяется через architecture-validator.
- **Архитектура packages/:** Простая утилитарная структура, без DDD.
- **Без бизнес-логики:** Только структурный каркас (ports, adapters, use cases). Все `execute()` методы остаются stubs (`throw new Error(...)` или `NotImplementedException`).
- **Без тестов:** Тестирование — отдельный следующий этап.
- **Tech stack:** NestJS 11.0.1, TypeScript 5+, gRPC, PostgreSQL+Drizzle, RabbitMQ, Redis — не меняем.
- **No magic values:** Все DI токены через `Symbol()` (не строки). Controllers/services/use cases — константы из `*.constants.ts`. Allowed: type literals, import paths, 0/1/-1, log messages.
- **No switch/case, no if/else chains (3+ branches)** для behavior selection.
- **No environment branching in app code** — нет `NODE_ENV` reads, нет `isDev`/`isProd`. Всё через `@email-platform/config`.
- **No infrastructure changes without user approval.** Порты/docker-compose/credentials — не трогаем.
- **No defaults/optionals in env schemas** — действительно каждый env var required.
- **Infrastructure-client layering** — identity→catalog, mechanisms→foundation, assembly+naming→apps. 999.7.x — reference (client-side). 999.10 — server-side pair.
- **Runtime smoke verification** — после phase runtime-smoke через `pnpm start:native` + `pnpm start:isolated`, package.json scripts only.
- **GSD workflow** — every edit routed через GSD command (здесь — execute-phase).

## Summary

**WHAT:** Унифицировать NestJS↔Hexagonal layer mapping для 4 gRPC микросервисов (auth, sender, parser, audience). Ввести трёхслойный stack `Controller → Service → UseCase`, переименовать `AuthGrpcServer → AuthController`, перенести `apps/{svc}/src/health/` в `infrastructure/controllers/rest/`, ввести Command DTO convention, переместить mappers в `infrastructure/persistence/mappers/`, создать skill `nestjs-hexagonal-mapping`, добавить ESLint layer guards, обновить docs.

**WHY:** После Phase 999.7.3 (client-side `Promisified<T>` Proxy) остался gap в server-side pattern'е: (1) naming inconsistency (`AuthGrpcServer` vs `HealthController`); (2) отсутствует Application Service слой (`Controller → UseCase implements Port` — 2-слойный сегодня); (3) нет зафиксированного skill для NestJS-Hexagonal mapping — drift риск. Фаза фиксирует single canonical form для всех 4 сервисов.

**HOW:** 7 plans в строгом порядке: skill first (Plan 1 — template), auth pilot (Plan 2 — validation), mechanical sweep 3 сервисов (Plans 3-5 — atomic commits), ESLint guards (Plan 6 — reveal), docs (Plan 7 — CLAUDE.md + ARCHITECTURE.md + STRUCTURE.md).

**Primary recommendation:** Pattern уже идиоматичен в auth (per audit in NOTES.md) — `implements XxxServiceController` + `@XxxServiceControllerMethods()` decorator. Фаза — rename + structure refactor + service layer insertion, НЕ изменение контрактов/bootstrap/proto. Бизнес-логика остаётся stubs (PROJECT.md constraint).

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| gRPC method dispatch | Infrastructure (controllers/grpc) | — | Only infrastructure knows proto types (D-04) |
| REST `/health/live`, `/health/ready` | Infrastructure (controllers/rest) | — | Liveness/readiness probes for Docker — Terminus pattern |
| proto↔domain mapping | Infrastructure (controllers/grpc) | — | Controller is the seam; service/use case never see proto (D-04) |
| Business operation orchestration | Application (services) | — | Per-feature service composes use cases (D-02) |
| Atomic business step | Application (use-cases) | — | Stateless, reusable (D-03) |
| Port contracts | Application (ports/inbound + outbound) | — | TypeScript interfaces we write by hand (D-05) |
| Command DTO | Application (commands) | — | POJO input shape, future class-validator (D-20) |
| Entity + VO | Domain | — | Pure TypeScript, zero external deps (D-06) |
| Drizzle query + row mapping | Infrastructure (persistence + persistence/mappers) | — | ORM concern, implements outbound port (D-21) |
| gRPC server bootstrap | Infrastructure (main.ts) | — | NestFactory.create + connectMicroservice — не меняется |
| Composition root | Root module (`{svc}.module.ts`) | — | One flat module per bounded context (D-11) |

## Controller Pattern

**Idiomatic ts-proto NestJS server-side pattern (VERIFIED via packages/contracts/src/generated/auth.ts L643-664 + NestJS 11.1.19 + ts-proto 2.11.6 docs).**

The `@XxxServiceControllerMethods()` decorator iterates all RPC methods, reads the descriptor for each, and applies `GrpcMethod("ServiceName", "methodName")` (or `GrpcStreamMethod` for streams). It's a compile-time code generation helper that replaces manual per-method `@GrpcMethod` decorations.

```typescript
// apps/auth/src/infrastructure/controllers/grpc/auth.controller.ts
import { Controller, Inject } from '@nestjs/common';
import { AuthProto, CommonProto } from '@email-platform/contracts';
import { LoginPort } from '../../../application/ports/inbound/login.port';
import { RegisterPort } from '../../../application/ports/inbound/register.port';
import { RefreshTokenPort } from '../../../application/ports/inbound/refresh-token.port';
import { ValidateTokenPort } from '../../../application/ports/inbound/validate-token.port';
import { RevokeTokenPort } from '../../../application/ports/inbound/revoke-token.port';
import { CreateUserPort } from '../../../application/ports/inbound/create-user.port';
import { ListUsersPort } from '../../../application/ports/inbound/list-users.port';
import { LoginCommand } from '../../../application/commands/login.command';
import { RegisterCommand } from '../../../application/commands/register.command';
// ... imports for other commands
import {
  LOGIN_PORT,
  REGISTER_PORT,
  REFRESH_TOKEN_PORT,
  VALIDATE_TOKEN_PORT,
  REVOKE_TOKEN_PORT,
  CREATE_USER_PORT,
  LIST_USERS_PORT,
} from '../../../auth.constants';

@Controller()
@AuthProto.AuthServiceControllerMethods()
export class AuthController implements AuthProto.AuthServiceController {
  constructor(
    @Inject(LOGIN_PORT)          private readonly loginPort: LoginPort,
    @Inject(REGISTER_PORT)       private readonly registerPort: RegisterPort,
    @Inject(REFRESH_TOKEN_PORT)  private readonly refreshTokenPort: RefreshTokenPort,
    @Inject(VALIDATE_TOKEN_PORT) private readonly validateTokenPort: ValidateTokenPort,
    @Inject(REVOKE_TOKEN_PORT)   private readonly revokeTokenPort: RevokeTokenPort,
    @Inject(CREATE_USER_PORT)    private readonly createUserPort: CreateUserPort,
    @Inject(LIST_USERS_PORT)     private readonly listUsersPort: ListUsersPort,
  ) {}

  async healthCheck(_request: CommonProto.Empty): Promise<CommonProto.HealthStatus> {
    // D-14 — REST probe is the standard; gRPC health uses grpc-health-check protocol
    // separately (see createGrpcServerOptions). Stub here is acceptable.
    return { serving: true };
  }

  async login(req: AuthProto.LoginRequest): Promise<AuthProto.TokenPair> {
    const cmd = new LoginCommand(req.email, req.password);
    const result = await this.loginPort.execute(cmd);
    return {
      accessToken: result.accessToken,
      refreshToken: result.refreshToken,
      expiresAt: result.expiresAt,
    };
  }

  async refreshToken(req: AuthProto.RefreshRequest): Promise<AuthProto.TokenPair> {
    const cmd = new RefreshTokenCommand(req.refreshToken);
    const result = await this.refreshTokenPort.execute(cmd);
    return { accessToken: result.accessToken, refreshToken: result.refreshToken, expiresAt: result.expiresAt };
  }

  // ... validateToken, revokeToken, createUser, listUsers — same pattern
}
```

**Critical notes:**
1. `implements AuthProto.AuthServiceController` — makes return types type-safe against proto (compile-time check).
2. The proto interface accepts `Promise<T> | Observable<T> | T` for unary methods — we always return `Promise<T>` (per ts-proto NestJS recipe).
3. Every method body is a **thin mapping layer**: `req → Command → port.execute(cmd) → proto response`. NO business logic in controller (D-04).
4. Controller is the **ONLY** layer importing `@email-platform/contracts` (proto). ESLint Override (Plan 6) enforces this.
5. Stream methods (none in current proto) would return `Observable<T>` — `@XxxServiceControllerMethods` auto-dispatches to `GrpcStreamMethod`.

[CITED: https://github.com/stephenh/ts-proto/blob/main/NESTJS.markdown — canonical `implements XxxServiceController + @XxxServiceControllerMethods()` pattern]

## Service Layer Pattern

**D-02:** Per-feature service. One service class per RPC method = one inbound port.
**D-04:** Service implements OWN port (not proto).

```typescript
// apps/auth/src/application/ports/inbound/login.port.ts
import type { LoginCommand } from '../../commands/login.command';

export interface LoginPort {
  execute(cmd: LoginCommand): Promise<LoginResult>;
}

export interface LoginResult {
  readonly accessToken: string;
  readonly refreshToken: string;
  readonly expiresAt: number;
}
```

```typescript
// apps/auth/src/application/services/login.service.ts
import { Inject, Injectable } from '@nestjs/common';
import { LoginPort, LoginResult } from '../ports/inbound/login.port';
import { LoginCommand } from '../commands/login.command';
import { VerifyCredentialsUseCase } from '../use-cases/verify-credentials.use-case';
import { IssueTokenPairUseCase } from '../use-cases/issue-token-pair.use-case';

@Injectable()
export class LoginService implements LoginPort {
  constructor(
    private readonly verifyCredentials: VerifyCredentialsUseCase,
    private readonly issueTokenPair: IssueTokenPairUseCase,
  ) {}

  async execute(cmd: LoginCommand): Promise<LoginResult> {
    // Composition (this example — two atomic use cases):
    const user = await this.verifyCredentials.execute(cmd.email, cmd.password);
    return this.issueTokenPair.execute(user);
  }
}
```

**Pure-delegation variant (when D-23 audit concludes one atomic use case is enough):**

```typescript
// apps/sender/src/application/services/create-campaign.service.ts
import { Inject, Injectable } from '@nestjs/common';
import { CreateCampaignPort, CreateCampaignResult } from '../ports/inbound/create-campaign.port';
import { CreateCampaignCommand } from '../commands/create-campaign.command';
import { CreateCampaignUseCase } from '../use-cases/create-campaign.use-case';

@Injectable()
export class CreateCampaignService implements CreateCampaignPort {
  constructor(private readonly useCase: CreateCampaignUseCase) {}

  async execute(cmd: CreateCampaignCommand): Promise<CreateCampaignResult> {
    return this.useCase.execute(cmd);
  }
}
```

**Per D-01 the service layer stays even for pure delegation** — it is the seam where cross-cutting concerns (logging, transaction wrap, domain events) will grow later.

**Key notes:**
- Service is `@Injectable()`.
- Service imports Commands and UseCases (plain classes) — no `@Inject()` tokens needed for use cases (they're auto-injected by type).
- Service NEVER imports `@email-platform/contracts` (D-18 ESLint guard).
- Service uses Commands as input (D-20) — NOT positional args.

## Command DTO Pattern

**D-20:** POJO class `XxxCommand` в `application/commands/`. Per-feature files. Controller маппит proto→command.

```typescript
// apps/auth/src/application/commands/login.command.ts
export class LoginCommand {
  constructor(
    public readonly email: string,
    public readonly password: string,
  ) {}
}
```

```typescript
// apps/auth/src/application/commands/create-user.command.ts
export class CreateUserCommand {
  constructor(
    public readonly email: string,
    public readonly password: string,
    public readonly role: string,
    public readonly organization: string,
    public readonly team: string,
  ) {}
}
```

**Why class and not interface:**
- Classes are runtime values → future `class-validator` decorators (`@IsEmail()`, `@MinLength(8)`) work immediately (deferred per CONTEXT.md).
- Constructor gives a single ergonomic creation site: `new LoginCommand(req.email, req.password)`.
- `readonly` fields prevent accidental mutation inside use cases.
- Named fields — adding a new field doesn't break method signature (scalability rationale from D-20).

**Controller call site (canonical):**

```typescript
async login(req: AuthProto.LoginRequest): Promise<AuthProto.TokenPair> {
  const cmd = new LoginCommand(req.email, req.password);
  const result = await this.loginPort.execute(cmd);
  return { accessToken: result.accessToken, refreshToken: result.refreshToken, expiresAt: result.expiresAt };
}
```

**Anti-patterns (explicitly rejected per CONTEXT.md D-20):**

```typescript
// ANTI 1 — positional parameters
execute(email: string, password: string): Promise<LoginResult>
// Adding a new field breaks callers.

// ANTI 2 — inline object
execute(input: { email: string; password: string }): Promise<LoginResult>
// No named type, can't be extended, no runtime value for future validation.
```

## Pitfalls

### Pitfall 1: `@XxxServiceControllerMethods()` decorator ordering

**What goes wrong:** Placing `@Controller()` below `@XxxServiceControllerMethods()` works, but placing them in opposite order or mixing with `@UseInterceptors()` etc. can produce subtle runtime dispatch misses where NestJS fails to register a method for a given RPC.

**Why it happens:** `@XxxServiceControllerMethods()` reads `Reflect.getOwnPropertyDescriptor(constructor.prototype, method)` and calls `GrpcMethod(...)` at class decoration time. If the decorator runs before `@Controller()` has wired up metadata, the GrpcMethod decorator misses.

**How to avoid:** Follow the established pattern (verified in all 4 current `*.grpc-server.ts` files):

```typescript
@Controller()                                 // ← FIRST
@AuthProto.AuthServiceControllerMethods()     // ← SECOND
export class AuthController implements AuthProto.AuthServiceController { ... }
```

**Warning signs:** `Cannot POST /auth.AuthService/Login` at runtime, or `MethodNotFound` from the client side.

[VERIFIED: all 4 existing `*.grpc-server.ts` files use this order consistently]

### Pitfall 2: Method name mismatch between `implements XxxServiceController` and actual methods

**What goes wrong:** ts-proto generates the controller interface with camelCase methods (`login`, `createUser`, `refreshToken`). If the class has a method named `Login` (Pascal) or `create_user` (snake) — TypeScript accepts it only if the interface has that method, but `@XxxServiceControllerMethods()` iterates a HARDCODED list of camelCase names (see `generated/auth.ts` L645-652). The decorator tries `Reflect.getOwnPropertyDescriptor(prototype, "login")`, finds nothing, and silently registers a broken handler.

**Why it happens:** ts-proto lowercase-first-letters RPC names (`Login` proto → `login` TS). The `XxxServiceControllerMethods` hardcoded array mirrors this. If the developer writes `Login()` in the controller, TypeScript implements fails but only if `implements` is declared; if someone removes `implements` for convenience, typescript no longer catches it.

**How to avoid:**
- ALWAYS declare `implements XxxProto.XxxServiceController` (TypeScript catches the mismatch).
- All method names must be camelCase (matching proto RPC names with first-letter-lowercased).
- The ESLint override 9 (Plan 6) does NOT forbid `implements` — only proto type imports in application/.

**Warning signs:** compiler error `Class 'AuthController' incorrectly implements interface 'AuthServiceController'. Property 'login' is missing`.

[VERIFIED: packages/contracts/src/generated/auth.ts L645-652 hardcoded `["healthCheck", "login", ...]` array]

### Pitfall 3: Duplicate RPC method registration (parser `runStorageSmoke` / `cleanupStorageSmoke`)

**What goes wrong:** Parser currently has `runStorageSmoke` / `cleanupStorageSmoke` method stubs in `apps/parser/src/infrastructure/grpc/parser.grpc-server.ts` (L44-52) AND in `apps/parser/src/test/storage-smoke.controller.ts` (L62, L71 via `@GrpcMethod('ParserService', 'RunStorageSmoke')`). NestJS microservice handler registration uses a `Map<name, handler>` keyed by `(service, method)`; the second registration wins. Today the smoke controller wins because `providers` / `controllers` array order places it after the main ParserGrpcServer (verified `apps/parser/src/parser.module.ts` L25-30).

**Why it happens:** Phase 22.3 added `StorageSmokeController` with direct `@GrpcMethod` as a smoke test. The main `ParserGrpcServer` also added stubs because the proto `ParserServiceController` interface has those methods (and `implements` forces declaration). Both registrations exist simultaneously.

**How to avoid in 999.10:**
- **When moving `parser.grpc-server.ts` → `parser.controller.ts`, REMOVE both `runStorageSmoke` and `cleanupStorageSmoke` stubs.**
- The new `ParserController` no longer `implements ParserProto.ParserServiceController` OR implements it partially — BUT partial implementation breaks the TypeScript `implements` contract.
- Resolution (recommended): Keep `implements ParserServiceController` and let the new `ParserController` provide stubs for `runStorageSmoke`/`cleanupStorageSmoke` — BUT the `@XxxServiceControllerMethods()` decorator iterates ALL 8 methods and overwrites the StorageSmokeController registration, breaking the smoke endpoint.
- **Correct resolution:** make the stub methods throw `NotImplementedException` in `ParserController` AND remove `StorageSmokeController`'s `@GrpcMethod` registrations by either:
   - (a) Moving `StorageSmokeController`'s logic into a plain injectable service, then inject that service into `ParserController` for those 2 RPCs, OR
   - (b) Keeping `StorageSmokeController` but deregistering the duplicate methods from `ParserController` — requires NOT decorating them via `@ParserServiceControllerMethods()`, which is incompatible with the "iterate all 8" generated decorator.
   - (c) Accepting that `StorageSmokeController` is already in `test/` and is a deliberate exception — in which case `ParserController` must stay WITHOUT `runStorageSmoke`/`cleanupStorageSmoke` methods, and does NOT declare `implements ParserServiceController` (it implements a subset interface).

**Recommended for Plan 4:** Option (a) — move smoke logic into `application/services/storage-smoke.service.ts` + new inbound ports, wire into `ParserController`. Smoke becomes first-class per canonical stack. But this shifts test smoke into the "real" architecture.

**Alternative (pragmatic):** Option (c) — `ParserController` declares `implements Omit<ParserServiceController, 'runStorageSmoke' | 'cleanupStorageSmoke'>`. But `@ParserServiceControllerMethods()` iterates all 8 methods and will try to decorate missing ones → runtime error.

**User decision required before Plan 4.** Research flags; planner/discuss-phase handles.

**Warning signs:** smoke endpoint stops returning — gateway `/test/parser/storage-service` returns `Not Implemented`.

[VERIFIED: `grep "runStorageSmoke\|cleanupStorageSmoke"` in both files + parser.module.ts L25-30 providers order]

### Pitfall 4: NestJS 11 hybrid app (`connectMicroservice` + `app.listen`)

**What goes wrong:** Forgetting `await app.startAllMicroservices()` before `app.listen(port)` starts the HTTP server without the gRPC server being listening. Health endpoint returns 200 on readiness but gRPC channel is broken.

**Why it happens:** NestJS 11 requires explicit `startAllMicroservices()` call in hybrid apps. Omitting it doesn't error at build time.

**How to avoid:** ALL 4 current `main.ts` files follow the pattern — DO NOT MODIFY `main.ts` in 999.10 (explicitly out of scope per CONTEXT.md code_context §Integration Points). Keep as:

```typescript
app.connectMicroservice(createGrpcServerOptions(SERVICE.auth, config.PROTO_DIR));
await app.startAllMicroservices();
await app.listen(config.AUTH_PORT, SERVER.DEFAULT_HOST);
```

**Warning signs:** gateway health check `5 upstreams: 4 down, 1 up` — all microservice gRPC clients fail to connect.

### Pitfall 5: Module provider order for duplicate DI tokens

**What goes wrong:** If two providers provide the same Symbol token (e.g., `LOGIN_PORT`), the LAST one wins silently. Easy to introduce during sweep refactoring when `useClass: LoginUseCase` and `useClass: LoginService` coexist temporarily.

**Why it happens:** Mechanical sweep (Plan 3-5) may leave a stale entry if the edit is incomplete.

**How to avoid:** Per atomic sweep plan, remove the old `{ provide: XXX_PORT, useClass: XxxUseCase }` IN THE SAME COMMIT that adds `{ provide: XXX_PORT, useClass: XxxService }`. Verify via grep `grep "provide.*XXX_PORT" apps/{svc}/src/` returns exactly one match.

**Warning signs:** service boots but `loginPort.execute(cmd)` calls the old use case directly (which tries to implement port that no longer extends command-based signature) → TypeScript error or runtime throw.

### Pitfall 6: Use case signature change — positional → Command DTO

**What goes wrong:** Existing use cases have `execute(email: string, password: string)` (positional). Plan 2 converts to `execute(cmd: LoginCommand)`. If controller still passes positional args → compile error.

**Why it happens:** Incomplete atomic commit leaves service calling `useCase.execute(email, password)` while use case now expects `execute(cmd: LoginCommand)`.

**How to avoid:** Each plan commit updates THREE things atomically per RPC:
1. Use case signature: `execute(cmd: XxxCommand)`
2. Service (calls use case with cmd)
3. Controller (builds command from proto)

**Warning signs:** `pnpm build` fails with "Expected 1 argument, got 2" or "Type 'string' is not assignable to type 'LoginCommand'".

### Pitfall 7: Symbol DI token collision across services

**What goes wrong:** `Symbol('LoginPort')` creates a UNIQUE symbol. Two services declaring `Symbol('LoginPort')` get DIFFERENT symbols. NestJS DI cross-module would fail. This is NOT a problem for 999.10 (one bounded context per symbol declaration — per-service `{svc}.constants.ts` file), but it's a trap if someone tries to extract DI tokens to a shared file later.

**Why it happens:** `Symbol()` vs `Symbol.for()` confusion — `Symbol.for('KEY')` is deduplicated by the global symbol registry; `Symbol('KEY')` is not.

**How to avoid:** Keep each service's tokens in its own `apps/{svc}/src/{svc}.constants.ts` — no cross-service token sharing. Existing pattern verified: all 4 services use plain `Symbol(...)` (NOT `Symbol.for(...)`) — correct for per-service scope.

**Warning signs:** `Nest could not resolve dependencies of the X. Please make sure that the argument at index [N] is available.`

### Pitfall 8: grpc-health-check registration order

**What goes wrong:** `createGrpcServerOptions()` registers `HealthImplementation` in `onLoadPackageDefinition`. If the controllers are registered BEFORE `grpc-health-check` binds, the gRPC server starts without the health service and gateway's aggregated health probe fails.

**Why it happens:** NestJS microservice lifecycle — `startAllMicroservices()` initializes gRPC server with load package def first, THEN binds controller handlers.

**How to avoid:** Do NOT modify `main.ts` bootstrap order. Keep `createGrpcServerOptions(SERVICE.auth, config.PROTO_DIR)` as-is.

**Warning signs:** Gateway `/health/ready` shows `auth.health` / `sender.health` / etc. as `down` even though each service's own `/health/ready` returns 200.

### Pitfall 9: File depth and relative import paths

**What goes wrong:** Moving `health.controller.ts` from `apps/auth/src/health/` (depth 2) to `apps/auth/src/infrastructure/controllers/rest/` (depth 4) breaks relative imports inside the file (e.g., `../parser.constants` in parser health).

**Why it happens:** Git mv preserves the file but imports use relative paths tied to old depth.

**How to avoid:** After every `git mv`, audit all imports in the moved file. For parser specifically:
- `import { PARSER_STORAGE_HEALTH, PARSER_STORAGE_HEALTH_KEY } from '../parser.constants'` (depth 2 → 1 step up)
- becomes `from '../../../parser.constants'` (depth 4 → 3 steps up)

**Warning signs:** `pnpm build` reports `Cannot find module '../parser.constants'`.

### Pitfall 10: Empty `src/health/` directory after move

**What goes wrong:** `git mv apps/auth/src/health/health.controller.ts apps/auth/src/infrastructure/controllers/rest/health.controller.ts` moves the file, but if anything else was in `apps/auth/src/health/` (schema cache, index.ts), it gets orphaned.

    const cmd = new LoginCommand(req.email, req.password);          // proto → command
