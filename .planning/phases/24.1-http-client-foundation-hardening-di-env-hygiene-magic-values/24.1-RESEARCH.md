### Pattern 1: Param-bag constructor + DI via useFactory

**What:** AbstractHttpClient takes a single `HttpClientDeps` object plus vendor-specific args. Foundation's `httpClientProvider` factory wires the deps; app-land supplies a `build` callback that closes over vendor-specific config (apiKey, baseUrl).

**When to use:** Any abstract class with 5+ DI collaborators where the constructor signature would otherwise become unreadable.

**Example:**
```typescript

  readonly cls: ClsService;
  readonly logger: HttpClientLogger;
  readonly executor: HttpRequestExecutor;
  readonly retry: RetryExecutorPort;
  readonly breaker: CircuitBreakerPort;
  readonly baseUrl: string;
  readonly defaultTimeoutMs: number;
  readonly logContext: string;

  readonly token: symbol;

    useFactory: (config: ConfigService, cls: ClsService, executor: HttpRequestExecutor, retry: RetryExecutorPort) => {

}
```

### Pattern 2: Chain-of-mappers for error normalization

**What:** Array of `ErrorMapper` objects with `matches(err)` + `map(err, ctx)`. `HttpErrorNormalizer.normalize(err, ctx)` scans in order, first match wins.

**When to use:** Converting an opaque error into one of N typed errors based on shape. Matches branching-patterns Pattern 3 (canHandle chain).

**Example:**
```typescript
// Source: synthesized from branching-patterns SKILL.md Pattern 3 + retry.policy.ts normalizeError

// foundation/external/http/errors/error-mapper.port.ts
export interface ErrorMapper {
  matches(err: unknown): boolean;
  map(err: unknown, ctx: { url: string; timeoutMs: number }): Error;
}

// foundation/external/http/errors/mappers/timeout-error.mapper.ts
export class TimeoutErrorMapper implements ErrorMapper {
  matches(err: unknown): boolean {
    return err instanceof Error
      && (TIMEOUT_ERR_NAMES as readonly string[]).includes(err.name);
  }
  map(_err: unknown, ctx: { url: string; timeoutMs: number }): TimeoutError {
    return new TimeoutError(ctx.url, ctx.timeoutMs);
  }
}

// foundation/external/http/errors/http-error-normalizer.ts
export class HttpErrorNormalizer {
  constructor(private readonly mappers: readonly ErrorMapper[]) {}
  normalize(err: unknown, ctx: { url: string; timeoutMs: number }): Error {
    const mapper = this.mappers.find((m) => m.matches(err));
    if (!mapper) return err instanceof Error ? err : new Error(String(err));
    return mapper.map(err, ctx);
  }
}

// Usage in HttpRequestExecutor:
const normalizer = new HttpErrorNormalizer([
  new TimeoutErrorMapper(),
  new NetworkErrorMapper(),
  // fallback is implicit (the `if (!mapper)` branch)
]);
```

### Pattern 3: Class-encapsulated opossum adapter

**What:** One class owns opossum breaker + consecutive-counter + event listeners. Kills holder-object smell. Provides `dispose()` for test cleanup.

**When to use:** Wrapping any third-party lib that bundles multiple concerns (opossum = state machine + events + timers).

**Example:**
```typescript
// Source: synthesized from @types/opossum 8.1.9 + CONTEXT.md D-04, D-12, D-13

// foundation/external/http/circuit-breaker/circuit-breaker.port.ts
export interface CircuitBreakerPort<TArgs extends unknown[] = unknown[], TReturn = unknown> {
  fire(...args: TArgs): Promise<TReturn>;
  get state(): CircuitState;
  dispose(): void;
}

// foundation/external/http/circuit-breaker/opossum-circuit-breaker.adapter.ts
export class OpossumCircuitBreakerAdapter<TArgs extends unknown[], TReturn>
  implements CircuitBreakerPort<TArgs, TReturn>
{
  private readonly breaker: CircuitBreaker<TArgs, TReturn>;
  private consecutiveFailures = 0;
  private readonly listeners: Array<[string, (...a: unknown[]) => void]> = [];

  constructor(
    innerFn: (...args: TArgs) => Promise<TReturn>,
    private readonly opts: CbOptions,
    private readonly onTransition: (t: CircuitTransition) => void,
  ) {
    const wrapped = this.wrap(innerFn);
    this.breaker = new CircuitBreaker<TArgs, TReturn>(wrapped, {
      resetTimeout: opts.halfOpenAfterMs,
      timeout: false,              // Pitfall 1 — do not race retry-loop timeout
      errorFilter: () => true,     // we drive open() ourselves
    });
    this.wireEvents();
  }

  private wrap(inner: (...a: TArgs) => Promise<TReturn>): (...a: TArgs) => Promise<TReturn> {
    return async (...args: TArgs) => {
      try {
        const r = await inner(...args);
        this.consecutiveFailures = 0;
        return r;
      } catch (err) {
        if (this.breaker.halfOpen) {
          this.consecutiveFailures = 0;
          this.breaker.open();
          throw err;
        }
        this.consecutiveFailures += 1;
        if (this.consecutiveFailures >= this.opts.consecutiveThreshold) {
          this.consecutiveFailures = 0;
          this.breaker.open();
        }
        throw err;
      }
    };
  }

  private wireEvents(): void {
    const open = (): void => this.onTransition('open');
    const half = (): void => this.onTransition('halfOpen');
    const close = (): void => this.onTransition('close');
    this.breaker.on('open', open);
    this.breaker.on('halfOpen', half);
    this.breaker.on('close', close);
    this.listeners.push(['open', open], ['halfOpen', half], ['close', close]);
  }

  async fire(...args: TArgs): Promise<TReturn> {
    try {
      return await this.breaker.fire(...args);
    } catch (err) {
      // D-13: Fragile message-match stays PRIVATE here
      if (this.breaker.opened
        || (err instanceof Error && err.message.includes(CB_BREAKER_OPEN_MESSAGE_SUBSTRING))
      ) {
        throw new CircuitOpenError(this.opts.api ?? 'unknown');
      }
      throw err;
    }
  }

  get state(): CircuitState {
    const cb = this.breaker.opened ? 'opened' : this.breaker.halfOpen ? 'halfOpen' : 'closed';
    return { cb, consecutiveFailures: this.consecutiveFailures };
  }

  dispose(): void {
    for (const [event, listener] of this.listeners) {
      this.breaker.off(event as 'open' | 'halfOpen' | 'close', listener);
    }
    this.breaker.shutdown();   // opossum's native shutdown
  }
}
```

### Anti-Patterns to Avoid

- **Over-decomposing `HttpRequestExecutor.execute()`:** Splitting a 35-line method into 7 tiny helpers creates more ceremony than value. Target: 3-4 private methods (URL construction, headers merging, fetch invocation, error-path wiring). Keep happy path readable top-to-bottom. Guidance in Claude's Discretion section of CONTEXT.md.
- **Re-introducing `setContext()` on injected PinoLogger:** Phase 23 Pitfall 6 — mutates the shared singleton, last-initialized subclass wins. `PinoHttpClientLoggerAdapter.onModuleInit` MUST use `PinoLogger.root.child({ context })`, not `@Inject(PinoLogger) private readonly logger.setContext(ctx)`.
- **Exporting internal error-mapper constants from the barrel:** `TIMEOUT_ERR_NAMES`, `CB_BREAKER_OPEN_MESSAGE_SUBSTRING`, `IDEMPOTENT_METHODS`, `RETRYABLE_STATUS_MIN` — all internal (D-17). The `index.ts` barrel should only expose consumer-facing symbols.
- **Adding `NODE_ENV`/`isDev` checks anywhere:** Forbidden by twelve-factor skill. HttpSmokeController stays gated by its location in `test/` (removed before release), not by an env check.
- **Using `config.get<T>(KEY) ?? fallback`:** Forbidden by env-schema skill. After D-18 migration to `getOrThrow`, the `!` and `??` combinations disappear together.

## Common Pitfalls

### Pitfall 1: `HttpClientLogger` port must defer creation to `onModuleInit`

**What goes wrong:** Constructing `PinoHttpClientLoggerAdapter` in constructor fails at runtime because `PinoLogger.root` is `undefined` before `LoggerModule.onModuleInit` runs.

**Why it happens:** `nestjs-pino` populates `PinoLogger.root` via its module's `onModuleInit` hook. Any code running earlier sees `undefined`.

**How to avoid:** In the adapter, store `undefined` in the logger field; implement `OnModuleInit` on the adapter; call `this.logger = PinoLogger.root.child({ context })` in `onModuleInit()`. **Same pattern applies regardless of how many adapters exist per service** (each adapter has its own onModuleInit).

**Warning signs:** Error `Cannot read properties of undefined (reading 'child')` at boot of any service importing an HTTP client.

**Source:** `packages/foundation/src/external/grpc/clients/abstract-grpc-client.ts` has the precedent `[VERIFIED: read-file]`. `packages/foundation/src/external/http/abstract-http.client.ts` comment lines 4-10 document Pitfall 2/Phase 23 Pitfall 6 `[VERIFIED: read-file]`.

### Pitfall 2: opossum v9 has NO native consecutive-failures mode

**What goes wrong:** Naive use of opossum's `errorThresholdPercentage` + `volumeThreshold` fails for low-traffic callers (e.g., notifier sending 1 msg/min) — the rolling window never accumulates enough volume to trigger opening.

**Why it happens:** opossum v9 is percentage-based by design. The old `maxFailures` option was removed. `[VERIFIED: opossum/lib/circuit.js in node_modules]`

**How to avoid:** Continue the Phase 24 approach — let the wrapper drive `breaker.open()` manually, set `errorFilter: () => true` to tell opossum to ignore its own stats, use `resetTimeout` for halfOpen→close transitions. D-12/D-13 encapsulate this inside `OpossumCircuitBreakerAdapter`.

**Warning signs:** Breaker never opens despite obvious failures; `breaker.opened` always `false`; production incident from cascading retries against dead vendor.

**Source:** Current `packages/foundation/src/external/http/circuit-breaker.factory.ts` comments 1-20 document this in detail `[VERIFIED: read-file]`. `@types/opossum/index.d.ts` confirms no `maxFailures` / no `consecutive` option in the type surface `[VERIFIED: grep]`.

### Pitfall 3: `timeout: false` is MANDATORY on CircuitBreaker construction

**What goes wrong:** opossum's per-fire timeout races `AbortSignal.timeout` in the retry loop. First one wins, observed behavior becomes unpredictable.

**Why it happens:** opossum has its own internal timer per fire; `AbortSignal.timeout(ms)` has its own timer per attempt. They fire at different cadences and both can reject the promise.

**How to avoid:** Always pass `timeout: false` in `CircuitBreaker` options. The retry loop's per-attempt timeout is the only timeout.

**Warning signs:** Tests that expect "TimeoutError after 5000ms" see opossum's `Error: Timed out after 3000ms` instead; mismatched expected vs actual timeout durations in logs.

**Source:** `circuit-breaker.factory.ts:36, 74-77` — explicit Pitfall 1 comment `[VERIFIED: read-file]`.

### Pitfall 4: Halfopen probe failure must explicitly reopen the breaker

**What goes wrong:** When `errorFilter: () => true` is in effect, opossum treats every thrown error during halfOpen as "filtered" (not a failure). The probe succeeds from opossum's POV, breaker auto-closes, next caller hits the still-broken vendor.

**Why it happens:** `errorFilter: () => true` is our escape hatch for "I drive opening myself" — but opossum's halfOpen→close logic runs regardless.

**How to avoid:** In the wrapper, `if (this.breaker.halfOpen) { this.breaker.open(); throw err; }` — explicitly re-open on probe failure. Already done in current factory; carries forward to adapter.

**Warning signs:** CB oscillates open/halfOpen/close rapidly; users see intermittent failures that should be "fast-fail with CircuitOpenError".

**Source:** `circuit-breaker.factory.ts:54-63` — explicit comment + code `[VERIFIED: read-file]`.

### Pitfall 5: Foundation build cache after package.json `exports` changes

**What goes wrong:** After any change to `packages/foundation/src/external/http/index.ts` or subfolder exports, Turbo may serve a stale compiled `dist/` from cache, consumer apps see old symbols.

**Why it happens:** Turbo input hashing includes source files but build output cache is separate; `dist/*.d.ts` changes may not invalidate cleanly.

**How to avoid:** After foundation refactor, run `rm -rf packages/foundation/dist && pnpm --filter @email-platform/foundation build` before relying on downstream apps. Validate with `pnpm typecheck` at workspace level.

**Warning signs:** TypeScript says "Module has no exported member `CircuitBreakerPort`" despite the export existing in source.

**Source:** Phase 22.1-03 STATE.md entry explicitly documents this pattern `[VERIFIED: STATE.md lines 91-93]`.

### Pitfall 6: `.env.docker.example` must stay byte-for-byte consistent with `.env.docker` key-set

**What goes wrong:** After D-31 creates `.env.docker.example`, future `.env.docker` changes might add a key without updating the example. Next developer copies example, misses the new key, service fails at boot with Zod validation error they don't understand.

**Why it happens:** There is no automated linter checking that `.env.docker` and `.env.docker.example` have the same key set. The only enforcement is human discipline and the env-schema skill review.

**How to avoid:** Add a check-list item to `docs/runbooks/env-setup.md` ("when adding env var, update ALL three files: `.env`, `.env.docker`, `.env.docker.example`"). Optionally: add a script in `package.json` (`scripts:check-env-parity`) that compares key-sets — but this is **out of scope** for 24.1 per Deferred Ideas.

**Warning signs:** New developer reports "service won't start, missing env var" that's listed in `.env.example` but not `.env.docker.example`.

**Source:** infrastructure-guard SKILL.md "Environment Files Sync Rule" `[VERIFIED: read-file]`; env-schema SKILL.md "Env Files Are the Contract" `[VERIFIED: read-file]`.

### Pitfall 7: `git rm --cached` does NOT remove the file from git history

**What goes wrong:** Developer assumes `git rm --cached .env.docker` erases the leaked token from commit `c638e69`. It does not — the token remains in git history forever.

**Why it happens:** `git rm --cached` only stops tracking going forward. History is immutable without filter-repo or BFG.

**How to avoid:** Explicitly document in the commit message for D-30: "Future commits will not track `.env.docker`. Existing commits retain the old token; it has been rotated via @BotFather." D-29 handles the actual security concern (rotation); history-rewrite was explicitly rejected in Deferred Ideas.

**Warning signs:** Security scanner flags the token again after the untrack — confirm this is a historical reference, not a current one.

**Source:** Git docs + D-29 explicitly states rotation is the security fix, not history rewrite `[CITED: CONTEXT.md D-29]`.

### Pitfall 8: `ConfigService.getOrThrow` throws `TypeError` at runtime, not at compile time

**What goes wrong:** Developer sees green typecheck, deploys to staging, service dies at boot with `TypeError: Configuration key "FOO_BAR" does not exist` because `.env` lacked the key and Zod schema somehow didn't validate (e.g., key typo in schema vs. key used in code).

**Why it happens:** `getOrThrow` runtime-checks AFTER Zod validation — if schema validates a typo'd key, getOrThrow on the different-typo'd code-side key still throws. The Zod → code-access linkage is not enforced at compile time.

**How to avoid:** ALWAYS use constants from per-service `*-client.constants.ts` (`TELEGRAM_ENV.BOT_TOKEN`, etc.) instead of string literals. This ensures the key written in the Zod schema IS the same key passed to `getOrThrow`. Already done in Phase 24; D-18 keeps this pattern.

**Warning signs:** Boot crash with `TypeError: Configuration key "<key>" does not exist`.

**Source:** `config.service.js:128-134` confirms runtime throw with descriptive message `[VERIFIED: read-file]`.

### Known Threat Patterns for NestJS + HTTP outbound

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Secret leakage in logs | Information Disclosure | D-16 (body never logged); **KNOWN ISSUE** Telegram URL contains token — documented, remediation in Phase 999.8 (SDK migration); URL redaction under debug flag deferred |
| Secret leakage in git history | Information Disclosure | D-29 Telegram token rotation (value invalidated); D-30 `git rm --cached` (stops future commits); git history NOT rewritten — old commits' token is dead weight |
| Unbounded retry on non-idempotent requests | Denial of Service (self-inflicted duplicate messages) | D-10 idempotency gate — POST/PUT/PATCH/DELETE are single-shot unless `{ idempotent: true }` is set explicitly |
| Cascading failures from downed vendor | Denial of Service | D-12 CB opens after 5 consecutive failures; halfOpen probe after 30s; CircuitOpenError fast-fails subsequent calls |
| Unbounded request latency | Denial of Service | D-11 per-attempt AbortSignal.timeout (5s default); retry adds bounded backoff (200ms-5s) |
| Config key typos at runtime | Denial of Service (boot crash) | D-18 `getOrThrow` throws TypeError with descriptive key at boot, not at first request |
| `.env.docker` drift from `.env.docker.example` | Configuration Tampering (silent) | `check-env-parity.sh` in runbook (Wave 0 gap); infrastructure-guard SKILL.md explicit rule |
| Developer committing new secrets | Information Disclosure | `.gitignore` blocks `.env.docker`; runbook documents rotation if accidentally committed |

### Token Rotation Procedure (D-29)

Operator-driven, external to code changes:

1. Open Telegram → chat with @BotFather → `/mybots` → select bot → "API Token" → "Revoke current token"
2. Confirm revocation; copy new token
3. Inject into Coolify: Production env → edit `TELEGRAM_BOT_TOKEN` → paste new value → save
4. Inject into Coolify: Dev env → same
5. Update local `.env.docker` with new value
6. Verify: Coolify redeploys notifier; notifier logs show successful Telegram API calls (no 401 Unauthorized)
7. Old token is now invalid — historical git commits containing it pose no active threat

**Commit order:**
- Operator completes steps 1-6 BEFORE any git commit in this phase.
- Then: `git rm --cached .env.docker` + `.env.docker.example` creation happen in same or subsequent commit.
