# Phase 24.1: HTTP client foundation hardening — Context

**Gathered:** 2026-04-16
**Status:** Ready for planning

<domain>
## Phase Boundary

Пост-аудит и полный архитектурный рефакторинг HTTP-клиентского foundation, созданного в фазе 24. Фаза НЕ добавляет функциональность — только улучшает:
1. **Security:** ротация утёкшего Telegram bot token и гигиена env-файлов.
2. **Архитектурная чистота:** декомпозиция God-class `AbstractHttpClient` на порт-адаптерную структуру (Executor / RetryExecutor / CircuitBreakerPort / HttpClientLogger), базовый класс ошибок, chain-of-mappers для normalization, разделение constants по темам.
3. **Качество кода:** устранение magic values, non-null assertions (`!`), избыточных optional chains (`?.`), if-instanceof цепочек в пользу декларативных паттернов (Record dispatch, canHandle-цепочки, chain-of-responsibility).
4. **DX:** устранение дублирования per-vendor module-boilerplate через `httpClientProvider(opts, build)` factory; миграция на native `ConfigService.getOrThrow()`.
5. **Архитектурное разделение:** вынос `HttpSmokeClient` из `test/` в `infrastructure/clients/http-smoke/` — клиент остаётся production-ready артефактом, контроллер и smoke-модуль остаются в `test/` и удаляются перед релизом.

**Out of scope (deferred):**
- Application-wide logging refactor (отдельная будущая фаза).
- Финальное назначение `HttpSmokeClient` в prod (DiagnosticHttpClient / HealthProbe / Baseline — решится позже).
- Бизнес-логика Telegram/AppStoreSpy/CloudFn адаптеров (оставляется D-18 из фазы 24 — skeleton).
- Zod-валидация `res.json()` ответов (техдолг T11, помечается TODO).

**Carrying forward из Phase 24 (CONTEXT.md D-01..D-20):** все 20 решений остаются в силе, кроме **D-15 reshape** (Pino-логирование переходит с `PinoLogger.root.child` workaround на DI-порт `HttpClientLogger`).

<decisions>
## Implementation Decisions

### Архитектурная декомпозиция (ports + adapters)

- **D-01:** `AbstractHttpClient` становится **тонким orchestrator** (~80-100 строк вместо 240). Принимает через constructor param-bag `HttpClientDeps { cls, logger, executor, retry, breaker, baseUrl, defaultTimeoutMs, logContext }` и делегирует работу коллабораторам.
- **D-02:** **`HttpRequestExecutor` class** (`client/request-executor.ts`) — выполняет одну HTTP-попытку: fetch + `AbortSignal.timeout` + `res.ok` check + log emit + error normalization. Не знает про retry или CB. Коллаборатор AbstractHttpClient через constructor.
- **D-03:** **`RetryExecutorPort` + `DefaultRetryExecutor` adapter** (`retry/retry-executor.port.ts`, `retry/default-retry-executor.ts`) — порт с методом `run<T>(attempt: () => Promise<T>, policy: RetryPolicy): Promise<T>`. Реализация применяет `shouldRetry` + `backoffWithJitter` через `RetryPolicyResolver`. Меняет раннее решение «RetryPolicy не декомпозируем» — теперь через port для testability и декларативности.
- **D-04:** **`CircuitBreakerPort` + `OpossumCircuitBreakerAdapter`** (`circuit-breaker/circuit-breaker.port.ts`, `circuit-breaker/opossum-circuit-breaker.adapter.ts`) — порт с методом `fire<T>(exec: () => Promise<T>): Promise<T>` и `get state: CircuitState`. Адаптер инкапсулирует opossum + consecutive-counter в **одном классе** (убирает holder-object `ref.breaker?.open()` smell). Меняет раннее решение «CB не декомпозируем».
- **D-05:** **`HttpClientLogger` port + `PinoHttpClientLoggerAdapter`** (`logger/http-client-logger.port.ts`, `logger/pino-http-client-logger.adapter.ts`) — **Domain-specific** интерфейс с двумя типизированными событиями: `call(fields: HttpClientLogFields)` и `transition(fields: CircuitTransitionLogFields)`. Level-логика (`status === 'OK' ? 'info' : 'error'`) и event-name константы живут **в адаптере**, не в AbstractHttpClient.
- **D-06:** Решение D-05 — промежуточное до будущей фазы application-wide logging. Port shape совместим с тем чтобы не ломать публичный интерфейс при миграции.

### Иерархия ошибок + нормализация

- **D-07:** **`HttpClientError` abstract base class** (`errors/http-client.error.ts`) — общий предок для `HttpError`, `TimeoutError`, `NetworkError`, `CircuitOpenError`. Поля `kind: 'http' | 'timeout' | 'network' | 'circuit-open'` + `context: { url: string; api?: string }`. Адаптеры могут делать `if (err instanceof HttpClientError)` для унифицированной обработки.
- **D-08:** `NetworkError.cause` — через native `ErrorOptions.cause` (Node 16.9+), не через поле `readonly cause: unknown`. Убирает type cast `(err as TypeError & { cause: unknown }).cause`.
- **D-09:** **`HttpErrorNormalizer` class** (`errors/http-error-normalizer.ts`) — chain-of-mappers pattern. Массив `ErrorMapper[]` с методами `matches(err)` + `map(err, ctx)`. Добавление нового типа ошибки = добавление mapper'а в массив, без правки if/else цепочки. Замена `normalizeError` функции из `retry.policy.ts`.

### Retry policy (отдельный модуль)

- **D-10:** `retry.policy.ts` расформировывается — чистые функции `resolveRetryPolicy`, `shouldRetry`, `backoffWithJitter`, `sleep` переезжают в `retry/` директорию как `retry-policy.resolver.ts`, `retry-policy.classifier.ts`, `retry-backoff.ts`, `sleep.ts`. `normalizeError` переезжает в `errors/` (D-09).
- **D-11:** `shouldRetry` остаётся instanceof-guard'ами (4 ветки без общего predicate). Это **не** нарушение branching-patterns skill — это type classification, не поведенческий switch.

### Circuit breaker (отдельный модуль)

- **D-12:** `circuit-breaker.factory.ts` → `circuit-breaker/opossum-circuit-breaker.adapter.ts`. Consecutive-counter и opossum breaker инкапсулируются в **одном классе**; holder-object (`ref.breaker?.open()`) + inline mutable state (`let consecutiveFailures`) исчезают. Класс имеет `dispose()` для cleanup event listeners (полезно в тестах).
- **D-13:** Fragile substring match `'Breaker is open'` (`HTTP_CLIENT_CB_BREAKER_OPEN_MESSAGE_SUBSTRING`) становится **приватной деталью** `OpossumCircuitBreakerAdapter`. Внешним API не экспонируется. `CircuitBreakerPort.fire()` сам бросает `CircuitOpenError` — AbstractHttpClient больше не делает double-check `breaker.opened || err.message.includes(...)`.

### Constants — split по темам

- **D-14:** `http-client.constants.ts` расформировывается. Новая структура по поддиректориям:
  - `client/constants.ts` — `HTTP_CLIENT_LOG` (log event names, публичный)
  - `client/request.constants.ts` — `HTTP_CLIENT_HEADERS { CONTENT_TYPE, APPLICATION_JSON }` (НОВОЕ, решает magic values из `abstract-http.client.ts:205`)
  - `retry/constants.ts` — `RETRY_DEFAULTS`, `IDEMPOTENT_METHODS`, `RETRYABLE_STATUS_MIN`
  - `circuit-breaker/constants.ts` — `CB_DEFAULTS`, `CB_BREAKER_OPEN_MESSAGE_SUBSTRING` (internal)
  - `errors/constants.ts` — `TIMEOUT_ERR_NAMES` (internal к `HttpErrorNormalizer`)
- **D-15:** `HTTP_CLIENT_DEFAULTS.TIMEOUT_MS` (5000) и прочие дефолты остаются hardcoded framework-defaults — документируется как «адаптеры могут переопределять per-construction через `HttpClientDeps.defaultTimeoutMs`». Не выносится в env, так как это framework-level дефолт, не приложенческая конфигурация. Если в будущем понадобится env-override — добавится `HTTP_CLIENT_TIMEOUT_MS` env-var (out of scope 24.1).

### Barrel exports cleanup

- **D-16:** `packages/foundation/src/external/http/index.ts` экспортирует **только consumer-facing** API:
  - `AbstractHttpClient`, `HttpClientDeps` (для наследников)
  - `httpClientProvider` factory helper (D-22)
  - `HttpClientError` base + все 4 конкретные ошибки
  - `HttpCallOpts`, `CircuitState`, `HttpMethod`, `HttpClientLogFields`, `CircuitTransitionLogFields`
  - `HTTP_CLIENT_LOG` (нужен адаптерам-расширителям логгера)
  - `CB_DEFAULTS`, `RETRY_DEFAULTS` (используются per-service модулями через httpClientProvider)
  - Типы портов `RetryExecutorPort`, `CircuitBreakerPort`, `HttpClientLogger` (для кастомных адаптеров)
- **D-17:** Убрать из публичного API: `HTTP_CLIENT_IDEMPOTENT_METHODS`, `HTTP_CLIENT_RETRYABLE_STATUS_MIN`, `HTTP_CLIENT_TIMEOUT_ERR_NAMES`, `HTTP_CLIENT_CB_BREAKER_OPEN_MESSAGE_SUBSTRING` — они internal.

### Type safety — устранение `!` и излишних `?.`

- **D-18:** **Все `config.get<string>(KEY)!`** заменяются на `config.getOrThrow<string>(KEY)` (native NestJS 11 API). Затрагивает 4 файла:
  - `apps/notifier/src/infrastructure/clients/telegram/telegram.module.ts:14, 21`
  - `apps/parser/src/infrastructure/clients/appstorespy/appstorespy.module.ts`
  - `apps/sender/src/infrastructure/clients/cloud-functions/cloudfn.module.ts`
  - `apps/gateway/src/test/http-smoke/http-smoke.module.ts` (после переноса — сам импорт остаётся)
- **D-19:** **Хелпер `getRequiredString` НЕ создаётся** — native `ConfigService.getOrThrow()` покрывает use case. Меняет T6 из раннего плана.
- **D-20:** **Optional chaining `?.` минимизируется** через инварианты constructor. Holder-object `ref.breaker?.open()` исчезает при инкапсуляции CB в класс (D-12). Oстающиеся `?.` только там где действительно опциональное значение (`opts.retries ?? DEFAULT`, `opts.headers ?? {}`).

### Declarative branching

- **D-21:** Императивные `if-instanceof`-цепочки заменяются на **chain-of-mappers / Record dispatch** где это уменьшает сложность:
  - `normalizeError` → chain `ErrorMapper[]` (D-09)
  - Level-выбор в логгере (`status === 'OK' ? 'info' : 'error'`) инкапсулируется в адаптере логгера (D-05)
  - `shouldRetry` — **остаётся** instanceof chain (4 типизированных guard'а без общего predicate, замена на Map полиморфно не читаемее)

### httpClientProvider factory (устранение дублирования 4 модулей)

- **D-22:** **`httpClientProvider(opts, build)` factory-function** в foundation (`provider/http-client.provider.ts`):
  ```typescript
  httpClientProvider({
    token: symbol;
    logContext: string;
    baseUrlEnvKey: string;
    timeoutMs?: number;
    cb?: Partial<CbOptions>;
  }, build: (deps: HttpClientDeps & { config: ConfigService }) => T): Provider
  ```
  Foundation резолвит общие deps (logger, executor, retry, breaker, baseUrl через `getOrThrow`, timeout, cbOptions) и передаёт их в callback. User-land делает `new Client(deps, vendor_specific_args...)` с **полной типизацией** constructor call.
- **D-23:** **Per-vendor модули остаются** (TelegramClientModule / AppStoreSpyClientModule / CloudFnClientModule / HttpSmokeModule) — семантическая граница сервиса, место для будущих vendor-specific interceptor'ов. Модуль становится ~10 строк вместо 16.

## Existing Code Insights

### Reusable Assets
- **`@nestjs/config` 4.0.3 `ConfigService.getOrThrow<T>(key)`** — native API для типизированного required-env access. Устраняет необходимость в собственном `getRequiredString` helper (D-18, D-19).
- **`nestjs-cls` 6.2.0** — `ClsService` глобально подключён. Correlation ID резолвится через `cls.getId()` в логгере — уже работает в текущем `AbstractHttpClient`, паттерн переносится в адаптер логгера.
- **`nestjs-pino` 4.6.0** — `PinoLogger.root.child({ context })` паттерн (Pitfall 6 из Phase 23) инкапсулируется в `PinoHttpClientLoggerAdapter.onModuleInit()`. Новые адаптеры не должны повторять этот workaround.
- **`opossum` 9.x** — зависимость foundation, остаётся. `OpossumCircuitBreakerAdapter` инкапсулирует все opossum-specific обходы (timeout:false, errorFilter:()=>true, consecutive-counter wrapper).
- **Phase 23 `AbstractGrpcClient` + `createDeadlineInterceptor`** — структурный прецедент для ports+adapters в foundation. Логика "lifecycle-hook для lazer init" переносится.

### Established Patterns
- **Foundation external/ vs internal/ partition** (Phase 22.1) — публичный API через `@email-platform/foundation/index`. Новая структура HTTP-слоя остаётся в `external/http/` с подразбиением по папкам (`client/`, `retry/`, `circuit-breaker/`, `logger/`, `errors/`, `provider/`).
- **Symbol.for() DI tokens** — все новые токены (`HTTP_CLIENT_LOGGER`, `HTTP_REQUEST_EXECUTOR`, `RETRY_EXECUTOR`, `CIRCUIT_BREAKER`) через `Symbol.for(...)` (D-20 из фазы 24).
- **`forRoot()` DynamicModule pattern** — per-vendor модули (`TelegramClientModule.forRoot()`, ...) сохраняют этот паттерн (D-23).
- **Per-service `infrastructure/clients/{vendor}/`** — Clean/Hexagonal boundary сохраняется (HttpSmokeClient тоже переезжает в infrastructure/clients/).
- **Structured logging через Pino** — `{ api, method, url, duration_ms, status_code, correlationId }` fields остаются, меняется только механизм доставки (через port).

### Integration Points
- **Per-service модули** получают новые deps через `httpClientProvider` callback (D-22) — изменения в 4 модулях (telegram, appstorespy, cloudfn, http-smoke).
- **Per-service client constructors** меняются с позиционных аргументов на `(deps: HttpClientDeps, ...vendorArgs)` — 4 client-файла.
- **`config.getOrThrow<string>(KEY)`** применяется в module factories (D-18) — 4 файла.
- **`docs/runbooks/env-setup.md`** — новый файл, детальная матрица окружений (D-32, single source).
- **`.env.docker.example`** — новый tracked шаблон; `.env.docker` становится uncached (`git rm --cached`).

<specifics>
## Specific Ideas

- "Избегать восклицательных и вопросительных знаков" — `!` (non-null assertion) убрать все без исключения; `?.` (optional chaining) оставить только там где значение действительно optional по типу, не как обход плохой модели.
- "Код должен быть хорошо декомпозирован и быть простым, возможно более декларативным" — ключевой принцип. Chain-of-mappers для error normalization, port+adapter для CB/Retry/Executor/Logger, param-bag `HttpClientDeps` вместо длинных позиционных конструкторов.
- CB/Retry решение **меняется** — в предыдущем обсуждении было «не декомпозируем», теперь **делаем через порты** — это результат ревизии после анализа архитектурной чистоты кода.
- `native ConfigService.getOrThrow()` вместо собственного `getRequiredString` helper — находка во время дискуссии, меняет T6 из прошлого плана.
- HttpSmokeClient сохраняет имя, просто разделяется concerns: конфиг+класс в infrastructure/, использование (модуль+контроллер) в test/. Удаление `test/` перед релизом не затрагивает клиент.
- `.env.docker.example` — вариант B (готовый к `cp` + 5 secrets), не A (всё placeholder). Ускоряет onboarding с ~10 минут до ~2.
