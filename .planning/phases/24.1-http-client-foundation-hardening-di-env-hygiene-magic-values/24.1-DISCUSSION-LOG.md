## createHttpClientProvider signature

| Option | Description | Selected |
|--------|-------------|----------|
| Factory-функция + callback | `httpClientProvider(opts, build)` — foundation резолвит общие deps, user-land пишет `new Client(...)` с полной типизацией. Per-vendor модули сохраняются. ~15 строк user-land на клиент. | ✓ |
| DynamicModule `HttpClientModule.forClient(...)` | Foundation возвращает готовый DynamicModule. Per-vendor модули исчезают. ~7 строк, но ослаблена типизация (`extraArgs: unknown[]`), NotifierModule знает про конструктор TelegramClient — размывает Clean boundary. | |

**User's choice:** Factory-функция + callback (Recommended).
**Notes:** Причины выбора: полная типизация constructor call, per-vendor module boundary сохраняется, Clean boundary не размывается. Затрагивает 4 файла: telegram.module.ts, appstorespy.module.ts, cloudfn.module.ts, http-smoke.module.ts.

## Full architectural refactor scope (финальная итерация)

После уточнения пользователя: «Код нужно разбить, избегать сложных ветвлений, восклицательных и вопросительных знаков, код должен быть хорошо декомпозирован и быть простым, возможно более декларативным» — полная переоценка scope.

### Scope split

| Option | Description | Selected |
|--------|-------------|----------|
| Всё в 24.1 | Одной фазой: R1-R12 (полная DI-декомпозиция) + T1/T3/T8/T9/T10/T11. Атомарно, per-service модули переписываются раз. ~4-6h. | ✓ |
| Split 24.1 + 24.2 | 24.1: security + mechanical + internal refactor (no breaking). 24.2: полная DI-декомпозиция + декларативные паттерны. | |
| Split 24.1/24.2/24.3 | Три маленьких PR'а: security, internal refactor, DI-порты. | |

**User's choice:** Всё в 24.1 (Recommended).

### Изменённые ранее решения

- **Ранее:** «CB и RetryPolicy НЕ декомпозируем через DI (overengineering для стабильного выбора opossum)».
- **Теперь:** CB через `CircuitBreakerPort` + `OpossumCircuitBreakerAdapter` (D-04), Retry через `RetryExecutorPort` + `DefaultRetryExecutor` (D-03). Причина: пользователь явно запросил декомпозицию и декларативность как приоритет над компактностью.
- **Ранее:** «T6 — создать `getRequiredString(config, key)` helper».
- **Теперь:** использовать native NestJS 11 `ConfigService.getOrThrow<T>(key)` (D-18, D-19). Причина: native API полностью покрывает use case, свой helper не нужен.

### Декларативные паттерны — applied in scope

- Chain-of-mappers для `normalizeError` (D-09) — массив `ErrorMapper[]` вместо if-instanceof chain.
- Level-логика в адаптере логгера (D-05) — вынесена из AbstractHttpClient.
- CB-port инкапсулирует `CircuitOpenError` throw (D-13) — убирает double-check `breaker.opened || substring`.
- `HttpClientDeps` param-bag вместо длинных позиционных конструкторов (D-01, D-22).
- Constants split по темам (D-14) — каждый концепт в своей директории.

### Сохранено без декомпозиции

- `shouldRetry` (D-11) — instanceof chain из 4 типизированных guard'ов. Type classification, не поведенческий switch. Замена на Map/polymorphism не улучшает читаемость.
