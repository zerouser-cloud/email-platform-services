## Implementation Decisions

### ESLint ban scope (V2)

- **D-01:** ESLint `from 'pg'` ban applies to **BOTH Override 4 (`apps/*/src/**`) AND Override 5 (`apps/*/src/infrastructure/**`)** — stricter than the symmetric ioredis pattern. Rationale: PG_POOL has zero legitimate consumers; the ioredis Override-4-only pattern exists because REDIS_CLIENT has a narrow-unlock consumer (`@nest-lab/throttler-storage-redis` in gateway throttle, Phase 999.12 D-13) — PG_POOL has no equivalent. Banning in BOTH overrides reflects the actual zero-consumer status and makes any future narrow-unlock require three explicit reversals (foundation comment + re-add export + carve a path-specific ESLint exception), making the unlock decision traceable at lint time.

### JSDoc references in apps

- **D-02:** `apps/auth/src/infrastructure/outbound/persistence/persistence.module.ts:7` AND `apps/audience/src/infrastructure/outbound/persistence/persistence.module.ts:8` JSDoc lines currently list `DRIZZLE/PG_POOL/PERSISTENCE_HEALTH` as foundation public outputs. After V1, `PG_POOL` is no longer public — leaving the JSDoc as-is is factually wrong, not just stale. Update both JSDoc lines to describe the actual post-V1 state. **Suggested wording (planner may refine):**
  ```
  foundation's PersistenceModule (which provides DRIZZLE + PERSISTENCE_HEALTH publicly;
  PG_POOL kept foundation-internal per Phase 999.19 F-02).
  ```
  This describes reality (the user's framing: «if it's forbidden in this context, that's what should be written»). Files added to V1 commit (not separate commit per D-03).

### Atomic commit boundary

- **D-03:** **2 atomic commits**, NOT 3, NOT 1.
  - **Commit 1 — V1 + apps JSDoc (4 files, "close public-API surface"):**
    - `packages/foundation/src/external/persistence/index.ts`
    - `packages/foundation/src/external/persistence/persistence.module.ts`
    - `apps/auth/src/infrastructure/outbound/persistence/persistence.module.ts`
    - `apps/audience/src/infrastructure/outbound/persistence/persistence.module.ts`
  - **Commit 2 — V2 (1 file, "regression-proof at lint time"):**

  - Rationale: V1 + JSDoc form one logical change (closing the leak surface includes documenting the new state). V2 is a separate concern (regression-proofing, not the fix itself). Each commit independently revertable while leaving the codebase in a meaningful state — revert V2 leaves PG_POOL still private (V1 stays); revert V1+JSDoc reopens the leak as a known regression. 3 commits dilute the conceptual unity; 1 commit conflates fix with regression-guard.
