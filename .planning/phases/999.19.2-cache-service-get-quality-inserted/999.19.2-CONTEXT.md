## Implementation Decisions

### Variant choice (Area 1)

- **D-01: V1 (A1+B1+C3) locked.** `RedisCacheService.get<T>(key, schema?: ZodType<T>): Promise<CacheGetResult<T>>` where `CacheGetResult<T>` is a discriminated union over `status: 'absent' | 'corrupt' | 'value'`. Optional Zod schema parameter on the existing method (B1, not a new method). Severity-aware logging (C3) — `logger.warn` on schema-mismatch (data-evolution-class signal), `logger.error` on JSON.parse failure (structural-corruption-class signal). `del(key)` self-heal in BOTH corrupt branches.

  **Rationale:** Verified before lock that V1 is the only one of {V1, V2, V4} that holds full **5-layer infrastructure symmetry** with L2 Persistence (`Drizzle` Tier 1 throws), L3 Storage (`AWS SDK` throws), L4 gRPC clients (`Promisified<T>` throws). All four layers' Tier 1 surfaces signal protocol/data failures back to caller; only L1 Cache currently swallows them. V1 closes that asymmetry without breaking single-Tier-1-method discipline. V2 (dual-method API `get<T>` + `getValidated<T>`) breaks single-method symmetry — Drizzle has no «validating select», Promisified has no «validating call». V4 (caller-side validation, log-only) inverts the discipline — foundation hides nothing while pushing parse-validate-handle to every caller, opposite of what L2/L3/L4 do.

- **D-02: Backward-compatible no-schema path preserved.** When caller does NOT pass `schema?`, V1 returns `{status: 'value', value: parsed as T}` after JSON.parse — i.e., happy-path behaves like the current code (unchecked `as T` cast). The cast is acknowledged as the optional-schema cost; opting into runtime safety is caller-controlled. Foundation does NOT force Zod adoption.

### Logger surface (Area 2)

- **D-03: PinoLogger via DI.** `RedisCacheService` constructor changes from `(redis: Redis, namespace: string)` to `(redis: Redis, logger: PinoLogger, namespace: string)`. Logger context set via `this.logger.setContext(RedisCacheService.name)` in the constructor. Symmetric to the dominant foundation pattern (6 foundation classes use `PinoLogger` via DI: `correlation.interceptor`, `rpc-exception.filter`, `grpc-to-http.filter`, `http-timing.interceptor`, `grpc-logging.interceptor`, `pino-http-client-logger.adapter`). Correlation ID propagates through `nestjs-cls` automatically — no manual wiring needed.

  **Reachability:** `LoggingModule.forGrpcAsync('{svc}')` is imported in every root `{svc}.module.ts` BEFORE `{Svc}CacheModule`, making `PinoLogger` globally available in the DI scope where `cacheServiceProvider` factory runs. Verified by grep — no app `{svc}.module.ts` violates this ordering.

- **D-04: Reject `@nestjs/common` Logger and console fallbacks.** `new Logger()` from `@nestjs/common` does NOT route through Pino transport, does NOT carry correlation ID via CLS, is NOT structured JSON. The single foundation site that uses it (`drizzle-shutdown.service.ts`) is an outlier and will be brought into symmetry in a future phase, not by following its drift here. `console.*` is unacceptable for an infrastructure-layer service.

### Corrupt branch shape (Area 3)

- **D-05: Sub-discriminated `reason` on corrupt.** `CacheGetResult<T>['corrupt']` carries `reason: 'json-parse' | 'schema-mismatch'`. Symmetric with how L2/L3/L4 expose failure sub-discrimination: gRPC `RpcException.code` (`UNAVAILABLE`, `DEADLINE_EXCEEDED`), Postgres `PostgresError.code` (`23505`, `40P01`), AWS SDK error classes (`NoSuchKey`, `AccessDenied`). Caller can build per-reason metrics/recovery without parsing logs.

- **D-06: Do NOT leak raw error / Zod issues through the port.** The `corrupt` branch carries ONLY the `reason` tag, never the underlying `SyntaxError` / `ZodError`. Raw error stays foundation-internal — logged with full structure but not exposed in `CacheGetResult`. This keeps the Tier 1 contract independent of `zod`'s issue shape (port not bound to `zod@4` internals), symmetric with how `Promisified<T>` exposes only `RpcException.code` not the raw transport buffer.

### Discriminated-union shape — final type contract

- **D-07: Final shape (locked):**
  ```typescript
  export type CacheGetResult<T> =
    | { readonly status: 'absent' }
    | { readonly status: 'corrupt'; readonly reason: 'json-parse' | 'schema-mismatch' }
    | { readonly status: 'value'; readonly value: T };
  ```
  String-literal discriminators (`'absent' | 'corrupt' | 'value'`, `'json-parse' | 'schema-mismatch'`) are type literals — explicitly allowed under the project no-magic-values exception («type literals, import paths, 0/1/-1 idioms, log messages» are out-of-scope of the skill). Planner does NOT wrap them in const objects.

### Branching discipline at caller-side (Area 1 follow-up)

- **D-08: Caller dispatch on `status` follows `branching-patterns` skill.** No `switch (result.status)` — that's behavior selection by key with 3+ branches, prohibited. Allowed shapes for callers:
  - **guard clause** for two-target collapse: `if (result.status !== 'value') return null; return result.value;`
  - **ternary** for inline narrow: `return result.status === 'value' ? result.value : null;`
  - **Record dispatch** (Pattern 1) when behavior genuinely differs across all three branches: `Record<CacheGetResult<T>['status'], (r) => …>` — only when needed.
  - The choice between guard clause / ternary / Record is local to each caller and decided in their own phase. THIS phase contributes ZERO callers.

- **D-09: Foundation-side `get<T>` body is guard-clauses-only — no `switch`, no 3+ if/else chain.** Sequential null check → try/catch around JSON.parse → optional schema guard → safeParse outcome guard → fall-through to value return. Each `if` is a guard / null check / early return, allowed by the skill.
