## Overview

Plan 03 is an inline-amendment fix closing the single re-review-surfaced finding **WR-A-01** (`999.19.2-REVIEW.md` post-Plan-02 re-review): Plan 02's lazy logger getter `private get logger() { if (!this._logger) ... }` is vulnerable to **Pitfall 6** (Phase 23, documented verbatim in `pino-http-client-logger.adapter.ts:4-8`) — `PinoLogger.root` is `undefined` until `LoggerModule.onModuleInit()` populates it; a future business-cache caller invoking `cache.get()` from another module's `onModuleInit()` (eager warm-up scenario) would hit `TypeError: Cannot read properties of undefined (reading 'child')`.

The mirror principle is load-bearing: future Phase 999.20 (Logger Port Design) will grep both adapter sites and unify them synchronously when the canonical pattern lands; identical shape eliminates false negatives.

## Findings Closed

### WR-A-01 — Pitfall-6 vulnerability in lazy logger getter (BLOCKER closed)

**REVIEW.md cross-ref:** `999.19.2-REVIEW.md` § WR-A-01 (post-Plan-02 re-review section).

**Root cause:** Plan 02's lazy getter pattern `private get logger() { if (!this._logger) { this._logger = PinoLogger.root.child(...); } return this._logger; }` defers logger construction until first call-site touch — but if that first touch happens during ANOTHER module's `onModuleInit()` lifecycle hook (e.g., a future business-cache eager warm-up: `await this.cache.get('warm-cache-key')` from `MyService.onModuleInit()`), the `PinoLogger.root` static may STILL be `undefined`. NestJS lifecycle ordering is "all providers constructed → all `onModuleInit()` hooks fire in dependency order" — but the order between sibling `LoggerModule.onModuleInit()` and a feature module's `onModuleInit()` is not guaranteed by the NestJS contract. Pitfall 6 (Phase 23) documented this exact race; `PinoHttpClientLoggerAdapter` chose the `OnModuleInit + ensureInit()` mirror to make eager init explicit + retain the lazy fallback.

**Closure:** Mirror the http adapter pattern verbatim. Three-layer protection:
1. **Eager init via `onModuleInit()`**: when our module's `onModuleInit()` fires, `LoggerModule.onModuleInit()` has already completed (DI graph dependency ordering — `RedisCacheService` is composed via the foundation `CacheModule`, which transitively pulls `LoggerModule` higher in the DI graph). `this.ensureInit()` populates `this.logger` BEFORE any caller's `onModuleInit()` could possibly invoke `cache.get(...)` because all `onModuleInit()` hooks run AFTER all providers' `onModuleInit()`s have completed wave-by-wave through dependency depth.
2. **Lazy fallback via `this.ensureInit()` at top of `get<T>()`**: if any non-DI path constructs `RedisCacheService` (manual `new` for tests, edge-case factory paths), `onModuleInit()` never fires — but `get<T>()` calls `ensureInit()` first, so `this.logger` initialises on first cache read.
3. **Idempotent `ensureInit()`**: the `if (!this.logger)` guard makes repeated calls cheap (single field check + branch-not-taken; no allocation, no `child()` re-call).

Empirical validation: both `pnpm start:native` and `pnpm start:isolated` brought up all 6 services with `/health/ready` returning `cache: up`. Startup logs scanned for `Cannot read properties of undefined`, `Nest can't resolve`, `TypeError`, `FATAL` — zero matches related to `RedisCacheService` or cache logger init.

## Lessons Learned

- **Mirror precedent is cheap insurance against future migration drift.** Plan 03 chose IDENTICAL shape over "similar enough" — same identifier (`ensureInit`), same internal structure (`if (!this.logger)`), same TEMP marker placement. The marginal cost (~3 lines of decision-making during planning) buys mechanical Phase 999.20 migration. Compare to a paraphrased shape that would force Phase 999.20 to handle each site individually.
- **Pitfall 6 is sneaky because lazy getters LOOK safe.** A reviewer reading "lazy getter — initialises on first touch" plausibly concludes "the first touch is at runtime, well after bootstrap, safe." But "first touch" could be ANY caller's `onModuleInit()` (eager warm-up). The race window is bounded but real. The `OnModuleInit + ensureInit()` mirror closes it explicitly: our `onModuleInit()` fires AFTER `LoggerModule.onModuleInit()` (DI ordering invariant), so by the time any sibling's `onModuleInit()` could call `cache.get()`, our `this.logger` is populated.
- **Re-review cycles catch what initial review misses.** Plan 02's REVIEW.md flagged BL-01 + WR-01..04 + IN-01..03; the *re-review* (post-Plan-02) flagged WR-A-01 — a Pitfall-6 vulnerability that wasn't visible until Plan 02's lazy-getter shape was concrete. The pattern: after a plan with significant structural change, do a focused re-review against project pitfall catalogs (Phase 23 documented pitfalls 1-6+) before declaring the phase complete. Cost: one extra review round; benefit: catching hidden race windows.
- **TEMP marker relocation is metadata-aware refactoring.** The 4-line TEMP block migrated from above the removed getter to above the new `ensureInit()` method. Relocation kept the architectural anchor exactly grep-able once (D-11.B + D-12.C invariant: `grep -c "TEMP: foundation logger DI pattern"` = 1). Future Phase 999.20 grepping for this marker finds the right spot regardless of the structural migration history.
