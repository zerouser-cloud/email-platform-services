# Phase 999.19.2 — Code Review Report

**Reviewed:** 2026-05-07
**Depth:** standard
**Files Reviewed:** 4

## Summary

Фаза 999.19.2 закрывает F-01 (RedisCacheService.get() — quality issue): добавляется discriminated-union `CacheGetResult<T>`, optional Zod-валидация, severity-aware logging, и self-heal `del()` в обоих corrupt branches. Реализация в целом совпадает с PLAN.md (must_haves.truths) и контрактом D-01..D-09.

Однако обзор находит **1 BLOCKER** и **4 WARNING** — большинство связано с DI-bootstrapping и tier-1 contract semantics. Самая серьёзная проблема — **Scope.TRANSIENT bleed-through** через `useFactory(... PinoLogger ...)` в `cache.providers.ts`: PinoLogger декорирован `@Injectable({ scope: Scope.TRANSIENT })` (verified в `node_modules/.pnpm/nestjs-pino@4.6.1/.../PinoLogger.js:123`), и при инъекции TRANSIENT-провайдера в фабрику NestJS делает сам провайдер CACHE_SERVICE **тоже TRANSIENT**. Это ломает singleton-инвариант `RedisCacheService` (cache state per-resolution) и плохо ложится на текущее `useExisting: RedisHealthIndicator → REDIS_CLIENT` архитектурное предположение — фабрика теперь конструирует новый RedisCacheService на каждый `@Inject(CACHE_SERVICE)`. RESEARCH.md сам пометил это как Landmine #1 и пропустил тест эмпирического поведения, делегировав смок-гейтом G-04/G-05.

Дополнительно: comment в `cache.interfaces.ts:23` остался устаревшим (упоминает "narrow config re-export" но фактически тип re-export расширился без обновления назначения), `prefixKey(key)` дважды вычисляется в hot-path `get()`, и нет защиты от `JSON.parse(raw) === null` (валидный JSON `"null"` пройдёт `if (raw === null)` сторону и попадёт в schema.safeParse как `null`, который Zod разрешит для `z.null()` или `z.unknown()` schemas — но без schema вернётся `{ status: 'value', value: null as T }` — потенциальный type-system gotcha).

## Blockers

### BL-01: TRANSIENT scope bleed-through через useFactory(PinoLogger) делает CACHE_SERVICE per-injection-scope

**File:** `packages/foundation/src/external/cache/cache.providers.ts:28-33`
**Issue:**
`PinoLogger` из `nestjs-pino@4.6.1` декорирован `@Injectable({ scope: Scope.TRANSIENT })` (verified at `node_modules/.pnpm/nestjs-pino@4.6.1*/nestjs-pino/PinoLogger.js:123`). Согласно [NestJS DI scope hierarchy rules](https://docs.nestjs.com/fundamentals/injection-scopes#scope-hierarchy), если `useFactory.inject` содержит TRANSIENT-провайдера, **сам factory provider становится TRANSIENT**:

> "Custom providers that depend on transient providers themselves become transient (unless explicitly marked otherwise)."

Текущий код:

```typescript
const cacheServiceProvider: Provider = {
  provide: CACHE_SERVICE,
  inject: [REDIS_CLIENT, PinoLogger],
  useFactory: (redis: Redis, logger: PinoLogger): RedisCacheService =>
    new RedisCacheService(redis, logger, options.namespace),
};
```

Последствия:
1. **Каждый `@Inject(CACHE_SERVICE)` получает свежий `RedisCacheService` instance.** В текущей фазе callers = 0, поэтому смок-тест G-04/G-05 не обнаружит regression — health/ready не использует `CACHE_SERVICE`. Future business-cache consumer словит surprising behaviour: per-request RedisCacheService construction overhead + потенциально per-request `setContext` race (мельтешение контекста в логах при concurrent requests).
2. **`useExisting: RedisHealthIndicator` для `CACHE_HEALTH` (строка 36-38) НЕ затрагивается** — `RedisHealthIndicator` injects `REDIS_CLIENT` напрямую, не через `CACHE_SERVICE`. Архитектурный baseline сохраняется, но это уже **разные scopes**: HEALTH = singleton, CACHE_SERVICE = TRANSIENT. Это нарушение симметрии 5-layer infrastructure invariant ("L1 Cache Tier-1 surface = singleton, как L2 Drizzle DRIZZLE"), на котором строится phase 999.19.

**Verification gap:** RESEARCH.md L1 явно отметил это как landmine и пропустил эмпирическую верификацию: "NestJS supports it syntactically; smoke gate at boot is the verification." Smoke gate G-04 проверяет только READY-state, а не singleton-семантику CACHE_SERVICE.

**Fix (выберите один):**

Вариант А (рекомендуется — соответствует D-04 нет console + D-03 PinoLogger):
Использовать `PinoLogger.root.child({ context: RedisCacheService.name })` лениво в конструкторе, без factory-inject TRANSIENT провайдера:

```typescript
import { PinoLogger } from 'nestjs-pino';
import type { Logger as PinoBaseLogger } from 'pino';

@Injectable()
export class RedisCacheService implements CachePort {
  private readonly prefix: string;
  private readonly logger: PinoBaseLogger;

  constructor(
    private readonly redis: Redis,
    namespace: string,
  ) {
    this.prefix = `${namespace}:`;
    this.logger = PinoLogger.root.child({ context: RedisCacheService.name });
  }
  // ...
}
```

И `cache.providers.ts` откатывается к pre-phase shape — singleton сохраняется.

Вариант B (явный scope override — менее предпочтительно):
Принудительно установить scope = DEFAULT на factory provider и подтвердить эмпирически, что NestJS не воспроизводит TRANSIENT поведение:

```typescript
import { Scope } from '@nestjs/common';

const cacheServiceProvider: Provider = {
  provide: CACHE_SERVICE,
  scope: Scope.DEFAULT,  // ← override TRANSIENT propagation
  inject: [REDIS_CLIENT, PinoLogger],
  useFactory: (redis, logger) => new RedisCacheService(redis, logger, options.namespace),
};
```

⚠️ Документация NestJS не гарантирует это работает — overriding scope inheritance запрещено в [официальном FAQ](https://docs.nestjs.com/fundamentals/injection-scopes). Требует эмпирической верификации (boot test + 2 sequential `@Inject(CACHE_SERVICE)` в test consumer + `===` reference equality check). Если фейлится — Вариант A обязателен.

**Severity rationale:** BLOCKER, не warning, потому что:
- (а) F-01 явный goal — "L1 cache в 5-layer infrastructure symmetry" с другими singleton tier-1 (DRIZZLE, S3 client, gRPC clients);
- (б) первый business-cache consumer (планируется в будущих фазах согласно SOLUTIONS.md) словит regression сразу;
- (в) verification gate G-04/G-05 в текущей фазе не покрывает scope check (0 callers → no observable behaviour);
- (г) правка "позже когда обнаружим" дороже, чем правка сейчас (миграция consumers).

## Warnings

### WR-01: prefixKey(key) вызывается до 4 раз в hot-path get() — code duplication + лишние string allocations

**File:** `packages/foundation/src/external/cache/cache.service.ts:21,31,45,48`
**Issue:**
В методе `get<T>` функция `this.prefixKey(key)` вызывается до 4 раз (строки 21, 31, 45, 48):

```typescript
const raw = await this.redis.get(this.prefixKey(key));      // 1
// ...
this.logger.error({ key: this.prefixKey(key), err }, ...);  // 2
// ...
this.logger.warn({ key: this.prefixKey(key), ...}, ...);    // 3 (только в schema-mismatch path)
```

Каждый вызов делает template literal allocation `${this.prefix}${key}`. При hot-path кэширования это лишнее. Также это дублирование логики (DRY violation) — один и тот же ключ вычисляется в 4 местах.

Кроме того, **`del(key)` сам делает префиксацию** (Landmine #4 в RESEARCH.md), так что внутри сервис делает префикс **5-6 раз** для одного логического вызова `get()` с corrupt entry.

**Fix:**
Вычислить prefixed key один раз в начале метода:

```typescript
async get<T>(key: string, schema?: ZodType<T>): Promise<CacheGetResult<T>> {
  const prefixed = this.prefixKey(key);
  const raw = await this.redis.get(prefixed);
  if (raw === null) {
    return { status: 'absent' };
  }

  let parsed: unknown;
  try {
    parsed = JSON.parse(raw);
  } catch (err) {
    this.logger.error({ key: prefixed, err }, 'cache: JSON.parse failed; deleting corrupt entry');
    await this.del(key);  // del() прав, prefixes сам
    return { status: 'corrupt', reason: 'json-parse' };
  }

  if (!schema) {
    return { status: 'value', value: parsed as T };
  }

  const result = schema.safeParse(parsed);
  if (!result.success) {
    this.logger.warn({ key: prefixed, issues: result.error.issues }, 'cache: schema mismatch; deleting corrupt entry');
    await this.del(key);
    return { status: 'corrupt', reason: 'schema-mismatch' };
  }

  return { status: 'value', value: result.data };
}
```

### WR-02: Edge case: `JSON.parse('null')` returns `null`, попадает в success path как `{ status: 'value', value: null as T }`

**File:** `packages/foundation/src/external/cache/cache.service.ts:38-40`
**Issue:**
Если в Redis сохранена строка `"null"` (валидный JSON для значения `null`), `raw` ≠ `null` (string `'null'`), `JSON.parse(raw)` succeeds и возвращает literal `null`. Без `schema?` параметра возвращается `{ status: 'value', value: null as T }` — `null` маскируется под `T`-typed value.

Это противоречит intuitive API contract ("`status: 'absent'`" должен покрывать "no meaningful value"). Caller с `schema = z.string()` получит `{ status: 'corrupt', reason: 'schema-mismatch' }` — корректно. Но caller без schema получит **typed `null` masquerading as T**, что приведёт к runtime NPE в downstream business logic (например, `result.value.someField` на null).

Это отчасти acknowledged D-02 ("happy-path behaves like the current code, unchecked `as T` cast"), но pre-phase implementation возвращал `T | null` (caller знал, что null возможен). Новая API возвращает `CacheGetResult<T>` без `null` варианта в `value` — поэтому API contract скрывает наличие `null`.

**Fix:**
Добавить guard на `parsed === null` после JSON.parse, перед возвратом success:

```typescript
let parsed: unknown;
try {
  parsed = JSON.parse(raw);
} catch (err) {
  // ...corrupt branch
}

// Guard: stored 'null' literal is treated as absent (or as a corrupt-equivalent)
if (parsed === null) {
  this.logger.warn({ key: prefixed }, 'cache: stored value is JSON null; treating as absent');
  await this.del(key);
  return { status: 'absent' };  // или { status: 'corrupt', reason: 'json-parse' }
}
// ...
```

Альтернатива — задокументировать в `CacheGetResult` что `value: T` может быть `null` runtime если caller сохранил `null` через `set()`. Это нарушает D-07 type contract.

### WR-03: `value: parsed as T` — unchecked cast в no-schema branch (pre-existing, но теперь явно part of contract)

**File:** `packages/foundation/src/external/cache/cache.service.ts:39`
**Issue:**
Строка 39: `return { status: 'value', value: parsed as T };`. Это double-unsafe: (1) `parsed: unknown` from JSON.parse, (2) явный cast `as T`, без runtime validation. D-02 acknowledges это как "optional-schema cost", но `as T` в production code на foundation-tier-1 контракте — серьёзный type-soundness compromise.

ESLint rule `@typescript-eslint/no-explicit-any` стоит на error в проекте (CLAUDE.md), но `as T` через generics ускользает от линтера.

**Fix:**
Один из двух вариантов:

Вариант А — мягкий (рекомендуется): добавить JSDoc warning над методом:

```typescript
/**
 * Get a cached value by key.
 *
 * **WARNING:** When called without `schema?`, the return value `{ status: 'value', value: T }`
 * carries an UNCHECKED type assertion (`parsed as T`). Caller is responsible for runtime
 * validation. Pass a `ZodType<T>` to enable schema-mismatch detection. See D-02 in
 * 999.19.2-CONTEXT.md.
 */
async get<T>(key: string, schema?: ZodType<T>): Promise<CacheGetResult<T>> { ... }
```

Вариант B — жёсткий: сделать `schema` обязательным параметром (breaking change, но безопасный по типам). Согласно CONTEXT.md D-02 это явно отвергнуто, но решение обоснования "Foundation does NOT force Zod adoption" не учитывает type-safety стоимость.

Поскольку D-02 locked, минимально — JSDoc warning (Вариант A).

### IN-01: setContext() side-effect в конструкторе — symmetric break с другими 6 PinoLogger sites в foundation

**File:** `packages/foundation/src/external/cache/cache.service.ts:17`
**Issue:**
RESEARCH.md явно отмечает (Landmine #2): "`setContext(RedisCacheService.name)` is a NEW convention site (0 prior `setContext` calls in foundation)". Все 6 reference foundation sites (correlation.interceptor, rpc-exception.filter, grpc-to-http.filter, http-timing.interceptor, grpc-logging.interceptor, pino-http-client-logger.adapter) НЕ вызывают `setContext` в конструкторе — они полагаются либо на (а) NestJS auto-context inference из inject site, либо (б) ручной `child({ context: ... })` для child loggers.

Это создаёт implicit "first-of-its-kind" pattern в foundation. Не bug, но точка симметрийного дрифта — future foundation classes могут начать копировать этот pattern, fragmenting the codebase.

**Fix (recommended for future phase, not BL):**
Добавить comment-обоснование рядом с `setContext` объясняющий, почему выбран именно этот pattern (vs `child()` или auto-inference):

```typescript
constructor(
  private readonly redis: Redis,
  private readonly logger: PinoLogger,
  namespace: string,
) {
  this.prefix = `${namespace}:`;
  // setContext() vs child(): factory-inject of TRANSIENT PinoLogger (D-03) gives a
  // dedicated instance per RedisCacheService — calling setContext is safe and
  // symmetric with NestJS conventions. See 999.19.2-CONTEXT.md L1 + Landmine #2.
  this.logger.setContext(RedisCacheService.name);
}
```

(Если BL-01 fix-A применится через `PinoLogger.root.child(...)` — этот info-комментарий устаревает автоматически.)

### IN-02: `del(key)` self-heal не блокирует ответ — fire-and-await — может маскировать Redis errors

**File:** `packages/foundation/src/external/cache/cache.service.ts:34,48`
**Issue:**
В обоих corrupt branches `await this.del(key)` происходит синхронно перед return:

```typescript
await this.del(key);
return { status: 'corrupt', reason: 'json-parse' };
```

Если Redis отвалится между `redis.get(...)` (succeeded) и `redis.del(...)` (network failure), `del()` бросит exception → весь `get()` промис rejects → caller получает unhandled exception вместо `{ status: 'corrupt', ... }`. Это нарушает D-06 inv "raw error stays foundation-internal" — caller словит low-level Redis error через rejection.

**Fix:**
Wrap `del` в try/catch:

```typescript
try {
  await this.del(key);
} catch (delErr) {
  this.logger.error({ key: prefixed, delErr }, 'cache: self-heal del() failed; corrupt entry persists');
}
return { status: 'corrupt', reason: 'json-parse' };
```

Это сохраняет contract `CacheGetResult` invariant — corrupt status всегда возвращается, независимо от self-heal success.

### IN-03: Inconsistent log key field — `key` вместо более явного `cacheKey` или `prefixedKey`

**File:** `packages/foundation/src/external/cache/cache.service.ts:31,45`
**Issue:**
Логи используют поле `key` для prefixed cache key:

```typescript
this.logger.error({ key: this.prefixKey(key), err }, '...');
this.logger.warn({ key: this.prefixKey(key), issues: ... }, '...');
```

В контексте многосервисного логирования (gateway/auth/sender/etc. все могут писать в один Loki/ELK aggregator), поле `key` слишком общее — сталкивается с RPC method-keys, Redis keys из других middleware, etc.

**Fix:**
Использовать более описательное имя:

```typescript
this.logger.error({ cacheKey: prefixed, err }, 'cache: JSON.parse failed; deleting corrupt entry');
this.logger.warn({ cacheKey: prefixed, issues: result.error.issues }, 'cache: schema mismatch; deleting corrupt entry');
```

Это улучшает grep/filter точность в production logs.
