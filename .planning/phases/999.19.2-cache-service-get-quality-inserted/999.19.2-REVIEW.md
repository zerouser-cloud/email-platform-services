## Warnings

### WR-A-01: Lazy logger getter — concurrent first-access race window (benign, but worth a note)

**File:** `packages/foundation/src/external/cache/cache.service.ts:24-29`
**Issue:**

Lazy getter:

```typescript
private get logger(): PinoBaseLogger {
  if (!this._logger) {
    this._logger = PinoLogger.root.child({ context: RedisCacheService.name });
  }
  return this._logger;
}
```

Поскольку Node.js однопоточный по runtime, между `if (!this._logger)` и `this._logger = ...` нет реального preemption — race не data-race. Однако **на первом `get(key)` вызове можно получить более одного re-entrant `this.logger` access** в одном tick (`logger.error(...)` вызывается дважды в schema-mismatch path: один раз для warn, потом в catch для self-heal del() error). Поведение детерминированное и benign — `PinoLogger.root.child(...)` идемпотентен в смысле "один child создаётся при первой установке `this._logger`, второй access уже видит cached".

Но есть тонкость: `PinoLogger.root` это accessor; если `LoggerModule.onModuleInit()` ещё не отработал к моменту первого `get<T>(...)` (например, manual-construction path или test bootstrap order), `PinoLogger.root` будет `undefined` → TypeError "Cannot read properties of undefined (reading 'child')". `pino-http-client-logger.adapter.ts` решает эту проблему явным `OnModuleInit.onModuleInit() → ensureInit()` гвардом (Pitfall 6 docstring там). Текущий `RedisCacheService` НЕ имплементирует `OnModuleInit` — полагается на то, что первый `get/set/del` вызов произойдёт после `LoggerModule.onModuleInit()`.

Для текущей фазы это OK потому что:
1. CACHE_SERVICE сейчас 0 callers (smoke-gate G-04/G-05 не использует кэш).
2. NestJS module init order гарантирует, что transitive `LoggerModule` инициализирован раньше, чем приложение начнёт обслуживать запросы.

Но **future business-cache consumer** может вызвать `get()` из другого `onModuleInit()` (eager cache warm-up, etc.) — там порядок не гарантирован, и `PinoLogger.root` может быть `undefined`. См. строки 4-8 в `pino-http-client-logger.adapter.ts`:

> "Pitfall 6 (Phase 23): `PinoLogger.root` is `undefined` until `LoggerModule.onModuleInit()` populates it."

**Fix (рекомендуется один из двух):**

Вариант А — добавить short-circuit guard на `PinoLogger.root` undefined (минимальное изменение, документирует риск):

```typescript
private get logger(): PinoBaseLogger {
  if (!this._logger) {
    // Pitfall 6: PinoLogger.root is undefined until LoggerModule.onModuleInit().
    // Defensive — defer caching if root not yet ready (rare; future eager-cache callers).
    const root = PinoLogger.root;
    if (!root) {
      // Return a minimal no-op or throw with explicit message; current shape would TypeError.
      throw new Error('RedisCacheService.logger accessed before LoggerModule init');
    }
    this._logger = root.child({ context: RedisCacheService.name });
  }
  return this._logger;
}
```

Вариант B — реплицировать `PinoHttpClientLoggerAdapter` shape: implement `OnModuleInit.onModuleInit()` который вызывает `ensureInit()`. Это даёт eager init при normal DI graph resolution и lazy fallback для manual-construction (последнего здесь нет, но симметрия с другим foundation адаптером ценна как precedent для future LoggerPort phase).

```typescript
@Injectable()
export class RedisCacheService implements CachePort, OnModuleInit {
  // ...
  onModuleInit(): void {
    void this.logger; // touch the getter to materialize _logger after LoggerModule init
  }
}
```

**Severity rationale:** WARNING (not BLOCKER): на текущей фазе с 0 callers симптом не наблюдается; runtime smoke-gate G-04/G-05 не покрывает. Тем не менее, **TEMP-маркер сам признаёт этот pattern as tactical** — фиксация Pitfall-6 защиты сейчас стоит дёшево и согласуется с prior-art (`pino-http-client-logger.adapter.ts`). Если LoggerPort Tier-1 phase (999.20) переписывает обращение всё равно — этот код будет переходным; но защита от Pitfall 6 для interim-period не лишняя.

Не BL-class потому что: (а) DI graph order гарантирует foundation-LoggerModule готов раньше CacheService.get-call в production HTTP/gRPC inbound flow; (б) 0 active callers; (в) фикс — 3-5 строк, low-risk.
