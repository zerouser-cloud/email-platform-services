**Researched:** 2026-05-07

## Summary

Все utверждения CONTEXT.md о файлах и номерах строк подтверждены побайтово. `cache.service.ts:16-26` действительно содержит unchecked `as T` cast + silent swallow. `cacheServiceProvider` в `cache.providers.ts:27-32` имеет ровно ту арность, что описана. `CacheGetResult<T>` правильно ляжет в существующий `cache.interfaces.ts` рядом с `CachePort` — никакого нового файла не нужно. Барель `index.ts` уже реэкспортирует `CachePort` через `export type {...}` блок — добавление `CacheGetResult` сводится к одной строке в существующем блоке.

Caller graph audit подтверждает «0 callers» из CONTEXT.md: `grep -rn 'CACHE_SERVICE\|CachePort'` в `apps/*/src` возвращает только импорты `CacheHealthIndicator` (Tier-1 health через bootstrap), `AppCacheModule` обёртки, и `CACHE_HEALTH` Symbol. Ни одного `@Inject(CACHE_SERVICE)`, ни одного `cache.get(...)`. Подпись метода можно менять без миграции вызовов.

`zod@^4.3.6` уже в `packages/foundation/package.json:35` (verified). Foundation уже импортирует `import { z } from 'zod'` в двух местах (`config/load-config.ts`, `config/create-config-module.ts`) — добавление `import type { ZodType } from 'zod'` в `cache.interfaces.ts` является нулевой dependency-cost change.

PinoLogger DI canonical shape извлечён из 6 указанных сайтов. **Самый чистый референс** — `grpc-logging.interceptor.ts:9` или `http-timing.interceptor.ts:9`: одностроковый constructor с `private readonly logger: PinoLogger`. Никакой из 6 канонических сайтов НЕ использует `this.logger.setContext(...)` — D-03 требует setContext, и это валидный публичный API метод (`PinoLogger.d.ts:43`), но создаёт новый convention в foundation. Это нормально, поскольку 6 существующих сайтов — это interceptors и filters (где context = method/handler name через ExecutionContext), а `RedisCacheService` — это long-lived service.

**Critical landmine surfaced:** `PinoLogger` декорирован `@Injectable({ scope: Scope.TRANSIENT })` (`PinoLogger.js:123`). Существующий код foundation НИГДЕ не инжектит `PinoLogger` через `useFactory.inject` — все 6 канонических сайтов используют constructor injection в обычные `@Injectable()` классы. Один прецедент в `http-client.provider.ts` СОЗНАТЕЛЬНО ИЗБЕГАЕТ инжекта PinoLogger в factory (Pitfall 6) и использует lazy `PinoLogger.root.child()` внутри adapter. Решение D-03 (инжект `PinoLogger` в `cacheServiceProvider.inject`) технически корректное, но создаёт новый прецедент. Альтернатива — манульно создать adapter в factory как делает `http-client.provider.ts`. Планнер/discuss должны принять решение осознанно.

**Primary recommendation:** Перед планированием явно подтвердить с пользователем: «PinoLogger через `useFactory.inject` создаёт новый прецедент в foundation (TRANSIENT-scope, ранее не использовался в factory). Альтернатива — `PinoLogger.root.child()` lazy внутри RedisCacheService onModuleInit (как делает `pino-http-client-logger.adapter.ts`)». Если пользователь подтверждает D-03 — fine, план идёт по нему; если нет — это меняет конструктор и factory shape.

### `packages/foundation/src/external/cache/cache.service.ts` (entire file — 39 lines, will become ~50 after V1)

```typescript
// Lines 1-14 — imports + class header + current constructor
import { Injectable } from '@nestjs/common';
import type Redis from 'ioredis';
import type { CachePort } from './cache.interfaces';

@Injectable()
export class RedisCacheService implements CachePort {
  private readonly prefix: string;

  constructor(
    private readonly redis: Redis,
    namespace: string,
  ) {
    this.prefix = `${namespace}:`;
  }

// Lines 16-26 — the body F-01 targets (CONTEXT.md claim verified verbatim)
  async get<T>(key: string): Promise<T | null> {
    const raw = await this.redis.get(this.prefixKey(key));
    if (raw === null) {
      return null;
    }
    try {
      return JSON.parse(raw) as T;        // ← line 22 — unchecked `as T` cast
    } catch {                             // ← line 23
      return null;                        // ← line 24 — silent swallow, no log, no del
    }
  }

  async set(key: string, value: unknown, ttlMs: number): Promise<void> {
    await this.redis.set(this.prefixKey(key), JSON.stringify(value), 'PX', ttlMs);
  }

  async del(key: string): Promise<void> {
    await this.redis.del(this.prefixKey(key));
  }

  private prefixKey(key: string): string {
    return `${this.prefix}${key}`;
  }
}
```

**Decisions confirmed:**
- D-01 — body 16-26 is the exact target. `as T` cast (line 22) + silent catch (lines 23-24) match AUDIT F-01 evidence exactly.
- D-02 — happy-path `JSON.parse(raw) as T` cast IS the «optional-schema cost» preserved.
- D-03 — current constructor is `(redis: Redis, namespace: string)` (lines 9-12). Becomes `(redis: Redis, logger: PinoLogger, namespace: string)` per CONTEXT.md «namespace last» (`<specifics>` 3rd bullet).
- D-09 — V1 body будет 4 sequential guard-clauses (null check → JSON.parse try/catch → optional schema guard → safeParse outcome guard) — нет `switch`, нет 3+ if/else цепочки.

## Landmines

### Landmine #1 — `PinoLogger` is `@Injectable({ scope: Scope.TRANSIENT })` (CRITICAL)

**Source:** `node_modules/.pnpm/nestjs-pino@4.6.1/.../nestjs-pino/PinoLogger.js:123` — `@Injectable({ scope: Scope.TRANSIENT })`.

**The trap:** В NestJS, когда factory provider инжектирует TRANSIENT-scoped provider в `useFactory.inject` array, NestJS resolution semantics могут быть surprising:
- Factory создаётся каждый раз заново при resolve consumer'а Tier-1 token.
- Если `cacheServiceProvider` теперь TRANSIENT-scoped транзитивно — это может изменить lifecycle `RedisCacheService` (был singleton, может стать TRANSIENT).
- Существующий `redisClientProvider` (`cache.providers.ts:16-25`) — singleton (Redis client должен быть singleton — connection pooling). Если `cacheServiceProvider` становится TRANSIENT, это нормально (service класс — value-object), но **ВАЖНО проверить Redis client остаётся одним**.

**No precedent in this codebase:**
- `grep -rn 'inject:.*PinoLogger\|PinoLogger.*useFactory'` → 0 matches across `packages/` + `apps/`
- Сценарий «factory provider inject PinoLogger» НИГДЕ не использовался в этом репо до сейчас.
- 6 канонических PinoLogger DI сайтов — все через constructor injection в обычные `@Injectable()` классы (не через factory).
- `packages/foundation/src/external/http/provider/http-client.provider.ts` СОЗНАТЕЛЬНО ИЗБЕГАЕТ inject PinoLogger в factory; использует lazy `PinoLogger.root.child()` внутри `pino-http-client-logger.adapter.ts` (Pitfall 6 documented в JSDoc этого adapter'а).

**Mitigation options (для discuss-phase, если planner хочет):**
1. **Option A (D-03 as written):** `inject: [REDIS_CLIENT, PinoLogger]` + factory `(redis, logger) => new RedisCacheService(redis, logger, options.namespace)`. Стандартный NestJS API; работает; создаёт новый прецедент.
2. **Option B (lazy root.child):** конструктор без `PinoLogger`, внутри `RedisCacheService.onModuleInit()` или lazy guard — `this.logger = PinoLogger.root.child({ context: RedisCacheService.name })`. Mirrors `pino-http-client-logger.adapter.ts` pattern. Не перепутывает scope.
3. **Option C (manual factory construction):** factory сам создаёт child logger — `useFactory: (redis: Redis) => new RedisCacheService(redis, PinoLogger.root.child({ context: 'RedisCacheService' }), options.namespace)`. Pitfall 6 documented — `PinoLogger.root` undefined до `LoggerModule.onModuleInit`, поэтому это ненадёжно если cacheServiceProvider runs до LoggerModule init.

**CONTEXT.md D-03 фиксирует Option A.** Это валидный architectural call; landmine — что это новый прецедент, не имеющий smoke verification из прошлых фаз. Runtime startup smoke (gate §«Validation Architecture») это покроет.

**Recommended action:** Planner создаёт Plan task explicitly fixating Option A + Validation gate с smoke verification. Если smoke падает с TRANSIENT-scope ошибкой — fall back to Option B (адаптер refactor).

### Landmine #2 — `setContext(RedisCacheService.name)` is a NEW convention in foundation

**Source:** `grep -rn 'setContext' packages/foundation` → 0 matches. Также 0 matches в `apps/`.

**The trap:** D-03 mandates `this.logger.setContext(RedisCacheService.name)` в конструкторе. Это валидный nestjs-pino API (`PinoLogger.d.ts:43`), но НИГДЕ в этом проекте не используется. Никаких практических примеров чтобы скопировать как код-snippet.

**Why it works:** `setContext()` присваивает `value` на field `protected context: string` экземпляра `PinoLogger`. Затем `call(method, ...)` использует это `context` чтобы стэмповать log entries. Standard nestjs-pino API.

**Mitigation:** Plan tasks включают verbatim line `this.logger.setContext(RedisCacheService.name);` после `this.prefix = ...` присваивания. Smoke verification покажет log-output корректный (logs должны иметь `"context":"RedisCacheService"` в JSON output).

Hard-link все три как один verifiable pattern.

### Landmine #4 — Accidental `as T` removal in happy path (D-02 violation)

**Source:** D-02 explicitly preserves the `as T` cast в no-schema branch.

**The trap:** Refactoring `get<T>` body, planner может «cleanly» убрать the unchecked cast — `JSON.parse(raw)` returns `unknown`, return without cast. TypeScript will complain (`unknown` not assignable to `T`). Planner solves by adding cast OR by mandating schema (breaks D-02). Right answer: keep `as T` cast в `value` branch when no schema.

**Mitigation:** Plan task для `cache.service.ts` body explicitly cites D-02 verbatim and shows the value-branch return as `{ status: 'value', value: parsed as T }`. Body skeleton:
```typescript
async get<T>(key: string, schema?: ZodType<T>): Promise<CacheGetResult<T>> {
  const raw = await this.redis.get(this.prefixKey(key));
  if (raw === null) {
    return { status: 'absent' };
  }
  let parsed: unknown;
  try {
    parsed = JSON.parse(raw);
  } catch (err) {
    this.logger.error({ key: this.prefixKey(key), err }, 'cache: JSON.parse failed; deleting corrupt entry');
    await this.del(key);
    return { status: 'corrupt', reason: 'json-parse' };
  }
  if (!schema) {
    return { status: 'value', value: parsed as T };       // ← D-02 cast preserved here
  }
  const result = schema.safeParse(parsed);
  if (!result.success) {
    this.logger.warn({ key: this.prefixKey(key), issues: result.error.issues }, 'cache: schema mismatch; deleting corrupt entry');
    await this.del(key);
    return { status: 'corrupt', reason: 'schema-mismatch' };
  }
  return { status: 'value', value: result.data };          // ← Zod-validated, no cast needed
}
```

**Note (this.del semantics):** `this.del(key)` calls existing method (cache.service.ts:32-34) — это значит `prefix` уже applied. Looking at `del()` body — `await this.redis.del(this.prefixKey(key));` — он сам вызывает `prefixKey`. То есть `this.del(key)` в новом get-теле проверяет: passed bare `key` (without prefix), `del()` add prefix. **Correct invocation: `await this.del(key);`** (NOT `this.del(this.prefixKey(key))` — это удвоит префикс).
