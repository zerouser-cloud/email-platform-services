### 2.1 L0 — Master invariant (Strict 3-zone + narrow-unlock)

Verbatim from CONTEXT.md D-A1, formatted as I-NN list:

- **I-0.1: Contracts zone purity** — `packages/contracts/src/` contains ONLY `*.proto`-generated TypeScript types and the `CONTRACTS_PROTO_DIR` constant. No business types, no DI tokens, no runtime logic. Vendor HTTP-skeleton types in `external/{vendor}/` — open question (see §1.6 + AUDIT pass).
- **I-0.2: Foundation = mechanisms zone** — `packages/foundation/src/external/<layer>/` exposes ONLY domain-agnostic shapes: factory functions, abstract base classes, Proxy builders, port interfaces, HealthIndicator/ShutdownService shapes. NO knowledge of specific business scenarios, NO knowledge of which service consumes what.
- **I-0.3: Apps = realisation + composition zone** — `apps/*/src/infrastructure/{inbound,outbound,bootstrap}/` builds adapters, composes DI, fixes namespaces from catalog identity. Apps inject through `Symbol()` DI tokens, never via class references from foundation.
- **I-0.4: Tier 2 raw lib instance leak ⇒ requires narrow-unlock** — any Tier 2 raw lib instance (`pg.Pool`, `ioredis Redis`, `S3Client`, `ClientGrpc`, future `amqplib Channel`/`Connection`) exported from foundation MUST have a documented narrow-unlock comment in the same file as the export, naming the single legitimate consumer (symmetric to Phase 999.12 D-13 REDIS_CLIENT for `@nest-lab/throttler-storage-redis`). ESLint guard (Override 4-style, like the ioredis ban) MUST exist for the raw lib import to prevent regression. **Anti-эталон: F-02 PG_POOL leak.**
- **I-0.5: Tier 1/2/3 layering applies to all 5 layers** — not only L4 outbound clients (where `infrastructure-client-layering` skill originated). Tier 1 = layer-name abstractions (CACHE_SERVICE, PERSISTENCE_HEALTH, MESSAGING_HEALTH); Tier 2 = raw lib instances (REDIS_CLIENT, PG_POOL, S3_CLIENT, CLIENT_GRPC, future AMQP_CLIENT); Tier 3 = library defaults (REDIS_DEFAULTS, PG_POOL_DEFAULTS, S3_DEFAULTS, GRPC_CLIENT_HEALTH).

## 8. Seed-Findings Dossiers (D-A4 Hybrid)

### 8.1 F-01 — `RedisCacheService.get<T>()` quality (expected major, L1)

**Source file:** `packages/foundation/src/external/cache/cache.service.ts:16-26`

**Verbatim evidence (current HEAD):**

```typescript
async get<T>(key: string): Promise<T | null> {
  const raw = await this.redis.get(this.prefixKey(key));
  if (raw === null) {
    return null;
  }
  try {
    return JSON.parse(raw) as T;
  } catch {
    return null;
  }
}
```

**Two distinct defects** in 11 lines:
1. **Unchecked JSON cast `as T`** — schema validation absent; whatever JSON.parse produces is force-cast to caller-supplied generic. Returns garbage if shape drifts.
2. **Silent corruption swallow `catch { return null }`** — caller cannot distinguish (a) `key absent` from (b) `key present but corrupt`. Both return `null`. The corrupt key keeps polluting cache until TTL.

**Violated contract (D-A3.1 multi-skill):**
- `clean-ddd-hexagonal` — Tier 1 abstraction CachePort.get<T>() loses information
- `infrastructure-client-layering` — Tier 1 should hide protocol concerns BUT signal protocol failures back to caller (otherwise consumers can't reason about failure modes)

**Impact:**
- Every business consumer of cached structured data risks runtime `TypeError: Cannot read property X of undefined` (cast to wrong type) OR silent stale-data bugs (corrupt key returns absent → callback re-fetches from source → re-caches → repeat).
- Production hard to debug: no log line, no metric.

**Pre-staged variants (D-A4 — 3-axis cartesian, 27 combinations, 3-4 selected for trade-off):**

**Axis A: Return-shape (3 values)**
- A1. Discriminated union — `get<T>(key, schema?: ZodType<T>): Promise<{status: 'absent' | 'corrupt' | 'value', value?: T}>` — caller MUST switch
- A2. Throw `CacheParseError` — `get<T>(key, schema?: ZodType<T>): Promise<T | null>`, throw on corrupt
- A3. Result type — `get<T>(key, schema?: ZodType<T>): Promise<Result<T | null, CacheParseError>>` — common across foundation utilities

**Axis B: Schema placement (3 values)**
- B1. Optional param on existing method — `get<T>(key, schema?)`
- B2. Separate method — `getValidated<T>(key, schema)` alongside `get<T>(key)` (raw/typed split)
- B3. Caller-side validation outside CachePort — port stays minimal `get(key): Promise<unknown | null>`, caller calls `schema.parse()`

**Axis C: Corruption side-effect (3 values)**
- C1. Log error + treat as cache-miss (corrupt key lives until TTL)
- C2. Log error + `del(key)` self-healing (next get fetches from source)
- C3. Severity-aware: log warn on schema-mismatch, log error on JSON.parse, `del(key)` in both cases

**Cartesian = 27 combinations.** SOLUTIONS author selects 3-4 most relevant in 7-col trade-off table; remaining 23 documented inline as «не выбраны по причине X» (D-10).

**Recommended starting pick** (per CONTEXT.md `<specifics>`): **A1 + B1 + C3** — discriminated union + optional schema param + severity-aware del. Rationale: explicit caller contract (A1 — caller can't ignore corrupt), backwards-compat (B1 — existing `get(key)` callers without schema still get null/value), self-healing (C3 — corrupt key purged). NOT a lock; SOLUTIONS author may recommend differently with rationale.

**Alternative picks worth surfacing in trade-off table:**
- A2 + B2 + C2 — throw on corrupt + separate `getValidated` method + del self-heal (clean separation, but dual method API surface)
- A3 + B1 + C2 — Result<T> + optional schema + del self-heal (most ergonomic if foundation already has `Result` utility — verify; expected: it doesn't yet)
- A1 + B3 + C1 — discriminated union + caller-side validation + log only (minimal Tier 1 surface, max caller responsibility — drift risk highest)
