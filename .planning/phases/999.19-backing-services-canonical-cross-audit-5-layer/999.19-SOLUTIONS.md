## F-01 — RedisCacheService.get<T>() quality (major, L1)

**Problem:** `RedisCacheService.get<T>(key)` collapses two distinct failure modes — `key absent` and `key present but corrupt JSON / shape-mismatched cached value` — into the same `null` return. Unchecked `as T` cast disables runtime type-safety. Corrupt cache entry persists until TTL because the silent swallow has no `del()` / log side-effect. Violates DESIGN.md I-1.6 (CachePort port loses information) cascading into I-0.5 (Tier 1 abstraction MUST signal protocol failures back to caller).

**Depends on:** —

This finding has **3 orthogonal axes × 3 values = 27 combinations**. SOLUTIONS author selects 4 most relevant in trade-off table; rejected combinations documented inline per D-10.

**Axis A — Return-shape (3 values):**

- A1. Discriminated union — `get<T>(key, schema?: ZodType<T>): Promise<{status: 'absent' | 'corrupt' | 'value'; value?: T}>`
- A2. Throw `CacheParseError` — `get<T>(key, schema?: ZodType<T>): Promise<T | null>` + throw on corrupt
- A3. Result type — `get<T>(key, schema?: ZodType<T>): Promise<Result<T | null, CacheParseError>>`

**Axis B — Schema-placement (3 values):**

- B1. Optional param on existing method — `get<T>(key, schema?)`
- B2. Separate method — `getValidated<T>(key, schema)` alongside `get<T>(key)`
- B3. Caller-side validation — port stays minimal `get(key): Promise<unknown | null>`, caller calls `schema.parse()`

**Axis C — Corruption side-effect (3 values):**

- C1. Log error + treat as cache-miss (corrupt key lives until TTL)
- C2. Log error + `del(key)` self-healing
- C3. Severity-aware: log warn on schema-mismatch, log error on JSON.parse, `del(key)` in both cases

**Picked combinations for trade-off (4 selected):**

| Variant | Approach | Pros | Cons | Complexity | Cost (files/commits) | Recommended |
|---------|----------|------|------|------------|----------------------|-------------|
| V1 (A1+B1+C3) | Refactor `RedisCacheService.get<T>` to discriminated union return + optional `schema?: ZodType<T>` parameter on the existing method + severity-aware logging (warn on schema-mismatch / error on JSON.parse) with `del(key)` self-heal in both branches | Explicit caller contract — caller MUST switch on `status`; backwards-compat for unschema-aware callers (just receive `{status: 'value'\|'absent', value?}`); self-healing prevents corrupt-key TTL pollution; severity-aware logs differentiate transient JSON.parse from schema drift; aligns L1 Tier 1 with REDIS_CLIENT D-13 narrow-unlock-discipline siblings | API surface change — every existing caller of `get<T>(key)` (currently 0 in apps; foundation-internal only — but future business-cache consumers must adopt new shape); requires new `CacheParseSeverity` discriminator type in `cache.interfaces.ts` | M | 2-3 files / 1 commit (`cache.service.ts` + `cache.interfaces.ts` + optional `cache.constants.ts` for severity tokens) | ✅ |
| V2 (A2+B2+C2) | Throw `CacheParseError` from a NEW `getValidated<T>(key, schema)` method + keep existing `get<T>(key)` returning `T \| null` for shape-agnostic callers + `del(key)` on parse failure inside `getValidated<T>` only | Clean separation between shape-aware and shape-agnostic call sites; existing callers untouched (zero migration); throw-based control flow familiar to TS consumers | Two-method API surface violates Tier 1 minimal-surface principle; throwing from infra Tier 1 mixes signalling styles (foundation utilities mostly return values not throws); `del(key)` only on `getValidated<T>` failure — untyped corrupt keys via the original `get<T>` lifeline still lingering until TTL | M | 2 files / 1 commit | — |
| V3 (A3+B1+C2) | Result type return — `get<T>(key, schema?: ZodType<T>): Promise<Result<T \| null, CacheParseError>>` — with optional schema + `del(key)` self-heal on parse failure | Most ergonomic if foundation already had `Result` utility (functional-style composition; explicit error type); single method retained | Foundation does NOT yet have `Result` utility — would need to build one as prerequisite (scope creep into a separate utility package); requires every caller adopt `.match` or `.unwrap` patterns; binds the entire foundation to a new functional idiom | L | 4-5 files / 2 commits (Result utility + cache.service.ts + interfaces + callers) | — |

**Rationale:** V1 (A1+B1+C3) is the only combination simultaneously satisfying I-1.6 (port surface caller-distinguishable) + I-0.5 (Tier 1 signals protocol failures) + cascade-awareness (severity-aware logging supports observability without bolt-on metric) per DESIGN §6 Principle 4. V2 rejected because dual-method surface violates Tier 1 minimal-surface principle and only `del()`s on the schema-aware path — leaves untyped corrupt keys via the original `get<T>` lifeline. **Rejected combinations (D-10 audit trail — non-picked cartesian cells):**

- **A2+B1+C1 / A2+B1+C2 / A2+B1+C3** — throw + optional schema — rejected: throw-based signalling inconsistent with foundation value-return convention; existing callers' `try/catch` discipline drift unbounded.
- **A2+B2+C1 / A2+B2+C3** — throw + separate method + non-C2 — rejected: V2's `del()`-in-validated path is the most defensible C combination given dual-method surface; without `del()` corrupt keys persist on the validated path too, defeating the separate-method rationale.
- **A2+B3+C1 / A2+B3+C2 / A2+B3+C3** — throw + caller-side validation — rejected: same as A2+B1 plus split responsibility from caller-side validation; double rejection.
- **A3+B1+C1 / A3+B1+C3** — Result + optional schema + non-C2 — rejected: same `Result` prerequisite scope-creep issue as V3; without del() the corrupt-key persistence problem remains.
- **A3+B2+C1 / A3+B2+C2 / A3+B2+C3** — Result + separate method — rejected: same `Result` prerequisite issue plus dual-method surface (compounds V2 and V3 issues).
- **A3+B3+C1 / A3+B3+C2 / A3+B3+C3** — Result + caller-side — rejected: same `Result` prerequisite plus split-responsibility issue; triple rejection.
- **A1+B3+C1** — discriminated union + caller-side + log-only — covered by V4; rejection reason in V4 row.

(Total enumerated rejected cells: ~22; combined with V1..V4 = 26 of 27. The 27th cell is the recommended V1 combination itself.)
