## §1 Purpose & Scope

This document locks the canonical shape of the email-platform monorepo backing-services 5-layer architecture (cache/Redis, persistence/Postgres, storage/S3, clients/gRPC, events/RabbitMQ) as of the end of Phase 999.18.x and formalises the architectural invariants that Plans 02-04 of Phase 999.19 use to measure drift, propose migrations, and verify the result. It is derived from `999.19-RESEARCH.md` §§1-2 (footprint inventory + proposed L0..L5 invariants) and `999.19-CONTEXT.md` `<decisions>` D-A1..D-A4 (locked decisions). DESIGN.md formalises a 6-axis invariant taxonomy: one master invariant L0 (Strict 3-zone + narrow-unlock) plus five per-layer invariant groups L1..L5, each cross-referenced to one or more of the project's 9 enforcing skills.

**What this doc IS NOT.** It is neither an audit (Plan 02 `999.19-AUDIT.md` produces F-NN findings against these invariants), a migration plan (Plan 03 `999.19-SOLUTIONS.md` proposes per-finding variants), nor a verification log (Plan 04 `999.19-VERIFICATION.md` records grep-proof rows). It proposes zero code fixes. It does not lock L5 implementation choices (RMQ has no canonical reference yet — every I-5.N statement carries `proposed` until a future 999.13 promotion replaces it with a real-implementation reference).

**Docs-only boundary** (PROJECT.md «без бизнес-логики, без тестов» + CONTEXT.md `<deferred>` + `infrastructure-guard` skill). Phase 999.19 mutates no code, no ports, no credentials, no docker-compose files, no `.env*` files. The phase produces five markdown artefacts under `.planning/phases/999.19-backing-services-canonical-cross-audit-5-layer/` (DESIGN, AUDIT, SOLUTIONS, VERIFICATION, SUMMARY) — code mutations live in 999.19.1..N sub-phases AFTER user approves SOLUTIONS.md per finding (CONTEXT.md D-08 + D-14). ROADMAP.md and the backlog are mutated ONLY by user-invoked `/gsd:insert-phase` calls after Plan 03 approval checkbox decisions.

**Clean/Hexagonal fit preview.** Each backing layer rides on the Phase 999.10 hexagonal stack (domain → application → infrastructure with ports/adapters) and the Phase 999.11.2 inbound/outbound/bootstrap canonical split. Foundation `packages/foundation/src/external/<layer>/` is Mechanism (Cockburn — domain-agnostic shapes); apps `apps/*/src/infrastructure/outbound/<layer>/` are Assembly (per-service realisation + naming + composition). The `infrastructure-client-layering` skill's Tier 1/2/3 framework applies uniformly to all 5 layers — Tier 1 = layer-name abstractions (CACHE_SERVICE, DRIZZLE, MESSAGING_HEALTH); Tier 2 = raw lib instances (REDIS_CLIENT, PG_POOL, S3_CLIENT, ClientGrpc, future AMQP_CLIENT); Tier 3 = library defaults (REDIS_DEFAULTS, PG_POOL_DEFAULTS). Full treatment in §5.

**Evidence base.** Every "Current state" block in §3 cites file paths and line numbers from `999.19-RESEARCH.md` §1-§2 + §3 scope-grid. No claim in this document should be unsupported by a reproducible grep against the workspace at the authoring HEAD. Where RESEARCH §1.6 flagged an open question (vendor HTTP types in `packages/contracts/src/external/`), DESIGN documents the open question rather than pre-classifying it — AUDIT (Plan 02) resolves with evidence.

## L0 Master Invariant

The master invariant defines the 3-zone architectural rule that ALL 5 backing layers MUST satisfy. It is the universal contract from which per-layer invariants L1..L5 (§3) are derived. Verbatim source: CONTEXT.md D-A1 + RESEARCH §2.1.

- **I-0.1:** Contracts zone purity — `packages/contracts/src/` contains ONLY `*.proto`-generated TypeScript types and the `CONTRACTS_PROTO_DIR` constant. No business types, no DI tokens, no runtime logic. Vendor HTTP-skeleton types in `packages/contracts/src/external/{telegram,appstorespy,cloud-functions}/` — open question per RESEARCH §1.6 (does HTTP vendor skeleton type belong in proto-only zone, or should it relocate to per-vendor adapter under `apps/*/src/infrastructure/outbound/http-clients/{vendor}/types.ts`?). AUDIT (Plan 02) classifies with evidence. Enforcing skill: `clean-ddd-hexagonal` SKILL.md §"Dependency Rule" (contracts is the leaf — nothing depends on apps) + `no-magic-values` SKILL.md §"Symbol DI tokens" (DI tokens belong with their consumer, never in contracts). Grep invariant: `find packages/contracts/src/ -name '*.ts' -not -path '*/generated/*' | wc -l` — current count 8 (per RESEARCH §1.6); AUDIT classifies each as proto-only or candidate-relocate. Canonical reference: Phase 999.7.x (contracts-as-proto-leaf established by gRPC client refactor sequence).

- **I-0.2:** Foundation = mechanisms zone — `packages/foundation/src/external/<layer>/` exposes ONLY domain-agnostic shapes — factory functions (`defineGrpcClient`, `CacheModule.forRootAsync`, `PrivateStorageModule.forBucket`), abstract base classes, Proxy builders (`promisifyGrpcClient`), port interfaces (`CachePort`, `StorageHealthIndicator`), HealthIndicator/ShutdownService shapes. Foundation has NO knowledge of specific business scenarios, NO knowledge of which service consumes what (no `auth`/`sender`/`audience` references in foundation source). Enforcing skill: `infrastructure-client-layering` SKILL.md §"Three-Layer Rule — Mechanism layer ownership" (Tier 1 layer-name abstractions live in foundation). Grep invariant: documented re-export list in `packages/foundation/src/external/<layer>/index.ts` per layer; `grep -rE '\b(auth|sender|audience|parser|notifier|gateway)\b' packages/foundation/src/ --include='*.ts'` should return 0 service-name references in foundation source (excluding test/comment lines). Canonical reference: Phase 999.7.x (foundation-as-mechanism baseline) + Phase 999.11.2 D-08 (bootstrap split formalised).

- **I-0.3:** Apps = realisation + composition zone — `apps/*/src/infrastructure/{inbound,outbound,bootstrap}/` builds adapters, composes DI, fixes namespaces from the Phase 999.4 `SERVICE` catalog identity (catalog provides `SERVICE.{svc}.id`; apps consume it). Apps inject through `Symbol()` DI tokens declared in app-local `*.constants.ts` files, never via class references from foundation. Enforcing skill: `nestjs-hexagonal-mapping` SKILL.md §"Composition root shape after 999.11.2" + `clean-ddd-hexagonal` SKILL.md §"Dependency Rule". Grep invariant: `find apps/*/src/infrastructure/ -type d -mindepth 1 -maxdepth 1 | sort -u` — every service has subset of `{inbound,outbound,bootstrap}` (gateway = inbound/rest + outbound/grpc-clients + bootstrap; notifier = inbound/rmq + outbound/storage + bootstrap; gRPC services = inbound/grpc + outbound/persistence|cache|storage + bootstrap). Canonical reference: Phase 999.11.2 (inbound/outbound/bootstrap canonical split) + Phase 999.10 (hexagonal stack establishment).

- **I-0.4:** Tier 2 raw lib instance leak ⇒ requires narrow-unlock + ESLint guard — any Tier 2 raw lib instance (`pg.Pool`, `ioredis Redis`, `S3Client`, `ClientGrpc`, future `amqplib Channel`/`Connection`) exported from foundation MUST have a documented narrow-unlock comment in the same file as the export, naming the single legitimate consumer (symmetric to Phase 999.12 D-13 REDIS_CLIENT for `@nest-lab/throttler-storage-redis` in gateway throttle). ESLint guard (Override 4-style, like the ioredis ban) MUST exist for the raw lib import to prevent regression in `apps/*/src/**` (Override 4) while allowing it in `apps/*/src/infrastructure/**` only via the foundation Symbol (Override 5). Enforcing skill: `infrastructure-client-layering` SKILL.md §"Tier 2 raw lib instance" + `no-magic-values` SKILL.md §"Symbol consistency" (DI tokens for narrow-unlock targets). Grep invariant: `grep -A 3 'Phase 999.12 D-13' packages/foundation/src/external/cache/cache.module.ts` matches the canonical narrow-unlock comment block (REDIS_CLIENT exemplar — D-13); `grep -rn "from 'ioredis'" apps/*/src/ --include='*.ts'` = 0; analogous expected for `from 'pg'` post-fix. **Anti-эталон: F-02 PG_POOL leak** — `packages/foundation/src/external/persistence/index.ts:4` exports `PG_POOL` from foundation public API without narrow-unlock comment; `PersistenceModule.exports[]` re-exports it; 0 consumers in apps. ESLint Override 4 has no `from 'pg'` ban entry. Canonical reference: Phase 999.12 D-13 (REDIS_CLIENT narrow-unlock formalisation) + Phase 999.7.x (foundation-mechanism boundary).

- **I-0.5:** Tier 1/2/3 layering applies to ALL 5 layers — not only L4 outbound clients (where the `infrastructure-client-layering` skill originated). Every layer MUST expose: Tier 1 = layer-name abstraction Symbol (`CACHE_SERVICE`, `DRIZZLE`, `PRIVATE_STORAGE`/`PUBLIC_STORAGE`, `Promisified<TRaw>` typed grpc proxy, future `MESSAGING_PUBLISHER`); Tier 2 = raw lib instance Symbol IF AND ONLY IF a narrow-unlock is documented (REDIS_CLIENT only — others kept private OR Tier 1 wrapper); Tier 3 = library defaults const (`REDIS_DEFAULTS`, `PG_POOL_DEFAULTS`, `S3_DEFAULTS`, `GRPC_CLIENT_HEALTH`, future `MESSAGING_DEFAULTS`). Enforcing skill: `infrastructure-client-layering` SKILL.md §"Tier 1/2/3 framework" (universal applicability). Grep invariant: per-layer Symbols in `packages/foundation/src/external/<layer>/<layer>.constants.ts` — exactly 1 Tier 1 layer-name token per layer; 0 or 1 Tier 2 token per layer (1 only with documented narrow-unlock). Canonical reference: Phase 999.12 (L1 cache full canonical exemplar) — the Tier 1/2/3 split is most cleanly visible there; symmetric expectation for L2..L5 is what AUDIT measures.

## §5 Clean/Hexagonal Fit

The 5-layer backing-services taxonomy maps cleanly onto Uncle Bob's rings (Clean Architecture) and Alistair Cockburn's primary/secondary adapter split (Hexagonal Architecture), with the `infrastructure-client-layering` skill's Identity / Mechanism / Assembly triad providing the catalog/foundation/apps split within Ring 4.

**Ring 4 — framework glue (Uncle Bob).** Each backing layer's bootstrap surface — `bootstrap/health/health.module.ts` (per-service health composition), `bootstrap/throttle/throttle.module.ts` (gateway rate-limit), `bootstrap/config/{svc}-config.module.ts` (per-service config DI binding) — lives in Ring 4 framework glue per `nestjs-hexagonal-mapping` SKILL.md «File-path reference table» row "infrastructure/bootstrap/". **Ring 3 — infrastructure adapters (Cockburn primary/driving + secondary/driven).** Each backing layer's adapter surface — `inbound/grpc/*.controller.ts` (gRPC controllers in 4 services), `inbound/rmq/event.consumer.ts` (notifier RMQ consumer — L5), `inbound/rest/{feature}/*.controller.ts` (gateway REST), `outbound/persistence/{aggregate}/pg-*.repository.ts` (L2 repositories), `outbound/cache/cache.module.ts` (L1 wrappers), `outbound/storage/*.module.ts` (L3 per-bucket Assembly), `outbound/grpc-clients/{upstream}/*-client.module.ts` (L4 per-upstream Assembly), future `outbound/publishers/{event-type}.publisher.ts` (L5) — lives in Ring 3. Foundation `packages/foundation/src/external/<layer>/` provides the Mechanism shapes that Ring 3 adapters consume.

**Ring 2 — application services / use-cases.** NEVER sees backing-layer DI tokens directly except through narrow ports. Application services (`apps/{svc}/src/application/services/`) orchestrate use-cases; use-cases (`apps/{svc}/src/application/use-cases/`) inject domain ports (e.g., `USER_REPOSITORY_PORT`, `LOGIN_PORT` per Phase 999.10.1 NAMING.md). I-0.3 (apps composition zone) + I-2.6 (repos inject DRIZZLE, not PG_POOL — domain ports inject the abstraction) keep Ring 2 backing-layer-agnostic.

## §6 Migration Principles

These principles govern how Plan 03 SOLUTIONS.md authors migration variants per finding and how Plan 04 VERIFICATION.md validates the final state. Carry-forward verbatim from Phase 999.1 §5 (CONTEXT.md `<decisions>` "Carry-forward 999.1 methodology" — D-01..D-19), with «999.1» → «999.19» substitution.

1. **Every drift gets ≥ 2 variants per CONTEXT.md D-05.** SOLUTIONS.md MUST provide a recommended variant plus at least one alternative for each finding (default 3 variants, F-01 cartesian extends to up to 4 picks from 27 combinations). Rationale: variants make trade-offs explicit (complexity vs cascade blast radius vs migration atomicity) and let the user approve the recommended option informed, rather than rubber-stamp. Rejected variants remain in SOLUTIONS.md Rationale field as audit trail per D-10 — future audit sees "variant X was considered and rejected because Y" and does not re-propose it.

2. **Atomic commit per finding-fix.** Each approved solution translates into ONE commit (or one bisect-safe group of commits) when executed in its assigned 999.19.N sub-phase. Sub-phase groupings share ≥ 1 of: file-coupling (F-NN and F-MM both edit `packages/foundation/src/external/persistence/`), migration atomicity (F-NN's fix breaks runtime if F-MM isn't applied simultaneously), test-ability (same grep-invariant set), or semantic coherence (all L4 grpc-client narrow-port additions belong together). CONTEXT.md D-09 owns the grouping criterion taxonomy; precedent: 999.11.3 + 999.1 atomic commits.

3. **Behaviour-preserving.** Phase 999.19 sub-phase migrations are docs-only or refactor-only — no business logic, no tests (PROJECT.md `<constraints>` «без бизнес-логики, без тестов»). Runtime behaviour MUST match pre-migration for every approved solution. Where a variant genuinely changes behaviour (e.g., F-01 V1 discriminated union return shape changes `get<T>()` caller contract from `T | null` to `{status, value?}`), the variant MUST be flagged in SOLUTIONS.md trade-off Cons column and the user's approval is treated as informed consent for the behaviour change.

4. **Cascade-aware.** When a narrow-port shape changes or a Tier 2 boundary moves, ALL projection call-sites update atomically in the same commit. Canonical cascades for this phase: F-02 PG_POOL fix Variant 3 (Tier 1 abstraction wrapper) cascades through every `outbound/persistence/{aggregate}/pg-*.repository.ts` (5+ files); F-01 fix Variant 1 (discriminated union return) cascades through every `cache.service.get<T>()` call-site (subset of 6 services depending on cache use). CONTEXT.md D-09 grouping heuristic captures cascade-shared-files. Partial cascades are disallowed — either the whole chain moves or none of it does.

5. **Infra read-only during audit.** Per `infrastructure-guard` skill: Phase 999.19 itself MUTATES NO `apps/*`, `packages/*`, `infra/`, `.env*`, or `docker-compose*` files. Code mutations live in 999.19.1..N AFTER user approves SOLUTIONS.md per finding (D-08 + D-14). SOLUTIONS variants that require infra mutations (e.g., new ESLint Override 4 entry banning `from 'pg'`) MUST be flagged "user-approval required at sub-phase execution time"; the sub-phase executor applies `infrastructure-guard` SKILL.md §"Pre-Change Checklist" when the user approves. Standard ports (5432, 6379, 5672, 9000, 50051-50054) preserved unconditionally.

6. **Verify-against-reality.** Every DESIGN invariant claim and every AUDIT finding MUST be grep-verifiable against the codebase at AUDIT-execution commit. VERIFICATION.md (Plan 04) captures the exact `bash` one-liners + expected counts + observed counts + commit hash per row; this is the 999.11.2 VALIDATION.md / 999.11.3 VERIFICATION.md / 999.1 VERIFICATION.md precedent adapted to audit-phase specifics (CONTEXT.md D-16). Paraphrased or approximately-correct commands break the "reader reproduces the result" contract and are not acceptable.

## §7 Out of Scope

The following concerns are EXPLICITLY out of Phase 999.19 scope. Each exclusion has a specific rationale tied to CONTEXT.md decisions or PROJECT.md constraints — DESIGN.md records them so future phases do not accidentally widen scope.

- **Code changes.** Any `apps/*` or `packages/*` mutations are deferred to 999.19.1..N sub-phases AFTER user approves SOLUTIONS.md per finding (CONTEXT.md `<deferred>` + D-08 + D-14). Plan 02 AUDIT, Plan 03 SOLUTIONS, Plan 04 VERIFICATION + SUMMARY are docs-only.

- **Business logic.** Phase 999.19 covers infrastructure abstractions only — PROJECT.md milestone v4.0 «Infrastructure Abstractions & Cross-Cutting» context. Business logic (use-cases bodies, domain rules, CSV import semantics, email-send orchestration) is a separate milestone.

- **Tests.** PROJECT.md `<constraints>` «без тестов» — testing is a separate downstream milestone. This phase validates structurally (grep/awk on markdown + grep against source files) rather than via a test framework. VALIDATION.md framework row is `N/A`.

- **Infrastructure file modifications.** `infrastructure-guard` skill — audit is read-only across ports, docker-compose, credentials, `.env*` files, CI/CD, deploy scripts. Any migration variant proposing an infra mutation carries "user-approval required at sub-phase execution time" per Migration Principle 5.

- **Pre-absorption of related backlog phases (999.13 RMQ, 999.14 S3, 22.5 Garage).** Independent audit per CONTEXT.md `<deferred>`. Redundancy surfaced in SOLUTIONS Backlog Impact section (D-15) with promotion-flag per finding, NOT pre-absorbed. User decides cancel / keep / merge during SOLUTIONS review.

- **Changes to `packages/contracts/` proto types.** Audit checks PURITY only (I-0.1) — does the directory contain only `*.proto`-generated TypeScript types and `CONTRACTS_PROTO_DIR` constant? Does NOT propose schema changes. Open question on vendor HTTP types in `packages/contracts/src/external/{telegram,appstorespy,cloud-functions}/` — AUDIT classifies (proto-only or candidate-relocate to per-vendor adapter), DESIGN does not pre-classify.

- **L5 RMQ implementation choices.** No locking of `amqplib` / `amqp-connection-manager` / `@golevelup/nestjs-rabbitmq`. That is 999.13's scope (per PATTERNS Anti-pattern row 5). DESIGN marks all I-5.N invariants `proposed` from skeleton + best-practices; real implementation reference appears only after 999.13 promotion.

- **ROADMAP mutations.** Phase 999.19 does NOT call `/gsd:insert-phase` or modify ROADMAP.md (CONTEXT.md D-14 + memory anchor `reference_gsd_sdk_phase_handlers_999_unsafe`). 999.19.N sub-phase numbers in SOLUTIONS.md `Pre-assigned sub-phase` field are PRE-ASSIGNED placeholders only — user manually invokes `/gsd:insert-phase 999.19.N` per approved F-NN after SOLUTIONS.md review. Backlog Impact decisions (cancel/keep/merge for 999.13/999.14/22.5/999.3/999.4) are manual ROADMAP edits via `/gsd:fast` per CONTEXT.md `<deferred>` carry-forward.
