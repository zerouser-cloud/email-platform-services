## Implementation Decisions

### Phase Scope & Implementation Depth

- **D-01:** **Split full-cycle: 999.18.1 = research + ADR + design only; impl punt в 999.18.2.** Rationale: user-mandate «максимальный упор на аудит, выявление проблем, крайних случаев, разработку полноценного решения с учётом этого» = design-heavy mandate. Mixing impl pressure в ту же фазу искажает research-оптику к «что быстрее имплементировать» вместо «что правильнее». Memory `feedback_report_dont_fix` подкрепляет: «report with options, let user choose, don't silently patch» — split сохраняет explicit user-gate между «варианты предложены» и «вариант реализован». 999.1 precedent в проекте уже доказывает многофазный full-cycle (999.1 = audit+design+SOLUTIONS, impl ушёл в 999.1.8 / 999.1.9 / далее). Phase-completeness rule (memory `feedback_phase_completeness`) НЕ нарушается — full-cycle через 999.18.1 (research+design) + 999.18.2 (impl) остаётся full-cycle, просто с inner user-gate.

- **D-02:** **Research must reach PoC / concrete code-snippet level**, не «paper exercise». Каждый D-17 кандидат получает: comparative spike (минимально — Dockerfile-snippet + sample turbo.json/nx.json/BUILD.bazel/etc.), benchmark если возможно (cold/warm build time, cache hit rate, image size), explicit list of trade-offs evaluated against project-fit criteria. Иначе 999.18.2 столкнётся с «теория не сошлась с реальностью» и придётся возвращаться.

### Research Scope

- **D-03:** **Deep research всех 6 D-17 кандидатов без pre-filter** — Turborepo, Nx, Bazel, Buck2, Pants v2, plain pnpm scripts. НИКАКОГО a priori bias к stay-on-current-stack. F-01 V1 (`syncInjectedDepsAfterScripts: [build]` — canonical pnpm 11 mitigation) может выиграть decision, но ТОЛЬКО если research empirically покажет, не как default «безопасный» pick.

Цель: избежать research-treadmill при сохранении completeness.

- **D-05:** **MAANG enterprise practices** — обязательная depth axis (per D-17): Google Bazel internal (Blaze paper, Bazel rules_nodejs migration), Meta Buck2 (Rust port, hermetic builds), Vercel Turborepo manifesto + Stream talks, Microsoft Rush + RushStack, Netflix Atlas. Ожидаемые критерии (для ориентира researcher-а, не lock): project scale (6→20 services growth horizon), TS-only stack (полиглот irrelevant), team size (small), ramp-up cost, NestJS ecosystem fit, k8s/GitLab CI portability, contract-generation placement compatibility, hermetic-build feasibility.

### Container Build Pattern Constraints (hard-locked)

- **D-07:** **pnpm как package manager — hard-locked.** Research НЕ пробует npm / yarn / bun миграцию. Rationale: current stack + memory `feedback_use_package_scripts` (всегда `pnpm <script>`); blast-radius package-manager swap несоразмерен expected gains; package-manager выбор уже эффективно решён до 999.18.1.

- **D-08:** **OCI containers / Dockerfile-based build — hard-locked.** Research НЕ пробует Cloud Native Buildpacks / ko / jib / Nix-image-builder альтернативы. Rationale: k8s + текущий Coolify-transition оба на OCI; альтернативы вынуждают либо Java/Go-side тулинг (jib/ko), либо radical-shift (Nix), оба превышают scope phase-cluster. Dockerfile multi-stage strategy сама по себе ОТКРЫТА для research output (multi-stage vs single-stage vs distroless).

- **D-09:** **Multi-arch (amd64 + arm64) — hard requirement.** Single-arch отвергается. Rationale: k8s arm64 nodes на DigitalOcean (per 999.18 D-13 + memory `project_hosting_infra`); F-08 BLOCKER в 999.18 AUDIT.md прямо указывает на отсутствие `platforms:` arg в `.github/workflows/docker-build.yml`. Это требование переносится на любой ADR-output orchestrator.

### Container Build Pattern Open for Research Output

- **D-10:** **Не локает заранее (research output)** — всё что НЕ в D-07/D-08/D-09 открыто для ADR-decision. Включая: `pnpm deploy --prod` keep/drop, `injectWorkspacePackages: true` keep-with-mitigation/drop-entirely, multi-stage strategy (multi vs single vs distroless vs scratch+node-binary), image base (node:22-alpine vs distroless vs custom), BuildKit cache mount strategies, layer ordering / lockfile-aware install caching, `pnpm fetch` offline install pattern, health probe split (readiness vs liveness vs startup), image determinism strategy (digest-pinning), runner-stage shape (`pnpm deploy` bundle vs manual COPY closure).

### Multi-arch CI Disposition (F-08)

- **D-11:** **ADR 999.18.1 фиксирует требование + recommended initial approach.** ADR говорит: «multi-arch (amd64+arm64) mandatory; recommended initial approach — `docker buildx` + QEMU emulation на amd64 GitLab runners (cost-zero start); native ARM runners — future optimization». DevOps владеет timing/migration to native runners и может отклонить recommended initial approach с justification. Сохраняет 999.18 D-19 invariant (DevOps decision authority на QEMU-vs-native trade-off) при этом давая impl-фазе 999.18.2 ready-to-implement spec.

### K8s as Real Deploy Destination (supersedes 999.18 D-13/D-14 partial)

- **D-12:** **K8s = real deploy destination** (Coolify официально abandoned per user 2026-05-03; конфирмирует memory `project_hosting_infra` 2026-04-30 «Никакого Coolify у нас не будет в целом, будет кубер и его инфра»). DevOps владеет k8s manifests / Helm / cluster networking — НЕ наша фаза. Наша design-сторона: build artefacts должны быть **runtime-agnostic** (работают на bare Docker / Coolify-transition / k8s-destination без hard-coded assumptions) и **k8s-ready** (multi-arch, image determinism, secrets через `process.env` per 12-factor, health probe shapes совместимые с k8s readiness/liveness/startup probe split). 999.18 D-13 (k8s as future-destination constraint) остаётся в силе как principle, но D-14 (k8s out of scope) уточняется: k8s НЕ перестал быть out-of-scope для impl, но архитектурно «mock-future» переводится в «real-destination». Это означает: ADR должна явно адресовать k8s readiness без проектирования k8s manifests.
