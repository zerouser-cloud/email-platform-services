**TL;DR.** 999.18.1 решает архитектурный кризис build-системы Email Platform: 12 deferred BLOCKER+MAJOR findings из 999.18 audit-а сводятся к **трём independent осям**, которые ADR должен закрыть:

**Что я узнал в research.** Шесть D-17 кандидатов разбиваются на три tier-а по project-fit:

- **Tier A (high project-fit):** Turborepo (current, обновлённый approach с `turbo prune --docker`), Nx (NestJS first-class plugins, `@nx/docker`), plain-pnpm-scripts (минимальный overhead, `pnpm fetch` + offline install — недооценённый baseline).
- **Tier B (counter-factual rigor required, low project-fit):** Bazel (через `aspect_rules_js` 3.x — преемник unmaintained `bazelbuild/rules_nodejs`).
- **Tier C (rejected with explicit rationale, near-zero project-fit):** Buck2 (TypeScript support — community / unofficial; нет first-class NestJS integration); Pants v2 (TypeScript "completed" но JS — packaging story всё ещё experimental, March 2025 issue #22151 open).

**Likely finalists (моя HONEST hypothesis после research, НЕ lock — ADR final-pick — отдельный document):**

- **Recommended candidate:** **Turborepo с `turbo prune --docker` pattern** + переход на manual `COPY --from=...` runner-stage closure (отказ от `pnpm deploy --prod`) + commit-time contract generation (F-12 V2) + lockfile-aware cache invalidation для generate task (F-24 V1).

- **Counter-factual baseline (rejected):** Bazel `aspect_rules_js` — production-ready, но Starlark ramp-up cost + NestJS-ecosystem-fit unproven для small team (CONTEXT D-04 small-team criterion).

Эти hypotheses — research output, не decision. ADR будет writer-ом sub-plan-а 999.18.1.

**Что critically матерится (carry-forward от 999.18 .continue-here.md):** F-01 V1 (`syncInjectedDepsAfterScripts: [build]`) — canonical pnpm 11 mitigation, но operates ВНУТРИ injection-model architecture которая community-flagged "foot gun" (pnpm Discussion #3938). ### 3.1. Turborepo (current, re-evaluated) — Tier A

**Overview.** Vercel-maintained monorepo build orchestrator (npm package `turbo`); current latest stable **2.9.8** [VERIFIED: `npm view turbo version` 2026-05-03]. Core mechanism: hash-based cache-keyed task execution с topological dependency graph (`dependsOn`). Local cache в `.turbo/cache/` + optional remote cache (Vercel Remote Cache / self-hosted).

**Canonical use case.** TS / JS / Next.js / NestJS monorepos на small-medium scale (5-50 packages); commitments к speed-of-incremental-rebuild и simple config DSL (single `turbo.json`). Vercel docs explicitly advertise NestJS / Express examples.

**Adoption indicators (HIGH).** Vercel — corporate steward; community: 28k+ GitHub stars; первый-class в Vercel platform. NestJS core team разработал `nest-turbo-starter` template (typv/nest-turbo-starter [CITED](https://github.com/typv/nest-turbo-starter)). Industry pattern stories: Optimised multi-stage Docker builds with TurboRepo and PNPM for NodeJS microservices ([CITED: fintlabs Medium 2024](https://fintlabs.medium.com/optimized-multi-stage-docker-builds-with-turborepo-and-pnpm-for-nodejs-microservices-in-a-monorepo-c686fdcf051f)).

**Concrete code spike (Dockerfile + config) — `turbo prune --docker` pattern (CANONICAL):**

```dockerfile
# syntax=docker/dockerfile:1
ARG NODE_VERSION=22-alpine

# ─── Stage 1: prune ───────────────────────────────────────────
FROM node:${NODE_VERSION} AS pruner
WORKDIR /app
RUN corepack enable
COPY . .
ARG APP_NAME
RUN pnpm dlx turbo prune @email-platform/${APP_NAME} --docker

# ─── Stage 2: install ─────────────────────────────────────────
FROM node:${NODE_VERSION} AS installer
WORKDIR /app
RUN corepack enable
# json layer — only package.jsons + lockfile (rebuilt on dep change only)
COPY --from=pruner /app/out/json/ ./
RUN --mount=type=cache,id=pnpm,target=/pnpm/store \
    pnpm install --frozen-lockfile

# ─── Stage 3: build ───────────────────────────────────────────
FROM installer AS builder
WORKDIR /app
COPY --from=pruner /app/out/full/ ./
ARG APP_NAME
RUN pnpm exec turbo run build --filter=@email-platform/${APP_NAME}

# ─── Stage 4: runner ──────────────────────────────────────────
FROM node:${NODE_VERSION} AS runner
RUN addgroup -g 1001 -S appgroup && adduser -S appuser -u 1001 -G appgroup
WORKDIR /app
ARG APP_NAME
COPY --from=builder /app/apps/${APP_NAME}/dist ./dist
COPY --from=builder /app/apps/${APP_NAME}/node_modules ./node_modules
COPY --from=builder /app/packages /app/packages
USER appuser
CMD ["node", "dist/main.js"]
```

**Benchmark / empirical comparison.**

- Cold build (no cache): turbo overhead minimal (~50-100ms wrapper); Dockerfile build dominated by `pnpm install` (current ~30-60s) + tsc per package (~5-15s × 4 packages). Order of magnitude same as current Dockerfile [CITED: community-reported via fintlabs Medium].
- Warm build (cache hit): turbo skips unchanged tasks; `turbo prune --docker` produces minimal context per service → install layer-cache hit on package.json-unchanged commits → ~5-10s install + ~0s build (cache restore).
- **Cache hit rate empirical for our repo: NOT MEASURED** — would require local benchmark in 999.18.2 spike. Reasoning: turbo cache restored when (a) inputs unchanged AND (b) toolchain version unchanged (currently F-24 broken).
- Image size: пост-`turbo prune` runtime image ≈ 200-280MB на base of node:22-alpine (typical), depending on per-app dep closure.

### 3.6. Plain pnpm scripts (no orchestrator) — Tier A baseline

**Overview.** No external orchestrator. Use `pnpm`-builtin recursive operations (`pnpm -r build`, `pnpm --filter ... build`), workspace topological order from `pnpm-workspace.yaml`, BuildKit cache mounts for speed. Plus: `pnpm fetch` для deterministic install layer separation.

**Canonical use case.** Small-medium TS monorepos где orchestrator overhead exceeds value. `pnpm` itself is a competent monorepo runner — recursive scripts honour workspace topology.

**Adoption indicators (HIGH for small teams).** No corporate steward; community = pnpm itself + ad-hoc users. [pnpm.io/docker](https://pnpm.io/docker) — official multi-stage Docker pattern. [Depot's Optimal Dockerfile for Node.js with pnpm](https://depot.dev/docs/container-builds/optimal-dockerfiles/node-pnpm-dockerfile) — community canonical reference.

**Concrete code spike (Dockerfile + scripts) — `pnpm fetch` + manual COPY:**

```dockerfile
# syntax=docker/dockerfile:1
ARG NODE_VERSION=22-alpine

# ─── Stage 1: fetch ───────────────────────────────────────────
# pnpm fetch downloads packages to virtual store WITHOUT installing
# layer cache key = pnpm-lock.yaml ONLY (not source code)
FROM node:${NODE_VERSION} AS fetcher
WORKDIR /app
RUN corepack enable
COPY pnpm-lock.yaml .npmrc ./
RUN --mount=type=cache,id=pnpm,target=/pnpm/store \
    pnpm fetch --frozen-lockfile

# ─── Stage 2: install + build ─────────────────────────────────
FROM fetcher AS builder
COPY pnpm-workspace.yaml package.json ./
COPY packages/contracts/package.json packages/contracts/package.json
COPY packages/config/package.json packages/config/package.json
COPY packages/foundation/package.json packages/foundation/package.json
ARG APP_NAME
COPY apps/${APP_NAME}/package.json apps/${APP_NAME}/package.json
# Install offline from fetched store
RUN --mount=type=cache,id=pnpm,target=/pnpm/store \
    pnpm install --frozen-lockfile --offline
COPY tsconfig.base.json ./
COPY packages ./packages
COPY apps/${APP_NAME} ./apps/${APP_NAME}
# Topological build via pnpm -r (no manual chain)
RUN pnpm -r --filter "./packages/*" build
RUN pnpm --filter @email-platform/${APP_NAME} build

# ─── Stage 3: runner (manual COPY closure) ────────────────────
FROM node:${NODE_VERSION} AS runner
RUN addgroup -g 1001 -S appgroup && adduser -S appuser -u 1001 -G appgroup
WORKDIR /app
ARG APP_NAME
# Manual COPY of resolved closure (no pnpm deploy --prod, no injection)
COPY --from=builder /app/apps/${APP_NAME}/dist ./dist
COPY --from=builder /app/apps/${APP_NAME}/package.json ./package.json
COPY --from=builder /app/apps/${APP_NAME}/node_modules ./node_modules
COPY --from=builder /app/packages ./packages
USER appuser
CMD ["node", "dist/main.js"]
```

## 5. Container Build Pattern Survey

This section addresses CONTEXT D-10 open-for-research items: multi-stage strategy, image base, BuildKit cache strategies, `pnpm deploy` keep/drop, `pnpm fetch` pattern, image determinism, runner-stage shape, `injectWorkspacePackages` keep/drop empirical assessment.

### 5.1. Multi-stage strategy

**Options:**

| Option                                                | Description                                                              | Pros                                                            | Cons                                                                          |
| ----------------------------------------------------- | ------------------------------------------------------------------------ | --------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| **A. Multi-stage (current)**                          | builder + runner                                                         | Standard pattern, smaller runtime image                         | Build+runtime in same Dockerfile; `pnpm deploy --prod` requires injection     |
| **B. Three-stage (prune + install + build + runner)** | turbo prune adds prune stage                                             | Minimal context per service; install layer cacheable separately | More complex Dockerfile                                                       |
| **C. Single-stage**                                   | No runtime separation                                                    | Simpler                                                         | Larger image (dev deps included), security concerns                           |
| **D. Distroless runner stage**                        | builder = node:22-alpine; runner = `gcr.io/distroless/nodejs22-debian12` | Smaller, no shell, no package manager → smaller attack surface  | No shell breaks compose `wget` healthcheck (couples с D8-Q5); harder to debug |
| **E. Scratch + node binary**                          | Hand-rolled node binary in scratch                                       | Smallest possible                                               | Heroic effort; loses node ecosystem flexibility                               |

**Recommendation for ADR.** **Option B (three-stage prune+install+build+runner)** if Turborepo wins; **Option B без prune (just split install / build / runner)** if plain-pnpm wins. Option D (distroless runner) is **STRONG SECONDARY consideration** for runtime image — but couples с healthcheck shape decision (compose `wget` won't work; need k8s-style `httpGet` от orchestrator).

### 5.2. Image base assessment

| ------------------------------------- | ------------------------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------- |

### 5.3. BuildKit cache strategies

**Current (`infra/docker/app.Dockerfile:25,50,57`):**

```
RUN --mount=type=cache,id=pnpm,target=/pnpm/store pnpm install --frozen-lockfile
```

Cache mount survives build invocations on same builder; partial cache value preserved across `rm -rf node_modules + reinstall` cycles (the store doesn't get nuked).

**Improvements per pattern survey:**

1. **`--mount=type=cache,id=pnpm,target=/pnpm/store`** — KEEP (already in use).
2. **Add `--mount=type=cache,id=node_modules,target=/app/node_modules`** — POSSIBLE but conflicts с manual COPY-runner-stage requirement (cache mount NOT included in image layer).
3. **`pnpm fetch` separate from `pnpm install`** — RECOMMENDED. Splits cache key: lockfile-only layer (rebuilds rarely) + install layer (rebuilds on workspace topology change). See §3.6 Dockerfile spike.

**Multi-arch BuildKit cache:** GitHub Actions cache (`type=gha`) used in current `.github/workflows/docker-build.yml:54` — works across runs. **Multi-arch caveat:** per-arch cache scope needed (`scope=${{ matrix.service }}-${{ matrix.platform }}`) once F-08 multi-arch lands; otherwise QEMU-emulated arm64 cache pollutes amd64 cache and vice versa.

**Recommendation for ADR.** Use `pnpm fetch` + `--mount=type=cache,id=pnpm` for store; per-arch `cache-to: type=gha,scope=${matrix.service}-${matrix.platform}` for multi-arch CI.

### 5.4. `pnpm deploy --prod` keep/drop assessment

**Current state:** Dockerfile Step 5 — `pnpm deploy --filter @email-platform/${APP_NAME} --prod /prod/app` — produces self-contained `/prod/app` directory with isolated `node_modules` containing only production deps. Required `injectWorkspacePackages: true` (per pnpm 11 invariants).

**Assessment:**

- ✓ `pnpm deploy --prod` correctly excludes dev-deps (drizzle-kit, ESLint, turbo) — verified by grep through Dockerfile.
- ✗ Couples to `injectWorkspacePackages: true` (the foot gun per Discussion #3938).
- ✗ Hard-link snapshots of workspace deps require sync mechanism.

**Drop variant (manual COPY runner):**

```dockerfile
FROM node:22-alpine AS runner
COPY --from=builder /app/apps/${APP_NAME}/dist ./dist
COPY --from=builder /app/apps/${APP_NAME}/node_modules ./node_modules
COPY --from=builder /app/packages ./packages   # для workspace deps resolution
```

- ✓ No injection model needed.
- ✗ Image larger (workspace `node_modules` may include hoisted dev-deps unless explicitly filtered).
- ✗ Need to manually filter dev-deps OR rely on pnpm's hoist-pattern not to leak them.

**`pnpm deploy --legacy` flag:** Deprecated in pnpm 11; not viable.

**Recommendation for ADR.** **DROP `pnpm deploy --prod` in favor of manual COPY runner stage** as part of Turborepo / plain-pnpm finalist; this structurally eliminates F-01 / F-14 (no injection model, no foot gun). Trade-off: image size +5-15% acceptable for the architectural cleanup. Use `pnpm prune --prod` in builder stage before COPY to eliminate dev-deps if size becomes a concern.

### 5.5. `injectWorkspacePackages: true` keep/drop empirical assessment

**Current verdict (community consensus per pnpm Discussion #3938):** "foot gun" — high risk of hard-link staleness when build artefacts (dist/) refresh after install snapshot.

**Empirical evidence (carry-forward от 999.18 AUDIT.md):**

- 5 prior infra fixes (132138d → da70085) — all addressing injection-staleness symptoms.
- Issue #2 (`error TS2307: Cannot find module '@email-platform/config'` at Dockerfile Step 4a) — direct manifestation.

**Mitigation paths:**

| Path                                                                                    | Description                                     | Pros                                   | Cons                                                                                                                      |
| --------------------------------------------------------------------------------------- | ----------------------------------------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| **M1: `syncInjectedDepsAfterScripts: [build]`** (F-01 V1)                               | Canonical pnpm 11 mechanism                     | Small fix; community-endorsed          | Operates within injection-model architecture (perpetuates foot gun); pnpm Issue #9837 — doesn't work with turborepo cache |
| **M2: Drop `injectWorkspacePackages` + drop `pnpm deploy --prod` + manual COPY runner** | Architectural eliminate                         | Foot gun extinct; deterministic builds | Image +5-15% size; need manual workspace dep resolution in runner                                                         |
| **M3: `pnpm fetch` + offline install + manual COPY**                                    | Decouples install layer from injection entirely | Most deterministic; cache-friendly     | Newer pattern; community examples sparser than M1 / M2                                                                    |

**Recommendation for ADR.** **M2 OR M3** (architectural eliminate) — NOT M1 (perpetuates foot gun). M2 vs M3 is finer-grained ADR call; both address F-01/F-02/F-14/F-15.

### 5.6. Image determinism mechanisms (k8s digest-pinning)

**Goal:** `docker buildx build` of same git SHA produces same image digest. Required for k8s `image: ghcr.io/.../auth@sha256:abc` deployment patterns.

**Mechanisms:**

1. **Frozen lockfile** (current — `pnpm install --frozen-lockfile`).
2. **Reproducible timestamps** — set `SOURCE_DATE_EPOCH=$(git log -1 --pretty=%ct)` in CI; pass to docker build args; use в Dockerfile to bake deterministic `build-info.json` timestamp instead of `date -u +...` (current Dockerfile line 76 uses `date -u` — non-deterministic).
3. **`--mount=type=cache` interaction:** cache mounts don't affect layer hashing → safe.
4. **Architecture-pinned base image:** use `node:22-alpine@sha256:<digest>` (digest-pin base) instead of tag.
5. **Eliminate `rm -rf` cycles** (F-02 closure) — these introduce filesystem-ordering nondeterminism.
6. **Manual COPY runner stage** (instead of `pnpm deploy`) — predictable file-set.

**Recommendation for ADR.** Adopt all six mechanisms. Most impactful: #2 (SOURCE_DATE_EPOCH), #5 (eliminate cycles), #6 (manual COPY).

## 6. Multi-arch CI Approach Assessment

**Hard requirement (CONTEXT D-09):** linux/amd64 + linux/arm64 mandatory; F-08 BLOCKER closure.

### 6.1. Approach A: `docker buildx` + QEMU emulation на amd64 GitHub-hosted / GitLab-hosted runners

**Pros:**

- Zero-cost-start: works on existing CI (no infrastructure changes).
- Single Dockerfile, single workflow.
- CONTEXT D-11 explicitly recommends this as initial approach.

**Cons:**

- arm64 build via QEMU is slow: typical reports 5-10× slower than native [CITED: [Blacksmith blog](https://www.blacksmith.sh/blog/building-multi-platform-docker-images-for-arm64-in-github-actions), [zenn.dev "Escaping QEMU Hell"](https://zenn.dev/135yshr/articles/366e686b56de0c?locale=en)]. For our project, arm64 leg добавит ~10-25 min per service per CI cycle.
- grpc-tools-on-musl-arm64 fragility known [CITED: grpc/grpc#21446 / #18338]. Mitigation: F-12 V2 (commit-time gen) eliminates this risk by removing proto-gen from per-arch Docker build.

**Cost estimate (CI runtime):**

- Current single-arch CI: ~3-5 min × 6 services parallel = 5-8 min wall-clock.
- Post-multi-arch QEMU: ~3-5 min amd64 + ~15-30 min arm64 (QEMU) = ~15-30 min wall-clock.
- Acceptable as initial; degrades developer experience.

### 6.2. Approach B: Native ARM runners (GitLab self-hosted ARM / GitHub Actions ARM-hosted [paid])

**Pros:**

- 5-10× faster arm64 builds [CITED: AWS CodeBuild + Develeap blog].
- Cleaner: no QEMU layer interactions.

**Cons:**

- Cost: GitHub Actions ARM-hosted requires GitHub Team / Enterprise plan [CITED: [GitHub docs via Blacksmith](https://www.blacksmith.sh/blog/building-multi-platform-docker-images-for-arm64-in-github-actions)].
- Self-hosted ARM runners: setup overhead for DevOps.
- DevOps zone per CONTEXT D-19 — DevOps decides timing.

### 6.3. Approach C: Cross-compilation (no QEMU emulation)

For pure-TS code (which compiles to platform-agnostic JS), cross-compilation is theoretically free — но we have native dependencies (`grpc-tools` build hook). Cross-compile feasibility for our stack:

- TypeScript → JS: arch-agnostic. ✓
- `grpc-tools` postinstall: native binary — needs per-arch build OR pre-built per-arch binaries from npm registry.
- `protobufjs` postinstall: arch-agnostic JS. ✓
- `@nestjs/core` postinstall: arch-agnostic. ✓

**Conclusion:** Cross-compilation possible for our stack IF F-12 V2 (commit-time gen) lands first (eliminates `grpc-tools` need at Docker build time). Per [Kevin Fan blog](https://kev.fan/posts/03-cross-compile/) — viable approach.

### 6.4. Recommendation for ADR

**Multi-arch initial strategy (per CONTEXT D-11):** `docker buildx build --platform linux/amd64,linux/arm64` + `docker/setup-qemu-action@v3` step before `docker/setup-buildx-action@v3` in CI workflow. Combined with F-12 V2 (commit-time contract gen) which eliminates grpc-tools-on-musl-arm64 fragility entirely. Cost-zero start; acceptable initial performance penalty.

**Native ARM runners migration path:** Future optimisation; DevOps zone per D-19; trigger condition = "CI cycle wall-clock exceeds 30 min consistently on dev/main pushes" OR "ARM nodes become majority of k8s cluster". Document in DEVOPS-HANDOFF.md (per D-19 contract).

## 8. Health Probe Split Assessment

### 8.1. Current state (verified via 999.18 AUDIT.md)

- All 6 services expose BOTH `/health/live` (deps-free, `this.health.check([])`) AND `/health/ready` (deps-checked, `this.health.check([persistence, cache, ...])`).
- Compose healthcheck wires `/health/live` × 6 [VERIFIED: `infra/docker-compose.yml` lines 26, 47, 72, 97, 120, 143].
- Asymmetry: smoke uses `/health/ready`; healthcheck uses `/health/live`.

### 8.2. K8s probe semantic mapping

| K8s probe                  | Purpose                   | Should target                                     | Failure consequence                            |
| -------------------------- | ------------------------- | ------------------------------------------------- | ---------------------------------------------- |
| `livenessProbe`            | "Process alive?"          | `/health/live` (deps-free)                        | Pod restart                                    |
| `readinessProbe`           | "Ready to serve traffic?" | `/health/ready` (deps-checked)                    | Pod removed from Service endpoints             |
| `startupProbe` (k8s 1.18+) | "Initial boot complete?"  | `/health/live` или `/health/ready` (longer grace) | Falls back to liveness/readiness after success |

**Cold-start observation:** ~28s observed in 999.11.1 (per AUDIT.md F-21). K8s `startupProbe` recommended `failureThreshold: 30, periodSeconds: 1` (30 second grace).

### 8.3. Required design changes

**On our side (NOT k8s manifests per CONTEXT D-12):**

1. **Compose healthcheck swap:** `/health/live` → `/health/ready` × 6 services (F-04 V1). Add `start_period: 30s` per service для cold-start grace (matches future k8s startupProbe).
2. **Document k8s probe shape contract** в DOCKERFILE-REFERENCE.md / MIGRATION-RUNBOOK.md per CONTEXT D-12 deliverable: `livenessProbe: /health/live`, `readinessProbe: /health/ready`, `startupProbe: /health/live` с `failureThreshold: 30 / periodSeconds: 1`.
3. **gRPC native probe optional** для non-gateway services (k8s 1.24+) — `grpc-health-check 2.1.0` already shipped; documented but NOT implemented (DevOps zone).

**No app-code changes required** — endpoints already exposed correctly.

### 8.4. Distroless interaction

If runner-stage moves to distroless (per §5.2 recommendation), compose `wget` healthcheck breaks (no shell). Two paths:

- **Path X:** Retain `node:22-alpine` runner stage; defer distroless к k8s-only deploy.
- **Path Y:** Use `httpGet`-style healthcheck в compose (Docker compose does NOT support native httpGet — must use a static binary like [grpc-health-probe](https://github.com/grpc-ecosystem/grpc-health-probe) embedded в image, OR `curl` static binary).

**Recommendation for ADR.** **Path X** initially (keep alpine runner для compose); plan distroless adoption AFTER compose flow retired (k8s-only). Avoids healthcheck flow rewrite during transition.

### 11.5. "Build determinism proof" definition for verification

Per F-20 closure mandate, the ADR must define what "image determinism" means operationally:

**Definition:** Building the same git SHA on the same host (or different hosts) using the documented Dockerfile + build invocation produces images with identical content digests (`docker buildx imagetools inspect` shows same `digest:` field). Verification recipe lives в `scripts/verify-image-determinism.sh` (Wave 0 of 999.18.2):

```bash
#!/bin/bash
set -euo pipefail
SHA=${1:-HEAD}
SVC=${2:-auth}
git checkout $SHA
docker buildx build --no-cache --load --build-arg APP_NAME=$SVC -f infra/docker/app.Dockerfile -t test:1 .
docker image inspect test:1 --format '{{.Id}}' > /tmp/digest1
docker buildx build --no-cache --load --build-arg APP_NAME=$SVC -f infra/docker/app.Dockerfile -t test:2 .
docker image inspect test:2 --format '{{.Id}}' > /tmp/digest2
diff /tmp/digest1 /tmp/digest2 && echo "DETERMINISTIC" || (echo "NON-DETERMINISTIC" && exit 1)
```
