## Stage 0: Build args + global setup

This pseudo-stage covers the Dockerfile preamble — `# syntax`, `ARG NODE_VERSION`, `ARG APP_NAME`, base image FROM declaration semantics. It is not an OCI stage proper but is the canonical anchor for all build-args + multi-arch directives + image-base discipline.

### Section 0.1: Dockerfile syntax pragma

**Code:**

```dockerfile
# syntax=docker/dockerfile:1
```

- **Purpose:** Enables BuildKit features (multi-stage, `--mount=type=cache`, `--mount=type=secret`, multi-arch buildx). Без pragma BuildKit features silently degrade к legacy builder semantics.
- **Invariant I-S0.1:** First non-comment line MUST be `# syntax=docker/dockerfile:1` (or pinned digest per OQ-10 if image-determinism is being tightened). Без неё BuildKit features silently degrade.
- **K8s-ready:** N/A — pragma applies at build-time only. Не влияет на k8s runtime.
- **Multi-arch:** N/A — pragma applies at build-time only. `docker buildx build --platform ...` использует BuildKit unconditionally.

### Section 0.2: Build-args declaration

**Code:**

```dockerfile
ARG NODE_VERSION=22-alpine
ARG APP_NAME
```

- **Purpose:** `NODE_VERSION` parameterises base image без forking Dockerfile per service. `APP_NAME` parameterises which app's `dist/` is copied into runner — single Dockerfile reused × 6 services (gateway / auth / sender / parser / audience / notifier).
- **Invariant I-S0.2:** `APP_NAME` has NO default value — build MUST fail если caller forgets `--build-arg APP_NAME=<svc>`. Это canonical fail-loud pattern; absent it, Docker builds an "empty" image silently (per RESEARCH §5.6 mechanism #4 fail-loud discipline).
- **Invariant I-S0.3:** `NODE_VERSION` default = `22-alpine` (per CONTEXT D-12 + project_devsecops_state). Bumping к `22.12-alpine@sha256:<digest>` is RECOMMENDED for image-determinism (per RESEARCH §5.6 mechanism #4 + OQ-10). ADR Decision (c) locked `node:22-alpine` initial; digest-pinning add-on remains optional optimisation deferred к 999.18.2 Wave 0 PoC measurement.
- **K8s-ready:** Build-arg discipline (`APP_NAME` per service) supports k8s ImageMeta `imagePullPolicy: Always` with per-service tags. `image: ghcr.io/<org>/<svc>:<tag>` pattern works because каждый service builds in isolation via same Dockerfile.
- **Multi-arch:** Both `node:22-alpine` and `gcr.io/distroless/nodejs22-debian12` publish multi-arch manifests (linux/amd64 + linux/arm64). Manifest-list resolution через `docker pull` selects correct arch automatically. No special handling required.

### Section 0.3: PROTO_DIR triple-duplication kill (F-05 resolution)

This is a critical Stage 0 invariant per F-05.

- **Current state (pre-999.18.2):** `infra/docker/app.Dockerfile:82` declares `ENV PROTO_DIR=/app/proto`. Same value duplicated в `.env.docker:64` AND `.env.docker.example:65`. Three sources of truth → drift risk.
- **Reference shape:** Dockerfile MUST NOT declare `ENV PROTO_DIR=...`. Single source of truth = `env_file:` directive в `infra/docker-compose.yml` reading from `.env.docker`. Local-native dev reads from `.env.docker` через `dotenv-cli` wrapping `pnpm start:native`.
- **Invariant I-S0.4:** `grep -c '^ENV PROTO_DIR' infra/docker/app.Dockerfile` MUST equal `0`. Если non-zero, F-05 has regressed.
- **Invariant I-S0.5:** `PROTO_DIR` value lives в `.env.docker` only; consumed via `env_file:` block. App reads through `process.env.PROTO_DIR` (НЕ from Dockerfile literal). Это closes the «3 sources of truth» drift surface architecturally.
- **K8s-ready:** k8s consumes `PROTO_DIR` via `envFrom: configMapRef: <svc>-config` — same env-discipline as compose `env_file:`. Никаких Dockerfile changes для k8s portability не нужно.
- **Skill cross-check:** `twelve-factor` §"Factor III — Config" — environment variables MUST come from environment, не baked into image. `env-schema` §"Required env vars" — `PROTO_DIR` is a Zod-required field в `packages/config/src/env-schema.ts`; baking literal в Dockerfile создаёт illusion-of-default-value которая нарушает no-defaults rule.

## Stage 1: Builder

Stage 1 produces compiled `dist/` artefacts + isolated dependency closure for the target app. Stage 1 output flows в Stage 2 через `COPY --from=builder ...` directives. Per ADR Decision Turborepo finalist (D.2 §D.1 weighted-sum 35.5 winner), the Stage 1 decomposition uses three sub-stages: **pruner** (turbo prune --docker output) → **installer** (manifests-only cache anchor) → **builder** (orchestrator-driven build).

### Per-Step decomposition

#### Step 1.1: Pruner stage entry (orchestrator-finalist-specific)

**Code (Turborepo finalist — per RESEARCH §3.1 spike):**

```dockerfile
FROM node:${NODE_VERSION} AS pruner
WORKDIR /app
RUN corepack enable
COPY . .
ARG APP_NAME
RUN pnpm dlx turbo prune @email-platform/${APP_NAME} --docker
```

- **Purpose:** `turbo prune --docker` produces minimal context per service в `/app/out/json/` (manifests only) + `/app/out/full/` (manifests + source). Splits "what changed in dependency graph" from "what changed in source code" — даёт Step 1.2 a stable manifest-only cache layer.
- **Invariant I-S1.1:** First COPY есть `COPY . .` (entire workspace) — `turbo prune` requires full workspace для compute the dependency graph slice. Это APPEARS to invalidate cache on every commit, но downstream Step 1.2 reference uses ONLY pruner output (`/app/out/json` + `/app/out/full`), которое IS cache-keyed by manifests. Pruner stage не ships в runtime image.
- **Invariant I-S1.2:** `corepack enable` MUST precede `pnpm dlx turbo prune` — pnpm 11 ships via corepack (per memory `project_devsecops_state` + Node 22 Corepack experimental status); absence breaks the prune invocation with «pnpm: command not found». ADR §D.2 enforces pnpm hard-lock per D-07.
- **K8s-ready:** Pruner stage is build-time only; doesn't ship к k8s. Turbo prune output (`/app/out/json` + `/app/out/full`) is the k8s-relevant slice (minimal closure per service). Smaller closure → smaller installer-stage output → smaller runtime image.
- **Multi-arch:** `corepack enable` and `pnpm dlx turbo prune` work on amd64 AND arm64 (no native binaries в turbo CLI per RESEARCH §6.4). No special handling. QEMU emulation runs prune CLI без known compatibility issues per RESEARCH §6.1.
- **Cache behaviour:** Pruner stage is NOT cache-friendly by design — every commit invalidates `COPY . .`. Это acceptable because pruner stage is fast (~5-10s) and downstream cache savings dominate (Step 1.2 cache hit rate ≈ 99% per RESEARCH §3.1 benchmark).
- **Trade-off vs alternatives:** Plain-pnpm baseline (RESEARCH §3.6) skips этот стейдж entirely — копирует manifests directly в Step 1.2 и uses `pnpm install --filter @email-platform/${APP_NAME}...` для closure isolation. Trade-off documented в ADR §Alternatives O-06 plain-pnpm.
- **F-NN coverage:** Closes F-03 (turbo invoked at Dockerfile boundary, не bypassed) — per ADR §D.3 row F-03 «turbo prune --docker + pnpm exec turbo run build = orchestrator-in-Docker active».

#### Step 1.2: Install layer (manifests-only cache anchor)

**Code:**

```dockerfile
FROM node:${NODE_VERSION} AS installer
WORKDIR /app
RUN corepack enable

# Manifests-only copy — install layer cache key
COPY --from=pruner /app/out/json/ ./
RUN --mount=type=cache,id=pnpm,target=/pnpm/store \
    pnpm install --frozen-lockfile
```

- **Purpose:** Establish the install-layer cache key. Manifests-only copy means changes к source code (Step 1.3) не invalidate the install layer. Cache mount `id=pnpm,target=/pnpm/store` provides cross-CI-run survival of pnpm content-addressable store. Per ADR Decision (b) drop-entirely + (a) drop pnpm-deploy, install здесь = single canonical install для weak target service.
- **Invariant I-S1.3:** Step 1.2 копирует ONLY package.json + lockfile from `/app/out/json/` — NEVER source code. Любой source-code COPY here invalidates Step 1.3 install cache на every code change (что бы defeat the entire pruner-anchor purpose).
- **Invariant I-S1.4:** `--mount=type=cache,id=pnpm,target=/pnpm/store` survives across CI runs в BuildKit. Different `id=` values produce isolated caches per consumer (per RESEARCH §5.3). Cache-id = `pnpm` is canonical; if shared с `npm` cache, would cross-poison.
- **Invariant I-S1.5:** Per ADR Decision (b) drop-entirely — `injectWorkspacePackages: true` is OFF в `pnpm-workspace.yaml`. Поэтому этот install layer's cache survives across all source-code commits (manifests-only key). Если ADR letter (b) were keep-with-mitigation (`syncInjectedDepsAfterScripts: [build]`), cache would be INVALIDATED на every dist/ change because pnpm runs sync hook post-build (per pnpm Issue #9837 known limitation cited в RESEARCH §3.1 sources). ADR locked drop-entirely → этот ограничения снят architecturally.
- **K8s-ready:** Install layer ships в Stage 2 manual COPY closure (per ADR Decision (a) drop pnpm deploy). Layer is byte-deterministic given same lockfile (cache key) → image-determinism unlocked (F-20 closure mechanism). k8s digest-pinning (`image: ghcr.io/<org>/<svc>@sha256:<digest>`) viable.
- **Multi-arch:** `pnpm install --frozen-lockfile` runs natively на amd64 AND arm64. Native modules (e.g., `bcrypt` если будет добавлен) build per-arch via `node-gyp` — extends build time +5-15s under QEMU emulation per RESEARCH §6.1 acceptance. Currently (pre-999.18.2) email-platform has no native-binary deps (Node 20 baseline + foundation packages — pure JS); QEMU cost is purely tsc compilation overhead.
- **Cache behaviour:** Layer hit rate ≈ 99% on typical commits (commits that don't touch package.json или lockfile). Lockfile bump → layer rebuild → ~30-60s install (warm pnpm store via cache mount) vs ~2-5min без cache mount.

#### Step 1.3: Build layer (orchestrator-driven build)

**Code (Turborepo finalist):**

```dockerfile
FROM installer AS builder
WORKDIR /app
COPY --from=pruner /app/out/full/ ./
ARG APP_NAME
RUN pnpm exec turbo run build --filter=@email-platform/${APP_NAME}
```

- **Purpose:** Compile TypeScript → JavaScript via the orchestrator finalist (Turborepo per ADR §D.2). `--filter=@email-platform/${APP_NAME}` restricts build к target app + its dep closure (defined в `turbo.json` `dependsOn`). Single invocation replaces Step 4a-4c-cycle archaeology of current Dockerfile.
- **Invariant I-S1.6:** Source code copy uses `/app/out/full/` (pruner output), не `COPY . .` — pruner already filtered к dep-closure. Re-COPYing full workspace would defeat pruning purpose (and cache invalidation surface).
- **Invariant I-S1.7:** Build invocation is `pnpm exec turbo run build` (НЕ `pnpm --filter ... run build` — что bypasses turbo cache, который IS the F-03 root cause). Если ADR picked Nx, equivalent invocation would be `pnpm exec nx build ${APP_NAME}`. Plain-pnpm finalist would replace c `pnpm --filter @email-platform/${APP_NAME}... build` (acceptable там because plain-pnpm finalist IS the no-orchestrator baseline). ADR Decision Turborepo locked here.
- **Invariant I-S1.8:** Per ADR Decision (b) drop-entirely — NO `RUN rm -rf node_modules apps/*/node_modules packages/*/node_modules` cycle (F-02 closure). NO `RUN pnpm install --force` (F-15 archaeology root-cause closure). Под architectural-eliminate posture, эти cycles physically не нужны — injection-staleness class extinct.
- **Invariant I-S1.9 (per ADR Decision (d) Placement A pre-build CI):** Generated proto files arrive через `COPY --from=pruner` (т.е. они были generated в commit-time CI step BEFORE `docker build` and committed к workspace). NO `RUN pnpm generate:contracts` invocation в этом stage (F-12 closure). Если бы ADR Decision (d) picked Placement B build-time hook, мы бы заменили этот invariant на `pnpm generate:contracts` invocation here, gated by `--mount=type=cache` для proto output. Placement A locked → no-op.
- **K8s-ready:** `dist/` output is per-app + deterministic given same source + same lockfile → image-determinism unlocked. `kubectl rollout` patterns work because image digest is stable.
- **Multi-arch:** `tsc` runs natively на amd64 AND arm64 (TypeScript is pure-JS). `pnpm exec turbo run build` works on both archs. Если `grpc-tools` is invoked here (only если ADR Decision (d) picked Placement B build-time hook) — RESEARCH §6.4 documents grpc-tools-on-musl-arm64 fragility per A2 + grpc/grpc#21446 + #18338. **Placement A pre-build CI eliminates этот concern entirely** (gen runs once на amd64 CI runner, output committed). ADR Decision (d) Placement A locks этот workaround structurally.
- **Cache behaviour:** Build layer cache invalidated на любой source-code change inside the dep-closure. Turbo's per-task cache restores когда `inputs` unchanged (per `turbo.json tasks.build.inputs` — typically `["src/**", "tsconfig.json", "package.json"]`). Per F-24 fix (ADR §D.3 row F-24), `tasks.generate.inputs += ["pnpm-lock.yaml"]` — но build task remains source-coded.
