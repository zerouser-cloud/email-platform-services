## Stage 0: Build args + global setup

This pseudo-stage covers the Dockerfile preamble — `# syntax`, `ARG NODE_VERSION`, `ARG APP_NAME`, base image FROM declaration semantics. It is not an OCI stage proper but is the canonical anchor for all build-args + multi-arch directives + image-base discipline.

### Section 0.1: Dockerfile syntax pragma

**Code:**

```dockerfile
# syntax=docker/dockerfile:1
```

- **Purpose:** Enables BuildKit features (multi-stage, `--mount=type=cache`, `--mount=type=secret`, multi-arch buildx). Без pragma BuildKit features silently degrade к legacy builder semantics.
- **Invariant I-S0.1:** First non-comment line MUST be `# syntax=docker/dockerfile:1` (or pinned digest per OQ-10 if image-determinism is being tightened). Без неё BuildKit features silently degrade.
- **K8s-ready:** N/A — pragma applies at build-time only. Не влияет на k8s runtime.
- **Multi-arch:** N/A — pragma applies at build-time only. `docker buildx build --platform ...` использует BuildKit unconditionally.

### Section 0.2: Build-args declaration

**Code:**

```dockerfile
ARG NODE_VERSION=22-alpine
ARG APP_NAME
```

- **Purpose:** `NODE_VERSION` parameterises base image без forking Dockerfile per service. `APP_NAME` parameterises which app's `dist/` is copied into runner — single Dockerfile reused × 6 services (gateway / auth / sender / parser / audience / notifier).
- **Invariant I-S0.2:** `APP_NAME` has NO default value — build MUST fail если caller forgets `--build-arg APP_NAME=<svc>`. Это canonical fail-loud pattern; absent it, Docker builds an "empty" image silently (per RESEARCH §5.6 mechanism #4 fail-loud discipline).
- **Invariant I-S0.3:** `NODE_VERSION` default = `22-alpine` (per CONTEXT D-12 + project_devsecops_state). Bumping к `22.12-alpine@sha256:<digest>` is RECOMMENDED for image-determinism (per RESEARCH §5.6 mechanism #4 + OQ-10). ADR Decision (c) locked `node:22-alpine` initial; digest-pinning add-on remains optional optimisation deferred к 999.18.2 Wave 0 PoC measurement.
- **K8s-ready:** Build-arg discipline (`APP_NAME` per service) supports k8s ImageMeta `imagePullPolicy: Always` with per-service tags. `image: ghcr.io/<org>/<svc>:<tag>` pattern works because каждый service builds in isolation via same Dockerfile.
- **Multi-arch:** Both `node:22-alpine` and `gcr.io/distroless/nodejs22-debian12` publish multi-arch manifests (linux/amd64 + linux/arm64). Manifest-list resolution через `docker pull` selects correct arch automatically. No special handling required.

### Section 0.3: PROTO_DIR triple-duplication kill (F-05 resolution)

This is a critical Stage 0 invariant per F-05.

- **Current state (pre-999.18.2):** `infra/docker/app.Dockerfile:82` declares `ENV PROTO_DIR=/app/proto`. Same value duplicated в `.env.docker:64` AND `.env.docker.example:65`. Three sources of truth → drift risk.
- **Reference shape:** Dockerfile MUST NOT declare `ENV PROTO_DIR=...`. Single source of truth = `env_file:` directive в `infra/docker-compose.yml` reading from `.env.docker`. Local-native dev reads from `.env.docker` через `dotenv-cli` wrapping `pnpm start:native`.
- **Invariant I-S0.4:** `grep -c '^ENV PROTO_DIR' infra/docker/app.Dockerfile` MUST equal `0`. Если non-zero, F-05 has regressed.
- **Invariant I-S0.5:** `PROTO_DIR` value lives в `.env.docker` only; consumed via `env_file:` block. App reads through `process.env.PROTO_DIR` (НЕ from Dockerfile literal). Это closes the «3 sources of truth» drift surface architecturally.
- **K8s-ready:** k8s consumes `PROTO_DIR` via `envFrom: configMapRef: <svc>-config` — same env-discipline as compose `env_file:`. Никаких Dockerfile changes для k8s portability не нужно.
- **Skill cross-check:** `twelve-factor` §"Factor III — Config" — environment variables MUST come from environment, не baked into image. `env-schema` §"Required env vars" — `PROTO_DIR` is a Zod-required field в `packages/config/src/env-schema.ts`; baking literal в Dockerfile создаёт illusion-of-default-value которая нарушает no-defaults rule.

## Stage 1: Builder

Stage 1 produces compiled `dist/` artefacts + isolated dependency closure for the target app. Stage 1 output flows в Stage 2 через `COPY --from=builder ...` directives. Per ADR Decision Turborepo finalist (D.2 §D.1 weighted-sum 35.5 winner), the Stage 1 decomposition uses three sub-stages: **pruner** (turbo prune --docker output) → **installer** (manifests-only cache anchor) → **builder** (orchestrator-driven build).

### Per-Step decomposition

#### Step 1.1: Pruner stage entry (orchestrator-finalist-specific)

**Code (Turborepo finalist — per RESEARCH §3.1 spike):**

```dockerfile
FROM node:${NODE_VERSION} AS pruner
WORKDIR /app
RUN corepack enable
COPY . .
ARG APP_NAME
RUN pnpm dlx turbo prune @email-platform/${APP_NAME} --docker
```

- **Purpose:** `turbo prune --docker` produces minimal context per service в `/app/out/json/` (manifests only) + `/app/out/full/` (manifests + source). Splits "what changed in dependency graph" from "what changed in source code" — даёт Step 1.2 a stable manifest-only cache layer.
- **Invariant I-S1.1:** First COPY есть `COPY . .` (entire workspace) — `turbo prune` requires full workspace для compute the dependency graph slice. Это APPEARS to invalidate cache on every commit, но downstream Step 1.2 reference uses ONLY pruner output (`/app/out/json` + `/app/out/full`), которое IS cache-keyed by manifests. Pruner stage не ships в runtime image.
- **Invariant I-S1.2:** `corepack enable` MUST precede `pnpm dlx turbo prune` — pnpm 11 ships via corepack (per memory `project_devsecops_state` + Node 22 Corepack experimental status); absence breaks the prune invocation with «pnpm: command not found». ADR §D.2 enforces pnpm hard-lock per D-07.
- **K8s-ready:** Pruner stage is build-time only; doesn't ship к k8s. Turbo prune output (`/app/out/json` + `/app/out/full`) is the k8s-relevant slice (minimal closure per service). Smaller closure → smaller installer-stage output → smaller runtime image.
- **Multi-arch:** `corepack enable` and `pnpm dlx turbo prune` work on amd64 AND arm64 (no native binaries в turbo CLI per RESEARCH §6.4). No special handling. QEMU emulation runs prune CLI без known compatibility issues per RESEARCH §6.1.
- **Cache behaviour:** Pruner stage is NOT cache-friendly by design — every commit invalidates `COPY . .`. Это acceptable because pruner stage is fast (~5-10s) and downstream cache savings dominate (Step 1.2 cache hit rate ≈ 99% per RESEARCH §3.1 benchmark).
- **Trade-off vs alternatives:** Plain-pnpm baseline (RESEARCH §3.6) skips этот стейдж entirely — копирует manifests directly в Step 1.2 и uses `pnpm install --filter @email-platform/${APP_NAME}...` для closure isolation. Trade-off documented в ADR §Alternatives O-06 plain-pnpm.
- **F-NN coverage:** Closes F-03 (turbo invoked at Dockerfile boundary, не bypassed) — per ADR §D.3 row F-03 «turbo prune --docker + pnpm exec turbo run build = orchestrator-in-Docker active».

#### Step 1.2: Install layer (manifests-only cache anchor)

**Code:**

```dockerfile
FROM node:${NODE_VERSION} AS installer
WORKDIR /app
RUN corepack enable

# Manifests-only copy — install layer cache key
COPY --from=pruner /app/out/json/ ./
RUN --mount=type=cache,id=pnpm,target=/pnpm/store \
    pnpm install --frozen-lockfile
```

- **Purpose:** Establish the install-layer cache key. Manifests-only copy means changes к source code (Step 1.3) не invalidate the install layer. Cache mount `id=pnpm,target=/pnpm/store` provides cross-CI-run survival of pnpm content-addressable store. Per ADR Decision (b) drop-entirely + (a) drop pnpm-deploy, install здесь = single canonical install для weak target service.
- **Invariant I-S1.3:** Step 1.2 копирует ONLY package.json + lockfile from `/app/out/json/` — NEVER source code. Любой source-code COPY here invalidates Step 1.3 install cache на every code change (что бы defeat the entire pruner-anchor purpose).
- **Invariant I-S1.4:** `--mount=type=cache,id=pnpm,target=/pnpm/store` survives across CI runs в BuildKit. Different `id=` values produce isolated caches per consumer (per RESEARCH §5.3). Cache-id = `pnpm` is canonical; if shared с `npm` cache, would cross-poison.
- **Invariant I-S1.5:** Per ADR Decision (b) drop-entirely — `injectWorkspacePackages: true` is OFF в `pnpm-workspace.yaml`. Поэтому этот install layer's cache survives across all source-code commits (manifests-only key). Если ADR letter (b) were keep-with-mitigation (`syncInjectedDepsAfterScripts: [build]`), cache would be INVALIDATED на every dist/ change because pnpm runs sync hook post-build (per pnpm Issue #9837 known limitation cited в RESEARCH §3.1 sources). ADR locked drop-entirely → этот ограничения снят architecturally.
- **K8s-ready:** Install layer ships в Stage 2 manual COPY closure (per ADR Decision (a) drop pnpm deploy). Layer is byte-deterministic given same lockfile (cache key) → image-determinism unlocked (F-20 closure mechanism). k8s digest-pinning (`image: ghcr.io/<org>/<svc>@sha256:<digest>`) viable.
- **Multi-arch:** `pnpm install --frozen-lockfile` runs natively на amd64 AND arm64. Native modules (e.g., `bcrypt` если будет добавлен) build per-arch via `node-gyp` — extends build time +5-15s under QEMU emulation per RESEARCH §6.1 acceptance. Currently (pre-999.18.2) email-platform has no native-binary deps (Node 20 baseline + foundation packages — pure JS); QEMU cost is purely tsc compilation overhead.
- **Cache behaviour:** Layer hit rate ≈ 99% on typical commits (commits that don't touch package.json или lockfile). Lockfile bump → layer rebuild → ~30-60s install (warm pnpm store via cache mount) vs ~2-5min без cache mount.

#### Step 1.3: Build layer (orchestrator-driven build)

**Code (Turborepo finalist):**

```dockerfile
FROM installer AS builder
WORKDIR /app
COPY --from=pruner /app/out/full/ ./
ARG APP_NAME
RUN pnpm exec turbo run build --filter=@email-platform/${APP_NAME}
```

- **Purpose:** Compile TypeScript → JavaScript via the orchestrator finalist (Turborepo per ADR §D.2). `--filter=@email-platform/${APP_NAME}` restricts build к target app + its dep closure (defined в `turbo.json` `dependsOn`). Single invocation replaces Step 4a-4c-cycle archaeology of current Dockerfile.
- **Invariant I-S1.6:** Source code copy uses `/app/out/full/` (pruner output), не `COPY . .` — pruner already filtered к dep-closure. Re-COPYing full workspace would defeat pruning purpose (and cache invalidation surface).
- **Invariant I-S1.7:** Build invocation is `pnpm exec turbo run build` (НЕ `pnpm --filter ... run build` — что bypasses turbo cache, который IS the F-03 root cause). Если ADR picked Nx, equivalent invocation would be `pnpm exec nx build ${APP_NAME}`. Plain-pnpm finalist would replace c `pnpm --filter @email-platform/${APP_NAME}... build` (acceptable там because plain-pnpm finalist IS the no-orchestrator baseline). ADR Decision Turborepo locked here.
- **Invariant I-S1.8:** Per ADR Decision (b) drop-entirely — NO `RUN rm -rf node_modules apps/*/node_modules packages/*/node_modules` cycle (F-02 closure). NO `RUN pnpm install --force` (F-15 archaeology root-cause closure). Под architectural-eliminate posture, эти cycles physically не нужны — injection-staleness class extinct.
- **Invariant I-S1.9:** Per ADR Decision (d) Placement A pre-build CI — generated proto files arrive через `COPY --from=pruner` (т.е. они были generated в commit-time CI step BEFORE `docker build` and committed к workspace). NO `RUN pnpm generate:contracts` invocation в этом stage (F-12 closure). Если бы ADR Decision (d) picked Placement B build-time hook, мы бы заменили этот invariant на `pnpm generate:contracts` invocation here, gated by `--mount=type=cache` для proto output. Placement A locked → no-op.
- **K8s-ready:** `dist/` output is per-app + deterministic given same source + same lockfile → image-determinism unlocked. `kubectl rollout` patterns work because image digest is stable.
- **Multi-arch:** `tsc` runs natively на amd64 AND arm64 (TypeScript is pure-JS). `pnpm exec turbo run build` works on both archs. Если `grpc-tools` is invoked here (only если ADR Decision (d) picked Placement B build-time hook) — RESEARCH §6.4 documents grpc-tools-on-musl-arm64 fragility per A2 + grpc/grpc#21446 + #18338. **Placement A pre-build CI eliminates этот concern entirely** (gen runs once на amd64 CI runner, output committed). ADR Decision (d) Placement A locks этот workaround structurally.
- **Cache behaviour:** Build layer cache invalidated на любой source-code change inside the dep-closure. Turbo's per-task cache restores когда `inputs` unchanged (per `turbo.json tasks.build.inputs` — typically `["src/**", "tsconfig.json", "package.json"]`). Per F-24 fix (ADR §D.3 row F-24), `tasks.generate.inputs += ["pnpm-lock.yaml"]` — но build task remains source-coded.

## Stage 2: Runner

Stage 2 produces the runtime image that ships к k8s (или compose). Stage 2's shape determines image size, attack surface, k8s probe-target reachability, and image-determinism feasibility. Per ADR Decision (a) DROP `pnpm deploy --prod` + (b) DROP-ENTIRELY `injectWorkspacePackages` + (c) `node:22-alpine` runner (initial; distroless deferred к Path X / R-01), Stage 2 uses a manual `COPY --from=builder` closure instead of a `pnpm deploy` bundle.

### Per-Step decomposition

#### Step 2.1: Runner stage entry + non-root user

**Code:**

```dockerfile
FROM node:${NODE_VERSION} AS runner
RUN addgroup -g 1001 -S appgroup && adduser -S appuser -u 1001 -G appgroup
WORKDIR /app
```

- **Purpose:** Establish a non-root runtime user (uid 1001 / gid 1001). k8s `securityContext: runAsNonRoot: true` requires non-root entry; alpine's default `node` user (uid 1000) acceptable, но explicit `appuser` соответствует project precedent (current `infra/docker/app.Dockerfile:53`). Per ADR Decision (c) image base — `node:${NODE_VERSION}` resolves к `node:22-alpine` initial; distroless swap-in path (`ARG BASE_RUNNER=...` toggle) deferred к Path X / R-01.
- **Invariant I-S2.1:** UID/GID are explicitly numeric (`1001`) — k8s `runAsUser: 1001` matches без name-resolution. Alphabetic-only users (`USER appuser`) require name resolution at admission control time (works on alpine; fragile across base-image changes — distroless containers без `/etc/passwd` would FAIL alphabetic USER directive resolution).
- **Invariant I-S2.2:** Last `USER appuser` directive precedes `CMD` (Step 2.4). All COPY directives BEFORE `USER` так что они have root permissions to write into `/app/`. Если COPY landed post-`USER`, files would be appuser-owned, что creates write-permission issues if any subsequent COPY is also expected to be appuser-owned (NestJS apps typically read-only at runtime, но runtime tmp dir creation through app code requires appuser write to `/tmp/`).
- **K8s-ready:** Non-root + numeric UID = `securityContext: runAsNonRoot: true, runAsUser: 1001` в pod spec works без modification. `readOnlyRootFilesystem: true` compatible because app writes только к `/tmp/` (Linux tmpfs on k8s emptyDir). Restricted PSS (Pod Security Standards `restricted` profile) compliance criterion satisfied.
- **Multi-arch:** `addgroup` + `adduser` are alpine BusyBox commands — work identically on amd64 + arm64 alpine images (same multi-arch manifest). No special handling required.
- **Cache behaviour:** Layer is reused across all builds (immutable user creation). Cache hit rate ≈ 100% — invalidation only on `NODE_VERSION` bump.

#### Step 2.2: Manual COPY closure (per ADR Decision (a) drop pnpm deploy)

**Code:**

```dockerfile
ARG APP_NAME
COPY --from=builder /app/apps/${APP_NAME}/dist ./dist
COPY --from=builder /app/apps/${APP_NAME}/node_modules ./node_modules
COPY --from=builder /app/packages /app/packages
COPY --from=builder /app/node_modules/.modules.yaml /app/node_modules/.modules.yaml
```

- **Purpose:** Manually compose the runtime image content from builder stage. Per ADR Decision (a) DROP `pnpm deploy --prod` — replaced by explicit COPY of (1) target app `dist/`, (2) target app's resolved `node_modules/`, (3) shared `packages/` (consumed via workspace symlinks resolved at install time), (4) `.modules.yaml` (pnpm's resolved-deps manifest — required для node_modules symlink integrity validation at runtime).
- **Invariant I-S2.3:** Per ADR Decision (b) DROP-ENTIRELY — `injectWorkspacePackages: true` is OFF в `pnpm-workspace.yaml`. Поэтому `apps/${APP_NAME}/node_modules/@email-platform/*` are workspace symlinks pointing into `packages/*` (NOT injected copies). The `COPY --from=builder /app/packages /app/packages` line MUST land BEFORE `node_modules` symlinks resolve at runtime — Docker COPY preserves symlinks as symlinks; runtime resolution depends on target existing. Если бы (b) был keep-with-mit, copies would carry `syncInjectedDepsAfterScripts: [build]` artifacts — но (b) drop-entirely architecturally eliminates this.
- **Invariant I-S2.4:** Image determinism (F-20 closure) — manual COPY closure is byte-deterministic given same builder-stage output. Combined с `SOURCE_DATE_EPOCH=$(git log -1 --format=%ct)` в CI invocation (per RESEARCH §5.6 mechanism #2 + OQ-05) — image digests reproduce across builds of same git SHA. Build determinism proof recipe lives в Appendix A (script authored в 999.18.2 Wave 0 per RESEARCH §11.4-§11.5).
- **Invariant I-S2.5:** NO `RUN pnpm install --prod` в этом stage. `pnpm deploy --prod` is dropped per ADR Decision (a) — manual COPY replaces it. Adding `pnpm install --prod` would re-introduce install-step variability (pnpm's lockfile resolution + native module rebuild on alpine) which breaks image determinism (F-20 regression class) AND re-introduces F-15 «archaeology» risk surface. Architectural-eliminate posture закрывает оба.
- **K8s-ready:** Image content is deterministic + multi-arch — k8s digest-pinning works (`image: ghcr.io/<org>/<svc>@sha256:<digest>`). Image size estimate ≈ 200-280MB на `node:22-alpine` base (per RESEARCH §3.1 spike). `imagePullPolicy: IfNotPresent` viable because digest pin guarantees unique content.
- **Multi-arch:** All COPY operations work identically на amd64 + arm64 (no native binary execution at COPY time). Native modules в `node_modules` were built per-arch в Step 1.2 install layer (different node_modules tree per buildx platform leg). QEMU emulation handles cross-arch COPY transparently per RESEARCH §6.1.
- **Cache behaviour:** Layer hit when builder-stage output unchanged. Per-app cache isolation via `${APP_NAME}` build-arg → каждый service has independent cache key. Multi-platform builds spawn one cache entry per platform leg (amd64 + arm64) per RESEARCH §6.4.
- **F-NN coverage:** F-01 (no injection mitigation needed — model dropped per ADR (b)), F-02 (no `rm -rf` cycles), F-15 (5 prior fixes archaeology root-cause structurally closed), F-20 (image determinism enabled per RESEARCH §5.6 mechanisms #1+#2+#6).

#### Step 2.3: Health probe shape callout + ENV discipline

**Code (no Dockerfile content — this is a callout subsection):**

None — Dockerfile does NOT define `HEALTHCHECK` directives (those live в `infra/docker-compose*.yml`). This subsection documents the SHAPE constraint that Stage 2 establishes для probe-target reachability.

- **Purpose:** Even though Dockerfile doesn't define healthchecks (per project convention — compose owns probe config; k8s manifests own probe config in deploy phase), the runner stage's shape determines what probe targets are reachable. Per `999.18.1-PATTERNS.md` Difference 5 — Dockerfile reference shape MUST flag this even when Dockerfile itself не defines probe.
- **Invariant I-S2.6:** Runner stage MUST contain a shell (`/bin/sh` или `/bin/ash`) для compose `healthcheck.test` invocations like `wget -qO- http://localhost:3000/health/ready || exit 1`. `node:22-alpine` ships c BusyBox `ash` — works нативно. Distroless `gcr.io/distroless/nodejs22` does NOT ship a shell — requires k8s-only HTTP probe (`httpGet:` not `exec:`). ADR Decision (c) locks alpine runner initial → этот invariant satisfied; distroless swap-in (Path X) requires compose healthcheck format migration к k8s-style HTTP probe AND `runtime-smoke-verification` skill's curl recipe needs ash-equivalent inside container OR moves к host-side curl only.
- **Invariant I-S2.7:** Runner exposes service port via `EXPOSE 3000` (или per-service mapping per `apps/${APP_NAME}/src/main.ts` listen port). compose `healthcheck.test: ["CMD-SHELL", "wget -qO- http://localhost:3000/health/ready || exit 1"]` invokes against this exposed port. Если EXPOSE отсутствует, port mapping в compose `ports:` всё равно работает (EXPOSE — это документация, не функциональный gate), но healthcheck container-internal call requires port reachable internally.
- **K8s-ready:** k8s `livenessProbe.httpGet` + `readinessProbe.httpGet` + `startupProbe.httpGet` work против EXPOSE'd port без modification (per RESEARCH §8.2 k8s probe semantic mapping). `startupProbe` recommendation: `failureThreshold: 30, periodSeconds: 1, httpGet: /health/ready` — covers ~28s cold-start observed в 999.11.1 (per RESEARCH §8.2 + OQ-08). `/health/live` (deps-free, fast) → liveness; `/health/ready` (deps-checked, может быть slow) → readiness/startup. Этот split уже implemented в `packages/foundation/src/health/` per Phase 999.11.1.
- **F-NN coverage:** F-04 / F-04-d8 are addressed в MIGRATION-RUNBOOK Wave 3 (compose-file edit, не Dockerfile edit). Однако Stage 2 shape DOES enable F-04 V1 (compose healthcheck `/health/live` → `/health/ready` swap) by providing shell + EXPOSE'd port + HTTP server (per F-04 V1 в 999.18-SOLUTIONS.md).
- **Skill cross-check:** `runtime-smoke-verification` §"Test ALL local startup flows" — both `pnpm start:native` (host curl :3000/health/ready) and `pnpm start:isolated` (container curl :4000/health/ready через compose healthcheck) preserved через Stage 2 shape. Distroless swap-in (Path X) would break `pnpm start:isolated` host-curl-via-exec patterns; Path X migration must update skill recipe simultaneously.

#### Step 2.4: Final USER + CMD

**Code:**

```dockerfile
USER appuser
CMD ["node", "dist/main.js"]
```

- **Purpose:** Drop privileges к `appuser` (uid 1001) and start the NestJS app via node entry point. Runtime entry point is the bundled `dist/main.js` produced by Step 1.3 builder stage; `node` binary inherited from base image.
- **Invariant I-S2.8:** `USER appuser` MUST be the LAST non-CMD directive before `CMD`. Subsequent COPY would land as appuser-owned; if missed, files would be root-owned and unwritable for runtime app needs (e.g., temp dir creation если app writes к `/tmp/`). Privilege escalation post-`USER` is not possible в OCI runtime — once dropped к appuser, container cannot return к root без `--user 0` runtime override (which deployment manifests should never apply).
- **Invariant I-S2.9:** `CMD ["node", "dist/main.js"]` uses exec form (JSON array), NOT shell form (`CMD node dist/main.js`). Exec form makes `node` PID 1 — receives SIGTERM directly from k8s pod termination signal. Shell form wraps в `/bin/sh -c` который doesn't propagate signals → k8s `terminationGracePeriodSeconds` exhausts before app gracefully shuts down (in-flight requests dropped, RabbitMQ unack'd, gRPC streams half-closed). Critical для NestJS `OnApplicationShutdown` lifecycle hooks + `nestjs-pino` graceful flush.
- **K8s-ready:** Exec form CMD + `node` as PID 1 = `terminationGracePeriodSeconds: 30` (default) gives the app explicit shutdown window. Critical для graceful in-flight request draining + connection close (per `nestjs-pino` shutdown hook patterns + 999.11.1 graceful-shutdown precedent).
- **Multi-arch:** `node` binary present на both amd64 + arm64 alpine images (same multi-arch manifest tag `node:22-alpine`). No special handling required.

### Stage 2 summary — composed runner shape

The runner stage as a whole is **a deterministic, multi-arch, k8s-ready, non-root, shell-equipped, exec-form-launched node:22-alpine image** assembled через manual COPY closure (no `pnpm deploy`, no `pnpm install --prod`, no `injectWorkspacePackages` artefacts). Каждый из these adjectives maps к specific invariants:

- **deterministic** → I-S2.4 (manual COPY + SOURCE_DATE_EPOCH = byte-reproducible) + I-S2.5 (no install-step variability) — F-20 closure mechanism.
- **multi-arch** → I-S2.5 + Step 2.2 Multi-arch annotation (per-arch node_modules built в Step 1.2; QEMU emulation per RESEARCH §6.4) — F-08 closure mechanism (CI side); Stage 2 inherits the per-arch manifest discipline transparently.
- **k8s-ready** → I-S2.1 (numeric UID for `runAsUser`) + I-S2.6 (shell для compose probe-shape parity with k8s `httpGet:`) + I-S2.9 (exec form CMD для SIGTERM propagation) + every `**K8s-ready:**` callout in Steps 2.1-2.4.
- **non-root** → I-S2.1 + I-S2.2 + I-S2.8 (USER discipline before CMD; numeric UID; final-USER-precedes-CMD ordering) — k8s `securityContext: runAsNonRoot: true` compliant out-of-the-box.
- **shell-equipped** → I-S2.6 (BusyBox `ash` from alpine base) — preserves compose `healthcheck.test: ["CMD-SHELL", ...]` flow during Path X transition window. Distroless swap-in (Path X) trades shell-presence for smaller attack surface; ADR Decision (c) deferred this to k8s-only deploy phase.
- **exec-form-launched** → I-S2.9 (`CMD ["node", "dist/main.js"]` JSON array) — `node` becomes PID 1, receives SIGTERM directly, NestJS `OnApplicationShutdown` hooks fire predictably.

**The runner stage's content lineage** (top-down): `node:22-alpine` → addgroup/adduser → `COPY --from=builder` (dist + node_modules + packages + .modules.yaml) → `USER appuser` → `CMD ["node", "dist/main.js"]`. Каждый layer is grep-verifiable post-implementation through the invariants above.

**What this stage does NOT do** (deliberate omissions, all driven by ADR Decision letters):

- No `RUN pnpm install --prod` (per Decision (a) DROP — manual COPY replaces deploy bundle; per I-S2.5).
- No `RUN pnpm prune --prod` (per Decision (a) trade-off — image +5-15% size accepted; mitigation deferred to 999.18.2 Wave 0 PoC measurement per ADR §C.4 R-02 contingent action).
- No `RUN pnpm generate:contracts` (per Decision (d) Placement A — generated files arrive via `COPY --from=pruner` of pre-build CI commit; per I-S1.9 closure).
- No `HEALTHCHECK` directive (per project convention — compose owns probe config; k8s manifests own probe config in deploy phase; per I-S2.6 + I-S2.7 callout discipline; per `999.18.1-PATTERNS.md` Difference 5).
- No `ENV PROTO_DIR=...` (per F-05 closure — Stage 0 §0.3 single source of truth in `.env.docker` via `env_file:`; per I-S0.4 + I-S0.5).
- No `RUN apk add wget` (alpine ships BusyBox `wget` natively — но distroless transition (Path X) WOULD require host-side curl OR exec-style http probe migration — flagged in I-S2.6 invariant).

## Appendix A: Build determinism proof recipe

Per F-20 closure mandate (per RESEARCH §11.5). The reference Dockerfile, когда invoked at fixed git SHA, produces identical image digests across builds.

```bash
#!/bin/bash
# scripts/verify-image-determinism.sh
# (Wave 0 of 999.18.2 per RESEARCH §11.4 — author там, не here)

set -euo pipefail
SHA=${1:-HEAD}
SVC=${2:-auth}
git checkout $SHA
docker buildx build --no-cache --load \
    --build-arg APP_NAME=$SVC \
    -f infra/docker/app.Dockerfile -t test:1 .
docker image inspect test:1 --format '{{.Id}}' > /tmp/digest1
docker buildx build --no-cache --load \
    --build-arg APP_NAME=$SVC \
    -f infra/docker/app.Dockerfile -t test:2 .
docker image inspect test:2 --format '{{.Id}}' > /tmp/digest2
diff /tmp/digest1 /tmp/digest2 && echo "DETERMINISTIC" || (echo "NON-DETERMINISTIC" && exit 1)
```

This recipe lives в `scripts/verify-image-determinism.sh` post-999.18.2 Wave 0. Documented здесь for reference only — script authoring is 999.18.2 Plan 0X scope. Под `SOURCE_DATE_EPOCH=$(git log -1 --format=%ct)` discipline (per RESEARCH §5.6 mechanism #2), the recipe MUST produce `DETERMINISTIC` or fail loudly.
