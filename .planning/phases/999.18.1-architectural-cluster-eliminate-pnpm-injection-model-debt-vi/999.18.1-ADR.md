### Problem statement

Email Platform — 6 NestJS микросервисов в pnpm monorepo (`apps/auth` + `apps/sender` + `apps/parser` + `apps/audience` + `apps/notifier` + `apps/gateway`) + 3 shared packages (`packages/contracts` + `packages/config` + `packages/foundation`). Current build pipeline (audit-snapshot per `999.18-AUDIT.md`):

- pnpm 11 + `injectWorkspacePackages: true` (community-flagged "foot gun" per pnpm Discussion #3938 — see RESEARCH §Sources Primary `pnpm Discussion #3938`).
- Single multi-stage `infra/docker/app.Dockerfile` reused × 6 services через `ARG APP_NAME` (per RESEARCH §3.1 baseline).
- Turbo orchestration на host; **bypassed inside Dockerfile** (per-package `pnpm --filter ... run build` invocations — F-03 per `999.18-AUDIT.md` F-03 §Evidence).
- Step 4b + Step 4d cycles `rm -rf node_modules + pnpm install --frozen-lockfile` to refresh injected dist (F-02; root cause F-01 per `999.18-AUDIT.md`).
- Multi-arch CI absent — `.github/workflows/docker-build.yml` has no `platforms:` arg (F-08 BLOCKER per `999.18-AUDIT.md`).
- Contract generation × 6 parallel CI jobs (F-12), with cache hash blind to ts-proto version (F-24 per `999.18-AUDIT.md` F-24 §Evidence).
- 5 prior infra fix commits (`132138d` / `fb8dee7` / `6fc9d3c` / `b9d1913` / `da70085`) form patch-on-patch archaeology (F-15 BLOCKER).

12 deferred BLOCKER+MAJOR findings из 999.18 audit (`F-01` / `F-02` / `F-03` / `F-04` / `F-04-d8` / `F-05` / `F-08` / `F-12` / `F-14` / `F-15` / `F-20` / `F-24`) clustered into THREE архитектурных оси per RESEARCH §1:

### D.2. Locked finalist + four coupled cross-cutting choices

**ADR-001 LOCKS: Turborepo + `turbo prune --docker` + manual `COPY --from=builder` runner stage closure + commit-time contract generation + lockfile-aware cache invalidation для generate task.**

The four coupled cross-cutting choices that this Decision binds atomically per RESEARCH §12.2 mandate:

- **(a) `pnpm deploy --prod` keep / drop → DROP.** Per RESEARCH §5.4 recommendation: «DROP `pnpm deploy --prod` in favor of manual COPY runner stage». The runner stage of the new Dockerfile uses `COPY --from=builder /app/apps/${APP_NAME}/dist + /app/apps/${APP_NAME}/node_modules + /app/packages` pattern (per RESEARCH §3.1 spike Stage 4 lines 191-200). Trade-off: image +5-15% size (per RESEARCH §3.1 / OQ-03) — acceptable for the architectural cleanup that eliminates F-01 / F-14 staleness class structurally.

- **(b) `injectWorkspacePackages: true` keep-with-mitigation / drop-entirely → DROP-ENTIRELY (M3 chosen).** Per RESEARCH §5.5 recommendation: «M2 OR M3 (architectural eliminate) — NOT M1 (perpetuates foot gun)». ADR locks **M3** — sub-pattern (post-999.18.3 amendment): Stage 1.1.5 fetcher: `pnpm fetch` (full set including devDeps) → Stage 1.2 installer: `pnpm install --offline --frozen-lockfile` (full, для builder needs) → Stage 1.3 builder: `nest build` + `pnpm prune --prod` (strip devDeps in-place) → Stage 2 runner: manual `COPY --from=builder /app/node_modules` (already pruned). Mechanism: separate `fetcher` sub-stage в Stage 1 populates virtual store из lockfile с full dep tree; installer sub-stage запускает `pnpm install --offline --frozen-lockfile` (no network, full set); builder runs `pnpm exec turbo run build` followed by `pnpm prune --prod` post-build для in-place devDeps removal; manual COPY runner per ADR §D.2 (a) DROP `pnpm deploy --prod`. Eliminates the entire pnpm Discussion #3938 «foot gun» class structurally — F-01 / F-14 / F-15 close ARCHITECTURALLY (per RESEARCH §3.1 F-NN coverage table). Rationale «делать максимально правильно архитектурно» (D-16 user review): M3 даёт лучшую cache-mount granularity (tarball cache отделён от install layer — отдельный `--mount=type=cache,id=pnpm-fetch` vs `--mount=type=cache,id=pnpm-install`); готовит проект к scale-out N=15-20 services per CONTEXT D-04 (Lockfile-only layer rebuilds rarely; install layer rebuilds on workspace topology change per RESEARCH §3.6 Dockerfile spike); supported pattern в pnpm community для production Docker builds (per pnpm.io/cli/fetch + RESEARCH §3.6 sources). M2 (drop injection + drop pnpm deploy + manual COPY) был initial executor's choice; D-16 user review escalated к M3 для long-term cache-friendliness под service growth horizon. **Post-999.18.3 sub-pattern clarification** (CONTEXT D-03): pre-amendment text «`pnpm fetch --prod` + `pnpm install --offline --frozen-lockfile` + manual COPY runner» reformulated на full-fetch + offline-install + post-build prune sub-pattern; M3 mechanism preserved, NOT revised. Triggered by T-PROC-03 fire (999.18.2 Wave 2/3/4 isolated smoke gate failures empirically falsified «transient cache desync» hypothesis; root cause = scope mismatch fetcher/installer). Sub-pattern endorsed per RESEARCH §5.4 (`pnpm prune --prod` mitigation) + Bazyli Brzóska (NestJS official Dockerfile) + Liran Tal (Snyk JSConf EU 2023 «Production-grade Docker for Node.js monorepos») для single-service-per-build context.

- **(c) Image base + healthcheck protocol — distroless runner сразу + transport-aligned healthcheck.** Per RESEARCH §5.2 image base table + §5.7 Path X/Y revisited: builder stage = `node:22-alpine` (proven small/fast install layer); **runner stage = `gcr.io/distroless/nodejs22-debian12:nonroot` (immediate adoption, no two-phase evolution)**. D-16 user review супernse'ит executor's initial Path X choice (alpine retain initial + deferred distroless): «Резало глаз что gRPC сервисы держат HTTP сервер только ради `wget /health/ready`». Transport-aligned healthcheck protocol — каждый сервис использует свой transport-natural healthcheck mechanism, не universally-HTTP:
  - **(c.1) gateway** — HTTP `GET /health/ready` (preserved — это HTTP сервис; компose healthcheck `wget -qO- http://localhost:3000/health/ready`).
  - **(c.2) auth / sender / parser / audience** (4 gRPC services) — gRPC `grpc.health.v1.Health/Check` через `grpc-health-check` package (уже в `package.json` deps); `grpc_health_probe` Go static binary копируется в runner stage; compose / k8s healthcheck использует `grpc_health_probe -addr=:<grpc-port>`. HTTP server в этих сервисах больше не запускается — phantom HTTP listener дропается per Wave 2 transport-aligned cleanup (см. MIGRATION-RUNBOOK Wave 2).
  - **(c.3) notifier** — gRPC Health-only server (вариант N-A — для consistency с другими non-HTTP сервисами); ранее notifier = pure RMQ consumer без external server; теперь добавляет минимальный gRPC Health-only listener регистрирующий только `grpc.health.v1.Health/Check`. Compose/k8s healthcheck тот же `grpc_health_probe -addr=:<grpc-port>`.

  Rationale (D-16 user review): (1) **Hexagonal-friendly** — каждый сервис имеет ровно один primary adapter (gateway = REST inbound; auth/sender/parser/audience = gRPC inbound; notifier = RMQ inbound + gRPC Health), нет phantom HTTP server'а в gRPC сервисах ради ALB/healthcheck'а. Соответствует `clean-ddd-hexagonal` skill Direction split inside `infrastructure/inbound/` partition. (2) **Smaller attack surface + smaller image** — distroless `gcr.io/distroless/nodejs22-debian12:nonroot` ≈ 80MB vs alpine + Node ≈ 50-150MB всё-равно лучше + no shell + no package manager + no debug — industry standard для production k8s deploy. (3) **K8s-ready immediately** — distroless multi-arch native (linux/amd64 + linux/arm64 per Google docs); k8s 1.24+ имеет native gRPC probe support (`grpc:` field в probe spec), но `grpc_health_probe` Go static binary — interim solution для compose + k8s 1.23-, removable per RE-EVAL trigger T-PROC-04. (4) **Closes pre-existing pitfall structurally** — parser /health/ready S3-timeout hang (memory `project_parser_health_s3_timeout`) — нет HTTP path = нет hang; `grpc.health.v1.Health/Check` имеет client-side deadline через grpc-health-check package config. (5) **Branching-patterns compliant** — transport-aligned dispatch (HTTP для gateway, gRPC для остальных) — естественный transport-natural выбор, не if/else NODE_ENV branching.

- **(d) Contract generation placement — Placement A pre-build CI step.** Per RESEARCH §7.4 recommendation: «**Placement A** (pre-build CI step), with F-24 fix sequenced FIRST in 999.18.2 impl (per 999.18 SOLUTIONS.md F-24 / F-12 ordering), and CI drift-check gate added to fail fast on unsync». ADR locks Placement A: `pnpm generate:contracts` invoked в CI workflow BEFORE matrix-style `docker buildx build`; generated files committed to git (idempotence guarantee per W5 D-W5-03 carry-forward); Dockerfile drops the `pnpm --filter @email-platform/contracts run generate` invocation. CI drift-check gate (`git diff --exit-code packages/contracts/src/generated/`) authored as part of 999.18.2 Wave 3.

**Implicit FIFTH coupled choice — Multi-arch initial strategy → `docker buildx build --platform linux/amd64,linux/arm64` + QEMU emulation на amd64 GitHub-hosted runners (cost-zero start).** Per RESEARCH §6.4 recommendation + CONTEXT D-11 explicit guidance.
