## Warnings

### WR-01: `loadConfig` кэш растёт без границ и не имеет очистки (возможная утечка в тестах / HMR)

**File:** `packages/foundation/src/external/config/load-config.ts:3-20`
**Issue:** Модульный кэш `const cache = new Map<z.ZodType, unknown>()` объявлен без ограничения размера и без экспортированного метода сброса. Для нормального boot-процесса (один схема-reference на процесс) это абсолютно корректно и даёт нужную идемпотентность. Но:

1. В unit-тестах, где одна и та же схема парсится под разные `process.env` (для покрытия негативных кейсов), кэш возвращает устаревший результат — тесты скрытно начинают проходить по старым данным.
2. В сценарии `ts-node-dev` / HMR модуль-уровневая `Map` переживает перезагрузки только в пределах одного модуля; при реимпорте foundation с новым экземпляром `Map` всё в порядке, но если тесты используют jest `resetModules`, поведение становится зависимым от того, очищается ли foundation.
3. `cache.set(schema, result)` кладёт в значение `unknown`, а возвращает `as z.infer<T>`. Если кто-то случайно вызовет `loadConfig(schemaA)` и `loadConfig(schemaB)`, где один — `ZodObject`, другой — `ZodEffects` от того же объекта, получатся разные ключи (это нормально, но усиливает зависимость от reference-identity).

Сейчас это не баг — это implicit assumption без теста. Стоит зафиксировать контракт.

**Fix:** Экспортировать `resetConfigCache()` (no-op в prod, использование — тесты) и задокументировать reference-identity-контракт inline. Минимально:

```typescript
const cache = new Map<z.ZodType, unknown>();

export function loadConfig<T extends z.ZodType>(schema: T): z.infer<T> {
  const cached = cache.get(schema);
  if (cached !== undefined) return cached as z.infer<T>;

  const result = schema.parse(process.env);
  cache.set(schema, result);
  return result as z.infer<T>;
}

/**
 * Clears the schema->config cache. Intended for test suites that mutate
 * process.env between cases. NEVER call in production code.
 */
export function resetConfigCache(): void {
  cache.clear();
}
```

Также: `if (cached)` — false-negative для валидных конфигов, где `undefined` не должен быть, но Zod может вернуть пустой объект `{}`, который truthy, так что здесь всё хорошо. Тем не менее `cached !== undefined` точнее передаёт намерение.

### WR-02: Приведение `as AuthEnv` / `as AudienceEnv` / etc. в каждом `main.ts` — потенциальный sink для drift между `*EnvSchema` и `*Env` type alias

**File:** `apps/auth/src/main.ts:10`, `apps/audience/src/main.ts:10`, `apps/gateway/src/main.ts:17`, `apps/notifier/src/main.ts:10`, `apps/parser/src/main.ts:10`, `apps/sender/src/main.ts:10`
**Issue:** Во всех шести `main.ts` повторяется шаблон:

```typescript
const config = loadConfig(AuthEnvSchema) as AuthEnv;
```

Приведение `as` нужно только потому, что `AuthEnv` объявлен как intersection (`GlobalTopology & DatabaseConfig & LoggingConfig & GrpcConfig`), а `z.infer<typeof AuthEnvSchema>` возвращает `ZodObject<MergeShapes<...>>` — структурно эквивалентный, но не идентичный intersection-типу. Комментарий в `create-config-module.ts:14-19` это признаёт для factory-пути и там же решение — параметр-дженерик `TEnv`. Однако `main.ts` всё ещё использует голый `loadConfig<TSchema>` без такого параметра, и потому вынужден делать `as`.

Риск: если схема изменится (добавится новое поле в `AuthEnvSchema` через `composeSchemas(..., NewSchema)`), но `AuthEnv` забудут обновить, `as` молча скроет рассинхрон — `config.NEW_FIELD` будет типизирован как `never` / `unknown`, но выдаст runtime-значение. TypeScript не предупредит.

**Fix:** Варианты:

1. **Проще всего:** убрать приведение и тип alias, положиться на Zod inference: `const config = loadConfig(AuthEnvSchema);` (тип вычислится автоматически). Тогда потребуется `type AuthEnv = z.infer<typeof AuthEnvSchema>` в schema-файле вместо ручного intersection — 0 LOC и 0 drift.

2. **Если intersection-alias критичен для читабельности:** расширить `loadConfig` дополнительным параметром-дженериком, как уже сделано в `createConfigModule`:

```typescript
export function loadConfig<T extends z.ZodType, TEnv = z.infer<T>>(schema: T): TEnv {
  // ...
}
// Call site:
const config = loadConfig<typeof AuthEnvSchema, AuthEnv>(AuthEnvSchema);
```

Это уберёт `as`, сделав рассинхрон compile-time ошибкой. Рекомендация: вариант 1 (меньше кода, такой же type-safety).

### IN-01: Несогласованность стиля barrel-экспорта между сервисами

**File:** все 6 `apps/*/src/infrastructure/bootstrap/config/index.ts`
**Issue:** Четыре сервиса (notifier, parser, sender, gateway-частично) используют именованный реэкспорт:
```typescript
export { NotifierEnvSchema, type NotifierEnv } from './notifier-env.schema';
```

Два сервиса (audience, auth, gateway) используют звёздный:
```typescript
export * from './audience-config.constants';
```

(Фактическая разбивка: gateway/audience/auth — `export *`; notifier/parser/sender — именованный.)

Функционально эквивалентно, но затрудняет grep и code-review, а также может пропустить случайно добавленные экспорты в звёздных файлах.

**Fix:** Выбрать один стиль для всей фазы/продукта. Рекомендация — явный именованный реэкспорт (как в notifier/parser/sender), поскольку он пересечением с CLAUDE.md §Module Design («public API only»). Привести остальные три к этому же виду в следующей косметической фазе.

### IN-04: `console.error` в `main.ts` bootstrap-блоках — намеренное исключение, но без документации

**File:** все 6 `apps/*/src/main.ts` (последние 3-4 строки каждого)
**Issue:**
```typescript
bootstrap().catch((err) => {
  console.error(BOOTSTRAP.FAILED_MESSAGE, err);
  process.exit(1);
});
```

`console.error` — единственное допустимое место (логгер ещё не поднялся), но это не очевидно без комментария. В CLAUDE.md §Logging весь платформенный лог идёт через nestjs-pino, и ревьюер будущей фазы может поднять ложный флаг.

**Fix:** Добавить короткий комментарий, объясняющий намеренное исключение:

```typescript
// Pino logger not yet bootstrapped — fall back to console for the fatal boot path.
bootstrap().catch((err) => {
  console.error(BOOTSTRAP.FAILED_MESSAGE, err);
  process.exit(1);
});
```

Применить ко всем 6 `main.ts`.

### IN-05: `apps/*/drizzle.config.ts` — `SERVICE.audience.id` / `SERVICE.auth.id` и т.п. — магическая семантика ключа

**File:** `apps/audience/drizzle.config.ts:14`, `apps/auth/drizzle.config.ts:14`, `apps/parser/drizzle.config.ts:14`, `apps/sender/drizzle.config.ts:14`
**Issue:** `schemaFilter: [SERVICE.audience.id]` — корректно, но предполагает, что `SERVICE.<key>.id` совпадает с именем pgSchema (`audience` = pgSchema `audience`). Этот инвариант задан в `packages/config/src/catalog/services.ts`, но в drizzle-конфиге не проверяется — если кто-то переименует `SERVICE.audience.id` на `"audience_v2"` для routing-целей, pgSchema молча поедет вместе с ним (или наоборот отстанет).

Не баг фазы 999.1.8 — структура унаследована. Но стоит зафиксировать, что identity-из-catalog и pgSchema-name связаны жёстко. Альтернатива — отдельное поле `SERVICE.audience.pgSchemaName`, но это уже работа отдельной фазы, не этой. Просто фиксируем как tech-debt.

**Fix:** Документировать инвариант либо комментарием в `SERVICE` каталоге, либо создать отдельный отложенный item в `deferred-items.md` для будущей фазы — разделить `id` (transport-level identifier) и `pgSchemaName`.
