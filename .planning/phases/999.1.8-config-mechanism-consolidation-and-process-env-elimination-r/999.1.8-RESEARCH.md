## Summary

Phase 999.1.8 is a full-cycle phase that **closes a known audit gap in Phase 999.1** (findings F-15 + F-16 surfaced post-phase-close) AND **implements the fix in the same phase**, unlike the docs-only 999.1 shape. The gap narrative: the current config artefact split violates its own canonical (`infrastructure-client-layering` §Three-Layer Rule) because `loadConfig` lives in `packages/config/` (Identity) instead of `packages/foundation/` (Mechanism), and four `drizzle.config.ts` files read `process.env` directly instead of through `loadConfig`. Symmetrically, 6× apps hand-write `@Global() {Svc}ConfigModule.forRoot()` class boilerplate (~60 LOC × 6 = ~360 LOC) that a foundation-owned factory can collapse to ~15 LOC per service.

The gRPC client pattern at `packages/foundation/src/external/grpc/clients/define-grpc-client.ts` is the exact precedent — same problem (distribute DI wiring across N instances with per-instance identity), same solution shape (factory function in foundation that returns a composed DynamicModule, apps call it once per instance). Applying the same architectural move to config eliminates the entire `@Global() @Module({}) static forRoot()` class pattern across all 6 services while preserving the `@Global()` scope (required by 999.11.1 Plan 10 Rule 3 — nested `forRootAsync` DI visibility).

**Primary recommendation:** Apply the gRPC precedent verbatim to config. Single factory function `createConfigModule<TEnv>` in `packages/foundation/src/config/`, plus relocated `loadConfig<T>` preserving cache-by-schema-reference semantics. Drizzle CLI edge uses dual-import (foundation `loadConfig` + config `DatabaseSchema`) — no re-export through foundation, stays honest about the Identity/Mechanism boundary. Plan 03 collapses into Plan 01 (design and audit amendments share the same files).

### 1.2 `loadConfig<T>(schema)` — verbatim relocation

```typescript
// packages/foundation/src/config/load-config.ts
import { z } from 'zod';

const cache = new Map<z.ZodType, unknown>();

/**
 * Validates process.env against the provided Zod schema.
 * Results are cached by schema reference for idempotency.
 * Works because each service passes the same module-level const schema reference.
 *
 * @param schema - A ZodObject or ZodEffects (refined ZodObject) to validate against
 * @returns Parsed and validated config object
 */
export function loadConfig<T extends z.ZodType>(schema: T): z.infer<T> {
  const cached = cache.get(schema);
  if (cached) return cached as z.infer<T>;

  const result = schema.parse(process.env);
  cache.set(schema, result);
  return result as z.infer<T>;
}
```

**Reason verbatim preservation:** The cache-by-schema-reference semantics are load-bearing (D-08 in 999.11.1 uses it so `useValue: loadConfig(...)` in a provider factory is safe to call eagerly at module-definition time without double-parsing). Any wording change risks subtle behavioral drift. [VERIFIED: `packages/config/src/config-loader.ts` L1-20 — 20 LOC, cache-based]

**Foundation dependency check:** `packages/foundation/package.json` does NOT list `zod` explicitly. Plan 04 MUST add `zod: ^4.3.6` to `packages/foundation/package.json` `dependencies` (matching `packages/config/package.json` version). This is **NOT an infra-guard-scope change** (no ports, no docker-compose, no .env — pure package.json update). [VERIFIED: `packages/foundation/package.json` L21-34 — no zod]

### 1.3 `createConfigModule<TEnv>` — new factory

```typescript
// packages/foundation/src/config/create-config-module.ts
import { Global, Module, type DynamicModule, type Provider } from '@nestjs/common';
import type { z } from 'zod';
import { loadConfig } from './load-config';

/**
 * Options for createConfigModule — foundation-side factory that consolidates
 * the per-service {Svc}ConfigModule boilerplate into a declarative call.
 *
 * TEnv is the service's composed env shape — inferred from the Zod schema.
 */
export interface CreateConfigModuleOptions<TEnv> {
  /**
   * The composed Zod schema describing this service's env-var surface.
   * Typically produced via composeSchemas(TopologySchema, DatabaseSchema, ...).
   */
  readonly schema: z.ZodType<TEnv>;

  /**
   * Service-scoped Symbol identifying the full {Svc}_CONFIG DI token.
   * Declared once per service in apps/{svc}/src/infrastructure/bootstrap/config/{svc}-config.constants.ts.
   */
  readonly token: symbol;

  /**
   * Optional list of narrow-port slice projections. Each entry binds a
   * foundation-owned *_CONFIG_PORT Symbol to a slice of the parsed env object.
   *
   * The factory internally wires each entry as a Provider with
   * `inject: [token]` + `useFactory: (env: TEnv) => slice(env)`.
   *
   * Per-service variance is preserved: gateway has 5 grpcUrls, sender 1,
   * parser 1, audience 1, notifier 0 grpc ports but 2 storage ports, auth 0.
   */
  readonly narrowPorts?: ReadonlyArray<{
    readonly port: symbol;
    readonly slice: (env: TEnv) => unknown;
  }>;
}

/**
 * Factory function returning a @Global() DynamicModule that:
 *   1. Binds the {SVC}_CONFIG Symbol to loadConfig(schema) via useValue.
 *   2. Wires each narrow-port provider as a slice projection useFactory.
 *   3. Exports {SVC}_CONFIG + every narrow-port token.
 *
 * @Global() scope is applied internally (D-09) so narrow-port providers are
 * visible to nested forRootAsync({inject: [...]}) dynamic modules — preserves
 * 999.11.1 Plan 10 Rule 3 fix.
 *
 * Symmetric to packages/foundation/src/external/grpc/clients/define-grpc-client.ts
 * — both are foundation-level mechanism factories that apps call once per instance.
 */
@Global()
@Module({})
class ConfigModuleHolder {}

export function createConfigModule<TEnv>(
  opts: CreateConfigModuleOptions<TEnv>,
): DynamicModule {
  const configProvider: Provider = {
    provide: opts.token,
    useValue: loadConfig(opts.schema),
  };

  const narrowPortProviders: Provider[] = (opts.narrowPorts ?? []).map(
    ({ port, slice }) => ({
      provide: port,
      inject: [opts.token],
      useFactory: (env: TEnv) => slice(env),
    }),
  );

  const exportedTokens: symbol[] = [
    opts.token,
    ...(opts.narrowPorts ?? []).map((p) => p.port),
  ];

  return {
    module: ConfigModuleHolder,
    global: true,
    providers: [configProvider, ...narrowPortProviders],
    exports: exportedTokens,
  };
}
```

**Three critical implementation notes for Plan 04 executor:**

1. **`@Global()` mechanism.** NestJS DynamicModule supports `global: true` on the return object (equivalent to `@Global()` on the anchor class). Both mechanisms work per NestJS docs. Precedent in this repo: `ClsModule.forRoot({ global: true, ... })` used in `packages/foundation/src/external/logging/logging.module.ts` L28, L73. Recommendation: use `global: true` on the return object — more declarative and matches the factory-function shape (no class-level decorator that is technically dead since `ConfigModuleHolder` is an internal anchor). Alternative: apply `@Global()` to `ConfigModuleHolder` AND set `global: true` on return — harmless redundancy, fails closed. Plan 04 executor picks one consistently. [CITED: NestJS docs — `@Global()` and `global: true` are equivalent mechanisms for DynamicModule]

2. **Anchor class is required.** NestJS DynamicModule's `module` field MUST reference a class decorated with `@Module({})`. The anchor is a named no-op class — does NOT appear in any consumer's DI graph except as the module key. Using `class ConfigModuleHolder {}` with `@Module({})` is precedent: `packages/foundation/src/external/persistence/persistence.module.ts` L7-17 uses `class PersistenceModule { static forRootAsync(): DynamicModule { return { module: PersistenceModule, ... } } }` — same pattern, inverted direction. For factory-function shape, a bare `@Module({}) class ConfigModuleHolder {}` sits at file top.

3. **Generic type inference.** `z.ZodType<TEnv>` constrains `opts.schema` so that `useFactory: (env: TEnv) => slice(env)` type-checks. The `TEnv` parameter MUST propagate through the factory type signature so apps get type-safe `slice: (env: AudienceEnv) => ({...})` callbacks. Example usage:
   ```typescript
   export const AudienceConfigModule = createConfigModule<AudienceEnv>({ schema: AudienceEnvSchema, ... });
   ```
   `AudienceEnv` is inferred from `AudienceEnvSchema` at the call-site; Plan 06 decides whether to declare `<AudienceEnv>` explicitly (belt-and-suspenders) or let TS infer it from `schema: z.ZodType<AudienceEnv>`. Recommendation: explicit `<AudienceEnv>` — matches the 999.11.1 `useValue: loadConfig(AudienceEnvSchema) as AudienceEnv` explicitness ethic; improves IDE hover signal; zero runtime cost.

## § 2. gRPC Precedent Comparative Analysis

The config factory is NOT a novel architectural move — it is the application of an established foundation pattern (`defineGrpcClient` + `Promisified<T>` from Phase 999.7.x) to a different infra concern. Each capability maps 1:1.

### 2.1 Symmetric anatomy table

| Responsibility | gRPC precedent | Config target | Symmetry notes |
|---------------|---------------|--------------|----------------|
| **Factory function** | `defineGrpcClient<TRaw>(opts)` in `packages/foundation/src/external/grpc/clients/define-grpc-client.ts` | `createConfigModule<TEnv>(opts)` in `packages/foundation/src/external/config/create-config-module.ts` | Both: single function in foundation, generic over consumer shape, returns DI composition unit |
| **Input shape** | `DefineGrpcClientOpts = { service, clientToken }` | `CreateConfigModuleOptions<TEnv> = { schema, token, narrowPorts? }` | Both: identity refs (catalog/schema) + per-instance DI token + optional transport-specific knobs |
| **Output shape** | `GrpcClientBuildResult = { imports, providers, exports, grpcToken, healthToken }` | `DynamicModule` directly | gRPC returns a recipe (app wires into its own `@Module` via spread); config returns a fully-assembled DynamicModule (app imports directly). Rationale: config has ONE instance per app (stage-of-boot entry), gRPC has MANY (one per upstream service) — the gRPC pattern leaves assembly to apps because the `clientsModule.registerAsync` + `facadeProvider` + `healthProvider` trio lives inside the app's `imports[]`; config's factory can self-assemble because there's no per-app wiring variance |
| **Generic type parameter** | `<TRaw extends object>` — consumer's proto-generated client type | `<TEnv>` — consumer's composed env shape | Both: propagate through `useFactory` callbacks so consumer code is typed end-to-end |
| **Identity source** | `packages/config/src/catalog/services.ts` `SERVICE.{svc}` | `packages/config/src/schemas/*.ts` + `apps/{svc}/src/infrastructure/bootstrap/config/{svc}-env.schema.ts` (composed) | Both: pure-data identity in `packages/config/`; Mechanism layer consumes |
| **`@Global()` handling** | `ClientsModule.registerAsync([...])` — inherited from NestJS microservices; not globally scoped but child injection resolution works because the factoryProvider runs at root level | Factory sets `global: true` on return object | Config MUST be global because foundation's `LoggingModule.forGrpcAsync`, `PersistenceModule.forRootAsync` etc. use nested `forRootAsync({inject: [LOGGING_CONFIG_PORT]})` that cannot see non-global providers (999.11.1 Plan 10 Rule 3) |
| **Consumer side call** | `const auth = defineGrpcClient<AuthProto.AuthServiceClient>({ service: SERVICE.auth, clientToken: SERVICE.auth.diToken });` + spread `...auth.imports`, `...auth.providers` in app's gRPC client module | `export const AudienceConfigModule = createConfigModule<AudienceEnv>({ schema, token, narrowPorts });` + `imports: [AudienceConfigModule]` in app's root module | Both: one-line factory call at app's Assembly slice |

### 2.2 Identity / Mechanism / Assembly split realization

| Tier | gRPC realization | Config target realization |
|------|------------------|---------------------------|
| **Identity (`packages/config`)** | `SERVICE.auth = { id, diToken, grpc, envKeys }` — what the service IS | `AuthEnvSchema = composeSchemas(TopologySchema, DatabaseSchema, ...)` — what env SHAPE the service expects; plus `DatabaseSchema`, `LoggingSchema` etc. atomic schemas |
| **Mechanism (`packages/foundation`)** | `defineGrpcClient` factory + `Promisified<T>` Proxy + `GrpcClientConfig` narrow port + `GRPC_CLIENT_CONFIG_PORT` | `createConfigModule` factory + `loadConfig` loader + 6× narrow `*_CONFIG_PORT` tokens (pre-existing) |
| **Assembly (`apps/{svc}`)** | Per-upstream `{xxx}-client.module.ts` (~22 LOC) calling `defineGrpcClient<XxxProto.XxxServiceClient>(...)` + re-exporting named tokens | `{svc}-config.module.ts` (~15 LOC) calling `createConfigModule<{Svc}Env>(...)` with inline narrowPorts tuple |

The shape parity is exact. Every criticism that could be made about the config factory was already debated and resolved for gRPC in Phase 999.7.x.

### 2.3 Decoupling mechanism: per-call-site proof

**gRPC:** `Promisified<T>` is a Proxy over ts-proto-generated interface. Consumer injects `Promisified<AuthProto.AuthServiceClient>`; never touches `grpc-js` internals; adding a new RPC in the `.proto` becomes callable with zero wrapper code. [VERIFIED: `packages/foundation/src/external/grpc/clients/promisify-grpc-client.ts`]

**Config:** `createConfigModule` consumes `CreateConfigModuleOptions<TEnv>` interface. Consumer passes `schema`, `token`, `narrowPorts` — never touches NestJS `@Module`/`@Global()` decorators; never declares `static forRoot()`; never hand-writes the slice-projection `useFactory` boilerplate. Adding a new narrow port to a service becomes a one-line addition to the `narrowPorts` array.

**Both decouplers share the structural insight:** mechanical composition boilerplate that varies only in proper nouns (service name, env schema name, narrow port list) belongs in foundation once, not replicated 6× across services. The factory parameterises exactly the proper-noun slots and compresses the rest.

### 2.4 What DOESN'T transfer from gRPC

- **`Symbol.for` derivation.** gRPC derives `grpcToken = Symbol.for('${upperId}_CLIENT_GRPC')` because it needs cross-module canonical identity (multiple files refer to "the auth gRPC client"). Config `{SVC}_CONFIG` is app-local — one file declares `export const AUDIENCE_CONFIG = Symbol('AUDIENCE_CONFIG')`, that identity is passed into `createConfigModule` via the opts. No derivation needed. This is fine — `no-magic-values` skill §Pattern 2 accepts both `Symbol()` and `Symbol.for()`; app-local uniqueness doesn't need global registry.
- **Health indicator coupling.** gRPC factory emits a `healthProvider` because gRPC clients have liveness state (can lose channel). Config has no runtime state to monitor; factory does not produce a health provider.
- **Build-result recipe return.** gRPC returns `{imports, providers, exports, grpcToken, healthToken}` recipe because per-upstream modules compose those into their own `@Module`. Config factory returns a `DynamicModule` directly because assembly lives one level higher (the app root imports it verbatim). This is a capability divergence, not an architectural one — both respect Identity/Mechanism/Assembly.

| Axis | Option A (re-export) | Option B (dual-import) |
|------|---------------------|------------------------|
| Line count | 1 import line | 2 import lines |

| infrastructure-client-layering alignment | Partial — re-export is a compromise. ### 7.1 `@Global()` scope preservation in factory (999.11.1 Plan 10 Rule 3)

### 7.2 Runtime DI resolve order — config MUST load before consumers

### 7.3 Cache invalidation — same-schema-reference preserved

### 7.5 ZodType generic inference flow

**Risk:** `z.ZodType<TEnv>` constraint — if `opts.schema` is a `z.ZodObject<X>` (output of `composeSchemas`), TS must infer `TEnv` from `X`. Zod 4.x's `z.ZodType` is a super-wide type; naive signature `<TEnv>(opts: { schema: z.ZodType<TEnv> })` might infer `TEnv = unknown` by default.

**Detection:** `useFactory: (env: TEnv) => slice(env)` — if `TEnv = unknown`, `env.DATABASE_URL` fails to compile; Plan 04 `pnpm build` catches.

**Mitigation:** Two approaches — research recommends **explicit inference path via `z.infer<typeof schema>`**:

**Option 1 (cleaner API):** Constrain via `<TSchema extends z.ZodType>`:
```typescript
export function createConfigModule<TSchema extends z.ZodType>(
  opts: { schema: TSchema; token: symbol; narrowPorts?: ... }
): DynamicModule {
  type TEnv = z.infer<TSchema>;
  // ...
}
```
`TEnv` derived inside function body from `TSchema`. Consumer calls `createConfigModule({ schema: AudienceEnvSchema, ... })` — no explicit type arg needed.

**Option 2 (explicit user-side):** Keep `<TEnv>` and consumer explicit:
```typescript
createConfigModule<AudienceEnv>({ schema: AudienceEnvSchema, ... });
```

**Recommendation:** Option 1 (TSchema-based). Plan 04 executor picks; both work. Option 1 requires less consumer-side verbosity; Option 2 is belt-and-suspenders.

[VERIFIED: Zod 4 supports `z.infer<typeof T>` for any `ZodType` subclass; `composeSchemas` returns `z.ZodObject<MergeShapes<T>>` which is assignable to `z.ZodType<{ ... }>`]

### 7.8 Symbol token collision between {SVC}_CONFIG and factory-owned anchor

### Pattern 1: Factory Function Returns @Global DynamicModule

**What:** Foundation-level generic factory that composes DI providers for consumers; returns a pre-assembled DynamicModule with `global: true`.

**When to use:** When N instances of the same composition pattern exist across apps, differing only in identity refs + DI tokens + narrow port slices.

**Example:**

```typescript
// Source: Symmetric to packages/foundation/src/external/grpc/clients/define-grpc-client.ts
// Target: packages/foundation/src/external/config/create-config-module.ts
import { Global, Module, type DynamicModule, type Provider } from '@nestjs/common';
import type { z } from 'zod';
import { loadConfig } from './load-config';

@Global()
@Module({})
class ConfigModuleHolder {}

export function createConfigModule<TSchema extends z.ZodType>(opts: {
  readonly schema: TSchema;
  readonly token: symbol;
  readonly narrowPorts?: ReadonlyArray<{
    readonly port: symbol;
    readonly slice: (env: z.infer<TSchema>) => unknown;
  }>;
}): DynamicModule {
  const env = loadConfig(opts.schema);
  const configProvider: Provider = { provide: opts.token, useValue: env };
  const narrowProviders: Provider[] = (opts.narrowPorts ?? []).map(({ port, slice }) => ({
    provide: port,
    inject: [opts.token],
    useFactory: (c: z.infer<TSchema>) => slice(c),
  }));
  return {
    module: ConfigModuleHolder,
    global: true,
    providers: [configProvider, ...narrowProviders],
    exports: [opts.token, ...(opts.narrowPorts ?? []).map((p) => p.port)],
  };
}
```

### Pattern 2: Inline Narrow Port Slice Tuples (D-13)

**What:** App-side, narrow port projections live as inline tuples in `createConfigModule({ narrowPorts: [...] })` — not pre-declared shared helpers.

**When to use:** Per-service narrow-port composition where shape varies (gateway 5 grpcUrls, sender 1, auth 0, notifier 2 storage).

**Example:**

```typescript
// Source: app-side consumption pattern (targets apps/audience/src/infrastructure/bootstrap/config/audience-config.module.ts)
import { createConfigModule } from '@email-platform/foundation';
import {
  PERSISTENCE_CONFIG_PORT,
  LOGGING_CONFIG_PORT,
  GRPC_CLIENT_CONFIG_PORT,
  type LoggingConfig,
  type PersistenceConfig,
  type GrpcClientConfig,
} from '@email-platform/foundation';
import { AudienceEnvSchema, type AudienceEnv } from './audience-env.schema';
import { AUDIENCE_CONFIG } from './audience-config.constants';

export const AudienceConfigModule = createConfigModule({
  schema: AudienceEnvSchema,
  token: AUDIENCE_CONFIG,
  narrowPorts: [
    {
      port: PERSISTENCE_CONFIG_PORT,
      slice: (c: AudienceEnv): PersistenceConfig => ({ DATABASE_URL: c.DATABASE_URL }),
    },
    {
      port: LOGGING_CONFIG_PORT,
      slice: (c: AudienceEnv): LoggingConfig => ({
        LOG_LEVEL: c.LOG_LEVEL,
        LOG_FORMAT: c.LOG_FORMAT,
      }),
    },
    {
      port: GRPC_CLIENT_CONFIG_PORT,
      slice: (c: AudienceEnv): GrpcClientConfig => ({
        PROTO_DIR: c.PROTO_DIR,
        GRPC_DEADLINE_MS: c.GRPC_DEADLINE_MS,
        grpcUrls: { PARSER_GRPC_URL: c.PARSER_GRPC_URL },
      }),
    },
  ],
});
```

**Diff from current shape:** 63 LOC (current audience-config.module.ts + audience-config.provider.ts combined) → ~27 LOC. Eliminates `@Global() @Module({}) class { static forRoot() { return { module: ..., providers: [...], exports: [...] } } }` wrapping.

### Anti-Patterns to Avoid

- **Anti-pattern: class with `static forRoot()` per service.** Status quo; violates I-3.5 after Plan 01 lands. Factory function + constant export replaces.
- **Anti-pattern: foundation re-exports Identity artefacts (`DatabaseSchema`) for CLI convenience.** Violates Three-Layer Rule. Dual-import is strict and honest (§3 Option B).
- **Anti-pattern: Shared slice helpers `createPersistenceSlice(env)` in foundation** (D-14 deferred). Per-service variance makes pre-declared slices awkward; keep inline tuples until N≥3 identical duplicates emerge post-Plan 06.
- **Anti-pattern: `loadConfig` compat re-export from `packages/config/`.** D-05 explicit prohibition; creates dual-cache risk (§7.3). Clean break.
- **Anti-pattern: CLI-specific `loadConfigCli` wrapper.** `loadConfig` is framework-free; CLI usage is symmetric to runtime. No need for a variant.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Per-service config `@Module({})` class + `static forRoot()` pattern | Hand-written class boilerplate × 6 | `createConfigModule<TEnv>({...})` factory | Incapsulates `@Global()`, providers, exports, useFactory narrow-port wiring; ~60 LOC → ~15 LOC per service (§1.3 + Pattern 2) |
| CLI edge direct `process.env.X` parsing | `SubSchema.parse(process.env)` in drizzle.config.ts | `loadConfig(SubSchema)` imported from foundation | Single process.env read-site (I-0.1 new wording); CLI + runtime symmetric; loader cache semantics preserved |
| Ad-hoc narrow port provider `{ provide: X, inject: [Y], useFactory: (c) => ({...}) }` blocks | Repetitive Provider structs × 6 services × N narrow ports each | `narrowPorts: [{ port, slice }]` tuples inside factory call | Factory materialises the Provider struct; apps specify WHAT (port + slice), not HOW (Provider shape) |
| Dual loadConfig implementations (e.g., if refactor introduces wrapper) | Cache wrapper around foundation's loadConfig | Direct import from foundation everywhere | Single cache Map → one canonical parsed result per schema reference; wrapper risks dual-cache (§7.3) |
| DynamicModule composition with forgotten `@Global()` | Ad-hoc anchor class | Factory always sets `global: true` | Preserves 999.11.1 Plan 10 Rule 3; nested `forRootAsync({inject: [...]})` DI visibility always correct |

**Key insight:** Every problem above has a near-identical gRPC twin already solved in `packages/foundation/src/external/grpc/clients/`. The work is not invention — it is pattern transfer. `defineGrpcClient → createConfigModule` is the canonical mapping; everything else follows.

## Common Pitfalls

### Pitfall 1: Forgotten `@Global()` in factory return

**What goes wrong:** Factory returns `{ module, providers, exports }` without `global: true`. Boot fails with `UnknownDependenciesException: can't resolve Symbol(LOGGING_CONFIG_PORT)` when `LoggingModule.forGrpcAsync` runs nested `forRootAsync({inject: [LOGGING_CONFIG_PORT]})`.

**Why it happens:** NestJS DynamicModule default scope is module-local; `@Global()` or `global: true` must be explicit. Easy to miss in factory refactor.

**How to avoid:** Factory ALWAYS sets `global: true` (D-09 locked). Add grep invariant to Plan 07: `grep -c "global:\s*true" packages/foundation/src/external/config/create-config-module.ts` → 1.

**Warning signs:** App boots fine through DI resolution until first foundation module with nested forRootAsync. Static gates don't catch — only dual-mode runtime smoke.

### Pitfall 2: Dual cache Map

**What goes wrong:** Plan 04 executor creates a transition wrapper in `packages/config/src/config-loader.ts` that re-exports from foundation. Wrapper has its own `Map<ZodType, unknown>`. Two parse results for the same schema reference → DI tokens bound to different objects; `===` identity breaks.

**Why it happens:** Tempting to preserve backward compat with a one-line shim; user stance D-05 explicitly forbids.

**How to avoid:** `packages/config/src/config-loader.ts` DELETED, not wrapped. Grep guard: `grep -rn "config-loader" packages/config/ --include='*.ts'` → 0.

**Warning signs:** Mysterious singleton bugs in foundation modules that depend on config object identity.

### Pitfall 3: Drizzle-kit import resolution failure

**What goes wrong:** After Plan 05, `pnpm -C apps/audience db:generate` fails with `Cannot find module '@email-platform/foundation'` or ESM/CJS loader error.

**Why it happens:** Drizzle-kit uses `tsx`/`tsimp` internal loader; with `"module": "node16"`, foundation's package.json `exports` field must surface the root `.` path correctly. Current foundation package.json is already compatible (§3.4 verification), but a mistaken edit to `exports` during Plan 04 (e.g., adding a new subpath that changes main) could break.

**How to avoid:** Plan 04 DOES NOT modify `packages/foundation/package.json` `"exports"` field — only adds `zod` to `dependencies`. Plan 05 verification: `pnpm -C apps/audience exec drizzle-kit check`.

**Warning signs:** `pnpm build` green; `pnpm -C apps/* db:generate` fails with module resolution error.

### Pitfall 4: Plan 06 commit ordering mid-migration

**What goes wrong:** Plan 06 commit 1 (auth migrated) + commit 2 (audience pending). After commit 1, auth works but audience still uses `AudienceConfigModule.forRoot()`. If `AudienceConfigModule` in Plan 06 is replaced by a CONST export (no static forRoot), audience's root module `AudienceConfigModule.forRoot()` call fails → `pnpm build` red.

**Why it happens:** The factory-function shape breaks the `.forRoot()` call; migration of `{svc}-config.module.ts` and `{svc}.module.ts` MUST be in the same commit, per service.

**How to avoid:** Plan 06 task template per service (4 files atomic):
1. `{svc}-config.module.ts` — replace class with factory const.
2. `{svc}-config.provider.ts` — DELETE.
3. `index.ts` — remove provider re-export.
4. `{svc}.module.ts` — remove `.forRoot()` call.

Single commit per service; all 4 files in one commit. `pnpm lint && pnpm build` green between every commit.

**Warning signs:** `pnpm build` red between Plan 06 per-service commits.

### Pitfall 5: Losing `@Global()` knowledge in executor context

**What goes wrong:** Plan 04 or Plan 06 executor, scanning current code, sees `@Global()` on `AudienceConfigModule` class and tries to preserve the decorator by applying it to the anchor class. Factory already applies `global: true` on return. No observable bug (both mechanisms work) but adds confusion.

**How to avoid:** Research §1.3 documents the pattern; Plan 04 task description explicitly says "use `global: true` on return; anchor class bare @Module({})".

**Warning signs:** Reviewer asks "why two mechanisms?" during code review.
