# Phase 999.1.8 Plan 05: App-Side createConfigModule Factory Migration — Summary

**One-liner:** Миграция 6 сервисов с hand-rolled `@Global() class {Svc}ConfigModule { static forRoot(): DynamicModule }` на foundation-owned `createConfigModule<typeof Schema, AliasEnv>({ schema, token, narrowPorts })` — 7 атомарных коммитов (1 foundation-fix + 6 per-service refactor), net -187 LOC, 100% паритет narrow-port slice-проекций с BEFORE state.

## Accomplishments

### I-3.5 full closure — foundation owns DI factory; apps consume it

**6 per-service migrations** — each service's `bootstrap/config/{svc}-config.module.ts` now exports a `const {Svc}ConfigModule` returned by `createConfigModule<typeof {Svc}EnvSchema, {Svc}Env>({ schema, token, narrowPorts })`. The factory internally decorates an anchor class with `@Global()` AND returns `global: true` — the 999.11.1 Plan 10 Rule 3 fix (nested `forRootAsync({inject: [*_CONFIG_PORT]})` visibility) is preserved without any app-side code.

### F-16 full closure — Mechanism layer responsibility

Before this plan, every service had its own `@Global() @Module({}) class {Svc}ConfigModule { static forRoot(): DynamicModule { ... } }` with a matching `{svc}ConfigProvider` const and a `.forRoot()` call at the root module. After this plan, the Mechanism (factory + narrow-port provider assembly + @Global scope + DI exports) lives exclusively in `@email-platform/foundation`; services only declare their narrow-port inventory (variance) + token (identity) + schema (reference).

### Provider absorption (D-12)

6× `{svc}-config.provider.ts` deleted. The `useValue: loadConfig(Schema)` pattern is now encapsulated inside the factory's `configProvider` — apps no longer expose a top-level provider const.

### Root module import form (D-11)

6× root `{svc}.module.ts` changed from `{Svc}ConfigModule.forRoot()` to `{Svc}ConfigModule`. This is a D-11-documented breaking change: the module is now a DynamicModule const, not a class with a static method.

### Foundation factory signature widening (Rule 3 blocking-fix)

The Plan 03-shipped signature `createConfigModule<TEnv>(opts: { schema: z.ZodType<TEnv>, ... })` proved incompatible with `composeSchemas(...)`-produced `ZodObject<MergeShapes<...>>` schemas at the call-site: Zod 4's `z.ZodType<TEnv>` output-only generic is too narrow for the composed ZodObject shape to assign into without a cast. The foundation factory signature was widened to `createConfigModule<TSchema extends z.ZodType, TEnv = z.infer<TSchema>>` — mirroring the canonical `loadConfig<T extends z.ZodType>(schema: T): z.infer<T>` shape. RESEARCH §7.5 Option 1 pre-approved this mitigation. Zero runtime change, zero public-API regression (Plan 03 was the factory's first & only publication wave — no prior consumers).

## Decisions Made

- **Rule 3 scope expansion — foundation factory signature widened.** RESEARCH §7.5 Option 1 pre-recommended this mitigation; Plan 03 shipped the narrower signature; Plan 05 discovered the incompatibility at first call-site (audience Task 1 pre-commit build failure). Applied as a dedicated `fix(999.1.8-05)` commit BEFORE the 6 refactor commits to maintain single-concern commit granularity and preserve the "no intermediate broken-build state" invariant.
- **Two-generic explicit factory form** — all 6 services invoke `createConfigModule<typeof {Svc}EnvSchema, {Svc}Env>` rather than relying on the single-generic default (`TEnv = z.infer<TSchema>`). Rationale: `{Svc}Env` is declared as a manual intersection alias in each `*-env.schema.ts` (e.g., `AudienceEnv = GlobalTopology & DatabaseConfig & RabbitConfig & LoggingConfig & GrpcConfig`) — structurally equivalent to `z.infer<typeof {Svc}EnvSchema>` but nominally divergent. The explicit second generic carries the alias through slice callbacks, matching the 999.11.1 explicitness ethic.
- **Per-service atomic commits (D-21 precedent)** — 6 independent refactor commits rather than 1 mega-commit. Each is bisectable; each passes static gate independently; cross-app imports are ESLint-forbidden so no mid-migration incoherence risk.
- **Bit-identical narrow-port slice preservation** — for every service, the new factory call's `narrowPorts: [...]` entries project the same fields with the same types as the BEFORE state's `useFactory: (c): ...` providers. Validated by pre-reading each BEFORE module file. Scope reduction is prohibited per plan.
- **Scope-boundary respected** — pre-existing `.planning/config.json` and `packages/foundation/src/external/grpc/clients/promisify-grpc-client.ts` drifts (documented in Plan 03 SUMMARY) NOT staged. Notifier event.consumer.ts lint warnings (2, from 999.1.8-04 SUMMARY) remain out of scope.

## Deviations from Plan

### Rule 3 (Blocking) — Foundation factory signature widening

**1. [Rule 3 - Blocking] TSchema extends z.ZodType generic form applied to foundation factory**

- **Found during:** Task 1 Step 5 (audience pre-commit `pnpm build`)
- **Issue:** `createConfigModule<AudienceEnv>({ schema: AudienceEnvSchema, ... })` failed with TS2322: `ZodObject<MergeShapes<...>>` is not assignable to `z.ZodType<AudienceEnv>`. Zod 4's `z.ZodType<TEnv>` output-only generic is too narrow to accept the composed ZodObject without a cast.
- **Pre-approved mitigation:** RESEARCH §7.5 Option 1 recommended — change the factory signature to `<TSchema extends z.ZodType, TEnv = z.infer<TSchema>>` mirroring `loadConfig<T extends z.ZodType>`.
- **Fix:** Modified `packages/foundation/src/external/config/create-config-module.ts`:
  - `CreateConfigModuleOptions<TEnv>` → `CreateConfigModuleOptions<TSchema extends z.ZodType, TEnv = z.infer<TSchema>>`
  - `schema: z.ZodType<TEnv>` → `schema: TSchema`
  - `createConfigModule<TEnv>` → `createConfigModule<TSchema extends z.ZodType, TEnv = z.infer<TSchema>>`
  - Zero runtime change (factory body unchanged). Public API wider but source-compatible with any hypothetical narrower Plan 03 consumer (none exist — Plan 05 is first consumer wave).
- **Commit:** `e2e301b` (`fix(999.1.8-05): widen createConfigModule factory signature to accept composed ZodObject schemas`)
- **Scope boundary:** Foundation-only. Did NOT modify Plan 03's intent (factory exists, returns `global: true` DynamicModule, encapsulates `loadConfig` + narrow-port providers). Did modify one line of the type signature, per pre-approved RESEARCH mitigation path.
