## Rollout стратегия

### Q1: Как секвенсировать refactor по 4 сервисам?

| Option | Description | Selected |
|--------|-------------|----------|
| Per-service sweep (Recommended) | auth → sender → parser → audience. Mirror 999.10 proven pattern. Atomic commit per service, minimal transient state, лёгкий revert по сервису. | ✓ |
| Per-layer sweep | Все Controllers → все Services → все UseCases → все Repositories. Cross-service consistency на слой, но transient inconsistency между сервисами. | |
| One atomic mega-commit | Все ~45 файлов одним commit'ом. Самый атомарный, но огромный diff и сложный revert. | |

**User's choice:** Per-service sweep
**Notes:** Mirror 999.10 structure.

### Q2: С какого сервиса начать pilot?

| Option | Description | Selected |
|--------|-------------|----------|
| auth (Recommended) | 6 RPC methods, mirror 999.10 (auth был pilot там). Меньший scope подтверждает pattern, дальше mechanical. | ✓ |
| audience | Самый яркий triple-suffix redundancy (8 inbound ports). Collision `listGroups()` / `listGroupsPort`. | |
| sender (самый крупный) | 10 RPC methods. Если pattern работает на крупнейшем — остальные тривиальны. | |

**User's choice:** auth
**Notes:** Mirror 999.10 pilot strategy.

### Q3: Как верифицировать после каждого service sweep?

| Option | Description | Selected |
|--------|-------------|----------|

## Edge cases + DI pattern

### Q9: Inbound port field нейминг — `{verb}{noun}Service` всегда, или `Service` только при collision?

| Option | Description | Selected |
|--------|-------------|----------|
| `Service` всегда (Recommended) | Universal mechanical rule. `this.loginService.execute()`, `this.listGroupsService.execute()`. Предсказуемо, 4 controller'а однообразны. | ✓ |
| `Service` только при collision | Drop suffix когда collision нет. Но в практике ~все proto method names = port names, collision есть везде. | |

**User's choice:** `Service` всегда
**Notes:** User попросил конкретные примеры перед ответом. Показан real case из `audience.controller.ts` (collision есть) vs `auth.controller.ts` (collision тоже есть — `login()` метод vs `login` поле). В обоих `Service` suffix нужен. User подтвердил universal rule.

### Q10: DI inject pattern — сохраняем текущий mixed?

| Option | Description | Selected |
|--------|-------------|----------|
| Mixed (Recommended) | Inbound ports → Symbol. Outbound ports → Symbol. UseCases → class reference. Consistent с 999.10. | ✓ |
| Symbol везде | UseCases тоже через Symbol. Вдвое больше boilerplate. | |
| Class reference везде | Ломает abstraction boundary на inbound. | |

**User's choice:** Mixed сохраняем
**Notes:** User попросил примеры. Показано: Symbol-всюду дублирует constants.ts и providers без выгоды; class-ref-всюду ломает dependency inversion. Confirm Mixed.

### Q11: Mixed-suffix audit — audit в auth pilot или только Repository + правило?

| Option | Description | Selected |
|--------|-------------|----------|
| Только Repository + общее правило (Recommended) | Audit выполнен inline в discuss-phase: 4 gRPC сервиса имеют только `*Repository*` outbound. NAMING.md документирует общее правило + отмечает `NotificationSenderPort` из notifier как future candidate. | ✓ |
| Формальный audit в auth pilot | Plan 2 начинается с grep по всем 4 сервисам. Findings зафиксированы в Plan'е. | |

**User's choice:** Только Repository + общее правило
**Notes:** Inline audit findings: auth → `UserRepositoryPort`; sender → `CampaignRepositoryPort`; parser → `ParserTaskRepositoryPort`; audience → `GroupRepositoryPort`, `RecipientRepositoryPort`. Notifier (out of scope) имеет `NotificationSenderPort` — domain-role candidate для future.
