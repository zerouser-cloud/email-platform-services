<decisions>
## Implementation Decisions

### Locked Naming Rules (from 2026-04-19 dialogue, pre-discussion)

- **D-01:** **Field name = runtime identity.** Controller-to-Service field → `{port}Service` (например `listGroupsService`). Service-to-UseCase field → action verb (например `verifyCredentials`). UseCase-to-Repository field → `{entity}Repository` (например `userRepository`). Field никогда не содержит `Port` suffix. `Port` — архитектурный концепт (interface boundary), не имя переменной. Source: D-LOCKED-NAMING-01 в `999.10.1-NOTES.md`.

- **D-02:** **Type = architectural contract.** Type в поле сохраняет `Port` suffix там где абстракция проходит: `listGroupsService: ListGroupsPort`, `userRepository: UserRepositoryPort`. `Port` виден при hover/grep — architectural signal там где он имеет значение. Source: D-LOCKED-NAMING-02.

- **D-03:** **Token = architectural concern.** DI tokens в `{svc}.constants.ts` сохраняют `_PORT` suffix: `LIST_GROUPS_PORT`, `USER_REPOSITORY_PORT`. Grep `_PORT` → полный список ports сервиса. Токены — architectural artifacts, читаются только в `@Inject(...)` и `provide:`, verbose имя там OK. Source: D-LOCKED-NAMING-03.

- **D-04:** **Domain-role vs architectural-role suffixes.** Domain-role suffixes (`Repository`, `Factory`, `Policy`, `Sender` — когда это ubiquitous language) — **mirrorятся на поле** (`userRepository: UserRepositoryPort`). Architectural-role suffixes (`Port`, `Adapter`, `UseCase`, `Boundary`) — **НЕ mirrorятся на поле**. Source: D-LOCKED-NAMING-04.

- **D-05:** **Canonical layer-by-layer matrix.**

  | Слой | Field name | Type | DI token | Runtime class |
  |------|-----------|------|----------|---------------|
  | Controller injects inbound port | `listGroupsService` | `ListGroupsPort` | `LIST_GROUPS_PORT` | `ListGroupsService` |
  | Service injects use case | `verifyCredentials` | `VerifyCredentialsUseCase` | — (class ref) | `VerifyCredentialsUseCase` |
  | UseCase injects outbound port | `userRepository` | `UserRepositoryPort` | `USER_REPOSITORY_PORT` | `PgUserRepository` |

  Единый pattern во всех 4 gRPC сервисах. Source: D-LOCKED-NAMING-05.

- **D-06:** **Outbound port interfaces не переименовываем.** Сохраняем `UserRepositoryPort`, `CampaignRepositoryPort`, `ParserTaskRepositoryPort`, `GroupRepositoryPort`, `RecipientRepositoryPort`. Vernon-style rename (без `Port` suffix) — отдельная future фаза 999.10.2 если решим. Source: D-LOCKED-NAMING-06.

- **D-07:** **Controller = inbound adapter; Service = inbound port implementation.** Два разных класса на inbound стороне. Controller (`AudienceController`) — protocol translator (gRPC ↔ Command DTO), **не реализует** inbound port. Service (`ListGroupsService implements ListGroupsPort`) — application service. Не путать с outbound стороной где adapter и port implementation совпадают (`PgUserRepository implements UserRepositoryPort`). Source: D-LOCKED-NAMING-07.

### Rollout Strategy (discussed 2026-04-19)

- **D-08:** **Per-service sweep, mirror 999.10 structure.** Последовательность plan'ов:
  - **Plan 1 (pilot):** auth — полный refactoring controller'а + outbound compliance audit.
  - **Plans 2-4 (sweep):** sender → parser → audience — mechanical replication с auth pilot'а.
  - **Plan 5 (docs):** финальный atomic commit обновляющий все 6 docs файлов.

  Per-layer sweep (все Controllers cross-service → все Services → ...) отвергнут — transient inconsistency между сервисами. One atomic mega-commit отвергнут — огромный diff, сложный revert. Source: обсуждение 2026-04-19 Область 1.

- **D-09:** **auth — pilot сервис.** Mirror 999.10 (auth был pilot там же). 6 RPC methods, знакомый refactoring scope. Audience рассмотрен (самая яркая triple-suffix redundancy с 8 портами и реальным collision `listGroups()`) — но auth как pilot даёт ту же mechanical validation на меньшем scope. Источник: обсуждение 2026-04-19 Область 1.

- **D-10:** **Verification gate после каждого per-service plan'а.** Последовательность: `pnpm lint` (чистый) → `pnpm build` (чистый) → полный `runtime-smoke-verification` skill (native + isolated, curl `/health/ready` → 200, 5/5 upstreams up). Mirror 999.10 gate pattern. Static-only gate (без smoke) отвергнут — даже rename-only refactor в теории может сломать DI resolution. Source: обсуждение 2026-04-19 Область 1.

### Outbound Scope (discussed 2026-04-19)

- **D-11:** **Outbound port interfaces не трогаем в этой фазе** (конкретизация D-06). Phase 999.10.1 — controller-centric refactor. Vernon-style outbound rename (`UserRepositoryPort` → `UserRepository`) deferred. Source: обсуждение 2026-04-19 Область 2.

- **D-12:** **Outbound compliance audit внутри каждого service plan'а.** В конце каждого per-service plan'а (после controller sweep): grep use-case constructor'ов, подтверждение что field = `userRepository` (domain-role mirrored), не `userRepositoryPort`. Ожидаемый результат — no-op (post-999.10 уже правильно), но проверяем системно. Пред-audit и skip-assumption отвергнуты — audit тривиален и ловит drift. Source: обсуждение 2026-04-19 Область 2.

### Edge Cases + DI Pattern (discussed 2026-04-19)

- **D-16:** **Universal `{verb}{noun}Service` rule для inbound port fields.** Все inbound port fields во всех controller'ах имеют suffix `Service`, даже когда method/field collision отсутствует. Причина: в практике ~все proto method names = port names (login/login, listGroups/listGroups, createCampaign/createCampaign), collision есть везде. Universal rule = 4 однообразных controller'а, предсказуемо, нет case-by-case thinking. Source: обсуждение 2026-04-19 Область 4.

- **D-17:** **Mixed DI inject pattern сохраняем.** Inbound ports → `@Inject(XXX_PORT) private readonly xxxService: XxxPort`. Outbound ports → `@Inject(XXX_REPOSITORY_PORT) private readonly xxxRepository: XxxRepositoryPort`. UseCases → `private readonly verbNoun: VerbNounUseCase` (class reference, без Symbol). Принцип: Symbol только на abstraction boundaries (inbound + outbound ports), class reference внутри application composition (Service→UseCase). Symbol-everywhere отвергнут (вдвое больше boilerplate ради симметрии), class-ref-everywhere отвергнут (ломает dependency inversion). Source: обсуждение 2026-04-19 Область 4.

- **D-18:** **Mixed-suffix audit — Repository-only правило.** Audit inline в discuss-phase показал: во всех 4 gRPC сервисах outbound ports — только `*Repository*` (UserRepositoryPort, CampaignRepositoryPort, ParserTaskRepositoryPort, GroupRepositoryPort, RecipientRepositoryPort). Единственный mixed-suffix case — Repository. NAMING.md документирует общее правило (domain-role mirror D-04) + отмечает `NotificationSenderPort` из notifier как future candidate для domain-role mirror (`notificationSender: NotificationSenderPort`). Формальный pre-flight audit в auth pilot — не нужен, findings уже зафиксированы. Source: обсуждение 2026-04-19 Область 4.

<specifics>
## Specific Ideas

- **Controller collision как motivating example в NAMING.md:** `AudienceController.listGroups()` method + `listGroupsService` field — видно что method name приходит из proto (внешний контракт), field name отражает runtime identity (внутренняя композиция). Это идеальный showcase того почему Port suffix в field name = noise.

- **Clean Code ch.2 reference явно в NAMING.md:** Uncle Bob's "Hungarian Notation and other forms of type encoding are simply impediments today" — zapret type encoding в variable names. Это authoritative anchor для anti-pattern note в DO-DONT.md.

- **Mirror 999.10 structure плотно в Plan'ах:** тот же порядок (pilot → sweep → docs), та же atomic commit granularity, тот же verification gate. Единообразие workflow + downstream reader'у знакомый shape.

- **Field rename ≠ DI resolution change:** ключевой insight — переименование field в controller'е не трогает provider bindings. DI по Symbol token'у, field — лишь синтаксис доступа. Это упрощает refactor и снижает risk.

</specifics>
