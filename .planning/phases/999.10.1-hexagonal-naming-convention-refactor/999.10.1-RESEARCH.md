## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-01** Field name = runtime identity. Controller→Service field = `{port}Service`. Service→UseCase field = action verb. UseCase→Repository field = `{entity}Repository`. Field никогда не содержит `Port` suffix.
- **D-02** Type = architectural contract. `listGroupsService: ListGroupsPort`, `userRepository: UserRepositoryPort`.
- **D-03** Token = architectural concern. DI tokens сохраняют `_PORT` suffix (`LIST_GROUPS_PORT`, `USER_REPOSITORY_PORT`).
- **D-04** Domain-role (`Repository`, `Factory`, `Policy`, `Sender`) mirrorится на поле. Architectural-role (`Port`, `Adapter`, `UseCase`, `Boundary`) — нет.
- **D-05** Canonical layer-by-layer matrix (Controller→Service→UseCase→Repository).
- **D-06** Outbound port interfaces (`UserRepositoryPort` etc.) — НЕ переименовываем.
- **D-07** Controller = inbound adapter; Service = inbound port implementation (два разных класса).
- **D-08** Per-service sweep. Plan 1 pilot (auth) → Plans 2-4 sweep (sender/parser/audience) → Plan 5 docs.
- **D-09** auth — pilot сервис.
- **D-10** Verification gate после каждого per-service plan: `pnpm lint` + `pnpm build` + `runtime-smoke-verification` (native + isolated, `/health/ready` 200, 5/5 upstreams up).
- **D-11** Outbound port interfaces не трогаем в этой фазе.
- **D-12** Outbound compliance audit внутри каждого service plan'а (grep use-case constructor'ов).
- **D-13** Финальный docs Plan (Plan 5) — один atomic commit для всех docs.
- **D-14** Docs scope — 6 файлов (CLAUDE.md, ARCHITECTURE.md, NAMING.md, EXAMPLES.md, DO-DONT.md, SKILL.md).
- **D-15** ESLint naming enforcement — не enforce.
- **D-16** Universal `{verb}{noun}Service` rule для всех inbound port fields (даже без collision).
- **D-17** Mixed DI inject pattern сохраняем: Inbound — Symbol; UseCase — class ref; Outbound — Symbol.
- **D-18** Mixed-suffix audit — Repository-only правило (в 4 gRPC сервисах outbound ports — только `*Repository*`). `NotificationSenderPort` из notifier отмечен как future candidate.

## Summary

Phase 999.10.1 — механический rename-refactor без изменений runtime поведения. 7 locked naming rules + 11 rollout/docs decisions зафиксированы в CONTEXT.md и NOTES.md на основе исследования Cockburn/Vernon/Hombergs/Uncle Bob/Seemann + 5 enterprise codebases.

**Три основных фронта работы (подтверждено Grep/Read в репо):**

1. **Controllers (31 field renames across 4 files)** — pure mechanical sed-style refactor: `xxxPort` → `xxxService` в field declarations + all internal use sites `this.xxxPort.execute` → `this.xxxService.execute`. DI tokens, providers, types не меняются.
2. **Use-cases (Repository-field audit — NOT no-op)** — текущие поля в `*.use-case.ts` **не соответствуют** D-05 (`userRepository: UserRepositoryPort`). Фактически используются collection names (`users`, `campaigns`, `tasks`, `_recipients`, `_groups`). Audience дополнительно имеет underscore-prefix pattern (`_recipients`, `_groups`). Каждый service Plan должен выполнить audit + rename.
3. **Services (UseCase-field audit — NOT no-op except auth)** — в auth services поля уже соответствуют D-05 (`verifyCredentials`, `issueTokenPair`, etc.). В sender/parser/audience services используется generic `useCase: XxxUseCase`. По D-05 нужен action-verb pattern. Исключения: auth (compliant), sender composed services (`transition` OK для TransitionCampaignStatusUseCase per worked example в 999.10), audience composed services (`transition` OK).

**Primary recommendation:** Plan 1 pilot (auth controller + use-case audit) — controller имеет 6 renames + 6 use-cases с `users` (non-compliant) field. Audit auth services — **no-op**. Затем Plans 2-4 mirror structure для sender/parser/audience с reflection на non-trivial use-case + service audit work. Finally Plan 5 docs atomic commit.
