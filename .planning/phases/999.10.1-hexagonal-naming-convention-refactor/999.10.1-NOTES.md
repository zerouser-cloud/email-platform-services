## Why This Phase Exists

После архитектурного пилота 999.10 (Controller → Service → UseCase 3-layer stack across 4 gRPC services) пользователь обратил внимание на вопрос нейминга при review `audience.controller.ts`:

> «У нас есть порт — это интерфейс, в его названии мы оставляем Port, при использовании Port убираем, а когда в DI мы прокидываем саму реализацию, она будет иметь префикс Adapter?»

И затем ключевой пункт:

> «FА что само по себе есть сейчас `await this.listGroups`? Это useCase? По идее это сервис, то есть в контроллере у нас сервис, в сервисах useCase? Мне не нравится префикс Port как часть кода, Port это интерфейс»

Текущий код в Phase 999.10 даёт pattern:

```ts
@Inject(LIST_GROUPS_PORT) private readonly listGroupsPort: ListGroupsPort,
```

Проблема: **triple-suffix redundancy** — `_PORT` + `Port` + `Port`. В одной строке слово "Port" повторяется трижды. Uncle Bob в Clean Code ch.2 "Meaningful Names" прямо говорит что такое кодирование типа в имя переменной = anti-pattern:

> "Hungarian Notation and other forms of type encoding are simply impediments today... People quickly learn to ignore the prefix (or suffix)."

Research (2 агента на web search через Cockburn, Vernon, Hombergs, Uncle Bob, Mark Seemann + real enterprise codebases: buckpal, IDDD_Samples, domain-driven-hexagon, ddd-forum, bitloops) выявил чистое решение.

## Dialogue Snapshot (2026-04-19)

### Round 1 — field name в Controller

**Пользователь:** правильно ли называть поле `listGroupsPort` или просто `listGroups`? Стоит ли у Symbol токенов суффикс `_PORT`?

**Research провёл web search** по 5 primary architecture sources + 10 enterprise codebases. TL;DR:
- Alistair Cockburn (Hexagonal author): порты назывются `For<Doing><Something>` (`ForObtainingRates`), без отдельного `Port` suffix
- Juan Garrido-Paz (Cockburn disciple): `private final ForObtainingRates forObtainingRates` — field = camelCase(type), без redundancy
- Vaughn Vernon (IDDD): `@Autowired private UserRepository userRepository` — но `Repository` это **domain-role suffix** (mirroring OK)
- Tom Hombergs (buckpal): **triple-suffix mirroring** (`loadAccountPort: LoadAccountPort`) — для grep/rename consistency в больших Java командах
- Mark Seemann (DI book): `reservationsRepository: IReservationsRepository` — field ≈ camelCase(type) без prefix/suffix noise
- Uncle Bob: type encoding в variable names = anti-pattern (Clean Code ch.2)

**Ключевое разграничение** (из research):

1. **Domain-role suffix** (`Repository`, `Service`, `Factory`) — **mirrorится на поле**. Это ubiquitous language. Vernon + Spring Data + .NET норма.
2. **Architectural-role suffix** (`Port`, `Adapter`, `UseCase`, `InboundPort`) — **НЕ mirrorится на поле** у Cockburn-native dialect. Нести architectural signal в narrative call-site — это Hexagonal jargon leak.

**Вывод round 1:**
- Option A (triple suffix): defensible но Hungarian
- **Option B (drop field suffix):** `LIST_GROUPS_PORT` token + `listGroups` field + `ListGroupsPort` type — dominant pattern per Garrido-Paz, Seemann
- Option C (drop all): рискует collision с domain types
- Option D (UseCase instead of Port): Hombergs dialect, но ломает уже принятые 999.10 conventions

### Round 2 — Adapter наименование

**Пользователь:** «Хорошо как это матчится с адаптером? То есть у нас есть порт — это интерфейс, в его названии мы оставляем Port, при использовании Port убираем, а когда в DI мы прокидываем саму реализацию, она будет иметь префикс Adapter?»

**Research второй round** — что говорят authors и codebases про наименование implementation'ов port'ов.

**Ключевая архитектурная поправка:** НЕ всё что implements port = Adapter. Есть асимметрия inbound ↔ outbound:

| Сторона | "Adapter" = | "Port implementation" = | Один класс? |
|---------|------------|-------------------------|-------------|
| **Inbound** (driving) | `AuthController` (вызывает port) | `LoginService` (implements port) | **Два разных класса** |
| **Outbound** (driven) | `PgUserRepository` (implements port) | `PgUserRepository` (сам же) | **Один и тот же класс** |

На inbound стороне implementation port'а — это **Application Service** (композиционный слой), а Controller — это Adapter (протокольный транслятор). На outbound стороне adapter и implementation совпадают.

**Enterprise codebases split:**

| Codebase | Inbound impl | Outbound impl |
|---|---|---|
| thombergs/buckpal | `SendMoneyService` | `AccountPersistenceAdapter` (H-style) |
| Vernon IDDD_Samples | `AccessApplicationService` | `HibernateUserRepository` (V-style) |
| Sairyss/domain-driven-hexagon (NestJS) | `CreateUserService` | `UserRepository` (V-style) |
| stemmlerjs/ddd-forum (TS) | `CreateUserUseCase` | `SequelizeUserRepo` (V-style) |
| bitloops/ddd-hexagonal-cqrs (TS) | `CreateTodoHandler` (CQRS) | `MongoTodoRepository` (V-style) |

В NestJS/TypeScript **Vernon dialect (technology prefix, без `Adapter` suffix) доминирует 4:1**. Текущий код email-platform правильный: `PgUserRepository implements UserRepositoryPort`.

### Round 3 — финализация field naming

**Пользователь:** «FА что само по себе есть сейчас `await this.listGroups`? Это useCase? По идее это сервис, то есть в контроллере у нас сервис, в сервисах useCase? Мне не нравится префикс Port как часть кода, Port это интерфейс»

**Это ключевое insight пользователя.** Он увидел что:
- В runtime в `this.listGroups` лежит **ListGroupsService** (что bind'ит DI)
- `Port` — architectural concept, не имя зависимости
- Field name должен отражать **runtime identity**

**Окончательная формула:**

- **Field name = runtime identity** (Service / UseCase / Repository — что DI actually injects)
- **Type = architectural contract** (Port interface — через что abstraction проходит)
- **Token = architectural concern** (хранится в `{svc}.constants.ts`, суффикс `_PORT`)
- **`Port` в field name никогда не появляется**

**Плюс решает collision:** `AudienceController` имеет метод `listGroups()` (implements proto) и поле для inbound port. Если поле назвать `listGroups` — collision. Если `listGroupsService` — collision решена + field reflects runtime.

## Locked Decisions (от пользователя в диалоге 2026-04-19)

Эти решения **уже приняты** и не требуют re-litigation в discuss-phase. Они должны попасть в CONTEXT.md как D-XX.

### D-LOCKED-NAMING-01: Field name = runtime identity

Field name отражает что DI bind'ит в runtime:
- Controller → Service (`listGroupsService`)
- Service → UseCase (`verifyCredentials`)
- UseCase → Repository adapter (`userRepository`)

**Никогда** field не содержит `Port` suffix. `Port` — это архитектурный концепт (interface/boundary), не имя переменной.

### D-LOCKED-NAMING-02: Type = architectural contract

Type сохраняет `Port` suffix там где он инжектится как абстракция:

```ts
// Controller → Service (через Port)
private readonly listGroupsService: ListGroupsPort

// UseCase → Repository (через Port)
private readonly userRepository: UserRepositoryPort
```

Type виден при hover/grep — architectural signal там где он имеет значение. Field — в narrative call-site — где signal становится noise.

### D-LOCKED-NAMING-03: Token = architectural concern, keeps `_PORT`

DI tokens в `{svc}.constants.ts` сохраняют `_PORT` suffix:

```ts
export const LIST_GROUPS_PORT = Symbol('ListGroupsPort');
export const USER_REPOSITORY_PORT = Symbol('UserRepositoryPort');
```

Токены — architectural artifacts. Grep `_PORT` → полный список ports сервиса за один запрос. Токен читается только в `@Inject(...)` и `provide:` — verbose token там OK.

### D-LOCKED-NAMING-04: Domain-role vs architectural-role suffixes

Разграничение:

- **Domain-role suffixes** (`Repository`, `Service`, `Factory`, `Policy`) — **mirrorятся на поле**. Несут ubiquitous language. `userRepository: UserRepositoryPort` ✓
- **Architectural-role suffixes** (`Port`, `Adapter`, `UseCase`, `Boundary`) — **НЕ mirrorятся на поле**. Только на типе/токене/файле.

Правило: если interface named с domain-role suffix (`UserRepository` без `Port`) — field mirrors его (`userRepository`). Если interface named с architectural suffix (`ListGroupsPort`) — field берёт runtime identity без suffix (`listGroupsService`).

### D-LOCKED-NAMING-05: Canonical layer-by-layer naming matrix

| Слой | Field name | Type | DI token | Runtime class |
|------|-----------|------|----------|---------------|
| **Controller injects inbound port** | `listGroupsService` | `ListGroupsPort` | `LIST_GROUPS_PORT` | `ListGroupsService` |
| **Service injects use case** | `verifyCredentials` | `VerifyCredentialsUseCase` | — (class reference, no Symbol) | `VerifyCredentialsUseCase` |
| **UseCase injects outbound port** | `userRepository` | `UserRepositoryPort` | `USER_REPOSITORY_PORT` | `PgUserRepository` |

Канонический pattern. Все 4 gRPC сервиса должны ему следовать.

### D-LOCKED-NAMING-06: Outbound port/adapter naming — keep current

**Не меняем** текущий outbound pattern:
- Interface: `UserRepositoryPort` (с `Port` suffix — consistency с phase 999.10 decisions)
- Adapter: `PgUserRepository` (Vernon-style technology prefix, без `Adapter` suffix)

Альтернатива (убрать `Port` с outbound interface → `UserRepository` à la Vernon) — **не в scope этой фазы**, отдельная decision если захотим Vernon-pure style. Current state: defensible и внутренне consistent.

### D-LOCKED-NAMING-07: Inbound adapter vs inbound port impl — clarified

**Controller** = inbound adapter (protocol translator: gRPC ↔ Command).
**Service** (LoginService, ListGroupsService, etc.) = inbound port implementation (application service).

Это **два разных класса** на inbound стороне. Controller **не реализует** inbound port — он **вызывает** его. Не путать.

## Updated Example — LoginService

Pattern для Service, инжектирующего UseCases:

```ts
@Injectable()
export class LoginService implements LoginPort {
  constructor(
    private readonly verifyCredentials: VerifyCredentialsUseCase,
    private readonly issueTokenPair: IssueTokenPairUseCase,
    // UseCase инжектится по classу, не через Symbol — не нужен _PORT token
  ) {}

  async execute(cmd: LoginCommand): Promise<LoginResult> {
    const user = await this.verifyCredentials.execute(cmd);
    //                          ↑ action name, type: UseCase
    const tokens = await this.issueTokenPair.execute(user);
    return { accessToken: tokens.accessToken, refreshToken: tokens.refreshToken };
  }
}
```

UseCases инжектятся через class reference (не Symbol), field name = action verb (`verifyCredentials`, `issueTokenPair`).

## Updated Example — UseCase

Pattern для UseCase, инжектирующего outbound Repository:

```ts
@Injectable()
export class VerifyCredentialsUseCase {
  constructor(
    @Inject(USER_REPOSITORY_PORT) private readonly userRepository: UserRepositoryPort,
    private readonly passwordHasher: HashPasswordUseCase,
  ) {}

  async execute(cmd: LoginCommand): Promise<User> {
    const user = await this.userRepository.findByEmail(cmd.email);
    //                          ↑ domain-role suffix (Repository) mirrored on field
    //                             type: UserRepositoryPort (architectural)
    // ...
  }
}
```

Здесь **domain-role suffix `Repository` в field name сохраняется** (D-LOCKED-NAMING-04). `userRepository` читается как "объект, работающий с users репозитария". Отличается от `listGroupsService` где `Service` тоже domain-role но уже инфраструктурно звучит — спорный момент.

## Open Questions for `/gsd:discuss-phase 999.10.1`

Эти вопросы НЕ закрыты, нужно решить в discuss-phase:

### 1. Rollout strategy: atomic sweep per service vs cross-cutting by layer?

**Опции:**
- **A. Per-service sweep:** auth целиком → sender целиком → parser целиком → audience целиком. Mirror 999.10 migration style. Plus: atomic, minimal transient state. Minus: 4 большие commit'ы.
- **B. Per-layer sweep:** все Controllers across 4 services → все Services → все UseCases → все Repositories. Plus: chance to see full cross-service consistency в одном commit per layer. Minus: больше transient states.
- **C. One atomic commit за весь refactor:** все файлы одним commit'ом (как 999.10-02 Plan 1 первый task). Plus: самый атомарный. Minus: огромный diff, сложнее review.

**Leaning:** A (per-service sweep) — mirror 999.10 proven pattern.

### 2. Outbound port interface rename scope?

Текущее: `UserRepositoryPort`, `CampaignRepositoryPort`, `ParserTaskRepositoryPort`, `RecipientRepositoryPort`, `GroupRepositoryPort`.

**Опции:**
- **A. Не трогаем** (D-LOCKED-NAMING-06) — consistent с `Port` suffix convention 999.10.
- **B. Vernon-style rename** — `UserRepositoryPort` → `UserRepository` (domain-role suffix уже carries weight; дополнительный `Port` redundant). Требует rename interface + все imports + constants.

**Leaning:** A (не трогаем). Если хотим Vernon-style — отдельная фаза 999.10.2.

### 4. ESLint enforcement of naming?

Сейчас ESLint guards только layer isolation (Override 8+9). Naming convention — NOT enforced.

**Опции:**
- **A. Не enforce.** Naming — convention, не rule. Code review ловит drift.
- **B. Custom ESLint rule** (`eslint-plugin-*` или inline) для проверки field name patterns. Напр.: field типа `XxxPort` не должен иметь name суффикс `Port`. Сложно написать, рискует false positives.
- **C. Naming lint через grep в CI** (не ESLint) — post-commit check.

**Leaning:** A (не enforce). Skill+docs достаточно.

### 5. Collision edge cases — controller method vs inbound port field

Если proto метод имеет имя `listGroups` (в `AudienceController`) И inbound port тоже называется `ListGroupsPort` — field должен быть `listGroupsService` per D-LOCKED-NAMING-05.

Но что если несколько методов указывают на тот же inbound port? (Gibraltar edge case, в 999.10 такого не было.) Или: что если два inbound ports имеют похожие имена (`ListUsersPort`, `ListGroupsPort`)? Field naming должен оставаться short.

**Leaning:** правило `{verb}{noun}Service` достаточно; per-method unique через protobuf API contract.

### 6. Domain-role vs architectural-role suffix edge cases

Текущие cases:
- `LoginPort` — architectural (Port suffix). Field: `loginService` ✓
- `UserRepositoryPort` — mixed (architectural Port + domain Repository). Field: `userRepository` (D-LOCKED-NAMING-04 правило: domain-role wins)
- ?? — есть ли другие mixed cases?

Нужен audit всех ports во всех 4 сервисах — выявить border cases.

### 7. Service inject pattern — Symbol or class reference?

Текущее (phase 999.10):
- **Inbound ports:** Symbol token (`LIST_GROUPS_PORT`)
- **UseCases:** class reference (`VerifyCredentialsUseCase` — no Symbol)
- **Outbound ports:** Symbol token (`USER_REPOSITORY_PORT`)

Это смешанный pattern. Сохраняем?

**Leaning:** да, сохраняем. UseCases — internal composition detail, concrete class OK. Ports — abstraction boundaries, Symbol token правильный.
