**Key empirical observations for LAYERS.md §Canonical Tree narrative:**

1. **Composer pattern is universal.** Every outbound category with ≥1 sub-slice has a category-level composer module (`persistence.module.ts`, `grpc-clients.module.ts`, `http-clients.module.ts`, `storage.module.ts`). Root module imports the composer, never individual sub-slices.
2. **Per-feature composer modules** (`user.module.ts` inside `persistence/user/`, `auth-client.module.ts` inside `grpc-clients/auth/`) are NestJS DynamicModules that wire per-aggregate DI bindings (`{provide: USER_REPOSITORY_PORT, useClass: PgUserRepository}`) and import foundation primitives they need (`PersistenceModule.forRootAsync()`).
3. **Audience `group/` has NO `mappers/` yet** — stub repository pending real persistence (see `group.module.ts` inline comment). Skill must NOT assert `mappers/` is mandatory at day-one; it's mandatory once a real Drizzle row→entity translation exists. Revise LAYERS.md §persistence/mappers/ narrative to match this reality.

5. **Inbound has `rest/` NOWHERE.** All HealthControllers live in `bootstrap/health/` (D-08). `inbound/rest/` is a future scaffold for feature-REST endpoints on gateway (currently NONE).
6. **One `grpc.module.ts` per inbound/grpc/ dir.** This is the inbound feature composer — it declares the `AuthController` (single file per proto service per D-03), binds inbound ports to services, and brings in the per-service use-cases and outbound persistence per the 999.11.2 Plan 10 Option A relocation pattern (see `apps/auth/src/auth.module.ts` line 14 comment for the canonical authority on this pattern).
