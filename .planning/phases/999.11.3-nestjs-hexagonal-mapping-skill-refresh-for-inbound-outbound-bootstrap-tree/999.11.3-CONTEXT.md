## Implementation Decisions

### Edit style (Area 1)

- **D-01:** **Inline rewrite** устаревших путей прямо в тексте. Skill как source of truth должен быть actual для читателя (новый человек или LLM в сессии) — append-only subsection сделала бы его внутренне противоречивым (ссылка на старый и новый путь одновременно). Append-only подход из `infrastructure-client-layering` Plan 09 подходил для 12-строчного delta; здесь 30+ устаревших ссылок, subsection стал бы равен размеру исходного текста. История preservируется в git log + VERIFICATION.md перечисляет commits.

### Plans decomposition (Area 2)

- **D-02:** **2 plans = 2 atomic commits.**
  - **Plan 01:** SKILL.md + LAYERS.md (core surface — главное определение каноничных путей + Canonical Tree переписывается; наибольший delta). Single atomic commit.
  - **Plan 02:** references/* (CALL-FLOW.md + PROTO-VISIBILITY.md + DO-DONT.md + NAMING.md + EXAMPLES.md + bidirectional cross-ref polish в infrastructure-client-layering/SKILL.md) + VERIFICATION.md с grep-proof таблицей. Single atomic commit.
  - Precedent: 999.11.2 Plan 09 делал 2 tasks в 1 atomic commit когда они были semantically связаны; здесь разделяем на 2 commit'а потому что core (Plan 01) самодостаточен как reading surface — `nestjs-hexagonal-mapping/SKILL.md` + `LAYERS.md` читаются первыми; references дополняют.
  - **D-13 per-commit gate** (из 999.11.2): `pnpm lint && pnpm build` exit 0 после каждого commit. Docs-only commits → full-turbo cache hit ожидаем.

### Verification discipline (Area 3)

- **D-03:** **Шаг-перед-правкой без следа в skill** + **финальный VERIFICATION.md с grep-proof таблицей.** Формула:
  1. *Перед каждой правкой:* grep/Read реального кода (`apps/*/src/`) для проверки утверждения, которое меняем. Эта работа **не оставляет следа в файлах skill** — читается чисто.
  2. *В конце фазы (Plan 02 final commit):* VERIFICATION.md в формате 999.11.2 VALIDATION.md — таблица «Canonical path / Invariant / Grep command / Expected count / Observed count / Status + commit hash». Каждая строка executable: будущий reader может запустить команду и получить тот же результат. Commit hashes embedded — self-auditing.
- **D-04:** **Embedded grep-invariants внутри skill-файлов rejected** (Option b). Rationale: paths в skill required maintenance при каждом tree-shift — precedent D-16 lesson 999.11.2 (когда paths move, grep-rules must follow, иначе silently stop enforcing). Skill остаётся narrative, VERIFICATION.md несёт грep-доказательную базу отдельно.
- **D-05:** **Слабая точка 999.11.2 учтена:** skill устарел незамеченно потому что 999.11.2 Plan 09 имел embedded invariants только для `infrastructure-client-layering` (§D-17 grep check `bootstrap/config` ≥ 1 + `999.11.2` ≥ 1), но не для `nestjs-hexagonal-mapping`. Здесь VERIFICATION.md покрывает оба skill: grep-invariants подтверждают что нет `infrastructure/controllers/grpc` или `infrastructure/persistence/pg-` (without aggregate subdir) в ни одном из скил-файлов, И что `inbound/grpc/`, `outbound/persistence/`, `bootstrap/config/` появляются с ожидаемой частотой.

### Extent (Area 4)

- **D-06:** **Comprehensive refresh.** Scope:
  1. Inline rewrite всех устаревших paths (см. §Phase Boundary).
  2. LAYERS.md §«Canonical Tree» полностью переписана под реальную структуру (scout подтверждён: `infrastructure/{bootstrap/{config,health},inbound/grpc,outbound/{grpc-clients,http-clients,persistence/{aggregate},storage/{bucket|reports}}}`).
  3. Новые секции в LAYERS.md:
     - §Bootstrap layer — три категории bootstrap: `config/` (env schema + provider + `@Global()` module + `{SVC}_CONFIG` Symbol per 999.11.1 D-08), `health/` (HealthModule wrapper per 999.11.2 D-08), `throttle/` (gateway only), `logging/` (foundation).
     - §Inbound feature slicing — `inbound/grpc/` (один file per proto service per 999.11.2 D-03), `inbound/rest/{feature}/` (multi-endpoint REST groups; future gateway feature phases), `inbound/rmq/` (notifier RMQ consumers per 999.11.2 D-05).
     - §Outbound feature slicing — `outbound/grpc-clients/{upstream}/`, `outbound/http-clients/{vendor}/`, `outbound/persistence/{aggregate}/`, `outbound/storage/{bucket-or-namespace}/` (parser double-module preserved per 999.11.2 D-02), `outbound/publishers/{event-type}/` (deferred for Phase 25 EventModule — show placeholder).
  4. Gateway D-11a exception documented: LAYERS.md §DI Tokens subsection + DO-DONT.md §9 (one-flat-module) gets a note. Pattern: gateway's constants.ts was deleted (single member `GATEWAY_CONFIG` became empty post-999.11.1 D-10); other 5 services keep root `{svc}.constants.ts` for cross-folder domain port Symbols.
  5. EXAMPLES.md — обновить file-path комментарии во всех 3 worked examples (Example 1 Login composite, Example 2 pure delegation, Example 3 proto↔command mapping) + добавить short snippet showing bootstrap/config/ slice shape. Content semantics не трогаем.

### Cross-references (Area 5)

- **D-07:** **Bidirectional cross-reference.** Rationale: paired skills (server-side + client-side) должны ссылаться друг на друга — unidirectional create asymmetry и reader landing в infrastructure-client-layering не узнает про server-side counterpart для нашего проекта.
  - В `nestjs-hexagonal-mapping/SKILL.md` §See Also: link на `infrastructure-client-layering/SKILL.md` §Config (Phase 999.11.2 refinement) — уже есть частично (line 110), проверим точность.
  - В `infrastructure-client-layering/SKILL.md`: verify that cross-ref to `nestjs-hexagonal-mapping` exists (shapка skill упоминает его как «server-side counterpart»); polish wording если неточность. Минимальное вторжение в sibling skill.

### Verification principle (user explicit requirement)

- **D-08:** **Verify-against-reality.** User explicit preference (2026-04-21): «Во время работы так же смотри реальный код проекта, что бы все совпадало». Каждое утверждение в skill проверяется grep/Read против `apps/*/src/` перед тем как правим. Если скил утверждает что `apps/auth/src/infrastructure/inbound/grpc/auth.controller.ts` существует — сначала `ls` или `Read`, потом правим skill. Принцип применяется к обоим planам.
