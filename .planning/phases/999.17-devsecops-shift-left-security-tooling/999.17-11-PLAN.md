**Canonical pnpm 11 build-script trust mechanism:**

`pnpm-workspace.yaml` (TOP-LEVEL keys):

```yaml
# Fail-closed posture: `false` (default) = warn only; `true` = exit non-zero on
# unreviewed build-script packages. Required for the trust gate to be a *gate*.
strictDepBuilds: true

# Map of package-name matcher → boolean. Replaces (and pnpm 11.0.0 REMOVED) the
# legacy `onlyBuiltDependencies` / `neverBuiltDependencies` / `onlyBuiltDependenciesFile`
# / `ignoredBuiltDependencies` keys. Every postinstall-bearing package in the
# transitive dep graph must have an explicit entry — no implicit allow.
allowBuilds:
  '@nestjs/core': true # NestJS bootstrap setup script (project-internal toolchain)
  '@esbuild/linux-x64': false # OS-specific binary downloader (DO NOT trust — esbuild parent already mirrors policy)
  esbuild: false # Parent package (downstream from Vite/Turbo build deps)
  grpc-tools: true # Required for proto codegen (project-internal toolchain)
  protobufjs: true # Required for runtime proto loading (project-internal toolchain)
```

**Matcher rules (verified via https://pnpm.io/settings):**

- Matcher is package-name-as-string (or `<name>@<semver>` for version constraint).
- A `false` parent (e.g. `esbuild: false`) does NOT cascade to OS-specific binary packages (`@esbuild/linux-x64`, `@esbuild/darwin-arm64`, etc.) — each must be listed explicitly.
- Pattern matchers like `'@esbuild/*'` are NOT documented as supported in pnpm 11.0.0 — use explicit per-package entries.

The binaries are in `@esbuild/linux-x64@*` (a different package from `esbuild`), so `esbuild: false` does not block them.

**Source of authority:** https://pnpm.io/settings#allowbuilds + https://pnpm.io/settings#strictdepbuilds + https://github.com/pnpm/pnpm/releases/tag/v11.0.0 (release notes — REMOVED `onlyBuiltDependencies`).
