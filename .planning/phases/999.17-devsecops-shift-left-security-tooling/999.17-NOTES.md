## Locked Architectural Decisions (pre-discussion)

### D-1: Three-layer security verification strategy

| Layer | Trigger | Speed budget | Contents | Bypassable? |
|-------|---------|--------------|----------|-------------|
| **L1: pre-commit** (husky + lint-staged) | git commit, staged files only | < 5 sec | gitleaks (secrets in diff), ESLint+Prettier (lint+format) | yes (`--no-verify`) |
| **L2: pre-push** (husky) | git push, vs origin/main | 10–30 sec | Semgrep `--baseline=origin/main`, `pnpm audit` (if lock changed), Trivy config (if Dockerfile/compose changed) | yes (`--no-verify`) |
| **L3: CI required gate** (GitHub Actions + branch protection) | PR / push | minutes | full gitleaks, full Semgrep, Trivy fs (SCA + license), Trivy config (all Dockerfiles + compose), Trivy image (after build), Syft (SBOM artifact), Quality Gate thresholds | **no** (branch protection enforces) |

**Rationale:** hooks ≠ security boundary, hooks = UX. Any developer can `--no-verify` to skip hooks. The CI gate is the actual enforcement. Hooks exist for fast developer feedback. The same checks run on both layers — one for speed, one for guarantee.

### D-2: Lean tooling stack

**Selected (in scope):**
- **gitleaks** — secret scanning (pre-commit + CI full)
- **Semgrep** — SAST for TS/Node/NestJS (pre-push incremental + CI full, with NestJS-specific baseline rules)
- **Trivy** in 3 modes (Swiss army knife covering 3 separate concerns):
  - `trivy fs` — npm SCA + license check (CI)
  - `trivy config` — Dockerfile + docker-compose misconfig detection (pre-push if changed + CI full)
  - `trivy image` — built artifact CVE scan (CI after build)
- **Syft** — SBOM generation as CI artifact (after image build)
- **husky 9** + **lint-staged** — pre-commit framework (D-3 unresolved: existing in repo or fresh install)
- **Quality Gate** as GitHub Actions thresholds (HIGH/CRITICAL CVE → block merge, new secret → block, SAST HIGH+ → block) — implemented as `if exit-code != 0` shell logic, NOT a separate service

**Rejected during analysis:**

| Tool | Reason for rejection |
|------|---------------------|
| **SonarQube** | 80%+ functional overlap with Semgrep. Heavy infrastructure (separate DB + server, license cost for private repos). Semgrep is FOSS, rule-based, lighter, designed exactly for TS/Node. SonarQube's value is centralized quality dashboards across multiple teams — not the user's situation. |
| **Standalone SCA tool (Snyk, OSV-Scanner, npm audit as primary)** | Trivy `fs` mode covers npm SCA + license check in one binary. Adding a separate SCA tool duplicates the function. `pnpm audit` retained as pre-push trigger only (lightweight diff-aware check), not as primary gate — Trivy CI is the gate. |
| **Talisman** | Functional overlap with gitleaks. Gitleaks is more popular, faster, supports both pre-commit and CI cleanly, has better ecosystem (e.g., GitHub Action). |

### D-3: Scope partition (dev vs devops layers)

**In scope (dev — this phase):**
- husky setup (pre-commit + pre-push hooks)
- `.github/workflows/security.yml` (CI workflows)
- Quality Gate thresholds config (in CI YAML)
- Documentation: how a developer runs checks locally
- Baseline Semgrep rules tuned for NestJS/TS
- Trivy config rules for Dockerfile + docker-compose

**Out of scope (devops — explicitly excluded from this phase):**
- Continuous Trivy `image` rescan of production images on cron schedule (CVE feed updates daily — needs scheduled scanner, alerts go to ops infrastructure, not dev workflow)
- Runtime security (Falco, Wiz, Aqua)
- DAST (ZAP, Burp) — needs staging environment with synthetic traffic
- Secrets management in production (Vault, SOPS)
- WAF / IDS / IPS / k8s admission controllers
- External synthetic monitoring (Datadog, Checkly) — already deferred to Phase 999.15

**Deferred to a separate future phase:**
- **Renovate / Dependabot** for automatic dependency updates — orthogonal concern (process around merge of auto-PRs vs the security scanners themselves). Could be picked up after 999.17 ships.

### D-4: Trivy mode-by-mode ownership table

User explicitly questioned whether Trivy belongs to dev or devops. Resolution:

| Trivy mode | Owner | Why |
|-----------|-------|-----|
| `trivy config` (static Dockerfile/compose analysis) | **dev (this phase)** — both pre-push hook and CI | Pure static analysis, doesn't need CVE feed updates. Catches misconfigs (USER root, latest tag, exposed secrets, missing healthcheck) at developer time. |
| `trivy fs` (npm deps + license) | **dev CI gate** | Needs CVE feed but blocks merge — prevents merge → deploy → vuln-in-prod path. Must be in CI required check. |
| `trivy image` (binary artifact) | **dev CI** initially + **devops continuous** rescan later | CI scans freshly-built image. Devops adds cron rescan of running production images (catches new CVEs published after image was built). The continuous rescan is OUT OF SCOPE here. |

### OQ-2: Renovate vs Dependabot vs neither (this phase)

Three sub-options:
- **(a) Include Dependabot in this phase:** native to GitHub, free, simplest. Auto-PRs for security updates.
- **(b) Include Renovate in this phase:** more flexible (monorepo-aware, group rules, pnpm catalog awareness), free for OSS but requires hosted bot.
- **(c) Defer to a separate phase:** dependency-update bot is an orthogonal concern (about merge process, not about scanners). Cleaner scope for this phase.

Pre-discussion lean: **(c) defer**. Phase 999.17 stays focused on detection/gating; auto-update bot becomes Phase 999.18 or similar.

### OQ-3: Quality Gate thresholds — strictness level

Block-on policy needs to be locked:
- **(a) CRITICAL only blocks:** permissive — only CRITICAL CVEs / SAST findings block merge. HIGH+ findings warned but not blocked.
- **(b) HIGH and above blocks:** stricter — HIGH/CRITICAL CVEs + HIGH+ SAST block merge. MEDIUM warned.
- **(c) Configurable per finding type:** secrets always block, CVEs HIGH+ block, SAST CRITICAL only block, license MEDIUM+ block. Most expressive but more YAML to maintain.

Pre-discussion lean: **(b) HIGH and above blocks** with explicit suppression rule for known-but-accepted findings (Trivy `.trivyignore`, Semgrep ignore comments).

### OQ-4: Pre-commit hook — required or only CI?

Sub-question: do we mandate pre-commit hook setup (every developer must run `pnpm install` triggers husky install), or only ship CI gate and let pre-commit be optional?

- **(a) Required:** husky install is part of `prepare` script in package.json — runs automatically on `pnpm install`. Every developer gets hooks. Catches secrets before push.
- **(b) Optional:** CI is the only enforcement. Developers who want fast feedback can opt in to hooks.

Pre-discussion lean: **(a) required**. Cost is negligible (one-time install), benefit is catching secrets before they ever reach git history (where remediation is rotation + history rewrite, painful).
