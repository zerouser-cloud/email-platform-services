<objective>
Fix the gitleaks allowlist regex blind spot identified as CR-02 in 999.17-VERIFICATION.md by removing the over-broad custom `[allowlist].paths` entry from `.gitleaks.toml`.

**Verifier root-cause (confirmed correct):** `.gitleaks.toml` line 17 regex `'''(.*?)(jpg|gif|doc|pdf|bin|svg|socket)'''` is unanchored. Python regex match against this codebase's actual source-file path prefixes proves four real source files are silently skipped:

- `apps/auth/src/documentation.ts` — substring `doc` matches
- `apps/sender/src/binary-helper.ts` — substring `bin` matches
- `apps/parser/icons/svg-loader.ts` — substring `svg` matches
- `infra/docker/socket-config.yml` — substring `socket` matches

A developer who commits an AWS key (or any other gitleaks-detected secret format) to one of these paths would have it pass dev-side gitleaks AND CI gitleaks — same `.gitleaks.toml` is inherited by `.gitlab-ci-security.yml.example` (CR-02 confirmed via verifier reproduction; cross-tier image-tag and config-file consistency was already VERIFIED in 999.17-VERIFICATION.md truth #11).

**Decision: Option B (delete the custom allowlist).** Per 999.17-VERIFICATION.md `gaps.missing[1]`, two remediation options exist:

- **Option A:** Anchor regex to extension end: `'''\\.(jpg|gif|pdf|bin|svg|socket)$'''` (drop `doc` — too greedy substring; if real `.doc` files need exclusion, separate `'''\\.docx?$'''` entry).
- **Option B:** Delete the custom `[allowlist].paths` entry entirely — gitleaks default config already covers binary file types per `.gitleaks.toml`'s OWN preamble: "the default config is comprehensive — only add rules that are unique to this codebase".

The plan picks **Option B**. Rationale:

1. **Minimal surface area** — eliminates the entire class of unanchored-regex bugs (no regex to get wrong).
2. **Honors the file's own design intent** — the preamble (lines 4-6 of `.gitleaks.toml`) explicitly says only add rules unique to this codebase. Binary file extensions are NOT unique to this codebase.
3. **`useDefault = true` already covers binary paths** — gitleaks ships a community-audited default `.gitleaks.toml` that excludes binary extensions (per gitleaks docs https://github.com/gitleaks/gitleaks#configuration). Re-implementing this locally is duplication.
4. **Safer fail-mode** — if gitleaks default ever updates its path exclusions, project inherits the update automatically. With a hand-rolled regex, project drifts.
5. **No real binary files at risk in this repo right now** — `find apps/ packages/ infra/ -name '*.bin' -o -name '*.pdf' -o -name '*.jpg' -o -name '*.gif' 2>/dev/null` returns zero matches at planning time. The custom allowlist was solving a hypothetical, not an actual, false-positive.

**Option A is documented as the alternative** in this plan's `<context>` block — if a future binary-file false-positive surfaces, an executor can swap to anchored-regex Option A by reverting this commit and applying Option A's pattern.

Output:

- `.gitleaks.toml` with the entire `[allowlist]` block removed (keeping the preamble + `[extend]` + commented-out `[[rules]]` example).
- Empirical proof: `gitleaks detect` against one of the previously-bypassed paths now scans it (no "allowlisted" output, no skip).
