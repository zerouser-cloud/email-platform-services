|----------|-------------|
| developer machine ↔ npm registry | `pnpm install`/`pnpm audit` HTTP fetches from registry.npmjs.org — registry endpoint must answer non-410 |
| developer machine ↔ Corepack pin | `packageManager` field controls which pnpm binary Corepack downloads; integrity via Corepack signature verification |
| project lockfile ↔ build cache | pnpm 11 lockfile may bump `lockfileVersion`; Turbo / Docker layer caches keyed off lockfile checksum |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-99917-01-01 | Tampering | `packageManager` pin (Corepack download path) | mitigate | Pin exact 3-part SemVer (`pnpm@11.x.y`), not a range. Corepack verifies signature on download. Documented in package.json (canonical source). |
| T-99917-01-02 | Information Disclosure | pnpm-lock.yaml diff during regeneration | accept | Lockfile metadata may bump; package contents do NOT (acceptance criterion enforces this). Reviewed by human in Task 2 checkpoint. |
| T-99917-01-03 | Denial of Service | `pnpm audit` HTTP 410 on legacy endpoint | mitigate | This task IS the mitigation — bump to v11 fixes the breakage (RESEARCH §Pitfall 3). |
| T-99917-01-04 | Tampering | Turbo cache invalidation post-pnpm-bump | accept | First post-bump build pays cache miss; subsequent builds cached. Documented as accepted side-effect of D-11. |
