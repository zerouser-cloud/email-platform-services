## Goal Achievement Summary

Phase 999.17 ships **most** of the shift-left tooling correctly: 17 phase artifacts present, 8 `security:*` npm-scripts wired, husky hooks honour the 1-line wrapper invariant, Docker scanner image tags consistent across DEVOPS-HANDOFF.md / .gitlab-ci-security.yml.example / package.json / scripts/security/*.sh, suppression baselines ship empty with strong governance comments, and the dual-runtime smoke (Plan 10) confirmed both runtime modes still boot post-changes.

But two BLOCKERs falsify the goal claim that "Layer 1 ships a working security gate":

1. **CR-01 reproduces empirically.** `pnpm-workspace.yaml#allowBuilds` is not a recognised pnpm settings key. Plan 02's Pre-Task amendment migrated build-script trust from a working `package.json#pnpm.onlyBuiltDependencies` (deleted in commit `ee9b119`) to a silently-ignored key. Three esbuild postinstall artifacts (Go-built ELF binaries) exist in this repo's `node_modules` despite `esbuild: false` in the new config — proving the postinstall ran. The phase regressed supply-chain posture from "working control" to "no control with misleading config", which is worse than not adding the change at all because a reviewer reading `pnpm-workspace.yaml` would conclude esbuild's postinstall is blocked.

2. **CR-02 reproduces empirically.** `.gitleaks.toml`'s `[allowlist].paths` regex `(.*?)(jpg|gif|doc|pdf|bin|svg|socket)` is unanchored. It matches `apps/auth/src/documentation.ts`, `apps/sender/src/binary-helper.ts`, `apps/parser/icons/svg-loader.ts`, `infra/docker/socket-config.yml` — paths the secret scanner should be checking. The same config is inherited by CI per `.gitlab-ci-security.yml.example`, so the blind spot survives the dev-→-CI handoff.

Both regressions are silent fail-open conditions. Plan 10's smoke tests passed because they did not exercise the failure paths: the gitleaks fake-AWS-key smoke used `.smoke-fake-secret.env`, which doesn't contain any allowlist substring, and no smoke ever attempted to install a postinstall-bearing package while observing pnpm's blocking behaviour. The two BLOCKERs therefore evaded "does it run" verification.

## Gaps Summary

The phase delivered the surface form of the three-layer shift-left security system — every required artifact exists, npm-scripts are wired, hooks fire, Docker tag pins are consistent — but two BLOCKERs invalidate the goal claim that "Layer 1 ships a working security gate":

1. **Build-script trust gate is functionally absent (CR-01).** Plan 02's Pre-Task amendment migrated trust from a working `package.json#pnpm.onlyBuiltDependencies` to an unrecognised `pnpm-workspace.yaml#allowBuilds` key. Plan 02's `patterns-established` note — "pnpm 11 trust list = `pnpm-workspace.yaml#allowBuilds` map" — is wrong and will mis-guide future plans if left uncorrected.

2. **Secret scanner has a path-substring blind spot (CR-02).** `.gitleaks.toml`'s allowlist regex `(.*?)(jpg|gif|doc|pdf|bin|svg|socket)` is unanchored. Four real-world paths in this codebase's apps/*/src tree match the regex and are silently skipped from scanning. CI inherits the same `.gitleaks.toml`, so the blind spot survives the dev→CI handoff.

Both BLOCKERs survived the Plan 10 phase-completion smoke because the smoke fixtures didn't trigger them: the gitleaks fake-AWS-key test used `.smoke-fake-secret.env` (no allowlist substring), and no smoke ever installed a postinstall-bearing package while observing pnpm's blocking behaviour. They are silent fail-open conditions — exactly the failure mode hardest to catch without behavioural reproduction.

The fix in both cases is small (one config-line change each + a verification step that reproduces the failure mode) and routes to `/gsd-plan-phase 999.17 --gaps`. Recommend a single sub-phase (or pair of `/gsd:fast` commits if simpler) addressing both, with the explicit acceptance criterion that:

- `pnpm install --offline` after deleting `node_modules/` + `pnpm-lock.yaml` emits `ERR_PNPM_IGNORED_BUILDS` listing every blocked package (including esbuild).
