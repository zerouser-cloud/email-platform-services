## 2026-04-29 Amendment (Plan 999.17-11)

**Context:** 999.17-VERIFICATION.md identified a fail-open in this plan's Pre-Task amendment (CR-01) — the `allowBuilds: { esbuild: false }` map alone did not block esbuild's postinstall semantically, because `strictDepBuilds` was unset and pnpm's default posture is warning-only (not fail-closed). Plan 999.17-11 root-caused the failure to:
- (a) **`strictDepBuilds` was unset** (pnpm default `false` = "warn but proceed"). With `strictDepBuilds: false`, pnpm prints `ERR_PNPM_IGNORED_BUILDS` lines but still exits 0 — install proceeds with `false`-listed postinstalls correctly skipped, but no developer-facing fail-closed gate exists.
- (b) **The verifier's CR-01 symptom** (3 ELF binaries in `@esbuild/linux-x64@*/bin/esbuild`) was empirically a measurement artifact: those binaries are part of the npm tarball payload and are unpacked by pnpm regardless of `allowBuilds` policy. The OS-binary packages have empty `scripts: {}` (verified — no install/postinstall to gate). The actual postinstall product would have been a modified `esbuild/bin/esbuild` (the parent's wrapper script); empirical re-verification under Plan 999.17-11 confirms that file remains the original ASCII Node.js shim, proving the parent `esbuild` postinstall was NOT executed even before this gap closure (the original `esbuild: false` entry was working semantically; only the strict mode was missing).

**Fix delivered by Plan 999.17-11:** `pnpm-workspace.yaml` now contains:
1. `strictDepBuilds: true` (top-level) — fail-closed posture.
2. The 4 original entries preserved (`@nestjs/core: true`, `esbuild: false`, `grpc-tools: true`, `protobufjs: true`).
3. `@esbuild/linux-x64: false` added (matcher-granularity defence-in-depth).

**Empirical verification (Plan 999.17-11 Task 3):** clean `rm -rf node_modules && pnpm install` exits 0 with only 2 postinstalls running (`@nestjs/core`, `protobufjs` — both `true`); zero `ERR_PNPM_IGNORED_BUILDS` lines; `esbuild/bin/esbuild` remains an ASCII Node script (postinstall did not run). Removing any single `true` entry and re-running clean install yields **exit code 1** with `ERR_PNPM_IGNORED_BUILDS Ignored build scripts: <pkg>` — gate fail-closes as documented. The lockfile is byte-stable through the gate transition (zero diff).

**`patterns:` correction:** the original second bullet's claim that `allowBuilds` alone constitutes a working trust gate is incomplete; corrected above to require `strictDepBuilds: true` for fail-closed enforcement and to call out matcher-granularity. Future plans referencing pnpm 11 trust syntax should consult the corrected bullet, not the original.

**Note for verifier's recommendation:** 999.17-VERIFICATION.md proposed restoring `onlyBuiltDependencies` (in `pnpm-workspace.yaml` or `package.json`). Per the pnpm 10.26+/11 docs (https://pnpm.io/blog/2025/12/29/pnpm-in-2025), `allowBuilds` was introduced in pnpm 10.26 as the granular-control replacement for `onlyBuiltDependencies`; the older key still works but `allowBuilds` is the post-10.26 canonical. Plan 999.17-11 chose `allowBuilds` (consistent with what Plan 02 already migrated to) but added the missing `strictDepBuilds: true` flag for fail-closed enforcement. The verifier was correct that the original Plan 02 amendment was non-functional; the planner's diagnosis ("`onlyBuiltDependencies` was REMOVED in pnpm 11.0.0") was wrong — the key was deprecated/superseded, not removed. The empirical fix (add `strictDepBuilds: true`) works regardless of which trust-list key is used.
