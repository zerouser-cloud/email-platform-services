**Gathered:** 2026-04-28
**Status:** Ready for planning

<domain>
## Phase Boundary

**В скоупе фазы — developer-side реализация трёхслойной системы security-проверок:**

- **L1 — pre-commit hook (husky + lint-staged):** быстрые (<5s) проверки на staged-файлах. Содержит: gitleaks `protect --staged` (secrets) + ESLint + Prettier (через lint-staged).
- **L2 — pre-push hook:** инкрементальные проверки (10–30s) на изменения relative `origin/main`. Содержит: typecheck (полный граф типов) + Semgrep `--baseline=origin/main` (SAST diff) + `pnpm audit` (если `pnpm-lock.yaml` изменился) + Trivy `config` (если Dockerfile/compose изменены) + env-parity (через npm-script wrapper над существующим `scripts/check-env-parity.sh`).
- **L3 — DEVOPS-HANDOFF.md (документ-артефакт фазы):** mini-инструкция для DevOps с инвентарём инструментов, рекомендуемой структурой CI pipeline, GitLab-targeted YAML примером (`.gitlab-ci-security.yml.example`), Quality Gate thresholds, server-side `pre-receive` hook паттерном, Renovate runner config.

**В скоупе НЕТ:**
- GitHub Actions `security.yml` — DevOps work, GitHub-период короткий, GitLab-целевой
- Continuous Trivy `image` rescan production-образов (cron) — DevOps owns
- Trivy `fs` + Trivy `image` локально — это CI-only (нужен CVE feed ~1GB, требует scheduled refresh)
- Runtime security (Falco, Wiz, Aqua), DAST (ZAP, Burp), secrets management в проде (Vault, SOPS), WAF/IDS/IPS — out-of-scope для всей фазы (devops layer)
- Renovate bot включение и его серверная сторона — DevOps owns, но `renovate.json` config файл лежит в репо как артефакт фазы
- Реализация бизнес-логики, тестов, новых сервисов — общие constraint'ы PROJECT.md

**Целевая платформа:** активно планируется миграция с GitHub.com на self-hosted GitLab. Все security-tooling должно быть **CI-platform-portable** (plain CLI tools в shell-скриптах, обёрнутых npm-scripts) — переезд = swap CI YAML wrapper, инструменты остаются.
</domain>

<decisions>
## Implementation Decisions

### Hook integration & layering (Area 1)

- **D-01:** Lint+Prettier перенесены в **pre-commit** через **lint-staged** (staged-файлы only, бюджет <5s). Typecheck остаётся в **pre-push** — нужен полный граф типов (TS в monorepo не валидируется per-file).
- **D-02:** Все hooks вызывают **npm-scripts из `package.json`** под namespace `security:*` (например `pnpm run security:pre-commit`, `pnpm run security:pre-push`, `pnpm run security:env-parity`). Логика живёт в скриптах. Hooks = 1-line wrappers. Согласуется с проектным правилом «use package.json scripts, не raw commands» (memory `feedback_use_package_scripts`).
- **D-03:** Gitleaks scope в pre-commit = **staged files only** (`gitleaks protect --staged`). Полный history-scan делает CI/DevOps.
- **D-04:** Defense in depth, **CI-platform-portable**:
  - Layer A (local hooks, UX): husky + lint-staged. Обходимо `git commit/push --no-verify` — это by-design git, принимаем.
  - Layer B (CI required gate, enforcement): GitHub branch protection сейчас → GitLab merge request rules после миграции. Все scanners вызываются через **plain CLI** в shell-скриптах, обёрнутых npm-scripts — переносится на любую CI платформу без переписывания логики.
  - Layer C (server-side push protection): на GitHub.com — **НЕ покупаем** GitHub Advanced Security (paid + не мигрирует). После переезда на self-hosted GitLab — добавляем `pre-receive` server-side hook (free на self-hosted) для блокировки push секретов до записи в repo. Документировано в DEVOPS-HANDOFF.md.

### Scope split & DevOps handoff (Area 2)

- **D-05:** Phase 999.17 реализует **только developer side**. CI security pipeline = DevOps owns. Артефакты фазы:
  - `.husky/pre-commit` + `.husky/pre-push` (новые/обновлённые)
  - `package.json` scripts namespace `security:*`
  - lint-staged config (в `package.json` или `.lintstagedrc.json`)
  - Конфиги scanners в репо: `.gitleaks.toml` (если нужно tuning), `.semgrep.yml` baseline (NestJS/TS-specific rules), `renovate.json`
  - Suppression baseline files: `.gitleaksignore`, `.semgrepignore`, `.trivyignore` (пустые, с шапкой-инструкцией)
  - `DEVOPS-HANDOFF.md` (mini-инструкция для DevOps)
  - `.gitlab-ci-security.yml.example` (GitLab CI YAML reference template)
  - Dev-facing документация (как разработчик запускает проверки локально)

- **D-06:** Trivy mode-by-mode распределение:
  - **`trivy config`** (статический Dockerfile/compose анализ) — **в pre-push локально + продублировано в DevOps CI**. Не требует CVE feed → быстро. CLI ставится одной командой (brew/apt/scoop). Ловит USER root, latest tag, exposed secrets, missing healthcheck.
  - **`trivy fs`** (npm SCA + license) — **CI only**. Требует CVE feed (~1GB). Локально не ставим.
  - **`trivy image`** (binary artifact CVE) — **CI only после image build**. Требует CVE feed. Локально не ставим.
  - Все три mode'а описаны в DEVOPS-HANDOFF.md с примерами вызова.

- **D-07:** Quality Gate thresholds — **per-finding-type recommendation в DEVOPS-HANDOFF.md** (не enforced в dev-side коде):
  - **Secrets** (gitleaks finding) → **always block**, never suppress without rotation
  - **CVE HIGH+** (Trivy fs/image) → block merge
  - **SAST HIGH+** (Semgrep) → block merge
  - **License: GPL/AGPL/SSPL** (Trivy fs license check) → block merge
  - **License: MIT/Apache/BSD/ISC** → allow
  - Known-but-accepted findings → suppression в `.gitleaksignore` / `.semgrepignore` / `.trivyignore` с обязательным комментарием (почему accepted, ticket/CVE link, дата re-evaluate)

- **D-08:** Auto-dependency-update bot = **Renovate** (CI-platform-portable, работает на GitHub App + self-hosted GitLab Renovate runner без изменения конфига). `renovate.json` ложится в корень репо в эту фазу с lean defaults:
  - `extends: ["config:base"]`
  - `vulnerabilityAlerts.enabled: true` + `osvVulnerabilityAlerts: true` (security updates only старт)
  - `lockFileMaintenance` для pnpm-lock
  - Monorepo grouping (один PR на patch-обновления в неделю)
  - Bot **не запускается в этой фазе** — config ждёт DevOps включения. Activate path описан в DEVOPS-HANDOFF.md.

- **D-09:** Suppression-файлы — **пустые baseline files с commented headers** в эту фазу:
  - `.gitleaksignore` — header объясняет формат `commit-sha:file:fingerprint` + правило «всегда комментарий почему»
  - `.semgrepignore` — header объясняет glob паттерны + правило документации
  - `.trivyignore` — header объясняет CVE ID формат + обязательный комментарий с reason/ticket/re-evaluate date
  - Файлы дискаверабельны для разработчика, но пусты — добавление = осознанное действие

- **D-10:** Env-parity check = **только npm-script wrapper** в эту фазу. **Скрипт `scripts/check-env-parity.sh` уже покрывает все 5 проверок** (Phase 24.1 Wave 0 + Phase 999.1.9 W10):
  1. `.env vs .env.docker` (pair check)
  2. `.env.docker vs .env.docker.example` (pair check)
  3. `.env vs .env.example` (pair check, добавлен в Phase 24.1)
  4. `.env.example vs Zod schemas` (schema-driven через grep)
  5. `.env.docker.example vs Zod schemas` (schema-driven через grep)

  Логика **не меняется**. Создаём `pnpm run security:env-parity` wrapper над существующим bash-скриптом, переключаем hook вызов на npm-script.

  TS rewrite (на `Object.keys(Schema.shape)`) **отложен** — текущие grep-ограничения theoretical (все 14 файлов схем используют плоский `KEY: z.xxx()` паттерн). Если в будущем появится `.merge()`/`.extend()`-схема — refactor схему обратно к плоскому паттерну (cheap fix) или выделим в отдельный todo.

<specifics>
## Specific Ideas

- **Hook namespace convention:** все security npm-scripts под `security:*` prefix (например `security:pre-commit`, `security:pre-push`, `security:env-parity`, `security:semgrep-diff`, `security:trivy-config`, `security:audit`). Один namespace → discoverable через `pnpm run | grep security:`.
- **«Hooks ≠ security boundary»** (D-1 в NOTES.md): hooks дают разработчику быстрый локальный feedback, обходимы `--no-verify` by design git, реальный enforcement = CI required check + branch protection (на GitHub) или MR rules + server-side `pre-receive` hook (после миграции на GitLab).
- **«CI-platform-portable»**: scanner вызывается одной CLI командой в shell-скрипте, обёрнутом в npm-script. CI YAML — тонкая обёртка. Перенос на GitLab = переписать YAML, инструменты не меняются.
- **`renovate.json` lean defaults — securityUpdates only на старте**: bot не флудит patch/minor PR'ами, только critical security fixes. Расширение конфига = отдельное решение DevOps + product owner.
- **DEVOPS-HANDOFF.md как mini-инструкция**: список инструментов, что каждый делает, на каком этапе CI, GitHub-период (короткий, минимум) vs GitLab-целевой (полный pipeline + server hooks). Один документ для передачи DevOps.

</specifics>
