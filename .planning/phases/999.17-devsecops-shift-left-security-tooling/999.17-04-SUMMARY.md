# Phase 999.17 Plan 04: Semgrep Configuration Baseline Summary

**One-liner:** SAST foundation — `.semgrep.yml` locks 5 registry rulesets (typescript, javascript, nodejs, owasp-top-ten, r2c-security-audit) per D-13 explicit composition; `.semgrepignore` establishes empty-body audit-trail baseline per D-09.

## What Was Built

Two configuration files at the repository root that together form the SAST scanner contract for Plan 07 (pre-push diff scan) and downstream DevSecOps phases:

1. **`.semgrep.yml`** — Version-controlled source of truth for which Semgrep registry rulesets the project depends on. Uses a project-convention `rulesets:` YAML field listing 5 registry IDs. The Plan 07 npm-script will parse this file via `grep -E '^\s+- p/' .semgrep.yml | awk '{print $2}'` and emit one `--config <id>` flag per entry.

2. **`.semgrepignore`** — Suppression baseline with an empty body. The 17-line header documents Semgrep's built-in defaults, four rules governing future entries (most importantly: every glob MUST have a WHY comment), and the preferred alternative (`// nosemgrep: rule-id` inline at the suppressed code).

## File Bodies

### `.semgrep.yml` (full)

```yaml
# Phase 999.17 — Semgrep ruleset composition baseline (D-13).
# See .planning/phases/999.17-devsecops-shift-left-security-tooling/.
#
# This file is the version-controlled source of truth for which Semgrep
# registry rulesets the project depends on. The actual scanner CLI
# invocation lives in package.json `security:semgrep-diff` (Plan 07) and
# MUST mirror this list as `--config p/<id>` flags.
#
# WHY explicit composition (not `--config=auto`):
#   - `auto` requires Semgrep cloud account login on every dev machine + CI runner
#   - `auto` ruleset can change upstream without a git diff in this repo
#   - explicit composition is reproducible, air-gappable, and code-reviewable
#
# CONVENTION: the `rulesets:` field below is a PROJECT convention, NOT a
# Semgrep-native YAML key. Plan 07's `security:semgrep-diff` npm-script
# parses this file via:
#   grep -E '^\s+- p/' .semgrep.yml | awk '{print $2}'
# and emits one `--config <id>` flag per entry. This keeps the registry
# list in one greppable, code-reviewable file. If a future Semgrep version
# adds a native YAML field for registry composition, this file migrates.

rulesets:
  - p/typescript
  - p/javascript
  - p/nodejs
  - p/owasp-top-ten
  - p/r2c-security-audit

# Local project rules (none initially per D-13 — registry composition only).
# Add a `rules:` block here only after a follow-up phase identifies a
# NestJS-specific gap that the registry rulesets miss. Track 2 weeks of
# findings before considering custom rules (RESEARCH §OQ-4).
# rules:
#   - id: project-internal-pattern
#     ...
```

```
# Phase 999.17 — semgrep suppression baseline. Body intentionally empty.
# See .planning/phases/999.17-devsecops-shift-left-security-tooling/.

#
# DEFAULTS already excluded by Semgrep:
#   build/, vendor/, dist/, node_modules/, .venv/, test/
#
# RULES:
# 1. Add a glob only with a comment explaining WHY this path needs to skip
#    SAST scanning specifically (not just "code I don't care about").
# 2. Test fixtures with intentional vulnerabilities go here.
# 3. Generated code (proto-generated TypeScript, schema codegen) goes here.
# 4. Empty file = clean state — Semgrep's defaults are usually sufficient.
#
# To ignore a single finding inline, use:  // nosemgrep: rule-id-here
# (preferred — keeps the suppression with the suppressed code)
```

## Convention Note

The `rulesets:` field name in `.semgrep.yml` is **a project-internal YAML convention**, NOT a Semgrep-recognized schema key. Semgrep's CLI does NOT auto-load registry IDs from this field. Plan 07's `security:semgrep-diff` npm-script bridges the gap by parsing this file and emitting `--config <id>` flags. This is the explicit trade-off chosen per D-13 — single greppable, version-controlled source of truth at the cost of one parsing layer in the npm-script.

If a future Semgrep release introduces a native YAML field for registry composition, this file migrates to that schema and the npm-script's parsing logic disappears.

## Registry ID Verification (RESEARCH §A2)

The 5 registry IDs were committed to the YAML in the order specified by the plan. Live availability verification against `semgrep.dev/p/<id>` is intentionally NOT performed by this plan — that requires network egress to semgrep.dev and is the responsibility of either:

- Plan 07 (when the npm-script first runs Semgrep against the rulesets — a missing/404 ruleset will surface as a scanner error and a follow-up amendment ticket).
- DEVOPS-HANDOFF.md (Plan 09) which will document the verification step as part of CI onboarding.

The 5 chosen rulesets are well-established Semgrep registry packages (`p/typescript`, `p/javascript`, `p/nodejs`, `p/owasp-top-ten`, `p/r2c-security-audit`); they have been stable identifiers in the Semgrep registry for years per the RESEARCH document. If `p/r2c-security-audit` is later renamed/deprecated, the fix is a single-line YAML edit in this file (the source-of-truth principle paying off).
