## Summary

Phase 999.17 ships dev-side shift-left security tooling: gitleaks/semgrep/trivy
docker-wrapped invocations on git hooks, suppression baselines, a Renovate
config, a CI reference template, and a DevOps handoff document.

Cross-tier image-tag consistency (the only check the phase explicitly calls out
in the handoff) passes — the verification grep emits exactly the four expected
lines: `anchore/syft:v1.40`, `aquasec/trivy:0.50.4`, `returntocorp/semgrep:1.50`,
`zricethezav/gitleaks:v8.30.1`. Husky hooks honour the 1-line wrapper invariant
and dispatch through `pnpm run`. Suppression baselines are intentionally empty
with strong governance comments (rotate-first policy, expiry dates).

That said, two BLOCKERs render parts of the security posture silently
non-functional, and the gitleaks allowlist regex creates a measurable
secret-scan blind spot. None of these were caught by smoke-test "does it run"
verification because all three fail open: pnpm silently ignores an unknown
config key, gitleaks silently regex-matches too many paths, and the path-with-
spaces docker invocation only breaks on machines whose repo path contains a
space.

## Critical Issues

### CR-01: `pnpm-workspace.yaml` uses bogus `allowBuilds:` key — silently no-op, every install script runs

**File:** `pnpm-workspace.yaml:4-8`

**Issue:** The file declares
```yaml
allowBuilds:
  '@nestjs/core': true
  esbuild: false
  grpc-tools: true
  protobufjs: true
```
`allowBuilds` is **not a recognized pnpm settings key**. The documented keys for
controlling install-script execution (per pnpm.io/settings) are
`onlyBuiltDependencies`, `neverBuiltDependencies`, and
`onlyBuiltDependenciesFile`.

I reproduced the behaviour against `pnpm@11.0.0` (matching `package.json`
`"packageManager": "pnpm@11.0.0"`):

- With `allowBuilds: { esbuild: false, ... }` → pnpm prints **no warning**, runs
  esbuild's `postinstall` (which downloads a platform binary into
  `node_modules/@esbuild/linux-x64@0.24.0/`). Net effect: every `postinstall` /
  `install` / `preinstall` script in the entire dependency tree runs, including
  for packages the author intended to block (e.g. `esbuild: false`).
- With the documented `onlyBuiltDependencies: [...]` key → pnpm correctly emits
  `ERR_PNPM_IGNORED_BUILDS` and skips scripts for non-listed packages.

This is the single largest supply-chain attack surface in the JS ecosystem
(install-script execution on `pnpm install`). The intent of phase Plan 02
(per the commit message `chore(999.17-02): migrate build-script trust to
pnpm-workspace.yaml#allowBuilds`) was to assert positive control. The
implementation instead asserts no control. Result: identical posture to a repo
with no build-script governance at all, but with a misleading config that
suggests otherwise (the `'esbuild': false` entry is particularly worrying — a
reviewer reading the file would conclude esbuild's postinstall is blocked when
it is not).

**Fix:** Translate to the documented keys. Allowlist for the three packages
the project trusts:

```yaml
packages:
  - 'apps/*'
  - 'packages/*'
onlyBuiltDependencies:
  - '@nestjs/core'
  - grpc-tools
  - protobufjs
```

`esbuild: false` becomes implicit — `onlyBuiltDependencies` is an explicit
allowlist; anything not listed is denied. Verify with `pnpm install` after
deleting `node_modules` and `pnpm-lock.yaml`: pnpm should emit
`ERR_PNPM_IGNORED_BUILDS` listing every blocked package (esbuild and any
transitive dep with install scripts not on the allowlist).

If a future package legitimately needs to run install scripts, add it to the
list with a code-review-visible comment naming the package and reason.

### CR-02: gitleaks `[allowlist].paths` regex matches substrings — secret scan skips `documentation.ts`, `binary.ts`, anything with `doc`/`bin`/`svg`/`socket` in the path

**File:** `.gitleaks.toml:16-18`

**Issue:** The regex
```toml
paths = [
  '''(.*?)(jpg|gif|doc|pdf|bin|svg|socket)''',
]
```
is unanchored. gitleaks treats `paths` entries as Go regex applied to the full
file path. Because none of the alternatives are anchored to the extension end
(`\.(...)$`), the regex matches anywhere a substring like `doc`, `bin`, `svg`,
or `socket` appears in the path:

| Path | Should secret-scan? | Matches allowlist? |
| ---- | ------------------- | ------------------ |
| `apps/auth/src/documentation.ts` | yes (TypeScript source) | YES — `doc` substring |
| `apps/sender/src/binary-helper.ts` | yes (TypeScript source) | YES — `bin` substring |
| `apps/parser/icons/svg-loader.ts` | yes (TypeScript source) | YES — `svg` substring |
| `infra/docker/socket-config.yml` | yes (infra config) | YES — `socket` substring |
| `apps/notifier/src/podcast.ts` | yes | YES — `doc` substring inside `podcast` |

Verified with `grep -E '(.*?)(jpg\|gif\|doc\|pdf\|bin\|svg\|socket)'` against
each path above — all match.

This produces a real, exploitable blind spot: a developer who commits an AWS
key to `apps/auth/src/documentation.ts` would have it pass dev-side gitleaks
silently. The CI gitleaks run uses `gitleaks git --no-banner --redact`
(`.gitlab-ci-security.yml.example:33`) which inherits the **same**
`.gitleaks.toml` allowlist, so CI inherits the same blind spot.

Additionally, gitleaks' default config already excludes binary file types via
its built-in rules — the custom allowlist is largely redundant for its stated
intent (skipping image/binary files), and only adds the false-negative surface.

**Fix:** Anchor each alternative to the end of the path with an extension
boundary. Replace with:

```toml
paths = [
  '''\.(jpg|gif|pdf|bin|svg|socket)$''',
  # Note: removed 'doc' (matches inside 'documentation', 'docker', etc.).
  # If .doc files specifically need exclusion, add an explicit entry like
  # '''\.docx?$'''.
]
```

Or, given gitleaks' default config already covers binary file types, **delete
the custom allowlist entirely** and rely on the embedded default. The phase
RESEARCH already states (`.gitleaks.toml:5-6`) that "the default config is
comprehensive — only add rules that are unique to this codebase" — that
guidance applies equally to allowlists.

After the fix, re-run the matrix above; only `*.bin`, `*.svg`, etc. should
match.

## Warnings

### WR-01: `package.json` `security:secrets-staged` uses unquoted `$(pwd)` — fails silently on repo paths containing spaces

**File:** `package.json:27`

**Issue:** The script
```json
"security:secrets-staged": "docker run --rm -v $(pwd):/repo -w /repo zricethezav/gitleaks:v8.30.1 git --pre-commit --staged --no-banner",
```
passes `$(pwd)` **unquoted** to the shell. If the user's repo path contains a
space (e.g. `/Users/Some Name/projects/email-platform`), the shell word-splits
the docker `-v` argument into `-v /Users/Some` followed by a stray
`Name/projects/email-platform:/repo`, which docker interprets as
`docker run with image "with"`:

```
$ docker run --rm -v $(pwd):/repo -w /repo zricethezav/...
docker: Error response from daemon: pull access denied for with, repository does not exist...
```

The three sibling scripts under `scripts/security/*.sh` correctly use
`"$(pwd):/repo"` — quoted. The `package.json` invocation is the only
inconsistent one and is also the **most-frequently-executed** entry point
(every `git commit`).

This isn't theoretical: macOS user directories like `/Users/User Name/` and
many corporate-laptop "Documents/" subtrees contain spaces. A new contributor
on such a machine sees a confusing docker error from `git commit` and either
disables the hook (`--no-verify`) or files a confusing bug report.

**Fix:** Quote the substitution. JSON requires escaping the embedded double
quotes:

```json
"security:secrets-staged": "docker run --rm -v \"$(pwd):/repo\" -w /repo zricethezav/gitleaks:v8.30.1 git --pre-commit --staged --no-banner",
```

Verify by `cd "/tmp/path with spaces" && cd /tmp/path\ with\ spaces &&
git init && pnpm run security:secrets-staged` — should not error with
`pull access denied for with`.

### WR-02: Renovate `packageRules` ordering — `apps/**` patch updates lose monorepo grouping

**File:** `renovate.json:16-28`

**Issue:** The two `packageRules` entries can both match an apps-internal patch
update, and Renovate's last-match-wins semantics cause the second rule to
override the first:

```json
"packageRules": [
    {
        "matchFileNames": ["apps/**", "packages/**"],
        "groupName": "monorepo internal"
    },
    {
        "matchUpdateTypes": ["patch"],
        "groupName": "all patch updates"
    }
]
```

A patch update to a dependency referenced in `apps/auth/package.json` matches
**both** rules. Per Renovate docs, when multiple `packageRules` match, fields
merge top-to-bottom and later values win for scalar fields like `groupName`.
Result: the patch update gets `groupName: "all patch updates"`, **not**
`"monorepo internal"`. The intended monorepo grouping for `apps/**` and
`packages/**` is silently overridden for any patch-level update.

This isn't a security issue but it defeats the explicit intent expressed in
the rule descriptions ("Group monorepo internal packages").

**Fix:** Either (a) reorder so the more-specific `matchFileNames` rule is
last:

```json
"packageRules": [
    {
        "description": "Group all patch-level updates into a weekly PR",
        "matchUpdateTypes": ["patch"],
        "groupName": "all patch updates",
        "schedule": ["before 3am on Monday"]
    },
    {
        "description": "Group monorepo internal packages — apps/* and packages/*",
        "matchFileNames": ["apps/**", "packages/**"],
        "groupName": "monorepo internal"
    }
]
```

Or (b) add `matchUpdateTypes` exclusions to the patch rule to avoid the
overlap:

```json
{
    "matchUpdateTypes": ["patch"],
    "matchFileNames": ["!apps/**", "!packages/**"],
    "groupName": "all patch updates"
}
```

Decide which intent reflects the phase D-08 goal (group-by-location vs
batch-by-update-type) and document it inline.

### WR-03: `security:pre-push` couples `typecheck` into the security script chain — orthogonal concern, breaks fail-fast semantics

**File:** `package.json:30, 33`

**Issue:**
```json
"security:pre-push": "pnpm run security:typecheck && pnpm run security:env-parity && pnpm run security:semgrep-diff && pnpm run security:audit-if-lock-changed && pnpm run security:trivy-config-if-changed",
"security:typecheck": "turbo run typecheck",
```
`security:typecheck` is a misleading alias — TypeScript type-checking is a
correctness gate, not a security gate. Worse, the `&&` chain means a typecheck
failure (e.g. a developer pushing a WIP branch with intentional `any`
violations) **prevents** the secret scan, SCA audit, and IaC scan from
running. The security gates are then masked by an unrelated correctness
failure.

This also violates project skill `twelve-factor` (12-factor §VII Port
Binding / single-responsibility scripts) and `branching-patterns` (the script
namespace `security:*` should mean "security tooling," not "everything pre-
push").

**Fix:** Split into orthogonal namespaces and run both in pre-push:

```json
"check:typecheck": "turbo run typecheck",
"check:env-parity": "bash scripts/check-env-parity.sh",
"security:pre-push": "pnpm run security:semgrep-diff && pnpm run security:audit-if-lock-changed && pnpm run security:trivy-config-if-changed",
"prepush": "pnpm run check:typecheck && pnpm run check:env-parity && pnpm run security:pre-push"
```

Then `.husky/pre-push` becomes `pnpm run prepush`. Now a typecheck failure
still fails the push, but `security:pre-push` invoked directly (e.g. by CI or
a developer running it manually) only does security work.

If the phase explicitly decided to couple them (D-XX), document it inline at
the script with a `# couples typecheck because <reason>` comment. Currently no
such rationale is recorded.

## Info

### IN-01: gitleaks `--pre-commit --staged` redundancy

**File:** `package.json:27`, `DEVOPS-HANDOFF.md:275`

**Issue:** Both flags are passed to `gitleaks git`:
```
git --pre-commit --staged --no-banner
```
Per `gitleaks git --help` (gitleaks v8.30.1):
- `--pre-commit` — "scan using git diff"
- `--staged` — "scan staged commits (good for pre-commit)"

These are documented as alternative modes. Empirically I confirmed both forms
exit 0 on a clean repo and produce identical scan output, so passing both is
not destructive — but it is redundant and may behave unpredictably if a
future gitleaks release changes the precedence rule.

**Fix:** Pass only `--staged` (the canonical pre-commit form per the help
text). Update both `package.json` and the `DEVOPS-HANDOFF.md` server-hook
template.

### IN-02: dev-side gitleaks invocation lacks `--redact` — secrets echoed to terminal on detection

**File:** `package.json:27`

**Issue:** CI invocation (`.gitlab-ci-security.yml.example:33`) uses
`--redact`; server-side pre-receive (`DEVOPS-HANDOFF.md:275`) uses `--redact`;
dev-side `security:secrets-staged` does **not**. On a dev-machine detection,
the actual secret value is printed verbatim to terminal stdout. If the
developer copy-pastes the gitleaks output into a Slack channel, GitHub issue,
or pair-programming screenshare seeking help, the secret is leaked at a
second hop.

The phase RESEARCH already calls `--redact` "mandatory in CI" for exactly
this reason (DEVOPS-HANDOFF.md:316). The same risk class applies to dev
machines that share screens.

**Fix:** Add `--redact` to the dev invocation, accepting the modest UX cost
that the developer must look at the redacted-form match in their own working
tree:

```json
"security:secrets-staged": "docker run --rm -v \"$(pwd):/repo\" -w /repo zricethezav/gitleaks:v8.30.1 git --staged --no-banner --redact",
```

If the team prefers un-redacted dev-side output for diagnostic purposes,
document the rationale in CLAUDE.md / phase D-record so it's an explicit
acceptance, not an oversight.

### IN-04: `.semgrep.yml` uses non-standard `rulesets:` key — relies on awk parsing in `semgrep-diff.sh`

**File:** `.semgrep.yml:22-27`, `scripts/security/semgrep-diff.sh:31-33`

**Issue:** `rulesets:` is a project-invented YAML key (the file's preamble
acknowledges this: "the `rulesets:` field below is a PROJECT convention, NOT
a Semgrep-native YAML key"). Parsing relies on a fragile shell idiom:

```bash
grep -E '^\s+- p/' .semgrep.yml | awk '{print $2}'
```

This breaks if:
- A reviewer re-formats the file with `prettier --tab-width 4` — the `^\s+`
  still matches but reviewers may not realize the script depends on
  whitespace.
- A future entry uses a `r/` prefix (registry) or local rule path — the
  hard-coded `p/` prefix in the regex silently drops it.
- The list-item indentation collapses to 0 spaces (technically valid YAML for
  a top-level sequence, though unusual under a key) — `^\s+` no longer
  matches.

`.lintstagedrc.json` already includes `*.{yml,yaml}` in its `prettier --write`
glob; an automatic format pass that changes spacing would not break things in
the current implementation, but the brittleness is real.

**Fix:** Use a YAML-aware parser. Options:
- `yq` (already a common tool in containerized devs):
  ```bash
  yq '.rulesets[]' .semgrep.yml
  ```
- A short Python one-liner (Python is in scope per project tooling):
  ```bash
  python3 -c "import yaml,sys; print('\n'.join(yaml.safe_load(open('.semgrep.yml'))['rulesets']))"
  ```

Either parser is more robust to formatting changes and gives clearer errors
when the schema drifts. If keeping the grep+awk form, add a comment in the
script explaining the indentation contract and add a lint-staged hook that
verifies the regex still parses ≥1 ruleset post-prettier.

### IN-05: JSON indentation inconsistent across config files (`renovate.json` 4-space vs `package.json` / `.lintstagedrc.json` 2-space)

**File:** `renovate.json` (4-space), `package.json` / `.lintstagedrc.json` (2-space)

**Issue:** `renovate.json` uses 4-space indentation; the other two
prettier-managed JSON files use 2-space. `.lintstagedrc.json` line 3 globs
`*.{...,json,...}` for `prettier --write`, and the project's `.prettierrc`
defaults to `tabWidth: 2`. Next time `renovate.json` is touched and committed
through lint-staged, prettier will rewrite it to 2-space, producing a noisy
unrelated diff.

**Fix:** Run `prettier --write renovate.json` once now to normalize the
indentation pre-emptively, eliminating the future cosmetic diff. No semantic
change.
