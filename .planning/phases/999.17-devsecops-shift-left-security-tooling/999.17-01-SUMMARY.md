## Decisions Made

- **Picked `pnpm@11.0.0` (not a `>=11.x` range):** Corepack requires a concrete 3-part SemVer for signature-verified download. `npm view pnpm dist-tags` showed `latest-11: 11.0.0` as the only stable 11.x release on 2026-04-29; pre-releases (`11.0.0-rc.3..5`) explicitly excluded.
- **Preserved `pnpm.onlyBuiltDependencies` in package.json:** Plan §interfaces invariant ("Leave ALL other fields unchanged ... do NOT touch pnpm.onlyBuiltDependencies — Phase 999.7.x decision"). pnpm 11 auto-injects an `allowBuilds:` migration prompt into `pnpm-workspace.yaml` on every install — this commit reverts that auto-injection. The migration choice is surfaced at the Task 2 checkpoint for the user.
- **Lockfile not bumped to v10/v11 format:** pnpm 11 accepts the existing `lockfileVersion: '9.0'` format unchanged; no diff was produced. This is the safest possible upgrade path (zero lockfile churn → zero Turbo cache miss for content-addressed entries).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 — Blocking install side-effect] Reverted pnpm 11 auto-injection of `allowBuilds:` stubs into `pnpm-workspace.yaml`**

- **Found during:** Task 1, Step 6 (`pnpm install` post-bump)
- **Issue:** pnpm 11 deterministically rewrites `pnpm-workspace.yaml` on every install, appending a `allowBuilds:` block with literal `"set this to true or false"` placeholder strings for each package previously listed in `package.json#pnpm.onlyBuiltDependencies` (`@nestjs/core`, `esbuild`, `grpc-tools`, `protobufjs`). This is pnpm 11's prompt to migrate build-script approval from the deprecated `package.json` field to the new `pnpm-workspace.yaml` canonical path. The literal placeholder text indicates pnpm expects the user to make a decision.
- **Why this is a deviation:** Plan §interfaces explicitly says "Leave ALL other fields unchanged (notably `pnpm.onlyBuiltDependencies` — Phase 999.7.x decision; do NOT touch)." pnpm 11's auto-injection violates this invariant transitively (it touches the same trust list, just in a different file).
- **Fix:** Reverted `pnpm-workspace.yaml` to its pre-upgrade state via `git checkout -- pnpm-workspace.yaml`. Verified two consecutive `pnpm install` runs reproduce the auto-injection deterministically — confirmed it is not a one-off.
- **Files modified:** none (revert restores prior state); `package.json#pnpm.onlyBuiltDependencies` preserved as-is.
- **Verification:** `git diff pnpm-workspace.yaml` is empty after revert; final commit (`c3807cc`) modifies only `package.json`.
- **Committed in:** `c3807cc` (Task 1 commit; deviation documented in commit message).

**Open architectural decision (deferred to Task 2 checkpoint):** Migrate to `pnpm-workspace.yaml#allowBuilds` (pnpm 11 idiomatic, future-proof) OR keep `package.json#pnpm.onlyBuiltDependencies` (preserves Phase 999.7.x decision exactly, but pnpm 11 will keep prompting on every install)? Resolution should be a follow-up plan in Wave 2+ if user opts to migrate.
