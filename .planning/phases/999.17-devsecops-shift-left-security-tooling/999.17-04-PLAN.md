`.semgrep.yml` reference body (PATTERNS §`.semgrep.yml` lines 200-209 + D-13):

The Semgrep YAML config schema supports two styles:
- **Style A (canonical, semgrep.dev/docs/writing-rules/rule-syntax):** local rules under top-level `rules:` key (each entry is a rule definition). Cannot reference registry IDs from `rules:`.
- **Style B (extends/includes):** uses `include:` / `exclude:` for path filters; registry composition is done via CLI `--config` flags, not via YAML.

Per D-13 + RESEARCH §Pattern 4: registry composition lives at the CLI invocation level (passed by `security:semgrep-diff` npm-script in Plan 07). The `.semgrep.yml` file's role here is to act as the **canonical, version-controlled record** of which registry rulesets the project relies on (greppable, diffable, code-review surface), so that Plan 07's CLI invocation reads from this file (via shell parsing) OR mirrors it verbatim.

The simplest, most diff-friendly representation is a top-level `rules:` field listing the 5 registry IDs as YAML strings. Semgrep's CLI does NOT auto-load registry IDs from this field, so Plan 07's npm-script must read this file and map each ID to a `--config` flag. This is acceptable per D-13 (explicit composition).

Reference body:
```yaml
# Phase 999.17 — Semgrep ruleset composition baseline (D-13).
# See .planning/phases/999.17-devsecops-shift-left-security-tooling/.
#
# This file is the version-controlled source of truth for which Semgrep
# registry rulesets the project depends on. The actual scanner CLI
# invocation lives in package.json `security:semgrep-diff` (Plan 07) and
# MUST mirror this list as `--config p/<id>` flags.
#
# WHY explicit composition (not `--config=auto`):
#   - `auto` requires Semgrep cloud account login on every dev machine + CI runner
#   - `auto` ruleset can change upstream without a git diff in this repo
#   - explicit composition is reproducible, air-gappable, and code-reviewable

rulesets:
  - p/typescript
  - p/javascript
  - p/nodejs
  - p/owasp-top-ten
  - p/r2c-security-audit

# Local project rules (none initially per D-13 — registry composition only).
# Add a `rules:` block here only after a follow-up phase identifies a
# NestJS-specific gap that the registry rulesets miss.
# rules:
#   - id: project-internal-pattern
#     ...
```

NOTE: the `rulesets:` field name above is a project convention (NOT a Semgrep-recognized YAML key). Plan 07's npm-script parses this file via `grep -E '^\s+- p/' .semgrep.yml | awk '{print $2}'` and emits `--config <id>` flags. This keeps the source of truth in one greppable file. If a future Semgrep version adds a native YAML field for registry composition, this file can be migrated.

| Boundary | Description |
|----------|-------------|
| developer code diff ↔ Semgrep scanner (Docker-wrapped) | Scanner reads `.semgrep.yml` to determine ruleset corpus; reads `.semgrepignore` for path filters |
| developer-added suppression entry ↔ code reviewer | `.semgrepignore` glob silently excludes paths from SAST; `// nosemgrep:` inline silently excludes findings; review process is the gate |
