## Summary

This is a tooling/process phase: zero business logic, zero TypeScript-app changes, zero infra changes. Output is a set of repo-root files (configs + suppression baselines + 2 docs) and a `package.json` `security:*` script namespace, wired into 2 husky hooks. The hard part is honest scope discipline — three rejected categories of work (CI implementation, server-side enforcement, continuous scanning) keep showing up as "would be nice to add", and CONTEXT.md already locked them out.

The lean stack is well-understood and battle-tested in 2026: gitleaks v8.30+, Semgrep, Trivy `config`-mode, Syft (mention-only), husky 9, lint-staged 16, Renovate. Each tool ships as a single CLI binary and works identically on GitHub-hosted runners and self-hosted GitLab runners — which is the explicit driver behind D-04 ("CI-platform-portable").

**One critical environmental finding:** `pnpm audit` is currently broken on pnpm 9.x and 10.x because npm registry retired the legacy audit endpoints on 2026-04-15 (HTTP 410). The fix shipped in pnpm v11. Project is pinned to `pnpm@9.0.0` in `packageManager`. Three viable options: (a) bump project to pnpm v11, (b) replace `pnpm audit` in pre-push with `osv-scanner` (drop-in for `pnpm-lock.yaml`), (c) skip the SCA step in dev-side and rely on CI Trivy `fs` per D-06. **The planner MUST resolve this before the first plan executes** — see Open Question OQ-1.

**Primary recommendation:** Adopt the locked stack as-is, structure the phase around 8–10 small plans (config files first, hooks second, docs last), and treat the phase as a "scaffold + document" phase — no semantic transformations of the codebase. Validation is mostly file-existence + content-shape checks, not behavioral.

### Pattern 1: Hook = npm-script wrapper, logic in `package.json`

**What:** husky 9 hook files contain a single `pnpm run <script>` invocation. All shell logic lives in `package.json` `scripts.security:*`. This honors the "use package.json scripts" project rule and makes hook content trivially diffable.

**When to use:** Every hook in this phase.

**Example:**

```bash
# .husky/pre-commit  (the entire file)
pnpm run security:pre-commit
```

```bash
# .husky/pre-push  (the entire file)
pnpm run security:pre-push
```

```jsonc
// package.json scripts (sketch — planner refines naming/grouping)
{
  "scripts": {
    "security:pre-commit": "lint-staged && pnpm run security:secrets-staged",
    "security:pre-push": "pnpm run security:typecheck && pnpm run security:env-parity && pnpm run security:semgrep-diff && pnpm run security:audit-if-lock-changed && pnpm run security:trivy-config-if-changed",
    "security:secrets-staged": "gitleaks git --pre-commit --staged --no-banner",
    "security:secrets-full": "gitleaks git --no-banner",
    "security:semgrep-diff": "semgrep ci --baseline-commit origin/main --error",
    "security:semgrep-full": "semgrep scan --error",
    "security:env-parity": "bash scripts/check-env-parity.sh",
    "security:typecheck": "turbo run typecheck",
    "security:audit-if-lock-changed": "TBD per OQ-1 — see Open Questions",
```

### Pattern 2: lint-staged config — package.json inline

**What:** lint-staged config goes in `package.json` `"lint-staged"` field OR in `.lintstagedrc.json` at repo root. For a monorepo with a single ESLint+Prettier toolchain at root, **package.json inline is the simpler choice**; `.lintstagedrc.json` only adds value when per-package configs are needed.

**When to use:** Always for this phase (single root config covers all of `apps/*` + `packages/*`).

**Example:**

```jsonc
// package.json
{
  "lint-staged": {
    "*.{ts,tsx,js}": ["eslint --fix"],
    "*.{ts,tsx,js,json,md,yml,yaml}": ["prettier --write"]
  }
}
```

Note: lint-staged docs caution against passing filenames to `tsc` — TypeScript ignores `tsconfig.json` for files passed as args. **Do not put `tsc` in lint-staged.** Typecheck is on pre-push as full-graph, not per-file [CITED: github.com/lint-staged/lint-staged].

Source: lint-staged docs.

### Pattern 3: Gitleaks staged-only invocation (post-v8.19 syntax)

**What:** The `gitleaks protect --staged` syntax was deprecated in v8.19.0. Project is locking gitleaks at v8.30+. The current canonical pre-commit invocation is `gitleaks git --pre-commit --staged`.

**When to use:** In `pnpm run security:secrets-staged` (called from pre-commit).

**Example:**

```bash
# Old (deprecated post-v8.19):
gitleaks protect --staged --source=.

# New (canonical 2026):
gitleaks git --pre-commit --staged --no-banner
# Optional: --redact to mask matched secrets in stderr output
```

Exit codes: `0` = clean, `1` = leaks or error, `126` = unknown flag. Configurable via `--exit-code int` [CITED: github.com/gitleaks/gitleaks].

Source: gitleaks v8.19+ command translation gist [CITED: gist.github.com/zricethezav/b325bb93ebf41b9c0b0507acf12810d2].

### Pattern 4: Semgrep diff vs `origin/main` in pre-push

**What:** Semgrep supports incremental scans against a git baseline. The CLI flag is `--baseline-commit <hash>` (NOT `--baseline-ref`).

**When to use:** In `pnpm run security:semgrep-diff` (called from pre-push).

**Example:**

```bash
# Resolve origin/main HEAD to a commit hash, then pass to semgrep
BASELINE=$(git rev-parse origin/main)
semgrep scan --config p/typescript --config p/owasp-top-ten --config p/nodejs \
  --baseline-commit "$BASELINE" --error
```

Or via `semgrep ci`:
```bash
semgrep ci --baseline-commit "$BASELINE"
```

Note: `semgrep scan` does not exit-fail on findings unless `--error` is passed. `semgrep ci` exits non-zero on findings by default [CITED: semgrep.dev/docs/cli-reference]. Use `semgrep ci --error` for explicitness.

**Ruleset composition** — multiple `--config` flags compose. Recommended NestJS+TS+OWASP baseline:

```bash
semgrep scan \
  --config p/typescript \
  --config p/javascript \
  --config p/nodejs \
  --config p/owasp-top-ten \
  --config p/r2c-security-audit \
  --baseline-commit "$BASELINE" --error
```

**Overlap caveat:** `p/typescript`, `p/javascript`, `p/nodejs` overlap significantly. Semgrep's default ruleset (`--config=auto`, login required) and `p/default` already include OWASP + JS + TS + framework rules curated by Semgrep [CITED: semgrep.dev/blog/2025/]. **Recommendation for `.semgrep.yml`:** start with `--config=auto` (or its non-login equivalent `--config p/default` — verify in plan-phase) plus a NestJS-specific local rules file; let plan-phase decide whether to compose individual `p/*` IDs explicitly.

Source: semgrep CLI reference, semgrep blog deep dive on JS detection.

### Pattern 5: Conditional pre-push steps (lockfile / Dockerfile changed)

**What:** Some pre-push checks should only run when relevant files changed since `origin/main`. Implement as a guard clause + early-exit-0 in the npm-script, NOT as an if/elif chain inside one big script (per `branching-patterns` skill).

**When to use:**
- `security:audit-if-lock-changed` — only if `pnpm-lock.yaml` changed
- `security:trivy-config-if-changed` — only if any of `Dockerfile`, `infra/docker/**`, `infra/docker-compose*.yml` changed

**Example (npm-script form):**

```bash
# scripts/security/audit-if-lock-changed.sh  (or inlined as one-liner in package.json)
git diff --quiet origin/main -- pnpm-lock.yaml && exit 0
# Lockfile changed → run the audit
exec pnpm audit --audit-level high
```

```bash
# scripts/security/trivy-config-if-changed.sh
git diff --quiet origin/main -- 'Dockerfile' 'infra/docker/**' 'infra/docker-compose*.yml' && exit 0
exec trivy config --severity HIGH,CRITICAL --exit-code 1 .
```

These are guard clauses (early `exit 0`), not behavior branches. They satisfy `branching-patterns/SKILL.md`.

Source: project skill `branching-patterns`; trivy config CLI [CITED: trivy.dev/latest/docs/scanner/misconfiguration].

### Anti-Patterns to Avoid

- **Hook with shell logic inline** — Violates `feedback_use_package_scripts`. All logic in `package.json` `security:*` scripts; hooks are 1-line wrappers.
- **Putting `tsc` in lint-staged** — TypeScript ignores `tsconfig.json` for filenames passed as args. Typecheck is full-graph in pre-push, not per-file in lint-staged [CITED: lint-staged docs].
- **`gitleaks protect --staged`** — deprecated post-v8.19. Use `gitleaks git --pre-commit --staged`.
- **`--baseline-ref origin/main`** — wrong flag. Semgrep flag is `--baseline-commit <hash>`. Resolve `origin/main` to a hash first.
- **Branching on environment identity in scripts** — never `if [[ "$NODE_ENV" = "production" ]]; then ...`. Hooks run wherever git runs.
- **Hand-rolled secret regexes in `.gitleaks.toml`** — gitleaks default config covers ~150 high-quality patterns. Project `.gitleaks.toml` should `extends`/inherit and only add project-specific rules (none expected initially) and project allowlists (false-positive paths if any surface).
- **Trivy `fs` or `image` in pre-push** — needs ~1GB CVE feed download. Locked OUT by D-06. Pre-push uses `trivy config` only.
- **GitHub Actions `security.yml` in this phase** — locked OUT by D-05. CI work is DevOps.
- **Quality Gate enforcement code in repo** — D-07 says "thresholds documented in DEVOPS-HANDOFF.md, not enforced in dev-side code." Don't write a `quality-gate.sh` script in this phase.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Secret detection regexes | Custom regex collection | gitleaks default config + small project additions | Default config is curated by gitleaks maintainers and audited by community. Hand-rolled regexes miss base64 entropy heuristics, key-format quirks, multi-line tokens. |
| SAST rules for TS/Node | Custom AST walker, ESLint security plugin tree | Semgrep registry rulesets | Semgrep's pattern syntax is purpose-built. Maintaining a hand-rolled walker is full-time work for a security-research team. |
| Dockerfile/IaC misconfig detection | Custom `grep` for `USER root` etc. | Trivy `config` (which wraps OPA + Defsec rules) | Trivy ships ~200+ checks (USER root, latest tag, exposed secrets, missing healthcheck, AVD-DS-NNNN catalog). Reproducing these is months of work. |
| Per-finding-type CI gate logic | Custom YAML gating + parsing | Tool-native exit codes + `if exit-code != 0` in shell | Each scanner already exits 0/1. Wrap in shell `&&` chains, let CI runner aggregate. No third-party "Quality Gate service" needed. |
| Auto-dependency-update bot | Cron + custom PR-creator | Renovate (or Dependabot — but Dependabot doesn't survive GitLab migration) | Bot maintenance is non-trivial — group rules, automerge windows, lock-file repair. Renovate is industry standard. |
| Server-side push enforcement | Custom Git server hook | GitLab `pre-receive.d/` directory + gitleaks invocation (post-migration) | Use GitLab's hook directory convention, not bespoke wiring. |
| SBOM generation | Custom dependency walker | Syft (CycloneDX or SPDX output) | CycloneDX is the OWASP standard; SPDX is the Linux Foundation standard. Both supported by Syft. Hand-rolling is wasted work. |
| `.env` parity check | Already exists — `scripts/check-env-parity.sh` | **Wrap the existing script.** Do NOT rewrite. | D-10 explicit. Phase 24.1 + 999.1.9 W10 already shipped this with all 5 checks. |

**Key insight:** This phase composes existing tools. Custom code is a smell.

## Common Pitfalls

### Pitfall 1: gitleaks deprecated command syntax in tutorials

**What goes wrong:** Most online tutorials still show `gitleaks protect --staged` — deprecated in v8.19.0 (June 2024). Using it works on v8.30 (commands are hidden, not removed) but emits a deprecation warning and may break in v9.

**Why it happens:** Doc lag. Search results returned mostly stale 2022–2023 articles.

**How to avoid:** Use `gitleaks git --pre-commit --staged` everywhere. Add a comment in `package.json` explaining the migration.

**Warning signs:** Stderr containing `WARN: this command is deprecated`. CI failure if a future version removes the alias.

### Pitfall 2: lint-staged passing TS file paths to `tsc`

**What goes wrong:** `tsc file1.ts file2.ts` mode IGNORES `tsconfig.json`. Pre-commit "passes" but typecheck silently regresses.

**Why it happens:** Common copy-paste bug from non-monorepo tutorials.

**How to avoid:** Never put `tsc` in lint-staged. Typecheck is `pnpm turbo run typecheck` in pre-push (full graph).

**Warning signs:** Pre-commit completes in <1s on TS changes — too fast to have run a real type check.

### Pitfall 3: `pnpm audit` HTTP 410 on pnpm 9.x and 10.x (April 2026 breakage)

**What goes wrong:** npm registry retired the legacy audit endpoints on 2026-04-15. pnpm 9.x and 10.x query `/-/npm/v1/security/audits` and `/audits/quick` — both return HTTP 410 Gone. `pnpm audit` exits non-zero in pre-push, blocking every push.

**Why it happens:** Project pinned to `pnpm@9.0.0` in `package.json` `packageManager` field. The fix shipped in pnpm v11 (April 15, 2026) using the new `/-/npm/v1/security/advisories/bulk` endpoint [VERIFIED: github.com/pnpm/pnpm PR #11268; github.com/pnpm/pnpm/issues/11265]. v9 and v10 are not backported.

**How to avoid:** **MUST be resolved by plan-phase.** Three options:
1. Bump project to `pnpm@11.x` in `packageManager` (fixes audit; carries semver-major migration risk — `auditConfig.ignoreCves` renamed to `ignoreGhsas`, etc.)
2. Replace `pnpm audit` with `osv-scanner -L pnpm-lock.yaml` in pre-push (works against the same lockfile; no registry dependency).
3. Drop the SCA step from pre-push entirely; rely on CI Trivy `fs` per D-06 (per-CONTEXT.md, the actual SCA gate is CI anyway).

**Warning signs:** Pre-push fails with `HTTP 410 Gone` from `pnpm audit` after the first lock change.

**Source:** [VERIFIED: github.com/pnpm/pnpm/issues/11265]; [CITED: github.com/orgs/community/discussions/192768] (npm Quick Audit retirement).

### Pitfall 4: Semgrep `--baseline-commit` requires resolvable hash

**What goes wrong:** `semgrep scan --baseline-commit origin/main` MAY work or MAY error depending on Semgrep version — the flag wants a hash, not a ref. Also: "Aborts run if not currently in a git directory, there are unstaged changes, or given baseline hash doesn't exist" [CITED: semgrep.dev/docs/cli-reference]. Pre-push hook runs after staged commits but before push — so unstaged changes shouldn't be present, but local-only branches without `origin/main` will fail.

**Why it happens:** Fresh clones, branches behind origin, missing `git fetch origin main`.

**How to avoid:** In `security:semgrep-diff`, run `git fetch origin main --depth=1` first, then `BASELINE=$(git rev-parse origin/main)`, then pass `$BASELINE` to `--baseline-commit`. Document this in the hook script.

**Warning signs:** Pre-push fails with `unknown revision 'origin/main'` or `baseline hash doesn't exist`.

### Pitfall 5: lint-staged not finding the right ESLint config in pnpm monorepo

**What goes wrong:** lint-staged 16 picks the closest config to each staged file. With `apps/*/.eslintrc.js` overrides existing, behavior may diverge from the root `pnpm run lint`.

**Why it happens:** Monorepos with per-package ESLint overrides.

**How to avoid:** Project has a single `.eslintrc.js` at root [VERIFIED: ls .eslintrc.js]. Confirm during planning that no `apps/*/.eslintrc.*` exists. If any do, add them to plan-phase's discovery list.

**Warning signs:** lint-staged reports different errors than `pnpm run lint`.

### Pitfall 6: husky 9 hook file format differences from husky <9

**What goes wrong:** husky 9 dropped the `#!/bin/sh\n. "$(dirname -- "$0")/_/husky.sh"` boilerplate at the top of hook files. Hooks created with husky 8 syntax will run TWICE in husky 9 (the boilerplate calls husky again).

**Why it happens:** Stale tutorials, leftover hook files from an older husky version.

**How to avoid:** Hook files in husky 9 are plain shell scripts, no shebang needed at top, no husky.sh source line. Just `pnpm run security:pre-commit`.

**Warning signs:** Same hook executes twice. Pre-commit takes 2x expected time.

### Pitfall 7: Renovate `config:base` deprecation noise

**What goes wrong:** Using `"extends": ["config:base"]` works but produces deprecation warnings on Renovate v36+. Project should use `config:recommended` going forward.

**Why it happens:** Doc lag — older tutorials show `config:base`.

**How to avoid:** Use `config:recommended` from the start.

**Warning signs:** Renovate dashboard shows deprecation warnings on first run.

### Pitfall 8: GitLab Free tier vs Premium SAST features confusion

**What goes wrong:** When writing `.gitlab-ci-security.yml.example` and DEVOPS-HANDOFF.md, easy to recommend GitLab's built-in `Security/SAST.gitlab-ci.yml` template — but GitLab Free gets only basic JSON reports, not MR integration / vulnerability management dashboards (Premium features) [CITED: docs.gitlab.com/user/application_security/sast/].

**Why it happens:** GitLab marketing pages don't always distinguish Free from Premium.

**How to avoid:** In DEVOPS-HANDOFF.md, document both paths:
1. **Plain CLI in `.gitlab-ci-security.yml.example`** (recommended) — gitleaks/Semgrep/Trivy as plain shell jobs. Fully portable, free, works on Free tier.
2. GitLab built-in templates — note as alternative. State explicitly: MR integration is Premium.

**Warning signs:** Deploying `.gitlab-ci.yml` based on tutorial → realizing dashboards are Premium-only after migration.

### GitLab pre-receive hook (server-side, post-migration — DEVOPS-HANDOFF.md content)

```bash
#!/usr/bin/env bash
# /var/opt/gitlab/gitaly/custom_hooks/pre-receive.d/10-gitleaks
# (or /opt/gitlab/embedded/service/gitlab-shell/hooks/pre-receive.d/10-gitleaks)

done
```

## Open Questions

1. **OQ-1: `pnpm audit` is broken on pnpm 9.x. What replaces it in pre-push?**
   - What we know: pnpm 9.0.0 is pinned in `package.json` `packageManager`. `pnpm audit` exits 410 since 2026-04-15. Fix only in pnpm v11.
   - What's unclear: which of three options the user wants:
     - **(A) Bump to `pnpm@11.x`** — fixes audit; carries semver-major migration risk (lockfile re-resolution, `auditConfig.ignoreCves` → `ignoreGhsas`, possible Turbo cache bust).
     - **(B) Replace with `osv-scanner -L pnpm-lock.yaml`** in pre-push — drop-in for pnpm-lock format; no registry dependency; one new CLI binary in the dev install list.
     - **(C) Drop SCA from pre-push entirely** — rely on CI Trivy `fs` per D-06. Pre-push retains conditional `audit-if-lock-changed` step but it's a no-op or removed.
   - Recommendation: **Option B (osv-scanner)** for this phase. Reasoning: (i) cheapest delta — one new binary, one one-liner npm-script; (ii) keeps developer-side SCA feedback alive; (iii) avoids forcing a pnpm major bump as a side-effect of a security tooling phase; (iv) project skill `architect-skeptic` favors the smallest reversible change. Plan-phase should confirm with user before locking.

2. **OQ-2: lint-staged config location — `package.json` inline vs `.lintstagedrc.json`?**
   - What we know: both supported by lint-staged 16. Both work in pnpm monorepos.
   - What's unclear: project preference.
   - Recommendation: **package.json inline** — fewer files, config co-located with scripts. Defer decision to planner if user has aesthetic preference.

3. **OQ-3: `.semgrep.yml` content — `--config=auto` (login required) vs explicit composition (no login)?**
   - What we know: `auto` requires Semgrep account login on first run. Explicit composition (`--config p/typescript --config p/owasp-top-ten ...`) does not.
   - What's unclear: whether the team is OK with a Semgrep account on each developer machine + each CI runner.
   - Recommendation: **explicit composition**. Avoids account dependency, makes the ruleset diff-able in git, fully air-gappable. Document `auto` as an opt-in in DEVOPS-HANDOFF.md.

4. **OQ-4: NestJS-specific custom Semgrep rules — defer or include in this phase?**
   - What we know: Semgrep's 2025+ default ruleset includes Express/NestJS/Hapi/Koa-aware rules per [VERIFIED: semgrep.dev/blog/2025/]. No urgent gap.
   - What's unclear: whether project has NestJS-specific patterns the registry rules wouldn't catch (e.g., custom DI tokens, controller injection patterns from this codebase's hexagonal layering).
   - Recommendation: **defer**. Ship `.semgrep.yml` with registry composition only in this phase. Track findings for 2 weeks of CI runs. If gaps surface, follow-up phase adds `rules/nestjs-internal.yml`. Plan-phase confirms.

5. **OQ-5: Where do `DEVOPS-HANDOFF.md` and `.gitlab-ci-security.yml.example` live — repo root or `docs/devops/`?**
   - What we know: both are conventional locations.
   - Recommendation: **repo root** for visibility (CONTEXT.md says repo root). Plan-phase can override.

6. **OQ-6: `package.json` `packageManager: "pnpm@9.0.0"` exact-pin vs range?**
   - What we know: exact pin "9.0.0" is unusual for `packageManager` (typically a stricter SHA-style). Project lock chosen by Phase 999.7.x onwards.
   - What's unclear: whether the security tooling phase should also pin gitleaks/Semgrep/Trivy versions (in DEVOPS-HANDOFF.md, since they're not npm packages).
   - Recommendation: **pin minimum versions** in DEVOPS-HANDOFF.md install section (e.g., gitleaks ≥ 8.30, Semgrep ≥ 1.50, Trivy ≥ 0.50, Syft ≥ 1.40). Don't pin exact — security tools update frequently with CVE-feed improvements.
