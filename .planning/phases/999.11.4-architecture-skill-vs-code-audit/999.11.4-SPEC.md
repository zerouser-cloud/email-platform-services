# Phase 999.11.4: architecture-skill-vs-code audit — Specification

**Created:** 2026-04-22
**Ambiguity score:** 0.17 (gate: ≤ 0.20)
**Requirements:** 7 locked

## Goal

Audit all 10 working project skills against current code state via Heavy verify-against-reality methodology with Directional Authority Taxonomy, producing `999.11.4-AUDIT.md` (per-skill sections + summary table) and `999.11.4-SOLUTIONS.md` (1-3 ranked remediation options per finding) for user-approved sub-phase creation outside this phase.

## Background

Current state — synthesized from scout (2026-04-22):

- **11 custom project skills exist in `.agents/skills/`** — 10 working with valid `SKILL.md` frontmatter (`name:` + `description:`); 1 broken (`error-handling` has only `references/`, no `SKILL.md`).
- **11 registered as Claude Code skills via symlinks** in `.claude/skills/` (commit `49a65d3` 2026-04-22).
- **Recent architectural phases introduced new patterns** that may have drifted skill-vs-code alignment:
  - 999.7.x: `defineGrpcClient()` factory + composition (`GrpcCaller`) + `Promisified<T>` Proxy
  - 999.1.8: `loadConfig` relocated to `packages/foundation/src/external/config/` + `createConfigModule({schema, token, narrowPorts})` factory symmetric to gRPC
  - 999.1.9: per-app config structure `packages/config/src/apps/{name}/` mirroring `/apps/{name}/`; `{SVC}_GRPC_PORT` env var; loadConfig signature simplification
  - 999.10 / 999.10.1: Controller → Service → UseCase 3-layer stack + runtime-identity field naming
  - 999.11.1: `{SVC}_CONFIG` Symbol pattern + `@nestjs/config` full removal + drizzle.config env-hygiene
  - 999.11.2: canonical `infrastructure/{inbound,outbound,bootstrap}/` tree across all 6 services
  - 999.11.3: refreshed **only** `nestjs-hexagonal-mapping` skill (1 of 11) — Plan 09 of 999.11.2 had updated only `infrastructure-client-layering`
- **Gap:** other 10 skills haven't been systematically audited against post-999.x code state. Drift likely in **both** directions:
  - **DESCRIPTIVE skills** (architectural) may be stale — code evolved past skill examples
  - **AUTHORITATIVE skills** (rules) may have code violations — accidental drift from skill rules

The phase audits all 10 working skills with explicit Directional Authority Taxonomy to prevent the catastrophic anti-pattern of "code has X, skill doesn't, add to skill" when X is actually a violation that should be removed from code.

## Requirements

1. **Per-skill audit coverage**: Every working skill in `.agents/skills/` (10 total, `error-handling` excluded) audited against current code.
   - Current: 1 skill (`nestjs-hexagonal-mapping`) refreshed in Phase 999.11.3; other 10 not systematically audited
   - Target: All 10 working skills have a corresponding section in AUDIT.md (sections MAY be empty if skill aligns — body becomes "no findings, skill aligned with code")
   - Acceptance: `AUDIT.md` contains exactly 10 `### Skill: {name}` sections — one each for: `branching-patterns`, `clean-ddd-hexagonal`, `composition-over-inheritance`, `env-schema`, `gsd-flow-guard`, `infrastructure-client-layering`, `infrastructure-guard`, `nestjs-hexagonal-mapping`, `no-magic-values`, `runtime-smoke-verification`, `twelve-factor`

2. **Directional Authority Taxonomy enforced per finding**: Every finding tagged with direction class.
   - Current: No documented mechanism; historical informal practice mixed code-vs-skill drift judgments
   - Target: Each finding has explicit direction tag from set `{AUTHORITATIVE, DESCRIPTIVE, HYBRID}`; pre-classification of 10 skills locked in this SPEC's `## Pre-Classification` table and used as starting point
   - Acceptance: 0 findings without direction tag in AUDIT.md; SPEC.md contains pre-classification table covering all 10 skills

3. **Verify-against-reality discipline (Heavy depth)**: Every claim backed by evidence.
   - Current: 999.11.3 precedent established this for one skill; no codified rule for general application
   - Target: Every finding includes grep output excerpt or `file:line` reference as evidence — verifier can re-run cited grep/file-read and reproduce the claim
   - Acceptance: 0 findings without evidence in AUDIT.md

4. **Phase-decision cross-references for DESCRIPTIVE/HYBRID findings**: Sanctioned-vs-ad-hoc distinction.
   - Current: No codified mechanism; informal review judgments
   - Target: For DESCRIPTIVE/HYBRID findings, cite the originating phase decision (D-XX in CONTEXT/SUMMARY of source phase); patterns appearing in code without sanctioned phase-decision get explicit `ad-hoc drift` flag (distinct from `skill stale`)
   - Acceptance: Every DESCRIPTIVE/HYBRID finding either has a phase-decision cross-ref OR is flagged `ad-hoc drift`

5. **Per-finding remediation type assignment**: SOLUTIONS knows what to propose.
   - Current: Phase 999.11.3 had implicit `refresh-skill` only; Phase 999.1 SOLUTIONS.md had multi-option per-finding format
   - Target: Each finding tagged remediation type from `{refresh-skill, fix-code, leave-as-is}`; SOLUTIONS.md provides 1-3 concrete remediation options per finding with trade-offs and recommended pick (Phase 999.1 precedent)
   - Acceptance: 0 findings without remediation type tag; SOLUTIONS.md has at least one remediation entry per AUDIT.md finding

6. **AUDIT.md structure: per-skill sections + summary table**
   - Current: No standard structure for our project's audit deliverables
   - Target: AUDIT.md begins with `## Summary` table (`skill | finding_count | direction_distribution`) followed by 10 `### Skill: {name}` sections with finding bodies
   - Acceptance: AUDIT.md has both `## Summary` table at top AND `### Skill: {name}` sections for each of 10 skills; reader can scan summary then drill into specific skills

7. **SOLUTIONS.md format follows Phase 999.1 precedent**
   - Current: Phase 999.1 used precedent — 2-4 options per finding with trade-offs and recommended pick; user approves outside phase and creates sub-phases via `/gsd:insert-phase`
   - Target: 999.11.4-SOLUTIONS.md follows the same pattern; phase 999.11.4 closes after AUDIT + SOLUTIONS written; sub-phase creation (999.11.4.1, 999.11.4.2, ...) happens in separate user-driven workflow outside this phase
   - Acceptance: SOLUTIONS.md contains 1-3 ranked options per finding with trade-offs and recommended pick; phase SUMMARY.md references SOLUTIONS.md as next-action input

## Boundaries

**In scope:**
- Audit of 10 working skills (named explicitly in Requirement 1)
- Writing `999.11.4-AUDIT.md` per structure in Requirement 6
- Writing `999.11.4-SOLUTIONS.md` per structure in Requirement 7
- Pre-classification of 10 skills with directional authority tags in this SPEC (`## Pre-Classification` section below)
- Methodology lock for auditor: Heavy depth + Directional Authority Taxonomy + verify-against-reality
- `error-handling` skill: documented in AUDIT.md summary as **"skipped — no SKILL.md, scheduled for dedicated error-handling phase"** (1-line note, no full section)

**Out of scope:**
- Implementing remediation (skill refreshes, code fixes) — deferred to user-approved sub-phases (999.11.4.1, .2, ...) per Phase 999.1 precedent — keeps audit phase audit-only and atomic
- Creating new skills for code patterns currently without corresponding skill — flagged as findings but skill-creation is a separate future phase (would warrant its own design dialogue)
- `error-handling` SKILL.md authoring — separate dedicated phase when project reaches error-handling design point (user explicitly deferred)
- CLAUDE.md audit as primary target — only `.agents/skills/{name}/SKILL.md` and its `references/*.md` files in scope; CLAUDE.md may be touched as side-effect when skill cross-refs change but is not the audit subject (CLAUDE.md drift is its own future audit)
- Built-in GSD skills (`gsd:*` from `get-shit-done/`) and Claude Code default skills (`update-config`, `simplify`, etc.) — those are GSD-runtime / Claude Code framework skills, not project skills

## Constraints

- **Heavy depth** is mandatory — every finding requires grep/Read evidence (precedent: Phase 999.11.3)
- **999.11.3 `nestjs-hexagonal-mapping` skill IS in scope** and re-audited — even though just refreshed, drift since may have re-introduced gaps (e.g., 999.1.9 services-first config layout, naming conventions interaction)
- **Pre-classification table** in this SPEC is the locked starting point; auditor MAY recommend reclassification of a skill in AUDIT.md (with rationale) but cannot silently apply a different direction
- **SOLUTIONS.md follows Phase 999.1 precedent** — 1-3 ranked options per finding with trade-offs and recommended pick
- **Audit subject is `.agents/skills/{name}/SKILL.md` + `references/*.md` files** only; not CLAUDE.md, not source code as primary
