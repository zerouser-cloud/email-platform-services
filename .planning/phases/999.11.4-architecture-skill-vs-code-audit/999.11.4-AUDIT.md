### F-02 (DESCRIPTIVE, icl): §"Redis / S3 / DB+ORM (single-instance)" conflates Redis/DB (true single-instance) with S3 (multi-instance per-bucket) — skill claim "`@Inject(S3_CLIENT)` directly from foundation" is contradicted by sanctioned Phase 22.1 subpath-export boundary (S3_CLIENT is internal-only) + 22.4 per-bucket module pattern

- **ID:** icl-F-02
- **Direction:** DESCRIPTIVE
- **Skill:** `infrastructure-client-layering`
- **Claim:** `SKILL.md` lines 193-198 group `Redis / S3 / DB+ORM` into a single "single-instance" bucket: "**Foundation:** module + constants exported directly (`CACHE_SERVICE`, `S3_CLIENT`, `DRIZZLE`). **Apps:** `imports: [CacheModule.forRootAsync(...)]`, then `@Inject(CACHE_SERVICE)` directly — no per-app constants." Reality for S3 since sanctioned **22.1 D-01..D-20** is different:
  1. `S3_CLIENT` lives in `packages/foundation/src/internal/storage/storage.constants.ts` — under the **`internal`** subpath export, blocked for apps by ESLint rule added in 22.1 D-14 (see `.eslintrc.js no-restricted-imports`).
  2. `S3CoreModule` had `@Global()` removed in 22.1 D-01 — explicit imports are required.
  3. Per-bucket modules (`PrivateStorageModule`, `SharedNamespaceModule` — the latter renamed from `ReportsStorageModule` in 22.5 D-19) are the consumer API. Each wraps `S3CoreModule` internally (22.1 D-03/D-04) and exposes a typed port (`PrivateStoragePort`, `NamespacedStoragePort` — 22.4 D-09) — NEVER the raw `S3_CLIENT`.
  4. Apps DO have per-app constants: per-service bucket tokens (e.g., `PARSER_STORAGE`, `AUDIENCE_STORAGE`) + per-namespace tokens (e.g., `REPORTS_NAMESPACE` via `SharedNamespaceModule.forNamespace({ namespace: 'reports', contentType: 'application/pdf' })`) — 22.4 D-07/D-12.
  
  So for S3 specifically: catalog=none (correct in skill), foundation has internal `S3_CLIENT` + public typed-port abstractions, apps MUST use per-bucket wrappers + per-app tokens. The "no per-app constants" clause in the skill is **only true for Cache and DB** — S3 is a multi-instance-per-service case masquerading as single-instance because "one S3 client, many buckets" is a subtle distinction the skill's taxonomy flattens. This is a **classification error** in the skill's Decision Tree: the "Step 1: How many instances per service?" question needs a sub-discriminator "(but for storage: how many buckets/namespaces?)".
