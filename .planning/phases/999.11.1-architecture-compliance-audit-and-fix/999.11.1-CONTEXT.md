- **D-07:** **drizzle.config.ts fix** — в каждом из 4 файлов (`apps/{auth,audience,parser,sender}/drizzle.config.ts`) заменить прямой `process.env.DATABASE_URL!` на Zod-validated через существующую `DatabaseSchema`:

  import { DatabaseSchema } from '@email-platform/config';
  import { defineConfig } from 'drizzle-kit';

  const env = DatabaseSchema.parse(process.env);

  export default defineConfig({
    dialect: 'postgresql',
    schema: './src/infrastructure/persistence/schema/index.ts',

### Canonical Config Access Contract (runtime — absorbs 999.2)

- **D-08:** **Per-service `{SVC}_CONFIG` Symbol** (A2 pattern — канон gRPC-стиля):
  - `apps/{svc}/src/{svc}.constants.ts` экспортирует `export const {SVC}_CONFIG = Symbol('{SVC}_CONFIG')` рядом с business port tokens (канон — все Symbol-токены в root constants)
  - `apps/{svc}/src/infrastructure/config/{svc}-config.provider.ts` определяет provider:
    ```typescript
    export const {svc}ConfigProvider = {
      provide: {SVC}_CONFIG,
      useValue: loadConfig({Svc}EnvSchema),
    };
    ```
  - `apps/{svc}/src/{svc}.module.ts` регистрирует provider в root composition
  - `{Svc}EnvSchema` уже живёт в `apps/{svc}/src/infrastructure/config/{svc}-env.schema.ts` — не трогаем расположение
  - Typed inject: `@Inject(SENDER_CONFIG) private readonly config: SenderEnv` — полная типизация без `!` и `as` касты

- **D-09:** **Layer injection rule** (где inject'ить `{SVC}_CONFIG`):
  - ✅ `infrastructure/**` (controllers, adapters, clients, repositories) — адаптеры знают про environment
  - ✅ Module factories (`useFactory`, `forRootAsync`) — composition root
  - ✅ `application/services/**` (implements inbound port) — service это **seam** между env и business logic, оркестрирует use-cases
  - 🚫 `application/use-cases/**` — use-cases получают env-values как **method args** (`execute(cmd, opts)`) от parent service. НЕ через `@Inject`.
  - 🚫 `domain/**` — no framework (уже enforced через ESLint Override 8)
  - **Обоснование:** use-case чист и тестируем (`new UseCase(mockSender).execute(cmd, { timeout: 5000 })` без config fixtures), переиспользуется в разных env-контекстах, signature = полный контракт.
  - ESLint enforcement для use-cases — follow-up (можно добавить override в `.eslintrc.js`), не блокирует фазу.

- **D-10:** **Foundation narrow config interfaces** (service-agnostic):
  - Foundation объявляет: `CacheConfig`, `PersistenceConfig`, `StorageConfig` и т.д. — только то, что реально нужно конкретному инфра-модулю
  - Apps делают slice из `{SVC}_CONFIG` в foundation shape через `useFactory`:
    ```typescript
    {
      provide: CACHE_CONFIG_PORT,
      useFactory: (c: SenderEnv): CacheConfig => ({ REDIS_URL: c.REDIS_URL }),
      inject: [SENDER_CONFIG],
    }
    ```
  - Foundation инжектит `CACHE_CONFIG_PORT` (узкий интерфейс), **не знает** про `SenderEnv`/`AuthEnv`
  - Identity (namespace) остаётся в `forRoot({ namespace })` opts — это идентичность сервиса, не env
  - Это **Approach C применённый на границе foundation↔apps** — reinforces infrastructure-client-layering skill (Identity / Mechanism / Assembly split)

- **D-11:** **Full replace `@nestjs/config`.** Убрать `@nestjs/config` из deps всех apps и foundation. Third-party NestJS модули (`ThrottlerModule.forRootAsync`, `TerminusModule.forRootAsync` и др.) мигрируют на `inject: [{SVC}_CONFIG]`. `loadConfig()` в `packages/config/` уже использует только `zod` + `process.env` — `@nestjs/config` для неё не нужен. Результат: один config-pattern в кодбазе, нулевой legacy.

- **D-12:** **Migrate все 14+ callsites** (999.2 absorbed):
  - `apps/gateway/src/infrastructure/controllers/rest/health.controller.ts` (после D-05 relocation) — убрать `SERVICE.auth.envKeys.GRPC_URL!` и `?? ''` паттерны
  - `apps/gateway/src/infrastructure/throttle/throttle.module.ts` (после D-06) — `configService.get<number>('RATE_LIMIT_BURST_TTL')!` → `config.RATE_LIMIT_BURST_TTL` (типизировано из `GatewayEnv`)
  - Все 6 `main.ts` — `loadConfig(XxxEnvSchema) as XxxEnv` cast остаётся (его решает 999.1 — TopologySchema refactor — вне нашего scope). Но регистрация `{SVC}_CONFIG` provider в main или в module — plan-phase решит.
  - `packages/foundation/src/cache/cache.providers.ts` — `config.get<string>('REDIS_URL')!` → narrow `CacheConfig.REDIS_URL` pattern (D-10)
  - `packages/foundation/src/persistence/persistence.providers.ts` — аналогично через `PersistenceConfig`
  - `packages/foundation/src/external/grpc/clients/*-client.module.ts` (все 5 client modules: auth / audience / parser / sender / notifier) — migrate все 14+ occurrences (explicitly left out of Phase 24.1 per orchestrator memo, теперь подхватываем)

<specifics>
## Specific Ideas

- **User phrasing (2026-04-20):** "каждый сервис берёт заготовки и мастерит себе клиенты, конфиги" — Canonical Config Access Contract **буквально** это и есть. A2 pattern воспроизводит gRPC-стиль для config.
- **User refinement of D1:** "может конфиги прокидывать на каждый сервис с самого верха в модуль, что бы они были доступны везде в слоях nest, но глубже в useCase уже прокидывать в конструктор" — уточнили в **method arg** (не constructor, так как constructor — DI seam для портов через NestJS). Use-case получает env-values как method args от parent service.
- **Symmetry with gRPC (Phase 999.7.x):** Config Access Contract — не новый паттерн, а применение canonical gRPC-стиля (Identity / Mechanism / Assembly) к config domain. Это следует зафиксировать в skill'е (новом или в `infrastructure-client-layering`). Последующие фазы (999.12 Redis, 999.13 RabbitMQ, 999.14 S3) используют тот же контур.
- **999.2 absorbtion rationale:** "не тронуть одни файлы дважды" + approach уже выбран в 999.11.1, разделение создавало бы координационный overhead без value.
