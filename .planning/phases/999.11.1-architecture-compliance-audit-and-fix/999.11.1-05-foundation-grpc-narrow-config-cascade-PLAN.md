Migrate `packages/foundation/src/external/grpc/clients/define-grpc-client.ts` — the gRPC client factory — from `inject: [ConfigService]` to `inject: [GRPC_CLIENT_CONFIG_PORT]` with a narrow `GrpcClientConfig` interface. All 5 per-upstream client modules (auth/sender/parser/audience/notifier) benefit mechanically — they don't change (they invoke `defineGrpcClient({ service, clientToken })`; migration is foundation-internal). DELETE the obsolete `grpc-client.module.ts` (zero consumers — pre-999.7 legacy per DC-01).

Addresses: **D-10** (foundation gRPC narrow config), **D-12** callsites IC-04 (5 callsites in define-grpc-client.ts) + IC-05 (obsolete module), **DC-01** (dead-code deletion), **PT-11** (don't confuse grpc-client.module.ts with define-grpc-client.ts).

**Complexity:** Unlike single-instance modules (Plan 04), gRPC clients have a per-upstream `GRPC_URL` environment key (`AUTH_GRPC_URL`, `SENDER_GRPC_URL`, etc.) — these are read via `opts.service.envKeys.GRPC_URL` from the SERVICE catalog. The narrow config carries `PROTO_DIR`, `GRPC_DEADLINE_MS`, AND a generic lookup for per-upstream `GRPC_URL`. Approach: GrpcClientConfig carries `PROTO_DIR: string`, `GRPC_DEADLINE_MS: number`, and `grpcUrlFor(serviceId: string): string` OR equivalent — the useFactory slice in each app reads its full `{Svc}Env` and synthesises the shape. See action block for concrete shape.
