## Executive Summary

The project is in remarkably good shape — after Phases 999.7.x (gRPC Promisified Proxy), 999.10 (hexagonal triple-layer), 999.10.1 (runtime-identity naming), and 999.11 (smoke surface removal), very few true architecture violations remain. The audit across the 9 canonical skills surfaces **24 violations total**: **18 BLOCKER** (fix in this phase per D-02) and **6 NON-BLOCKER** (remediation backlog).

The BLOCKER surface is dominated by two concerns: (a) the 5 already-known structural placements (2 health + 3 smoke + 1 throttle feature-submodule + 4 drizzle env-hygiene files), and (b) the Canonical Config Access Contract migration — **18 distinct `configService.get(...)!` / `config.get(...)!` / `as LogLevel` callsites** in foundation + gateway + apps that need to move to per-service `{SVC}_CONFIG` tokens with narrow foundation slices. There are **10 files** importing `@nestjs/config` across the workspace that need to be cleaned; 7 `package.json` files with `@nestjs/config` dependency entries to remove (6 apps + foundation).

The NON-BLOCKER surface includes 1 notifier 2-layer pattern leftover (HandleEventUseCase implements HandleEventPort — pre-999.10 shape, notifier was out of scope), 1 notifier field-naming leftover (`handleEventPort: HandleEventPort` — 999.10.1 was gRPC-only), 1 obsolete `GrpcClientModule` file with zero consumers (dead code), 1 empty `apps/notifier/src/infrastructure/external/` directory, and 2 catalog-adjacent low-severity findings.

**Primary recommendation:** Execute 8 atomic commits in the order prescribed by §7 (Commit Sequence). Each commit is TS-compilable in isolation because the `{SVC}_CONFIG` provider is registered BEFORE any callsite migration — existing `AppConfigModule`/`ConfigService` stays live during the migration window and is only removed in the final commit after every consumer has been moved. The drizzle fix ships in a single atomic commit across 4 files (Claude's discretion: **inline `DatabaseSchema.parse(process.env)` per file**, not a shared helper — 4 files × 2 lines is below any DRY threshold).

### Foundation narrow config interfaces — contract with apps (D-10)

The foundation factories receive **typed narrow slice interfaces** and no longer import `ConfigService`. Each foundation module defines its own narrow config interface; each app's useFactory slices from `{SVC}_CONFIG` into that shape.

Per-module mapping is enumerated in §5 below. The key pattern repeated across all foundation modules:

```typescript
// packages/foundation/src/external/cache/cache.interfaces.ts (extend existing)
export interface CacheConfig {
  readonly REDIS_URL: string;
}

// packages/foundation/src/external/cache/cache.module.ts (if not already exposing it)
// Expects a provider bound to CACHE_CONFIG_PORT (Symbol). Foundation NEVER reads REDIS_URL
// from ConfigService — it reads it from the typed CacheConfig parameter.

// App useFactory (apps/sender/src/sender.module.ts):
{
  provide: CACHE_CONFIG_PORT,
  useFactory: (c: SenderEnv): CacheConfig => ({ REDIS_URL: c.REDIS_URL }),
  inject: [SENDER_CONFIG],
}
```

Foundation exports `CACHE_CONFIG_PORT` as a Symbol; apps register the slice useFactory as a provider. `CacheModule.forRootAsync()` internally `inject: [CACHE_CONFIG_PORT]` instead of `inject: [ConfigService]`.

## drizzle.config.ts Fix — Concrete Shape Decision

CONTEXT.md D-07 presents the inline shape verbatim. Claude's discretion (explicit in DISCUSSION-LOG.md) asks whether to inline `DatabaseSchema.parse(process.env)` per file or to extract a shared `createDrizzleConfig()` helper in `packages/config/`.

### Shape A — Inline (recommended)

```typescript
// apps/parser/drizzle.config.ts
import { DatabaseSchema } from '@email-platform/config';
import { defineConfig } from 'drizzle-kit';

const env = DatabaseSchema.parse(process.env);

export default defineConfig({
  dialect: 'postgresql',
  schema: './src/infrastructure/persistence/schema/index.ts',
  out: './drizzle',
  dbCredentials: { url: env.DATABASE_URL },
  schemaFilter: ['parser'],
});
```

**Metrics:** 4 files × 3 extra lines each = 12 LOC added across 4 files. Each file is independently readable. Zero new exports in `packages/config/`.

### Shape B — Shared helper

```typescript
// packages/config/src/drizzle-helper.ts (NEW file)
import type { Config } from 'drizzle-kit';
import { defineConfig } from 'drizzle-kit';
import { DatabaseSchema } from './schemas/database';

export function createDrizzleConfig(opts: {
  schema: string;
  out: string;
  schemaFilter: [string];
}): Config {
  const env = DatabaseSchema.parse(process.env);
  return defineConfig({
    dialect: 'postgresql',
    schema: opts.schema,
    out: opts.out,
    dbCredentials: { url: env.DATABASE_URL },
    schemaFilter: opts.schemaFilter,
  });
}

// apps/parser/drizzle.config.ts
import { createDrizzleConfig } from '@email-platform/config';

export default createDrizzleConfig({
  schema: './src/infrastructure/persistence/schema/index.ts',
  out: './drizzle',
  schemaFilter: ['parser'],
});
```

**Metrics:** +1 helper file (~18 LOC), each drizzle.config.ts shrinks to ~7 LOC (saves ~4 LOC × 4 files = 16 LOC). Adds a new export to `@email-platform/config` — increases public-API surface for something used by 4 build-tool files only.

### Recommendation: **Shape A (inline)**

Rationale:
1. **DRY threshold unmet.** The 3 lines being duplicated are `import { DatabaseSchema }`, `const env = ...`, plus the inline reference `env.DATABASE_URL`. At 4 call-sites this is below any reasonable DRY trigger.
2. **drizzle-kit is build-tool surface.** These files run at CLI invocation time (`pnpm --filter @email-platform/{svc} db:generate` etc.), not in the app runtime. Adding a helper pulls it into `@email-platform/config`'s public exports — a cost paid forever for a one-time-per-service readability gain.
3. **Consistency with existing patterns.** Each drizzle.config.ts already has service-specific `schemaFilter`; each carries a small amount of service-specific knowledge. Inlining the env read preserves the "one file = one service's drizzle config" property.
4. **The helper doesn't genuinely encapsulate anything risky.** If `DatabaseSchema` ever changes, the 4 files get updated identically either way (same import path).

Caveat: If the planner prefers Shape B purely for symmetry with the runtime Canonical Config Access Contract, that's a valid judgement call — the gains/losses are small. Ship whichever shape reaches consensus.

## Pitfalls & Non-obvious Gotchas

### PT-01 — `@nestjs/config` transitive imports (TerminusModule, ThrottlerModule)

**Risk:** Some NestJS ecosystem packages have `@nestjs/config` as a peer or internal dep. Removing it from our deps might fail at runtime if a third party tries to inject `ConfigService`.

**Mitigation:** Verified — `@nestjs/terminus` and `@nestjs/throttler` do NOT internally inject `ConfigService` (they accept options via `.forRoot(...)`). The Phase 20 decision log records `@nestjs/config` is used exclusively for `ConfigService` consumer-side. After Commit 9, run `pnpm install` and `pnpm build` — if transitive peer-missing warnings appear, document them but don't block.

### PT-02 — Docker build impact

**Risk:** The Docker build (`infra/docker/app.Dockerfile`) installs deps from the workspace — if `@nestjs/config` was listed and gets removed, verify the resulting image still boots.

**Mitigation:** D-15 dual-mode smoke `pnpm start:isolated` exercises a **full docker compose up --build** including image rebuild. The smoke gate catches Docker-build regressions automatically. No extra tooling needed.

**Mitigation:** Confirmed — `DatabaseSchema` in `packages/config/src/schemas/database.ts` is a pure Zod schema with zero `@nestjs/*` imports, so it's CLI-safe. Inlining is Shape A (§6).

### PT-06 — Provider registration: main.ts vs module.ts

**Risk:** CONTEXT.md mentions "регистрация `{SVC}_CONFIG` provider в main или в module — plan-phase решит".

**Recommendation:** Register in `{svc}.module.ts` (see Commit 1 shape). Rationale:
1. Keeps main.ts focused on Nest bootstrap (app-level concerns: logger, shutdown hooks, pipes, listen)
2. Module composition is the canonical place for providers — matches every other provider in the codebase
3. `main.ts` has the raw `loadConfig(XxxEnvSchema)` call already; reading that value via DI inside modules preserves test-mockability (a test can override `{SVC}_CONFIG` provider without touching main.ts)

### PT-07 — Use-case method-arg pattern (D-09)

**Risk:** Use cases MUST NOT `@Inject({SVC}_CONFIG)`; they receive env-values as method args from parent Service.

**Current state:** grep `apps/*/src/application/use-cases/**/*.ts` for `@Inject(.*CONFIG)` or config types = 0 matches. Today no use case injects config. Post-phase, if a use case needs env values, the parent Service injects `{SVC}_CONFIG` and passes them:

    return this.useCase.execute(cmd, { timeout: this.config.OPERATION_TIMEOUT_MS });

// UseCase — NO @Inject, receives opts as method arg
