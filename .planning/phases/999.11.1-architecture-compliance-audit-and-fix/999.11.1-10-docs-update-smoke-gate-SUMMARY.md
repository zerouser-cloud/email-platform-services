**Smoke gate attempt 1 (before Rule 3 fix): FAILED.**
```
ERROR [ExceptionHandler] UnknownDependenciesException:
  Nest can't resolve dependencies of the pino-params (?).
  Please make sure that the argument Symbol(LOGGING_CONFIG_PORT) at index [0]
  is available in the LoggerModule module.
```
Affected audience + parser + sender + auth + notifier + gateway on boot — systemic failure.

**Root cause analysis (investigation ~3min):**
- Plan 04 (commit `ab918d5`) introduced `LOGGING_CONFIG_PORT` + other narrow-config providers in EACH app's ROOT module `providers:[]` array.
- NestJS rule: root module providers are NOT automatically global. Nested dynamic modules (imported into root) can only resolve tokens visible in their own scope — NOT walk up to root's `providers:[]` unless the providing module is marked `@Global()`.
- Foundation modules that use nested third-party `forRootAsync` — `LoggingModule.forXxxAsync` → `PinoLoggerModule.forRootAsync({inject: [LOGGING_CONFIG_PORT]})`, `defineGrpcClient` → `ClientsModule.registerAsync({inject: [GRPC_CLIENT_CONFIG_PORT]})`, `ThrottleModule` → `ThrottlerModule.forRootAsync({inject: [GATEWAY_CONFIG]})` — all execute resolution in the nested scope and fail.
- Before Plan 09 (commit `2d14d30`), `AppConfigModule` wrapped `ConfigModule.forRoot({ isGlobal: true })` which made `ConfigService` globally resolvable — that global marker masked the scope issue for every pre-Plan-04 call-site. Plan 09 removed `AppConfigModule` without carrying the `@Global()` marker over to the replacement providers, leaving the scope regression unobserved until D-15 runtime smoke.

**Rule 3 fix (Auto-fix blocking issue):** Introduce a `@Global()`-decorated `{Svc}ConfigModule` per service. Each `{svc}-config.provider.ts` now exports both the legacy `{svc}ConfigProvider` (kept for minimal diff; unused after this commit) AND the new `@Global()` `{Svc}ConfigModule` with `static forRoot(): DynamicModule` that registers:
- `{svc}ConfigProvider` (binds `{SVC}_CONFIG` via `useValue: loadConfig({Svc}EnvSchema)`)
- Each narrow `*_CONFIG_PORT` slice useFactory (previously at root `providers:[]`)
- All tokens listed in `exports:[]`

Each `{svc}.module.ts` updated to import `{Svc}ConfigModule.forRoot()` FIRST in `imports:[]` (before any foundation module), and the duplicated root-level slice providers are removed.

## Architectural Discoveries

### NestJS DI scope for nested third-party forRootAsync
Foundation modules like `LoggingModule.forGrpcAsync` import third-party dynamic modules (e.g. `PinoLoggerModule.forRootAsync`) whose `inject:` field resolves tokens from the nested module's scope — NOT from the root module's `providers:[]`. The only way root-level tokens become visible is via `@Global()` on the providing module. This is a **systemic property of Clean DI architecture using narrow ports + foundation factories**, not a single-case bug. Every infra-client migration phase that defines tokens at root-level providers[] must mark the providing module `@Global()` — now enforced by the refined skill.

### Dual-mode smoke is the ONLY gate that catches this class of bug
Per-commit static gate (`pnpm lint && pnpm build`) cannot detect DI resolution failures — those only surface at NestJS `InstanceLoader` time during runtime boot. Plans 01-09 all passed their D-14 gates without catching the Plan 04 + Plan 09 latent combination. D-15 dual-mode smoke is the first (and, in this architecture, the only) gate that samples the runtime DI graph. This validates the RESEARCH §9 Nyquist architecture — static checks alone are insufficient for DI-heavy NestJS codebases.

### @nestjs/config's `isGlobal: true` was the implicit masking mechanism
Pre-Plan-09, `AppConfigModule.forRoot({isGlobal: true})` wrapped the entire ConfigService. This `isGlobal` flag made `ConfigService` resolvable from EVERY nested module in the app — including nested `PinoLoggerModule.forRootAsync({inject: [ConfigService]})`. When Plan 09 replaced `ConfigService` with `{SVC}_CONFIG` providers at root level, the scope regression was invisible — but only because the replacement path's Global equivalent was never added. The current `@Global()` per-service pattern restores the visibility semantics with better type safety (each service sees its own narrow config, not the whole env).
