## Decisions Made

- **Re-export over bespoke interface** where possible (CacheConfig ← RedisConfig, PersistenceConfig ← DatabaseConfig, LoggingConfig direct) — zero drift, single source of truth in `@email-platform/config`. LoggingConfig re-export carries `LogLevel` / `LogFormat` branded enum types natively, eliminating the need for `as LogLevel` / `as LogFormat` casts in the two `forXxxAsync` factories (IC-03 double-win).
- **StorageConfig split into StorageCoreConfig + PublicStorageConfig** — these are two distinct module concerns (S3 client construction vs public-URL uploads), so two narrow interfaces is correct granularity. Apps provide each slice separately.
- **STORAGE_CORE_CONFIG_PORT re-exported via `external/storage/index.ts`** (runtime value + type) — the Symbol physically lives in `internal/storage/storage.constants.ts`, but apps must not reach into `@email-platform/foundation/internal` (ESLint enforced). Explicit re-export at the public external barrel keeps the app surface clean.
- **Single atomic commit (OQ-7)** — tried-and-true 999.11 pattern: atomic per concern. Splitting per foundation module (5 sub-commits) would have triggered the SAME 6 app-module edits in each sub-commit (providers array surgery per app per slice). The planner's recommendation held: one commit at 26 files is simpler to review than 5 commits at 10-15 files each with overlapping app churn.
- **ConfigModule dropped from imports arrays** of s3-core.module and shared-namespace.module — no consumer of `ConfigService` remained in those modules after the swap, so the import is dead weight. `AppConfigModule.forRoot` at app-level still registers the module globally; this local drop is a no-op runtime change.
- **PT-06 respected** — slice providers registered in `{svc}.module.ts` `providers[]` array (alongside the existing `{svc}ConfigProvider`), NOT in `main.ts`. Matches CONTEXT.md D-09 "Module factories" rule.

## Deviations from Plan

**1. [Rule 3 - Blocking issue — module barrel reach] Added STORAGE_CORE_CONFIG_PORT runtime-value + type re-export to `packages/foundation/src/external/storage/index.ts`**

- **Found during:** Task 4 (parser.module + notifier.module app wiring)
- **Issue:** The plan §files_modified list lacked `external/storage/index.ts` among the barrels to update, but parser + notifier must import `STORAGE_CORE_CONFIG_PORT` (Symbol runtime value) from the public foundation barrel. The Symbol's physical home (`internal/storage/storage.constants.ts`) is unreachable from apps per the `@email-platform/foundation/internal` ESLint guard. Without this re-export the `STORAGE_CORE_CONFIG_PORT` token would be ESLint-inaccessible to apps.
- **Fix:** Added `export { STORAGE_CORE_CONFIG_PORT } from '../../internal/storage'` (runtime value) + `export type { StorageCoreConfig } from '../../internal/storage'` (type) to `external/storage/index.ts`, parallel to the pre-existing pattern for `StorageHealthIndicator` / `PrivateStoragePort` type-only re-exports. The StorageCoreConfig *type* mirrors the pre-existing external-barrel pattern; the Symbol *runtime value* re-export is the new piece.
- **Files modified:** 1 (`packages/foundation/src/external/storage/index.ts`)
- **Commit:** `ab918d5` (combined atomic)
- **Impact:** Accepting this was the only way for app modules to DI the token without reaching into the internal subpath. Adds 1 file to the touch count vs plan's 22 (final: 26 files — 22 planned + 1 barrel fix + 3 created).

**2. [Rule 1 — Prettier nit] Collapsed 3-line notifier.module.ts import to single line**

- **Found during:** Task 4 lint pass
- **Issue:** Initial multi-line import `{ HANDLE_EVENT_PORT, NOTIFICATION_SENDER_PORT, NOTIFIER_CONFIG }` tripped prettier/prettier rule (line length below max, so must be inlined).
- **Fix:** Collapsed to single line — `import { HANDLE_EVENT_PORT, NOTIFICATION_SENDER_PORT, NOTIFIER_CONFIG } from './notifier.constants';`
- **Commit:** `ab918d5`

No other deviations. No architectural escalations.
