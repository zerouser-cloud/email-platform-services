### #2 — D-13 ThrottlerStorage Redis Connection Sharing

**Decision: Share the Redis connection** instantiated by `outbound/cache/AppCacheModule` rather than create a separate client. **Implementation: expose `REDIS_CLIENT` only as a *transitive* (re-exported by the wrapper) provider used by `ThrottleModule` — do NOT promote `REDIS_CLIENT` to foundation public barrel.**

**Why share:**
- One Redis TCP connection per gateway process is preferable to two (operational simplicity, fewer file descriptors).
- Identity boundary preserved — same `REDIS_URL` source, same connection lifecycle (managed by `RedisShutdownService`), one health check (REDIS_HEALTH already covers the connection).
- Phase 21 D-04 invariant ("REDIS_CLIENT not exported publicly") is honored if the leak is **scoped to a single application-level wrapper module** that already exists for that service. The invariant prevents the foundation's PUBLIC barrel from leaking the raw client to *any* consumer; it does not prevent the foundation from making it available **inside its own DynamicModule's providers array** for callers who explicitly opt in.

**Mechanism (the planner can codify this):** The foundation `CacheModule.forRootAsync({namespace})` already creates `REDIS_CLIENT` as a provider (cache.providers.ts line 16-25 — verified). The provider is currently bound but **not exported** from the DynamicModule (cache.module.ts line 14: `exports: [TerminusModule, CACHE_SERVICE, REDIS_HEALTH]` — REDIS_CLIENT absent). To share the connection with the throttler, either:

- **Option A (recommended for D-13 scope, minimal change):** In gateway's `outbound/cache/cache.module.ts` thin wrapper, **import** `REDIS_CLIENT` (Symbol) from the foundation's existing internal export path **OR** bind a passthrough provider at the wrapper level. Re-export it from the wrapper's `exports`. Then `ThrottleModule` (gateway-specific) can `@Inject(REDIS_CLIENT)` inside its `useFactory` to construct `new ThrottlerStorageRedisService(redis)`.

  **Snag:** `REDIS_CLIENT` is currently **not** in the foundation public barrel (`packages/foundation/src/external/cache/index.ts` lines 1-15 — verified, REDIS_CLIENT absent). It is `export`-ed from `cache.constants.ts` (line 3: `export const REDIS_CLIENT = Symbol('REDIS_CLIENT')`) but the barrel does not re-export it. **The planner has two paths:**

  - **Path A1 (preferred):** Add `REDIS_CLIENT` to `packages/foundation/src/external/cache/index.ts` exports list. This *narrowly* unlocks Phase 21 D-04 — adding a documented exception. Document the exception in 999.12 SUMMARY.md and inline-amend Phase 21 SUMMARY (#11). Single-line foundation change.
  - **Path A2 (avoidance):** Rebuild the connection inside `ThrottleModule.forRootAsync` from `CACHE_CONFIG_PORT` (which gateway will get via D-15). This creates a **second** Redis TCP connection per gateway process. Operationally inferior but preserves Phase 21 D-04 verbatim.

  **Recommended: Path A1.** Phase 21 D-04 was framed against *direct application consumers* leaking abstraction. The throttler use case is structurally a foundation-adjacent concern (rate-limit storage), not business code. Documenting the narrow exception (one external library — `@nest-lab/throttler-storage-redis` — receives the raw client) preserves the spirit of D-04 while avoiding redundant connections. The ESLint guard added by D-08 (which forbids `ioredis` import in `apps/*/src/**`) prevents the regression that D-04 was protecting against.

- **Option B (rejected):** Build a new ioredis instance in gateway throttle. Inferior — second connection, second health check, divergent shutdown lifecycle.

**Recommended `ThrottleModule` shape (post-migration):**

```typescript
// apps/gateway/src/infrastructure/bootstrap/throttle/throttle.module.ts
import { Module } from '@nestjs/common';
import { APP_GUARD } from '@nestjs/core';
import { ThrottlerGuard, ThrottlerModule } from '@nestjs/throttler';
import { ThrottlerStorageRedisService } from '@nest-lab/throttler-storage-redis';
import type Redis from 'ioredis';
import { REDIS_CLIENT } from '@email-platform/foundation';  // narrow public unlock (Path A1)
import { GATEWAY_CONFIG } from '../config/gateway-config.constants';
import type { GatewayEnv } from '@email-platform/config';
import { THROTTLE_TIER } from './throttle.constants';
import { AppCacheModule } from '../../outbound/cache';  // brings REDIS_CLIENT into scope

@Module({
  imports: [
    AppCacheModule,  // provides REDIS_CLIENT, REDIS_HEALTH, CACHE_SERVICE
    ThrottlerModule.forRootAsync({
      inject: [GATEWAY_CONFIG, REDIS_CLIENT],
      useFactory: (config: GatewayEnv, redis: Redis) => ({
        throttlers: [
          { name: THROTTLE_TIER.BURST, ttl: config.RATE_LIMIT_BURST_TTL, limit: config.RATE_LIMIT_BURST_LIMIT },
          { name: THROTTLE_TIER.SUSTAINED, ttl: config.RATE_LIMIT_SUSTAINED_TTL, limit: config.RATE_LIMIT_SUSTAINED_LIMIT },
        ],
        storage: new ThrottlerStorageRedisService(redis),
      }),
    }),
  ],
  providers: [{ provide: APP_GUARD, useClass: ThrottlerGuard }],
})
export class ThrottleModule {}
```

**Note on namespacing in the throttler storage:** `ThrottlerStorageRedisService` writes its own keys (sliding-window ZSETs). It does **NOT** use the `RedisCacheService.prefix` from foundation — that prefix only applies to `CACHE_SERVICE.get/set/del` calls. Throttler keys will land at the global root unless we wrap them. **For Phase 999.12 scope this is acceptable** because:
- Only one consumer exists (gateway).
- Future namespace collision is not a concern at single-gateway-cluster scale.
- The throttler library may not expose key-prefix injection (`@nest-lab/throttler-storage-redis@1.2.0` constructor accepts `Redis | string | Redis.Cluster | undefined` only — no prefix option per README).
- A k8s deployment with multiple gateway clusters could revisit this via per-deployment Redis logical-DB separation (`redis://host:6379/2`).

**Document this nuance in SUMMARY.md** (the throttler keys are not namespace-prefixed — by design, one consumer scope today).

### #3 — D-08 ESLint Override Syntax for `ioredis` Ban

**Existing pattern (verified `.eslintrc.js` lines 82-118):** Two `apps/*/src/**` overrides already exist — one general (line 83, lists workspace packages to ban) and one infrastructure-scoped (line 103). The cleanest path: **add a separate, narrowly-scoped `apps/*/src/**` override** specifically for `ioredis` so the existing patterns are not perturbed.

**Recommended addition to `.eslintrc.js` overrides array:**

```javascript
// Override 10 (Phase 999.12 D-08): Forbid raw ioredis import in apps.
// Apps must consume CACHE_SERVICE from @email-platform/foundation; ioredis is
// foundation-internal. This override catches regressions at lint time.
// Reference phase: .planning/phases/999.12-redis-canonical-alignment/
{
    files: ['apps/*/src/**/*.ts'],
    rules: {
        'no-restricted-imports': ['error', {
            patterns: [{
                group: ['ioredis', 'ioredis/*'],
                message: 'Apps must not import ioredis directly — use CACHE_SERVICE token from @email-platform/foundation. See .agents/skills/infrastructure-client-layering/SKILL.md and Phase 999.12 D-08.',
            }],
        }],
    },
},
```

**ESLint nuance — multiple overrides on the same `files:` glob:** ESLint applies overrides cumulatively when `files:` patterns match. Existing Override 4 (line 83) already targets `apps/*/src/**` with a `no-restricted-imports` rule banning workspace packages. **Adding a second `apps/*/src/**` override with `no-restricted-imports` for ioredis WILL OVERWRITE the workspace-package ban for the same files**, because ESLint merges override blocks but the `no-restricted-imports` rule is replaced wholesale (the rule does not deep-merge `patterns` arrays). [VERIFIED: ESLint documentation behavior — overrides replace, do not merge, leaf rule values]

**Recommended fix:** Extend Override 4 (the existing `apps/*/src/**` general one at line 83) by adding `'ioredis'` and `'ioredis/*'` to its existing `group` array. **Do NOT create a new override block.** Concrete diff:

```diff
 {
     files: ['apps/*/src/**/*.ts'],
     rules: {
         'no-restricted-imports': ['error', {
             patterns: [{
                 group: [
                     '@email-platform/gateway', '@email-platform/gateway/*',
                     '@email-platform/auth', '@email-platform/auth/*',
                     '@email-platform/sender', '@email-platform/sender/*',
                     '@email-platform/parser', '@email-platform/parser/*',
                     '@email-platform/audience', '@email-platform/audience/*',
                     '@email-platform/notifier', '@email-platform/notifier/*',
                     '@email-platform/foundation/internal',
                     '@email-platform/foundation/internal/*',
+                    'ioredis',
+                    'ioredis/*',
                 ],
-                message: 'Apps cannot import from other apps or from foundation internal. Use contracts for shared types; wrap internal primitives in infrastructure/.',
+                message: 'Apps cannot import from other apps, from foundation internal, or from ioredis directly. Use contracts for shared types; consume CACHE_SERVICE token from @email-platform/foundation for Redis access (Phase 999.12 D-08).',
             }],
         }],

 },
```

**Single-message tradeoff:** the consolidated message is slightly less specific. **Alternative:** keep two `patterns` entries inside the same override (more verbose, sharper messages):

```diff
 'no-restricted-imports': ['error', {
-    patterns: [{
+    patterns: [
+        {
         group: [...workspace-packages-list...],
         message: 'Apps cannot import from other apps or from foundation internal. Use contracts for shared types; wrap internal primitives in infrastructure/.',
-    }],
+        },
+        {
+            group: ['ioredis', 'ioredis/*'],
+            message: 'Apps must not import ioredis directly — use CACHE_SERVICE token from @email-platform/foundation. See Phase 999.12 D-08.',
+        },
+    ],
 }],
```

**Recommended: Alternative (two patterns blocks)** — preserves message specificity per-violation. The plan-checker will appreciate the targeted message for ioredis violations.

**Verified NestJS 11 module re-export semantics:** `exports: [CacheModule]` re-exports the module's own exports transitively. NestJS imports DAG resolution: Module A imports Module B, Module B re-exports Module C → providers from Module C are visible to consumers of Module A. [CITED: NestJS docs — Modules / Re-exporting modules]

**Verified `outbound/persistence/persistence.module.ts` (the canonical sibling):**

```typescript
import { Module } from '@nestjs/common';
import { CampaignModule } from './campaign';

@Module({
  imports: [CampaignModule],
  exports: [CampaignModule],
})
export class AppPersistenceModule {}
```

This shape (re-export the imported feature module, not its internal tokens) is the project's canonical form. The persistence sibling exports a sub-module (`CampaignModule`); we adapt it to export the foundation's `CacheModule` directly because there are no per-aggregate sub-modules under cache (D-03: thin wrapper, no app-level Symbols).

**Concrete shape for `AppCacheModule` (canonical, ready for plan to codify):**

```typescript
// apps/{svc}/src/infrastructure/outbound/cache/cache.module.ts
import { Module } from '@nestjs/common';
import { CacheModule } from '@email-platform/foundation';
import { SERVICE } from '@email-platform/config';

/**
 * AppCacheModule (Phase 999.12 D-03) — thin app-level wrapper around the
 * foundation CacheModule. Fixes the namespace from the catalog identity in a
 * single place per service. Re-exports the foundation CacheModule so consumers
 * (HealthController via REDIS_HEALTH; future business services via CACHE_SERVICE)
 * receive both providers transitively.
 *
 * `App` prefix disambiguates from foundation's `CacheModule` inside the root
 * module's imports list. Shape mirrors AppPersistenceModule (Phase 999.11.2 D-06).
 *
 * No app-level Symbols (Anti-Pattern 5 — true-single-instance infra).

@Module({
  imports: [CacheModule.forRootAsync({ namespace: SERVICE.{svc}.id })],
  exports: [CacheModule],
})
export class AppCacheModule {}

(Replace `{svc}` with the literal service id at the import site — `SERVICE.sender.id`, `SERVICE.auth.id`, etc.)

```

When `AppCacheModule` declares `exports: [CacheModule]`, those three providers become available to any module that imports `AppCacheModule` — including `HealthModule`. ### #8 — `CacheModule` Single-Instantiation (D-05 / E-06)

**Precedent — SmokeTestModule double-instantiation (Phase 22.3):** Verified — `.planning/phases/22.3-storage-smoke-test-endpoints/22.3-03-SUMMARY.md` describes `SmokeTestModule` registered alongside other modules in `gateway.module.ts`. **The "double-instantiation anti-pattern" mentioned in CONTEXT.md E-06 refers to a class of past errors** where calling `Module.forRoot(...)` (or `forRootAsync`) in **two different parent modules** causes NestJS to create **two distinct providers** for the same conceptual singleton — including two underlying connections, two health indicators wired to different instances, etc. [VERIFIED via prior phase docs and NestJS DI semantics]

**The relevant rule:** `forRootAsync` returns a fresh `DynamicModule` each call; if that returned `DynamicModule` is registered in `imports:` of TWO different parent modules, NestJS DI treats them as two separate scopes by default, **not** as a singleton. The way to enforce singleton sharing is either (a) `@Global()` (not preferred — hides dependency), or (b) **call `forRootAsync(...)` exactly once**, in a wrapper module, then have all consumers `imports:[WrapperModule]`. NestJS reuses the wrapper-module instance across multiple consumers (same module reference → same provider scope).

**This phase's architecture:** `AppCacheModule` calls `CacheModule.forRootAsync({namespace: SERVICE.{svc}.id})` exactly once. Both `HealthModule` (Ring 4) and the root module (e.g., `SenderModule`) import `AppCacheModule` — NestJS resolves them to the **same** instance. ✓ Single-instantiation preserved.

**Question: does the root module need to import `AppCacheModule` if `HealthModule` already imports it?** Architecturally yes (D-05 was framed for the rollout to *future business consumers* — those will be added in feature modules under `apps/{svc}/src/infrastructure/outbound/{aggregate}/`, and they will import `AppCacheModule` directly when they need `CACHE_SERVICE`). For the **999.12 phase scope** itself (no business bindings except gateway throttle):

| Service | Root must import AppCacheModule? | Why |
|---------|----------------------------------|-----|
| sender | No (HealthModule covers) | No business consumer in 999.12 — root is fine without it |
| auth | No | No business consumer in 999.12 |
| audience | No | No business consumer in 999.12 |
| parser | No | No business consumer in 999.12 |
| notifier | No | No business consumer in 999.12 |
| **gateway** | **Yes** | **`ThrottleModule` consumer needs `REDIS_CLIENT` — gateway root imports `ThrottleModule` which depends on AppCacheModule** |

**Single-instantiation guarantee (verified by NestJS semantics):** Even if root imports `AppCacheModule` AND `HealthModule` imports it AND `ThrottleModule` imports it (gateway case — three importers), NestJS creates exactly one instance because they all reference the same `AppCacheModule` class.

**Recommendation for plan-phase:** All 6 services' root modules **may** import `AppCacheModule` directly for forward-compatibility (future business consumers will need it), but it's not strictly required in 999.12. **Pragmatic minimum:** sender/auth/audience/parser/notifier root unchanged (HealthModule pulls it in transitively); gateway root adds `AppCacheModule` import (required for `ThrottleModule`'s injection chain). Document the choice in SUMMARY.md.

## Surprises / Gotchas

These are findings that the CONTEXT.md decisions did not explicitly account for:

### S-1: Throttler keys are NOT prefixed by SERVICE.gateway.id

**Issue:** `RedisCacheService.prefixKey()` (foundation `cache.service.ts` line 36) only applies the namespace prefix to `get/set/del` calls made through `CACHE_SERVICE`. The `ThrottlerStorageRedisService` (`@nest-lab/throttler-storage-redis@1.2.0`) writes its **own** ZSET keys via raw ioredis commands — these keys land at the Redis root key space without the `gateway:` prefix. **Cross-namespace risk:** if any other service writes to keys named like `<some-throttler-key>` (very unlikely given the throttler key format), collisions could occur.

**Why CONTEXT.md missed it:** D-04/E-02 frame namespace isolation around `CachePort` semantics. The throttler is explicitly out-of-CachePort (E-05) — and the implication that throttler keys WON'T benefit from prefix isolation wasn't called out.

**RESOLVED:** Document in 999.12 SUMMARY.md as a known minor limitation. Future remediation if needed: switch to a Redis logical DB (`redis://host:6379/2`) for throttler isolation, or wrap `ThrottlerStorageRedisService` in a `KeyPrefix`-injecting decorator class. Both are out-of-scope for 999.12.

### S-2: `reflect-metadata` peer-dep version skew

**Issue:** `@nest-lab/throttler-storage-redis@1.2.0` declares `reflect-metadata: '^0.2.1'` peer-dep. Gateway's `package.json` pins `^0.2.0`. `^0.2.0` allows `0.2.x`, so `0.2.1` satisfies — at install time, pnpm is unlikely to complain. But peer-dep audits in stricter modes might warn.

**RESOLVED:** During the install commit (#9 of plan), if pnpm shows a peer-dep warning, plan-phase should bump gateway's `reflect-metadata` to `^0.2.1` or `^0.2.2`. Trivial fix.

### S-3: Foundation `CacheModule` does NOT re-export `REDIS_CLIENT`

**Issue:** `cache.module.ts` line 14 has `exports: [TerminusModule, CACHE_SERVICE, REDIS_HEALTH]` — `REDIS_CLIENT` is bound in providers (line 16-25 of providers.ts) but **not exported from the DynamicModule's `exports` array**. Even after `index.ts` exports the `REDIS_CLIENT` Symbol (Path A1 in #2), DI resolution would fail because the consumer wouldn't see the provider unless `cache.module.ts` exports it.

**Impact:** Path A1 (#2) needs **two** foundation edits, not one:
1. `packages/foundation/src/external/cache/index.ts` — add `REDIS_CLIENT` to the exports list (so app code can import the Symbol).
2. `packages/foundation/src/external/cache/cache.module.ts` line 14 — add `REDIS_CLIENT` to `exports: [TerminusModule, CACHE_SERVICE, REDIS_HEALTH, REDIS_CLIENT]` (so DI propagates the provider).

Plan-phase #9 commit (gateway throttle migration) should account for both edits.

**Why CONTEXT.md missed it:** D-07 says "REDIS_CLIENT остаётся приватным (Phase 21 D-04 invariant)" — there's a tension between "stays private" and "throttle migration needs it". This research resolves it by recommending narrow public exposure scoped to one consumer (gateway throttle), documented in SUMMARY.md and Phase 21 amendment (#11).

### S-4: AppCacheModule will be the canonical sibling for future `RmqModule` (Phase 999.13)

**Observation:** Phase 999.13 (RabbitMQ canonical alignment) is deferred. When it lands, it will face the same single-instance-vs-multi-namespace question. AppCacheModule (D-03 thin wrapper, no app-level Symbols) is **structurally simpler** than what future `AppRmqModule` will need (RMQ has named queues with stable identities — closer to gRPC pattern). Plan-phase doesn't need to plan for this, but document in SUMMARY.md "AppCacheModule pattern is the simplest of the canonical infra-client patterns; do not assume RMQ will follow the same shape."

### S-5: Notifier's HealthModule pattern is DIFFERENT (no DI token for RabbitMqHealthIndicator)

**Issue:** Notifier's `bootstrap/health/health.module.ts` registers `RabbitMqHealthIndicator` as a class-based provider (line 23: `providers: [RabbitMqHealthIndicator]`) — not behind a Symbol DI token. Its HealthController injects via class reference (`private readonly rabbitmq: RabbitMqHealthIndicator`).

**Why this matters for D-20:** When notifier gains REDIS_HEALTH (which IS a Symbol), the controller will mix both styles in one constructor:

```typescript
constructor(
  private readonly health: HealthCheckService,
  private readonly rabbitmq: RabbitMqHealthIndicator,        // class-based (existing)
  @Inject(PUBLIC_BUCKET_HEALTH) private readonly publicBucket: StorageHealthIndicator,  // Symbol (existing)
  @Inject(REDIS_HEALTH) private readonly redis: CacheHealthIndicator,                    // Symbol (NEW)
) {}
```

This is fine — NestJS handles mixed DI styles. But it's a stylistic asymmetry the plan-checker might flag. Document in SUMMARY.md that the asymmetry pre-exists 999.12 (RabbitMqHealthIndicator stub will be promoted to Symbol pattern in Phase 999.13 — NOT in 999.12 scope).

### S-6: The CLAUDE.md matrix has rows for "Storage adapter" but no separate row for cache

**Verified:** `CLAUDE.md` §"NestJS↔Hexagonal Layer Mapping" file-path reference table (lines visible in research targets) contains rows for:
- Repository adapter (outbound persistence)
- Upstream gRPC client (outbound grpc-clients)
- External HTTP client (outbound http-clients)
- Storage adapter (outbound storage)

**Missing:** Cache adapter row. D-09 closes this gap. Recommended row text (parallel to existing rows):

```markdown
| Cache adapter (Redis) | Infrastructure (outbound) | `apps/{svc}/src/infrastructure/outbound/cache/` | `cache.module.ts` (re-exports foundation `CacheModule` — `CACHE_SERVICE` + `REDIS_HEALTH`) |
```

### S-7: Sender-config.module.ts ALREADY has CACHE_CONFIG_PORT — no D-15 edit needed for sender

Verified — `apps/sender/src/infrastructure/bootstrap/config/sender-config.module.ts` line 49-51:
```typescript

```

Sender is the only existing implementation. D-15 is a 5-service rollout (auth + audience + parser + notifier + gateway). Plan-phase should explicitly state: "sender skipped from D-15 — already complete."

   - What we know: `RedisShutdownService` is auto-bound (line 44 of providers.ts) and triggers `OnApplicationShutdown` lifecycle hook — NestJS calls it automatically when the module is destroyed; explicit export is not required for the lifecycle to fire.
   - What's unclear: Whether downstream apps need it as a directly-injectable provider for any reason.
   - RESOLVED: **No change** — leave it as-is (auto-bound, internal). Phase 21 already verified this works.

   - What we know: Phase 21 D-04 is locked. 999.12 amends it (#11).
   - What's unclear: Whether plan-checker reads the amendment in 999.12 SUMMARY.md before flagging the violation.
