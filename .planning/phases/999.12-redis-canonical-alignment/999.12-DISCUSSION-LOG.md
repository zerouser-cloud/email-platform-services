### User clarification round

User responded with deeper architectural questions:
- Why exclude gateway? Is gateway + caching bad?
- Single Redis instance vs per-service — what's industry canonical?
- Kubernetes forward-look
- PG symmetry
- Intent: cache client ready-to-use во всех сервисах, чтобы когда business phase востребует — было frictionless

### Claude's refined analysis (provided to user)

1. **Gateway + Redis is architecturally OK** (Netflix Zuul, Kong, Tyk, Stripe gateway use Redis for distributed rate limit). Our current `@nestjs/throttler` uses in-memory storage → breaks при 2+ replicas. **Real gap, not speculative.**

2. **Shared Redis canonical** for 6-service system up to ~100 services. Namespace prefix isolation via SERVICE.{svc}.id. K8s forward-look: shared Redis cluster (Sentinel / Bitnami chart / managed) — same app code.

3. **PostgreSQL symmetry:** current shared PG + pgSchema = same canonical pattern. Not changed in 999.12.

4. **Universal rollout viable IF combined with concrete gateway use case** → throttle→Redis storage migration closes архитектурную дыру (distributed rate limit) и justifies gateway Redis inclusion.
