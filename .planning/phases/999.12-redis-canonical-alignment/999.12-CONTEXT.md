**Gathered:** 2026-04-24

## Phase Boundary

Выровнять Redis cache client с canonical infra-client pattern (symmetry с gRPC post-999.7.x + persistence) и развернуть structural cache client во всех 6 сервисах (auth, sender, audience, parser, notifier, gateway). Gateway получает concrete use case — миграция `@nestjs/throttler` storage с in-memory на Redis-backed, закрывая distributed rate-limit gap. Остальные 5 сервисов получают structural cache caркас (CACHE_SERVICE доступен через DI), без business bindings — consumers появятся в future business-logic фазах.

**В scope:**
- Миграция sender: `CacheModule.forRootAsync({namespace})` из `bootstrap/health/health.module.ts` → новый `outbound/cache/cache.module.ts`
- Создание `outbound/cache/cache.module.ts` в оставшихся 5 сервисах (auth, audience, parser, notifier, gateway)
- Env schema changes: `+ ...RedisSchema.shape` в 5 env schemas (все кроме sender, у которого уже есть)
- `{svc}-config.module.ts` в 5 сервисах: добавить `{ port: CACHE_CONFIG_PORT, slice: (c): CacheConfig => ({ REDIS_URL: c.REDIS_URL }) }` в narrowPorts
- HealthController во всех 6 сервисах: `@Inject(REDIS_HEALTH)` + добавить в readiness check
- Gateway specific: throttle storage migration — `@nestjs/throttler` default → Redis-backed storage (closes distributed rate limit)
- ESLint override: запретить `ioredis` import в `apps/*/src/**`
- CLAUDE.md §NestJS↔Hexagonal Layer Mapping: добавить row для Cache adapter в file-path matrix
- D-15 dual-mode runtime smoke gate (precedent 999.11.1/999.11.2)

**НЕ в scope:**
- Business cache bindings / adapters / use cases в non-gateway сервисах (structural only — consumers в future business phases)
- Sessions / token revocation / pub-sub абстракции (Phase 21 D-02 остаётся locked для этих use cases)
- Redis HA topology (Sentinel / Cluster mode) — future k8s migration scope
- Foundation `defineCacheClient` factory — избыточно для single-instance (Anti-Pattern 5 per skill ICL)
- PostgreSQL peer audit — отдельная mini-phase если drift найдётся; current shared PG + pgSchema pattern canonical (symmetric с Redis), не меняется

- Skill `infrastructure-client-layering` refinement — skill уже canonical post-999.11.4.1 (D-4 invariant: skill = principles, CLAUDE.md = inventory)

<decisions>
## Implementation Decisions

### Classification + placement (Area 1)

- **D-01:** Redis = **Category B (internal-only per-service infra)** по классификации, которая различает **две ортогональные оси**: (a) Scope/ownership (bounded context isolation, "наш private vs shared") и (b) Direction of control flow (Cockburn: "кто инициирует вызов"). Приложение driving Redis (мы говорим GET/SET) ⟹ **outbound driven adapter** (Ring 3), симметрично persistence. "Внутренний" означает namespace isolation (namespace `SERVICE.{svc}.id`), НЕ layer placement.

- **D-02:** **Placement** = `apps/{svc}/src/infrastructure/outbound/cache/cache.module.ts`. Симметрия с `outbound/persistence/` (тоже internal-only driven adapter) и с `outbound/grpc-clients/{upstream}/` (cross-service driven adapter). Cockburn: direction of control flow определяет inbound/outbound, не ownership.

- **D-03:** **Thin app-level wrapper module** — не foundation-direct import в `{svc}.module.ts`. Shape:
  ```typescript
  @Module({
    imports: [CacheModule.forRootAsync({ namespace: SERVICE.{svc}.id })],
    exports: [CacheModule],  // re-export foundation CacheModule → все её exports видны consumer'ам
  })
  export class AppCacheModule {}
  ```
  НИКАКИХ app-level symbols — только re-export foundation `CACHE_SERVICE` + `REDIS_HEALTH` через `exports:[CacheModule]`. Фиксирует namespace-from-catalog в одном месте per service.

- **D-04:** **Namespace source** = `SERVICE.{svc}.id` из catalog (`@email-platform/config`). Единый источник identity. Symmetry с gRPC (tokens derived via `Symbol.for(service.id + ...)`). Rename в catalog → namespace автоматически подхватывается. Zero drift risk.

- **D-05:** **HealthModule coupling** — HealthModule в `bootstrap/health/` импортирует `outbound/cache/cache.module.ts` (app-level wrapper) напрямую через `imports:[...AppCacheModule]`. Cross-ring import: Ring 4 (bootstrap) → Ring 3 (outbound) разрешён (framework может знать про adapters, обратное — нет). Precedent: HealthModule уже импортирует foundation PersistenceModule для DATABASE_HEALTH — та же логика. Single instantiation: CacheModule загружается один раз (через outbound/cache/), HealthController и будущие business consumers смотрят на один instance.

### Foundation API (Area 2)

- **D-06:** **Foundation `CacheModule.forRootAsync({namespace})` API остаётся без изменений.** Не вводим `defineCacheClient` factory — Anti-Pattern 5 per skill ICL: factory для derivation-from-catalog нужен при multiplicity (gRPC = много upstreams). Redis = true-single-instance → fixed tokens (`CACHE_SERVICE`, `REDIS_HEALTH`) уже достаточны, derivation избыточна. Skill ICL post-999.11.4.1 чётко закрепил pattern.

- **D-07:** **Public API barrel** (`packages/foundation/src/external/cache/index.ts`) остаётся как есть: exports `CacheModule`, `CACHE_SERVICE`, `REDIS_HEALTH`, `REDIS_DEFAULTS`, `REDIS_HEALTH_CHECK`, `CACHE_CONFIG_PORT`, types (`CachePort`, `CacheHealthIndicator`, `CacheModuleOptions`, `CacheConfig`), `RedisHealthIndicator` class. `REDIS_CLIENT` остаётся **приватным** (Phase 21 D-04 invariant: apps смотрят только на абстракции, не на raw client).

### Guard rails + documentation (Area 3)

- **D-08:** **ESLint override** в `.eslintrc.js`: `no-restricted-imports` для `apps/*/src/**` запрещающий `ioredis` / `ioredis/*`. Message: *"Apps must not import ioredis directly — use CACHE_SERVICE token from @email-platform/foundation"*. Analog существующих overrides против `@email-platform/foundation/internal` вне infrastructure/. Catches regressions at lint time.

- **D-09:** **CLAUDE.md §"NestJS↔Hexagonal Layer Mapping"** получает новую row в file-path matrix:
  ```
  | Cache adapter (Redis) | Infrastructure (outbound) | apps/{svc}/src/infrastructure/outbound/cache/ | cache.module.ts (re-exports foundation CacheModule — CACHE_SERVICE + REDIS_HEALTH) |
  ```
  Симметрия с existing rows для Storage adapter, Repository adapter, Upstream gRPC client. Concrete path matrix для downstream agents.

- **D-10:** **Skill `infrastructure-client-layering` остаётся без правок.** Post-999.11.4.1 skill уже описывает true-single-instance pattern абстрактно (Redis упомянут как example). По D-4 invariant из 999.11.4.1: skill = principles, CLAUDE.md = inventory. Concrete paths идут в CLAUDE.md, не в skill.

### Scope + rollout (Area 4)

- **D-11:** **Universal rollout на 6 сервисов** (включая gateway). Все получают structural outbound/cache/ каркас. Non-gateway 5 — без business bindings (PROJECT.md "no business logic" constraint); gateway имеет concrete consumer via throttle→Redis migration (D-13). Ready-to-use для future business phases. Cost: ~28 edited + 6 new files.

- **D-12:** **Gateway включён** как archetypal Redis consumer для distributed rate limiting — canonical industry pattern (Netflix Zuul, Kong, Tyk, Stripe API gateway). PROJECT.md constraint "gateway = REST facade" refers to **domain state** (users/campaigns); cross-cutting state (rate-limit counters) — legitimate gateway concern. Без shared rate-limit storage 2+ replicas gateway's throttler counts independently (fundamental distributed rate-limit break). Решение этой дыры = concrete use case, не speculative.

- **D-13:** **Throttle → Redis storage migration** в gateway. `@nestjs/throttler` default `ThrottlerStorage` = in-memory (breaks при 2+ replicas); замена на Redis-backed storage (`@nestjs/throttler-storage-redis` или эквивалент — конкретная library selection в plan-phase research). Consumes shared Redis, namespace = `SERVICE.gateway.id`. Closes distributed rate-limit gap. **Это единственный business binding в scope 999.12.**

- **D-14:** **Shared Redis topology preserved** (не per-service Redis instances). Один Redis container (Coolify hosted), namespace prefix isolation via SERVICE.{svc}.id. Industry canonical для 6-service system до scale 100+ services. Kubernetes forward-look: shared Redis cluster (Bitnami chart / Sentinel / Cluster mode) — **same app code**, только topology meta. Per-service Redis = over-engineering для current scale; HA решается cluster mode, не per-service isolation.

- **D-15:** **Env schema changes** в 5 сервисах (кроме sender): `+ ...RedisSchema.shape` в `packages/config/src/apps/{auth,audience,parser,notifier,gateway}/env.schema.ts`. Sender уже имеет RedisSchema.shape. `REDIS_URL` — shared env var, один Redis URL для всех сервисов. `.env` / `.env.docker` / `.env.example` — убедиться что `REDIS_URL` present для всех 6 сервисов (если не было — infra approval trigger; документировать в plan-phase).

- **D-16:** **Phase 21 D-02 partial unlock:** rate-limiting enters scope (specifically для gateway via Redis-backed throttler storage). Sessions / token revocation / pub-sub **остаются deferred** в Phase 21 D-02 — не в scope 999.12. Unlock documented в этой phase context.

- **D-17:** **Cross-service invariants** (edge cases) зафиксированы в <specifics> — enforce via architecture: каждый сервис имеет свой `outbound/cache/` с namespace = SERVICE.{svc}.id, физически не импортирует другой сервис (existing apps/*/src/** ESLint override блокирует cross-app imports). Inter-service cache peek невозможен via composition; inter-service state sync — только через gRPC/RMQ, не через direct Redis access в чужой namespace.

## Specific Ideas

### Edge cases invariants (enforced via architecture)

- **E-01:** **Cross-service Redis access forbidden.** Каждый сервис имеет свой `outbound/cache/` с namespace = SERVICE.{svc}.id. sender не импортирует audience/outbound/cache/ (blocked by existing apps/*/src/** ESLint override против cross-app imports). Inter-service state sync → gRPC/RMQ, не direct Redis peek.

- **E-02:** **Namespace isolation = bounded context boundary.** sender пишет в `sender:*`, audience в `audience:*`. Не "best practice suggestion" — это semantically-enforced invariant: каждый `outbound/cache/cache.module.ts` hardcodes `namespace: SERVICE.{svc}.id` через catalog, нет механизма cross-namespace access в canonical API.

- **E-03:** **Multiple Redis instances per service not in scope.** Если в будущем (auth) понадобится session store + отдельный rate-limit cache в том же сервисе — это future design decision (новый port/module, не multi-namespace в одном сервисе). Phase 21 D-02 стандарт применяется.

- **E-04:** **Shared Redis server preserved.** Не меняется topology (один Redis container, Coolify hosted). Logical isolation через prefix. Per-service Redis instances = over-engineering для current 6-service scale.

- **E-05:** **Redis pub/sub / Streams / rate-limit (вне gateway) — не в CachePort.** Phase 21 D-07 invariant: CachePort = строго kv cache с TTL. Future use cases → новые ports (PubSubPort / RateLimiterPort / etc.), не расширение CachePort. **Исключение в 999.12:** gateway throttle использует Redis через `@nestjs/throttler` storage API, **не через CachePort** — это отдельная library-owned интеграция, не расширение нашей абстракции.

- **E-06:** **HealthModule cross-ring import pattern documented.** HealthModule (Ring 4 bootstrap) импортирует outbound/cache/AppCacheModule (Ring 3 adapter) — корректно per Cockburn (framework может знать про adapters, обратное — нет). Avoids double-instantiation CacheModule (precedent 999.11 SmokeTestModule anti-pattern).

- **E-07:** **Inter-service cache client sharing невозможен.** Другой сервис физически не получит injection `CACHE_SERVICE` в чужой namespace (его outbound/cache/ namespace = его SERVICE.id, не чужой). Isolation enforced via composition structure, не только convention. Не semantic "guideline" — structural impossibility в рамках нашей DI.

### Two orthogonal axes clarification (foundational для всех D-*)

- **Ось A — Scope / ownership** (bounded context isolation): "наш private Redis namespace" vs "shared across services". Определяет namespace prefix, schema name, bucket name. Применима к Redis, PG, S3.
- **Ось B — Direction of control flow** (Cockburn hexagonal): "кто инициирует вызов"? Приложение driving external (outbound) vs external driving app (inbound). Определяет layer placement (inbound/ vs outbound/ vs bootstrap/).

**НЕ смешивать.** "Внутренний для сервиса" (namespace-isolated) ≠ "inbound adapter". Cache = internal-namespace (Ось A) + outbound direction (Ось B). Same для PG (pgSchema isolated + outbound direction).

### gRPC canonical as template (symmetry baseline)

gRPC layers (для справки):
- **contracts** (packages/contracts) — proto files + ts-proto generated TS types
- **catalog** (packages/config) — `SERVICE.{svc}` identity (id, diToken, grpc metadata)
- **foundation** (packages/foundation) — `defineGrpcClient` factory + `Promisified<T>` Proxy + health indicator
- **apps** — `outbound/grpc-clients/{upstream}/{upstream}-client.module.ts` thin wrapper + category composer

Redis analog (в 999.12):
- **contracts** — N/A (нет wire schema, ioredis encapsulates protocol); "contract" = `CachePort` interface в foundation
- **catalog** (packages/config) — `RedisSchema` / `RedisConfig` (env validation) + `SERVICE.{svc}.id` (namespace source)
- **foundation** (packages/foundation) — `CacheModule.forRootAsync` (не factory, т.к. single-instance), `CachePort` abstraction, `RedisHealthIndicator`
- **apps** — `outbound/cache/cache.module.ts` thin wrapper (re-export foundation CacheModule, намespace from catalog)

**Ключевое asymmetry:** gRPC factory derives per-upstream tokens via `Symbol.for(service.id_*)` — multi-instance mechanism. Redis single-instance ⟹ fixed foundation tokens (CACHE_SERVICE, REDIS_HEALTH), derivation не нужна. Это **intended** (не drift) — skill ICL post-999.11.4.1 документирует.

### k8s forward-look (non-blocking future note)

**Shared Redis topology** (D-14) остаётся canonical на k8s:
- Production pattern: shared Redis cluster (Bitnami/redis-cluster chart, Redis Sentinel, или managed Redis like AWS ElastiCache / Redis Cloud)
- **Same app code** — один `REDIS_URL` env var, cluster endpoint прозрачен для клиента
- HA via cluster mode / failover, не via per-service isolation
- Per-service Redis только при huge scale (100+ services) или specific compliance boundary

**PostgreSQL symmetry** — current shared PG + pgSchema isolation = **same pattern**, на k8s:
- Managed PG (CloudSQL / RDS / CloudNativePG operator) или shared PG StatefulSet
- Schema isolation preserved
- Per-service PG только при scale justifies

**Out of scope для 999.12:** реальная k8s migration, HA topology implementation — отдельный milestone. Здесь только **зафиксировать direction** чтобы будущие фазы не переоткрывали вопрос.

### Rate limit migration specifics (D-13)

- Current: `@nestjs/throttler` с default in-memory `ThrottlerStorage` — breaks при 2+ gateway replicas (каждая replica считает свой лимит)
- Target: Redis-backed `ThrottlerStorage` (e.g., `@nestjs/throttler-storage-redis`) — shared state across replicas
- Config: storage берёт REDIS_URL через GATEWAY_CONFIG; namespace = SERVICE.gateway.id (automatic via D-04)
- **Не расширение CachePort** — throttler API requires specific `ThrottlerStorage` interface (library-owned); integration через cache client на уровне Redis connection, не через `CACHE_SERVICE` injection. Plan-phase research решит: (a) использовать отдельный Redis connection specifically для throttler, или (b) reuse CacheModule's REDIS_CLIENT через new provider (требует either exposure или custom adapter)
