## Deferred Verification (per RESEARCH §10 + threat-model)

### D-20 Burst Test (single-replica)

**Status:** Deferred to phase-completion smoke gate at the close of Plan 11 (the canonical D-20 dual-mode gate `start:native` + `start:isolated` → 6/6 Redis health checks up + smoke). Per RESEARCH §10, the single-replica burst-test (11 rapid requests → 429 on the 11th) is feasible inside a running stack; this plan documents the test command for the phase-exit gate and the verifier:

```bash
# Once stack is up via `pnpm start:native` (waits for boot, /health/ready returns 200):
for i in $(seq 1 11); do
  curl -i -o /dev/null -w "%{http_code}\n" http://localhost:3000/<some-routed-endpoint>
done | tee /tmp/999.12-10-burst-test.txt
# Expect: 10 × 200 (or 401 etc. — what matters is throttler decision flow), then 429 on the 11th.
```

**Rationale for deferral:** The burst-test requires the full docker-compose stack (postgres + redis + rabbitmq + minio + 6 services) to be running. `pnpm start:native` is a long-running watcher (`turbo run dev`). Running it inside the executor session would either (a) hang the executor if foregrounded, or (b) leak background processes if backgrounded, both of which conflict with worktree-isolated atomic execution. The phase-exit smoke gate (Plan 11 acceptance) is the canonical seam for this verification per RESEARCH §10.

### Distributed-Rate-Limit-with-2-Replicas (multi-instance)

**Status:** Deferred to **Phase 999.15 production smoke** per RESEARCH §10. Both `pnpm start:native` and `pnpm start:isolated` boot a single gateway replica locally; meaningful 2-replica rate-limit assertions cannot be made until the production deployment runs gateway behind a reverse-proxy with N>=2 replicas. Documented as a known-deferred verification, not a gap.

### T-999.12-10-01 — Redis-Outage Throttle Behavior (DoS Surface)

**Status:** Deferred to Phase 999.15 production smoke. `@nest-lab/throttler-storage-redis@1.2.0` README does not specify open-vs-closed fail behavior on Redis outage. The library may:
- Throw → ThrottlerGuard rejects request (fail closed — DoS during cache outage),
- Swallow → ThrottlerGuard treats as un-throttled (fail open — DoS bypass during cache outage),
- Configurable via constructor options (not declared in README — would require reading the library source or empirical test).

This is the highest-severity threat in this plan (medium — rate-limit DoS surface). Mitigation: empirical verification in production-grade environment (Phase 999.15) before relying on rate-limit guarantees in production. Not a blocker for 999.12 because the limitation is honestly stated.

## Known Limitations (RESEARCH §S-1)

**Throttler key namespacing:** `ThrottlerStorageRedisService` writes its sliding-window ZSET keys via raw ioredis commands at the **Redis root keyspace** — these keys do **NOT** receive the foundation `RedisCacheService` `gateway:` namespace prefix. At single-gateway-cluster scale this is acceptable (collision risk negligible). Future remediation paths (logical-DB separation `redis://host:6379/2` for throttler keys, or wrapper class that injects key-prefix) are **deferred** out of phase scope. Documented here for completeness.
