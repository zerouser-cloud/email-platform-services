<findings>
<!-- Behavioural essence — do NOT just reference the ID. -->

icl-F-01 (behaviour): The skill's §Config → "Apps" subsection presents a ~30-line hand-rolled code example showing a bespoke `@Global() @Module({})` class with a `static forRoot(): DynamicModule` method that manually wires a provider and a collection of narrow-config-port slices. In current project reality this bespoke shape was absorbed by a foundation-level config factory that accepts (schema, DI token, narrow config ports) and returns a ready DynamicModule — consumers no longer hand-roll the module class. The code example is ACTIVELY misleading (it names class shapes and method signatures that no longer match any existing production code), AND it duplicates structural assertions about canonical files and `forRoot()` semantics that are already documented in the paired nestjs-hexagonal-mapping skill's references. The fix: replace the hand-rolled example with an abstract description of the config-factory mechanism (reusing the wording locked by Plan 01), link to the factory's enclosing directory per D-2, use at most one fictional FooService inline example per D-3.

icl-F-02 (behaviour): The skill's §"Redis / S3 / DB+ORM (single-instance)" groups three conceptually distinct storage backends under one "single-instance" label. Architectural reality is that S3 storage follows a multi-instance pattern — a shared S3 core module plus per-namespace (per-bucket) module factories that expose typed storage ports, crossing a subpath-export boundary. Redis and DB+ORM are true single-instance infra (one connection per service). Grouping them under "single-instance" is a categorical error that teaches readers to write `@Inject` calls that bypass the typed-port abstraction. The fix: split the section into two clearly-labelled conceptual subsections — (a) "True-single-instance infra (Redis, DB+ORM)" describing the direct-token-from-foundation pattern by role, and (b) "Multi-instance-per-namespace infra (S3 storage)" describing the shared-core-plus-per-namespace-factory pattern by role. Each subsection describes the architectural pattern using fictional names; neither section enumerates specific class names or paths.
</findings>
