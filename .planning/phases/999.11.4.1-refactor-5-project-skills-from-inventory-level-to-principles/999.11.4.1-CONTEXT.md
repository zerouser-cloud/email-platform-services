<decisions>
## Implementation Decisions

### Granularity rule (principle vs inventory)

- **D-1:** Rename test is the authoritative heuristic. If an assertion in a skill breaks when a file/class/variable is renamed, it is inventory; if it survives the rename, it is a principle. Rename test applies at refactor time AND at verification time — every new assertion in refactored skills must pass the test.
- **D-2:** When a skill wants to describe a mechanism (factory, module, adapter), the primary content is abstract description of role + behavior. Secondary optional content is a link to the enclosing **directory** (not a specific file). Directory moves are rare major refactors; specific file renames happen constantly — abstract text + directory link survives most rename churn.
- **D-3:** At most one inline code example per principle. Examples use fictional names (FooService, BarRepository) — never real production class names. This prevents coi-F-01-style defects (canonical example references deleted code).
- **D-4:** Every SKILL.md receives a header-block near the top: "This skill describes timeless principles. Do NOT add inventory (specific file paths, port numbers, class names, enumerated counts). For current-state lookups, link to tracked config files or provide a grep command." This is the primary guardrail against future inventory creep.

### Replacement targets (where removed inventory goes)

- **D-5:** Infrastructure identifiers (ports, hostnames, credentials) are referenced by ROLE, not by specific filename. Skill text: "infrastructure identifiers live in tracked env templates and docker-compose infra configuration; for current inventory, read those files." Specific filenames are NOT named — they can be renamed themselves.
- **D-6:** ESLint enforcement paths — skill links to the project's ESLint config by relative path (currently `.eslintrc.js`) with abstract description of what is enforced. Config is the single source of truth for path globs; skill never duplicates them. If project migrates to flat config, skill path updates once.
- **D-7:** Class and method names — only fictional names in skill body, including in anti-pattern sections. Real production names (e.g., historically `GrpcCaller`, `AbstractHttpClient`, `createConfigModule`) must not appear. Anti-patterns describe the behavioral pattern ("injecting a foundation class directly bypassing the factory"), not a specific name.
- **D-8:** Inventory snapshots (class/path censuses) are replaced by inline grep commands the reader runs on demand. Example: "to see current inheritance census, run: `grep -rn 'extends ' apps/ packages/ --include='*.ts'`". Top-level workspace paths (`apps/`, `packages/`) are treated as stable — their rename would be a massive refactor touching everything.

### Plan structure

- **D-9:** 5 plans for skills-with-findings (one per skill). 1 consolidated plan for 4 aligned-skills minor sweep. Total 6 plans. Planner may split aligned sweep into 4 separate plans (→ 9 plans total) if consolidation creates task ordering issues.
- **D-10:** Execution order — (a) `nestjs-hexagonal-mapping` + `infrastructure-client-layering` first, paired within consecutive plans (both require the same abstract description of config-factory principle; doing them together ensures consistent wording). (b) Then smallest-first on remaining findings-heavy skills: `infrastructure-guard` → `runtime-smoke-verification` → `composition-over-inheritance`. (c) Last: aligned-skills sweep (the 4 aligned skills should receive the header rule wording that emerged during the 5 primary refactors).
- **D-11:** Per-skill atomic commits. One commit per skill refactor. For paired plans (nhm+icl): still 2 separate commits (one per skill), not a combined commit — preserves granular `git revert` per skill.
- **D-12:** For 4 aligned skills, apply D-1..D-4 rules + minor sweep — not a full 999.11.4-style audit. At minimum: add D-4 header block + single rename-test pass through skill body. Extract any latent inventory found per D-5..D-8. If sweep finds zero latent inventory, commit contains only the header-rule addition.

### Verification approach

- **D-13:** Rename-test proof per finding — executor writes a one-line entry per closed finding in the plan SUMMARY: "Assertion {X} survives rename of {element}: yes + rationale" (or "no" with corrective action). Verifier re-runs rename-test against every new assertion in the refactored skill body.
- **D-14:** Before/after diff review — verifier reads `git diff` of each per-skill commit. Removed lines must be inventory; added lines must pass rename-test. Double audit (findings addressed + no inventory drift back).
- **D-15:** Newcomer test per refactored skill — separate agent simulates a newcomer who reads the skill for the first time and attempts to apply it to code they've never seen. Catches coi-F-01-style defects (skill mentions deleted/nonexistent code) + clarity gaps. Overhead ~30 min per skill.
- **D-16:** Findings closure is dual-tracked — (a) flip `☐ Pending review` → `☑ Approved (→ 999.11.4.1)` in each matching row of `999.11.4-SOLUTIONS.md`; (b) `999.11.4.1-SUMMARY.md` includes a `## Findings Closed` section mapping each F-xx to the commit hash that closed it.

### Claude's Discretion

- Plan file breakdown — 6 plans (1 per primary skill + 1 aligned-sweep) OR 9 plans (strict-per-skill) — planner chooses based on how homogeneous the aligned-sweep tasks are.
- Exact wording of the D-4 header-rule block — planner drafts during Plan 01 execution; subsequent plans reuse the locked wording.
- Newcomer test agent type — `general-purpose` with an explicit "simulate newcomer" prompt, or a new specialized skill-reviewer agent. Planner picks during plan design.
- Aligned-sweep commit granularity — 1 combined commit vs 4 per-skill commits. Low impact either way.

</decisions>

<specifics>
## Specific Ideas

- User emphasized "timeless vs inventory" as the core meta-rule — every principle must survive future refactors without text updates. Rule is recursively self-applied: even the skill's own examples, references, and grep commands must pass rename-test.
- Skill header rule (D-4) is the load-bearing preventive mechanism — without it, future authors add inventory drift silently. User explicitly picked this over pre-commit hooks and PR-review-only approaches.
- Newcomer test (D-15) is the quality gate — user explicitly rejected pure diff review as insufficient. Rationale: a skill can pass rename-test yet still be unclear to a first-time reader.
- Paired nhm+icl execution (D-10) — both skills share the "config-factory principle" — if refactored separately they'd diverge in wording. User's preference for consistent cross-skill phrasing drives the paired ordering.

</specifics>
