## Warnings

### WR-01: NAMING.md violates its own "no inventory" guardrail — concrete class names

**Status:** RESOLVED (2026-04-24, commit recorded in 999.11.4.1-REVIEW-FIX.md).

**File:** `.agents/skills/nestjs-hexagonal-mapping/references/NAMING.md:10-25, 45-97, 121-189`
**Issue:** The file's own opening rule (line 3) says: "Do NOT add inventory (specific file paths beyond stable workspace roots, class names tied to a particular production service, enumerated counts of services / ports / tokens)." The File↔Class Table (lines 11-24) hardcodes production class names: `AuthController`, `LoginService`, `VerifyCredentialsUseCase`, `LoginCommand`, `LoginPort`, `UserRepositoryPort`, `PgUserRepository`, `UserMapper`, `User`, `Email`, `PasswordHasher`, `UserRegisteredEvent`. The Field Naming Rules (lines 45-97) and Worked Examples (lines 121-189) repeatedly reference production entities like `AudienceController`, `AudienceServiceController`, `ListGroupsPort`, `LIST_GROUPS_PORT`, `LoginService`, `VerifyCredentialsUseCase`, `IssueTokenPairUseCase`, `PauseCampaignService`, `ResumeCampaignService`, `TransitionCampaignStatusUseCase`, `NotificationSenderPort`, plus concrete file paths like `apps/audience/src/infrastructure/inbound/grpc/audience.controller.ts` and `apps/auth/src/application/services/login.service.ts`. These fail the "rename test" the same section mandates on line 3 — renaming any of these would make the sentences false.

**Fix:** Replace every `AuthController` / `LoginService` / `VerifyCredentialsUseCase` / etc. with templated placeholders (`{Svc}Controller`, `{Feature}Service`, `{Operation}UseCase`) per the pattern already established by `LAYERS.md`. Replace concrete paths like `apps/audience/src/infrastructure/inbound/grpc/audience.controller.ts` with `apps/{svc}/src/infrastructure/inbound/grpc/{svc}.controller.ts`. Replace "applied across all 4 gRPC microservices (auth, sender, parser, audience)" with role-based phrasing such as "applied across every gRPC microservice in the workspace — run `ls apps/` for the current inventory". Keep the *patterns* (Pascal/camel case, suffix rules, field↔token relationships) — drop the *instances*.

### WR-02: NAMING.md enumerates phase-specific D-decision numbers as load-bearing rules

**Status:** RESOLVED (2026-04-24, commit recorded in 999.11.4.1-REVIEW-FIX.md).

**File:** `.agents/skills/nestjs-hexagonal-mapping/references/NAMING.md:26, 46-47, 77-78, 188, 190, 195, 219-224`
**Issue:** Numerous rules are anchored to specific decision IDs from specific phases — `D-04`, `D-08`, `D-09`, `D-11`, `D-16`, `D-17`, `D-18`, `D-19`, `D-21`, `999.10`, `999.10.1`, `999.11.2`. Examples: "**D-16 universal rule**: every inbound port field carries the `Service` suffix" and "**D-19 strict verb+noun rule**: field name is derived mechanically..." and "optional per D-19 — introduced only when real business logic arrives". These decision numbers are phase-local artefacts — they have no meaning outside the specific phase CONTEXT/PLAN docs where they were defined. Readers of the skill years from now (or on other teams) will see "D-16 universal rule" without any way to look up what D-16 is. This is a subtler form of inventory leak: instead of leaking a class name, the file leaks a phase-decision identifier.

**Fix:** Name the *rule*, not the decision number. Rewrite "**D-16 universal rule**: every inbound port field carries the `Service` suffix" as "**Inbound-port field suffix rule**: every inbound port field carries the `Service` suffix". Keep the optional phase citation as a historical-context footnote at the end of the section (e.g., "Historical note: this rule was locked in Phase 999.10.1 — see `.planning/phases/999.10.1-*/` for the decision record") rather than as the rule's identifier. A phase is a stable directory (D-8 exception), a D-number is not.

### WR-03: NAMING.md and LAYERS.md disagree on inventory strictness despite sharing the same skill

**Status:** RESOLVED (2026-04-24, commit recorded in 999.11.4.1-REVIEW-FIX.md).

**File:** `.agents/skills/nestjs-hexagonal-mapping/references/NAMING.md:1-7` vs `.agents/skills/nestjs-hexagonal-mapping/references/LAYERS.md:1-7`
**Issue:** Both files open with a "do not add inventory" guardrail, but their content diverges sharply in how strictly each honors it. `LAYERS.md` uses templated placeholders throughout (`{svc}`, `{Feature}Port`, `{Aggregate}Mapper`) and routes every concrete lookup to `CLAUDE.md §"NestJS↔Hexagonal Layer Mapping"` or to a `find`/`grep` command. `NAMING.md`, by contrast, is saturated with concrete production identifiers (see WR-01). Since both files belong to the *same* skill (`nestjs-hexagonal-mapping`) and are meant to be read together, this inconsistency is internally contradictory — readers are told principles-only, then handed a file that lists named-production artefacts as its primary illustration medium. The phase charter calls out this exact pattern as the refactor target for 5 skills.

**Fix:** Apply the same transformation to `NAMING.md` that was applied to `LAYERS.md`. The *table structure* stays (File↔Class mapping is useful pedagogy); only the table *contents* need to switch from production names to template placeholders. Keep at most one worked example per section using a clearly-fictional placeholder service (e.g., `FooService`, already used by `LAYERS.md` line 323). Example rewrite: the first row "`auth.controller.ts` | `AuthController`" becomes "`{svc}.controller.ts` | `{Svc}Controller`". Pattern already exists in `LAYERS.md` §Composition Root (line 323: "Illustrative shape (fictional `FooService` — names are placeholders, not production)"). Reuse that idiom throughout.

**File:** `.agents/skills/composition-over-inheritance/SKILL.md:319`, `.agents/skills/infrastructure-client-layering/SKILL.md:286`
**Issue:** The two skills cross-reference each other with different spellings of the same verb:

- `infrastructure-client-layering/SKILL.md:286`: "this skill concretises the rule for infra-client facades"
One uses American spelling ("-ization"), the other British ("-ises"). Trivial, but the two sentences describe the exact same relationship and should read identically.
**Fix:** Pick one spelling (the rest of the documentation leans British — "organisation" pattern is more common in existing files like "concretises", "materialises") and apply consistently. Replace `.agents/skills/composition-over-inheritance/SKILL.md:319` "concretization" → "concretisation" (or both to "concrete application" to sidestep the ism entirely).

### IN-04: Minor — `runtime-smoke-verification` hardcodes an example `GATEWAY_PORT` env var name

**File:** `.agents/skills/runtime-smoke-verification/SKILL.md:222, 247`
**Issue:** The skill uses `GATEWAY_PORT` / `GATEWAY_HTTP_PORT` as example env-var names in its grep recipes and workflow templates. This is mostly fine — the skill immediately shows *how to discover* the actual name via `grep -hE '^(GATEWAY|GATEWAY_HTTP)_PORT=' .env*` — but the workflow-template block on line 247 uses `${GATEWAY_PORT}` as a concrete placeholder that assumes one of the two names actually exists. If the project renamed its env var to `API_PORT` or `HTTP_PUBLIC_PORT` tomorrow, the workflow template would silently become wrong.
**Fix:** Replace `${GATEWAY_PORT}` in the workflow template with `${PUBLIC_HTTP_PORT}` (a role name, not a project-specific identifier) and add one line: "substitute with the actual env-var name returned by the grep recipe in §How to discover the health endpoint and port". Low-impact nit — the discovery recipe already handles the rename case; this just closes the last loop.

### IN-05: `infrastructure-guard` documents the env-template naming pattern imprecisely

**File:** `.agents/skills/infrastructure-guard/SKILL.md:56`
**Issue:** The grep recipe hardcodes two specific env-template filenames: `grep -rh '_PORT=' .env.example .env.docker.example 2>/dev/null | sort -u`. This is slightly tighter than the skill's own rule ("tracked env templates at the repository root"), because the recipe names the two current templates rather than enumerating whatever `.env*` files exist. If the project adds a third template (e.g., `.env.staging.example`), the grep will miss it and no reader will notice.
**Fix:** Use the broader glob the skill already uses elsewhere on the same file (line 79: `ls .env*`): replace the fixed file list with `grep -rh '_PORT=' .env* 2>/dev/null | sort -u`. This matches the same pattern used in `runtime-smoke-verification` (line 222) and avoids enumerating the current template set in the skill body.
