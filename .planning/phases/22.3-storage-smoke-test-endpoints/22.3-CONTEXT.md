# Phase 22.3: storage-smoke-test-endpoints - Context

**Gathered:** 2026-04-10
**Status:** Ready for planning

<domain>
## Phase Boundary

Temporary per-service HTTP debug endpoints that exercise the full StoragePort surface (upload/download/exists/getSignedUrl) on every bound bucket. Accessible via gateway REST through gRPC proxy. No env flag gating -- endpoints are temporary and will be removed after verification. Cleanup (delete) is a separate endpoint accepting a key returned by the smoke cycle.

Deliverables: gRPC methods in parser.proto and notifier.proto, smoke controllers in parser/notifier/gateway, gateway REST routes under `/test/`.

</domain>

<decisions>
## Implementation Decisions

### No env flag
- **D-01:** Smoke endpoints ship without any feature flag or env var gating. They are temporary code -- will be deleted after storage verification across all environments is complete.
- **D-02:** No NODE_ENV/isDev/isProd checks, no ENABLE_* vars. Code is unconditionally registered. This avoids the "works in dev, dormant in prod" code smell rejected in Phase 22.2.

### gRPC contract
- **D-03:** Two gRPC methods added to existing service proto files (parser.proto, notifier.proto):
  - `RunStorageSmoke` -- runs full cycle on ALL buckets of the service: upload test file -> exists (expect true) -> download (compare content) -> getSignedUrl. File is NOT deleted. Returns per-step results + test file key for each bucket.
  - `CleanupStorageSmoke(key)` -- deletes file by key, returns result.
- **D-04:** Proto changes go into existing parser.proto and notifier.proto (not a separate smoke.proto). Minimal diff, easy to remove later.
- **D-05:** RunStorageSmoke covers ALL buckets the service owns in one call:
  - Parser: runs cycle on `parser` bucket AND `reports` bucket, returns results for both.
  - Notifier: runs cycle on `reports` bucket only.
- **D-06:** RunStorageSmoke does NOT delete files. User inspects via MinIO/Garage WebUI, then calls CleanupStorageSmoke with the returned key when ready.

### Gateway REST routes
- **D-07:** Gateway exposes REST endpoints under `/test/` prefix:
  - `GET /test/parser/storage-service` -> calls parser.RunStorageSmoke via gRPC
  - `DELETE /test/parser/storage-service?key=...` -> calls parser.CleanupStorageSmoke via gRPC
  - `GET /test/notifier/storage-service` -> calls notifier.RunStorageSmoke via gRPC
  - `DELETE /test/notifier/storage-service?key=...` -> calls notifier.CleanupStorageSmoke via gRPC
- **D-08:** Gateway smoke controller lives in `apps/gateway/src/test/` and proxies gRPC calls to backend services, returning JSON results.

### Cross-service verification
- **D-09:** No dedicated cross-service endpoint. Both parser and notifier independently smoke-test the `reports` bucket. If both pass -- shared storage is proven to work. The `reports` bucket is the same physical bucket (`REPORTS_BUCKET = 'reports'`) accessed through the same `REPORTS_STORAGE` DI token in both services.
- **D-10:** Cross-service flow is verified manually: call parser smoke (reports bucket results OK) + call notifier smoke (reports bucket results OK) = shared storage works.

### Module structure
- **D-11:** Smoke controllers live in `test/` directory in each service:
  - `apps/parser/src/test/storage-smoke.controller.ts`
  - `apps/notifier/src/test/storage-smoke.controller.ts`
  - `apps/gateway/src/test/storage-smoke.controller.ts`
- **D-12:** `test/` directory is explicitly temporary -- entire directory deleted when smoke testing is complete. Clean separation from production code.
- **D-13:** Smoke controllers are registered in their service's root module imports (parser.module.ts, notifier.module.ts, gateway.module.ts) -- simple addition, simple removal.

### Claude's Discretion
- Proto message structure (SmokeResult, SmokeStepResult etc.)
- Test file content and naming (e.g., `smoke-test-{timestamp}.txt`)
- Response JSON shape from gateway
- Whether to wrap smoke controller in a SmokeModule or register controller directly
- Error handling approach (return error details in response vs throw)
- getSignedUrl expiry duration for test

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- StoragePort interface with 5 methods -- smoke cycle maps 1:1 to these methods
- Per-service StorageModule already wired: parser has PARSER_STORAGE + REPORTS_STORAGE, notifier has REPORTS_STORAGE
- DI tokens (PARSER_STORAGE, REPORTS_STORAGE) are Symbols -- inject in smoke controller same as health controller
- Proto generation pipeline (`pnpm generate:contracts`) already in Turbo -- adding rpc methods triggers codegen

### Established Patterns
- Health controllers inject storage via `@Inject(TOKEN)` -- smoke controllers follow the same pattern
- Gateway proxies gRPC calls to backends via client wrappers in `infrastructure/clients/`
- Proto files define service + rpc methods, codegen produces TypeScript interfaces
- Controllers registered in root module `controllers: [...]` array

### Integration Points
- Parser proto: add 2 rpc methods (RunStorageSmoke, CleanupStorageSmoke)
- Notifier proto: add same 2 rpc methods
- Parser/notifier: new `test/` directory with smoke gRPC controller
- Gateway: new `test/` directory with REST controller proxying gRPC smoke calls
- Root modules: register new controllers
- Proto codegen: re-run `pnpm generate:contracts`

</code_context>

<specifics>
## Specific Ideas

- Endpoints are explicitly temporary -- user will delete `test/` directories across all services after verification is complete
- RunStorageSmoke intentionally does NOT delete files so user can visually verify through MinIO/Garage WebUI before cleanup
- CleanupStorageSmoke accepts the key returned by RunStorageSmoke -- user controls when to delete
- Route prefix `/test/` clearly separates from production API surface (`/health/`, gRPC services)
- Pattern is extensible: `/test/cache-service`, `/test/persistence-service` etc. for future infrastructure verification
- Cross-service verification is manual: both services independently proving reports bucket access is sufficient proof

</specifics>

<deferred>
## Deferred Ideas

- `/test/cache-service` endpoints for Redis CacheModule verification -- same pattern, separate phase when needed
- `/test/persistence-service` for PostgreSQL verification -- same pattern
- Automated cross-service test (gateway orchestrates parser upload -> notifier download in one call) -- overkill for temporary debug endpoints
- Auth protection for smoke endpoints -- not needed since endpoints are temporary and will be removed

</deferred>
