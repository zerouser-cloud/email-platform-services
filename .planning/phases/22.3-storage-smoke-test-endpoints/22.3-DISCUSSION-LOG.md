## Env flag gating

| Option | Description | Selected |
|--------|-------------|----------|
| ENABLE_STORAGE_SMOKE | Dedicated env var, Zod sub-schema | |
| ENABLE_DEBUG_ENDPOINTS | General debug flag for all debug endpoints | |
| STORAGE_SMOKE_ENABLED | In STORAGE_* namespace | |
| No flag at all | Endpoints are temporary, no gating needed | ✓ |

**User's choice:** No flag. User challenged the premise -- env flags for behavior gating contradict 12-factor approach established in the project. Endpoints are temporary debug code, will be deleted after verification.
**Notes:** User explicitly stated: "Зачем мы вообще делаем какой-то флаг? У нас 12 факторное приложение, такие флаги вообще противоречат нашему подходу." This aligns with Phase 22.2 decision to reject env-gated auto-provisioning.

## Endpoint design

### Routing

| Option | Description | Selected |
|--------|-------------|----------|
| Only on services (direct HTTP) | Direct HTTP to parser/notifier, no gateway changes | |
| Through gateway too | Gateway proxies to backends | ✓ |

**User's choice:** Through gateway. Reason: in start:isolated, dev, and prod only gateway is exposed externally.

### Transport

| Option | Description | Selected |
|--------|-------------|----------|
| HTTP proxy in gateway | Gateway does HTTP fetch to backends | |
| gRPC methods for smoke | Standard gRPC like all other gateway-to-backend calls | ✓ |
| Only on services, docker exec | No gateway proxy, test via docker exec | |

**User's choice:** gRPC methods. Follows platform pattern.

### Proto organization

| Option | Description | Selected |
|--------|-------------|----------|
| In existing proto files | Add rpc to parser.proto and notifier.proto | ✓ |
| Separate smoke.proto | New proto file for smoke test service | |

**User's choice:** Existing proto files. Minimal diff, easy to remove.

### Contract shape

| Option | Description | Selected |
|--------|-------------|----------|
| One rpc, full cycle | RunStorageSmoke runs upload->exists->download->getSignedUrl->delete | |
| One rpc per operation | 5 separate rpc methods | |
| One rpc with action param | Single rpc with action selector | |
| Two rpc: cycle + cleanup | RunStorageSmoke (no delete) + CleanupStorageSmoke(key) | ✓ |

**User's choice:** Two rpc. User wanted to inspect files in WebUI before deletion. Suggested separate cleanup endpoint accepting key from smoke result.
**Notes:** User asked for 30-second pause before delete initially. Evolved to separate cleanup endpoint for better control.

### Bucket handling

| Option | Description | Selected |
|--------|-------------|----------|
| One rpc = all buckets | RunStorageSmoke tests all buckets of the service | ✓ |
| Bucket as parameter | Separate call per bucket | |

**User's choice:** All buckets in one call.

## Cross-service flow

**Discussion:** User asked what "smoke notifier" meant. Clarified that cross-service is proven by both services independently passing smoke on the same reports bucket. No dedicated cross-service endpoint needed.

**Decision:** Manual verification -- parser smoke OK on reports + notifier smoke OK on reports = shared storage works.
