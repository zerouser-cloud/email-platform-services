# Phase 22.3: storage-smoke-test-endpoints - Research

**Researched:** 2026-04-10
**Domain:** NestJS gRPC + REST smoke endpoints for S3 StoragePort verification
**Confidence:** HIGH

## Summary

This phase adds temporary debug endpoints to parser and notifier services that exercise the full StoragePort surface (upload, download, exists, getSignedUrl) on every bound bucket, then exposes those via gateway REST routes under `/test/`. The endpoints are unconditionally registered (no feature flag -- user decision D-01/D-02) and will be deleted after verification.

The main technical challenge is that **notifier has no gRPC server or proto file**. The SERVICE catalog defines notifier without a `grpc:` field, its `main.ts` does not call `connectMicroservice()`, and `notifier.proto` does not exist. CONTEXT.md decision D-03 assumes "existing service proto files (parser.proto, notifier.proto)" but notifier.proto is not existing -- it must be created. This requires: (1) creating `notifier.proto`, (2) adding gRPC config to `SERVICE.notifier` in the catalog, (3) wiring gRPC server in `notifier/main.ts`, (4) codegen. This is the single largest risk in the phase -- all other work (parser proto additions, gateway REST proxy, smoke controller logic) follows established patterns.

**Primary recommendation:** Create notifier.proto with only the 2 smoke rpc methods, add minimal gRPC server setup to notifier, implement smoke controllers following the same DI injection pattern as health controllers, and expose via gateway REST under `/test/`.

### Pattern 1: gRPC Smoke Controller (backend services)
**What:** Controller injecting StoragePort tokens via `@Inject()` and executing the full smoke cycle
**When to use:** Parser and notifier smoke controllers
**Reference:** Health controllers use identical DI injection pattern [VERIFIED: parser health.controller.ts lines 14-18]

```typescript
// Source: [VERIFIED: apps/parser/src/health/health.controller.ts pattern]
@Controller()
@ParserProto.ParserServiceControllerMethods()
export class StorageSmokeController implements Partial<ParserProto.ParserServiceController> {
  constructor(
    @Inject(PARSER_STORAGE) private readonly parserStorage: StoragePort,
    @Inject(REPORTS_STORAGE) private readonly reportsStorage: StoragePort,
  ) {}

  async runStorageSmoke(_request: CommonProto.Empty): Promise<ParserProto.StorageSmokeResponse> {
    // Run cycle on each bucket, collect results
  }

  async cleanupStorageSmoke(request: ParserProto.CleanupSmokeRequest): Promise<ParserProto.CleanupSmokeResponse> {
    // Delete by key from specified bucket
  }
}
```

**Key insight:** The `@ParserServiceControllerMethods()` decorator auto-registers all methods. After proto codegen, the new methods will be included in the decorator's method list. The controller implements `Partial<ParserServiceController>` because it only handles smoke methods, not the full service interface. [VERIFIED: generated parser.ts ParserServiceControllerMethods function, lines 589-609]

**IMPORTANT:** Actually, ts-proto generates a single `ParserServiceControllerMethods()` that registers ALL rpc methods. This means the smoke controller AND the existing ParserGrpcServer both need to implement the full interface -- or one controller handles everything. The established pattern is one controller per service (`ParserGrpcServer`). Adding a second controller that handles only smoke methods while the first handles the rest could cause conflicts with `@GrpcMethod` registration.

**Recommended approach:** Add smoke methods to the existing `ParserGrpcServer` controller (and create `NotifierGrpcServer` for notifier), OR create a separate smoke controller that selectively registers only smoke methods via manual `@GrpcMethod()` decorators instead of the all-in-one `@ParserServiceControllerMethods()`.

### Pattern 2: Selective gRPC Method Registration
**What:** Use `@GrpcMethod('ParserService', 'RunStorageSmoke')` manually instead of `@ParserServiceControllerMethods()` 
**When to use:** When a controller handles only a subset of service methods
**Why:** Avoids conflict with existing controller that already uses `@ParserServiceControllerMethods()`

```typescript
// Source: [VERIFIED: @nestjs/microservices GrpcMethod decorator pattern]
@Controller()
export class StorageSmokeController {
  constructor(
    @Inject(PARSER_STORAGE) private readonly parserStorage: StoragePort,
    @Inject(REPORTS_STORAGE) private readonly reportsStorage: StoragePort,
  ) {}

  @GrpcMethod('ParserService', 'RunStorageSmoke')
  async runStorageSmoke(_request: CommonProto.Empty): Promise<ParserProto.StorageSmokeResponse> {
    // ...
  }

  @GrpcMethod('ParserService', 'CleanupStorageSmoke')
  async cleanupStorageSmoke(request: ParserProto.CleanupSmokeRequest): Promise<ParserProto.CleanupSmokeResponse> {
    // ...
  }
}
```

This is cleaner because:
1. Smoke controller stays in `test/` directory -- easy to delete
2. Existing `ParserGrpcServer` is untouched (no need to implement smoke methods there)
3. NestJS allows multiple controllers to handle methods from the same gRPC service [ASSUMED]

### Anti-Patterns to Avoid
- **Adding smoke methods to ParserGrpcServer:** Mixes temporary debug code with permanent service code. Use separate controller with manual `@GrpcMethod()`.
- **Reading NODE_ENV or ENABLE_SMOKE_TEST:** Violates D-01, D-02, and twelve-factor skill.
- **Importing StoragePort implementations directly:** Inject via DI tokens (PARSER_STORAGE, REPORTS_STORAGE).
- **Creating a separate smoke.proto:** Violates D-04. Methods go into existing service proto files.

## Common Pitfalls

### Pitfall 1: Dual Controller gRPC Method Conflict
**What goes wrong:** Two controllers both decorated with `@ParserServiceControllerMethods()` -- NestJS may silently override handlers or throw.
**Why it happens:** ts-proto generates an all-or-nothing decorator that registers every rpc method.
**How to avoid:** Use manual `@GrpcMethod('ParserService', 'MethodName')` on the smoke controller. Only `ParserGrpcServer` uses the generated `@ParserServiceControllerMethods()`.
**Warning signs:** Methods not responding, unexpected 'not implemented' errors.

### Pitfall 2: Notifier gRPC Port Not Configured
**What goes wrong:** Notifier starts but gRPC server silently fails because no port is defined.
**Why it happens:** `SERVICE.notifier` currently has no `grpc:` config, and env schemas don't include gRPC port.
**How to avoid:** Add `grpc: { port: 50055, serviceName: 'NotifierService' }` to SERVICE catalog. Ensure port 50055 is consistent across env files.
**Warning signs:** Gateway cannot connect to notifier gRPC, connection refused errors.

### Pitfall 3: Proto Field Number Conflicts
**What goes wrong:** New proto messages collide with existing field numbers.
**Why it happens:** Adding messages/fields to an existing proto file without checking existing field numbers.
**How to avoid:** New messages (SmokeResult etc.) use their own field numbering starting from 1. New rpc methods don't have field numbers. Only risk is if adding fields to existing messages (not needed here).

### Pitfall 4: Gateway gRPC Client Proto Path
**What goes wrong:** Gateway can't find proto file at runtime because `PROTO_DIR` is not configured for gateway.
**Why it happens:** Gateway currently doesn't use gRPC clients, so it may not have proto path configuration.
**How to avoid:** Use `resolveProtoPath()` from foundation with the correct proto directory. Ensure `PROTO_DIR` is available in gateway env or use the contracts package's built-in path.
**Warning signs:** "ENOENT: no such file or directory" errors on startup.

### Pitfall 5: Smoke File Content Comparison
**What goes wrong:** Downloaded content doesn't match uploaded content due to encoding.
**Why it happens:** Buffer vs string conversion, content-type mismatch.
**How to avoid:** Upload a simple text string as `Buffer.from('...')` with `text/plain` content type. Compare downloaded buffer with `.toString()`.

### Smoke Cycle Logic (per bucket)

```typescript
// Source: [design based on StoragePort interface -- storage.interfaces.ts]
async function runSmokeCycle(storage: StoragePort, bucket: string): Promise<BucketResult> {
  const testKey = `smoke-test-${Date.now()}.txt`;
  const testContent = Buffer.from(`smoke-test-payload-${Date.now()}`);
  const steps: StepResult[] = [];

  // Step 1: upload
  try {
    await storage.upload(testKey, testContent, 'text/plain');
    steps.push({ step: 'upload', success: true, detail: '' });
  } catch (err) {
    steps.push({ step: 'upload', success: false, detail: String(err) });
    return { bucket, testKey, steps, allPassed: false };
  }

  // Step 2: exists
  try {
    const found = await storage.exists(testKey);
    steps.push({ step: 'exists', success: found, detail: found ? '' : 'exists returned false' });
  } catch (err) {
    steps.push({ step: 'exists', success: false, detail: String(err) });
  }

  // Step 3: download + compare
  try {
    const downloaded = await storage.download(testKey);
    const match = downloaded.equals(testContent);
    steps.push({ step: 'download', success: match, detail: match ? '' : 'content mismatch' });
  } catch (err) {
    steps.push({ step: 'download', success: false, detail: String(err) });
  }

  // Step 4: getSignedUrl
  try {
    const url = await storage.getSignedUrl(testKey, 300_000); // 5 minutes
    steps.push({ step: 'getSignedUrl', success: url.length > 0, detail: url });
  } catch (err) {
    steps.push({ step: 'getSignedUrl', success: false, detail: String(err) });
  }

  const allPassed = steps.every((s) => s.success);
  return { bucket, testKey, steps, allPassed };
}
```

// Source: [design based on NestJS ClientGrpc pattern]
@Controller('test')
export class StorageSmokeController {
  private parserService: ParserProto.ParserServiceClient;
  private notifierService: NotifierProto.NotifierServiceClient;

  constructor(
    @Inject('PARSER_PACKAGE') private readonly parserClient: ClientGrpc,
    @Inject('NOTIFIER_PACKAGE') private readonly notifierClient: ClientGrpc,

  onModuleInit() {
    this.parserService = this.parserClient.getService<ParserProto.ParserServiceClient>('ParserService');
    this.notifierService = this.notifierClient.getService<NotifierProto.NotifierServiceClient>('NotifierService');
  }

  @Get('parser/storage-service')
  runParserSmoke() {
    return this.parserService.runStorageSmoke({});
  }

  @Delete('parser/storage-service')
  cleanupParserSmoke(@Query('key') key: string, @Query('bucket') bucket: string) {
    return this.parserService.cleanupStorageSmoke({ key, bucket });
  }
}

## Open Questions

1. **Notifier gRPC infrastructure scope**
   - What we know: Notifier has no gRPC server, proto file, or catalog config. Adding full gRPC support requires 6-7 changes.
   - What's unclear: Is this acceptable scope for a "temporary smoke test" phase? The gRPC infrastructure will remain even after smoke endpoints are removed.
   - Recommendation: Proceed -- gRPC on notifier will be needed eventually (other phases may add gRPC methods). The smoke phase is a natural catalyst. Flag to user that gRPC setup is permanent while smoke endpoints are temporary.

2. **CleanupStorageSmoke bucket identification**
   - What we know: D-06 says cleanup accepts a key. Parser has 2 buckets. User needs to specify which bucket to clean.
   - What's unclear: Should cleanup accept `bucket` + `key`, or should each bucket result include enough info to route cleanup?
   - Recommendation: CleanupSmokeRequest should include both `bucket` (string) and `key` (string). The RunStorageSmoke response includes the bucket name in each result, so the user knows which bucket to specify.

3. **Gateway proto path resolution**
   - What we know: Gateway currently has no gRPC client setup (GrpcClientsModule is empty).
   - What's unclear: How to resolve proto file paths in gateway (PROTO_DIR env var or contracts package path).
   - Recommendation: Use `CONTRACTS_PROTO_DIR` exported from `@email-platform/contracts` (already exported in index.ts). This avoids adding new env vars.
