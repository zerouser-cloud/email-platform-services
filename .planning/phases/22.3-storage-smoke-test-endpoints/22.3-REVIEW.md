## Summary

Phase 22.3 adds storage smoke-test endpoints across three tiers: gateway (HTTP → gRPC proxy via `SmokeTestModule`), parser (gRPC handler via `StorageSmokeController`), and notifier (gRPC handler via `StorageSmokeController`). Proto contracts are correctly defined in both `parser.proto` and `notifier.proto`. The `packages/contracts/src/index.ts` barrel and `packages/config/src/catalog/services.ts` are untouched and correct.

The implementation is structurally sound with no critical security issues or data-loss risks. Three warnings and three informational issues are noted below.

## Warnings

### WR-01: `SmokeBucketEntry.token` field is declared but never read

**File:** `apps/parser/src/test/storage-smoke.controller.ts:12-28`

**Issue:** The `SmokeBucketEntry` interface declares a `token: symbol` field (line 12), and each entry is constructed with `token: PARSER_STORAGE` / `token: REPORTS_STORAGE` (lines 26-27), but no code path ever reads `entry.token`. The notifier counterpart (`apps/notifier/src/test/storage-smoke.controller.ts`) defines the same `SmokeBucketEntry` interface *without* the `token` field, confirming it serves no purpose here.

**Fix:** Remove the `token` property from the interface and from the two array-element literals:

```typescript
// Before
interface SmokeBucketEntry {
  readonly token: symbol;
  readonly bucket: string;
  readonly storage: StoragePort;
}
this.buckets = [
  { token: PARSER_STORAGE, bucket: PARSER_STORAGE_BUCKET, storage: this.parserStorage },
  { token: REPORTS_STORAGE, bucket: REPORTS_BUCKET, storage: this.reportsStorage },
];

// After
interface SmokeBucketEntry {
  readonly bucket: string;
  readonly storage: StoragePort;
}
this.buckets = [
  { bucket: PARSER_STORAGE_BUCKET, storage: this.parserStorage },
  { bucket: REPORTS_BUCKET, storage: this.reportsStorage },
];
```

### WR-02: `config.get<string>(...)!` non-null assertions bypass validated config in `SmokeTestModule`

**File:** `apps/gateway/src/test/smoke-test.module.ts:23,35`

**Issue:** The `useFactory` functions call `config.get<string>('PARSER_GRPC_URL')!` and `config.get<string>('NOTIFIER_GRPC_URL')!`. These env vars are defined in `TopologySchema` (generated from `SERVICE` catalog, which includes `notifier` and `parser`), and `GatewayEnvSchema` composes `TopologySchema` — so the values are guaranteed non-null at bootstrap. However, the non-null assertion `!` on `ConfigService.get()` is a project-wide anti-pattern: if the key name ever drifts or a typo is introduced, the error surfaces as a runtime crash rather than at startup validation. The pattern used everywhere else in the codebase is to extract typed config via `loadGlobalConfig()` in `main.ts` and inject it directly, or to use `SERVICE.parser.envKeys.GRPC_URL` to drive the key.

**Fix:** Use the typed env key from the service catalog to eliminate the magic string, and keep the `!` only as a last resort with an inline comment noting the guaranteed presence:

```typescript
url: config.get<string>(SERVICE.parser.envKeys.GRPC_URL!)!,
// ...
url: config.get<string>(SERVICE.notifier.envKeys.GRPC_URL!)!,
```

This at least ties the key to the single source of truth in `services.ts` and makes any catalog renaming a compile error.

### WR-03: `notifier` is registered as a gRPC microservice but `SmokeTestModule` in gateway treats it as a gRPC server — notifier has no `GrpcClientsModule` registration

**File:** `apps/gateway/src/test/smoke-test.module.ts:28-39`

**Issue:** `SmokeTestModule` creates its own `ClientsModule.registerAsync` for both `PARSER_SMOKE_CLIENT` and `NOTIFIER_SMOKE_CLIENT`. This is correct architecture for ad-hoc test clients. However, `apps/notifier/src/main.ts` (line 15-17) registers the gRPC microservice with `app.connectMicroservice(createGrpcServerOptions(...))` and starts it with `await app.startAllMicroservices()`. The notifier gRPC server handles `RunStorageSmoke` and `CleanupStorageSmoke` via `@GrpcMethod` decorators in `apps/notifier/src/test/storage-smoke.controller.ts`. But `apps/notifier/src/notifier.module.ts` uses `LoggingModule.forHttpAsync('notifier')` (line 19) rather than `forGrpcAsync`. A pure-gRPC service like notifier should use `LoggingModule.forGrpcAsync` to get the correct gRPC logging interceptors. Using `forHttpAsync` leaves the gRPC transport unlogged and omits the `GrpcLoggingInterceptor` and `CorrelationInterceptor` configured in the gRPC logging path.

**Fix:** Change the logging module in `notifier.module.ts`:

```typescript
// Before
LoggingModule.forHttpAsync('notifier'),

// After
LoggingModule.forGrpcAsync('notifier'),
```

### IN-01: `parser.grpc-server.ts` stub methods emit `NotImplementedException` but are registered via `@ParserServiceControllerMethods()` — same gRPC service now has split handler registration

**File:** `apps/parser/src/infrastructure/grpc/parser.grpc-server.ts:44-54`

**Issue:** `RunStorageSmoke` and `CleanupStorageSmoke` are stubbed in `ParserGrpcServer` (lines 44-54) with `throw new NotImplementedException(...)`. At the same time, `apps/parser/src/test/storage-smoke.controller.ts` registers the real implementations via `@GrpcMethod('ParserService', 'RunStorageSmoke')` and `@GrpcMethod('ParserService', 'CleanupStorageSmoke')`. NestJS resolves `@GrpcMethod` decorators by method name matching, and when two handlers for the same service+method exist in different controllers, the last-registered one wins (non-deterministic in large modules). The inline comment says "implemented in Plan 02" indicating this is intentional interim state, but the stubs should be removed from `ParserGrpcServer` now that Plan 02 is complete to avoid the dual-registration ambiguity.

**Fix:** Remove `runStorageSmoke` and `cleanupStorageSmoke` stub methods (lines 42-54) from `apps/parser/src/infrastructure/grpc/parser.grpc-server.ts`. The real implementation in `StorageSmokeController` is sufficient.

### IN-02: `Date.now()` called twice within `runSmokeCycle` creates content/key timestamp mismatch

**File:** `apps/parser/src/test/storage-smoke.controller.ts:61-62`, `apps/notifier/src/test/storage-smoke.controller.ts:57-58`

**Issue:** Both smoke controllers call `Date.now()` independently for `testKey` (line 61/57) and `testContent` (line 62/58). In practice the two calls will return the same millisecond, but under heavy load or a slow JS event loop tick they could differ, meaning `testKey` and the embedded `testContent` payload would carry different timestamps. This makes the download content comparison unreliable as a diagnostic tool (the content would still match itself, but the key and embedded payload would be inconsistent for human inspection).

**Fix:** Capture `Date.now()` once:

```typescript
const now = Date.now();
const testKey = `smoke-test-${now}.txt`;
const testContent = Buffer.from(`smoke-test-payload-${now}`);
```

### IN-03: `SMOKE_TEST_CONTENT_TYPE` and `SMOKE_SIGNED_URL_EXPIRY_MS` constants are duplicated across parser and notifier smoke controllers

**File:** `apps/parser/src/test/storage-smoke.controller.ts:8-9`, `apps/notifier/src/test/storage-smoke.controller.ts:7-8`

**Issue:** Both files independently define identical module-scoped constants with the same values (`'text/plain'` and `300_000`). This is minor for temporary smoke-test code, but if the expiry needs changing before these endpoints are removed, both files must be updated.

**Fix:** Either accept the duplication given the temporary nature of this code (mark with `// TODO: remove after storage verification`), or extract to a shared `smoke-test.constants.ts` file co-located in each service's `test/` directory. No action strictly required.
