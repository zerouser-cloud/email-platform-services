<decisions>
## Implementation Decisions

### Direction split (from v2 research, locked)

- **D-01:** `infrastructure/` делится на три подпапки по Cockburn+Uncle Bob semantics:
  - `inbound/` — primary/driving adapters (translate external input → application ports)
  - `outbound/` — secondary/driven adapters (implement outbound ports, translate domain → external)
  - `bootstrap/` — Ring 4 framework glue (not adapters — composition root machinery: config, health, throttle, logging)

- **D-02:** Feature-slicing внутри каждого направления (orthogonal axis to direction):
  - `outbound/persistence/{aggregate}/` (per aggregate: user/, token/, campaign/)
  - `outbound/grpc-clients/{upstream}/` (per upstream service: auth/, sender/, etc.)
  - `outbound/http-clients/{vendor}/` (per vendor: telegram/, appstorespy/, cloud-functions/)
  - `outbound/publishers/{event-type}/` (per event type)
  - `bootstrap/{concern}/` (per cross-cutting concern: config/, health/, throttle/, logging/)

- **D-03:** gRPC controllers: один файл per proto service в `inbound/grpc/{service}.controller.ts` — NestJS idiom (один `@GrpcMethod` class implements full proto-service interface), не исключение. Proto service IS the inbound boundary feature for the bounded context.

- **D-04:** REST controllers feature-slice где применимо: `inbound/rest/{feature}/{feature}.controller.ts` для multi-endpoint groups. Single file для trivial case (currently только HealthController — но он уходит в bootstrap/health/ per D-08, поэтому `inbound/rest/` пока пустая).

- **D-05:** RMQ consumers feature-sliced per event/queue: `inbound/rmq/{event-type}.consumer.ts` (notifier only сейчас).

### Composition (Area 1)

- **D-06:** **Keep composer pattern везде.** Category-level composer module (GrpcClientsModule / PersistenceModule / HttpClientsModule / PublishersModule) импортирует все per-feature sub-modules. Root `{svc}.module.ts` импортирует composers, не individual sub-modules. Rationale: root чище (одна строка на категорию), scalable (добавление 6-го upstream — add sub-module, root не трогаем), consistent с foundation.PersistenceModule pattern.

### Bootstrap @Module wrapping (Area 4)

- **D-07:** **Все bootstrap concerns через @Module:** `{Svc}ConfigModule`, `HealthModule`, `ThrottleModule` (gateway only), foundation `LoggingModule`. Root `{svc}.module.ts` импортирует эти modules, не их internal providers/controllers напрямую.

- **D-08:** **Создать `HealthModule` в `bootstrap/health/health.module.ts`** для всех 6 сервисов (сейчас health.controller регистрируется напрямую в root `controllers: []`). Module wraps `TerminusModule.forRootAsync` + `HealthController`. Root импортирует `HealthModule` вместо `HealthController` в `controllers[]`.

### DI tokens placement (Area 2)

- **D-09:** ~~gRPC client tokens переезжают в `outbound/grpc-clients/clients.constants.ts`~~ **CORRECTED per RESEARCH OQ-1 (2026-04-20):** original wording referenced tokens (`AUTH_SERVICE` etc.) that don't exist — actual tokens (`AUTH_CLIENT_GRPC`, `AUTH_GRPC_HEALTH`, etc.) are **already per-sub-module** in `infrastructure/clients/{upstream}/{upstream}-client.module.ts`, and ESLint Override 7 bans `*-client.constants.ts` in gRPC client paths (established 999.7.x precedent). **Final D-09:** tokens stay per-sub-module. Relocation of module files from `infrastructure/clients/{upstream}/` to `outbound/grpc-clients/{upstream}/` (subsumed by D-02) automatically satisfies the "tokens near consumers" intent. No new `clients.constants.ts` file created.

- **D-10:** `{SVC}_CONFIG` token + `{Svc}ConfigModule` оба в `bootstrap/config/`:
  - `bootstrap/config/{svc}-config.constants.ts` — `{SVC}_CONFIG = Symbol(...)`
  - `bootstrap/config/{svc}-config.module.ts` — `@Global()` module (per 999.11.1 Rule 3 fix)
  - `bootstrap/config/{svc}-env.schema.ts` — Zod schema (перемещается из infrastructure/config/)
  - `bootstrap/config/{svc}-config.provider.ts` — provider (перемещается из infrastructure/config/)

- **D-11:** Root `{svc}.constants.ts` удаляется если становится пустым после D-10 migration. **CLARIFIED per RESEARCH (2026-04-20):** applies ONLY to gateway. Other 5 services (auth, sender, parser, audience, notifier) keep their root `{svc}.constants.ts` — contain cross-folder **domain port Symbols** (`LOGIN_PORT`, `CAMPAIGN_REPOSITORY_PORT`, etc.) consumed by `infrastructure/inbound/grpc/` controllers AND `infrastructure/outbound/persistence/` repositories. Per `infrastructure-client-layering` skill, cross-folder tokens stay in root. Only gateway's constants (single member `GATEWAY_CONFIG` post-999.11.1) becomes empty after D-10 and is deleted.

### Exports (Area 3)

- **D-12:** `index.ts` barrel везде где ≥ 2 exports:
  - Feature folders (e.g. `outbound/grpc-clients/auth/index.ts` → export `AuthClientModule` + optional token re-export)
  - Composer level (e.g. `outbound/grpc-clients/index.ts` → export `GrpcClientsModule` + все 5 tokens)
  - Direction level (`outbound/index.ts`) — только если root импортирует 2+ items оттуда (редко нужно с composer pattern — вероятно не создаём)
  - Consistent с packages/foundation convention

### Migration discipline

- **D-13:** **Behavior-preserving refactor.** PROJECT.md constraint: без бизнес-логики, без тестов. После каждого commit — `pnpm lint && pnpm build` exit 0 (per-commit gate from 999.11.1 D-14 precedent).

Evidence → `/tmp/999.11.2-native-ready.json` + `/tmp/999.11.2-isolated-ready.json`, вложить в финальный SUMMARY.md.

## Specific Ideas

- User's exact phrasing (2026-04-20): «в таком подходе у нас тогда получается не per feature? То есть внешнее у нас будет в outbound, создание клиентов для grpc, rabbit, redis, s3?» — resolved in discussion: **direction-slicing и feature-slicing ортогональны**, оба применяются. Ось 1 = direction (inbound/outbound/bootstrap per Cockburn+Uncle Bob — mandatory). Ось 2 = feature (внутри каждого направления — Screaming Architecture).
- User's exact phrasing: «фичи от обязки, инфры, машинерии» разделять — addressed by Cockburn+Uncle Bob split: adapters (inbound/outbound) vs framework glue (bootstrap). Framework machinery (config, health, throttle, logging) выделены в `bootstrap/`, отдельно от adapters — это и есть разделение «features vs infra machinery», которое просил user.
- User's exact phrasing: хочу «screaming architecture» подход — reconciled: screaming на двух уровнях. Service level (`apps/auth`, `apps/gateway`) кричит boundary. Feature level (`outbound/grpc-clients/auth/`, `outbound/persistence/user/`) кричит feature. gRPC/REST/RMQ labels — это transport boundary внутри inbound, не нарушение SA (Screaming Architecture позволяет technology-boundary labels на правильном уровне).
