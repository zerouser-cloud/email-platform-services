## Decisions Made

See frontmatter `key-decisions`. Most notable:

1. **D-SENDER-01 (HealthModule dual-wiring)** — Sender is the first service in Phase 999.11.2 whose HealthController injects BOTH `DATABASE_HEALTH` and `REDIS_HEALTH`. Foundation's `PersistenceModule` and `CacheModule` are both NOT `@Global()`, so HealthModule explicitly imports both with `CacheModule.forRootAsync({ namespace: 'sender' })` preserving the service-level Redis namespace. This extends Plan 01's D-AUTH-01 pattern to dual-wiring.

2. **D-SENDER-02 (First HTTP composer)** — `HttpClientsModule` is the first composer of its kind in the codebase. Its shape mirrors `GrpcClientsModule` exactly (single-sub wrapping `CloudFnClientModule.forRoot()`), establishing the template for Plans 04 (parser → appstorespy) and 05 (notifier → telegram). Keeping the composer layer for one sub-module is justified per D-06 verbatim — future vendors added by editing the imports/exports array, not by restructuring the root.

3. **D-SENDER-03 (Pitfall 3 net-cancel)** — The research identified Pitfall 3 as a depth-shift hazard in cloudfn.module.ts after SENDER_CONFIG relocates to `bootstrap/config/`. Inspection during Task 5 confirmed the file previously imported SENDER_CONFIG via `../../../sender.constants` (3 ..). The cloudfn.module.ts move deepens the source by 1 level, AND the SENDER_CONFIG relocation deepens the target by 1 level (root → bootstrap/config/), so the net `..` count is preserved at 3. The new import reads `../../../bootstrap/config/sender-config.constants` — comment added to the module documenting the cancellation so future readers don't attempt a "fix".

4. **App-level composer naming** — `AppPersistenceModule` chosen over `PersistenceModule` (identical to Plans 01 and 02's decision) to avoid name collision with foundation's module inside `sender.module.ts` imports. `HttpClientsModule` and `GrpcClientsModule` don't need the `App` prefix because foundation has no modules with those names.

5. **@Global() config module preservation with 5 slice tokens** — Sender's `SenderConfigModule` exports `SENDER_CONFIG` + 4 narrow slices (`PERSISTENCE_CONFIG_PORT`, `LOGGING_CONFIG_PORT`, `CACHE_CONFIG_PORT`, `GRPC_CLIENT_CONFIG_PORT`) — one more than audience (which has no cache consumer). The `CACHE_CONFIG_PORT` slice is consumed inside `CacheModule.forRootAsync({ namespace: 'sender' })` → `useFactory` chain within foundation.
