## Decisions Made

See frontmatter `key-decisions`. Most notable:

1. **D-PARSER-01 (HealthModule storage-wiring)** — Parser is the first service in Phase 999.11.2 whose HealthController injects `PARSER_STORAGE_HEALTH` through a service-owned storage composer. Foundation has no global storage module, so HealthModule explicitly imports the parser `AppStorageModule` (which transitively imports `BucketModule`, which binds `PARSER_STORAGE_HEALTH` via `PrivateStorageModule.forBucket(...)`). This extends Plan 01's DATABASE_HEALTH-via-PersistenceModule pattern and Plan 03's REDIS_HEALTH-via-CacheModule pattern to a third propagation channel.

2. **D-PARSER-02 (Four-composer milestone)** — Parser is the only service in the per-service migration waves that exercises all four outbound composer categories (persistence + grpc-clients + http-clients + storage). No other service will need all four: audience has no HTTP vendor + no storage; sender has no storage; auth/notifier have neither grpc-clients nor http-clients nor storage. The plan's 6-task atomic commit was sized accordingly (over the standard 2-3 target).

3. **D-PARSER-03 (Storage double-module canonical split)** — The old `infrastructure/storage/` had two modules: `ParserStorageModule` (private bucket wrapper) + `StorageModule` (composer with inline `SharedNamespaceModule.forNamespace({namespace:'reports',...})`). The new `infrastructure/outbound/storage/` canonically separates the three responsibilities: (a) `bucket/bucket.module.ts` holds the private bucket wrapper (class renamed `ParserStorageModule` → `BucketModule` to match folder-name convention, matching Plan 01's per-aggregate sub-module naming); (b) `reports/reports.module.ts` extracts the inline `SharedNamespaceModule.forNamespace` block into a dedicated sub-module with the exact same options copied verbatim; (c) `storage.module.ts` becomes the composer `AppStorageModule` importing both sub-modules. DC-06 legitimate composition is preserved — every capability from the old tree is reachable through `AppStorageModule`.

4. **D-PARSER-04 (Pitfall 3 net-cancel second proof)** — `appstorespy.module.ts` previously imported `PARSER_CONFIG` via `../../../parser.constants` (3 `..`). The module's own move deepens depth by 1 (`infrastructure/clients/appstorespy/` → `infrastructure/outbound/http-clients/appstorespy/`), AND the `PARSER_CONFIG` relocation changes target (`parser.constants` at src root → `bootstrap/config/parser-config.constants` 2 levels deep into infrastructure). Net: the new relative import `../../../bootstrap/config/parser-config.constants` still reads 3 `..` but points into the bootstrap/config slice instead of src. This mirrors Plan 03's sender `cloudfn.module.ts` net-cancel pattern.

5. **App-level composer naming** — `AppPersistenceModule`, `AppStorageModule` (App* prefix) to avoid name collisions with foundation's `PersistenceModule`, `StorageModule`, `SharedStorageModule`. `GrpcClientsModule`, `HttpClientsModule` don't need the `App` prefix because foundation has no modules with those names. Consistent with Plans 01/02/03 App-prefix convention.

6. **@Global() config module preservation with 6 slice tokens** — Parser's `ParserConfigModule` exports `PARSER_CONFIG` + 5 narrow slices (`PERSISTENCE_CONFIG_PORT`, `LOGGING_CONFIG_PORT`, `STORAGE_CORE_CONFIG_PORT`, `PUBLIC_STORAGE_CONFIG_PORT`, `GRPC_CLIENT_CONFIG_PORT`) — the most slice tokens of any service in this wave. `STORAGE_CORE_CONFIG_PORT` + `PUBLIC_STORAGE_CONFIG_PORT` are consumed inside `PrivateStorageModule.forBucket(...)` + `SharedNamespaceModule.forNamespace(...)` → `useFactory` chains within foundation.
