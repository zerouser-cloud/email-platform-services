## User Constraints (from CONTEXT.md)

### Locked Decisions

**Direction split (from v2 research, locked)**

- **D-01** `infrastructure/` делится на три подпапки по Cockburn+Uncle Bob semantics:
  - `inbound/` — primary/driving adapters (translate external input → application ports)
  - `outbound/` — secondary/driven adapters (implement outbound ports, translate domain → external)
  - `bootstrap/` — Ring 4 framework glue (not adapters — composition root machinery: config, health, throttle, logging)
- **D-02** Feature-slicing внутри каждого направления (orthogonal axis to direction):
  - `outbound/persistence/{aggregate}/` (per aggregate: user/, token/, campaign/)
  - `outbound/grpc-clients/{upstream}/` (per upstream service: auth/, sender/, etc.)
  - `outbound/http-clients/{vendor}/` (per vendor: telegram/, appstorespy/, cloud-functions/)
  - `outbound/publishers/{event-type}/` (per event type)
  - `bootstrap/{concern}/` (per cross-cutting concern: config/, health/, throttle/, logging/)
- **D-03** gRPC controllers: один файл per proto service в `inbound/grpc/{service}.controller.ts` — NestJS idiom (один `@GrpcMethod` class implements full proto-service interface), не исключение. Proto service IS the inbound boundary feature for the bounded context.
- **D-04** REST controllers feature-slice где применимо: `inbound/rest/{feature}/{feature}.controller.ts` для multi-endpoint groups. Single file для trivial case (currently только HealthController — но он уходит в bootstrap/health/ per D-08, поэтому `inbound/rest/` пока пустая).
- **D-05** RMQ consumers feature-sliced per event/queue: `inbound/rmq/{event-type}.consumer.ts` (notifier only сейчас).

- **D-06** **Keep composer pattern везде.** Category-level composer module (GrpcClientsModule / PersistenceModule / HttpClientsModule / PublishersModule) импортирует все per-feature sub-modules. Root `{svc}.module.ts` импортирует composers, не individual sub-modules.

## Executive Summary

Phase 999.11.2 is a **pure physical-tree refactor**: `apps/{svc}/src/infrastructure/` is decomposed into Cockburn primary/secondary + Uncle Bob Ring 3/4 sub-bins (`inbound/`/`outbound/`/`bootstrap/`), with intra-direction feature-slicing. No application code, no domain code, no controller bodies, no adapter bodies are rewritten — only files move and their imports are updated.

**Per-service file moves (measured from current tree):**

| Service | Moves | Creates (new modules/barrels) | Deletes |
|---|---|---|---|
| gateway | 14 | ~8 | 1 (`gateway.constants.ts` per D-11) + 2 empty dirs |
| auth | 8 | ~5 | 0 (root constants stays — see §6) + 0 |
| sender | 11 | ~6 | 0 + 0 |
| parser | 15 | ~7 (including 2 storage sub-modules) | 0 + 0 |
| audience | 9 | ~5 | 0 + 0 |
| notifier | 8 | ~5 | 0 + 3 empty dirs |
| **totals** | **≈ 65 moves** | **≈ 36 creates** | **1 file + 5 empty dirs** |

**Creates breakdown:** 6 × `HealthModule` (D-08), 6 × `{Svc}ConfigModule`-relocated barrels + per-concern bootstrap index, 5 × GrpcClientsModule composer relocated / created, 3 × PersistenceModule app-level composer (auth/parser/audience wrap their 1-aggregate sub-module — sender already single aggregate; see §4), 3 × HttpClientsModule composer (sender + parser + notifier), parser storage composer, notifier publishers shell (future).

**Primary recommendation:** ship as **~11 atomic commits** (bullseye strategy — per-service commits grouped by direction, with the per-service tree ready at end of each commit, so `pnpm build` is green at every checkpoint). See §7 for the exact sequence. Final commit aggregates CLAUDE.md + `.eslintrc.js` + skill verification + D-15 dual-mode smoke evidence per 999.11.1 precedent.

Key risks are well-bounded:
1. Per-commit `pnpm lint && pnpm build` gate catches every broken import immediately.
2. Most moves are `git mv` + relative-path fix, which TypeScript + ESLint resolve statically (no runtime dependency walk).
3. D-15 dual-mode smoke gate at the end catches any DI-wiring regression (the only category of breakage that `tsc` can miss — e.g., `@Global()` visibility + `@Inject()` provider lookup).

The two subtle issues planners must watch:
- **D-09 is already materialised** — gRPC client tokens (`AUTH_CLIENT_GRPC`, `AUTH_GRPC_HEALTH`, etc.) are **already per-module**, exported from each `{upstream}-client.module.ts`. CONTEXT.md's reference to `AUTH_SERVICE` etc. is stale naming from an earlier draft. No new `clients.constants.ts` file is needed; the relocation of these module files to `outbound/grpc-clients/{upstream}/` automatically satisfies D-09. See §6 and §13 OQ-1.
- **D-11 empties only gateway** — 5 of 6 root `{svc}.constants.ts` files still carry domain port Symbols (`USER_REPOSITORY_PORT`, `LOGIN_PORT`, etc.) that are deliberately root-scoped (cross-folder: application layer + infrastructure adapters both import them). Only `gateway.constants.ts` (single member: `GATEWAY_CONFIG`) becomes empty after D-10 and is deleted. See §6.

### Anti-Patterns to Avoid

- **Mixing inbound + outbound under a single `adapters/` bucket** — collapses Cockburn's primary/secondary distinction.
- **Moving adapters into `bootstrap/`** — `bootstrap/` is Ring 4 framework glue only (config/health/throttle/logging).
- **Creating `inbound/rest/health/`** — D-08 relocates HealthController to `bootstrap/health/`; it is not an inbound adapter.
- **Creating `clients.constants.ts` at `outbound/grpc-clients/`** — would violate ESLint Override 7. gRPC tokens stay per-module, derived via `defineGrpcClient`. See §6 for the correct interpretation of D-09.
- **Adding `index.ts` when only 1 export exists** — D-12 says "barrel где ≥ 2 exports". Respect it to avoid boilerplate.
- **Re-exporting the raw `defineGrpcClient` result object** — §infrastructure-client-layering SKILL Anti-Pattern 4. Each module exports only the named tokens (`AUTH_CLIENT_GRPC`, `AUTH_GRPC_HEALTH`) alongside the module class.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---|---|---|---|
| TerminusModule wiring | Custom health aggregator | `TerminusModule.forRootAsync()` wrapped by new `HealthModule` | Battle-tested, supports HealthCheckService DI |
| Env schema loading | New loader | `loadConfig(XxxSchema)` from `@email-platform/config` | Already cached by schema ref (999.11.1 precedent) |
| gRPC token derivation | New `clients.constants.ts` hand-written symbols | `defineGrpcClient<T>({ service, clientToken })` — emits `grpcToken` + `healthToken` from catalog ID | Single source of truth; ESLint Override 7 ENFORCES this pattern |
| ConfigModule @Global wiring | New decorator logic | Existing `@Global() @Module({})` + `forRoot()` pattern from 999.11.1 Plan 10 | Rule 3 DI-scope fix is already proven |
| @Module composer for multi-sub-module | Custom DI helper | Standard `@Module({ imports: [SubA, SubB], exports: [SubA, SubB] })` | Standard NestJS idiom, matches foundation.PersistenceModule |

**Key insight:** This phase is 100% file re-location + import-path rewrites. Any code that looks like "re-implementation" is a planning error — revert and grep for the canonical pattern in `packages/foundation` or Phase 999.11.1 SUMMARY files.

## Composer Modules — Edge Cases

D-06 says "keep composer pattern везде". Interpretation across service categories:

### Rule (proposed recommendation, respecting D-06)

1. **Category with ≥2 sub-modules:** composer is a clear win (fewer root-level imports, scalable). Examples:
   - `gateway.outbound.grpc-clients/` — 5 upstreams (auth/sender/parser/audience/notifier) → `GrpcClientsModule` composer is worthwhile and already exists (see `apps/gateway/src/infrastructure/clients/grpc-clients.module.ts`).
   - `audience.outbound.persistence/` — 2 aggregates (recipient/group) → composer worthwhile.
2. **Category with exactly 1 sub-module:** D-06 says "keep composer везде" — the composer is a thin shell imposing a consistent idiom. Recommendation: **honour D-06 verbatim** — create the composer even for single-sub case. Rationale: (a) consistency across services simplifies planning (the root `{svc}.module.ts` always imports `SomethingModule` composer regardless of how many features live under it); (b) adding a second sub-module later is friction-free (add sub-module, add one line to composer — no change to root); (c) the cost is a 5-line `@Module({ imports: [X], exports: [X] })` file per category. Total cost across all 6 services ≈ 10–12 single-sub composers. This is negligible vs. the scaling benefit.

## Pitfalls & Non-obvious Gotchas

### Pitfall 1 — `git mv` vs. delete+recreate

**What goes wrong:** using `git rm` + `git add` (or plain `mv`) breaks git blame history.

**How to avoid:** always `git mv OLD NEW`. Git preserves rename detection.

**Warning sign:** `git log --follow NEW_PATH` shows only the commit from this phase (vs. full history).

### Pitfall 2 — Import-path rewrites: catch every consumer

**What goes wrong:** file moves but a stale `import './old/path'` somewhere compiles because TypeScript resolves through a barrel.

**How to avoid:** per commit, after `git mv`, run:
```bash
# Check for references to any path that no longer exists
rg -n "from ['\"](.*/infrastructure/(controllers|clients|config|throttle|storage|messaging|external)[^'\"]*)['\"]" apps/ --type ts
```
If the output lists ANY path that the commit was supposed to eliminate, the commit is incomplete.

**Warning sign:** `pnpm build` green but `pnpm lint` flags `no-restricted-imports` violations — means a compilation accidentally still resolves to the old layer path via a barrel re-export.

### Pitfall 3 — Absolute depth shifts when tokens stay at root

When a file moves into `infrastructure/outbound/http-clients/{vendor}/` but imports `{svc}.constants` (still at root `apps/{svc}/src/{svc}.constants.ts`), the relative depth changes:

- OLD path `infrastructure/clients/cloud-functions/cloudfn.module.ts` → `../../../sender.constants` (3 `..`).
- NEW path `infrastructure/outbound/http-clients/cloud-functions/cloudfn.module.ts` → `../../../../sender.constants` (4 `..`). **DIFFERENT.**

Also, when `{SVC}_CONFIG` moves INTO `bootstrap/config/`, files that previously imported `{SVC}_CONFIG` from root must be updated to import from `'../../../bootstrap/config/{svc}-config.constants'` — NOT from the root constants file anymore.

**How to avoid:** per-commit, after moves, grep for `{svc}.constants` in the relocated files and verify depth is correct:
```bash
for f in $(find apps -path '*/infrastructure/outbound/**' -name '*.module.ts' -newer /tmp/phase-start); do
  grep -H "from.*${SVC}.constants" "$f"
done
```
Eyeball each line; every stale path will stand out.

**Warning sign:** `pnpm build` fails with "Cannot find module '../../../sender.constants'".

### Pitfall 4 — Empty source dirs auto-untrack (git behaviour)

After `git mv`, the source directory is empty. `git status` shows it as untracked (because git doesn't track empty dirs), but a subsequent `find` still sees the dir on disk.

**How to avoid:** after all moves in a commit, run `rmdir apps/{svc}/src/infrastructure/{clients,controllers,config,throttle,storage,messaging,external}` (the specific dirs that are now empty). Use `rmdir` (not `rm -r`) to guarantee no surviving files.

**Warning sign:** `find apps/{svc}/src/infrastructure -type d -empty` returns matches after the commit.

### Pitfall 5 — `main.ts` provider registration referencing moved constants

`apps/{svc}/src/main.ts` imports `{Svc}EnvSchema` from `./infrastructure/config` (the old path). After D-10 moves the schema to `./infrastructure/bootstrap/config`, main.ts MUST update its import in the same commit.

**How to avoid:** the per-service commit must touch `main.ts` whenever `bootstrap/config/` is created.

**Warning sign:** commit passes `pnpm lint` (because main.ts wasn't linted? — no, it IS linted) and fails at runtime with "Cannot find module".

### Pitfall 6 — Barrel chicken-and-egg

Creating `inbound/grpc/index.ts` that re-exports a module whose file is imported elsewhere via the barrel → if the barrel is created BEFORE the target file exists, compilation breaks.

**How to avoid:** within a single commit the order is (1) `git mv` files, (2) create new module files that reference the moved files, (3) create barrels last — ordering inside a commit doesn't affect the git commit snapshot (all files are atomic per commit), but it affects the order of edits the planner describes per task. Encourage planner to instruct: "create barrels LAST in each task's edit list" for cognitive clarity.

### Pitfall 7 — Inline `THROTTLE_TIER` constants in throttle.module.ts

Gateway's current `throttle.module.ts` declares `const THROTTLE_TIER = {...}` inline. Per no-magic-values skill (and the D-07 refactor discipline) this should be hoisted into a sibling `throttle.constants.ts` when the module moves to `bootstrap/throttle/`. This is OPTIONAL from CONTEXT.md perspective (not mentioned in D-01..D-17) but consistent with existing patterns like `cloudfn-client.constants.ts`.
