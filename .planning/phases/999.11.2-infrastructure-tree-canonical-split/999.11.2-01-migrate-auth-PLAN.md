**Foundation PersistenceModule status (verified via `packages/foundation/src/external/persistence/persistence.module.ts`):**
- `PersistenceModule` is **NOT @Global()** — it's a regular `@Module({})` class with static `forRootAsync()` returning a dynamic module.
- `PersistenceModule.forRootAsync()` exports `[TerminusModule, DRIZZLE, PG_POOL, DATABASE_HEALTH]`.
- Consumers must explicitly import `PersistenceModule.forRootAsync()` — NestJS does NOT propagate a non-global dynamic module's exports transitively across sibling modules.

**Downstream consequences for this plan:**

1. `PgUserRepository` (verified via `pg-user.repository.ts`) injects `@Inject(DRIZZLE)`. When it moves into `UserModule`, UserModule MUST explicitly `imports: [PersistenceModule.forRootAsync()]` to make DRIZZLE visible, because UserModule is a standalone `@Module` class — it cannot rely on a sibling in the root composition to provide DRIZZLE unless that sibling is `@Global()`.

2. Auth's `HealthController` (verified) injects `@Inject(DATABASE_HEALTH)`. When it moves into `HealthModule`, HealthModule MUST explicitly `imports: [PersistenceModule.forRootAsync()]` to make DATABASE_HEALTH visible. (Alternative: the root `auth.module.ts` keeps importing `PersistenceModule.forRootAsync()` — but then `PersistenceModule.forRootAsync()` is imported TWICE — once at root, once in HealthModule. NestJS handles dynamic module re-importing by reference equality, but different `forRootAsync()` calls create DIFFERENT dynamic modules. Safest: import ONCE inside HealthModule, stop importing at root.)

3. Simpler alternative adopted by this plan: HealthModule imports `PersistenceModule.forRootAsync()`, UserModule imports `PersistenceModule.forRootAsync()`. Each dynamic module instance is independent (foundation's providers have `useFactory` based on config — each call yields the same Drizzle pool because `loadConfig` is cached, and Drizzle pool creation happens once per factory but the pool itself is ref-counted by pg). **CRITICAL validation:** Phase 999.11.1 research established that `PersistenceModule.forRootAsync()` can be imported by multiple modules in the same app without creating duplicate pools because the underlying `pg.Pool` is created in a single factory and the dynamic module is treated as a provider-set. However, to be strictly safe, we keep `PersistenceModule.forRootAsync()` at the root level ONLY (inside root `auth.module.ts`), and make `AppPersistenceModule` + `HealthModule` rely on root re-providing it. Actually that DOESN'T WORK for non-global modules. **Final decision (D-AUTH-01 for this plan):** Keep `PersistenceModule.forRootAsync()` in root `auth.module.ts` imports AND inside `UserModule` imports AND inside `HealthModule` imports. NestJS deduplicates by module class reference when they share the same dynamic provider set — verify at runtime via smoke test. If duplicate-pool issue surfaces, Plan 10 dual-mode smoke catches it.

**Conclusion (final planning decision for concrete actions below):**
- Task 4: `UserModule` declares `imports: [PersistenceModule.forRootAsync()]` (needed for `DRIZZLE` token to bind `PgUserRepository`).

Root imports only composers: `[AuthConfigModule.forRoot(), HealthModule, LoggingModule.forGrpcAsync('auth'), AppPersistenceModule, GrpcModule]`.
